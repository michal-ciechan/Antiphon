## D-1 (blocker) packed-refs.lock removal has no ownership or live-holder proof

- Where: src/Antiphon.SessionRunner/RunnerRepositoryMaintenance.cs, `ReleasePackedRefsLock`
  (called on the budget/shutdown kill path after `Kill(entireProcessTree: true)`).
- Failure: the method deletes any `<repo>/.git/packed-refs.lock` whose mtime is at or after
  `startedUtc - 1s`. Mtime only says "written during (or up to 1 s before) the pass", not
  "written by the gc tree". By design the pass does not block dispatcher, retention or park
  git calls that start during gc, and agents' own git in worktrees (which share this common
  .git) is not counted at all. Any of them that deletes a ref (retention `branch -D`,
  `fetch --prune`, `update-ref -d`; after `gc` every ref is packed, so every deletion
  takes packed-refs.lock) may hold the lock at the instant of the kill. On Linux (server2)
  `File.Delete` unlinks a lock that a live git holds. Then a second git can create a new
  lock with O_EXCL, and the first holder's `rename(packed-refs.lock, packed-refs)` moves
  the second writer's half-written lock into place: lost ref updates or a truncated
  packed-refs for the shared repository and all its worktrees. The existing witness
  `C1818_budget_kill_removes_a_stale_packed_refs_lock` shows the gap. Its "fresh" lock is
  written by test code in the start delegate, not by the child, and the code removes it.
  No test proves that a lock written during the pass by a process outside the gc tree
  survives.
- Why it blocks: before this change the worst case was a stale lock that fails ref
  deletions until someone removes it, which fails safe. After it, a narrow race can corrupt
  refs. The brief's danger-area (a) sets the bar at "only a lock that THIS pass wrote
  and no live git holds (age/ownership/pid proof)". Only the age proof is present, and
  its 1 s slack points the wrong way.
- Fix: remove the lock only with proof. Either (i) before the kill, record the lock's
  identity (inode/size/mtime) only if a process in the gc tree has it open (Linux:
  /proc/<pid>/fd of gc and its descendants). After the kill, delete only if the same file
  is still there unchanged and no other process holds it. Or (ii) fail safe: leave the
  lock, set the row reason to something like `packed_refs_lock_left` and log it for the
  operator. Add a red-first witness: a lock created during the pass by a process outside
  the gc tree, held open across the kill, must survive. Keep the "older lock is left"
  case. Fix the docs (session-runtime-invariants.md "removes a lock written during that
  pass") to match.
