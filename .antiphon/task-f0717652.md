## Brief items

1. **Keystroke delivered at most once.** A stale-observation result comes from only two places, and both happen before any byte reaches the backend.
   - (a) The pre-write checks at `src/Antiphon.SessionRunner/SessionRunnerRuntime.cs:1675-1693`.
   - (b) `Fence` at `:1697-1708`, which throws `DialogInputRefusedException`. It runs first under `WithScreenLock`. It runs again inside `WriteBackendAsync` under `_gate`, before `_inputRevision++`, before the input log and before the single `write()` call (`:4350-4368`).

   The input is written in one backend call, not in chunks. So once `write()` has started, `Fence` cannot fire again. A backend exception is not a `DialogInputRefusedException`: it sets `_terminalInputUncertain` and then propagates. The HTTP client maps it to `Unknown` (IOException). The phone-home client maps an error frame to `Unknown` or throws. Neither replays a request: each phone-home request gets a new GUID, and the client has no reconnect resend. So no path returns stale-observation after a partial write or after the write has begun.

   The worst case is zero duplicated bytes. The only extra side effect of a retry is a repeated `BeginDeliveryWrite`/`CaptureDeliveryEvidenceAsync` plus `qualification.Discard()`, which the refusal invalidates. That is evidence bookkeeping, not input.

   For the probe token plus Ctrl+U pair: the write callback is per input. A stale Ctrl+U re-sends only Ctrl+U, and test 1 pins `[token, KillLine]`.

   A transient stale observation is now absorbed within 3 attempts.
2. **Other outcomes behave as at base.**
   - Written returns.
   - Unknown raises IOException with the same message, through the same `RequireWritten`.
   - Every other refusal raises `ProviderDialogInputRefusedException(reason)`.
   - No new or broader catch was added.
   - When the attempts run out, the code raises the same type with reason `stale-observation`, through `RequireWritten`.
   - The guard throw uses the same type and the same reason.
   - `Request()` refusals (ModalBlocked/ObservationUnknown for intent None) still happen before the send.
3. **Deadline.** The snapshot, the send and `Task.Delay(50 ms, ct)` all take `ct`. On the readiness path `ct` is the `bounded` probe-budget token from `ClaudeStartupReadiness`. OperationCanceledException propagates; nothing swallows it. The loop is capped at 3 attempts.
4. **Snapshot-change guard.** It is correct and it is needed:
   - For intent None, the runner checks only that the dialog is Clear, not the key. A trust or effort key re-sent after the dialog has gone would be typed into the composer. The guard prevents that, and mutant M4 is red.
   - For dialog intents, the runner re-validates the key on the live screen at the fence (`ClaudeDialogActions.AllowsTrustKey`/`AllowsEffortKey`). A re-send over a changed dialog would therefore still be refused as ModalBlocked.
   - None → dialog transitions are refused by the guard, or by the runner as ModalBlocked.

   I found no case where a re-send is allowed over a changed screen. A wrong refusal only fails the launch, as it did at base.
5. **Callers.** Only `RunnerClaudeAdapter` uses this method: the early trust gate (`:176`) and readiness (`:196`). The in-process `Pty/ClaudeAdapter.cs:111` has its own `WriteStartupAsync` and is unchanged. Codex and Grok adapters do not call it.
