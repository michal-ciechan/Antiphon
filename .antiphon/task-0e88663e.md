## 3. Defects

**D-1 — dead-host recovery kill runs on ordinary reads and repeats every second in the observer loop.**
Where: `src/Antiphon.SessionRunner/SessionRunnerRuntime.cs:4550-4553` (`_client is null && RunnerSealPresent -> ReleaseDeadHost`) and `:4563-4568` (pipe-failure catch keyed on `runnerSeal`), reached from `ReadCustodyAsync(seal:false)` (`:499`) and from `ObserveCustodyThenShutdownAsync` (`:4586-4604`). That loop continues on every reason except `custody_observer_unavailable`.
Failure (probe-proved on the tip): I added two temporary methods to `RunnerCustodyReleaseTests`, using `ReleaseWorld.Open(adopt:true)` (session with no client, as `CreateAdoptedExited` produces after a runner restart) and a prior `runner-seal.json`, then removed them. (a) `ReadCustodyAsync(seal:false)` -> `PROBE ordinary kills=1 reason=released_unknown`. (b) `StartCustodyObserverForTests` with a descendant remaining -> `PROBE loop kills=4 completed=False` in 3.5 s. So an ordinary GET after a runner restart, or the runner's own 1 s poll, calls the sudo kill helper on the recorded container, without bound.
Why: the plan (P-3 Release ownership) says "Require an explicitly releasing API call AND … runner-seal.json. **A prior seal record alone does not authorize recovery from an ordinary read** … Ordinary reads, adoption and elapsed time never invoke this recovery kill." The disposition table's host-crashed row says "One bounded helper/observation attempt per request". The loop turns recovery into a periodic, age-driven releaser.
Fix: pass explicit release intent (the `seal` argument of `ReadCustodyAsync`) into `CollectCustodyAsync`. Call `ReleaseDeadHost` only for an explicit seal:true request, never because a seal record exists. End the observer loop, with no kill, on any dead-host/Unknown result. Add a portable witness: ordinary read plus prior seal plus adopted no-client session gives zero kills, and the loop with a dead host and a prior seal gives zero kills.

**D-2 — on the Linux launch-failure path, a released-zero host never re-arms linger, so it is immortal.**
Where: `src/Antiphon.PtyHost/HostSession.cs:170-177` (launch catch -> `StartLingerExpiry`, withheld by `ShouldWithholdLinger` because native intent is recorded). The only re-arm sites are `:444/:450` inside `ObserveCustodyUntilFinalAsync`, and that loop starts only from `ObserveExitAsync` (`:414`), which runs only after a successful launch (`:225`). `GetCustodyAsync(seal:true)` -> `HostCustodyJournal.ReleaseFailedLinuxAsync` writes `linux-release-disposition.json` but arms nothing.
Failure: a fast root exit makes `RecordTracking`'s `Process.GetProcessById` throw (or the `tracking.json` write fails) after `RecordStartIntent`. That is exactly the case the plan names. Terminal cleanup's explicit release kills the container and writes the released-zero disposition, and the runner stops polling on that disposition. The PtyHost process then lives forever with no linger, no Shutdown and no owner. That is a leaked process, which the "release leaves it killed, pooled or owned" invariant forbids.
Why: P-3 (`StartLingerExpiry`) says "withhold … in both exit and launch-failure paths … An Unknown released-zero host starts a fresh existing linger". The disposition table row says "Host linger/disposal | Fresh existing TTL <=24 hours after durable release disposition".
Fix: after the explicit-seal observation in `GetCustodyAsync`, or in `ReleaseFailedLinuxAsync`, arm linger whenever `HasReleaseDisposition()` holds, whatever path the host took. Cover it with a real fault-injected witness (D-3).

**D-3 — two native witnesses are stubs: no fault and no tree removal, and they cannot go red for their defects.**
Where: `tests/Antiphon.PtyHost.Tests/LinuxCgroupCustodyTests.cs:220-235` (`C1614_Failed_tracking_explicit_release_terminates_without_receipt`) and `:204-217` (`C1614_Missing_tree_never_finalizes_naturally`). The author's report lists both as "Known weak bodies".
Failure: Failed_tracking launches a normal held payload with no fault after native intent and plants no `runner-seal.json`. On a qualified image the explicit seal writes a real receipt, so the test fails even when production is right. It cannot exercise the launch-failure arm, so it would never catch D-2. It also asserts `ExitRequested.IsCompleted`, which the plan forbids ("Do not count ExitRequested alone … await actual staged host exit"). Missing_tree never removes the tree. Its "echo" root either finalizes to a real receipt (test red with production correct) or reaches Unknown because placement was not recorded (green for the wrong reason). Neither outcome tests the missing-tree rule.
Why: the plan's witness obligations call for a deterministic `tracking.json` persistence refusal after native intent, with actual host exit, and a provisioning-fixture `rmdir` of the owned empty tree before the gated read. NP-34 would credit these witnesses.
Fix: implement both arms as the plan specifies (deterministic `tracking.json` fault plus runner seal plus wait for host process exit; gated read plus nonrecursive removal of the owned tree). Commit them red-first at a SHA without the fix (D-2) before NP-34 is commissioned.
