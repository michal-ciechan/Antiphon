## Design verdict

The design is now correct for exactly-once delivery and no loss, within the line model the base already had. The evidence is the walk below, run against `AgentMentionRouter.cs` at the tip.

Two structural facts close the earlier rounds' root causes:

- **The scanner yields at most one mention per line.** `MentionScanner` uses `(?<message>[^\r\n]+)`, which takes the rest of the line. In `@helper do x @helper do y` the second `@helper` is part of the first mention's message. A line therefore cannot hold "the same target twice", or a later different target, as separate mentions.
- **`Version` is now a `long` from one router-wide `Interlocked.Increment`.** It is used in both schedule (`:233`) and claim (`:327`). A recreated state can never reuse an older debounce's generation. Wrap would take 2^63 increments, which is not practical. The `int` concern in the brief does not apply.

### Sequence walk at the tip

| Scenario | Result |
|---|---|
| Split mention (`@helper please` + ` inspect it\n` within 300 ms) | The claim bumps the generation, so the first debounce is stale or finds the state gone. Queued once. |
| Partial delivered by the debounce, then the continuation | The pre-filter and the `already` snapshot skip `lines[0]`. Delivered once, as the partial text (base behaviour). |
| Partial, then ` it\n@helper then run lint\n` (round-4 D-1) | `lines[0]` is skipped. Line 2 is in `later` and always queues. Enqueued twice: 2 bodies, 1 duplicate skip. |
| Continuation with the same target twice on one line | It is one mention (see the scanner), so it is skipped as a whole when the debounce routed that target. That matches base `34a7d0b8`/`68565db92`, which skipped every `lines[0]` mention whose key was routed. The original design dedupes the continuation line by target. The text added after the partial is never delivered (A-1). |
| Continuation with a different target | Routes when that target is the line's first mention. A different target after a first mention is absorbed into that mention's message (unchanged from base). |
| Completed line with no pending state | `ClaimCompletedMentions` returns `continuation`+`later` unfiltered. No keys and no generation are needed, because no debounce can be outstanding without a state. |
| Two chunks completing quickly | Each producer serialises observes per session (see A-4). The second chunk sees the first chunk's stored remainder. |

| Debounce fires between the pre-filter and the claim | The claim's snapshot sees the key and skips. Delivered once. |
| Debounce fires during the liveness read | The generation is already bumped (stale), or `Settle` has removed or recreated the state (gone or newer generation). |
| Read cancelled, throws, or returns not-live | Cancelled: `Settle(null)` once, then rethrow. Other throw: warning logged, then `Settle(null)`. Not-live: route falls back to the status filter (base behaviour). Each case enqueues once. |

| Stale debounce with a recreated state (round-4 A-1) | It now records `DebounceStale` (witness 2). |

## Advisories (all unchanged from base; none blocks)

- **A-1, the line model:** a debounce-delivered partial suppresses the entire continuation line, including text added after the pause and any `@other` absorbed into that line's message. Base did the same. Changing it would need a message-level key, not a target-only key.
- **A-2, channel full on the debounce path:**
  1. The debounce adds the key before `TryWrite`.
  2. If the channel is full, the command is dropped (logged), but the continuation is still skipped as a duplicate.
  3. So that mention is lost, with a log line.

  Base did the same.
- **A-3, memory:** `_pendingText` and `_pendingStates` entries are never removed for a session that ends mid-partial. Each is bounded at 4096 chars per session id. There is no disconnect hook, as in base.
- **A-4, the observe window:** since round 2, the observe spans a database read between the `_pendingText` append and the stored remainder. Two concurrent observers for one session would route a line twice. All production producers serialise per session:
  - `PhoneHomeEventScheduler` allows one active observer per session.
  - `StartPump` throws until the previous observer group has joined.
  - The desktop pump awaits each event.
  - A held-event deadline cancels the read, which settles and returns.

  The residual case: an Npgsql read that ignores cancellation past `HeldEventDeliveryTimeoutSeconds`, which makes the pump abandon it. Also, the test-only `Register` adapter path fires `ObserveOutputAsync` unawaited. Not reachable in normal operation, so no action is needed. Worth a note if the pump contract ever changes.
