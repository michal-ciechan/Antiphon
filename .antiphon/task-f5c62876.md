## Defects

**D-1: `Blocked` hides a running session from occupancy and from the CARD-0079 selector (plan D-1 "It continues to own its seat, workspace reservation and concurrency occupancy"; S2 file list).**
The plan claims the held task keeps its concurrency occupancy, but the code counts in-flight work
as Dispatched/Working only:
- `DispatchConcurrencyPolicy.cs:364-368`: `IsOpen` = Queued/Dispatched/Working and `IsParallel`
  = Dispatched/Working. These drive the stage and absolute 409 caps.
- `AgentTaskDispatcher.cs:510-516`: the local (desktop) process-cap `active` count is
  Dispatched/Working.
- `AgentTaskPipelineStatusService.cs:182-188`: `fleetInFlight`/`inFlightRows`, and with them
  `localInFlight`, are Dispatched/Working. This is the route orchestrators read for remaining
  slots.
- `CheckCompactionContinuationService.cs:619/653`: the CARD-0079 Check continuation selects
  Dispatched/Working. A held Check task (the plan says "all roles"; Check falls back to
  `DefaultTimeoutMinutes`, `TaskDeadlinePolicy.cs:129`) drops out of the one sanctioned
  automatic Working-stop path.

None of these files is in S2's ownership list. The source has 72 files that reference
`AgentTaskStatus.Working`, and the plan's shared predicate names about seven consumers.

*Scenario:* Code is at its cap of 4. One Code task hits 240 min while running tests and becomes
Blocked. The pipeline route now reports remaining=1, and the standing keep-at-depth rule
dispatches a fifth Code task. The held session is still building, so five Code sessions run
against a cap of four. On the desktop, the local MaxConcurrentTasks admits one extra process. A
hold that is never answered keeps that overshoot indefinitely (parking is off).

*Fix (preferred):* keep `Status=Working` and represent the hold as the attempt-scoped typed
fields the plan already adds (episode, HeldAt, ack). Show it through attention, the parent note
and the typed Reply shape. Accept the typed ceiling Reply on a Working task with a current
episode. Every existing Working consumer then stays correct, and the "do not widen Blocked"
census disappears. *Alternative:* keep Blocked, but commit an exhaustive census of
Dispatched/Working selectors with a disposition for each site. The census must at least cover
concurrency, the local cap, pipeline in-flight, CARD-0079, TaskProgressPolicy and attention. Add
V-rows proving that a held task still counts toward stage, absolute and local-host occupancy and
stays in the CARD-0079 population.

**D-2: `Continue` is an unbounded, permanent waiver, and "phase supervision still catches real hangs" is false for tails that only the ceiling supervises (plan D-1 "Continue … suppressing further role-ceiling holds for this attempt"; D-4 "At cap, Continue is still an explicit decision").**
`TaskDeadlinePolicy.ClassifyPhase` (`TaskDeadlinePolicy.cs:280-296`) arms a phase clock only for
UserPrompt/ToolResult/Thinking/AssistantText (model wait) and ToolCall (local tool). Every other
last row maps to `(Ceiling, Zero)`. Its doc comment says "an unrecognised tail gets the
wall-clock ceiling and nothing tighter", and the existing test
`a_compaction_tail_does_not_read_as_a_stalled_model_call` (`AgentTaskOverdueDeadlineTests.cs:207`)
pins that behaviour. Meanwhile `TranscriptWorkingStateQuery` still reports Working after an
`(auto)` CompactBoundary, a TurnTitle or a Queue* row, because these are not end predicates.

*Scenario:* a Code session auto-compacts at 200 min and the provider never continues. That is
the CARD-0079 shape, which has no automatic handling outside Check seats. At 240 the hold asks
the question and says "Its session is still working". The orchestrator answers Continue.
Nothing ever supervises that attempt again: seat, worktree and occupancy are held forever (no
parking deadline), and the hang is hidden by an explicit waiver. Extending to the 720 cap and
then answering Continue gives the same result. A queued Refine that lands as the last row of a
hung session behaves the same way.

*Fix:* make Continue re-arm a later hold rather than suppress all future holds, for example one
more role-ceiling interval, bounded by the 720 absolute cap. Past the cap the only options are
an explicit operator Continue or Cancel. The question text and DTO must state the last row
kind, its age, and whether any phase clock currently applies ("no phase deadline covers this
tail"), so the decider knows the ceiling is the only supervision left. Add a V-row with a
compaction or queue tail that is held, continued, and asked again.

**D-3: Deploy slicing changes operator-authorized drain policy without a decision, and the "delegated context" predicate is unnamed (plan D-4: "No wait expiry authorizes stopping a seat …"; S4 edits `docs/docker-stack.md`).**
`docs/docker-stack.md:126` (step 5) says that at the 240-minute `OldRunnerStillBusy` cap "the
operator explicitly authorizes stopping the remaining server2 sessions" through `runner-slots.ps1
release`. The plan's replacement procedure says an overall-deadline expiry authorizes no seat
stop and the delegate reports Blocked. It does not say whether step 5's operator authorization
survives the S4 docs edit. That is a silent revocation of an operator policy, which is the
operator's choice and not this card's.

The plan also says "while running in a delegated context, reject WaitIdleMinutes > 60 or
Phase=all" without naming the predicate. The script already keys on `ANTIPHON_TASK_TOKEN`
(`deploy-server2.ps1:35`). The predicate must be named and tested, including the case of an
operator shell launched from inside a delegate, which inherits the variable.

Finally, the 30-minute default slice exceeds a Claude Code delegate's 10-minute foreground Bash
cap. Under delegate-basics' foreground rule, the tool would end a 30-minute call mid-wait. Either
bound the delegated slice below the agent's foreground limit, or prove the script is safe when
interrupted (drain retained, no partial mutation) and cite that proof.

*Fix:* state explicitly that step 5/8's four-hour cap and its operator stop authority are kept
verbatim, with the sliced waits mapping onto that same absolute deadline, or put the change to
the operator as `next: decide`. Name the env predicate and add it to V-10. Size the default
delegated slice to the agent's tool limit.

**D-4: A Failed task's complete report still never reaches the caller (plan D-2 wire text "return a complete report … evidence for triage"; D-5).**
The D-2 notice tells a failed live session to produce a complete report. But the selectors
accept Dispatched/Working only, Reply on a Failed task is refused, and no producer forwards that
report to the parent. This is exactly how the 8edda999 rollout lost its report.

Under the plan, a Deploy can still be Failed while alive by the 20-minute model wait (or by an
unsafe-rm refusal or another non-ceiling writer). Its rollout state report then lands only in a
transcript that nobody is told to read.

*Fix:* forwarding is not correction. When the same attempt and generation of a Failed task emits
a complete marked report, enqueue one triage note to the parent. The note quotes or links the
report, makes clear the outcome is unchanged, carries `next=decide`, and lists D-5's superseder
facts. Witness it with a C1161-shaped eligible/busy/crash method. If the plan deliberately
declines this, it must say so and give the caller the exact `delegate.ps1` command that surfaces
a Failed task's post-failure report. Either way, address the Deploy-report case by name.

**D-5: The regression scope omits the affected existing classes (plan "Ordinary verification roster"; Cost "No broad Unit/full-suite rerun is authorized").**
The plan changes `TryFailOverdueAsync`'s disposition, every `FailAndNotifyAsync` save (the D-2
notice "in the same transaction as the failure event"), reply/runtime/save-fence selectors, and
the janitor's TTL and cap arms. Yet it runs one method of `AgentTaskOverdueDeadlineTests` (about
40 methods; several pin the shape of the Failed save, for example
`an_expired_hold_writes_the_abandonment_in_the_same_save_as_the_failed_status` at :796), two of
`TaskDeadlinePolicyTests`, and one changed janitor method.

The cap-arm janitor tests are not run, although D-10 changes cap semantics:
`the_per_directory_cap_skips_a_mid_turn_agent` (:928),
`the_janitor_enforces_the_per_directory_cap_oldest_first` (:1008) and
`the_janitor_does_not_retire_a_warm_agent_whose_session_is_mid_turn` (:871). Neither are
`BootStallDetectionTests`, `AgentTaskReplyC547HoldTests`, the
`DelegationDispatchRecoveryBoundaryTests.*` partials or the
`SessionRuntimeActionRecoveryTests`/coordinator classes. The verification profile requires
"every named full affected integration class". As written, a regression would surface only at
nightly, and the 51-minute estimate leaves out that cost.

*Fix:* name the affected full classes (at least `AgentTaskOverdueDeadlineTests`,
`AgentTaskPoolTests`, `TaskDeadlinePolicyTests`, `BootStallDetectionTests`,
`AgentTaskReplyC547HoldTests`, `DelegationDispatchRecoveryBoundaryTests`,
`SessionRuntimeActionRecoveryTests`, plus whatever D-1's census touches) as green-group rows
with exact counts. Re-cost the plan, and state how the Final profile's Unit-lane obligation is
met (sharded, per CARD-1573) rather than declared unauthorized.

## Answers to the brief's questions

1. **Hold coverage.** The hold applies to a task in Dispatched/Working whose session is Working
   by transcript activity, for all roles. Boot stays detection-only. On ordering, the plan
   *correctly* fixes today's max-fraction selection: a breached phase must win over a larger
   ceiling fraction (`TaskDeadlinePolicy.cs:255`). A held task with a model-wait or tool tail is
   still failed by its phase deadline. A held task with a compaction, queue or title tail is not
   (D-2).
   - Extend is bounded at 720 absolute. Continue is unbounded (D-2).
   - Cancel stops the open task (verified in round 1).
   - Keeping the seat is acceptable for a Working session only if the session still counts as
     occupancy (D-1).
   - The parent hold note has real-producer eligible, busy and post-commit crash arms with
     complete-UserPrompt plus decoy assertions (V-9). That is adequate.
2. **Deploy.** A Deploy that is Working at 240 becomes Blocked and answerable, not Failed. Hold
   then Extend is enough for the role ceiling, and declaring `-CeilingMinutes` for a planned
   long rollout is optional. A single 240- or 480-minute ToolCall would still trip the 90-minute
   tool deadline, so slicing is required (D-3). A Deploy failed by a phase deadline still loses
   its report (D-4).
3. **Removal safety.** The remaining Failed+live paths are *told* through the durable notice
   (the census table is good), but the resulting report is stranded (D-4). Successor fencing:
   Retry and the attempt fence stop a double run, and a held task's settlement forces
   `next=decide` when a same-card, same-role successor exists. That is adequate apart from A-1.
4. **Pooled-stall detection.** It is sound: report-only, durable, deduplicated, and with no new
   kill. Removing the time-based janitor kill of a Working session brings the code into line
   with the stall invariant (A-2).
5. **Checkpoints.** The import succeeds with the counts verified above. Classification, roster
   and limiter declarations are complete. Every estimate is a whole number of minutes. The
   regression scope is short (D-5).
6. **Targets.** Master plus reviewed rc ports, sequenced after CARD-1604 on master and after
   CARD-1615 for S4. This is sound.
