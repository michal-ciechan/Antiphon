## D-1 (defect, new regression): the claim drops a second same-target mention in one delta

- **Where:** `server/Application/Services/AgentMentionRouter.cs:283-295` (`ClaimCompletedMentions`). The key is `PendingRouteKey(mention) => mention.Target` (line 394).
- **Failure:**
  - The claim does `RoutedKeys.Add` for each ready mention in turn. That makes it a dedupe by target *within* the completed batch, not only against what the debounce already queued.
  - Any pending state for the source triggers it. `SchedulePendingMentions` creates a state for any non-whitespace remainder, with or without a mention. A previous chunk ending mid-line is enough, and `ObserveOutputAsync` also splits one burst at `SignalRMaxChunkChars`.
  - Scenario: chunk `Status: work`, then chunk `ing\n@helper run the tests\n@helper then run lint\n`. The router queues only `run the tests`. `then run lint` is recorded as `command-skipped-duplicate` and never routed.
  - Round 2 enqueued every `ready` mention, so both were routed.
- **Witness:**
  - Scratch `R77d5_two_same_target_lines_after_partial`. It builds the router directly with diagnostics, plus a `FakeTimeProvider`.
  - `(True)` (partial first): red at `261e35c82`, `CommandEnqueued should be 2 but was 1`. Trail: `pending-scheduled version=1` -> `command-skipped-duplicate target=helper` -> one `command-enqueued`.
  - `(False)` control (same text in one delta): green.
  - Both cases are green at `1423c937e`.
- **Why it matters:** this is a silent loss of a legitimate mention to the recipient, on ordinary chunked output. Brief priority (1) is no LOSS.
- **Fix (for Code):** claim only against keys the debounce already queued. Inside the lock, take the keys that were in `RoutedKeys` before this claim. Skip only a mention whose target was already present. Add the rest to `RoutedKeys` without skipping repeats within the batch. Keep the `Version++`. Add a committed witness for the D-1 scenario that is red at `261e35c82`.

## D-2 (defect, new regression): a cancelled liveness read keeps the claim, so nothing ever delivers the mention

- **Where:**
  - `AgentMentionRouter.cs:94` (the claim) together with `:103-106` (the OCE rethrow skips the enqueue).
  - The source state is left in `_pendingStates` with the claimed key and a bumped `Version`.
  - `_pendingText` still holds the completed line, because line 121 is never reached.
- **Failure:**
  1. Pending `@helper please inspect`, then ` it\n` arrives. The claim adds `helper` and bumps the version, then `capture` is cancelled.
  2. The debounce goes stale (`version=1 current=2`), so it delivers nothing.
  3. The next delta re-parses the retained `@helper please inspect it\n`. `PendingRouteExists(helper)` is now true, so that delta skips it as well.
  4. Net: zero route commands.
  - At round 2 the same path ended with the debounce queuing the partial once, which is still a delivery. In the no-state case, the next delta re-routes the retained line.
- **Reachability:** this is not shutdown-only. The token is the phone-home pump's `stop.Token`, linked by `StartPump` (`server/Infrastructure/Agents/SessionRunner/PhoneHomeRecoveryPump.cs:302-311`). It is cancelled when a runner's live connection is replaced or its socket closes (`:131-132`). The singleton router and the source session both survive that. Review 7e117ffd's A-6 had called this shutdown-only; that was wrong for this pump.
- **Witness:**
  - Scratch `R77d5_cancelled_read_after_claim_then_next_delta`.
  - Red at `261e35c82`: `CommandEnqueued should be >= 1 but was 0`. Trail: `debounce-stale version=1 current=2` -> `command-skipped-duplicate target=helper` -> `pending-cleared`.
  - Green at `1423c937e`.
- **Fix (for Code):** on the OCE path, do not leave a claim with no command behind it. Either:
  - enqueue the claimed mentions with `observed: null` before rethrowing. This matches the "failed read still delivers" rule, and the status filter still applies. Or:
  - release the claim under `state.Gate` before rethrowing: remove the keys this call added, and leave the version bumped only if the full line is re-routable.

  Add a committed witness for the D-2 scenario that is red at `261e35c82`.

## Checked and found sound

- **Debounce vs claim, both orders:**
  - The debounce holds `state.Gate` from its second version check through its enqueue.
  - If the claim runs first, the version bump makes the debounce stale at either lock.
  - If the debounce runs first, its `RoutedKeys.Add` makes the claim skip the full line. The truncated text is delivered once, which is the pre-existing accepted shape.
  - No lock is held across an await or IO. `EnqueueCommand` is a non-blocking `TryWrite`.
- **Throwing or not-live read:** the claim is still enqueued with a null or not-live stamp, and the route then uses the Starting/Running filter. This does not fail open.
- **Enqueue failure after the claim:** `TryWrite` never throws. A full or completed channel logs `CommandDropped`; this is pre-existing.
- **Serialization:** production callers await `ObserveOutputAsync` per event: `SessionRunnerEventPump.cs:416` and `PhoneHomeRecoveryPump.cs:434`. Two completed lines in quick succession are therefore serialized, and the line 115-116 `TryRemove` after the await removes the claimed state. Only the test-adapter `Register` path fires observes concurrently.
- **Round 2 properties:** unchanged. These are the observe-time stamp, the stale-live generation and card/agent match, the detached flush, and the held-transcript witness (green in the class run below).
- **Original debounce purpose:** with no newline the path is unchanged, so an unfinished line is still delivered once after 300 ms. `Channel_mention_split_across_pty_chunks...` is green.
- **Tests:**
  - The debounce runs on the internal `Clock` seam (`FakeTimeProvider`). Production keeps `TimeProvider.System`, and the seam is not resolved from DI.
  - The witnesses hold the read with a TCS, advance the clock until the debounce resolves, and assert the `CommandEnqueued` count plus the recipient rows.
