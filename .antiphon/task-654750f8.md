## Defects

### D-1: the Hosts page and /api/hosts/stats still say `stale` for a retired runner
- **Where:** server/Infrastructure/Agents/SessionRunner/HostStatsPollService.cs:146 (`DescribeAsync`).
- **Failure:** server2-temp is retired and offline. GET /api/hosts/stats returns `state: offline, reason: stale`, and the HostCard (client/src/features/hosts/HostCard.tsx:33) shows `stale`. The probe reproduced this (`reason=stale`).
- **Why:**
  - The card says to surface retired/draining "in the session-runners catalogue unavailableReason/DTO **and the UI** instead of 'stale'". The Hosts page is the only UI that shows a runner's reason. RunnerDefaultsSection shows only `offline`.
  - The brief's claim that "/api/hosts/stats copies this reason" is wrong. HostStatsPollService builds its own SessionRunnerCatalogueEntryDto from the descriptor (`descriptor?.Stale == true ? "stale" : "unavailable"`) and never reads DrainState. HostStatsCache.cs:96 copies that reason, not SessionRunnerCatalogue.Row's.
  - HostStatsCacheTests (7) feed hand-built rows into Project, so they cannot witness this path.
- **Fix:**
  - Share one reason function between SessionRunnerCatalogue.Row and HostStatsPollService.DescribeAsync. Its precedence is retired, then draining, then stale/unavailable for ineligible runners. Feed it `_directory.DrainState(id)`, the ISessionRunnerDirectory default member.
  - Add a HostStatsPollServiceTests witness: a configured runner with no peer, ApplyState retired, then TickOnceAsync. Assert the cache row has reason `retired`, and add a draining case. It must be red at 69045e335.
  - Owner: Code task 359d84c5.

## Advisories
- **A-1:** RunnerAlarmCoordinator.cs:73 (ResolveAsync, :240-243) is now reachable in production. When a raised runner is retired or drained, every notified caller gets "[runner X recovered] ... is dispatch-eligible again ... Queued work bound to it dispatches on the next tick". That text is false for a retired runner. The text predates this branch (CARD-0726), but this is the first wiring that reaches it. The open-alarm witness has no notified caller, so it cannot see this. Suggest a "no longer alarmed: <reason>" variant.
- **A-2:** Draining has no bound. A runner left draining is excluded forever. That covers a drain without retireWhenIdle that was never cleared, or a retire that never completes. If it then goes down, it never raises, and callers with live Working sessions on it (a drain keeps sessions running) get no outage note. CARD-0726 D-5 intends this, but nothing else alarms on it. Consider alarming a draining runner that still has live sessions or pinned open tasks, or one that has been draining past a bound.
- **A-3:** docs/ops-http.md:143 still says `unavailableReason` is `draining` only when the runner is eligible and draining. It should add retired/draining for ineligible rows.

## Verified sound
- `Excluded` returns null for: no configured slot, an empty id, a slot whose State was never loaded, and a cleared state (Draining false, RetiredAt null). The probe and the M3 kill confirm this.
- DrainState is never cleared once applied, so a transient miss cannot silence a runner. RunnerStateLoader (Program.cs:952) starts before RunnerAlarmHostedService (:954). A failed read throws at startup instead of silently excluding.
- An open alarm resolves on the next evaluation. The episode is removed, so AttentionService.Alarms drops the item. Each later tick takes the excluded early return, so there is no re-raise and no flapping.
- Catalogue eligibility is unchanged:
  - `available`, `dispatchEligible` and `acceptingNewWork` still come from the descriptor or `eligible && !draining && !retired`.
  - `retired` appears only when the runner is not eligible. An eligible runner gets `draining` or null.
  - No script, tool or client code compares the catalogue `unavailableReason` to `stale`.
  - deploy-server2.ps1 gates read `/api/session-runners/{id}/status`, which this branch leaves unchanged and which a witness covers.
