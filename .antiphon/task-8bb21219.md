"A full route queue now refuses the new command" is a product change in `AgentMentionRouter`. `Wait` mode plus `TryWrite` makes `TryWrite` return false at 1024, which logs `CommandDropped`. Before, the oldest command was discarded silently. Both behaviours lose one mention at the cap, so this one is acceptable and no worse. It is new production behaviour, though: at the cap, the newest mention is dropped instead of the oldest.

## 2. Root cause: a real product race, and the fix reaches production

Yes, it was a production loss. Before the fix, the interleaving on any runner was:

1. The output chunk completes the `@fake hello` line.
2. `ObserveDelta` enqueues the route command and returns.
3. The same session's exit event is observed next, and `CloseSessionOnExitAsync` commits `Stopped`.
4. The router worker reaches `RouteMentionAsync`, which filters the source by `SourceStatuses` (Starting/Running), gets no match, and returns `source-missing`.

So a session that prints a mention and exits immediately lost the mention in production. The observer now awaits the insert. Both production consumers use it: `SessionRunnerEventPump.DispatchEventAsync` and `PhoneHomeRecoveryPump.ObserveEventAsync`. The fix is therefore not test-only.

Residual (pre-existing, advisory): any `Stopped` writer outside the per-session observer order still races the route the same way, for example an operator stop or a reconciliation close. The author notes that output replayed after stop does not route.

## D-1 (defect): the observer's wait can stall the whole event stream

Where: `server/Application/Services/AgentSessionRuntime.cs:146` awaits `ObserveAndRouteAsync`. That task completes only when the router worker reaches each command. `AgentMentionRouter.ProcessAsync` (around line 218) is one serial `ReadAllAsync` loop, and each command runs `RouteMentionAsync` to the end, including `FlushIfIdleAsync`. `FlushIfIdleAsync` goes through `DeliverNextLockedAsync` and `DeliverAsync` to `WaitForTranscriptConfirmAsync`. On the observable branch, that polls the database for the target's UserPrompt record for up to `TranscriptConfirmTimeoutSeconds` (default 30). Those records are written by `ObserveTranscriptAsync`, which is fed by the same event pump.

Failure: on the desktop runner, `SessionRunnerEventPump` (registered unconditionally, `server/Program.cs:941`) consumes events for all sessions one at a time (`SessionRunnerEventPump.cs:53-73`). The interleaving:

1. Session S prints `@T one\n@U two\n`, in one chunk or in consecutive chunks.
2. The observer enqueues cmd1 (to T) and cmd2 (to U), then awaits `WhenAll`.
3. The worker inserts cmd1. Durable1 completes, but cmd2 is still pending.
4. The worker runs `FlushIfIdleAsync(T)`: it types into idle T and polls for T's UserPrompt.
5. T's transcript event is next on the same stream. The pump is still inside S's `ObserveOutputAsync`, waiting for Durable2, which completes only after cmd1's flush returns.
6. The flush waits the full 30 s and reaches an unconfirmed verdict. `HandleDeliveryFailureAsync` then treats a delivered prompt as failed, which risks a re-entry or duplicate. All events for every session on that runner, including exits, transcripts and output, stall for those 30 s.

A single mention while the worker is still flushing another session's mention has the same shape. The author's comment ("Release the source observer before flush…") covers only the observer's own command, not commands queued behind another flush.

On phone-home (`PhoneHomeEventScheduler`, 4 shared workers), each such observer holds a worker for up to 30 s. With four, T's transcript is blocked the same way.

There is also no cancellation: `ObserveAndRouteAsync` ignores the pump's `ct`. On `Dispose`, commands still in the channel never complete `Durable`, so an awaiting observer hangs until host stop.

Why: it trades a rare lost mention for a 30 s stall of the whole stream and a false delivery-failure verdict. That is a new production regression on the delivery path. No test covers a second command queued behind a flushing one, or the non-phone-home pump.

Fix (for Code): do not make observation wait on the serial worker's flush. Preferred: record at observe time that the line completed while the source was live, for example by passing the observed source status or generation in the command, and let `RouteMentionAsync` accept that source even if it is `Stopped` by the time the route reads it. Then `ObserveDelta` stays fire-and-forget. Alternatives:
- Move publish/flush off the serial worker, so `Durable` completes in queue order without waiting on another command's delivery.
- Bound the observer's wait with `ct` and a short timeout, and complete pending `Durable` TCSs on dispose.

Add a witness: two mention lines (or two sessions) with the first target's flush held, asserting the second observation and an unrelated transcript event are not blocked.
