## D-1 ReviewRoundGuard throws on a non-ASCII digit, and the throw fails Review creation

- Where: server/Application/Services/ReviewRoundGuard.cs:20-25 (`(\d{1,4})` then `int.Parse`), called with no
  catch from server/Application/Services/AgentTaskService.cs:1309-1311.
- Failure: .NET `\d` matches any Unicode decimal digit (Nd) but `int.Parse` takes only ASCII 0-9. A brief line
  `round: ４ of 3` (fullwidth, U+FF14) or `round: ٤` (Arabic-Indic, U+0664) matches the regex, and `int.Parse`
  throws `FormatException`. CreateAsync awaits the guard directly, so the exception aborts the Review create.
  Proven: a temporary probe `Should.NotThrow(() => ReviewRoundGuard.Evaluate("CARD-0001", "round: ４ of 3", []))`
  was red with `System.FormatException` (same build as the mutants below; probe removed afterwards).
- Why: the brief and the card require that the guard never refuses or fails a Review create. A throw is the worst
  failure mode: a warning-only feature blocks dispatch. No test feeds the guard a malformed brief (garbage, ROUND 4,
  round: 99999, Unicode digits).
- Fix: match `[0-9]{1,4}` (or RegexOptions.ECMAScript) and `int.TryParse`. Also wrap the call site the way the routing
  pin warning does (AgentTaskService.cs ~4425: `catch (Exception ex) when (ex is not OperationCanceledException)`),
  so that any guard fault becomes a warning or nothing and never a create failure. Red-first witnesses: the Unicode-digit
  probe on `Evaluate`, and a CreateAsync case (AgentTaskCardBindingTests) with a `round: ４` Review brief that must
  create with no exception.
