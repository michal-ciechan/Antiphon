## Defects

### D1. Linked worktree HEAD reflog is not a tip (P1 fail-open)

Where: `scripts/c590-remote.sh` `consider_tips`, `git -C "$where" rev-parse --path-format=absolute --git-path logs` (line 4538). The same hole makes `docs/docker-stack.md` line 295 false: "each worktree's private refs and HEAD (also bare HEAD), and both sides of every reflog entry must prove publication".

Failure: In a blobless `--filter=blob:none --no-checkout` seed, `git worktree add --detach` a linked worktree, commit, then `git reset --hard HEAD~1`. Private commit `639d8960a378ee86717c978e89e21d068207da74` remains in `.git/worktrees/linked/logs/HEAD` and in that worktree's `ORIG_HEAD`. It is not an ancestor of published HEAD `85c6c5d624d774bd38b5945bf9fc56124295daca`, `for-each-ref` does not list it, and it is absent from the common `.git/logs`. `git -C <linked> rev-parse --git-path logs` returns the common logs directory. `git rev-parse --git-path logs/HEAD` returns `.git/worktrees/linked/logs/HEAD`. Re-running the extracted helper exits 0, prints only the published tip twice, and reports `repositories=2 partial=2`. The private oid is not mentioned. Removal would discard a commit Git itself still records.

Why: `--git-path logs` is `$GIT_COMMON_DIR/logs`. A linked worktree's private HEAD reflog lives under `$GIT_DIR/logs`. The author's `linked-head` case leaves HEAD on the private commit, so `rev-parse HEAD` hides this. `linked-private` stores `refs/worktree/recovery`, which `for-each-ref` sees, then expires logs. The untested shape is the reflog after the ref has moved. The same cause would miss any reflog that lives only under the linked git dir after `git bisect reset`; that sequence was not separately reproduced.

Fix: For every worktree, also read `$(git rev-parse --absolute-git-dir)/logs`, both old and new oids, and add a regression that resets a detached linked worktree and expects `RecycleUnpublishedWork`. Rewrite the docker-stack sentence so it matches the code. The documentation test pins `GIT_NO_LAZY_FETCH=1` and does not pin this sentence, which is why the false sentence stayed green.

### D2. ORIG_HEAD and FETCH_HEAD are invisible until prune (P2 fail-open window)

Where: `consider_tips` enumerates `for-each-ref` and reflog files only. `ORIG_HEAD` and `FETCH_HEAD` are not refs and are not lock markers.

Failure: After a local commit, `reset --hard HEAD~1`, and `reflog expire --expire=all --all`, the unpublished oid remains in `ORIG_HEAD`, `cat-file` succeeds, and the audit passes. Separately, `git fetch <other-url> master` of a commit that exists only there leaves that oid solely in `.git/FETCH_HEAD` (no expire required). Re-checked this round: oid `e273f0793f1552c780d9253e34d5f039c033e8bb` was not listed by `for-each-ref`, `cat-file` succeeded, audit exit 0, `repositories=1 partial=1`. `git gc --prune=now` then deleted the object (`cat-file` gone) while `rev-parse FETCH_HEAD` still printed the dangling oid. These names are not gc roots. A one-shot `git fetch origin pull/N/head` has the FETCH_HEAD shape. Volume removal before prune destroys recoverable objects; removal after prune does not.

Fix: Treat resolvable per-worktree `ORIG_HEAD` and `FETCH_HEAD` as commit tips, or refuse while those files name objects that are still present. Do not treat this as the same hole as the linked reflog: Git drops these objects on prune, and it keeps the linked reflog.
