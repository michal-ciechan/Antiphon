## (3) Kill-site table re-derived

Searched for StopDelegateAsync (Cancel, RequeueCore, BlockOnWall), `_sessions.KillAsync` (never-started watchdog,
FailWedgedAtLimitAsync), PoolDelegateRelease kills (settled pool agents), and every caller of
RequeueAsync/RequeueCoreAsync/RetryAsync/EscalateAsync/RerouteAsync/RerouteOnWallAsync, plus the dispatcher's own
`Status = Queued` (routing-blocked resume at :1820, which kills nothing). I found no NEW kill-then-park path introduced by
the chain. The table has two omissions or mislabels, both advisory:
- A-1 (mislabel, pre-existing): the "RetryAsync (list-governed task)" row says the only park is a Required pin. A chain
  task created with an explicit `-AgentId` of a standing agent whose ModelId is held also escapes the refusal and is
  killed. At the tick the walk compares tier aliases. If it picks the task's own (kind, level), the outcome is None,
  exhaustion is false and the task parks behind the hold. If it picks another tier, the tick reroutes and launches on the
  agent's ModelId, which is the held model (pre-existing CARD-0090/0182 tick behaviour). This is the same residual as
  disclosed gap 2, reached through Retry instead of the wall. `MatrixDefaultApplies` excludes AgentId, and a pin that
  carries an agent is single-candidate, so it sets no RoutingPinId. Only an explicit `-Complexity` + `-AgentId` create
  reaches it.
- A-2 (omission): `AgentTaskDispatcher.RecoverReleasedSeatAnswersAsync` (:5305) calls `RetryAsync` automatically for a
  Blocked released-seat task. When it falls through the released-seat branch, the new refusal throws, the caller logs
  "Released-seat answer recovery deferred" and it retries the next tick. Nothing is killed (the seat is already released)
  and the answer is kept. This matches ContinueReleasedSeatAnswerAsync's own RequireAsync, so it is not a defect.
- A-3 (pre-existing race, armed only when the auto clock is configured; it ships disarmed): `AutoEscalateStalledAsync`
  writes `tracked.FailureReason` on the shared context and then calls EscalateAsync. If a hold appears between the
  IsHeldAsync skip and RequireAsync, the refusal is caught and the unsaved FailureReason can ride a later SaveChanges in
  the same scope. Every EscalateAsync exception there already behaves this way.
