## Priority 1: a real fix or a smaller window?

It is a smaller window. `Consume` (CheckpointFileReader.cs:105) calls
`stream.ReadAsync(...).AsTask().WaitAsync(deadline.Token).GetAwaiter().GetResult()`. On Linux the handle is synchronous,
so ReadAsync queues the pread to a thread-pool worker. The caller blocks a worker while it waits. The stall window is a
TimeProvider CTS armed before the open, so it measures from arming until the timer fires. That covers three things:
the open and inspection, the wait for a pool worker to pick up the queued pread, and the syscall itself. The refusal
also needs a pool worker, because the timer callback that cancels the wait runs on the pool. A real read takes
microseconds, so almost all of the measured time is pool queueing.

Probe (scratchpad console app against the built Antiphon.HostCleanup.dll; N pool tasks each call `ReadBytes` once on a
healthy 85-byte regular file; default pool, no CPU burners):

| Window | N=64 | N=128 | N=200 | N=400 |
|---|---|---|---|---|
| 3 s (red build) | n/a | 55/128 refused | 104/200 refused | n/a |
| 6 s (tip) | 0 refused, max 459 ms | 0 refused, but successful reads took up to 4.6 s | 82/200 refused | 252/400 refused, refusals landed at 6.0-16.4 s |

Every refusal was `read-stalled: 0 of 85 bytes`. A synchronous `FileStream.Read` of the same file on a non-pool thread
took 0.25 ms. When the pool was capped at 4 workers with 4 or 8 callers, nothing completed and nothing was refused within
45 s (the watchdog fired). The pread and the timer callback both wait for a worker, so the read hangs instead of being
refused. That is a pre-existing liveness gap, not fail-open: nothing is ever accepted. The same failure can still happen
at 6 s. It only needs about 1.5-2x more concurrent blocked readers. A desktop at 100% CPU with 39-way test fan-out is
the right condition to reach that.

The measured sample (p95 0.46 ms, max 274 ms, n=440) never reproduced the failure, so 6 s is not derived from a measured
p95 under the failing condition. It is twice a censoring point. The doc and the comment say so honestly.

A-1 (advisory, follow-up card, not blocking): make the Linux regular-file read not depend on the pool.
- Option 1: a synchronous `stream.Read` / `RandomAccess.Read` on the caller thread. It runs inline in about 4 ms even
  when the pool is saturated (see the earlier Review 7ba417d9 D-1 probe).
- Option 2: if a hung filesystem (FUSE/NFS) must still be bounded, do the pread on a dedicated non-pool thread. The
  caller then waits on a monotonic `ManualResetEventSlim.Wait(remaining)`, and each delivered chunk re-arms that wait.
  No pool timer is involved, so the window counts only time the read is actually outstanding, and the refusal can fire
  under starvation.
- Either option, with a starvation witness: a capped pool plus N blocked callers, asserting a healthy file reads and a
  silent stream is still refused.
- Windows (OVERLAPPED) can keep ReadAsync, but the timer-on-pool refusal gap applies there too.

## Priority 2: fail-closed behaviour

- A read that never progresses is still refused. The witness passes on a controlled clock, and so do
  HostCleanupCheckpointReadDeadlineTests, the C1307 tests, custody and EOF.
- A caller cancel stays a cancellation.
- The Windows read-mode contract is unchanged (CheckpointWindowsReadModeTests green). The OVERLAPPED, NOFOLLOW,
  CLOEXEC and SEQUENTIAL flags are untouched, and custody and adoption are green.

A-2 (advisory, pre-existing since CARD-1358, doubled by this change): there is no overall cap. Every delivered chunk
re-arms the window, and a chunk can be a short read. A source that returns 1 byte every 5.9 s, or a file a writer
appends to slowly, holds the read until EOF or until the size limit plus one byte. Worst cases:
- An 85-byte receipt: about 8 min.
- A 64 MiB receipt or a 1 GiB stamp under a 1-byte trickle: effectively unbounded.
- A 1 GiB stamp whose full 256 KiB chunks each arrive just under 6 s: 4096 x 6 s, about 6.8 h, up from 3.4 h.

The comment "the total is bounded by the chunk count" is wrong for short reads. Only the caller's CancellationToken
bounds the total. A regular local file cannot trickle, so this is low risk. If a total cap is wanted, it belongs in the
A-1 follow-up as an overall deadline proportional to the inspected size, plus a fixed floor.

## Priority 4: is the red witness real?

Yes, and it is deterministic: a ControlledTimeProvider is advanced inside the injected stream's ReadAsync, with no wall
time involved. It went red at 30af312ec (2/2) and is green at the tip. It witnesses the constant, not the mechanism: it
models a slow read syscall, not a starved pool continuation, so it would stay green under the real starvation failure.
That is part of A-1.
