## Defects

### D-1 (major): the queue root cause is unreachable, and V-1 would witness a test-only state

**Where:** Ground truth row 1, D-2's motivating text, and V-1. CARD-1603's description and S3 plan
Risk 8 carry the same claim.

**Failure:** an expired or just-claimed optional brief can never be a capacity-selected row.

- `ApplyCapacityHoldAsync` holds and selects only Channel/Scheduled rows (`SessionMessageQueueService.cs:5534-5536`).
- `SelectedMessageId` is stamped only from that set (`:5557-5573`). The only other stamp,
  `StampQueueActionAsync` (`CapacityRecoveryService.cs:968-986`), has test-only callers.
- Both brief cancellers require `ExecutionTaskId != null` (`:2206-2209`, `:2235-2236`). Every
  production `ExecutionTaskId` row is Delegation origin:
  - `SessionMessageQueueService.DispatchBrief.cs:228-230`;
  - `AgentTaskDispatcher.cs:5455-5461` and `:8996-8998`;
  - `AgentSessionService.cs:1132-1134`;
  - `AgentTaskDispatcher.cs:5372-5380`, which filters `Origin == Delegation`.
- A run batches only rows of the head's own origin (`:2601-2625`). The redeem at `:2578-2589` fires
  only when `pending[0]` is keyed, and the unheld rows are placed before the selected row
  (`:5620-5625`).

So the expiry paths S3 review A-2 cites (`CancelExpiredBriefsAsync` and
`CancelJustClaimedExpiredBriefsAsync`/`OptionalBriefExpiredException`) can never cancel a selected
row. V-1 could only be built by seeding a Delegation brief through test-only `StampQueueActionAsync`.
It would go red on today's code, but it witnesses a state production cannot produce. That leaves the
plan with no real producer-to-recipient test.

**Real producers** that can cancel a selected Channel/Scheduled row, and do leave the grant cycling:

- Human Drop `CancelAsync` (`:1205-1208`). It works on a Pending row either before redeem, or after a
  reverted attempt has already redeemed it.
- `CancelParkedIfStaleAsync` (`:1389-1392`).
- `RemoteSpillCourier.MarkUndeliverable` (`RemoteSpillCourier.cs:270-282`).

**Why the grant keeps cycling:**

- **Before redeem (`ActionPending`):** D-12 expiry runs `RearmRevokedGrantOnAsync`, then
  `PrepareNextAttemptOnAsync` (`CapacityRecoveryService.cs:1203-1223`, `:1370-1408`). That re-keys
  the canceled row too, because `:1400-1407` has no status filter. It never increments
  `AdmissionCount`, so the wait never reaches Exhausted.
- **After redeem:** `SelectedMessageId` counts as an execution receipt
  (`CapacityRecoveryPolicy.cs:92-96`). Revalidation is then re-armed forever (`:1347-1355`).
- **Bound the plan omits:** `ObserveTranscriptAsync` (`:879-905`) progresses a LiveSession wait by
  `SessionId` on any successful report-boundary turn. The leak therefore lasts until the session
  next completes a successful turn, and the V-1 fixture must not produce one.

**Fix:**

- Re-ground the queue half on the real cancellers.
- Rebuild V-1's arms as `human-drop-before-redeem` (count 0) and `human-drop-after-redeem` (count 1,
  after a reverted attempt), or as parked-stale. Drive them through the real queue API.
- Have the orchestrator correct the CARD-1603 and S3 Risk 8 wording.

### D-2 (major): finishing the wait on a canceled selection drops a live consumer

**Where:** D-2 and Risk 6.

**Failure:** a LiveSession wait serves the session's whole held queue, not one row.

**Scenario (a), a pending row that was never selected:**

1. The wait is not currently granted (Ready, Deferred, or re-armed after expiry).
2. `SelectedMessageId` is X, which has been canceled.
3. A new held Channel row Y is Pending and unselected. `ApplyCapacityHoldAsync` stamps a row only
   while the provider grant names the wait (`:5557-5566`).
4. The plan's recheck finds X still canceled and still selected, so the wait is set to Canceled.
5. Y is now never selected. There is no unfinished wait (`:5544-5552`), and `selected` excludes
   Canceled waits (`:5584-5592`). Y stays "Held" until a human prompt.

At base, Y would have been stamped and delivered on the next grant.

**Scenario (b), later input:** any later Channel/Scheduled row on that still-walled session is held
with no wait, because `HasTerminalCapacityHoldAsync` (`:5629-5644`) is still true.

**Why Risk 6 doesn't cover this:** Risk 6 assumes compatibility may create a new episode. But
`ReconcileCompatibilityAsync`'s cursor (`:988-1132`) only moves forward: it filters `k > afterKey`
and keeps the cursor when no keys are left. It never revisits a session key. Nothing recreates the
wait, so the change turns a provider leak into stuck Channel/Scheduled input.

**Fix:** choose one of these.

- Under the gate, clear the stale selection (the wait's `SelectedMessageId` and the canceled row's
  key) instead of finishing the wait. Then stop granting a LiveSession wait that has no pending held
  row.
- Or finish only when no Pending Channel/Scheduled row exists, and have `ApplyCapacityHoldAsync`
  register a wait when a held row finds none.

Either way, add guard arms `unselected-held-pending` (wait not granted) and
`later-held-input-after-cleanup`. Each must assert that the row is delivered on a later grant.

## Item 3: dependency on S3-A (advisory A-1)

The ordering claim is correct.

**What breaks if Code starts before S3-A lands:**

- **Misclassification.** At base, the supervisor stamps the session key outside the reservation
  (`AgentSupervisorService.cs:517-523`). A non-reserve arm that creates a new session gives it no key
  (`AgentControlService.cs:728` sets one only for `supervisedFresh`) and no wait generation
  (`AcceptAsync` stamps only `admittedCapacity`, `:804-816`). D-3's null-generation rule would
  therefore supersede the supervisor's own admitted start of an agent that has no pointer.
- **CP-4 floor.** The floor of 20 is unmeetable on base, which has only 6 results.
- **Conflicts.** S3-A adds +132 lines to `CapacityRecoveryService.cs` and +116 to
  `AgentSupervisorService.cs`.

S3-A moves both stamps into the reservation (`ConsumeAdmittedStartAsync` and
`RedeemOnAsync(... receipt: Admitted, stampSessionId/StartedAt)`).

## Other advisories

- **A-2: the standing path (D-3/D-4) is sound.**
  - The `NOWAIT` row locks and `pg_try_advisory_xact_lock` never block.
  - Session-before-agent order matches `AgentControlService.cs:543-549`.
  - S3-A's supervisor consume uses the `Admitted` receipt with no launch receipt, so its waits stay
    D-3 candidates with a full generation.
  - The inherited-key ambiguity is legacy-only once S3-A is in.
  - CAS on state/`Version`/`ActionKey`/selection is required. `Version` is not a concurrency token
    (`AppDbContext.cs:2903-2924`), as the plan states.
- **A-3: cross-process race.** The queue gate exists only within one process, and
  `ApplyCapacityHoldAsync` writes `SelectedMessageId` without the provider lock or a `Version++`
  (`:5569-5573`). If two server processes overlap (for example during a staged rollout), one can
  stamp a new row onto a wait the other just canceled. This is a pre-existing class; name it in Risks.
- **A-4: possible resurrection of a canceled row.** `SessionMessageQueueService.ResumeReceipt.cs:122-127`
  resets rows to Pending with no status filter. Prove it cannot resurrect a Canceled selected row, or
  include the message's Canceled status in the cleanup transaction's conditional write.
- **A-5: Unit lane wording.** "No full Unit/assembly run" should defer to the Code brief's
  verification profile (Final requires the Unit lane).
- **A-6: rc and master (item 6).** D-5 is right: product hosts track rc, and the port should follow
  S3-A reaching rc. Live land/dispatch risk is low (bounded batches, try-locks). Measure how long the
  queue cleanup holds the per-session delivery semaphore across its DB transaction.
