## (1) Stranger kill / live writer (late pass, server/Infrastructure/Git/OwnedProcessTree.cs:499-560)

A late child is a row in the follow read (CaptureSnapshot = a breadth-first walk from the root pid
over the current parent map) that meets all of these:
- its parent pid is one this wave signalled;
- it was not in any sealed snapshot;
- it is not the server or owner pid;
- its start ticks are readable and not later than the clock sample taken before the follow read
  (MaskRowsStartedAfter);
- its start is at or after the parent's recorded start.

Before the kill, Signal reads the child's start time again through a fresh handle and compares it.
No marker is used in this pass.

Parent cases:
- **Present, same ticks:** children are walked, as before.
- **Present, different ticks:** skipped. This is new. The log line is
  `repository_child_tree_kill kill_failed pid=<p> reason=parent_identity_mismatch`: the pid and a
  fixed token only.
- **Present, ticks masked** (the stranger started after the follow clock sample): walked. Its
  children start after it, so they are masked too, and none qualifies. Safe.
- **Missing:** cannot happen in production. The breadth-first walk always emits a parent row
  before its children, so this case is reached only through injected test tables.
- **Windows:** every signalled pid keeps a retained handle until after the follow read
  (KillHeld/finally), so its pid cannot be reused there.

### A-1 (advisory; existed before this change, and the diff narrows it)

On Linux, a parent row can be present with unreadable ticks (null) and still be walked. Scenario:
1. The root pid is reaped and reused within the 2 s reap window by a stranger P'.
2. P' spawns child C.
3. The /proc parent map records C with parent P'.
4. P' exits before ReadTicks(P'), so its row is null.
5. C is still alive and readable, with a start later than the old root's start.
6. C is accepted and killed.

Before this diff the same scenario, and the readable case too, killed C, so the change opens no
new path.

Fix if wanted: on Linux, treat a null-tick parent row as a stranger. Linux reparents orphans, so a
dead parent never legitimately keeps a parent-pid edge. The Windows orphan reason applies only on
Windows.

No live writer is released: the guard only removes kills.

## (2) A-4 (WaitForRetainedHandle, :425-434)

The no-handle path is unreachable in production. Every signalled pid passed KillHeld, which adds
the pid to `retained` in its finally block. If it were reached:
- it returns false at once, so StillAlive > 0, HoldersGone is false, and the journal is kept;
- it does not loop: Reap waits once per pid, and each WaitForExit is bounded by the remaining
  ReapBoundMilliseconds;
- it cannot hang.

The landing-fence code (marker, job object, keep-on-cannot-tell) is unchanged: the diff touches
only PlanLateChildren, WaitRetained, and the visibility of RetainedProcess.
