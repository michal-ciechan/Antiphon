## (1) D-2 safety

The flag is stored in `<root>/.antiphon/worktrees/<sha256(path)>.json`, written atomically (temp file, flush, `File.Move` overwrite). The order in `CreateAsync` is: save the intent (`CreationComplete=false`), run `git worktree add` (git writes `locked initializing` before the checkout and deletes it only after the checkout succeeds), `rev-parse --absolute-git-dir`, then save with `CreationComplete=true`. `TouchAsync` rewrites the record with `with { LastTouchedAt }`, so the flag is kept. No other writer exists.

**A crash after completion but before the flag is saved:** the record still says incomplete, but the registration is unlocked because git already removed `initializing`. The D-2 guard `!matching[0].Locked || LockReason != "initializing"` therefore throws `ConflictException ... nothing removed`. The good worktree is **not deleted**. See disclosure A for its liveness cost.

| State | D-2 outcome |
|---|---|
| no creation record / schema 1 | returns immediately; the old path/branch checks apply |
| record complete (any live or used worktree) | returns immediately, so nothing is touched |
| record incomplete, no registration at the path | returns; then "path exists" or "branch exists" refuses |
| registration locked with another reason (`operator hold`) or unlocked | refuses, removes nothing (C1448_OtherLockReasonRemovesNothing) |
| two registrations at the path | refuses (`matching.Length != 1`) |
| registration on another branch / intent for another repo or branch | refuses |
| branch ahead of or behind InitialSha, or missing | refuses (C1448_MovedBranchRemovesNothing); committed work is kept |
| branch moves during recovery | `update-ref -d <ref> <InitialSha>` old-value check fails, so the branch is kept and the refusal is named |
| locked initializing, at InitialSha, directory present (partial) | `worktree remove --force --force`: git validates that `<dir>/.git` points back to this admin dir and removes only that tree (it does not follow nested symlinks) |
| same, `.git` file not yet written | git refuses, giving InvalidOperationException; nothing removed; the dispatcher fails the task |
| same, directory absent | deletes only the admin dir whose `gitdir` equals `<path>/.git`, and only when exactly one matches (no prune) |
| path registered to a different repository | this repository's list has no match, so it returns; "path exists" refuses |
| two concurrent creates for one path | serialised by the repository lease plus a per-path `FileShare.None` lock file (flock on Linux) |
| symlink or junction at the path | git's validation of the `.git` back-pointer bounds the remove; .NET `Directory.Delete(recursive)` of the admin dir does not follow links |

## Disclosures (not defects under the verdict policy)

- **A. Liveness: a crash or cancellation just after a successful add.** This is the interval between `git worktree add` returning and the `CreationComplete=true` save (one `rev-parse` and the write; a tick-cancellation OCE there is outside the add's rollback catch). It leaves a complete, unlocked, good worktree flagged incomplete. D-2 refuses, so nothing is removed. D-1 now refuses to adopt it every time and the task Fails with the named message. The base would have adopted it. Recovery is manual. The window is milliseconds against the seconds-to-minutes window of the original incident, and the plan decided this behaviour in D-1. Possible follow-up: in D-2, when the record is incomplete but the registration is unlocked, the branch is at InitialSha and the `.git` back-pointer validates, complete the record instead of refusing.
- **B. Coverage gaps.** No test guards against an unbounded admin delete (needs a sibling missing-directory registration). No direct guard covers a complete record whose registration is locked `initializing` (mutation b is caught only through the heal tests). As already disclosed, D-3's warning and the AgentSessionService filter have no test.
- **C. D-2 does not check the partial directory for uncommitted or untracked files.** RollbackFailedAddAsync does check `status`; D-2 does not. After this fix, no path can adopt a locked-initializing checkout, so no session writes there. Only a half checkout adopted before the fix, holding uncommitted files and whose same task id is dispatched again, would lose those files. Committed work is always kept.
- **D. Branch delete check.** D-2 checks only the path for remaining registrations before `update-ref -d`; it does not check whether another registration has the same branch checked out (rollback does). Git refuses a double checkout without `--force`, so this is minor.

Suggested Backlog (one card): CARD-1448 follow-up covering a sibling-registration guard for the no-directory recovery, a complete-record + locked-initializing guard, an AgentSessionService card-spawn filter test, and optionally disclosure A's completion path.
