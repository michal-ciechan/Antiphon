# Debug 52410842: S4a long-path untracked file not held, removal Partial

## Severity (first)

**HIGH: a default-on feature can delete a worktree that holds uncommitted bytes.** The S4a clean proof
accepts a `git status` that silently skipped part of the tree. Today:

- **Desktop hosts are NOT exposed.** `git merge-base --is-ancestor 3eb9d0027 919d8d42f` exits 1, so S4a is
  not in the build the hosts run.
- **rc/2026-11-06 IS exposed.** `3eb9d0027` is an ancestor of `origin/rc/2026-11-06` (exit 0). The fix
  needs an rc port. It changes the policy service, LandingDtos and LandingGit.
- **What was lost on the Windows host (reasoned from the code, not observed):** a removal that ends Partial
  has already deleted, depth-first, every entry of the set-aside tree that sorts before the deep chain. That
  includes the `.git` file, the tracked files, `.gitignore`, `keep.txt` and the other shallow entries.
  The deep untracked file most likely **survived**. The no-follow delete opens each entry with a raw
  `CreateFileW` and no `\\?\` prefix, so it cannot open a path past MAX_PATH either, and that is exactly what
  made the run Partial.
  - The tree is left renamed to the set-aside path, unregistered, and with its local branch kept. It stays
    Partial on every retry: the retry skips the pre-check because the command intent is spent, and
    `Delete(aside)` fails at the same path each time.
  - The committed bytes can be recovered from the branch (local and origin). The unsaved file sits only in
    the set-aside directory.
  - **On a host whose process is long-path aware (LongPathsEnabled=1 plus a longPathAware manifest), the
    delete would finish. The row would read Removed and the unsaved bytes would be gone.**
- **Exposure:** the tree must have an untracked file that is not ignored and that git cannot see.
  - The usual case is a path past about 260 characters under a directory that is not ignored. Typical
    sources are a deep build or package tree the task did not ignore, or a long generated path.
  - A directory git cannot open (ACL or permission) is the same shape. On Windows the ignored-content gate
    may refuse that one (see the Linux result below).
  - This is uncommon in a normal task worktree, but S4a sweeps every legacy desktop tree aged 48 h or more,
    up to 25 per tick, so a rare shape is still reached.

## Cause (answer to question 1: option (a))

- `server/Application/Services/DesktopLegacyReleasePolicyService.cs:405-407` (base 84e19071e): the
  pre-check runs `git status --porcelain=v1 -z --untracked-files=all --ignore-submodules=none` through the
  **git CLI**. `status` is not among the commands `InProcessGitReads.Handled` answers in process (those are
  rev-parse, show-ref, symbolic-ref and merge-base), so libgit2 is not involved. The check treats
  `Succeeded && Output == ""` as clean.
- Git for Windows without `core.longpaths` cannot open a directory past MAX_PATH. In `dir.c`
  `open_cached_dir`, git warns `could not open directory '<dir>/': Filename too long` on stderr, lists
  nothing under that directory and **exits 0**.
- `LandingGit.ExecuteProcessAsync` (`server/Infrastructure/Git/LandingGit.cs:247-248` at base) discards
  stderr completely ("Never expose Git stderr"). The warning therefore never reached the policy, and the
  empty listing passed as clean.
- The test fixture's repository does not set core.longpaths. Note that a linked worktree reads the common
  config, so a clone that sets `core.longpaths=true` would protect its worktrees. The policy should not
  depend on that.
- The guarded removal re-proves the tree with the same status arguments (`LandingGit.cs:801`,
  `InspectAsync`), so it is blind in the same way. On Windows the ignored-content gate enumerates with
  managed .NET, which is long-path capable, and it passed. The tree then went through MoveAside →
  `UnregisterAsync` → `WorktreeNoFollowDelete.Delete`. `DeleteWindows` threw at the deep entry
  (`no_follow_open_failed`), which gives `worktree_removal_incomplete`, directoryGone=true and
  unregistered=true. Line 344 of the policy service then records the row as **Partial**.

**Linux reproduction (real git 2.47.3):** an unreadable untracked directory gives exit 0, an empty listing
and `warning: could not open directory 'src/deep/': Permission denied`.

- At base, the new witness shows the pre-check passing and a SYSTEM release being filed, after which the
  guarded removal ran: three `status` calls were made in the tree.
- On Linux the removal's ignored-content gate then refused the tree with `Refused cleanup_inspection_error`,
  so the tree stayed intact. On Windows (long path) that second guard did not trigger.

## Fix (test-first, on feat/card-task-52410842)

- The pre-check status now runs as `git -c core.longpaths=true status ...`, so Git for Windows sees the
  deep path and reports `source_dirty`. This is what the native N-2b case expects.
- `LandingGitResult.WroteStandardError` is a bool and carries only the fact, never the stderr text.
  `LandingGit` sets it for every process run.
- The pre-check holds a tree whose clean listing came with stderr output as **`status_untrusted`**. This
  fails closed for any directory git could not open, whatever the cause. A status that is dirty or failed
  stays `source_dirty`.
- `docs/orchestration-loop.md`: `status_untrusted` is added to the S4a Held reasons.
- The tests use `DesktopLegacyWorld.Subcommand()`, which skips the leading `-c`, wherever they matched
  `args[0] == "status"`. That covers Prechecked, the read-only allowlist and three census sites.

## Not fixed (needs a decision): options

1. **The guarded removal's own re-proof** (`LandingGit.InspectAsync`, `LandingGit.cs:801`) still runs
   status without core.longpaths and ignores stderr. It is used by lands too. Adding the same two checks
   there would make the removal a real second guard. The risk is that a land refuses on a status warning,
   which is fail-safe. This is recommended as a follow-up card with its own Review.
2. **`WorktreeNoFollowDelete.DeleteWindows`** opens each entry without `\\?\`, so a deep ignored tree,
   such as N-2's `obj/...`, ends Partial and the tree is stuck set aside and unregistered. Recording the
   deep tree's state is already a card per the N-2 note. The options are to use extended paths, or to
   refuse before MoveAside when any entry is past MAX_PATH, which keeps the tree intact.

## Recommendation (the operator decides)

Do not ship S4a **ON by default** in rc/2026-11-06 without this fix ported. Either port the three commits
(the pre-check fix is self-contained and clean onto rc), or ship with `WorktreeLegacyRelease:Execute=false`
(dry run) until CP-25 is green on Windows at the fixed SHA. The hosts on 919d8d42f are unaffected today.
