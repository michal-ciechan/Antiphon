## Change

- `WorktreeRenames` (server/Infrastructure/Git/WorktreeRenames.cs):
  - Adds the `DeleteTree` init seam. Its default is `WorktreeNoFollowDelete.Delete`.
  - Adds `IsTransientDelete`. It returns true only when all of these hold:
    - running on Windows;
    - the exception is not a `NestedRepositoryPreservedException`;
    - it is an `IOException` or `UnauthorizedAccessException`;
    - its code is in {5, 32, 33, 145}.
  - Adds `Win32Code`, which accepts both the raw code and the 0x8007xxxx form.
  - `IsSharingConflict` is unchanged.
- `WorktreeNoFollowDelete.DeleteSettled` makes at most `SharingAttempts` (5) attempts, with `SharingPause`
  (100 ms) between them:
  - Each attempt re-runs the whole walk through `DeleteTree`.
  - It retries a transient error.
  - On Windows only, it also waits while the tree is still visible after a delete that returned.
  - Before each retry, after the pause, it checks whether the tree is already gone. A pending delete that
    finished during the pause is therefore a success. Without this check the next walk would fail on the
    missing path with 3, a refusal that is not retried.
  - After the last attempt it rethrows, or returns with the tree still present. The caller's existing
    refusal stands.
- `GuardedWorktreeRemoval`:
  - Both delete sites (the resume site at ~:91 and the post-unregister site at ~:185) call `DeleteSettled`.
  - The Detail of a delete that throws becomes `set-aside: <aside>; delete_error_<code>`.
  - A delete that returns but leaves the tree visible keeps the bare `set-aside: <aside>`. So the Detail
    now shows which of the two sites refused.
  - The residue, the kept set-aside tree, the record and the resume path are all unchanged. Nothing is
    forced.
- Two exact-match assertions change, deliberately. Both are in Windows-only tests:
  - `LandingRemovalPolicyControlTests.cs:~467`
  - `WorktreeGuardedCleanupTests.cs:~409` (`C665_LockedFileMidDeleteResumesOnLaterPass`)

  Both now expect `"set-aside: " + aside + "; delete_error_32"`. Reading the code: the held
  `FileShare.Read` stream makes the no-follow open of that file (DELETE access) fail with
  ERROR_SHARING_VIOLATION. Both tests stay green by reading: still worktree_removal_incomplete, a partial
  tree, then the later pass is clean. Each first pass now takes about 2.4 s, inside the class timeouts.
- The V36 baseline comment (`LandingRemovalPolicyControlTests.cs:185`) now names the delete as well.

## Callers and added delay

A lasting hold of code 32 costs about 2.4 s. On each attempt the inner open makes 5 attempts with
4 × 100 ms between them; there are 5 attempts, with 4 × 100 ms between them. That gives 5 × 0.4 + 0.4 s.
Before this change the same hold cost 0.4 s. A lasting 5, 33, 145, or tree still visible costs 0.4 s,
where before it cost 0 s. A walk stops at the first refusal, so each re-walk covers only what remains.
The pause is `Thread.Sleep`, the same as the existing MoveAside and Record retries.

| caller | path | per-candidate worst added |
|---|---|---|
| AgentTaskLandingProtocol:456 (post-land cleanup) | WorktreeManager.TryRemoveAsync → WorktreeGuardedCleanup → RemoveDirectoryAsync | +2.0 s. failedAt is stamped after the loop, so the 10 s extra-work budget is not consumed. The retry pass is nominated only for worktree_remove_failed, so it never doubles |
| TaskWorktreeRetirementService:386 (settled-task retirement, incl. S4a ReleaseSystemAsync) | TryRemoveAsync → RemoveAsync → RemoveDirectoryAsync | +2.0 s; one delete site per pass (the resume and post-unregister sites are exclusive) |
| WorktreeResidueSweepService:564 | same | +2.0 s |
| DelegationWorktreeService:909 (LocalMerge) | same | +2.0 s |
| VerificationCleanupService:124 | GuardedVerificationRemoval | unaffected (does not use these delete sites) |

S4a (DesktopLegacyReleasePolicyService): `MaxReleasesPerTick` is 25 by default and validated to 1..100.
Suppose every candidate in a tick hits a lasting code-32 hold:

- worst per tick is 25 × 2.4 s = 60 s, where before it was 25 × 0.4 s = 10 s, so +50 s;
- at the maximum setting of 100 it is 240 s.

For a transient hold (the case this fixes), a candidate becomes clean after one 100 ms pause instead of
leaving residue that waits for the next tick.
