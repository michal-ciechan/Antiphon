## Data-loss analysis (priority 1)

- **A batch contains whole trees.** The batch unit is `RootTaskId` (DataRetentionService.cs:503-506). Every keep predicate is keyed on `t.RootTaskId` and ranges over the whole table (`member.RootTaskId == t.RootTaskId`, and `liveRootIds` over all rows). So all rows of a root pass or fail together. `GroupBy(RootTaskId).Max(...)` is taken over the full tree. The only new conjunct is `batch.Contains(t.RootTaskId)`, so at the same instant each batch's eligible set equals the old eligible set ∩ batch.
- **The candidate set still covers every eligible tree.** The prefilter is "any row with `COALESCE(CompletedAt, CreatedAt) < cutoff`". It is a superset of the old eligible set (old rule: `Max(...) < cutoff`). It only selects which roots to examine; deletion still requires the unchanged eligibility rules.
- **Each batch is atomic.** The delete is unchanged: retirement attempts, then retirements, then depth-descending deletes, in one transaction (:603-630). A failure rolls the whole batch back. Mutant M3 showed this incidentally: an FK failure on one tree left a fully old 4-row tree intact (D=4), not partially deleted.
- **Protection is not re-checked inside the delete transaction.** That was already true at base: base loaded the outbound ids, ran the eligibility query outside the transaction, then deleted. The live, landing, supervision and other predicates are now evaluated fresh per batch, right before that batch's delete, so their window is no wider than before. See A-1 for the one snapshot whose window widened.

## Cursor (priority 2)

- **Memory only.** The cursor is a singleton `DataRetentionTaskCursor` (Program.cs:622). A restart begins from the start; deleted roots leave the candidate set, so a restarted scan still progresses.
- **Ordering is consistent.** Ids are GUIDs, but `RootTaskId > @after` and `ORDER BY RootTaskId` both evaluate in Postgres uuid order, and the cursor value comes from that same SQL order.
- **There is a wrap rule.** An empty or short batch resets the cursor to null. A root that sorts below the cursor is visited by the next scan. Probe R1654Probe_RootBelowCursorIsPrunedAfterWrap proves it: the low root survives the scan in progress, the scan completes and resets, and the next sweep deletes it.

## Advisories (none blocks the land; file as cards)

- **A-1 (DataRetentionService.cs:497): the outbound-id snapshot is taken once per Tasks pass.** A ChannelOutboundDelivery that becomes protected after line 497 and names a member of a tree that is past retention and otherwise unprotected would not stop that tree's batch. The same TOCTOU existed at base. The window grew from about one eligibility statement to the whole pass (≤50 batches). The realistic producer is implied delegation tasks with an undelivered bundle, which are fresh, so the risk is negligible. Fix: call `LoadOutboundTaskIdsAsync` per batch.
- **A-2 (:503-528): a batch that fails deterministically stalls the scan.** The cursor stays before the failing batch, so later roots are never pruned while it keeps failing. Base was worse: everything stalled. A fix could skip past a batch after N consecutive failures and log it.
- **A-3 (backlog passes): the passes after Tasks are still single unbounded statements under the 30 s default.** These are SubscriptionUsageSamples (DELETE), WorktreeResidueHeldRows (DELETE of about 14.5k rows, trivial) and AuditArchive.
  - AuditArchive (AuditService.cs:291-299) is not an archive. It is one UPDATE that nulls `FullContent` past RetentionDays, with no copy. That is the designed CARD-0044 behaviour and unchanged here.
  - The first catch-up after weeks is the intended retention, not new scope.
  - If one of these times out, it now fails in isolation every sweep and makes no progress. CARD-1487 territory.
- **A-4 (performance-standards): batch cost is unmeasured.** Nothing shows a 100-root batch is materially cheaper than the 28 s whole-table query: `liveRootIds` NOT IN and the anti-join subqueries still touch the whole table. `IX_AgentTasks_RootTaskId_CreatedAt` exists, so it is plausible. Worst case is 50 × several statements × 60 s per sweep. `LoadOutboundTaskIdsAsync` still runs under the 30 s default, before `SetCommandTimeout`. Get desktop EXPLAIN/timing after deploy.
- **A-5: no witness that DI injects the singleton cursor into the scoped service.** MS DI resolves a registered optional parameter, so it is correct by construction. Without the singleton, the cursor would reset every sweep.
