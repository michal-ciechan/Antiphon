(c) Cursor. `CommitLegacyCursorAsync` runs after every visit including a caught failure, in its own transaction, as an update-or-insert of the singleton row. A crash before the commit revisits the row; a revisit is idempotent (episode reuse under the task lock, release-ledger CAS). A run is bounded by `pageSize * passBudget` (96) visits. The test proves the cursor survives `RestartAsync` and that eight rows end with exactly one episode each after a poisoned visit.

(d) Fresh window. `FreshLegacyWindow` requires, for `LegacyDiscovery` episodes only, the runner's `FirstObservedAt` present, `StableFor >= 120 s`, and `FirstObservedAt + StableFor >= park.CreatedAt + 120 s`. `park.CreatedAt` is the durable discovery instant; the runner proof is reset on activity, generation or epoch change (`TerminalSeatReleaseObservation.cs:39-49`), so an in-memory reset can only move the window later. The test's 30 h, 119.999 s and 120.001 s arms exercise the boundary. See disclosure 1 for the cross-clock weakness.

## Disclosures (Backlog card candidates, not defects)

1. `FreshLegacyWindow` compares runner wall-clock timestamps (`FirstObservedAt + StableFor` is the runner's observation time) with the server's `park.CreatedAt`. Line 1013 of the same file states the convention "StableFor is measured by the runner; never subtract its timestamps from our clock". A runner clock ahead of the server by N seconds shortens the post-discovery window by N; at 120 s or more it vanishes. Idleness and publication remain gated (runner-side 120 s stability, publication receipt, conditional release), so this is not a fail-open. Suggested form: require the server-measured `now - park.CreatedAt >= 120 s` together with `StableFor >= now - park.CreatedAt`, using `StableFor` only as a duration.
2. Sweep cost and concurrency. `NextLegacyPageAsync` wraps once the tail is short, so with fewer than 32 Blocked rows each pass revisits the same rows and every call handles each row up to three times. The dispatcher calls it every tick (`Delegation:PollIntervalSeconds` default 5) and the Hangfire job every 2 minutes, without the gate `DiscoverScheduledAsync` uses. Each handle of a Requested or Held park without a receipt runs `PrepareAsync` (Git inspection, possibly push) and each published candidate runs an observation RPC plus two `VerifyAsync` calls. Two overlapping sweeps can also collide at `TryAdmitConsumerAsync`, holding the park `park_workspace_reserved` until the next tick re-requests it. Suggested: stop the pass loop when the wrap returns to the starting cursor, guard the sweep with the discovery gate, and back off Held episodes.
3. `RunnerSlotReconcileJob.ExecuteAsync` adds the sweep's visit count to its `released` total, so the Hangfire job result overstates releases. Nothing branches on it.
4. The Code report attributes dispatcher-hook coverage to `AgentTaskPoolTests`; that class constructs the dispatcher without a `TerminalRunnerSeatReleaseService`, so the hook is exercised only by the `SweepAsync` arm inside CP-9. Coverage exists; the attribution is wrong.
5. The red commit `59737e78c` carries most of the production code and stubs only the sweep loop, so the red run proves the sweep dependency only. G-171..G-181 and PC-23/PC-24 remain for method-scoped Mutation, as the profile requires.
6. `AdvanceAsync` now calls `ReleaseSourceAsync(verify: true)` before and after the `BeforeDispatch` cut; in production the cut is null, so every dispatch verifies twice. Harmless duplication.

Also noted: the new `park_binding_missing` and `park_ownership_ambiguous` holds apply to fast-path episodes too. `LoadAsync` in the publication service already refused a null `ReportDigest`, so the first only names an existing refusal; the second is a new conservative hold keyed on exact path equality. Parking is default-off and unactivated, so neither changes shipped behaviour; S5 (`BlockedTaskParkReleaseTests`) stays green.
