## Defects

**D-1: Existing direct consumers of the changed functions are outside the closed checkpoint list.**
- Where: `### Checkpoints`, and Source findings row "A public reader requires…".
- Failure: these existing classes call the functions M2 rewrites, but no CP row runs them:
  - `RcFullTimingContractTests` (S1, `Antiphon.Tests.Scripts`):
    - `:321-322` call `Publish-NightlyChunkObservation`.
    - `:465` calls `Complete-TestPhaseLaunch`.
    - `:796-798` call `Write-TestPhaseExecutedManifest` three times across suites (antiphon/e2e/orphan `scripts`), then `Invoke-TestPhaseRunSummary`.
  - `TestPhaseSupervisorTests` (`:131` reads `timing/groups-executed.json` directly after `Complete-TestPhaseLaunch` at `:413-427`).
  - `TestPhaseSummaryTests`, whose other methods include `C1514NativeProbe.VerifyAsync` (`:125`).
  - `PosixHarnessToolTests`, which runs `scripts/test-qualification-timing.ps1` (`:1472` calls `ConvertTo-TestPhaseSummaryRows`).

  The plan names `C1514NativeProbe` and `TestPhaseSupervisorTests` as consumers but runs neither, and does not mention `RcFullTimingContractTests` at all. M2 can break these silently. An example is a direct `Write-TestPhaseExecutedManifest` caller that expects a flat file, or orphan-suite join evidence. This is also the only orphan-outcome coverage the brief asked about.
- Why: a closed checkpoint list must cover the known consumers of changed code; a later Review would otherwise find them as unlisted reds.
- Fix: add regression rows on the M2 build:
  - `RcFullTimingContractTests/*` (count its methods).
  - `TestPhaseSupervisorTests/*`.
  - `PosixHarnessToolTests` (exact method).
  - The native `TestPhaseSummaryTests` method, on CP-6 or as a Windows row.

  State each row's min count from the source, and update the 26/37 totals.

**D-2: "Generation" and the seal contradict the replacement-across-attempts contract; rerun into an existing root is undefined.**
- Where: Protocol steps 1, 3 and 5, the seal paragraph, V-4, V-5 and V-7.
- Failure:
  - Context: the old writer merges any later invocation that shares a timing root. It replaces same-(suite, chunk) entries, keeps the first header and appends the rest.
  - Contradiction: the plan seals a generation at the terminal finalizer and says "a valid seal refuses further writes". Yet V-4 demands old-writer bytes for "same-suite replacement across attempts".
  - Concrete case: run 1 finishes and seals; a second invocation reuses the root. That happens with an explicit `-TimingRoot`, a continued `-RunId`, or the selection-attempt `TimingRoot` (`nightly-run-impl.ps1:481/588`). Every one of its chunk publications is then refused. Each emits only `phase-summary-failed`, and its rows never reach the projection, where the old code would have merged them.
  - Undefined generation rules: the plan never says when a new generation is created or who creates it, though V-7 tests "a replaced generation". It also never says how "attempt" binds to the writer context while being excluded from the replacement key.
- Why: D-2 (preserve recoverable completed-chunk evidence) and the byte-equivalence goal both depend on this, and it cannot be designed during Code.
- Fix: specify how a generation is chosen per invocation and attempt. Then specify one of two behaviours for a sealed or previously used root:
  - (a) open a new generation seeded from the sealed projection, keeping the old merge and header semantics; or
  - (b) refuse at initialisation, before any test launches, with an explicit reason and the verdict unaffected.

  Make V-4 and V-5 assert the chosen rule on a real second process.

**D-3: Exact byte equivalence ignores the old writer's round-trip asymmetry.**
- Where: Protocol step 5, V-3 and V-4.
- Failure:
  - The old final document serialises the last-published row fresh. Every earlier row and the header `runId`/`suite`/`attempt` have been through `ConvertFrom-Json` at least once.
  - On pwsh 7 that round trip is not the identity. Verified on 7.5.4: `ConvertFrom-Json` turns `"2026-10-30T03:02:00Z"` into a `DateTime`, and `[string]` then prints `10/30/2026 03:02:00`.
  - So a date-shaped `-RunId`, chunk or path value changes in every row except the last.
  - A reducer that re-serialises every journal row once, or splices stored row text, therefore produces different bytes. V-3's inputs (Unicode, quotes, backslashes, controls) would not catch it.
  - Double formatting differs under Windows PowerShell 5.1 (.NET Framework prints 15 significant digits). V-15's "PS5.1 projects compatible bytes" is therefore unachievable as byte equality for `hostWallSeconds` from a Stopwatch.
- Why: the brief and D-2 require byte-equivalent final artifacts, and the pinned-oracle tests must be able to discriminate this.
- Fix: state the rule — prior rows and the header round-tripped exactly once through the production `ConvertFrom-Json` typing, the final row fresh, a replaced row moved to the end and treated as fresh. Add date-shaped run/chunk values and a non-terminating double to V-3/V-4 against the pinned old writer, under pwsh 7.
- V-15: define PS5.1 as parse-compatible, with the multiset of UIDs and outcomes plus field order. Alternatively, name the PS7 host as the only byte oracle.

**D-4: One publication failure disables journaling for the rest of a 23-hour run.**
- Where: Protocol step 3 ("A publication exception invalidates the writer context until recovery") and V-11.
- Failure:
  - Today a failed publish (for example a Windows antivirus or indexer sharing violation on Replace) loses only that chunk; the next chunk rewrites everything.
  - In the plan, the context stays invalid "until recovery". The only recovery named is a restart or the explicit `-RecoverExecutedManifest`, and that refuses while the writer is live.
  - So every later chunk, potentially hundreds, gets no record. The projection then silently covers only the prefix, marked only by `phase-summary-failed`.
  - V-11 checks that the verdict and prior evidence are preserved, not that later chunks continue.
- Why: this regresses recoverable completed-chunk evidence (D-2) for the qualification runner, and the trigger is common on Windows.
- Fix: specify in-process recovery on the next publish. Do one bounded, measured rescan of the committed prefix to re-derive the sequence, with a bounded commit retry. Add a V-11 or V-5 case: inject one rename failure at chunk k, then assert chunks k+1..n are committed, chunk k is reported missing, and there is no gap-induced refusal of the whole projection. That rescan is O(prefix) per failure, not per chunk; budget it.

**D-5: The liveness and external-reader witnesses cannot go red, and the reader inventory is too narrow.**
- Where: V-13, and the Readers/Evidence-gap paragraph.
- Failure:
  - V-13 drives `Update-QualificationSupervisorHeartbeat`. That function takes `Trx`/`Bytes`/`DiagnosticProgress` as caller-supplied values and never reads the timing directory, so "journal writes occur while observations are unchanged" is tautological.
  - No M1/M2 mutation can make V-13 red. That includes its claimed "removing stamp production", since the stamp is written in the `nightly-tests-impl.ps1` loop.
  - The real liveness exposure is an external producer of those inputs (`supervise-rc.ps1`, outside the repo) or an operator/orchestrator watch script that polls `groups-executed.json` size, mtime or chunk count. Those go stale mid-run under the new schedule.
  - The plan's inventory obligation names only `supervise-rc.ps1`, and it names no replacement progress signal for such readers.
- Why: AGENTS forbids a new test that cannot go red. The brief requires the plan to state the real liveness signal.
- Fix:
  - Re-scope V-13 to the production loop (inside V-9's harness): assert the `C487_INVOCATION` stamp and the TRX/log signals per chunk, and that removing the stamp turns it red. Keep the 17-PASS harness as an R-row.
  - State the live progress signal for watchers explicitly: the last committed journal sequence, read via the default `summarize-test-phases.ps1` live read or the accessor, or the newest committed record name. Note that `tests.log` per chunk is unchanged.
  - Extend the pre-rollout inventory to operator and orchestrator qualification watcher tools as well as `supervise-rc.ps1`.

## Advisories

- A-1, at-scale differential: V-16 seeds a legacy prefix plus one record (seed import), so the 240/385-chunk reduction of journal records is never compared byte-for-byte with sequential old-writer output. Add a portable, sequence-level differential: many chunks with small outcome counts (cheap with the old writer), with replacement, failure, missing-TRX and cross-suite events. If the 28bbb58e TRX set is retained, also replay it natively against that run's final `groups-executed.json` (`9db1b295…`).
- A-2: Protocol step 6 says "projects after … failed chunk". That reads as per-failed-chunk projection, which brings back O(n) per failure. Say "terminal outcome categories"; V-9 already forbids projection between chunks.
- A-3: V-2 and V-1 are good deterministic cost oracles (rows traversed and bytes, not wall time). Keep the 0/240/480 counters as row visits, not durations. CP-6's 20 samples per prefix are diagnostics only.
- A-4: Re-anchor every file:line on the S1-integrated base. S1 shifts the writer to `:1379` and the publish call to `:1394`; S3 shifts the call to about `:1406`.
