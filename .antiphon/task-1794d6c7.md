## Sign-in: confirmed product deadlock, fixed

At the assigned base, `server/Application/Services/AgentSessionService.cs:408-415` opens the failure-evidence transaction, locks the session, then locks its agent `FOR UPDATE`. At `:458` it awaits incident recording. That helper creates a separate scope/context at `:1575-1580`. Inserting `AgentIncidents` needs the referenced agent's foreign-key key-share lock (`server/Infrastructure/Data/AppDbContext.cs:542-546`). The outer transaction holds the conflicting agent lock and cannot commit until `AgentSessionService.cs:480`, after the awaited writer returns. Thus caller transaction -> awaited incident insert -> caller transaction is a real await cycle.

This agrees with the supplied native evidence: backend 95 idle in transaction, backend 96 inserting the incident and waiting on transaction 749 held by 95. The earlier static frozen-clock explanation does not explain that captured lock cycle.

The fix at current `AgentSessionService.cs:414-418` uses `FOR NO KEY UPDATE` for the agent. Session-first ordering and the session `FOR UPDATE` lock remain. Status/pointer writers and deletion remain excluded; the incident insert can acquire its FK key-share lock. The witness actually attempts both a competing UPDATE and DELETE while the failure handler holds the lock and requires PostgreSQL `55P03` for each.

`AgentSessionLaunchFailureTests.Sign_in_failure_records_incident_without_waiting_on_its_own_agent_lock` forces the sign-in failure for Grok and ClaudeCode through the fake protocol adapter.
