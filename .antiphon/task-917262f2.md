## (3) New defects

### D-1: Portable S1 rows never build or run Antiphon.Agents.Pty.Tests, so the canary-side wiring has no witness that can go red

**Where:** Implementation slices S1c-executable, S1c-profile, S1c-startup-oracles,
S1c-delivery-oracles and S1c-sanitization; `### Checkpoints` rows CP-17, CP-18, CP-3, CP-19 and
CP-20. All of them have `Build = tests/Antiphon.Tests`. V-3a's "No fixture-only resolver that
live callers bypass" and V-3d's "Same evidence path used by CP-5/C514" are the affected claims.

**Failure:** these slices edit sources that only Agents.Pty.Tests compiles:
- `ClSession.cs`;
- `ClaudeSubmitContractTests.cs` / `ClaudeSubmitContractLiveTests.cs`;
- `ClaudeRemoteControlAtStartupCanaryTests.cs`;
- `ClaudeRemoteControlMenuCanaryTests.cs`.

Antiphon.Tests links only `tests/Shared/*`, not ClSession or the canaries (`Antiphon.Tests.csproj`
lines 51-179). Concrete scenario:
1. S1c-delivery-oracles adds `LiveClaudeDeliveryEvidence` and the canary computes it.
2. The canary keeps `ClaudeSubmitContractHarness.DonePattern` as its actual pass condition.
3. CP-19 is green, because it tests the helper with a fake Enter-lost capture.
4. The Agents.Pty.Tests compile is never checked before native acceptance.
5. Native CP-5 then passes on the screen pattern whenever the live turn succeeds.

The Mutation PC "accept screen echo without Enter (V-3d)" also mutates only the helper.

The same shape applies elsewhere:
- ClSession could still resolve PATH `cl` while CP-17 passes. The plan wants CP-17 to prove
  C680 and ClSession are wired, and it cannot.
- The startup canary could keep `SpecialFolder.UserProfile` (lines 365, 376) while CP-18 passes.
- `Console.WriteLine("ARM SCREEN:\n" + runner.SnapshotScreen())` could stay unrouted while CP-20
  passes.

**Why:** the CARD-0585 rule says a witness that cannot go red for the change it credits is a
stub. There is also a second gap: a compile break in Agents.Pty.Tests is first seen in the paid
native window, and only an unlisted build would catch it earlier.

**Fix:**
- Give each S1c slice that touches Agents.Pty.Tests a portable row that builds
  `tests/Antiphon.Agents.Pty.Tests` (net9.0, no Windows TFM, so it builds on server2).
- In that row, run a new Unit class inside Agents.Pty.Tests (for example
  `LiveClaudeCallerWiringTests`). It must call the **canary-side** entry points with fake inputs:
  - `ClSession` lane-mode resolution against a fake PATH containing `cl.exe` / `cl.bat`;
  - the startup/menu sandbox path resolver under a fake CLAUDE_CONFIG_DIR;
  - the harness verdict function fed an Enter-lost capture;
  - the canary print/assert helpers fed a sentinel.
- Where a call site cannot be invoked without ConPTY, add a structural witness over the named
  canary files: no `SnapshotScreen()` / `Console.WriteLine` / assertion message outside the
  sanitizer, and no `DonePattern` verdict. Give it its own Mutation PC.
- State the C680 wiring witness separately, because C680 is in Antiphon.Tests.

**Why:** a self-compare check cannot go red.

### D-3: The sanitizer witness passes on absence alone and cannot see the real row sinks it claims

**Where:** sanitizer paragraph ("verify they never occur in row console.log, TRX, receipts or
public summaries"); V-3e EvidenceIsSanitized / RowArtifactsAreSanitized; CP-20.

**Failure 1:** the oracle is "inspect actual console/TRX/receipt/public output bytes for
absence". The check is satisfied when:
- the seeded path never executed;
- the sink captured nothing;
- the sanitizer suppresses all output.

**Failure 2:** a test cannot inspect the TRX or `rows/<CP>/console.log` of the checkpoint run it
is executing in, because they are written after it ends. CP-20 is an Antiphon.Tests class that
cannot reach the Agents.Pty.Tests print sites (D-1). So "row console/TRX" can only mean a fake
in-process writer.

**Fix:**
- Each sentinel case also emits a benign per-case presence marker through the same path. Require
  the marker to be present and the sentinel absent in the same bytes, which is the positive
  control.
- Prove the real row sinks in one of two ways:
  - S1c-sanitization launches a nested owned test-host or checkpoint child over a fake-backed
    canary row and scans its emitted TRX/console;
  - or move the scan into the S1b wrapper as a post-run gate over the real row artifacts, with
    its own V-2 case, so that a found sentinel gives INVALID/20 and the result is never published.
- Seed through success, assertion and SkipTestException paths, as the plan already says.

### D-4: Mandatory `--setting-sources ""` changes CP-6's production-argv premise, and the settings attestation targets a source the CLI no longer loads while omitting one it always loads

**Where:**
- Seams ¶2: `--setting-sources "" excludes ambient user/project settings` for **every** core
  launch, "the control … with no --settings file";
- Seams ¶4 projection;
- V-3b SettingsProjectionDetectsDrift ("User settings edit without revision bump invalidates
  projection");
- V-5b UnknownSettingsRefuseReuse.

**Failure 1:** `ClaudeRemoteControlAtStartupCanaryTests` defines the control as the "current
Antiphon-like argv". The off case asserts the `--settings` overlay "must not replace
user/project settings", via the `permission-mode` / `atis-latch` JSONL checks at lines 106-112.
Production ApplyOff does not pass `--setting-sources ""`.

With the mandated flag:
- CP-6 qualifies an argv that production never uses.
- The "keeps user/project settings" assertions lose their subject: there are no user/project
  sources left to keep.
- Precedence between the overlay and loaded user, project or local settings is never exercised.

So green CP-6 credits ApplyOff from a different launch shape.

**Failure 2:** with sources empty, `<configDir>/settings.json` is not loaded. A witness that edits
user settings proves the projection reads a file that does not affect the run, which is the
"attestation reads the wrong file" case. Meanwhile the projection list never names two sources
the CLI keeps loading whatever `--setting-sources` says:
- the OS-level **managed policy settings** file;
- `<configDir>/.claude.json` global state.

Either can change remote-control or permission behaviour without changing the attested digest.

**Fix:**
- Isolate by a lane-owned CLAUDE_CONFIG_DIR plus an owned cwd and its ancestry scan, which
  already makes the user and project sources lane-owned.
- Keep the production setting-source set for CP-6/C514, or else add an argv-parity witness
  against the production ApplyOff/launch builder that records each deliberate difference.
- Make the projection enumerate the sources the attested CLI actually loads in lane mode,
  including the managed policy path and `.claude.json` keys.
- Put the drift witness on a source that is loaded.
