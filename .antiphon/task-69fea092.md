## Defects

### D-1: release sends TERM to any live pid in the live-probe file, including a pid that has been reaped and reused
- Where: `scripts/c590-remote.sh:4348` (`c849_fixture_reap_probe`: `kill "$pid"` runs whenever `/proc/<pid>` is live and not a zombie; only `kill -9` checks `jobs -pr`). The entries come from `c849_fixture_publish_live_probe`. Nothing removes an entry after its probe has been `wait`ed. Only `c849_fixture_clear_live_probes` drops the file, and that runs at the end of the barrier or lock phase.
- Failure: in `c849_fixture_race_lock_probe` (`:4497`), `wait "$holder" && wait "$waiter"` reaps the shared-generation probes, and their lines stay in `.fixture-live-probes`. The private holder then fails to arrive within 30 s (`FixtureNuGetLockHolderFailed`), or TERM/INT arrives during the private generation. `write_result` then hits the EXIT trap, then `c849_fixture_finalize` (`:5468`), then `release_live_probes`. For each shared line, `probe_proven` fails because the `--rm` container is gone, and `reap_probe <old pid>` runs. If the kernel has reused that pid, the unrelated process gets SIGTERM. The same applies, with a shorter window, to the pid already `wait`ed in `c849_fixture_wait_slot_markers` and to `wait "$a" ||` in the barrier. This is not a remote case on this fleet. `pid_max` is 32768, and this runner allocated about 1,500 pids in 10 s, so the counter wraps roughly every 3–4 minutes. The fixture runs as `mc` on the host, so any mc-owned process is in range, including the runner's builds and session processes.
- Repro (no Docker): extract `c849_fixture_probe_exited`, `c849_fixture_job_pid` and `c849_fixture_reap_probe` from bf45b89b4. Start `sleep 60` from another shell, so the pid is live but not in this shell's job table, and call `c849_fixture_reap_probe <pid>`. Result: `KILL <pid>`, and the process is dead. The round-2 witness `c1192_reap_witness` (`c1192-workspace-contract.sh:4315`) even states that a live pid from another shell "is signalled with TERM". It asserts only that `-9` is not sent.
- Second effect, same root: the same reaped lines go through `c849_fixture_note_unproven_probe` and write `foreign: left untouched container c849-<RUN>-lock-holder-shared` (or `restore-p2` after a slot exit 4) into residue and the ledger. That container was this run's own, and it is already gone. The diagnosis survives because WROTE=1, but the ledger names a foreign container that never existed.
- Why: this is a wrong-target kill on the production host. Round 1's A-4 asked for "only kill pids still listed by jobs -pr". Round 2 applied that to `-9` only.
- Fix: send TERM and KILL only while `c849_fixture_job_pid` lists the pid. Better still, remove a probe's line, or mark it waited, as soon as the parent `wait`s it. For an unproven line, check `c849_fixture_resource_state container <cid>` first. If the container is absent (1), treat it as already gone, not foreign. Witness: a reaped probe whose pid is held by a non-job `sleep` must get no signal at all.

### D-2: a probe whose `docker run` is still in flight when a refusal or signal arrives is never released, and its container can hold a build slot indefinitely
- Where: `scripts/c590-remote.sh:3225-3251` (`c849_fixture_launch`: the probe is published only from the in-loop branch; the loop gives up after 200 × 0.05 s, and the after-`wait` fallback records the id but never publishes), `:4398-4414` (release reads only `.fixture-live-probes`, then clears it), and `:5422` (finalize's `consumer_release`: "an unacquired roster entry is not cleanup authority", so a probe with no `.fixture-id-<name>` yet gets no kill and no residue).
- Failure: both restore probes start together. p1 refuses fast, for example on the name collision that round 1's D-1 was about: `helper_lookup` returns before any `docker run`. At that moment p2 is usually inside `docker run`, with an empty cidfile and nothing published. `wait_slot_markers` returns 1, release finds no p2 line, clears the file, and `write_result FixtureRestoreBarrierFailed`. Finalize finds no p2 identity yet and returns 0 for it, and the parent exits. p2's container keeps running. It waits for a slot (up to 45 min), takes it, writes `slot-held`, and loops forever on `while [ ! -e /fixture/race/go ]` (`driver.sh`). `build-slot.ps1`'s renew thread keeps that lease alive, and the lease line appears in `race-p2.log` only after the parent has already DELETEd the leases. The result is one host build slot gone until someone removes the container by hand. The 10 s cap makes this worse: any create slower than about 10 s is never published at all, not even later. Round 1 tracked by name immediately, so it did not have this gap (it had the wrong-target one instead).
- Repro (fake Docker, scratch copy of bf45b89b4's harness): the fake `docker_run_payload` creates an empty cidfile for `restore-p2` and sleeps 2 s before writing the id. Plant a foreign `c849-<RUN>-restore-p1` and run `c1192_slot_barrier`. Result: `d2-diagnosis=FixtureRestoreBarrierFailed`. When the barrier returns, `containers/` still holds `c849-c1192fixture0001-restore-p2`, the order log has no `kill <p2 cid>`, and `.fixture-live-probes` is empty. The harness's own `c1192_kill_jobs` is what removes p2 later. The fixture never does.
- Why: the brief names starving live tasks and reaching beyond the documented 45-minute bound as defects. This is an indefinite slot hold on an ordinary refusal path.
- Fix: release has to cover every launched probe pid, not only the published ones. For example, for each probe pid (`$a`/`$b`/holder/waiter) that is still a job but has no line, wait a bounded time for it to publish or exit. Drop the 200-spin cap and poll the cidfile until docker exits. Give the probe a stop marker that the launch loop checks, so it kills its own recorded cid. Anything still unpublished at the bound goes to residue as `unproven in-flight probe <name>`, so finalization fails closed and says why. Witness: the in-flight repro above must end with p2 killed by cid, or with p2 in residue.

### D-3: the new behavioural witness `C849_Refused_launch_keeps_a_foreign_container_and_signals_release_proven_cids` is nondeterministic
- Where: `scripts/fixtures/c1192-workspace-contract.sh:4197-4198` (`printf '%s\n' "$traps" | grep -qx …` under `set -euo pipefail`, `:7`), and the INT leg of `c1192_signal_witness`.
- Failure, observed on bf45b89b4 with an unmodified harness, plus a scratch copy that only adds trace lines:
  - (a) `signal-TERM-installed=0`. bash line-buffers stdout, so `printf` writes line by line. `grep -q` exits on the first match, the next `printf` write gets SIGPIPE, and pipefail turns the check into a false negative. In isolation, 8 parallel loops of 3,000 gave 4 false negatives. It also showed up once in 48 harness runs.
  - (b) `signal-INT-exit=2` with `DIAGNOSIS=FixtureBuildSlotTimeout`. My tip run made while the pin rows were running gave this, and so did 2 of about 72 runs under parallel load. A trace showed INT sent to the barrier shell with its trap installed (both probes already published), no `c849_fixture_on_signal INT` entry, and the barrier falling through to its 30 s deadline. The INT was not acted on. I did not find the root cause. A plain `x=$(sleep)` loop runs the trap every time, so this is not the simple command-substitution case. It needs a Debug pass, because a targeted `kill -INT` of the real fixture could be lost the same way. TERM was 143 in every run.
  - In these runs the C# test is red about 1 in 25–50 times under load, so it would flake the nightly and qualification lanes.
- Fix: (a) use `grep -qx … <<<"$traps"`, or `[[ $'\n'"$traps"$'\n' == *$'\n'"trap …"$'\n'* ]]`. (b) Find out why INT is dropped. Until then, send INT only after a marker the handler cannot race, or retry the send until the handler's trace appears, and do not report it green on one sample. Rerun the class row 20× under load before calling it deterministic.

## Advisories (no Review rerun needed for these alone)
- A-1: a metadata-write refusal in launch (`:3245-3249`) deletes the cidfile and returns 2 without recording the id in residue. For `create` or `run -d`, the container this run created is forgotten. This predates round 2 (round 1 behaved the same). Record the id in residue before removing the cidfile.
- A-2: a TERM/INT that arrives while the EXIT trap is finalizing runs `on_signal` and exits mid-finalization, with EXIT already cleared. Volumes can then remain without a residue line, and the process exit (143) disagrees with the receipt (`exit 2`). Run `trap '' INT TERM` at the start of the EXIT handler. This predates round 2.
- A-3: SIGHUP is still untrapped (round 1 A-5). p3's foreground launch can now be interrupted at its `wait`, but p3 is untracked, so a signal during p3 leaves its container to finalize's id path. That path has no fingerprint yet, so the container goes to residue: fail-closed, but it stays.
- A-4: the slot deadline uses `date +%s`, which is wall clock. A forward clock step ends the wait early with exit 4, and a backward step lengthens it. `/proc/uptime` or bash `EPOCHREALTIME` deltas would be safer. Low risk.
- A-5 (slot protocol, as the brief asked): `c849_lock` (a host flock) serializes fixtures that share a root. Other build-slot consumers never hold one slot while waiting for another. With capacity 4 there is no deadlock: holding one slot idle while waiting for the second is bounded at 45 minutes, and that is documented. Recommendation: a shorter wait for the second grant (for example 10 minutes) once the first is held, so a 4/4-busy host loses at most about 10 minutes of one slot. This is the operator's choice, not a defect. D-2 is the unbounded case.
