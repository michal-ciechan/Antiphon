## Advisories

**A-1 (PC-1 kill expectation is wrong).** The owed PC-1 says the witness "must fail because feature.txt is absent or is not the rewritten bytes" under a mutant that skips the hash compare in `CustodyOf` and in `RemovalApproval.RejectChanged`. With that mutant the witness still goes red, but at `result.Residue.ShouldBe("set_aside_content_changed")` with actual `tracked_bytes_changed`: after `CustodyOf` passes, the post-move `TrackedBytesAsync(aside, ..., empty map)` at `:223` re-reads the rewritten blob fresh, `git hash-object` confirms the mismatch, and `RestoreRegisteredTreeAsync` puts the tree back with the file intact. The mutant never reaches the delete. The Mutation brief should expect the residue assertion as the kill, or widen the mutant to also skip the post-move tracked-bytes read (then the delete runs and the `RejectChanged` mutant lets the file go, which is the stated expectation). Not a code defect; no rerun.

**A-2 (negligible).** On a pass-2 stamp miss `EntryManifest` calls `ReadReceipt` and so also computes an unused SHA-1; `RegularFileHash` would do. Only entries whose stamp changed between the two passes pay it.

**N-1 (behaviour note, decision-accepted).** A rewrite that keeps length and mtime inside the receipt-to-move window now moves the tree aside and restores it (`set_aside_content_changed`, restore asserted by the witness) where base refused in place (`tracked_bytes_changed` / `source_changed`). The decision document's phrase "set-aside left in place" is imprecise: the tree is put back and the record cleared. The retry schedule is unchanged (a cleared set-aside is a fresh bind on the next due tick).
