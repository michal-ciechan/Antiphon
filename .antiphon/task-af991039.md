### D-1 (blocker, acceptance gap, introduced): the phone-home lane never sends `ifNoneMatch` in production
- Where: `server/Infrastructure/Agents/SessionRunner/PhoneHomeRunnerClient.cs:97-98` (`_bufferHold`/`_snapshotHold` are instance fields) with `server/Infrastructure/Agents/SessionRunner/PhoneHomeRunnerDirectory.cs:169` (`Resolve` returns `new PhoneHomeRunnerClient(live, ...)` on every call) and `server/Infrastructure/Agents/SessionRunner/RoutingSessionRunnerClient.cs:125-134` (`Route` resolves per read; `RunnerTerminalSession`, `RunnerClaudeAdapter`, `AgentSessionRuntime` all hold the routing singleton; `AgentSessionRuntime.cs:2128` also resolves per call).
- Failure: every 50 ms/250 ms/500 ms buffer or snapshot poll against a phone-home runner (the server2 fleet) runs on a fresh client whose hold is empty, so `match` is always null, the frame never carries `ifNoneMatch`, the runner never answers `notModified`, and the server parses the full body on every poll exactly as at base. The card's "the server sends If-None-Match" holds only for the HTTP lane (`PhoneHomeRunnerDirectory` captures one `SessionRunnerHttpClient` instance as `_local`, Program.cs:371-372, so that hold does persist).
- Why: the hold must live as long as the runner connection, not the per-call client. `PhoneHomeLiveConnection` already is that long-lived object (it carries `Capabilities`).
- Fix: move the two `PtyReadHold`s onto `PhoneHomeLiveConnection` (or cache one `PhoneHomeRunnerClient` per live connection in the directory), and add a witness that drives two reads through `PhoneHomeRunnerDirectory.Resolve`/`RoutingSessionRunnerClient` (two separate `Resolve` calls on one live connection) and asserts the second frame carries `ifNoneMatch`. The existing `PtyConditionalReadClientTests.Phone_home_reuses_the_held_body_only_when_the_runner_advertises_it` constructs one client for both calls, so it cannot go red against the production wiring.
- Not a safety regression: the phone-home behaviour at the tip is byte-for-byte today's full body.
