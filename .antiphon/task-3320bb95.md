### 2. The retained-wait design against master

**Unselected Y and later Z:**

- The cleanup rotates the action and clears the selection. The next grant names W's new key.
- `ApplyCapacityHoldAsync` (`:5557-5573`) then picks the unkeyed held row.
- The `selected` set (`:5579-5593`) and the redeem then deliver on the same wait.
- Later input behaves the same way, because the wait is still unfinished and still found by
  `SessionId` (`:5545-5552`).

**No cycling:** an empty wait is excluded before `Take(batch)`. An outstanding grant whose demand is
lost is released to Ready once, and later empty ticks find no grant to release.

The release keeps `ActionKey`, and that makes a known race benign:

1. A concurrent flush stamps Z under the still-held key.
2. The flush's `RedeemAsync` refuses `grant-mismatch`.
3. Z stays linked to the current action, so it counts as demand on the next tick.

**Standing half:**

- S3-A stamps `SessionId` and `SessionStartedAt` in the reservation (`CapacityRecoveryService.cs:396-399`;
  `AgentControlService.cs:857`, `:1032`).
- The model-hold registration still lacks generation fields (`AgentSupervisorService.cs:434-445`).
- The D-3 table is correct.

**Lock order:** gate `WaitAsync(0)`, then message `NOWAIT` with the detach, then the provider
try-lock, then the wait CAS.

- The writers that take the provider lock first are `PrepareNextAttemptOnAsync` (`:1480-1515`) and
  `BumpWaveOnAsync`. They block on the message row only while the cleanup's try-lock fails and rolls
  back. There is no deadlock.
- The demand-loss branch only reads queue rows under the provider lock (MVCC).

**Conditional updates:** `Version` is not an EF concurrency token, so the explicit CAS is required, and
the plan says so. `DeferResumeAbsenceAsync` is a real writer that resurrects rows
(`ResumeReceipt.cs:120-131`) and is covered by V-3.

**Restart mid-cleanup:** each candidate runs in one transaction. A crash rolls it back, and the next
tick rediscovers it.
