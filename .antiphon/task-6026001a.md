## Per fix

**A. TranscriptTailer.LocateAsync / EvaluateCandidates**
- The full scan covers two things: the exact id in every project dir, and C1–C4 over every `*.jsonl`. It now backs off from 250 ms, doubling to 5 s (`MaxFullScanInterval`) while nothing relevant changes. It drops back to 250 ms on any relevant change: a file appearing or vanishing, an undecided candidate changing, or an input-log append.
- A cheap watch runs every poll and brings the full scan forward to the next poll when something moves. It looks at:
  - the `SessionInputLog.Version`
  - the mtime of the root, the cwd's project dir (Claude's name: non-alphanumerics become `-`) and every dir holding a cwd-matched candidate
  - length and mtime of up to 64 undecided candidates (cwd still unknown, or C4 not yet proven).
- The exact `<id>.jsonl` is still checked in the cwd's project dir on every poll.
- Fault judgement (CARD-0073/0101/0181 refusal and no-candidates reports, UnboundReason) still runs every poll on the latest verdict. Its timing keeps 250 ms resolution; the verdict it reads is at most one full-scan interval old. The root-fault poll counting is unchanged.
- Files whose recorded cwd is known to be another project get no stat at all (before, `GetLastWriteTimeUtc` was 12% of the trace). Every other file gets one FileInfo stat whose (length, mtime) lets the probe skip an unchanged file without opening it.
- I did not use timestamps carried by the directory enumeration (`FileSystemEnumerable`): on NTFS a directory entry can hold stale size and time for a file that another process keeps open, and a skip based on stale data could miss a qualifying append. Because of that, operator requirement 4 (benchmark the fastest way to read timestamps) was not run.

**B. TranscriptCandidateProbe / SessionInputLog / PromptSubmissionMatch**
- The probe re-runs C4 only when its retained prompts changed or the input log's version changed. The verdict depends only on those two, so it is unchanged.
- SessionInputLog caches the normalized buffer, and the cache is cleared on every append. It uses the new `PromptSubmissionMatch.IsConfirmedByNormalized(body, NormalizedRecord)`, which follows the same rule.
- `IsConfirmedBy(string, string)`, which the server path uses, now shares the same `ContainsNeedle` code. A cross-check test (`Normalized_record_overload_matches_the_string_overload`) confirms the two overloads agree.

**C. SessionCpuWatchdogService**
- The tailer now keeps `TranscriptWorkingState.WorkingAccumulator` up to date per entry. `Classify` is the same fold, and a randomized test checks the two agree at every step.
- The watchdog reads `runtime.GetWorkingVerdict(id)`, so it no longer copies and reclassifies a snapshot. Codex and Grok tailers fall back to `Classify(Snapshot())` through a default interface method.
- The gates and their order are unchanged. I did not do the CPU-first reorder, because it would change the kill window: on a cool sample with an unknown idle state, the detector can neither keep nor drop its baseline faithfully, so an idle-at-window-start check would be lost.

**D. HostStatsSamplerService.ReadProcesses**
- Not changed. It runs every 5 s (`HostStats:IntervalMs`). Per session it reads the child and the pty-host: `Process.GetProcessById` + `WorkingSet64` + the CPU probe.
- On Windows, `GetProcessById` enumerates every process on the system for each call. One snapshot per tick would be the fix, but I could not verify that from Linux, so it is reported only, with no card filed.

## Measured counts (Linux, fake time; red value → value at the tip)

- W1, an unbound session with an unchanged root, 240 polls over 61 s: 240 full scans (one per poll) → at most 21 (the asserted bound).
- W2, an unchanged C4-refused candidate over 120 more polls: 258 C4 match queries → 18, which does not grow, and zero new file opens. Touching the file causes exactly 1 new open and a C4 re-check.
- W3, 50 queries after one append: 50 buffer normalizations → 1, and one more after the next append.
- W4, watchdog sweeps: 4 transcript snapshots → 0. An idle session with hot CPU is still killed, and a working session is never killed.

## Worst-case bind latency

| Case | Worst case |
|---|---|
| Exact id in the cwd's project dir | ≤ 1 poll (250 ms), as before |
| New forked file in the cwd's project dir or in a dir that already holds a cwd-matched candidate | ≤ 1 poll (test: 1–2 polls) |
| A watched undecided candidate becomes C4-true after an append, or after new input | ≤ 1 poll |
| Anything else (exact or forked file in any other dir, a C1 claim released, more than 64 undecided candidates) | ≤ 5 s + 1 poll |
