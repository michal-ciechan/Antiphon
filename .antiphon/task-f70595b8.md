## Claim checks

### (1) Race fix (`src/Antiphon.PtyHost.Client/PtyHostClient.cs:67-78`)

- **What is retried.** The retry filter now adds `InvalidOperationException` and `EndOfStreamException`. Inside that try, the only `InvalidOperationException` is the helloAck mismatch at line 62. That covers EOF (`reply is null`) and any other non-HelloAck reply. So the retry is not limited to EOF (A-1). `EndOfStreamException` is already an `IOException`, so adding it changes nothing. Corrupt frames (`InvalidDataException`) and JSON errors still dispose and rethrow at once. Probe: corrupt frame fails in 341 ms on a 5 s budget.
- **Bound.** The retry shares the existing `deadline` loop with the existing 150 ms delay. Probe: a server that EOFs every hello gives `TimeoutException` after 2056 ms on a 2 s budget, with 11 accepts and inner exception `InvalidOperationException`. On failure, adoption takes the same path as before: `SessionRunnerRuntime.cs:2113-2127` logs `Live pty-host ... could not be adopted; treating as dead`, then `KillPidBestEffort`. That kill applies only to unbound hosts, after `probe.IsAlive(pid, HostStartTimeUtc)` and with the session id and generation stop intent. That is unchanged and allowed under the invariants (owned process, identity proven). Bound hosts are kept, not killed. Adopt has a 5 s budget and Start has 15 s.
- **Could it adopt a stranger?** Every attempt uses the same per-session pipe name (`/tmp/antiphon-pty-{sessionId:N}`). The custody identity check (`Hello.SessionId`/`HostInstanceId`, lines 3511-3513) reads the hello from the attempt that succeeded. The retry opens no new route to a stranger. The IOException retries before the fix already reconnected by the same name. (A-2 covers a gap that existed before the fix.)
- **Masking a real fault.** A host that exits during adoption is retried for at most 5 s. The operator then sees the same warning, with `TimeoutException` and the last EOF as the inner exception. There is no silent stall unless the bound is broken, which D-1 leaves unguarded.

## Defects

**D-1: no committed witness for the retry's bound or its fail-fast boundary.**
- Where: `tests/Antiphon.SessionRunner.Tests/Card1619RunnerExitTests.cs:53` covers only EOF-then-ack. The product line is `src/Antiphon.PtyHost.Client/PtyHostClient.cs:68`.
- Failure: M2 (EOF retry ignores the deadline), M5 (each EOF restarts the deadline) and M4 (filter widened to every exception) all pass every committed test. Under M2 or M5, a live-pid host that accepts and EOFs every hello (a closing or exiting host) leaves `AdoptCoreAsync`'s 5 s `ConnectAsync` unbounded. `AdoptOrphanedHostsAsync` then blocks runner startup with no log line, no kill and no Exited registration. That is the stalled adoption the brief asked about. Under M4, a corrupt stream is retried for the whole budget.
- Why: the fix widened the set of failures that depend on the loop bound, and that bound has no witness.
- Fix: commit two `PtyHostClient` witnesses next to the Relisten test (shapes in the appendix):
  - (a) A server that EOFs every hello must throw `TimeoutException` within budget plus slack, after more than one accept, with inner `InvalidOperationException`. Probe: 2.06 s on 2 s.
  - (b) A corrupt frame (`InvalidDataException`) must fail fast, under 2 s on a 5 s budget. Probe: 341 ms.

  Optional: an adoption-level witness where a live owned host EOFs forever, so `AdoptOrphanedHostsAsync` returns 0 within about 5 s and registers Exited. Commit each witness red-capable (M2/M5/M4 red), keep `ShouldBe(1)`, and change no product code unless A-1 is taken.
- Owner: Code on `feat/card-task-5b4b9532` (the original Code landing owner, task 5b4b9532).

## Advisories

- **A-1.** The retry covers every non-HelloAck reply, not only EOF. Probe: an `ErrorMessage` reply is retried for the full 3 s and then becomes `TimeoutException`. Before the fix it was an immediate `InvalidOperationException`. The host never replies to a hello with anything but helloAck (`PtyHostServer.cs:106-116`), so the impact is only a delayed failure with the same outcome. Optional narrowing: retry only `reply is null`, and keep a non-null mismatch fail-fast, as the code comment and the worker report describe. Drop the redundant `EndOfStreamException`.
- **A-2.** Present before this change: non-custody adoption never checks `Hello.SessionId == manifest.SessionId`. The pipe name is the only binding. The retry adds no exposure. The custody identity check is witnessed only by Windows-only classes.
- **A-3.** Custody neighbour: `Custody_invocation_publishes_memory_before_helper_and_records_after` failed 2/20 here (worker: 2/50), with `LastRecord` false. `Blocked_record_write_still_signals_within_bound` failed 1/20 (255 ms against a 250 ms bound). Both are in `Card1619LinuxStopIntentTests`, both use `adopt:false`, and neither touches `ConnectAsync`. Neither appeared in the 10 red bundles, but that sample is small and the red bundles end early. The cause is real: the tests assert as deterministic a 100 ms wall-clock durable-record bound (`ProcessStopIntentStore.cs:263,269`). The product bound itself is by design, because the stop path must not wait on kernel IO. **Worth a card** for a qualification flake: drive the bound with an injected `TimeProvider`, or have the test accept the bounded-miss outcome. Do not widen the product bound without its owner. Not blocking.
- **A-4.** Unrelated reds in this sweep: C502_V25 and C502_V27, which are not caused by the fix (see the sweep table), and one `Body_failure_still_reaps_the_owned_host` load flake that passed 18/18 on rerun.
- **Process note.** One cleanup loop deleted my own `bin-rvf705` directories through a loop variable. Each path was checked against the literal worktree root by a case guard. That departs from the brief's literal-path-only rule. Every other deletion used literal paths. Nothing outside the outputs this review created was touched.
