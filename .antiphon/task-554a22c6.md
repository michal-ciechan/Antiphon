## Why two trap lines

One combined `trap` line cannot tell the handler which signal fired. The brief requires exit 130 for INT and 143 for TERM. The handler before this round always exited 143, including for INT. That is a required behaviour change.

`c849_fixture` installs three plain lines and no `eval`:

```
trap 'c849_fixture_on_signal INT' INT
trap 'c849_fixture_on_signal TERM' TERM
trap 'ec=$?; trap - EXIT; c849_fixture_exit "$ec"; exit "$ec"' EXIT
```

`c849_fixture_on_signal` clears INT and TERM, releases proven probes, and exits 130 for INT and 143 otherwise. The EXIT trap then finalizes volumes and keeps that code. C1189 and C1191 select the EXIT trap with `StartsWith("trap ")` and `EndsWith(" EXIT")`, and pin the INT and TERM lines by exact equality. C1189 also asserts the fixture does not contain `eval "trap `. C976 still sees exactly one `trap 'ec=$?;` line in the whole file.

Bash 5.2.15 does not inherit traps into a background subshell. The harness installs the plain trap lines inside the barrier shell by extracting them from `declare -f c849_fixture` and stripping `declare -f`'s trailing semicolon.

SIGHUP stays untrapped. That predates this change. A-5 and A-7 (SIGHUP, an unlogged lease, a SIGKILL driver) stay out of scope.

## D-1 proven-CID cleanup

`c849_fixture_launch` refuses a name that already exists and records nothing to delete. A live-probe line (`pid cid name`) is written only after a 64-hex id is recorded and `docker inspect` matches owner `c849-fixture`, `fixture-run` for this run, the probe role, and the name. Release re-checks that proof at kill time and then runs `docker kill` and `docker rm -f` on the id. An unproven name is residue plus a ledger line, and finalization exits 2 while residue remains. A name collision is never ownership.

Foreground p3 is not tracked, so release cannot kill the fixture shell.

This is a regression of this round's launch rewrite, fixed here. No other new defect was left open.
