**Verdict: defects found. Do not merge to rc.** The Linux pipe-drain fix works: the parent-death grandchild is now killed and the journal clears, and the mutants on that path go red. The new Windows tree walk, though, drops the start-time ordering guard that .NET's own `Kill(entireProcessTree)` has. On Windows that lets the walk kill unrelated processes (D-1). ## Defects

### D-1 (High, Windows stop path): stale parent ids pull in unrelated processes, which are then killed

- **Where:** `server/Infrastructure/Git/OwnedProcessTree.cs:18-42` (`Descendants`), `:143-163` (`WindowsParents`) and `:44-71` (`Kill`).
- **Failure:** `Descendants` treats any process whose recorded parent pid equals a pid in the set as a child. Windows never rewrites `th32ParentProcessID`. Take a live process S whose creator died, where that dead creator's pid value has since been reused by the owned git root (or by any captured descendant). S is captured, and so is its whole subtree. Its start ticks are read from S itself at snapshot time, so the kill-time check `StartTicks(pid) == ticks` passes and S is terminated. The root's own identity is never checked, and no parent-before-child ordering is required.
- **Concrete scenario:** the AppHost was started by a short-lived launcher (pid P) that has exited. Windows hands pid P to a land `git push`. The push hits `git_timeout`, and `TryKill` calls `OwnedProcessTree.Kill`. The walk finds the AppHost (parent P) and kills it, then walks and kills its children (session runner, dashboard, dcp). Only the server is skipped, because only `Environment.ProcessId` is excluded. Windows hands out freed pids quickly, and the creator pid of a long-lived process is exactly the kind of freed pid that gets reused, so this collision is not exotic.
- **Why it is a regression:** the code it replaces, .NET's Windows `Process.Kill(entireProcessTree: true)`, only accepts a child when `StartTime < child.StartTime && Id == child.ParentProcessId` (`IsParentOf`, using handle pairs). That is from the .NET source; I did not execute it here because this host is Linux. The Linux build's `IsParentOf` is `Id == ParentProcessId` only (IL inspected on .NET 9.0.10 on server2). That matches Linux, where parent ids stay live, and is why the new code is safe on Linux and unsafe on Windows. AGENTS.md / session-runtime-invariants require identity to be proven before any kill.
- **Fix:** take a creation time for every candidate, including the root (from the owned handle, or the journal's `StartTicks`). Accept a child only when its start time is at or after its parent's. Fail closed, meaning do not walk past a pid, when its start time cannot be read. The durable alternative is to put Windows git children in a Job Object and terminate the job. Add a pure witness: a stale parent id older than its parent is excluded, and so is its subtree.

### D-2 (Medium, test adequacy): the pid-reuse guard and the self-exclusion have no witness, and no seam exists to write one

- **Where:** `OwnedProcessTree.cs:66-70` (kill-time `StartTicks(pid) == ticks`), `:37` (`Environment.ProcessId` exclusion), `:79-141` (private static `StartTicks`, `Terminate`, `ParentByPid`).
- **Failure:** these mutants all **survived** the 13-test selection: M2 (drop the start-tick comparison), M3a (re-walk at kill time instead of using the snapshot), M7 (drop the server self-exclusion), M8 (one snapshot pass instead of four) and M9 (release the journal while the root is still alive). The brief's witness needs a fake descendant list where one pid now has different start ticks and must not be signalled. It cannot be written: the parent map, the tick read and the terminate call are not injectable, and `Descendants` takes no start times. So D-1 cannot be witnessed either.
- **Fix:** split the code into a pure planner, `Plan(parents, startTicks, rootPid, rootTicks)`, and an executor, `Execute(plan, readTicks, terminate)`, with both delegates injected. Witnesses: a reused pid is not signalled; a stale parent id is excluded (D-1); the self pid and the self subtree are excluded; a root identity mismatch walks nothing.

### D-3 (Low-Medium, Linux): an exited root is still walked by its pid

- **Where:** `server/Infrastructure/Git/LandingGit.cs:287-293` calls `OwnedProcessTree.Kill` regardless of `HasExited`. `OwnedProcessTree.cs:44-66` walks `rootId` without verifying who owns it.
- **Failure:** on Linux, `HasExited == true` means the runtime has reaped the root, and its children were reparented when it exited. Any process with parent == `rootId` can therefore only belong to a stranger that reused the pid, and that stranger's children are killed. server2 has `pid_max` 32768, and it wrapped within minutes during this review. The window is small (cancellation racing the exit), but the walk can only do harm.
- **Fix:** on Linux, skip the walk when the root has exited. Or apply D-1's root start-tick check on every platform.

### D-4 (Low, diagnostics and failure-mode regression): a failed snapshot silently becomes a root-only kill

- **Where:** `OwnedProcessTree.cs:147,151` (`INVALID_HANDLE_VALUE` and `Process32First == false` return an empty map with no log line), `:102-113`, `:71-76` (a failed root kill is swallowed with no log).
- **Failure:** when the snapshot is empty because enumeration failed, only the root is killed (`entireProcessTree: false`). That is strictly weaker than the old `Kill(entireProcessTree: true)`. The worker's native triage says "`descendants=0` and the json remains ... `repository_child_tree_kill_snapshot_failed` will say so". That is false for both silent paths. "`descendants>0` and sleeper alive" also cannot tell a tick mismatch from access denied, because neither is logged.
- **Fix:** log a snapshot failure with `Marshal.GetLastWin32Error()`. Fall back to `root.Kill(entireProcessTree: true)` when the snapshot failed. Log each skipped pid with its reason (`reused`, `denied`).

## Advisories

- **A-1, kill order:** descendants are killed in dictionary order while the root is still alive, and the root is killed last. There is no SIGSTOP freeze; the .NET Unix implementation SIGSTOPs the root first. A live root can start a child after the snapshot. That child is not killed and holds the pipes, so the journal stays until it exits, by the same mechanism the detached-pipe rows witness. Kill the root first once the set is captured, or stop the set first.
- **A-2, TOCTOU:** `StartTicks(pid)` and `Terminate(pid)` each open a separate `Process`. The parent map is also read before the ticks, so a pid reused between those two reads records the stranger's ticks. Use one `Process` per pid and re-check the parent when the ticks are read.
- **A-3, identity helper (brief 1e):** the code uses `Process.StartTime` UTC ticks. That is the same identity domain as `RepositoryChildJournal.TryStartTicks`, `LandingGit.IsProcessAliveAsync` and `recover-repository-children.ps1`. It is **not** CARD-1619's boot-id plus /proc identity (`src/Antiphon.SessionRunner/LinuxProcessIdentity.cs`), which lives in the runner and is not referenced by the server. Boot id is unnecessary for an in-memory snapshot. Even so, this is a third private copy of the tick read; reuse the `IsProcessAliveAsync` logic.
- **A-4, attribution (brief 1f):** this is a library kill outside CARD-1619's `ProcessStopIntentStore`. Only stderr records it, and only the root pid and a count, not the pids killed. The old `Kill(entireProcessTree)` path behaved the same way. Consider logging the pid and tick list that was killed.
- **A-5, daemons (brief 1d):** a credential helper or fsmonitor daemon that is still a captured descendant at kill time is killed, the same as before. A daemon already reparented to init on Linux is not. On Windows nothing is reparented, so a "detached" daemon whose parent is still in the set is killed, which matches .NET. This is consistent with the old behaviour. There is no bound on tree size beyond the four passes, which is acceptable.
- **A-6, test-side kill:** the `finally` of `C448_ParentDeathGrandchildDoesNotKeepTheJournal` calls `KillHolder(pidFile)` on a pid the test has just proved dead. That runs `Kill(entireProcessTree: true)` with no start-identity check (helper at `LandingGitTests.cs:736-747`). Reuse within seconds is negligible, but recording the ticks next to the pid would remove it.
- **A-7, unbounded wait:** the background `process.WaitForExit()` in the handoff (`LandingGit.cs:226-240`) blocks a pool thread for as long as a root survives its kill, for example after access denied. The fence is correctly held for that time.
- **A-8, Windows skip (brief 3):** the `Skip.Test` on Windows for the new parent-death test is acceptable. `PR_SET_PDEATHSIG` is Linux-only, and the skip message names the two native rows.
  - **Owed native reruns** on a Windows checkout containing `c70d88af9`: `RepositoryMutationLeaseTests.C448_V28_CancellationAwaitsOwnedGitBeforeReleasingExclusion` and `LandingGitTests.C1076_RunOptionsBudgetKillsASlowPushAndClearsItsJournal`. Keep stderr.
  - `descendants=0` with the json remaining: the snapshot missed the tree. Per D-4 this may happen with no log line.
  - `descendants>0` with the sleeper alive: the terminate missed it, from a tick mismatch or access denied (not distinguishable today).
  - `descendants>0` with the sleeper dead and the json remaining: the problem is in the drain or delete path; read `CleanupFailure`.
  - These native runs cannot witness D-1; that needs the planner seam from D-2.

## Journal (brief 2)

Every exit path leaves either no record or a recoverable one:

- **Normal exit:** the record is removed (`Exited`) once the drain finishes.
- **Cancel or timeout that drains within the grace:** removed (`Exited`).
- **Handoff:** the record is removed only when both streams reach EOF and the root has exited. If the root is still alive, a background `WaitForExit` runs first and then removes it. If the root is still running after that, `retained_running_root` keeps the record.
- **Owner crash:** the record stays. The recovery script removes `dead`, `reused` or `completed` records with `-Execute -ConfirmDescendantsExited` and keeps `alive` and `unknown` ones.
- **`delete_failed`:** after the 2 s / 50 ms retry, `CleanupFailure=delete_failed` is saved and an `IOException` is thrown. The continuation catches it (`cleanup_continuation_failed`). The root is dead, so recovery removes the record after confirmation.

Nothing in this diff can make the fence permanent. The record is removed only after stream EOF, so it is never removed while a holder still has the pipes. M5 (skip the release) went red on the two detached-pipe rows.
