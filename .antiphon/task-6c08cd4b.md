## Defect R1: a boot-wedge relaunch replaces a pool delegate's process without restamping `PoolProviderProjectionJson`

- **Where:** `server/Application/Services/AgentTaskDispatcher.cs` `RelaunchWedgedAsync` (~6427-6575). It starts a new session for the same pool row. Its spec comes from `FinishDispatchedLaunchSpecAsync` → `BuildLaunchSpecAsync`, which re-reads the project's `ProviderEndpointsJson` at that moment (6966-6973). It restamps nothing: the only stamp is the cold-launch block at 5965, and the doc comment there says "does not delete the pool agent".
- **Failure:** Project P has no endpoint. A pool delegate is dispatched to a P task and gets stamp null. Its boot wedges. During the wedge window the operator sets F. The relaunch then starts a process with F, and that process holds the resolved key value in its env. The task completes and the row goes warm with stamp null. The operator then clears F. The next P task gets `taskWouldGet == null == stamp` and an equal inherit-list, so the predicate returns `true`. That task runs through proxy F with F's key, after the operator cleared F. This is the exact D1 shape ("launched with F kept serving after F was cleared"). The reverse also happens: stamp F, relaunch under F', map changed back to F, and the predicate matches a process routed to F'.
- **Why:** the repair's own invariant (plan D1 "restamped on every relaunch of the row"; `Agent.PoolProviderProjectionJson` doc "stamped at every cold launch and relaunch") does not hold on this relaunch path. No test drives the producer: every witness calls `InheritedEnvMatchesPool` with a hand-built stamp from `PoolFingerprint`. Nothing checks that the dispatcher writes the stamp from the map its launch actually used. A dispatch-level producer→recipient test is missing.
- **Fix:** derive the stamp from the same map read the launch spec uses, so stamp and process cannot diverge. One way: compute it inside `FinishDispatchedLaunchSpecAsync`/`BuildLaunchSpecAsync`, or pass the single read into both. Restamp it in `RelaunchWedgedAsync` for `agent.IsPoolDelegate`. Check the AgentControlService start/resume paths that can launch a pool delegate's session (`AgentControlService.cs` ~694, ~1110-1136). They resolve the project from the boardless pool row, so they project nothing while keeping the old stamp. Either retire the pool row there, or restamp it null. Add dispatcher-level witnesses: (1) a cold launch writes the fingerprint of the map it launched with; (2) a boot-wedge relaunch after the map changed restamps it, and the next task under the original map does not reuse the process.
- **Related disclosure:** the same split-read leaves a narrow time-of-check/time-of-use (TOCTOU) race on the ordinary path. The stamp reads the map inside the claim transaction (5967), and the spec re-reads it after commit (6125 → 6971). It is only exploitable with two operator edits in that window. The same fix closes it.
