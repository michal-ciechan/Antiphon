## Advisories (cards, never hold the land)

- **A-1:** Two writers to the real config remain in tests:
  - `ClaudeHarness.TrustDirectory` (E2E headed, opt-in) and `ClaudeTrustPromptCanaryTests` (live) still write the developer's real config.
  - If any ordinary E2E run ever launches the check interpreter, its runner launch seeds `ClaudeLaunchTrustSeed` into the runner's inherited `CLAUDE_CONFIG_DIR`/`~/.claude.json`. That is the real file outside this witness.

  Fix: also export `CLAUDE_CONFIG_DIR=<workspace>/claude` into the `IsolatedSessionRunner` environment.
- **A-2:** In topology B (server2 sidecar), the server-side `SeedClaudeTrust` writes to a config that the sidecar Claude never reads; the runner seed (CARD-1778 D-2) is the effective one. The server-side seed is dead weight there and could later be gated to the co-located topology. On the desktop it still primes the shared file, so it should not be removed outright.
- **A-3:** A blank or whitespace setting such as `Delegation__SpecialistClaudeConfigPath=` passes through as the config path. The seed then becomes `NoConfigFile` and is silently disabled, rather than falling back like the sibling settings, which floor blank values with `IsNullOrWhiteSpace`. The failure is safe because the launch-time answerer remains the fallback. Consider trimming or nulling blank values, requiring an absolute path, and adding a docs line.
- **A-4 (for Mutation):** A PC that drops `?? _settings.SpecialistClaudeConfigPath` makes the unit witnesses seed `DefaultConfigPath()`. On server2 that is the real `/state/claude/.claude.json`. Run those mutants with `CLAUDE_CONFIG_DIR` set to a temp directory.
