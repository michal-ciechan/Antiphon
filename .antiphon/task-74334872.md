## Defect (found): leftover state-init refuses the resume

Where: `scripts/c590-remote.sh` `c1008_bind_generation`, resume branch `ownedRemoved=false`, `runners=0` (added by `fa3e06f02`):

```
printf '%s' "$gen_owned" | jq -e --argjson saved "$C1008_RECORD" \
    'all(.[]; .Image==$saved.generation.imageId)' >/dev/null \
    || c1008_refuse RecycleGenerationMismatch
```

Failure: `gen_owned` is every project container except `build-slots`, so it includes the exited `state-init`. `generation.imageId` is the session-runner image (`antiphon-server2/session-testing:<sha12>`), while `state-init` runs `antiphon-server2/server:<sha12>` (`docker-compose.server2-runner.yml`). The removal loop removes the session-runner first (census order) and then state-init, journaling a receipt after each. A crash or a failed journal save between those two `docker rm` calls leaves phase `stopped`, `ownedRemoved=false`, no session-runner and one state-init. The resume then hits this leg and refuses `RecycleGenerationMismatch`, with no scripted way forward (the journal is partial, `-ResumeRecycle` is the only recovery, and the old runner is already gone). On the live rollout that is a stranded host needing manual cleanup.

Why the tests are green: `C1008HostFixture.Container()` gives every container `Image = sha256:aaaa…` and the fake `docker image inspect` answers the same id for any tag, so `C1008_Recycle_receipt_records_disk_and_partial_failure`'s `remove` boundary (which is exactly this scenario: `mv` fails once `removeReceipts` is non-empty, then `C1008_RESUME=1` expects exit 0 and three removals) passes. The S4 real-Docker fixture (`c1008-recycle-real-cases.mjs`) also uses one `image` for both services, so CP-9 would not catch it either. Confirmed by reading and by a jq simulation: with a leftover `{service: state-init, Image: sha256:server}` the `all(...)` returns false.

Regression: at `f2f1b684`/`origin/master` the same resume went straight to `c1008_reconcile_owned "$model"`, whose `c1008_owned_mounts` proved the state-init's three mounts (unchanged across generations) and whose `any($saved.owned[]; .Id==$c.Id and .Image==$c.Image and .Topology==$c.Topology)` already pins each leftover's Id, Image and Topology to the journal. S2 keeps that reconcile (now with the previous model, correct) but adds the wrong image leg in front of it.

Fix (Code): scope the leg to session-runner leftovers, e.g. `all(.[]; .Config.Labels["com.docker.compose.service"]!="session-runner" or .Image==$saved.generation.imageId)` (vacuous when `runners=0`, so effectively rely on the reconcile's per-container Id/Image/Topology match), or compare each leftover to the journaled `.owned[]` entry with the same `Id`. Make it detectable: give the host fixture's `state-init` a distinct image id (e.g. `sha256:cccc…`, with the fake `image inspect` answering the session-runner id only for `session-testing:*`) and, in the real-Docker fixture, a different `image` for `state-init`; then the `remove` boundary of `C1008_Recycle_receipt_records_disk_and_partial_failure` is red on the current shell and green after the fix. Also add the negative control for a leftover session-runner with a foreign image (the leg's real purpose). The S1-tip behaviour must come back: that resume exits 0 with three removals.
