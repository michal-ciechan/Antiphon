## D-1 (blocker): the native TRX reader never matches a real TRX, so the 60 s grace kill is dead code

- Where: `scripts/lib/nightly-owned-process.cs` `TryReadTrxSummary` (called by `ExecutionEvidenceFinished`, the only trigger for `Observation.CompletedButHung` / the grace kill).
- Failure: it takes `text.LastIndexOf("ResultSummary")`. Every TRX closes with `</ResultSummary>`, so that search lands on the closing tag. `outcome` reads as "" and `Counters` is not found, so the method returns false. Probe: `Add-Type -Path scripts/lib/nightly-owned-process.cs` on Linux pwsh, then reflection. The case's own fixture shape (`<ResultSummary outcome="Completed"><Counters total=119 .../></ResultSummary>`) and the real `scripts/fixtures/nightly/c487-probe/all.trx` with counters set to 119/119 both give `TryReadTrxSummary=False outcome='' total=-1` and `ExecutionEvidenceFinished=False`. The PowerShell `Test-NightlyExecutionFinished` gives True on the same files and diag.
- Effect on production: a completed-but-hung chunk still waits for the full launch watchdog (1801 s for g4), not 60 s. After that, the PowerShell post-hoc path labels the chunk `completed-but-hung` and the C# capture is still written, because `WriteHangCapture` runs on any `TimedOut`. So the next Windows run gets the diagnosis, but the commit/note/handoff claim "waits 60 s and then kills" is false.
- Why the tests missed it: `Test-Group4CompletedHang` exercises the PowerShell model `Invoke-NightlyCompletionGrace`, which production does not call (its only caller is the test). The C# side is covered only by text-presence asserts (`Contains('total ran:')`, `Contains('Observation.CompletedButHung = true')`, `IndexOf` order). Those cannot go red for a broken reader. Case 25/25 is green with the defect present.
- Fix: search for the opening tags (`LastIndexOf("<ResultSummary")`, then `"<Counters"` after it). Add an executable witness that `Add-Type`s `nightly-owned-process.cs` (this compiles on Linux pwsh) and calls `ExecutionEvidenceFinished` on the Group4 fixture and on a real-shape TRX. Expect: finished=true, and false for the low/no-stop/partial/Failed variants. It must be red at 89fd55cef. Either delete `Invoke-NightlyCompletionGrace` or drive the native loop instead of a PowerShell twin. Correct the investigation note.

## Advisories (cards, never hold a land)

- A-1 (grace size and status): the 60 s grace has not been measured. Once D-1 is fixed, a host that takes more than 60 s to flush after the TRX turns a former PASS into FAIL. Before arming the kill, record the exit latency from `ExecutionFinishedAtMilliseconds` for green chunks for one observe-only run. Then set the grace near 2x the measured p95 (docs/test-performance-standards.md). Keep the gate on `outcome=Completed` (this already implies failed=0) plus executed==total. Keep the result red. The reason is already distinct; add a dedicated summary field so the rc repair loop can tell a harness hang from a test failure without parsing reasons.
- A-2 (stale evidence): the native probe runs at t=0 and never re-probes after its first hit. The TRX path and diag dir are not cleared before launch. A direct `nightly-tests.ps1` rerun into the same `-LogRoot` would see the old Completed TRX and old diag, then kill the new host at 60 s. This is unreachable from `nightly-run` and release-cut, which nest a fresh run dir per run. Fix: ignore a TRX or diag older than launch.
- A-3: the outcome class moves from TIMEOUT to TESTS, so `publicationTerminal` changes from `timeout` to `failed-run`. This is intended. Consumers that key on `timeout` should know.
- A-4: instrument `DaemonLogRotationTests` first. It is Windows-only (skipped on Linux, which matches the failed repro), it starts a `pwsh.exe` daemon-style script, and it kills the tree only in its timeout catch. `BuildSlotEndToEndTests` holds at most 120 s and kills the entire tree, so it cannot explain 22 minutes. `BlockedParkWireTests` `git` without `using` (1067/1077) leaks handles rather than processes, unless the box's global git config starts fsmonitor or credential daemons; check that config.
