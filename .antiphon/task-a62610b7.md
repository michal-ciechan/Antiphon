## Defects

### D-1: Startup method 3 is vacuously green without its positive control

**Where:** "Scoped project and first roster", item 3, and its sentence demoting the control
("The control that assumes auto-connect is the host default is an explicitly inventoried
diagnostic, not a core requirement").

**Failure:** the test's only hard assertion is
`ClaudeRemoteControlAtStartupCanaryTests.Settings_file_prevents_auto_connect_and_keeps_startup_records`
asserting `evidence.Armed.ShouldBeFalse(...)` (lines 96-101). Everything else is weak:
- the `permission-mode` / `atis-latch` checks only run `if (evidence.JsonlPath is not null)`;
- the composer check is a screen check.

The observation window is `OverlayObserve` = 8 s. The Control method waits `BridgeAppear` = 15 s.

The method passes green when any of these is true:
- the account or host default is not auto-connect (the Control would skip for exactly this
  reason, lines 55-61);
- the bridge service is down or slow;
- remote-control is signed out;
- the bridge arrives between 8 s and 15 s.

In each case, nothing about `--settings remoteControlAtStartup:false` was exercised.

**Why:** the lane credits "settings-off prevents auto-connect", which is the production ApplyOff
premise, from a negative assertion that has no positive control in the same run and host epoch.

**Fix:**
- Make `Control_auto_connects_a_bridge_session_before_the_first_user` a required precondition
  row in the same lane run (it costs 0 prompts).
- If the control skips, method 3 is INCONCLUSIVE, never GREEN.
- Make method 3's window at least the control's measured bridge-appearance time (or the 15 s
  BridgeAppear), not 8 s.
- Make V-4 and CP-6 state the control dependency, and give S1c a witness where control-absent
  means inconclusive.

### D-2: CP-5 and CP-7 cannot go red for what V-4 credits them with (screen-only, no transcript UserPrompt, no bridge check)

**Where:** roster items 2 and 5, the V-4 oracle ("bridge-preserving menu conversion"), and the
CP-5/CP-7 Expect cells.

**Failure 1 (C514, CP-7):** `C514_Idle_menu_clearance_preserves_bridge_and_converts_prompt`
(`ClaudeRemoteControlMenuCanaryTests.cs:86-121`) has two problems:
- **Nothing checks the bridge after Esc.** Its last assertion is
  `ComposerDeliveryEvidence.FragmentIsVisible(s, token) || s.Contains(token)`. A token that was
  only typed into the composer and never submitted matches that predicate, so "converts prompt"
  passes even when Enter is lost.
- It **skips** (lines 101-104) when there is no pre-established bridge.

**Failure 2 (CP-5):** `ClaudeSubmitContractLiveTests` uses the
`ClaudeSubmitContractHarness.DonePattern` regex `" for \d+s"` over the screen
(`ClaudeSubmitContractTests.cs:65`). There is no transcript UserPrompt receipt.

**Why:**
- AGENTS.md and this review's contract say only a transcript-confirmed, complete UserPrompt
  counts as delivery evidence. A screen redraw is not.
- Today only C680 (roster item 1) meets that bar. The plan says "a screen echo alone must not
  become a new delivery verdict", but then credits two screen-only verdicts.

**Fix:**
- S1c must add transcript-confirmed complete-UserPrompt assertions to CP-5 and C514, keyed by the
  unique token and session id. C680's ExpectationDelivery/transcript path is the model to follow.
- S1c must also add a post-dismissal bridge assertion to C514: the same bridgeSessionId is still
  present in `~/.claude/sessions/<pid>.json` (or an equivalent).
- Add red witnesses for each: an Enter-lost fake and a bridge-dropped fake. Otherwise these are
  stub tests by the CARD-0585 rule.
- Until then, list CP-5 and CP-7 as diagnostic and not core credit.

### D-3: CP-5 launches real Claude with `--dangerously-skip-permissions` in the candidate checkout; the instruction/settings it loads are outside the fingerprint

**Where:** "Input fingerprint" (Live semantic witnesses / Test sources) and S1c scope.

**Failure:**
- `ClaudeSubmitContractHarness.LaunchReadyAsync` calls `runner.StartAsync(app, args, ...)` with
  no cwd. `PtyAgentRunner.LaunchCoreAsync` defaults to `Environment.CurrentDirectory`
  (`PtyAgentRunner.cs:143`).
- The checkpoint tool runs rows with `WorkingDirectory = repo` (`Program.cs:595`).
- So the live CLI starts at the repository root with permission bypass, and loads:
  - `CLAUDE.md` → `@AGENTS.md`;
  - every parent-directory CLAUDE.md above the worktree;
  - the project `.claude/settings.json`, including its PreToolUse hook
    `scripts/hooks/orchestrator-investigation-hook.mjs`;
  - `.claude/skills/**`;
  - user-level `~/.claude` settings/hooks (see D-5).

**False-green scenario:**
1. A docs-only rc commit changes AGENTS.md or `.claude/skills`. AGENTS.md is not in any MSBuild
   closure and is not named in the live roots.
2. The fingerprint stays equal, so an older green looks compatible.
3. Separately, the live model has write/exec permission inside the tree being qualified. That
   risks the source-clean attestation and violates "only owned scratch" (which the plan applies
   to ClaudeDangerousTests but not to this test).

**Fix:**
- S1c pins cwd to an owned temp directory for CP-5 (and every core row) and uses explicit
  `--setting-sources` / `--settings` the way C680 does.
- Until a row is hermetic, the fingerprint must include repository-root instruction/settings
  inputs (CLAUDE.md, AGENTS.md and its imports, `.claude/**`, `.mcp.json`) and must declare
  parent-directory and user-home instruction files as unknown, which disables reuse.
- Extend the rot test (V-1) beyond C# namespaces: any file the CLI loads from cwd ancestry or
  `.claude/` that falls outside the declared set must refuse.

### D-4: The CLI identity and "immutable owned copy" guard does not hold on the cl-wrapper route, and the lane has two resolution routes

**Where:** the Input fingerprint "CLI identity" row, and Guard details "CLI auto-update".

**Failure:**
- C680 resolves `claude.exe` straight from PATH (`ClaudeDialogWatchdogCanaryTests.cs:28,190-192`).
- The PTY rows use `ClSession.ResolveOrThrow() = ResolveCl() ?? ResolveClaude()`. `ResolveCl`
  searches the whole PATH for `cl.bat|cl.ps1|cl.cmd|cl.exe` before it looks for any claude
  (`ClSession.cs:21-38`).

As a result:
- An owned claude copy placed first on PATH is bypassed whenever any `cl.*` exists anywhere on
  PATH. The wrapper then re-resolves the installed, mutable, auto-updating claude.
- On a Visual Studio developer PATH, `cl.exe` is the MSVC compiler.

So:
- One lane run can execute two different Claude binaries.
- The plan's own rule "an unprovable wrapper chain is inconclusive" makes CP-5..7 permanently
  inconclusive on the wrapper-managed host D-3 recommends.
- A `--version` probe of the wrapper can report the version of a different binary than the one
  the test spawns.

**Fix:**
- S1c adds an explicit lane-owned executable seam, for example an `ANTIPHON_LIVE_CLAUDE_EXE`
  read by both ClSession and C680, which the lane wrapper sets to the attested immutable copy.
- Refuse (INCONCLUSIVE) when the resolved route differs from the attested path.
- Attest every route actually used, per row.
- Add a V-5 case where a wrapper is present but the owned copy is attested, so a mismatch refuses.

### D-5: The D-3 "dedicated test account/profile" conflicts with tests that hardcode the OS user profile; user-level settings/hooks are not isolated

**Where:** D-3, Effective non-secret configuration, External-state contract ("opaque
operator-maintained credential/profile revision").

**Failure:**
- `ClaudeRemoteControlAtStartupCanaryTests` reads and writes
  `Environment.SpecialFolder.UserProfile` paths directly (lines 365, 376, 544): `~/.claude.json`
  (it pre-trusts the sandbox there), `~/.claude/projects` and `~/.claude/sessions`.
- Product code and `ClaudeProjectTrust` honour `CLAUDE_CONFIG_DIR`. These tests do not.

Consequences:
- **Option 1, a CLAUDE_CONFIG_DIR test profile.** Trust seeding and session-file evidence look in
  the wrong home. Method 4 fails, which reads as RED. Method 3's `Armed=false` gets easier to
  reach, so the D-1 vacuous green gets worse.
- **Option 2, the runner OS user.** That is the profile shared with the operator's and the
  production fleet's Claude sessions on that host. The tests then race them on `~/.claude.json`
  writes, and the D-7 native lock does not serialize production sessions.
- **User-level settings leak in.** ClSession deliberately keeps user-level settings and hooks
  (`ClSession.cs` comment: user-level SessionStart hooks such as memsearch). Changes to them
  alter CP-5..7 behaviour.
- **The fingerprint can miss it.** It binds those settings only through an operator-maintained
  opaque revision. An edit without a revision bump keeps the fingerprint equal. Under the D-6
  bounded-reuse exception, that is a false green.

**Fix:**
- S1c makes the four PTY rows config-dir aware (one helper shared with `ClaudeProjectTrust`) and
  launches them with `--setting-sources ""` or a lane-owned settings file, so user hooks are
  excluded.
- Derive the profile revision mechanically from a projected, allowlisted, non-secret settings
  subset. Any unknown key disables reuse. Do not rely on a manual bump.
- Re-scope D-3 as a real choice (see the decision list).

### D-6: A mid-run provider or bridge outage reads RED (exit 1), not INCONCLUSIVE

**Where:** the Exit/outcome table and "Provider retry policy".

**Failure:** preflight passes, then the provider degrades.
- CP-5 `done.ShouldBeTrue` fails after 2 min.
- Method 4 `after.SessionFileBridgeId.ShouldNotBeNullOrWhiteSpace` fails.
- C680's dialog wait times out.

These are assertion failures "after setup was established", so the table makes them exit 1 RED
("Debug the exact failure"). The opposite also happens: the tests' setup-time
`SkipTestException`s ("TUI did not reach ready", "trust dialog did not clear", "bridge not
pre-established") are product or test failures as often as outages. The plan gives no rule for
splitting skip reasons. To the checkpoint receipt, skip and fail are both `row_failed`.

**Why:** the brief requires outages to read INCONCLUSIVE with a distinct exit code, never green
and never a code failure. The plan only meets this for preflight.

**Fix:**
- Classify after the run from evidence. Example: a transcript with a UserPrompt receipt followed
  by an API-error / overloaded / rate-limit record, or a failed post-failure availability
  re-probe, gives `20 INCONCLUSIVE/provider-outage`.
- Without such evidence, an assertion failure stays RED.
- Map skip reasons to typed setup outcomes through a closed table. An unknown skip reason is
  INCONCLUSIVE/unclassified, never RED and never GREEN.
- Add V-2 cases: mid-run outage after receipt, giving 20; and assertion red with a healthy
  provider, giving 1.

### D-7: The CP-4..7 checkpoint evidence bypasses the lane's sanitizer

**Where:** "Credentials …" ("default to sanitized metadata"), V-3 `EvidenceIsSanitized`, and
"Receipt" (private evidence).

**Failure:**
- The existing rows print raw screens unconditionally, for example
  `Console.WriteLine("ARM SCREEN:\n" + runner.SnapshotScreen())` at
  `ClaudeRemoteControlAtStartupCanaryTests.cs:161`, `LogEvidence`, and many
  `"Screen:\n" + SnapshotScreen()` assertion messages.
- The checkpoint tool keeps these in its TRX and `rows/<CP>/console.log`.
- A bridged screen can carry the claude.ai remote-control session link. That link is
  account-gated, but the plan itself classes it as sensitive.
- V-3 only proves the new lane outputs are sanitized, against a fake backend.

**Fix:**
- Treat the checkpoint row outputs of live rows as restricted diagnostics: private root, never
  copied into public summaries or committed reports.
- Have S1c redact bridge URLs and device codes at the test's print sites, or route them through
  one redaction helper.
- Extend V-3 so a seeded bridge-URL sentinel in a row console/TRX never reaches public outputs.

## Advisories (not blocking)

- **A-1, stale lock reason.** `Enter-ReleaseGateNativeLock` can return `stale-shared-lock`. Map it
  explicitly (INVALID or a dedicated subtype, never an implicit takeover) in the exit table and V-2.
- **A-2, live rows in the same closed table.** CP-4..7 (paid live) sit in the same closed
  `### Checkpoints` table as portable rows. A routine `run --plan` of the S1c-native group outside
  the wrapper would spend quota with no native lock. Put CP-4..7 in a separate lane manifest
  consumed only by `run-live-lane.ps1`, or have the wrapper refuse unless it holds the lock.
- **A-3, no S1 witness that Full is unchanged.** The plan says S1 leaves Full unchanged, but no
  S1 row proves that adding `Category("LiveClaude")` and `tests/live-lanes.json` changes neither
  `policyHash` nor the Full discovery census. Add an S1a assertion: census and required/excluded
  UID sets byte-identical before and after. V-11 only covers S3c.
- **A-4, S2a is too big for one slice.** S2a (closure, CLI/shim, native/runtime, config and
  external, 8 tests) is not one 30-60-minute slice. Split it into S2a-1 (repository closure,
  reusing the graph reader) and S2a-2 (CLI/runtime/config attestation). S1c similarly grows by
  D-1..D-5: plan it as at least three commissions (seams/oracles, red witnesses, native run).
- **A-5, `[Explicit]` with an OR filter.** CP-6/CP-7 target `[Explicit]` classes. TestDesign
  must confirm with real TRX that TUnit runs Explicit methods under the parenthesized-OR
  treenode filter. Exit 0 or `--list-tests` does not count, and a zero count is not red.
- **A-6, absent vs empty environment.** Per the OS-branch witness rule
  (`docs/testing-and-build.md#os-branch-witnesses`), V-2 `ChildEnvironmentIsScoped` must
  distinguish an absent key from an empty value. C680 relies on present-but-empty `CLAUDE_CODE_*`
  overrides.
- **A-7, waits.** These are test-owned deadlines; the lane adds no new operator-input wait:
  - C680 has a 6-minute body deadline;
  - the core lane has a 25-minute ceiling;
  - the preflight refuses before any TUI, so there is no wait for an operator login.

  With parking disabled, a delegate that asks the operator keeps its seat and has no automatic
  release deadline (CARD-1083). The plan states this correctly.
- **A-8, performance.** CP-4's 12-minute estimate leaves little room over the 509 s build plus
  106 s driver sample (n=1/n=3). The plan correctly labels these provisional and keeps the
  CARD-0680/1404 6-minute exception explicit. Nothing is over 30 minutes.
- **A-9, project lanes.** On "lanes for each isolated project", the plan is correct that
  project granularity does not work for Antiphon.Tests. Antiphon.Tests:
  - references server, SessionRunner, NightlyWatchdog, `tools/Antiphon.Checkpoints`, FakeLlmApi,
    DockerStack.Fixture and HostCleanup;
  - link-compiles files from Antiphon.SessionRunner.Tests and Antiphon.Agents.Pty.Tests
    (FakeHerdrServer, CodexStartupFixtures, …);
  - pulls in `scripts/lib/BuildDriverEnvironment.cs` through the server project;
  - its Scripts namespace executes `scripts/**` from the tree at runtime, which the MSBuild graph
    never sees.

  A per-project lane must therefore be per-namespace inside Antiphon.Tests, with runtime-script
  inputs declared. Until then, D-10's "unknown forces Full" has to stand.

## Which lanes can honestly claim "provably unaffected on a fingerprint hit"

**None of the live/provider lanes.** That includes the live-Claude core even after D-1..D-7 are
fixed, because remote model, bridge and quota are unversioned. The plan's D-6 already concedes
this, and does not make the "provably" claim.

**Candidates only after a qualified, complete closure:**
- pure client Vitest/lint with a locked dependency tree;
- hermetic script-contract fixtures whose script/interpreter/fixture closure is declared;
- frozen land-graph/definition evaluation.

Even for these, "unaffected" means "equal captured inputs", not proof.

**Must always run per candidate:**
- native Windows ConPTY/pty-host/session-runner;
- server/DB/git integration;
- E2E/browser;
- Docker/DinD/custody;
- installer/packaging;
- real-CLI stub lanes, until loopback-only routing is qualified;
- any Telegram live arm.
