# Review 6cd85b51: CARD-1076 LandingGit budget-kill drain bound (subject bef1beb0)

Reviewed source: feat/card-task-bef1beb0 @ 46c3d8b93a0bc31ea5840e5da803b29a958c5489 (red witness 48a24df44, fix 46c3d8b93), base rc/2026-10-27 070d35b80653d40d697e462e419414610be85d66. Host: server2 runner mirror (Linux).

Outcome: 2 defects. The budget-kill bound works, and the witness is green with no leaked sleeper. But the fix drops the descendant fence: the repository child journal is deleted while a provably live descendant of a mutating git command still holds the pipe. It also adds an unwitnessed deadline to the normal (non-killed) drain.

## Defects

### D-1: the child journal is cleared while a live descendant still holds the redirected pipe (new fail-open vs base)
- Where: server/Infrastructure/Git/LandingGit.cs:130 (`if (process.HasExited) journal?.Exited(process);` after ReleaseChildAsync abandons the streams at :175), and :826 (same in RunGitInputBytesAsync, the update-ref --stdin batch). tests/Antiphon.Tests/Infrastructure/LandingGitTests.cs:615 asserts this fail-open: the journal is empty while `HolderAlive` is true.
- Failure: a mutating land git command (push with a pre-push hook, rebase with post-rewrite/post-checkout, update-ref with reference-transaction) has a hook that leaves a reparented descendant holding stdout or stderr. When the budget fires, ReleaseChildAsync gives up after KillDrainGrace and the root has exited, so the journal record is deleted. The call throws git_timeout, the land fails and releases its lease, and `RepositoryChildJournal.FirstFencingAsync` finds no record. The next land is admitted while that descendant can still run git against the repository (refs, index, objects). If the server dies in that window, `recover-repository-children.ps1` has nothing to inspect.
- Why: the base kept the record until both streams drained (old comments: "Keep the standing journal until both streams drain; worker death in that interval must still fence admission"). RepositoryChildJournal.cs documents the same invariant: a Completed record fences because "a crash before the streams drained leaves descendants unproven", and "Only the owning invocation removes its journal after awaiting its child". The pipe drain is the only descendant proof this design has. The fix now removes the fence exactly when the descendant is proven alive. At the base, the same shape blocked: the land held its lease until EOF and admitted nothing.
- Fix: keep the prompt `git_timeout` return, but do not call `journal.Exited` when the streams were abandoned. Move the deletion into the abandon continuation: in ObserveAbandoned, run it on every completion state, not only OnlyOnFaulted, and capture a deleter that does not touch the disposed Process. The record is then removed only once the abandoned streams reach EOF; a server death before that leaves the record for recover-repository-children.ps1, as at the base. Apply the same change at :826. Flip the witness at :615 to assert the record is present while the holder lives, then kill the holder and poll with a bound until it clears. The Windows C1076_RunOptionsBudgetKillsASlowPushAndClearsItsJournal journal check at :576 needs the same bounded wait-for-clear, because its msys sleeper holds the pipe.

### D-2: new deadline on the normal-completion drain, unwitnessed and contrary to the brief's criterion
- Where: server/Infrastructure/Git/LandingGit.cs:122 (`await Task.WhenAll(output, error).WaitAsync(budget.Token);`, which replaces the base's unbounded post-exit drain).
- Failure: git exits 0 (for example a push whose remote ref already moved) while a hook or another descendant keeps stdout/stderr open past the remaining budget (5 min default, 20 min for remote-prep-push). The base waited for EOF and returned success. Now the result is discarded and git_timeout is thrown, turning a completed mutation into a failure. Through D-1 the journal is also cleared on this path, because the root has exited.
- Why: the brief requires the bound to apply only after the budget kill, never to a normally completing process. The Windows failure (pre-push `sleep 30`) is on the kill path; this line is not needed for it. No test exercises the root-exited-normally-while-holder-lives path.
- Fix: either restore the base unbounded drain after a normal exit, or keep the bound as a deliberate decision. If it stays, add a witness (root exits 0, holder keeps stdout past a short budget) that asserts the chosen outcome and that the journal stays per D-1.

## Checks requested by the brief
1. Output on the normal path: when the drain finishes inside the budget, all of stdout and stderr is read to EOF; nothing is truncated. The added deadline is D-2. `git gc --auto` daemonize closes stdio, and ServerGitProcess.DisableAutoMaintenance is applied, so gc is not the exposure. Hooks are.
2. Classification after the kill: git_timeout is still raised (`!ct.IsCancellationRequested && budget.IsCancellationRequested`), and partial output is discarded. A record is cleared only when the root handle has exited (`HasExited` guard; Exited also re-checks), but not only after descendants release (D-1). The surviving grandchild can do whatever its hook does to the repository after the call returns. At the base the call did not return, so the lease and fence held. That difference is D-1.
3. Handles and races: TryKill swallows InvalidOperationException and Win32Exception (the base Kill could throw out of the catch, so this is an improvement). There is no double dispose: ReleaseChildAsync disposes only its own CTSs, and `using var process` disposes once. Exit-vs-kill races are covered by HasExited plus the swallowed exception. The second, non-tree Kill is skipped when the root has already exited.
4. Callers and arithmetic: RunGitInputBytesAsync callers are cat-file --batch (:541, :665, read-only) and update-ref --stdin (:1069, mutating; D-1 applies). Its normal path is unchanged: CopyToAsync and ReadToEndAsync were already bound by the budget token. All ExecuteProcessAsync callers get D-2. No budget+grace addition exists: grace is its own fixed CTS, and `CancelAfter(options.Budget ?? DefaultBudget)` is unchanged from the base, including its behaviour with TimeSpan.MaxValue. Cancellation via ct still rethrows OperationCanceledException.
5. Witness: `[Timeout(60_000)]` wall cap, skipped on Windows, plain /bin/sh double fork, `sleep 20` self-limits, and KillHolder runs in `finally`. After both runs, `ps` showed no `sleep 20`/`sleep 30` processes. Measured elapsed: C1076_PIPE 4.18 s (2 s budget + 2 s grace), C1076_BUDGET 2.25 s. Red at 48a24df44 by construction (the base waits 20 s, failing both `< 15 s` and HolderAlive). I did not rerun the red; PCs stay pending for Mutation.

## Advisories
- A-1: abandoned ReadToEndAsync tasks keep the parent's pipe fds open until the holder exits. This is bounded by the holder's lifetime and acceptable. With D-1's fix they also carry the journal deletion.
- A-2: in the witness, if the call returns before the holder writes holder.pid, `int.Parse(File.ReadAllText(...))` throws: the test goes red rather than hanging, and the holder ends on its own after 20 s.
- A-3: a stream fault in the catch path (ReadToEndAsync throwing) still escapes before journal, NoteServerGit and git_timeout classification. This is the same as the base.
- Cleanup: the bin-r6cd output directories (about 32: server/, src/*/, tests/*/, tools/*/) are left in place, because the brief's cleanup rule forbids recursive deletion. They are gitignored, and the worktree is otherwise clean.
