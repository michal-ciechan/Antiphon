## Findings

### D-1 — a symlink of OneDrive\Backups is followed, and prune then deletes matching dumps there

Where: `scripts/postgres-snapshot.ps1` `Invoke-SnapshotPlainOneDriveCopy` (the `LinkType` check around the destination child) and `Update-SnapshotPlainRetention`. `Test-SnapshotPathInside` is lexical (`Path.GetFullPath`) and does not resolve a reparse point. The primary destination uses `Test-SnapshotContainsLink`, which refuses any reparse point on that directory or its parents. The OneDrive copy checks `LinkType` only on the child folder `Backups\antiphon-postgres`.

Failure: On Linux, with `OneDrive\Backups` as a symbolic link to an outside directory that already held `antiphon-postgres` (notes, a Hermes-named dump, and eight `antiphon-<UTC>.dump` files), `Invoke-SnapshotPlainOneDriveCopy` returned `state=ok`. The new plain dump was written through the link. Retention then removed the two oldest matching dumps in that outside folder (`antiphon-20261101T000000Z.dump` and `antiphon-20261102T000000Z.dump`). `notes.txt` and `hermes-backup.dump` stayed. A symbolic link of the child folder itself returned `state=failed` and wrote nothing outside. A missing `Backups` directory returned `state=missing` and created nothing.

Why: The tip commit says a junction or symlink still fails closed so the copy cannot leave `Backups`. That is true for the child folder and false for `Backups` itself. Filesystem calls follow the parent link. The lexical inside-check still sees `SyncRoot\Backups\antiphon-postgres`. Prune then lists `antiphon-*.dump` in the followed directory and deletes names that match `^antiphon-[0-9]{8}T[0-9]{6}Z\.dump$`. A Windows junction of `Backups` is the same shape and was not executed here.

Fix: Before creating the child, copying, or pruning, refuse when `Backups` or any parent of the destination child is a symbolic link or junction. Keep accepting a cloud-filter reparse whose `LinkType` is empty. On refusal, write nothing and delete nothing. Add a witness that a symlink (and, on Windows, a junction) of `Backups` returns failed, leaves the outside tree unchanged, and does not create `Backups` when it is absent.

### D-2 — verify-before-prune is not pinned

Where: `scripts/postgres-snapshot.ps1` `Invoke-SnapshotPlainPublish` calls `Update-SnapshotPlainRetention` only after the second `pg_restore --list`. `scripts/test-postgres-snapshot.ps1` `Test-PlainVerifyBeforePrune` calls `Get-SnapshotPruneSet -Verified $false` and `Test-SnapshotPlainVerified` directly. `Test-PlainPlan` asserts the plan text contains "prune only after the new file is verified". `Test-PlainOneDriveCopy` calls the copy function, not publish.

Failure: On a copy of the script, dropping `^` and `$` from `SnapshotPlainDumpPattern` made `Test-PlainRetention` fail (`plain retention ignores ciphertext names`, 4 passed, 1 failed, exit 1). Moving the `Update-SnapshotPlainRetention` call to before `$ready = ($list.Exit -eq 0)` left `PlainVerifyBeforePrune` 6 passed / 0 failed, `PlainPlan` 19 / 0, and `PlainOneDriveCopy` 46 / 0, all exit 0. The product tree was not edited.

Why: The current publish function does return before retention on dump, verify, and copy failure. The named witness does not execute that function, so it cannot go red when the call moves earlier. That is a missing acceptance for the prune-after-verify rule, not an advisory wording gap.

Fix: Add a witness that fails when retention runs before the second `pg_restore --list` succeeds, and that still fails closed when verification fails (nothing deleted). Keep the anchored-pattern witness.
