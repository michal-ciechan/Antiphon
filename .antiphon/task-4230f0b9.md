## A-1 (advisory): lazy print shows the DOM at read time, not poll time

When the DOM changes after the last failing poll and nothing re-polls, the FINAL message's first dump shows the DOM at the timeout instead of the DOM that poll saw. The second dump (onTimeout, the timeout DOM) is unchanged. Reproduced:
- c05b: fake timers advanced inside the callback; an app timer mutates the DOM in the advance that fires the timeout. Base shows `first` then `second`; tip shows `second` twice.
- c15: within(detached node) mutated by a timer (outside the MutationObserver).
- c16: async callback still pending while the DOM changes.
- c14: a poll error stored by user code and read later. The new guard case 1 deliberately pins this ('later', not 'present').

No repo test uses these patterns (the only advance-inside-waitFor is the guard itself). In the ordinary path MutationObserver re-polls on every change to the observed document, so the DOM at read time equals the DOM at poll time. A fix would need a DOM snapshot, which is the cost being removed. Suggested: one comment line in pollingElementError.ts, which today says "prints what the default prints", noting the print reflects the DOM at first read.

## A-2 (advisory): the final error's message becomes read-only

waitFor's onTimeout converts the accessor with `{value}` only, so the descriptor ends writable:false (base: writable:true). A strict-mode `err.message = ...` on a timed-out waitFor error would throw TypeError at tip only. Nothing does this: grep of client/src finds no message assignment, and vitest 4.1.0's serializer assigns to a clone. Cheap fix if wanted: on first read the getter redefines `message` as a writable data property holding the printed text.
