## Defects

Original Code landing owner: fd72b5eb-bdad-4e98-a6e1-df6d1a54979e.

### D-1 (regression): a listed name the walk will not handle is skipped silently, the marker is then removed, and the root leaks forever

- **Where:** `CheckpointNativeIo.Anchored.cs` ListAnchoredLinux, which drops names that fail `AnchoredDelete.EntryNameSafe(windows:false, ...)`. That check rejects `\` on Linux too. `CheckpointTempRootSweep.AnchoredInventory`, `CollectAnchored`, and the completion block at `CheckpointTempRootSweep.cs:181-187`. ListAnchoredWindows has the same skip-on-unsafe pattern.
- **Failure:** a root containing `plain.txt` and a file literally named `C:\Antiphon\x.txt`, a common Linux artifact of a mishandled Windows path.
  - Tip: inventory passes and DeleteBounded reports complete (5 bytes). The lock and marker are unlinked, then the root rmdir fails ENOTEMPTY and the receipt shows `delete-IOException=1`. The root is left holding only the backslash file. It has no marker, so every later sweep skips it as `marker-invalid` and the index entry is never unregistered.
  - Base 4563e525 on the same fixture: completed=1, root removed.
- **Why:** a name the anchored layer cannot process is treated as if it did not exist. The inventory under-counts and the custody marker is destroyed before the root is proven empty.
- **Fix:**
  - On Linux, accept every readdir name except `.` and `..` in ListAnchored, UnlinkAnchored and TruncateAnchored. Only `/` separates components, and unlinkat on a dirfd is safe for `\`.
  - On both platforms, make any name the layer still refuses throw from ListAnchored instead of being skipped. The inventory then returns incomplete and the marker survives.
  - Add a witness with a backslash-named file that is red at the tip.

### D-2 (fail-open, pre-existing, now in newly written code): truncation follows hard links and shrinks a file outside the root

- **Where:** `TruncateAnchoredLinux` and `TruncateAnchoredWindows` in `CheckpointNativeIo.Anchored.cs`, reached from `DeleteBounded` when `length > left`.
- **Failure:** `outside/foreign.bin` (1000 bytes), hard-linked as `root/payload.bin`, swept with MaxBytes=100. At the tip the foreign file is 900 bytes afterwards. Base gives the same result (900), so this predates the branch.
- **Why:** statx already fetches STATX_NLINK (it is in mask 0x3CF) but nothing checks it. Unlinking a hard link only drops a name, but truncating one destroys bytes that belong outside the root. MSBuild hard-link copies and `cp -l` make this realistic for build outputs in a checkpoint root. The brief names hard links explicitly.
- **Fix:**
  - On the opened fd, refuse truncation when nlink != 1 (Linux statx nlink; Windows `WindowsInfo.NumberOfLinks`). Unlink that name instead and do not count its bytes as reclaimed.
  - Add a hard-link witness that is red at the tip.

### D-3 (low regression): truncation is no longer made durable

- **Where:** `DeleteBounded` partial-truncate branch, and `TruncateAnchoredLinux`/`TruncateAnchoredWindows`.
- **Failure:** base ran `SetLength` then `Flush(flushToDisk: true)`, under the comment "Preserve durable truncation for native handles". The tip calls ftruncate with no fsync on Linux, and on Windows disposes the FileStream with no `Flush(true)`.
- **Why:** this removes a stated base guarantee without saying so. The receipt can count reclaimed bytes that a crash restores.
- **Fix:** call fsync on the file fd after ftruncate on Linux, and `Flush(true)` before dispose on Windows.

### D-4 (low, Windows semantics change): the truncate share mode widened from FileShare.None to read/write/delete

- **Where:** `TruncateAnchoredWindows`, `OpenChild(..., 0xC0000000)`. OpenChild always passes share 7.
- **Failure:** base `_io.Open(file, FileMode.Open, FileAccess.Write, FileShare.None)` failed if any other handle was open. The tip now truncates a file under a live opener, such as a leaked child, AV or an indexer.
- **Why:** this is a Windows behaviour change, and it cannot be executed on Linux.
- **Fix:** let OpenChild take a share argument and pass 0 for the truncate open. That keeps base sharing semantics.

## Answers to the brief's questions

### 1. Containment

- **Symlinked parent or root:** fails closed. Every component is opened with openat O_DIRECTORY|O_NOFOLLOW from `/`, which was witnessed red→green. `..` and `.` components are refused, a relative path is refused, and a file swapped for a symlink after listing is unlinked as a link because statx uses AT_SYMLINK_NOFOLLOW.
- **Deletes are fd-relative:** every delete is unlinkat on the walked dirfd, including the root rmdir and the root lock and marker. Only the index-file Unregister is path-based, which the claim states.
- **Advisory, not new:**
  - The walk crosses mount and bind-mount boundaries. No st_dev check was made at base either, and this cannot be witnessed without root.
  - A real directory renamed into the root between listing and unlink is followed, because the per-entry identity (dev/ino) is not bound from list to unlink. The card's Fix asked for "the recorded identity".
  - Recording dev/ino in AnchoredChild and checking them before unlinkat, and refusing a child directory whose dev differs from the root's, would close both. A cheap follow-up.

### 2. Ordinary trees

- **Unchanged:**
  - Custody order and the byte budget. Specials go first, without bytes; files are ordered marker last and ownership files before it.
  - Two fds at most at once, closed on every path.
  - An explicit stack, no recursion.
- **Changed:**
  - Read-only handling: neither base nor tip calls chmod. A failure now surfaces as `delete-IOException` where base surfaced `delete-UnauthorizedAccessException`, because the receipt skip key changed. No test asserts the old key.
  - An entry that vanishes mid-delete now throws (statx ENOENT). Base File.Delete and the `files.Where(FileExists)` pass tolerated it, so the root is now retained until the next sweep.
  - Cost: each unlink re-walks the path from `/`, which is O(depth) openat+statx per entry. That is bounded by MaxDescendantEntries=10000 and the 2 s MaxDuration, and was not measured. Advisory.
- See D-1 for a skipped name and D-3 for durability.

### 3. FIFO and socket

The new path never opens a FIFO:
- Classification is statx AT_SYMLINK_NOFOLLOW.
- The listing is readdir on `/proc/self/fd/N`.
- Truncation opens only after statx says regular, with O_NONBLOCK|O_NOFOLLOW, and checks again with fstat.

The custody reads (`ReadMarker`, `TestRootGuard.TryLock`, `RunOwnershipStore.Read`) are path-based opens unchanged from base, and they run before or independently of the new walk. A marker or lock replaced by a FIFO would block there at base as well. Advisory.

### 4. Windows

Read only, not executed.
- The code is ASCII and compiles in the partial.
- Delete-disposition through NtCreateFile is relative to a handle chain opened with OPEN_REPARSE_POINT. A reparse child is removed as itself, without FILE_NON_DIRECTORY_FILE.
- ListAnchoredWindows enumerates by the GetFinalPathNameByHandle string, not by handle. That is listing only, and the deletes re-walk.
- Behaviour changes against base: D-3, D-4, and the exception-type change in the receipt key.
- Native Windows verification is still pending, as the card requires.
