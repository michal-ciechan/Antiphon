## Blockers

### B-1 Park stamp is read after the pass, not before the reconcile

Where: `server/Infrastructure/Orchestration/AgentTaskLandNotificationHostedService.cs`, `ScanLandNotificationsOnceAsync` collects `parked` and `RememberRescansAsync` reads the stamp once after the whole pass.
Failure: the stamp that later decides "unchanged" (session Status, StartedAt, max UserPrompt/QueuedUserPrompt Sequence) is taken at the end of the pass. Any change that lands between a note's reconcile and the end of the pass is absorbed into the stamp; the next pass sees the note as unchanged and it waits for its backoff (1 min, doubling to 5) instead of reconciling on the next pass. The window is the remainder of the pass, which is long exactly when it matters: the first pass after a restart (every AwaitingReceipt note reconciles, those with attempts pull transcripts), or any pass after a busy caller's prompt (all that caller's notes reconcile).
Why: contradicts the report's staleness statement ("a database-visible status, StartedAt or prompt-sequence change is reconciled on the next hosted pass") and the card's acceptance (reconcile when receipt or session state actually changes). Consumers that wait on Confirmed/Canceled: `TerminalRunnerSeatReleaseService.HasPendingDeliveryAsync` holds a runner seat release while a note to that session is neither Confirmed nor Canceled; `PipelineHandoffActionService.BindReceiptAsync` refuses `handoff_foreign_receipt` until the TaskCompletion note is Confirmed.
Fix: read the stamp before reconciling. Load stamps for every session on the page before the page's reconciles (the same two queries as `LoadStampsAsync`) and pass that pre-reconcile stamp to `Remember`; a change after the read is then caught on the next pass (cost: one extra reconcile in the race, in the safe direction). Witness: land a prompt or status change between a note's reconcile and the end of the pass (a `LandDeliveryBoundary` hook between pages, or a second page of notes) and assert the next pass reconciles it.

### B-2 Queue-row changes are not a wake source

Where: `RescanPark` and `LoadStampsAsync` stamp only the session row and the transcript; the note's `SessionQueuedMessages` row (Status, DeliveryAttempts, DeliveryVerdict, CanceledAt) is never read for a parked note.
Failure: (a) delivery of the queued note (Pending to Sent, DeliveryAttempts 0 to 1) does not wake it; confirmation then depends on the live transcript stream landing the UserPrompt row, which `AgentSessionRuntime.CatchUpTranscriptAsync` documents as unreliable (prompt written 0.9 s after submit, stored 45 s later; 90 s stream lag measured; rows landing only at session end), the very reason the reconcile pulls the runner transcript. That pull now runs only at the backoff, up to 5 min. (b) A queue cancel becomes `Canceled` only at the backoff; the seat release treats Canceled as terminal but AwaitingReceipt as pending, so a stop sequence (status wake first, the queue's cancel sweep after) holds the runner seat for the rest of the backoff.
Why: the card's acceptance is "reconciled when its receipt or session state actually changes"; a delivery attempt and a cancel are receipt-state changes. The Code report discloses the wait; with a seat-release consumer and the documented stream unreliability it is not an acceptable replacement for the 5 s pull, and the fix is one statement per pass.
Fix: add the note's queue row (Status, DeliveryAttempts, DeliveryVerdict, CanceledAt) to the stamp with one `Id IN (parked QueueMessageIds)` read per pass (or per page), keeping the quiet pass at 0 updates; add a wake witness per field (mark one row Sent with attempts=1; cancel one row). The residual case, a receipt that exists only on the runner with no row change, stays bounded by the backoff pull and is acceptable.
