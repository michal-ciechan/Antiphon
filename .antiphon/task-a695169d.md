## Defects

**D-1 `Landing:GitBackend` states a backend the land does not run.**
- Where: `server/Application/Settings/LandGitBackendSettings.cs` (`LandGitBackend.Resolve`,
  `git_backend_not_built`), `LandingGit.BeginOperationScope`/`Observe` (`Backend = Cli`), profile line
  in `AgentTaskLandService.cs` (`backend=Cli inProcess=…`).
- Failure: default `Cli` while libgit2 answers ~116 reads per land; an operator who sets
  `Landing:GitBackend=Cli` to rule libgit2 out of a land incident still gets libgit2; setting `LibGit2`
  logs "is not built yet; the land git backend is Cli" although libgit2 is built and on. The real
  switch, `ANTIPHON_GIT_INPROCESS=off`, is not read by or reflected in the setting, and observer records
  of libgit2 answers carry `Backend=Cli`.
- Why: the plan predates 40c2ab63c and assumed `Cli` meant "no libgit2". S1 is a new, startup-validated,
  operator-facing setting, so the mismatch ships the moment it lands.
- Fix (operator's choice): (a) drop `Landing:GitBackend` (settings type, resolver, Program.cs lines,
  BS-* tests, profile `backend=`) from S1 and keep typed reads + observer; or (b) make the setting own
  the operator's switch (e.g. values `InProcess` default / `Cli` = in-process off), which changes the
  zero-behaviour-change claim only for a non-default value; or (c) keep it but rename/redocument it as
  "IGitSession backend" and print the operator's libgit2 hits as such. Also decide whether Track L
  continues on a per-scope session at all, given 4a4945b6c.
