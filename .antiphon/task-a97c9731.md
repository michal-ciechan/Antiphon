## Safety questions from the brief

1. **Census scoping.** Every bound refusal is still a per-row check that runs in both passes, before any comparison: `RecycleBoundTasks` for an open row and `RecycleLandInFlight` for a bound land (`deploy-server2.ps1:~847-853` and `~868-871`; `c590-remote.sh:6631-6638` and `6679-6682`). Neither check changed.
   - The only refusals the change removes are `Unstable` results for rows that are not bound: an off-runner appearance with a land, an off-runner runnerId or land change, and per-scope id-list changes. None of those tasks can write to the temp volumes.
   - "Bound" means `runnerId` equals `server2-temp`. The PowerShell check uses `-eq`, which is case-insensitive. The jq check uses `==`, which is case-sensitive; that difference already existed. The PowerShell census runs first and would refuse a case variant.
   - The census has no separate "session runner" field. Temp-runner sessions are covered by `c1008_status_proof`, which on the same host run requires `retiredAt` equal to the expected stamp, plus drain and redirect checks and `c1008_zero` (sessions, runnerSessions and queuedTasks all 0).
   - Lands use the same bound rule.
   - Apply does not reuse the preview's census. The `-RetirementProof` invocation runs `Wait-RecycleTaskCensus` again (`deploy-server2.ps1:1483`), and the host runs `c1008_status_proof` → `c1008_tasks_wait` again live inside the apply's `c1008_recycle`. 2. **The C1087 "unstable" vector now passes.** That is correct: the task is off-runner and its land is Completed. Vectors that must still refuse remain:
   - C1693 `bound-appears`: a bound row appears in pass 1 and refuses `RecycleBoundTasks`.
   - C1087 bound Queued/Dispatched/Working/Blocked.
   - The C994 host vectors `bound-requested`, `bound-started` and `bound-land-pending-succeeded` against `server2-temp`.
3. **Host-proof retry.** Only `snapshot` is retried, at most 3 attempts, and each attempt gets only what is left of the one network budget (`$remaining`). The inner function also rejects a budget of 0 or less with `deadline`.
   - Every attempt starts again from `ls-remote`: a fresh advertisement, a fresh fetch, all required-object and unpublished checks, and the post-bundle `ls-remote` comparison.
   - These reasons are never retried: `unpublished-*` and `object-*`, every Git failure (reason `git`), `origin`, `clock`, `existing` and `advertisement`.
   - A retry cannot turn unpublished work into a pass, because the unpublished check runs again against the new advertisement.
   - The failed attempt's own bundle is deleted only when the proof file is absent. If that delete fails, the next attempt refuses `existing`, so it fails closed.
   - The log line is `repo=<validated relative> attempt=<n> reason=<[a-z-] token>`. It contains no URL and no stderr.
4. **HostCaseFailed suffix.** It is gated by `^[A-Za-z][A-Za-z0-9 =._/:,-]{0,299}$`. I checked it in pwsh:
   - `abc\nC1609_RETIREMENT state=Ready` → rejected.
   - `abc\r\n` → rejected.
   - `abc\n` → accepted. That only adds a trailing newline and cannot forge a line.
   - The text stays on the `Rolling deploy stopped: HostCaseFailed …` line, and nothing parses that line for authority. The apply consumes a host-validated Ready record, not console text.
