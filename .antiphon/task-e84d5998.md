## Checks

1. R-3 re-check predicate (`TickLockStillHeldAsync`). PostgreSQL `SET_LOCKTAG_INT64` stores `(uint32)(key>>32)` as
   classid, `(uint32)key` as objid, objsubid 1. The SQL `((k>>32)&4294967295)::oid` / `(k&4294967295)::oid` matches that.
   Probed on postgres:16 (16.15): 13 bigint keys were held in one session (the tick key -128319412194417907, 1, -1, 5,
   -5, 0, INT64 min/max, 0x7fffffff80000000, 0x80000000ffffffff, 0x00000001ffffffff, 0xffffffff00000000,
   0x8000000080000000). Each matched exactly one pg_locks row, and the tick key matched 0 after an unlock. The old
   unmasked form gives `ERROR: OID out of range`. An int4-pair lock with the same halves (objsubid 2) matches 0. The
   key held by another backend gives 0 with `pid = pg_backend_pid()` and 1 without it, so the pid filter does the
   work. A lock that is not held, a query that throws, or `_lockHeld` false returns false: the mirror loop stops
   with Deferred `tick_lock_lost`, the remainder becomes `queued_next_tick`, and an Execute temp sweep gets a
   `tick_lock_lost` row and is not sent. This fails closed. If EF reopens after a break, the check runs on a new
   backend whose pid differs, so it also fails closed. Cost: one query per Execute retain candidate (bounded by
   MaxRemovalsPerTick + MaxAbsentPerTick), plus one per Execute temp sweep.
2. Regression witness: mutant M1 (unmasked classid cast) turns C1677RetentionServerTests 78/100 red. That
   reproduces the Code regression, and the existing Execute tests pin the negative-key path. A lock really lost
   mid-tick: mutant M2 (no re-check) makes C1812_a_lost_tick_lock_sends_no_destructive_retain red (Sent expected 0,
   was 1).
3. R-1: when the unlock throws, `pg_terminate_backend(pg_backend_pid())` runs, then `NpgsqlConnection.ClearPool`,
   then close. Each step is in its own try, so nothing throws out of the release. I verified on PG16 that
   self-terminate releases the lock. Mutant M4 (no discard) makes the failed-unlock test red: the unpooled probe
   could not acquire. ClearPool also drops idle sibling connections, and busy ones are discarded when they return.
   This is documented, and acceptable.
4. R-2: the save uses CancellationToken.None. An abort before or after the insert finishes the run `tick_cancelled`
   once and throws OCE. StartExecuteAsync's finally then unlocks, disposes and exits; no background tick starts and
   nothing is finished twice. Mutant M5 (save with ct) makes the aborted-save test red.
