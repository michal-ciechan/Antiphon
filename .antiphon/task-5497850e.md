# Phone-home split mention lost when rows run together

Outcome: fixed. `Finite_stall_preserves_connection_order_and_delivery` lost the split `@fake hello` mention because the same session's exit committed `Stopped` while `RouteMentionAsync` was still reading the source. The session observer now waits until that completed-line route has inserted the queue row. The new witness failed before that wait and passed after it. The class then passed 10/10.

Branch `feat/card-task-5497850e`, base `68565db92359eadea14180c745c0a28711a36872`.

## Cause

The hello line is extracted once on the newline chunk (`messageChars=5`, so the 300 ms pending debounce does not enqueue it). `RouteMentionAsync` then requires the source session to be `Starting` or `Running`. The phone-home scheduler has one active observer per session, but `ObserveDelta` returned as soon as the command was queued. Later events on that session, including `last` and the exit, were observed while the background route's source query was still in flight. `CloseSessionOnExitAsync` set the source to `Stopped` (status 4). The query returned `found=false` and the route returned `ok=false reason=source-missing`. Waiting longer cannot insert the row after that refusal.

Sibling rows do not share a debounce map, clock, schema, or router. Each `PhoneHomeHostedRunner` has its own database. They add database and thread load, which makes the source query lose the race. That matches the earlier reviews: the method alone was green, and the class together lost the row more often under CPU burners.

No duplicate hello was observed. The `@fa` remainder is a different mention (empty message) and the later `last` chunk makes that debounce stale.

## Baseline, before the fix

Ten runs of `/*/*/PhoneHomeBackpressureTests/*` on a diagnostic build of the base (the dump was not committed). `Finite_stall_preserves_connection_order_and_delivery` failed runs 1, 7, and 9 (3/10). Each failure was `mentionCount=0`, source status `Stopped`, recipient `fake` still `Running`, one `command-enqueued` for `target=fake messageChars=5`, then `source-query-returned found=false` / `route-returned ok=false reason=source-missing`. The other rows in those runs passed. Passes were not "slow successes": the lost runs hit the existing 5 s `UntilAsync` cap because the row was never inserted.

Pairwise bisect was not run. Both captured failures were this session's own exit, not a shared-state partner. A one-run-per-pair bisect would not have named a single interfering row.

## Fix

`AgentSessionRuntime.ObserveOutputAsync` awaits `AgentMentionRouter.ObserveAndRouteAsync` before publishing the text delta. That task is the completion of commands enqueued synchronously by a completed line. `RouteMentionAsync` signals that completion immediately after `EnqueueMentionAsync` and before publish/flush, so a single event consumer cannot deadlock delivering the target. Refusals complete the same task when the route returns. `void ObserveDelta` still discards the task, so the outage harness is unchanged. The 300 ms pending debounce is not awaited.

The route queue no longer uses `DropOldest`. A full queue (1024) refuses the new command and completes nothing the observer is awaiting. Dropping the oldest item would have left that observer parked forever. Under the cap, behavior is unchanged. Past the cap, the newest command is refused instead of the oldest being discarded.

`SourceStatuses` is still `Starting` and `Running`. Output replayed after the session is already stopped does not route.

The overflow window in `Finite_stall` is before `Bus.Release`, while the split chunks are still queued. The await applies only while those chunks are being observed, after the hold. The class runs below kept the original pending-event, credit, and delta assertions.
