## D-1 (blocker, regression) `ReadGrantedHolder` reads `pg_locks` cluster-wide for a database-scoped lock

- Where: `server/Infrastructure/Agents/HangfireConfiguration.cs:703-720` (`ReadGrantedHolder`), used by `ReplaceConnection` (`:600-606`), `OwnOpenBackendStillHolds` (`:631-651`) and `ReclaimOwnBackend` (`:676-693`). The test helper `FindWorkerLockPidsAsync` (`HangfireDurableStorageTests.cs:702-712`) has the same shape.
- Failure: `pg_try_advisory_lock(1743, 1)` is local to the current database, but `pg_locks` lists advisory locks of every database in the cluster. The query filters `classid`, `objid`, `granted` only: no `database`, no `objsubid`. A second Antiphon instance on a sibling database of the same cluster (staging/test database beside `antiphon`, the shared dev Postgres with per-run test databases, or any other product using key 1743/1) shows as the holder. Consequences on this process: (a) its session dies (Postgres restart) → `ReplaceConnection` reads the foreign pid → `holder is int` → `Lost()` → `StopHost`: a wrong stop and a container restart, where the pre-change code re-took the lock through the database-scoped `pg_try_advisory_lock` and kept running; (b) a transient check-query failure on a live own backend → `OwnOpenBackendStillHolds` reads the foreign pid ≠ `_backendPid` → `Lost()` → wrong stop (the exact A-2 case this card fixes, now reintroduced through another route); (c) a foreign holder whose pid equals the remembered `_backendPid` → `ReclaimOwnBackend` runs `pg_terminate_backend` against another database's session. `SessionStillHoldsLock` is unaffected only because it filters `pid = pg_backend_pid()`.
- Evidence (fresh, postgres:16-alpine throwaway container `c1774-rv1-pgprobe`, stopped after): holder session in database `otherdb` (`SELECT pg_try_advisory_lock(1743,1), pg_sleep(60)`); from database `antiphon`, the product's query returned `pid=80 database=16385 datname=otherdb classid=1743 objid=1 objsubid=2 granted=t`; in the same `antiphon` session `pg_try_advisory_lock(1743,1)` returned `t` while that row existed; counts `cluster_rows=2 own_db_rows=1 own_db_other_sessions=0` with and without `database = (SELECT oid FROM pg_database WHERE datname = current_database())`.
- Why it matters: brief item "another worker holding the lock still stops the host on that tick (no regression: the pg_locks check cannot be fooled)". The new check can be fooled by a holder in another database, and the card is runtime-sensitive (a wrong stop restarts the server container; a wrong terminate kills a foreign session).
- Fix: add `AND database = (SELECT oid FROM pg_database WHERE datname = current_database()) AND objsubid = 2` to `ReadGrantedHolder` (and to the test helper and the operator one-liner in `docs/docker-stack.md:957`, which otherwise terminates sibling-database holders). Witness: an integration test that holds `(1743, 1)` from a second database on the shared testcontainer (`CREATE DATABASE` through the admin connection), terminates the lease backend, calls `EnsureHeld` and asserts the lease re-acquires in its own database, the host is not stopped, and `FindWorkerLockPidsAsync` scoped to the test database sees exactly the new pid. Mutant: drop the `database` predicate → the witness reads the foreign pid and `EnsureHeld` throws "another worker".

## Advisories (D-2: cards, no land hold)

- A-1 (correctness edge) `ReplaceConnection` reads the new backend pid after the swap (`:609-611`). If `ReadBackendPid(fresh)` throws after `owned = true` (link broken right after the lock was taken while the server session stays alive), `_connection` is the fresh session but `_backendPid` is the old pid; the next tick sees its own fresh backend as a foreign holder and stops the host. Read the pid before the swap and assign both under the gate.
- A-2 (identity) A pid is the only identity of "our own previous backend". After a Postgres container restart pids restart small, so a different worker's lease backend can reuse the remembered pid and `ReclaimOwnBackend` terminates it instead of stopping this host. Record `(pid, backend_start)` from `pg_stat_activity` at acquisition and compare both. Needs two workers on one database, which the contract forbids, so advisory.
- A-3 (verification) The reclaim path (`ReclaimOwnBackend`: own connection not `Open`, server backend still holding) has no committed witness; it is exercised only as a side effect of the author's `OwnOpenBackendStillHolds` mutant. A cheap seam that swaps `_connection` for an unopened connection while the test keeps the old one alive would prove terminate-then-retake, one holder, pid changed, host kept.
- A-4 (doc) The stated overlap "15 s plus the Hangfire drain (15 s) plus host shutdown (30 s)" is a loose bound: hosted-service `StopAsync` runs inside the host's 30 s shutdown budget, so the overlap is at most 15 s + 30 s, and the server container's default Docker stop grace (10 s) cuts it further. State ≤ 45 s or say the sum is conservative.
- A-5 (robustness) `WithinCrashExpiryWindow` uses wall-clock UTC. A forward clock step while Postgres is unreachable shortens the retry window; `TimeProvider.GetTimestamp()` is monotonic and still fakeable.
- A-6 (doc) `CommandTimeout=5` applies to every lease command (check, take, keepalive `set_config`, side reads, reclaim), not only Dispose's unlock. A Postgres that answers a trivial query in more than 5 s now counts as an unreachable tick inside the 60 s window. Acceptable, but the doc line names only the unlock.
