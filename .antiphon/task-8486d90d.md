## Findings

### D-1 (regression / fail-open: the preview writes the volume). Owner: Code 23f87511
- **Where:** scripts/c590-remote.sh:7756 (`unshare --user --map-root-user --mount bash "$ns"`), and the `ns.sh` exec at :7736.
- **Failure:** in the uid-1654 branch the audit program, and every repo-controlled executable it triggers (core.fsmonitor; also clean filters during `git status`), runs as userns root with the full capability set over the private mount namespace. A hook can `mount -o remount,bind,rw` the original path or `/work` and write the volume (probe 3). If it defers the write with a detached child, the after-digest still matches, the preview prints `auditPending=false`, and the volume is modified afterwards (probe 4). Nothing kills descendants when the namespace's main process exits. Apply's helper container is uid 1654 without CAP_SYS_ADMIN, its volume mount is read-only, and the container's processes die with it.
- **Why:** this is the D1 contract the redo had to close: no write through any alias, and the digest is only a backstop. The added test exercises this exact branch, with a hook that only appends directly, so it passes.
- **Fix:** after the mounts, drop every capability before exec in all branches. For example: `setpriv --inh-caps=-all --bounding-set=-all --no-new-privs`, or a nested unprivileged userns, so remount and umount fail. Run the program in its own PID namespace (`unshare --pid --fork --mount-proc`) so every descendant dies before the after-digest. Add witnesses for a remount-rw hook and for a delayed-writer hook. Both must refuse or leave the bytes unchanged, including after a wait.

### D-2 (security / new fail-open: repo-controlled code on the host). Owner: Code 23f87511
- **Where:** scripts/c590-remote.sh:7734 and :7764. This is the production path: the server2 user `mc` calls `sudo -n env … unshare --mount`, then `setpriv` to 1654 on the host root filesystem.
- **Failure:** fsmonitor and clean filters configured in a volume repo's `.git/config` now run on the server2 host as host uid 1654, with host networking and the whole host filesystem except the remounted volume. On server2 the Codex home and the GitHub token directory are host paths owned by uid 1654 (docs/docker-stack.md:962). Apply ran the same code in an isolated helper with only `/work` (read-only) and a tmpfs `/tmp`. Whether 1654 can traverse `/home/mc`, or has sudo on the host, is unverified. This branch has no test: the fixture always takes the uid-1654 branch.
- **Why:** the brief requires that the preview never runs hooks with more authority than apply, and that the preview never fails open.
- **Fix:** neutralise repo-configured executables in the shared audit program, which keeps preview and apply identical. For example, set `GIT_CONFIG_COUNT` entries `core.fsmonitor=false` and `core.hooksPath=/dev/null`, and refuse or disable `filter.*` drivers. Also confine the preview view, for example tmpfs over `/home`, `/root` and the `SERVER2_ROOT` secrets, or chroot into the pinned image rootfs. Add a witness that runs the root/sudo branch, or a seam that forces it.

### D-3 (preview ≠ apply audit environment). Owner: Code 23f87511
- **Where:** scripts/c590-remote.sh:7676-7678 and 7736. The pinned image is inspected only as a gate. The program then runs with host `bash`, `git` and `jq`.
- **Failure:** apply runs the image's pinned Git 2.47.3 (docs/docker-stack.md:891). The preview runs whatever Git the server2 host has (kernel 4.15 host; version unverified). The program uses `rev-parse --path-format=absolute` (Git ≥2.31) and other version-sensitive output, so a preview can refuse where apply passes. Differences in porcelain or ref handling could also make a preview pass where apply refuses. The test cannot see this, because the runner's `/usr/local/bin/git` is the same 2.47.3. The docs claim "the same publication audit as apply".
- **Fix:** run the program against the pinned image's Git, for example by chrooting into the image rootfs, which also helps D-2. Otherwise gate the preview on a host Git version check that refuses with a named class. Record the host version as evidence.

### D-4 (performance standards: unbounded, unbudgeted phase). Owner: Code 23f87511
- **Where:** scripts/c590-remote.sh:7620-7650 (`c1008_tree_digest`), called twice per volume.
- **Failure:** the digest makes one `sudo -n sha256sum` or `readlink` process per file over the whole volume, before and after the audit. It sits outside the 10800 s audit cap and has no measurement. With sudo stubbed it measured ~3.3 ms/entry here (1306 entries in 4.2 s at load 17). On an 800-repository standing volume with build outputs (millions of entries), real `sudo` makes this hours per pass.
- **Fix:** one privileged pass (for example a single `sudo -n find … -exec sha256sum {} +` or one `sudo bash` digest), a measured phase, and inclusion under the audit budget. If D-1's cap drop and PID namespace make the bytes immutable by construction, scope the digest down.
