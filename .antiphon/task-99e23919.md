### 1. Land regression from the stderr rule

The rule applies to every scope except IdentityOnly, so the land resolver's IdentityAndStatus inspections are covered. Here is what a land does when the status warns:

| Call site | Outcome |
|---|---|
| `AgentTaskLandSourceResolver:287` | `RefuseAsync("status_untrusted")` with diagnostic (`status` command, exit 0). A distinct code, never `source_dirty`, so the adoption-recovery branch does not run. |
| `:466` | Refuses before the CAS move. |
| `:353` and `:494` | `adopt_local_changed` (a misleading code, but fail-closed) |
| `DelegationWorktreeService` | Local merge fails with receipt `status_untrusted` |

Possible stderr sources for a clean `git status`, checked against git 2.47.3:

- **Unreadable global config.** I reproduced this: with HOME set to an unreadable directory, status warns twice (`warning: unable to access '<HOME>/.config/git/ignore': Permission denied`) and exits 0, while rev-parse stays silent. This is the realistic fleet-wide outage shape. It does not apply today: the server image runs as uid 1654 (app, HOME=/home/app), the same user as this runner.
- **`GIT_TRACE*` set in the server environment.** Would trigger the rule.
- **Git for Windows config-path warnings and fsmonitor warnings.** Only if configured.

Sources that cannot trigger it:

- safe.directory and a broken config both exit 128, so they were already `status_error`.
- In modern git, `status` does not emit CRLF warnings (`convert_to_git` runs with no RNDTRP flag).
- Prompts are disabled by `GIT_TERMINAL_PROMPT=0`.
- Lock contention: `GIT_OPTIONAL_LOCKS=0` means status writes no index.
- `core.longpaths` on Linux is an unknown key, which git ignores silently.

Survey: across 60 runner worktrees on server2, the exact command wrote **0** bytes to stderr. I could not check a Windows land (desktop not used).
