## Verification priorities

### (1) The refusal path kills the host

A refusal throws inside `AdoptAsync` and lands in the sweep's catch at `src/Antiphon.SessionRunner/SessionRunnerRuntime.cs:2114-2128`. With no custody binding and no `WorkspaceUseGate`, that catch:

1. disposes the session;
2. calls `KillPidBestEffort(manifest.HostPid)`;
3. registers the session as Exited;
4. deletes the manifest.

The pid kill is guarded only by the earlier `probe.IsAlive(HostPid, HostStartTimeUtc)`. So a squatter who answers with another session gets the real host killed.

**The kill path is not new.** Any adoption exception reaches it. Before this change a squatter could already trigger it by answering hello with a non-helloAck frame (`PtyHostClient.cs:65`, CARD-1634) or by hanging up so the connect timed out. The change adds one more trigger. It does not widen what a squatter can do.

**This is the lesser harm.** Before the change the stranger was adopted. It received every later Write/prompt and Attach, it could forge output and exit, and the real host was orphaned. Now the outcome is a denial of service on one session.

**Advisory, cheap fix (do not fix in this review).** Throw a dedicated identity exception, or test the fixed message. On that exception, skip `KillPidBestEffort` and `TryDeleteFile`, and register the session as a pending conflict. The `WorkspaceUseGate` branch at :2119 already does this with `RunnerSession.CreateWorkspaceConflict`. The cost: the real host keeps running unattached until its linger ends or an operator steps in. The squatter holds the path in either case. This is invariant I-5 from the worker's proposed follow-up card.

### (2) Nothing reaches the stranger before the check

`ConnectAsync` writes only `HelloMessage(ProtocolVersion)` (`PtyHostClient.cs:59`). The steps before it in `AdoptCoreAsync` run on the runner alone: `RetainCheckout`, Grok receipt `VerifyAsync`, and the screen setup. The check at :3559 runs before the Linux start-time read, before custody, and before any `GetStatusAsync`/`AttachAsync`/Write. On refusal, `RunnerSession.DisposeAsync` (:4497) unhooks the handlers and disposes the pipe. It sends nothing. The client's read loop starts in its constructor, but it only reads, and no handlers are wired at that point. The witness `AssertRefused` asserts that the fake host received no request after hello.

### (3) Legacy manifest rule

Both host writers record `HostInstanceId`: the launch-pending manifest (`HostSession.cs:161`) and the running one (`:220`). Its value is `Guid.NewGuid()` (`:40`), the same value the helloAck carries (`:360`). Later writes (`:306`, `:477`) use `with`, which keeps the value.

The runner's own pre-write (`SessionRunnerRuntime.cs:733`, Grok receipt) has no instance id. It also has `HostPid = 0`, and the sweep never adopts a manifest with `HostPid <= 0` (:2100). Custody recovery (`RunnerCustodyLedger.cs:103`) is custody-only, and that path is unchanged.

Witness: `Real_host_records_its_hello_instance_and_is_adopted`. M3 makes it red.

Who can write the manifest: the manifest directory is created with default `Directory.CreateDirectory` and a plain `File.WriteAllText` (`PtyHostManifest.cs:57-60`). No `UnixCreateMode` is set anywhere, so the directory is 0755 under umask 022. That is runner-uid writable only. Another uid cannot make a new manifest look legacy. The same uid can do anything already. Live server2 permissions were not inspected.

### (4) The compare

The ids are `Guid` values and the compare is value equality (`:3644`). There is no string handling, trimming or casing. Every textual Guid form parses to the same 128-bit identity.

The log is a fixed template with `_sessionId` only. The exception message is the fixed `pty_host_identity_mismatch`, and the witness asserts that the stranger's id appears in neither D nor N format.

Missing, null or empty hello session ids are all refused:

- `Guid.Empty` never matches, because the sweep deletes manifests whose `SessionId == Guid.Empty` (:2031), so `_sessionId` is never empty.
- A missing JSON field deserializes to `Guid.Empty` and is refused.
- A JSON `null` for the non-nullable `Guid` throws `JsonException`, so adoption fails.
- A null `HostInstanceId` against a recorded one is refused, and is witnessed by `(True)`.

This is shown by reasoning only: no test has an empty hello session id (advisory A-2).
