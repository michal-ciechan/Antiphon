### B-1 Specialist working directories are not shared with the sidecar (D-5 defeated, check-interpreter tool policy unarmed)
- Where: docker-compose.server2-server.yml:76-78 (`Delegation__CheckInterpreterWorkingDirectory: /state/check-interpreter`, diagnose, output-distiller), :22
  (server-state-init creates those directories on the `server-state` volume), :143-145 (sidecar mounts `runner-state:/state` and `work:/work`, no `server-state`).
- Failure: server/Application/Services/StandingSpecialistProvisioner.cs:195-204 (`WriteToolPolicy`) creates the working directory and writes the deny-all
  hook `<dir>/.claude/settings.json` on the SERVER's filesystem, and `SeedClaudeTrust` seeds the server's claude.json; server/Application/Services/AgentControlService.cs:447
  checks existence on the server, then the launch goes to the direct runner `http://server-session-runner:8080`. In the sidecar `/state` is the `runner-state`
  volume: `/state/check-interpreter` does not exist there and the hook is not there. The specialist either fails to start in the sidecar or, if the pty creates
  the cwd, runs without the policy that `ToolPolicyRequired: true` demands. D-5's purpose (the sidecar hosts the three specialists) is not met.
- Why: the shape was copied from the root docker-compose.yml (CARD-0590), which has the same split; this card makes it the production control plane.
- Fix: place the three specialist directories on the shared `work` volume (for example `/work/specialists/check-interpreter`, `/work/specialists/diagnose`,
  `/work/specialists/output-distiller`), create them in server-state-init, point the three `Delegation__*WorkingDirectory` keys at them, update the needle list in
  scripts/deploy-server2-server.ps1 and the pins in Server2ProductionServerContractTests, and add a witness that every specialist working directory lies under a
  mount both `server` and `server-session-runner` declare at the same container path.

### B-2 `-Execute` deadlocks on compose output
- Where: scripts/deploy-server2-server.ps1:183-201 (`Invoke-ServerUp`): `RedirectStandardOutput`/`RedirectStandardError` are set and `WaitForExit()` is called
  without ever reading either stream.
- Failure: `docker compose up -d` builds three images from `build:` contexts on first use and streams the build log to stderr; when the pipe fills the child
  blocks and the script never returns, leaving compose mid-`up` on the host. Reproduced without docker: dot-sourced the script and called `Invoke-ServerUp`
  with a fake `docker` that writes 1 MiB to stderr and exits 0: hung until an external `timeout` killed the child at 39 s (then returned `compose-up-failed`);
  a one-line control returned in 0 s. Only the test's own `RunDeployAsync` drains both streams; the production path does not.
- Why: redirected pipes are never drained; `Invoke-ServerGate` has the same shape (sequential `ReadToEnd` on stdout then stderr) with small output.
- Fix: inherit the console (no redirection) or read both streams asynchronously before `WaitForExit`; add a refusal-mode witness with a fake docker that emits
  more than 64 KiB.
