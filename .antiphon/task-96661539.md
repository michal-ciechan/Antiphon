## Item 3 — advisory A-2 (not fixed)

Non-custody adoption is a real local exposure.

`AdoptCoreAsync` (`src/Antiphon.SessionRunner/SessionRunnerRuntime.cs`) connects to `manifest.PipeName` and checks `Hello.SessionId`, `HostInstanceId`, and `verificationCustodyV1` only when `VerificationBinding` is set (the check is the `if (VerificationBinding is { } binding)` block immediately after connect). The launch path does the same: the session-id check runs only inside `if (VerificationBinding is { } binding)`. A non-custody adopt is bound only by the pipe name.

A local process that binds `/tmp/antiphon-pty-{sessionId}` during connect or relisten is adopted as that session, including when the ack names a different session. Custody adoption already refuses a mismatched `Hello.SessionId` and `HostInstanceId`. The hello retry does not open a new route; this gap was already on the non-custody path.

Card-ready line: Non-custody pty-host adoption accepts any helloAck on manifest.PipeName and never checks Hello.SessionId against the manifest session. A local process that binds `/tmp/antiphon-pty-{sessionId}` during connect or relisten is adopted as that session, including when the ack names a different session. Custody adoption already refuses a mismatched Hello.SessionId and HostInstanceId. Compare those ids on the non-custody path too; the pipe name alone is not a peer identity. A matching-session check would not stop a stranger who copies the id out of the path.
