## B-1 (blocker): run-checkpoint.ps1 inherits a caller's phase root, so the script witness is red in the journal-enabled lanes and writes its fixture journal into the live row root

Where: `scripts/run-checkpoint.ps1` Invoke-Dotnet (`PhaseJournalDiagnostic.EnableProcess($psi, ...)` then `ConfiguredRoot($psi)`), `scripts/lib/PhaseJournalDiagnostic.cs` `Enable` (SetIfBlank), `tests/Antiphon.Tests/Checkpoints/PhaseJournalKillDiagnosticTests.script_killed_row_prints_the_same_diagnostic` (raw `ProcessStartInfo("pwsh")`), `scripts/test-run-checkpoint.ps1` Invoke-C585Runner (no ANTIPHON_TEST_PHASE_* scrub).

Failure: `ProcessStartInfo.Environment` is pre-populated from the current process, so `SetIfBlank` keeps an inherited `ANTIPHON_TEST_PHASE_ROOT`/`GROUP_ID`/`RUN_ID`. Under an `tests/Antiphon.Tests` checkpoint row (which this change now always runs with those variables set) or the nightly/rc lane (`Enable-TestPhaseExecutionEnvironment` sets them for the host), any run-checkpoint.ps1 started from inside the test host enables the row's journal in the OUTER root, the diagnostic is computed over the outer root (every file under it and its `chunk-*`), and the harness shim writes its fake `chunk-c1748/cases-4-c1748.jsonl` into the outer row's live evidence root.

Evidence (checkpoint tool, tip 60a2afd4, run `20261108-062148-793f`): CP-1 `/*/*/PhaseJournalKillDiagnosticTests/*` executed=4 passed=3 failed=1. The red case printed `JOURNAL-DIAGNOSTIC CP-1 completed=4 pending=2 outcome-passed=3 outcome-failed=0 outcome-skipped=1 in-flight=Antiphon.Tests.Checkpoints.PhaseJournalKillDiagnosticTests.script_killed_row_prints_the_same_diagnostic,Antiphon.Tests.Sample.left` (the outer host's own cases counted), and `.antiphon/checkpoints/20261108-062148-793f/rows/CP-1/phase/chunk-c1748/cases-4-c1748.jsonl` exists beside the real `chunk-7dd10649…/cases-6915-….jsonl`. Direct probe at the tip with `ANTIPHON_TEST_PHASE_ROOT` pointing at a seeded root: `test-run-checkpoint.ps1 -Case C1748_KilledRowPrintsJournalCounts` fails `C1748 journal diagnostic` with `completed=4 pending=2 outcome-passed=2 outcome-failed=1 outcome-skipped=1 in-flight=Antiphon.Tests.Sample.left,Outer.Host.c`, and the fixture file lands in the seeded root. The same case passes for a direct `dotnet run` lease with no phase variables (Code's environment), which is why Code saw 4/4.

Why: the tool path is correct (RowRunner enables on a copy of the manifest environment and ProcessDriver applies it over the inherited one, so the row root wins), but the script path consults the ambient process environment, and the new witness does not strip phase variables from its pwsh child the way `LandingGitFixture.StartProcess` does with `TestTiming.RemovePhaseVariables`. The witness therefore cannot pass in the lane the change itself creates, and it pollutes live evidence.

Fix: (1) in run-checkpoint.ps1, remove inherited `ANTIPHON_TEST_PHASE_*` from `$psi.Environment` before `EnableProcess` (or set the row's root unconditionally on the script path; keep SetIfBlank only for a manifest-provided value on the tool path); (2) strip the five phase variables from the pwsh child in `script_killed_row_prints_the_same_diagnostic` and/or in Invoke-C585Runner; (3) add a witness that pre-sets `ANTIPHON_TEST_PHASE_ROOT` in the harness environment and asserts the row's own `rows/<name>/phase` root is used and the inherited root gains no file. Red-first against the current script.
