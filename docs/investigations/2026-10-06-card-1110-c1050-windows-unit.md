## Why that assertion fails

`C1008PlatformContractTests` is `[Category("Unit")]` (`C1008PlatformContractTests.cs:16`). The ordinary Unit lane is `/*/*/*/*[Category=Unit]` (`docs/testing-and-build.md:156`). That filter selects every method of the class, including the two Windows audits.

Each audit's first statement is a hard failure on any other OS, and only then calls `RunWindowsAuditAsync`:

- `C1050_Windows_remote_outcomes_are_exact` at `C1008PlatformContractTests.cs:103-104`
- `C1050_Windows_rolling_outcomes_are_exact` at `C1008PlatformContractTests.cs:111-112`

Both lines are `OperatingSystem.IsWindows().ShouldBeTrue("c1050-native-windows: audit requires Windows placement")`.

The CARD-1050 plan states the same contract: require native Windows as an assertion, and "running them on Linux is an explicit placement failure, not a skip or emulation" (`docs/superpowers/plans/2026-10-04-card-1050-windows-bash-host-tests-plan.md`, methods 4 and 5). Its Linux rows CP-2, CP-4 and CP-6 omit these two method names. Its Windows rows CP-1, CP-3 and CP-5 include them. Out of scope includes "No whole Unit". The introducing commits therefore had no declared row that selects these methods on Linux.

## What the code implies on Windows

Not run. `OperatingSystem.IsWindows()` is true there, so line 103 / 111 passes and `RunWindowsAuditAsync` runs. It then requires an already built `Antiphon.Tests.exe` beside the assembly (`C1008PlatformContractTests.cs:123-124`) and `checkpoint-build-source.json` in the output directory or its parent (`:126-130`). `BuildStep.PropertyArguments` sets `UseAppHost=false` only when the host is not Windows (`tools/Antiphon.Checkpoints/Execution/BuildStep.cs:28-29`), which is what produces that exe on a Windows checkpoint row. A Windows run without the stamp fails at `c1050-child-source` before `Audit`. With the stamp and the exe, the current first statements imply the closed skip multiset plus five portable passes. That implication is source structure, not a Windows execution.

## Which exclusion mechanism exists

The repo does not have a method-scoped lane that drops two methods out of `Category=Unit`.

- Platform skip used by other Windows-only Unit methods: `throw new SkipTestException(...)` before any work. `BuildSlotScriptTests.cs:137` (`Windows PowerShell 5.1 qualification requires Windows`). `AmServiceDeployReadinessTests.cs:115-116` (`Native Windows Git tool discovery qualification`). The Unit lane then counts them skipped. The reason is the exception message. There is no second registry of those messages.
- Lane category is class-scoped Unit xor Integration (`TestLaneCategoryGuardTests.cs:6-8` and `:45-48`). A Unit class with an Integration method fails that guard. There is no Windows category the Unit filter ignores.
- A registered reason is required for the Slow allowlist: a class row without a preceding comment fails `missing-reason` (`TestClassificationPolicyTests.cs:88-94`). Method-level Slow fails `method-level-slow` (`:98-109`). Marking this class Slow would slow-lane the Linux-runnable siblings and still would not remove Category Unit.
- `tests/linux-test-roster.json` exclusions need an owner and a reason (`LinuxTestRosterTests.cs:56-65`, `MissingExclusionOwner`). That roster is the Docker container lane. This class is not listed there, and a class exclusion would also drop `C1050_Guard_matches_native_platform`, the two first-statement audits, and `C1050_Audit_rejects_empty_or_incomplete_outcomes`, which are meant to run on Linux.

The mechanism that matches this shape is the in-method `SkipTestException` on `!OperatingSystem.IsWindows()`, leaving `Audit` and the literal rosters untouched. CARD-1050 explicitly did not want that skip. Category Unit makes that choice a Unit-lane failure on every Linux runner.
