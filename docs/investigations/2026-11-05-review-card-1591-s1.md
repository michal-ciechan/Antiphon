### B-2: historical withhold evidence can create false or duplicate Critical incidents

Where: server/Application/Services/ChannelBridgeService.WithheldIncident.cs:62-71, 87-105; server/Application/Services/SessionMessageQueueService.DialogAdmission.cs:35-59; tests/Antiphon.Tests/Application/ChannelInputWithheldIncidentTests.cs:99.

Failure: a channel row charged for a dialog refusal can subsequently wait legitimately while its Running session works, compacts or is suspended. WithholdCount/FirstWithheldAt are deliberately retained, so this row still satisfies every scan predicate and raises ChannelInputWithheld at ten minutes. Running is process state, not idle/eligible state. Existing ContinuityHoldIncidentAt, SuspensionHoldIncidentAt and LivenessHoldIncidentAt are also never checked: a previously incidented inbound that is later queued and withheld can raise a second Critical incident for the same inbound, contrary to the brief's exclusion.

Why: D-4's historical-field predicate is insufficient for the stronger no-false-alarm requirement in this review brief. The test named WorkingUnchargedRowStaysQuiet only seeds withholdCount=0; it does not put the recipient into a Working state and does not exercise a previously charged row.

Fix: use the existing durable eligibility/hold state to exclude legitimate current holds and enforce the agreed per-inbound suppression across existing hold reasons. Preserve the input guard. Add independent busy/compacting/suspended and existing-stamp cases using the real producer and queue.

Attribution: introduced behavior, identified by source tracing; no unmutated reproduction is claimed.

### B-3: the final eligibility check is not synchronized with queue disposition

Where: server/Application/Services/ChannelBridgeService.WithheldIncident.cs:84-122.

Failure: only ChannelInbounds is locked. After the scan reads a Pending queue row at line 92, another transaction may deliver, cancel or transfer it before line 121 commits the incident. Queue status, attempts, withhold reset and session state are ordinary nonlocking reads, so the inbound lock does not fence those updates. Rows already Sent/Canceled/transferred before the reads are excluded; that does not close the read-to-write race.

Why: the transaction provides atomic stamp-plus-incident insertion and serializes competing scanners, but it does not provide atomic eligibility against queue writers.

Fix: make eligibility and incident/stamp insertion share an audited database serialization boundary with the queue disposition, preserving a consistent lock order and avoiding the session queue semaphore. Add deterministic barrier tests for delivery, cancel and transfer between eligibility read and commit.

Attribution: introduced concurrency gap, identified by source inspection; no live race reproduction is claimed.

### B-4: the 64-row cap still performs N+1 reads and does not bound backlog scan cost

Where: server/Application/Services/ChannelBridgeService.WithheldIncident.cs:56-77, 82-122; server/Infrastructure/Data/AppDbContext.cs:654, 1780.

A full page makes 193 SELECT statements, plus 64 SaveChanges operations and transaction boundaries. The full inbound read also materializes EnvelopeJson although the incident must not use its body. Take(64) caps returned IDs, not rows scanned/sorted to find them. No index leads the global FirstWithheldAt ordering/eligibility predicate; the existing channel-correlation partial index requires a ChannelReplySettledAt predicate absent here.

Why: this violates the brief's no-N+1 requirement and provides no 340+ backlog cost evidence. The plan itself prescribed no index, so the plan needs correction too. A blocked first row lock also delays the remaining page; there is no SKIP LOCKED or pass-local wait bound.

Fix: batch/project only required fields, use bounded nonblocking claims with consistent lock order, and measure the actual query plan/command count on 340+ pending rows and retained historical data before deciding the required index. Preserve one atomic incident/stamp result per inbound.

Attribution: introduced implementation/cost gap; counts above are source-derived, not measured database round trips.

### B-6: the scan task can silently end on non-shutdown cancellation
