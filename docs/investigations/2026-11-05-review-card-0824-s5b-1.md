## Advisories

- **A-1: legacy release re-read swaps the validated snapshot (Checkout path).**
  - Where: `DesktopLegacyReleasePolicyService.cs:298` (`fresh = …SingleAsync` after inspection) and
    `:405` (`PrecheckAsync` replaces `task`).
  - Failure: if a terminal Checkout task's row changes after `Classify` and before the action,
    `ReleaseSystemAsync` gets the *new* `ConcurrencyToken`. The I-8 `stale_approval_snapshot` fence
    therefore no longer binds the release to the row that `Classify` judged, and the precheck evidence
    comes from yet another read.
  - Why not a blocker: `ReleaseCoreAsync` re-checks status, settling floor and source SHA, and the
    guarded removal re-proves dirty, source and origin (`Removal_re_proves_every_fact_after_filing`).
  - Fix: read into a separate variable and hold `task_changed` unless its `ConcurrencyToken` equals the
    validated row's. Apply the same fix in `PrecheckAsync`.
- **A-2: Checkout-path deltas the Code report does not list. All are safe direction; state them in
  rollout notes.**
  - (a) `TaskWorktreeRetirementService.RemoveRemoteMirrorAsync:547-550` now skips unreleased slots and
    `ReloadAsync`s the task. It no longer clears a held slot's `RemoteWorktreePath` (an improvement),
    but the reload would discard unsaved tracked edits to that row. I found no current caller with such
    edits.
  - (b) `DesktopLegacyReleasePolicyService.Fingerprint` now includes kind and binding, so every existing
    check-cursor fingerprint changes once on deploy, giving a one-time recheck of backed-off trees.
  - (c) `CardWorktreeCleanupService` rediscovery recomputes `ExclusionReason` on existing targets.
  - (d) The protocol now reloads the operation before `RequireTaskIdentityAsync`.
  - (e) `GuardedWorktreeRemoval` reads the owner row once per removal.
- **A-3: the owner-row refusal in `GuardedWorktreeRemoval` (`:26-28`) has no witness (O-1 survives).**
  It is the only RefOnly fence for callers that build a Checkout-typed source, such as
  `DelegationWorktreeService.RemoveLocalAsync` (LocalMerge) and `VerificationCleanupService`.
  `TryMergeBackCoreAsync` also runs symbolic-ref, commit and rebase in `task.WorktreePath`. For a
  RefOnly owner, that path is the identity path. Today it is unreachable: there is no producer, and
  the identity path is never registered. Fix: add a witness that calls the LocalMerge removal for a
  RefOnly owner whose source is typed Checkout. S5b-2 should refuse merge-back for RefOnly before any
  Git call in the identity path.
- **A-4: `ref_only_preparation_incomplete` (`AgentTaskLandSourceResolver.cs:54`,
  `AgentTaskLandingProtocol.cs:91`) has no witness (O-2 survives).** It is harmless now, because a
  Planned or RefCreated ref cannot pass branch or remote observation. S5b-3 creates those states and
  should add a witness, such as a land against a `RefCreated` binding.
- **A-5: the down-migration cannot run while RefOnly landings exist.** `Down` of
  `20261105110702_Card0824RefOnlyDesktopCoordinates` restores `GitDirectory NOT NULL`, which fails once
  RefOnly landing rows exist. This fails closed and matches the D-6 rule of draining before downgrade.
  Add it to the rollout notes.
- **A-6: C1 is sensitive to checkout location.** Its `card-intent` leg returns `artifact_unpreserved`
  when the checkout lives under `/tmp`, even with no mutation; it is green under `/work/worktrees`. I did
  not isolate the cause. SourceLanding Mutation shards for PC-62..PC-81 should use worktrees outside
  `TEMP`, or the fixture should be fixed first.
- **A-7: minor binding-path comparison.** `RecordPlannedAsync` checks for a conflicting binding owner
  with exact string equality on `RepositoryPath`, while `ResolveAsync` compares with `PathsEqual`. On
  Windows, a case-only difference could get past the unique index. There is no producer yet; S5b-3
  should normalise the path or compare with `PathsEqual`.
