## Mechanism and alternatives

- **The readiness failure initiated cleanup.** The dispatcher queues launch before the message. The service waits for readiness before marking the session Running or flushing that message. The adapter uses the 60,000 ms setting and logs the failed wait before returning false. The service throws on that false verdict, and its catch issues a generation-scoped kill before logging the launch failure. On Windows this kill path stamps `KilledByRequest` before calling the backend kill. That source sequence reconstructs the caller from the deadline warning, the stored PTY exit and the subsequent launch failure logs. [AgentTaskDispatcher.cs, line 6534](../../server/Application/Services/AgentTaskDispatcher.cs#L6534), [RunnerGrokAdapter.cs, lines 185 and 371](../../server/Infrastructure/Agents/SessionRunner/RunnerGrokAdapter.cs#L185), [AgentSessionService.cs, line 605](../../server/Application/Services/AgentSessionService.cs#L605), [readiness throw](../../server/Application/Services/AgentSessionService.cs#L2775), [cleanup catch](../../server/Application/Services/AgentSessionService.cs#L751), [generation kill](../../server/Application/Services/AgentSessionService.cs#L873), [PtyAgentRunner.cs, line 586](../../src/Antiphon.Agents.Pty/PtyAgentRunner.cs#L586)
- **The two screen reasons explain how the gate can time out.** A positive observation requires a recognized idle composer with qualified geometry, an empty input marker and the enabled hint. `Working` is a negative observation, including when recognized busy status or cancel/queue hints appear. Two stable positives spanning the settle interval are required to open the input gate. The logged count is the current streak, which resets on a negative observation. `mcpSeen` records that an MCP banner appeared at some point. Desktop `Unknown` identifies the last tracked classification. The lost capture prevents identifying the exact feature of the screen that failed recognition. The server2 `Working` capture establishes a second manifestation of the deadline and shows that a live, busy TUI can remain outside the gate. [GrokStartupReadiness.cs, lines 25 and 89](../../src/Antiphon.Agents.Pty/GrokStartupReadiness.cs#L25), [deadline report](../../src/Antiphon.Agents.Pty/GrokStartupReadiness.cs#L162)
- **Reported restart and launch race.** The session had already ended and the task had settled at the reported restart time. The normal restart preserves detached PTY hosts. Killing their sessions requires the explicit `-KillSessions` branch, which calls `/sessions/kill-all` ([session-runner-restart-health.ps1, lines 123 and 228](../../scripts/session-runner-restart-health.ps1#L228), [SessionRunnerRuntime.cs, line 2677](../../src/Antiphon.SessionRunner/SessionRunnerRuntime.cs#L2677)). There is no evidence of an earlier restart or drain overlap in the task history. The card's report that the runner was stale by 24–25 source changes lacks a historical runner build SHA in the retrieved evidence. Staleness is unproven as either the cause of the readiness failure or the reason the task was admitted.
- **Pool release, stall and cancellation.** The normal unowned-pool sweep excludes a Dispatched owner, and the stall detector selects a streaming run attempt. The retained task events and message show no started turn. Task cancellation ordinarily writes Canceled after stopping the delegate, and there is no such event. The independently recorded deadline and launch failure account for the stop in this window. - **Auth, native CLI exit and PTY host crash.** The recognized sign-in screen has a typed launch block and a task failure-code path. Neither that code nor an auth incident was retrieved. An unrecognized screen or profile condition remains possible. An ordinary spontaneous child exit would select `ProcessExited`, and the cold-host disappearance path records `ProcessVanished`. The stored `KilledByRequest` observation supports a kill path, with no affirmative crash evidence.
