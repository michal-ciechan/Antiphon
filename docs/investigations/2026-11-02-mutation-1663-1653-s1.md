## Method

- **Leases:** one build-slot lease per mutant. The command was `dotnet run --project tests/<P> -p:UseAppHost=false`
  with the default native output. Each lease built the mutant and ran its witness filter.
- **What counts as red:** a run counted as red only if it built with no `error CS`, ran a nonzero number of tests
  with 0 skipped, and the named assertion failed.
- **SessionRunner PCs:** one mutant per build. They all edit `SessionRunnerRuntime.cs`, so they cannot be batched.
  They were split across two detached worktrees at 907edaebb.
- **CARD-1663 and server PCs:** batched into rounds. Each round took at most one mutant per file, and each mutant
  in a round had its own witness method. These mutants are independent: they touch different files and methods,
  and each fails a different assertion.
- **Antiphon.Tests filter:**
  `/*/Antiphon.Tests.Application/*/(C1663*)|(a_draining_or_retired*)|(recovery_resolves*)|(program_wires*)|(Pty_identity_unproven*)`.
  It runs 12 tests per round.
- **Slot waits:** 60-451 s per lease.
- **Evidence root (outside the repo):**
  `/tmp/claude-1654/-work-worktrees-task-14adea19/a013bb8b-b283-4f84-a2fe-35ed5f3a668f/scratchpad/`.
  It holds per-mutant `*.diff`, `*.log`, `trx/*.trx`, `results-{A,B,C}.tsv`, and the mutation specs `muts.js`
  and `mutsA.js`.

## Decisions for the caller

1. **PC-26: equivalent by masking.**
   - **Why it cannot go red:** the designed site `SessionReconciliationService.cs:363` (pass 1c) comes right
     after `Status == "Running"` (:361). Every pending runner row reports `Starting`: CreatePendingConflict sets
     `_status = "Starting"`, and Herdr pending rows do too. So no pending row reaches :363.
   - The pass-1 filters at :519-520 and :1135-1136 are masked the same way.
   - The "held" half of V-8 (DB stays `Running`) therefore rests on the runner reporting `Starting`, and no
     server mutation at :363 can turn it red.
   - **Default:** reclassify PC-26 as equivalent in the test design.
   - **Alternative:** if the guard is meant to stand alone, add a V-8 sibling that seeds a `Running` +
     `Pending="pty_host_identity_unproven"` DTO and asserts the DB row stays `Running` with no relaunch. Note
     that this shape is not reachable in production.
2. **M1663-6: coverage survivor, low severity.**
   - **The gap:** no test pins the `eligible ? null : _directory.DrainState(id)` gate in HostStatsPollService.cs:145.
   - **Observable effect:** when the stats poll fails for a dispatch-eligible runner that is draining, HostStatsCache
     marks it `offline` and shows `UnavailableReason`. With the mutant that reason reads `"draining"`; today it
     reads `"stale"` or `"unavailable"`. This contradicts Review 53edd261's claim that eligible runners "get the
     same reason as before".
   - **Proposed witness** (not written): a HostStatsPollServiceTests case with an eligible runner in a draining
     state whose stats endpoint fails, asserting the pre-1663 reason.
   - **Alternative:** decide that `"draining"` is the better answer and drop the gate. The catalogue already
     says `"draining"` for an eligible draining runner.
3. **PC-D2: equivalent on the S1 path.**
   - **Why it does not go red there:** ReleaseUnprovenHostIfDead checks `_pendingReason` under the gate, and
     the first release clears it, so a second release never calls CompletePendingAsExited. Review b6b7abdc
     recorded the same survivor.
   - **Exposure:** the guard is unpinned for the other callers of CompletePendingAsExited (Herdr R2-R5/R7).
   - **Proposed witness** (not written): call CompletePendingAsExited twice on a pending row and assert exactly
     one SessionExited event and a `false` second return.
4. **PC-22: the documented equivalence is argued and holds.**
   - Review b6b7abdc and the CARD-1653 memory both argue it: the runtime's StartAsync catch
     (SessionRunnerRuntime.cs:760) calls `session.TearDownFailedLaunch()` on the same `_hostPid`, so skipping the
     inner teardown still kills the fake host.
   - This run confirms it: 3/3 green.
