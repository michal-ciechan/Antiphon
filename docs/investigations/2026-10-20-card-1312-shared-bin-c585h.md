## 1. Shared path and concrete failure mechanism

`New-C585Case` creates a GUID-suffixed scratch/results directory
(`scripts/test-run-checkpoint.ps1:65`), but `Invoke-C585Runner` independently
defaults `OutputPath` to `bin-c585h/` (line 84). Every call uses
`tests/Antiphon.Tests` (line 121) and the repository working directory (line 145).
The unique results directory therefore does not isolate build output.

Both `Test-C585_FreshResultsDir` calls omit `OutputPath` (lines 320 and 324).
`Test-C589_SlotGranted` also omits it (line 470). Neither requests `NoBuild`.
`Get-CheckpointOutputLayout` and `Get-CheckpointBuildStampPath`
(`scripts/run-checkpoint.ps1:280`, `scripts/run-checkpoint.ps1:394`) resolve them to:

```text
<repo>/tests/Antiphon.Tests/bin-c585h/
<repo>/tests/Antiphon.Tests/bin-c585h/checkpoint-build-source.json
```

The dotnet shim does not compile binaries: its build arm only exits with the
configured code (`scripts/test-run-checkpoint.ps1:41`); its run arm copies fixture
TRX (`scripts/test-run-checkpoint.ps1:52`). Nevertheless, the real checkpoint driver
creates the output directory and writes the build-source stamp after that successful
shim build (`scripts/run-checkpoint.ps1:1124`, `scripts/run-checkpoint.ps1:1133`).
The harness's outer cleanup removes its temporary results and control directories
only (`tests/Antiphon.Tests/Scripts/ScriptHarnessProcess.cs:44`,
`tests/Antiphon.Tests/Scripts/ScriptHarnessProcess.cs:124`). Those are separate from
the repository output directory.

Despite its name, `Remove-CheckpointCheckedFile` does **not** delete the old stamp.
It returns `pre-existing-build-source` if the stamp exists, or `pre-existing-output`
if its parent exists (`scripts/run-checkpoint.ps1:384`). Its caller records a failed
build with exit 2 before invoking the shim (`scripts/run-checkpoint.ps1:1100`).
The run phase is skipped and the driver exits 2
(`scripts/run-checkpoint.ps1:1158`, `scripts/run-checkpoint.ps1:1177`).

Concrete sequential reconstruction, matching the stored baseline account:

1. Begin with that output absent. `C585_Green` calls the default runner
   (`scripts/test-run-checkpoint.ps1:193`), succeeds, and leaves the stamp.
2. `C585_FreshResultsDir` first intentionally occupies its own results directory.
   The driver rejects it at `scripts/run-checkpoint.ps1:585`, before output handling;
   this is the intended first arm.
3. Its second invocation changes only the results stamp. Results admission succeeds,
   but the old **build** stamp still exists. It returns exit 2, so the assertion
   `C585 FreshResultsDir a different stamp succeeds` fails
   (`scripts/test-run-checkpoint.ps1:325`).
4. `C589_SlotGranted` subsequently obtains its scripted slot, hits the same existing
   build stamp, performs no build/run, and releases the slot in `finally`
   (`scripts/run-checkpoint.ps1:628`, `scripts/run-checkpoint.ps1:1169`).
   Its exit-zero, exact build-argv, and `POST,build,run,DELETE` assertions cannot pass
   (`scripts/test-run-checkpoint.ps1:474`, `scripts/test-run-checkpoint.ps1:475`,
   `scripts/test-run-checkpoint.ps1:480`).

The two methods can also contaminate each other without `C585_Green`: a successful
second arm of FreshResultsDir writes the shared stamp before SlotGranted starts;
conversely, a completed shim build in SlotGranted writes it before FreshResultsDir
starts, even if SlotGranted later fails an assertion.

### Concurrency, deletion, and reuse

Within one TUnit assembly process these cases are serialized:
`RunCheckpointScriptTests` has `[ParallelLimiter<ProcessSpawnLimit>]`
(`tests/Antiphon.Tests/Scripts/RunCheckpointScriptTests.cs:13`), whose `Limit` is 1
(`tests/Antiphon.Tests/TestHelpers/ProcessSpawnLimit.cs:15`).
Direct harness all-case execution is also sequential
(`scripts/test-run-checkpoint.ps1:1228`).

The limiter is not a cross-process lock. Independent harness or test-host processes
in the same checkout can overlap, and the offline slot shim is not a real shared
lease (`scripts/test-run-checkpoint.ps1:108`). No concurrent schedule is needed to
explain the recorded red, and no actual concurrent race was established here.
These two build-mode cases collide and refuse; they do not delete or intentionally
reuse the other's output. The separate `C585_NoBuild` case explicitly requests reuse
(`scripts/test-run-checkpoint.ps1:330`, `scripts/run-checkpoint.ps1:616`).
