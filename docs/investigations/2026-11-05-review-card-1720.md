## Blockers

### B-1: the CLI `--total-timeout` lint refuses committed live-lane harnesses

- **Where:** `tools/Antiphon.Checkpoints/Program.cs:673-688` (`LoadSelection`). It compares against `RowTimeout.DeriveTotalMinutes`, which includes the `max(30, ...)` floor (`tools/Antiphon.Checkpoints/Execution/RowTimeout.cs:21`).
- **Failure:** whenever any selected row has a positive `EstimatedMinutes`, every `--total-timeout` below 30m is refused with exit 2, whatever the row budgets are. Totals between 30m and `2*sum+10` are refused as well. The following committed callers pass no `--total-timeout-override-reason` and are now refused before they start:
  - `scripts/test-live-lane-startup.ps1:44`, `scripts/test-live-lane-delivery.ps1:44` and `scripts/test-live-lane-isolation.ps1:78` pass `--total-timeout 26m`. Their rows come from `docs/superpowers/plans/2026-10-31-card-1545-s1c-test-design.md`: CP-3 6, CP-19 6, CP-18 6 and CP-24 10 minutes. That derives 30 or more. With `-Controls`, startup derives 32 even without the floor.
  - `scripts/test-live-lane-evidence.ps1:149` passes `-TotalMinutes 20` for CP-29, which has an estimate of 1. That derives 30.
- **Reproduced at the subject tip with the built tool:**
  1. `import --plan docs/superpowers/plans/2026-10-31-card-1545-s1c-test-design.md`
  2. `run <yaml> --rows CP-3 --total-timeout 26m` gives `refused: checkpoint-total-below-derived: explicit totalTimeoutMinutes 26 is below derived 30`, exit 2.
  3. The same command with `30m` passes the lint and stops at the deliberate `source_mismatch`.
- **Coverage gap:** no test exercises the existing callers. The only pre-existing CLI-total test, `CheckpointAdmissionContractTests` (10m), uses a command row with no estimate, so the lint skips it. Committed docs also carry about 30 `--total-timeout` examples below 30m (10m, 12m, 15m to 28m). These are historical, but they show that small totals are normal use.
- **Why it matters:** the card asks for a lint against "the real sum of the row budgets". The 30-minute floor is a default for when no total is given. It is not a row-budget derivation. The change breaks working harnesses that ran fine before.
- **Smallest fix:**
  1. Lint against the estimate-derived value `2*sum+10`, without the floor, in all three entry points. The docs and template sentence `Derive total=max(30,2*sum+10)` then describe the default, not the lint threshold.
  2. Update the four scripts to a total at or above their selection's derivation, or pass `--total-timeout-override-reason`. The startup `-Controls` case needs at least 32m.
  3. Add a test that drives `LoadSelection` with each script's real row selection and total.

  An alternative is to drop the CLI check and keep only the plan/YAML directive lint, since the incident's explicit 30 came from the request. Either way, the scripts must be re-verified.
