## Findings by question

### (1) A-1: loops cannot stop the host and do not spin

- The host keeps the default `BackgroundServiceExceptionBehavior.StopHost` (no override in server/ or
  src/). `ExecuteAsync` still rethrows the first sibling to complete. The fix does not rely on
  that setting. Each loop handles every exception except a host-token OCE:
  - wake `ChannelBridgeService.cs:214`: `ex is not OperationCanceledException || !ct.IsCancellationRequested`,
    logged at Warning; the outer `catch (OperationCanceledException) when (ct.IsCancellationRequested)` ends it.
  - stall check `:381`: the same filter. `Task.Delay` sits outside the inner try, so only the host token
    can end it.
  - withheld `WithheldIncident.cs:104-125`: `return` only when `ct` is cancelled. Any other exception,
    including report-write failures, is logged and the loop continues.
- Shutdown: every loop condition is `!ct.IsCancellationRequested`. A non-OCE thrown during shutdown is
  logged and the loop exits on the next check. V-1 joins each loop within 5 s after cancelling.
- No hot loop. After a failure the wake loop waits `WakeIdleTick` (10 s) or the next inbound signal, and
  drains every queued signal before the next pass. So its rate is bounded by inbound acceptance plus
  6 passes a minute. The withheld loop always waits 10 s, including after a report write. The stall
  check runs once a minute. At most one Warning per pass (two in the withheld loop when the report
  write also fails). The delay is fixed, not exponential, which is acceptable at these rates.

### (2) A-2: starvation, query-only

- No migration and no model change. The page statement gains two `EXISTS` semi-joins, evaluated
  before `LIMIT 64`:
  - an unstamped inbound with an agent (`ChannelInbounds.QueueMessageId` is indexed, AppDbContext.cs:665);
  - a Running session (PK lookup).
  No DDL, lock or snapshot concern, and the previous binary is unaffected. The partial index, the keyset
  cursor, `FOR UPDATE OF q SKIP LOCKED`, `lock_timeout 100ms`, `statement_timeout 2s` and the 5 s pass
  bound are unchanged. The candidate statement still re-checks every predicate under lock.
- Witness: `C1723_IneligibleBacklogDoesNotConsumePage` (incident and stopped). It seeds 192 older,
  already-stamped (or Stopped-session) withheld heads and one fresh eligible row. The fresh row must be
  stamped on the first pass with at most 16 DB commands, and no input is sent. Mutants M2 (PC-4) and
  M6 (PC-5) each turn exactly their own variant red.

### (3) A-3: consecutive-failure attention item

- After 3 consecutive failed passes, one Critical `ChannelReplyLost` incident is written with reason
  `ChannelWithheldScanFailed` and a null AgentId. It surfaces through the existing
  `RecentCriticalIncident` attention projection. There is no new kind or sink.
  - Once per streak: `_withheldFailureReported` is the latch.
  - Retries reuse the same GUID with `ON CONFLICT ("Id") DO NOTHING`, so an uncertain commit cannot
    duplicate the row.
  - A successful pass resets the counter, the latch and the id, so the next streak re-arms.
- Witness: `C1723_RepeatedScanTimeoutRaisesOnceAndSuccessRearms`, normal variant and first-write-cancelled
  variant. It checks the K-1 quiet / K once / sustained once / reset / re-arm sequence. It also reads a
  real `AttentionService` row: one grouped item whose evidence says "3 consecutive". Mutant M3 (PC-6)
  turns both variants red.
- Not noisy: `IncidentPageNotifier` filters `AgentId != null`, so this monitor incident never pages
  Telegram (see A-3 below).

### (4) No input, no queue lock, no flush

The new code is two catch filters, two `EXISTS` predicates and `ReportWithheldScanFailureAsync`. That
method opens its own scope and transaction and makes one bounded `INSERT ... ON CONFLICT`. None of this
writes session input, takes the session queue semaphore, or calls `FlushSessionAsync`. Every V-2 variant
asserts `SentInput` is empty. No input wait changed: nothing new parks or releases a session, so the
parking question (CARD-1083) does not apply.

### Producer to recipient

Delivery code is unchanged. The changed wake catch sits on the producer-to-recipient path. R-2

## Advisories

A-1 (`ChannelBridgeService.cs:316` and `:483`; availability, pre-existing shape). The per-agent batch catch
in `DrainPendingAsync` and the wake-refusal catch in `ProcessAgentGroupAsync` still exclude every
`OperationCanceledException`.
- Failure: one agent's local cancellation escapes `Task.WhenAll` and aborts the rest of the pass. A
  plausible source is an HttpClient timeout surfacing as `TaskCanceledException` from the wake call. The
  owned-session flush sweep and `PassCompleted` are skipped for every agent, and the loop now retries.
  If the cancellation repeats on each pass, the stall check raises `ChannelWakeWorkerStalled` after
  5 min, although other agents' batches progressed. Before this change, the same exception stopped the
  host, so this is a strict improvement.
- Smallest fix: use the same host-token filter (`ex is not OperationCanceledException || !ct.IsCancellationRequested`)
  at :316 and :483. Add a witness where one agent's wake throws a non-host OCE while a second agent's row
  is still queued and the pass heartbeat advances.

A-2 (page SQL residual population; latency only). The page now excludes stamped inbounds and non-Running
sessions. It still admits rows the candidate statement excludes for as long as their state lasts:
- inbounds carrying `ContinuityHoldIncidentAt`, `SuspensionHoldIncidentAt` or `LivenessHoldIncidentAt`
  (a previously held inbound later queued and withheld is excluded permanently);
- agents under a supervision or compaction hold;
- transcript-working sessions.
Such rows can still use page budget. A newly aged row is reached within about 10 s x ceil(N/64) plus a
wrap tick, so this is not a missed alarm. Smallest fix if it matters: add the three inbound hold-stamp
predicates to the `ChannelInbounds` EXISTS.

A-3 (presentation of the monitor incident). The incident has a null AgentId.
- `AttentionService` groups by (AgentId, Kind), so the item is labelled "session unknown" and carries an
  OpenAgent action with no agent.
- It also merges with any other null-agent `ChannelReplyLost` rows.
- It never pages: `IncidentPageNotifier` requires an AgentId.
This matches the brief (existing attention kind, no new sink). The operator should know the scan-failure
signal is dashboard-only, not a Telegram page.

A-4 (test strength and history).
- V-1's wake variant counts SQL commands. It does not prove that a pending inbound is delivered after
  the faulted pass. Seeding one inbound and asserting it reaches the queue/transcript would bind the
  producer-to-recipient outcome directly.
- The `failIncidentWrite: true` variant of V-3 and the Warning-level assertion were added in the fix
  commit e33acee6b. They were never red before the fix. PC-9 (Mutation) is their real detector.
