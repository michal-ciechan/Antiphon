## Measurement rule

For each TUnit process: outer wall starts immediately before the build-slot wrapper and ends when it exits. Runner wall starts immediately after slot grant (including subsecond wrapper launch overhead). **Pre-first-body** is grant to the first executed `UnitTestResult/@startTime`; **execution span** is first start to last `UnitTestResult/@endTime`; **post-last-body** is last end to wrapper exit. These outer setup/teardown measurements are upper bounds for the one-time assembly hooks because they also include runner discovery/reporting and possibly the first/last test's local hook. **Case sum** is the sum of `UnitTestResult/@duration` for executed cases, which can exceed execution wall because tests overlap. **Body occupied** is the union of all reported case intervals; **in-run gap** is execution span minus that union. TUnit's TRX does not report `[Before(Test)]` and `[After(Test)]` as separate phases: E2E's serial test structure exposes their cost as gaps between test bodies, mixed with scheduling and diagnostics. Do not mislabel those gaps as one-time setup or as test-body execution. Slot wait and build are separate. For Vitest, a temporary reporter recorded each `TestCase.diagnostic().startTime` and `duration`; its per-file setup is overlapping worker work, not one global fixture.

The timestamp wrapper records monotonic elapsed seconds and UTC launch time in JSONL. The build used a fresh `bin-a7timing/` output, `--no-incremental --force`, `UseAppHost=false` for the documented Linux FakeClaude collision, and `-nodeReuse:false`. NuGet package and npm package caches remained warm; this is a clean compilation/output measurement, not a cold network download.

### Named boundaries and what they do

- **Antiphon.Tests:** `TestDbFixture.InitializeAsync` in `tests/Antiphon.Tests/TestHelpers/TestDbFixture.cs` is `[Before(Assembly)]`. `SharedStoreWarmup.SelectionNeedsSharedStore` checks the selected tests; if true, `TestDbFixtureLifecycle.BootstrapAsync` creates and starts one `postgres:16-alpine` Testcontainer, runs EF `Database.MigrateAsync`, clears the pool, clones `antiphon_test` to `antiphon_tmpl`, marks it a template and disallows connections. `ProductionRunnerGuard.PointEveryProgramBootAwayFromTheProductionRunner` and `PtyBackendEnvGuard.ClearInheritedPtyBackend` are other assembly hooks. The first test begins only after these. `TestDbFixture.DisposeAsync` is `[After(Assembly)]` and releases the owned container after the last test. `TransactionalTestBase.SetupAsync` and `TeardownAsync` wrap *each* database test with begin/rollback/dispose; `CreateIsolatedSchemaAsync` clones a database under a fixture-wide clone lock inside individual test cases. The one-time database start is paid once by the entire selected assembly, while these latter costs remain per case.
- **Pty:** `PtyBackendEnvGuard.ClearInheritedPtyBackend` in `tests/Antiphon.Agents.Pty.Tests/PtyBackendEnvGuard.cs` is `[Before(Assembly)]`; there is no shared database or global browser hook. Process creation is in test bodies and their local fixtures. The first/last TRX case boundaries therefore enclose the substantive suite work, with only runner discovery/assembly guard before and runner reporting after.
- **E2E:** `PtyBackendEnvGuard.ClearInheritedPtyBackend` and `OwnedLandServerChild` are `[Before(Assembly)]` hooks. `SharedApp.GetAsync` in `tests/Antiphon.E2E/Fixtures/SharedApp.cs` lazily creates a single shared `AntiphonAppFixture` on first use; `SharedAppTeardown.TearDownSharedApp` is `[After(TestSession)]`. Most browser classes instead call `AntiphonAppFixture.InitializeAsync` and `PlaywrightFixture.InitializeAsync` from `[Before(Test)]`, then dispose them from `[After(Test)]` (for example `BoardE2ETests`). `AntiphonAppFixture.InitializeAsync` concurrently starts an isolated SessionRunner and Postgres container, then `StartHostAsync` starts Kestrel via `WebApplicationFactory`. Browser launch is `PlaywrightFixture.InitializeAsync`; context creation is per test. These local hook costs fall **between reported TRX bodies** in this run, rather than in the one-time assembly setup/teardown. Some cases report a zero body duration after their `[Before(Test)]` failed. `UsePrebuiltFrontend` resolves `client/dist` and `EnsureClientBundleIsCurrent` rejects stale output.
- **Vitest:** `client/vite.config.ts` selects `jsdom` and `src/test/setup.ts`. That setup module installs DOM shims, uses `beforeAll` to call MSW `server.listen`, `afterEach` to call Testing Library `cleanup` and `server.resetHandlers`, and `afterAll` to call `server.close`. These are per test file/worker lifecycle hooks, not one global fixture. Vite config load, transforms and worker startup precede the first test; closing workers and reporter output follow the last. `scripts/test-client.ps1` can emit JSON with `-JsonResultPath` without changing test behavior.

## Recording design

`tools/Antiphon.Checkpoints` already writes `ReportBuild.Seconds`, `ReportRow.Seconds`, and TRX-derived class sums to `report.json` (`ReportModel.cs`, `RowRunner.cs`, `TrxReport.cs`). Extend its TRX parser to retain earliest case start, latest case end, case-duration sum, **union of case intervals**, and executed count; record the child process start/end in `RowRunner`/driver. Add a nullable `timing` object on each row: `slotWaitSeconds`, `buildSeconds`, `setupSeconds`, `executionWallSeconds`, `bodyOccupiedSeconds`, `testDurationSumSeconds`, `inRunGapSeconds`, `teardownSeconds`, `wallSeconds`, `timingSource`, and `clockValid`. The in-run gap is the signal for per-test fixture work and scheduling; call it exactly that until hooks emit their own markers. Use `null` when a TRX has no timestamps or a row times out; never invent zero. Keep existing report schema fields for compatibility and bump `SchemaVersion` when consumers have a reader update. This is a small extension of existing evidence, not a new runtime service.

For durable history, add the same parser to the **nightly runner** (`scripts/lib/nightly-tests-impl.ps1`) at its existing per-suite TRX verdict point and append one compact JSONL record per suite under its producer-owned `StateRoot`, with SHA, profile, host, filter/chunk, counts, phase seconds, and result. That root already retains per-run logs outside ephemeral worktrees. For client tests, `test-client.ps1 -JsonResultPath` supplies counts, per-file times and case durations but **omits case start times**; add a tiny Vitest reporter using `onTestCaseResult` and `testCase.diagnostic().startTime/duration`, as the temporary measurement reporter did. Mark per-file jsdom/MSW setup distinctly from one-time runner setup; do not compare its case sum as if files were serialized. For E2E, optional structured markers around `AntiphonAppFixture.InitializeAsync` and `DisposeAsync` can subdivide the large in-run gap into container, migration, host, browser and teardown cost without a tracing subsystem. A simple weekly query over the JSONL gives p50/p90 for each lane and surfaces setup drift. Full checkpoint rows can use their existing `report.json` immediately; nightly JSONL supplies a stable regular cadence without adding a database table.
