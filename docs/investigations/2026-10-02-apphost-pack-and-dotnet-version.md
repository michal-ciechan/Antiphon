# Apphost pack and .NET version for a cold Seed (2026-10-02)

## Verdict and evidence boundary

- **CONFIRMED:** The Seed smoke explicitly demands `Microsoft.NETCore.App.Host.linux-x64/9.0.20` in the NuGet cache, asserts that the SDK pack directory does not contain it, and builds and executes a `net9.0` native apphost with an empty package source (`scripts/c590-remote.sh:1435-1466`). An empty cache therefore fails before Seed can pass. The smoke pins `RuntimeFrameworkVersion=9.0.20` and `TargetLatestRuntimePatch=false`; the SDK's `KnownAppHostPack` also names `9.0.20` for `net9.0`.
- **CONFIRMED:** The runner image is built with `mcr.microsoft.com/dotnet/sdk:10.0` and based at runtime on `mcr.microsoft.com/dotnet/aspnet:9.0`; the build stage's `/usr/share/dotnet` is copied into the `session-testing` image (`docker/session-runner-grok/Dockerfile:35-45,166-169,207-209`). The `10.0` tag floats; the Dockerfile does not pin an SDK patch or image digest. `global.json:2-8` asks for SDK `10.0.204`, `rollForward: latestMinor`, and Aspire AppHost SDK `9.5.2`. This is already an SDK 10 / target .NET 9 repository, not an SDK 9 repository.
- **CONFIRMED, local task container:** `dotnet --list-sdks` returned `10.0.401`; `dotnet --list-runtimes` returned `Microsoft.NETCore.App` and `Microsoft.AspNetCore.App` at both `9.0.20` and `10.0.12`. `/usr/share/dotnet/packs` has `Microsoft.NETCore.App.Host.linux-x64/10.0.12`, `Microsoft.NETCore.App.Ref/10.0.12`, and `Microsoft.AspNetCore.App.Ref/10.0.12`, but no 9.0 versions. In this installed SDK, `Microsoft.NETCoreSdk.BundledVersions.props:161-179` declares the *known* `net9.0` runtime, reference pack and apphost pack at `9.0.20`; the declaration does not mean those packs are physically installed. The SDK target explicitly generates `PackageDownload` items for missing packs (`/usr/share/dotnet/sdk/10.0.401/Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.FrameworkReferenceResolution.targets:78-86,190-225`).
- **UNCONFIRMED, live server2 container:** `ssh mc@server2` first refused host-key verification; with a temporary non-persistent host-key setting it refused public-key authentication. No `docker inspect` or `docker exec` on the current server2 runner was possible from this mirror. CARD-0849's 2026-09-30 host observation says the runner then had SDK `10.0.401`, only the `10.0.12` apphost pack in `/usr/share/dotnet/packs`, and a separately cached `9.0.20` NuGet apphost pack. That is historical board evidence, not a fresh live-container measurement. Recheck with `ssh mc@server2 'docker exec antiphon-runner-session-runner-1 dotnet --list-sdks'`, the corresponding `--list-runtimes`, and a read-only `ls`/`cat` of its SDK `Microsoft.NETCoreSdk.BundledVersions.props` when authorized SSH works.

## Version inventory

- **CONFIRMED:** Every one of the repository's **41** `.csproj` files declares `<TargetFramework>net9.0</TargetFramework>` (reproduce with `rg -n '<TargetFramework>' --glob '*.csproj' .`; representative application, host, and test citations: `server/Antiphon.Server.csproj:4`, `Antiphon.AppHost/Antiphon.AppHost.csproj:6`, `src/Antiphon.SessionRunner/Antiphon.SessionRunner.csproj:4`, `tests/Antiphon.Tests/Antiphon.Tests.csproj:4`). `Directory.Build.props:14-25` and `Directory.Build.targets:25-27` do not set target framework, `TargetLatestRuntimePatch`, `RollForward`, or a runtime version. The sole project `RollForward` is `Major` in `tools/Antiphon.Checkpoints/Antiphon.Checkpoints.csproj:11`; no project pins `RuntimeFrameworkVersion` or `TargetLatestRuntimePatch`. The Seed smoke is the explicit exception (`scripts/c590-remote.sh:1451-1452`). `global.json`'s SDK roll-forward governs SDK selection, not app runtime roll-forward.
- **CONFIRMED (Microsoft release metadata, 2026-10-02):** Latest stable .NET 9 is runtime `9.0.20` and SDK `9.0.318` (9.0.3xx band); it is STS in maintenance until **2026-11-10**. Latest stable .NET 10 is runtime `10.0.12` and SDK `10.0.401` (10.0.4xx band); it is active LTS until **2028-11-14**. .NET 10 is the latest generally available stable release; .NET 11 is RC only. Sources: [Microsoft download table](https://dotnet.microsoft.com/en-us/download/dotnet), [official release index](https://builds.dotnet.microsoft.com/dotnet/release-metadata/releases-index.json), and [.NET 9 release record, which pairs SDK 9.0.318 with runtime 9.0.20](https://builds.dotnet.microsoft.com/dotnet/release-metadata/9.0/releases.json).
- **CONFIRMED:** Current version alignment is mixed: Aspire `9.3.0` package and project SDK versus `9.5.2` in `global.json` (`Antiphon.AppHost/Antiphon.AppHost.csproj:2,14-16`; `global.json:7`); EF Core and Npgsql EF Core are 9.x (`server/Antiphon.Server.csproj:43-51`; `src/Antiphon.Messaging.Service/Antiphon.Messaging.Service.csproj:20-21`); TUnit is `1.44.0` (`tests/Antiphon.Tests/Antiphon.Tests.csproj:17`). CI still installs `9.0.x` (`.github/workflows/ci.yml:20-22,41-43`) while Docker and `global.json` select SDK 10.

## Why the `9.0.20` download occurs

**CONFIRMED:** A `net9.0` `Exe` with `UseAppHost=true` and RID `linux-x64` selects `Microsoft.NETCore.App.Host.linux-x64` at `9.0.20`: the project's `RuntimeFrameworkVersion` is `9.0.20`, the SDK's `KnownAppHostPack` names `9.0.20`, and `ResolveAppHosts` receives both the runtime version and known pack list (`scripts/c590-remote.sh:1451-1452`; local SDK `Microsoft.NETCoreSdk.BundledVersions.props:173-177`; `Microsoft.NET.Sdk.FrameworkReferenceResolution.targets:184-225`). `TargetLatestRuntimePatch=false` suppresses automatic runtime patch selection; it does not install a pack. The missing-pack condition is **a matching 9.0.20 apphost absent from `/usr/share/dotnet/packs` and from NuGet's cache**, not merely an SDK older than the target runtime. SDK 10.0.401 knows the 9.0.20 pack but physically ships the 10.0.12 pack. The SDK downloads missing packs during restore (SDK target cited above; [Microsoft NETSDK1145 documentation](https://learn.microsoft.com/en-us/dotnet/core/tools/sdk-errors/netsdk1145)). With an empty source, this works only if the package is already cached.

**CONFIRMED:** `UseAppHost=false` is the Linux checkpoint default (`scripts/run-checkpoint.ps1:164-174`; `docs/testing-and-build.md:216`). It does **not** remove all native apphosts from the test graph: the `Antiphon.Tests` targets restore/build PtyHost, FakeClaude and FakeGrok again with `UseAppHost=true` (`tests/Antiphon.Tests/Antiphon.Tests.csproj:171-198`), as do the E2E and SessionRunner test targets (`tests/Antiphon.E2E/Antiphon.E2E.csproj:53-63`; `tests/Antiphon.SessionRunner.Tests/Antiphon.SessionRunner.Tests.csproj:61-67`). CARD-0847 documents the resulting cold-cache failure. These native executables are needed by their tests; changing the outer checkpoint switch alone does not fix them.

## Options and cold-cache effect

| Option | Effort / risk | Cold Seed effect |
|---|---|
| **A. Add latest 9.0 SDK alongside SDK 10** | **Medium.** SDK 9.0.318 should supply the matching 9.0.20 host and reference packs ([release record](https://builds.dotnet.microsoft.com/dotnet/release-metadata/9.0/releases.json)); confirm pack inventory in a rebuilt image. Keep SDK 10 because `global.json` requires it. Replacing `sdk:10.0` with `sdk:9.0` alone breaks that pin. Copying the needed packs from a pinned SDK 9 stage is narrower than installing both SDKs. Follow the Dockerfile's pinned version / checksum conventions for new downloaded artifacts; floating `sdk:9.0` tags do not provide an immutable patch. | **INFERRED:** The existing net9 apphost smoke can restore offline with an empty NuGet source once both 9.0.20 host and reference packs physically exist under `/usr/share/dotnet/packs`. The smoke checks in `scripts/c590-remote.sh:1444-1446` must change because they currently *require* the NuGet entry and *forbid* the SDK pack. Real repo builds still need ordinary NuGet packages. |
| **B. Make the Seed smoke `UseAppHost=false`** | **Small for smoke, high coverage risk.** A plain `net9.0` library/Exe avoids the apphost, but SDK 10 also lacks the net9 reference pack, so it still needs `Microsoft.NETCore.App.Ref/9.0.20` from NuGet. A `net10.0` smoke could use SDK-bundled packs only, but would no longer prove net9 builds are ready. Running a DLL with `dotnet` would replace the native-executable assertion (`scripts/c590-remote.sh:1460-1462`). Existing test inner builds still require a native apphost. | **INFERRED:** Removes the special apphost download only for a smoke that no longer checks it; does not make net9 repo builds or the present Seed validation offline-capable by itself. |
| **C. Bake the 9.0.20 packs into the image** | **Small to medium.** Put the versioned host **and reference** packs under `/usr/share/dotnet/packs`, or use a verified offline package source with NuGet restore configured to consult it. A baked `/home/app/.nuget/packages` entry is hidden by the cache volume's `volume.nocopy: true` mount (`docs/docker-stack.md:5-15`). Pin artifact versions and hashes/digests and update as .NET 9 patches change. | **INFERRED:** Like A, makes the current net9 smoke independent of a warm NuGet cache after changing its cache-only assertions. Ordinary project `PackageReference`s still require online restore or a separately populated cache. |
| **D. Migrate the whole repo to .NET 10 LTS** | **Large, separate card.** Change all 41 TFMs, `global.json`/SDK policy, Aspire AppHost SDK and hosting packages, EF Core / Npgsql provider major versions, Docker build/runtime/test images, CI and nightly SDKs, and publish/test scripts. Check TUnit compatibility and client/build tooling; client JavaScript need not change solely because the server TFM changes. Validate database migrations, runtime/ASP.NET behavior, native pty-host and Linux/Windows tests before rollout. | **INFERRED:** With SDK/runtime 10.0.401/10.0.12 and all smoke/test projects on net10, SDK-bundled host and reference packs can eliminate this *net9* special-pack dependency. Other NuGet packages still need restore. A partial migration leaves net9 native producers needing the 9.0 pack. |

**CONFIRMED:** CARD-0849 is the parent cache-persistence rollout; this pack is one item in `/home/app/.nuget/packages`, not the whole cache. The Seed currently verifies that package plus cache layout, npm and a leased build (`docs/docker-stack.md:3-19,48-57`). Its donor-stage validation also requires both cached 9.0.20 host and reference package metadata (`scripts/c590-remote.sh:1595-1608`), and later hashes and recovery checks depend on those cache entries (`scripts/c590-remote.sh:1703-1704,2068-2105`). Thus moving the packs into the image requires revising the full Seed cache contract and controls, not only the three smoke assertions. An offline pack smoke and a populated ordinary dependency cache are separate conditions. A cold cache with no donor import may fill ordinary packages online, but the current empty-source smoke cannot make its first apphost-pack download online. The cold first-Seed path also needs coordination with CARD-0912, whose existing board text still assumes a saved archive.

## Recommendation

**INFERRED:** For the imminent cold Seed, keep the net9 native-apphost smoke meaningful and make 9.0.20 host **and reference** packs available outside the mounted NuGet cache, preferably by copying them from a pinned .NET 9 SDK image into the runner's `/usr/share/dotnet/packs`; revise the Seed's cache assertions, hash/recovery controls and first-Seed path, then verify the cold offline smoke in the rebuilt image. **INFERRED:** Plan a separate full .NET 10 LTS migration to honor the latest-stable preference and the approaching .NET 9 support end, while treating ordinary NuGet package restoration as an independent cache/online concern.
