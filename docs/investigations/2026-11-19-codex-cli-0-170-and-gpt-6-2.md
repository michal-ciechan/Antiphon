## 4. How the pin rides the rc/2026-11-29 rollout

`CODEX_VERSION` is an image build ARG. It changes only when a new runner image is built from a commit whose Dockerfile has the new pair. Product hosts track the current `rc/YYYY-MM-DD` tip, not master (`docs/docker-stack.md:5-8`).

Fetched 2026-11-19:

- `origin/rc/2026-11-29` is `26a99f1a747d94120aeff8f0d6b9a2e7c7d4e248` and still has `ARG CODEX_VERSION=0.160.0` at `docker/session-runner-grok/Dockerfile:136`.
- `origin/rc/2026-11-19` is `ab7af12c699039270af7e22a5d7fd794035bc325` and still has `ARG CODEX_VERSION=0.160.0` at line 135.

The upgrade has to land on `rc/2026-11-29` before that line's image rebuild. A master-only commit does not enter the rollout. The staged rollout is `scripts/deploy-server2.ps1 -Rolling -Sha <rc tip> -Phase <name>`, one phase per gate, after the live Windows qualification ends. Standing `server2` keeps accepting until `server2-temp` has passed canary. Running sessions stay on the old container until that runner is drained; the new image is a new container.

Order: server2 image first, desktop npm second. If the same rc SHA also switches High and Medium to `gpt-6.2-sol`, a desktop Codex still on 0.160.0 will be asked for a slug its catalog does not have. Do not dispatch desktop Codex at the new slug until `codex --version` there prints `0.170.0`.

Smoke after the server2 image is up, as uid 1654 on the new container, then a real session:

1. `codex --version` prints `codex-cli 0.170.0`. The image build already asserts this. Repeat it in the running container.
2. One Codex launch through `delegate.ps1 -Kind Codex` on server2. Watch the first screen for an update modal, a trust modal, or a Daybreak/consent dialog. The seeded config is supposed to skip update and trust for `/work/repos/antiphon`.
