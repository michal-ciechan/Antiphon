# CARD-0650: silent overnight dispatch stall

**Verdict: confirmed.** A dead repository-child journal fenced worktree dispatch. The dispatcher detected the hold on each queued task and escalated it in task events and server logs, but that path never enqueued a caller note. The task check and progress-stall paths only select dispatched or working tasks. The orchestrator received no prompt about the fence while idle, and it discovered the hold only after the operator asked about CARD-0647 at 07:05 UTC. This is a notification and aggregate-observability gap, not a failure of the hold detector.

All times below are UTC. The server log renders the same instants in London daylight time (`+01:00`). Evidence is from read-only PostgreSQL queries, stored transcript rows, the server log, and code. The observed running server had been restarted onto `048c9eb2` at 02:05 according to orchestrator transcript sequences 86383–86389; the cited hold, check, attention, pipeline, and health code is unchanged between that commit and this investigation checkout (`git diff 048c9eb2 c5e32c2` changes only other parts of `AgentTaskDispatcher.cs`).

## Why the existing surfaces did not prompt it

| Mechanism | Code path and observed limit |
| --- | --- |
| Hold aging | `TraceHeldAsync` persists a changed `Held` reason (`server/Application/Services/AgentTaskDispatcher.cs:874–887`). `EscalateHeldAgeAsync` persists one Warning and one Error `HeldAged`, logs them, and publishes `AgentTaskChanged` to subscribers; it does not call `SessionMessageQueueService` or enqueue a caller note (`AgentTaskDispatcher.cs:1019–1090`). The DB/log rows above prove it ran. An event-bus update requires a listening UI consumer; it is not a session prompt. |
| Progress stall detector | It selects only `Dispatched` or `Working` tasks with `DispatchedAt` and `AgentSessionId` (`AgentTaskDispatcher.cs:2603–2631`). Queued held tasks have neither dispatch timestamp nor worker session. Its `TaskProgressStalled` incident therefore could not be raised for this freeze. |
| Scheduled checks and check interpreter | `RunScheduledChecksAsync` likewise selects `Dispatched`/`Working` tasks with `NextCheckAt`, caller session, and session reply (`AgentTaskDispatcher.cs:3354–3373`). The interpreter is invoked by `AgentTaskCheckService.RunCheckAsync` for a selected task and its note is addressed to `ParentSessionId` (`server/Application/Services/AgentTaskCheckService.cs:139–154,225–247`). No check was selected for these three queued tasks, so interpreter health was immaterial to this stall. |
| CARD-0079 Check seats | The continuation sweep discovers only agents satisfying `StandingSpecialistSeatPolicy.Seat`; that policy is explicitly `AgentTaskRole.Check` (`server/Application/Services/CheckCompactionContinuationService.cs:62–94`; `server/Application/Services/StandingSpecialistSeatPolicy.cs:15–28`). It responds to an explicit auto-compaction boundary and silent synthetic continuation on such a seat, not an idle orchestrator or queued dispatch. `CheckCompactionRecoveries` had zero detections during this interval. |
| Attention feed | `AttentionService` builds `DispatchHeld` items from queued task `Held`/`HeldAged` events after 300 seconds, one item per task with the latest hold detail, severity, and `OpenDrawer` action (`server/Application/Services/AttentionService.cs:1217–1286`). At 02:49 it could have displayed three Error task items, each naming the same fence; it does not group them into a repository-wide condition or deliver them as caller prompts. The endpoint is a read-only GET (`server/Api/Endpoints/AttentionEndpoints.cs:8–23`). Server log request census for local 03:05–08:06 (`02:05–07:06Z`) found **zero** `GET /api/attention` requests. |
| Pipeline endpoint | `GET /api/agent-tasks/pipeline` is a read-only projection (`server/Api/Endpoints/AgentTaskEndpoints.cs:67–71`; `server/Application/Services/AgentTaskPipelineStatusService.cs:10–12`). It returns the three queued rows but `ToQueued` derives only shared-checkout lease, sibling land, routing pin, concurrency cap, or default `awaitingDispatch`; it never reads Held events or the child journal (`AgentTaskPipelineStatusService.cs:300–378`). A row with no other named reason appears as `awaitingDispatch`, not journal-fenced. Its one request in the freeze was at 07:05:43, after the human question (`...antiphon-20260924.log:5529–5533`). |
| Health | `/health` registers the PostgreSQL check and maps the health endpoint (`server/Program.cs:300–305,874–875`), with no dispatch or Git-journal check. The server log shows repeated health requests during the freeze (for example `...antiphon-20260924.log:3778–3780`); they say nothing about worktree admission. |

**Visibility verdict:** the task drawer/events and fleet attention feed could expose the fence only as separate task conditions. The pipeline's queue reason and `/health` did not expose it. There was no single dispatch-wide fence state or push to the idle orchestrator. The operator's 07:05 question caused the first effective read, about five hours after the first journal hold.

## Reproduction of the evidence join

Read-only queries used `docker exec -i antiphon-postgres psql -U antiphon -d antiphon`. Filter `AgentTasks` by the three IDs to compare `CreatedAt`, `DispatchedAt`, `CheckCount`, and `ParentSessionId`; join `AgentTaskEvents` by task ID and order by `At`; filter `SessionQueuedMessages` by the parent session and `CreatedAt` in `[02:05,07:07)`, and `TranscriptEntries` by the same session and timestamp. The critical absence claims are bounded to those windows; later delivery after recovery is a separate episode. The local server log file is not a durable DB ledger, so its request census supports the access observation only for the retained log interval.

## Remaining uncertainties

- The exact Git child command interrupted by the 02:03–02:05 restart is not proven. The stored journal, dispatcher hold reason, and successful recovery establish the fence mechanism; they do not assign the creating process beyond the journal's PID.
- There is no historical attention snapshot. The three `DispatchHeld` items at 02:49 are reconstructed from the retained queued/event rows and `AttentionService` code, not a captured HTTP response.
- The log request census covers this server's retained file; it cannot rule out a consumer of another server instance or an unlogged external observation. The parent session's persisted queue and transcript still show no prompt about the hold.

## Not done, noted

Minimal watchdog shape for Plan: group existing aged Held events by repository and identical fence reason, emit one deduplicated dispatch-wide condition and a receipt-tracked note to affected parent sessions after the error threshold, while leaving journal recovery manual.
