## Taxonomy proposal

### Exact write format, and how new labels coexist with legacy labels

These are the facts the write must respect, all read on master:
- **Labels are a JSON array of strings, and a write replaces the whole array.** `PATCH /api/cards/{id}/content` with `labels` does `card.LabelsJson = BoardService.SerializeLabels(request.Labels)` (`server/Application/Services/CardService.cs:639-640`). Leaving `labels` out means "unchanged". Sending `[]` clears the labels. The body also needs `concurrencyToken` (a fresh one: every write rotates it) and a non-empty `reason`. `GET /api/cards/limits` returns `maxReasonLength: 4000`.
- **There is no label count or length limit.** `GET /api/cards/limits` returns no label field: `{"maxTitleLength":300,"maxDescriptionLength":20000,"maxReasonLength":4000,...}`. The content validator (`CardService.cs:1805-1830`) has no label rule, and the column is `jsonb` (`AppDbContext.cs:1224`). Self-impose a limit: at most 8 labels per card, each at most 40 characters, all lower-case `[a-z0-9:-]`.
- **Where the comma-joined strings come from.** `scripts/card.ps1` declares `[string[]]$Labels` and sends `@($Labels)` (`card.ps1:177,784`). Under `pwsh -NoProfile -File card.ps1 ... -Labels a,b` PowerShell does not split the comma, so the server receives `["a,b"]`. Reproduced here with a stub script: `-File` gives `count=1 {"labels":["a,b"]}`, `-Command "& script -Labels a,b"` gives `count=2 {"labels":["a","b"]}`. 78 of the 110 labelled cards carry that artifact. **The bulk apply must therefore not go through `card.ps1 edit -Labels` under `-File`.** Send the JSON body directly with `Invoke-RestMethod`, or call card.ps1 in-process with a real array.
- **Reserved prefixes.** Do not use `status:` or `priority:`: the tracker sync owns and strips them (`TrackerSyncMarkers.IsManagedLabel`). Do not use `complexity:` or `ui:`: the diagnose seat owns them and keeps them at the end of the list (`CardDiagnosisLabels.cs`). `type:` and `area:` collide with neither.
- **Order matters on the card face.** The board shows only the first two labels (`client/src/features/board/BoardCard.tsx:55` `slice(0, 2)`; `CardRow.tsx:103` shows one when stacked). Search matches each element with `ILIKE` (`server/Infrastructure/Data/CardReadQuery.cs:23`), so substring search finds both legacy forms.

The recommended new list for each card is: `type:<t>`, then `area:<a1>`, `area:<a2>`, and so on, then each legacy word split on `,` and trimmed (de-duplicated, original order), then any existing `complexity:`/`ui:` labels. For example, CARD-0413 `["deploy,channels"]` becomes `["type:reliability-ops","area:deploy-rollout","area:channels","deploy","channels"]`.

This **prepends** the new labels, so the face shows type and first area. The brief said "append". Appending gives exactly the same set, but the face keeps showing the legacy pair. That is an operator choice; see the decision list. Splitting `"deploy,channels"` into two elements loses no word. Leaving it joined keeps one bogus `deploy,channels` label that no exact filter can match.

### Bulk-applying 376 writes safely

1. **Dry run first.** Read `2026-10-08-backlog-triage.json` (after the operator edits it). For each card, `GET /api/cards/{id}` and compute the new list as above. Write a diff file (old→new, one card per line) and review it. Skip any card whose new list equals its current one: the apply is idempotent and can be re-run.
2. **Pilot**: apply 10 cards, then `GET` each and check the stored array and the card face.
3. **Batches of 25**, at about 1 write per second, with a few seconds' pause between batches. Every content write appends a `CardRevision` and publishes a `CardChanged` SignalR event to every client (`CardService.cs:604-649`). A burst of 376 would storm open boards and the revision table for no benefit.
4. **Re-read the token for each card immediately before its PATCH**. Never reuse a token from the dry-run read. On `409` (a concurrent diagnose-seat or human write), re-read once, recompute from the new current labels, and retry once. If it fails again, log it and move on.
5. **One reason string** for every write, for example: `Backlog triage 2026-10-08 (docs/investigations/2026-10-08-backlog-triage.md): add type:/area: labels; legacy labels kept (comma-joined values split, no word removed).` Send labels only: no title, description, importance or urgency, so no other field changes. A labels-only write does not reset the rank position (`cellChanged` covers only importance and urgency, `CardService.cs:606-607,633-634`).
6. **Side effects to expect.** `UpdatedAt` moves to now on all 376 cards, so `-UpdatedSince` listings and anything that sorts by recency will see the whole backlog as touched once. None of the 376 Backlog cards is linked to a GitHub issue (`externalIssue` is null on every one), and card.ps1 says "Saving a card never syncs". So no label leaves Antiphon from this apply. A card exported to GitHub later would carry its `type:`/`area:` labels (`TrackerBidirectionalSyncService.cs:571-582`).
7. **Rollback.** Each card's previous `LabelsJson` is in its revision history (`GET /api/cards/{id}/revisions`, `card.ps1 history`).

The recommended states (close, merge, duplicate) are **not** labels. Act on them with `card.ps1 close`/`edit` and a reason, card by card, after the operator approves. Do not encode them as `triage:*` labels: those would go stale the moment the card moves.
