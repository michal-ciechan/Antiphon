## Verdict

- **Desktop checkouts per day are almost all runner halves.** 1,132 tasks created from 10-27 to
  11-03 got a desktop checkout, and every path is distinct: the leaf is `card-task-<own id>` in
  1,132 of 1,132. Of these, **1,070 (94.5 %) are runner halves** (server2 plus server2-temp) and
  62 are desktop-run. That is about **75 to 175 runner halves a day (median about 150)** and
  4 to 11 desktop-run tasks a day. This confirms plan §1's inference with the rows themselves.
- **Slot versus ref-only (A-D-6): ref-only.**
  - No runner-half consumer needs file *content* that git objects cannot give.
  - The land already tolerates a missing desktop half by design.
  - What does need a registered checkout today is the checkout's own maintenance: the
    settlement-sync fast-forward and its clean/registration postconditions, the push from it, and
    baseline `rev-parse HEAD` in it.
  - Slots add a hazard that this read found and the amendment does not cover: a released slot
    path gets reused while a later land of the old task still binds that path (§3).
  - Confidence: medium-high on the consumer table. The decision stays with `decide`.
- **Recommended cut.** S5b becomes a ref-only "no desktop checkout for runner tasks" slice with
  no pool. S5a and S5c are deferred, because desktop-run tasks (4 to 11 a day) are bounded by
  S4a. Effort is in §5.

## 1. What the dispatcher creates on the desktop per task

Code path, at base `c2f1f83a3`:

- `AgentTaskDispatcher.cs:5999-6001` calls `_worktrees.CreateForTaskAsync(claimed, repositoryLease, …)`
  under the repository mutation lease, inside the claim.
- `DelegationWorktreeService.CreateForTaskAsync` (`DelegationWorktreeService.cs:364-503`):
  - **SourceLanding Mutation on a runner**: the snapshot is created *on the runner*. `WorktreePath`
    is the runner path, and there is no desktop checkout (`:379-399`).
  - **SourceLanding Mutation on the desktop**: a verification snapshot (`:400-407`).
  - **Ordinary Worktree task, any runner**: it adopts an existing `task-<8hex>` registration
    (`:409-427`, retry or crash reuse). Otherwise it resolves the base (`-StartRef`/repair SHA,
    `-BaseTask`/card-current `cardBase`, requested ref, configured default; `:428-432`), mints the
    branch and calls `_worktrees.CreateAsync(repoPath, "task-<8hex>", baseRef, lease, branch)`
    (`:436-440`). The directory is `<WorktreeBasePath>\card-task-<8hex>` (preflight path,
    `:333-341`).
  - The `RunnerId` does not change this: **a server2 task gets the same full desktop checkout as a
    desktop task**.
- The runner half follows:
  1. `RemoteWorkspacePreparer.cs:255` → `RemoteWorkspaceService.PushBranchAsync`, which runs
     `rev-parse HEAD` and `git push origin <branch>` *in the desktop checkout*
     (`RemoteWorkspaceService.cs:107-129`);
  2. the runner mirrors the branch.
  3. The class comment states the design: "The DESKTOP worktree stays canonical … landing,
     retirement, residue and progress accounting all keep reading it" (`RemoteWorkspaceService.cs:17-31`).
- **Why a server2 task has a desktop checkout:** custody and landing. Settlement fast-forwards the
  desktop branch from origin (the event "Desktop worktree confirmed at the runner's pushed commit"
  appears on 41 of the 42 landed tasks), and landing, retirement, residue and progress read
  `task.WorktreePath`.
- **Qualification clones are not per task.** The Windows rc run uses its own owned clones
  (`C:\Antiphon\releases\checkout`, `checkout-<id>`, candidates under
  `C:\Antiphon\releases\candidates\rc-<date>-<sha12>`; `docs/release-gates.md:490-500`, rc skill
  step 1). The nightly bootstrap already sets `core.longpaths=true` there (`release-gates.md:498-499`,
  `scripts/lib/nightly-run-impl.ps1:528,535`). They are outside `C:\Antiphon\worktrees` and outside
  S5.

## 3. A slot-specific hazard not in the amendment: path reuse versus a late land

- The amendment's S5b release trigger is: terminal, runner slot released, sync Confirmed or None,
  no live follow-up, **no pending land**.
- Lands are requested *after* settlement: p50 1 min, p90 54 min, max 12 h (above). So a desktop
  slot released at Confirmed sync is usually free, or already re-leased to another task, when its
  task's land arrives.
- The land then binds `task.WorktreePath` = `ws-NN`, which now holds **another lessee's**
  registration:
  - the index-lock probe runs on that checkout (`AgentTaskLandService.cs:917-923`), so the other
    task's index lock holds this land;
  - `LandOperationFactory:71-77` canonicalises that path and reads its git dir;
  - the ticket's `SourceRegistrations`/`SourceCanonical` bind it (`AgentTaskLandingProtocol.cs:614-616`);
  - the post-land guarded cleanup targets it.
- An absent directory is the tolerated case; a reused one is not.
- About a dozen other path-equality consumers (the identity rows in §2) would see a terminal task
  and a live task "sharing" `ws-NN`.
- S5b lists only `WorkspaceUseAdmission`, `TerminalRunnerSeatReleaseService` and
  `TaskWorktreeRetirementService` as slot-aware.
- Holding the slot until the land is not bounded, because 96 % of runner halves never land. With
  even a 1 h hold, peak demand is 28, against the amendment's pool of 16 + 4 overflow.

## 5. Recommendation and effort

1. **S5b (ref-only, replaces "desktop halves lease from the pool").** Behind a flag, an eligible
   runner task (`RemoteWorkspaceService.IsEligible`) gets no desktop checkout. The consumers in §2
   switch from checkout operations to ref operations. It needs a decision on what `WorktreePath`
   holds, because the land refuses null (`AgentTaskLandSourceResolver.cs:43`) and tolerates a
   non-existent path. That design belongs to `plan`.
   - Effort: TestDesign 3 h; Code 8 to 10 h (dispatch creation, push, baseline, settlement sync,
     the check, reply and deliverable reads, retirement no-op, legacy recovery refusal); Review 2
     rounds; one windows-native dispatch-settle-land row.
   - About **1.5 to 2 pipeline days**, the same order as slot S5b, but with **no S5a prerequisite**
     (about 1.5 days saved) and no §3 hazard.
2. **S5a and S5c: defer.** Desktop-run tasks are 4 to 11 a day, with 2 open at peak. S4a's release
   policy bounds them. The Windows mechanics (longpaths, the RM probe, re-home) matter only there.
   Re-open S5a+S5c if S4a plus ref-only still leaves the desktop registry above about 100.
3. **S4a stays as amended.** It is still the only bound on desktop-run trees and on the legacy
   runner halves created before ref-only ships.
4. **If `decide` keeps slots instead,** S5b must add the §3 path-reuse rule for the land and for
   every identity consumer, and size the pool for late lands (≥ 28 at a 1 h hold), or decouple
   the land from `WorktreePath` first. Decoupling the land is half of ref-only anyway.
