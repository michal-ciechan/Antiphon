## 1. Native caller environment

Before this change, `CallerWakeTests.Adopted_native_recipient_reads_its_report` removed a fixed list of variables before exec: `ANTIPHON_TASK_ID`, `ANTIPHON_TASK_KIND`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN`. On Unix the pty inherits the test host's environment, so a test host started from a Claude session passed its own `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_EFFORT`, `CLAUDE_PID` and similar variables to the native caller. The witness therefore passed only when the runner had already unset them.

The test now builds the launch environment itself. Every inherited or overlay `CLAUDE*` or `ANTHROPIC*` name without an overlay value is set empty, which the Windows pty merge treats as removal. On Unix each of these names is passed to `env -u`, together with the overlay's other emptied names. The overlay's own values are kept: the stub base URL, the synthetic key, the isolated `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`.

Witness: `CallerWakeTests.C2074_Native_caller_strips_every_inherited_provider_variable`. The test checks a fixed set of inherited names and also checks this test host's real environment.

## 3. Null-AgentId retention bucket

`PruneIncidentsAsync` groups by `AgentId` and keeps the newest `IncidentCapPerAgent` (500) per group. Every incident with a null `AgentId` falls in one group.

**Stall incidents are not the risk.** After the group 86 fix (`3f285cbb35d28a45782c860fd364319b06349f5f`), `TryRaiseProgressStallAsync` writes a null `AgentId` only when the task's agent row is gone. That episode is deduped by `SessionId`. A null-AgentId stall is rare, and a separate bucket for it would not protect anything.

**The real risk is to pending runner slot release intents.** `RunnerSlotService` records each release and each deferred kill (CARD-0679 D-7, `RecordDeferredKillAsync`) as a `RunnerSlotReleaseIntent` incident with a null `AgentId` and `FailureReason = "pending:..."`. `ReconcilePendingReleasesAsync` reads only those rows to decide what is still owed. A pending deferred kill stays pending while its runner is unreachable. It shares the null bucket with fleet notices that have no agent: `HostBudgetChanged`, `OrchestratorInstructionsRegenerated`/`WriteFailed`, `RunnerForceRetired`, `RunnerSlotForceReleased` for seats with no standing agent, `ApiErrorTurnDied` and vanished-agent stalls. Once 500 newer null rows exist, the cap deletes the pending intent. The decided kill is then never sent and the remote session is never released, which breaks the process-release rule in AGENTS.md. The production database was not reachable from this server2 mirror, so the real null-bucket rate was not measured. The deletion follows from the code alone once the bucket passes 500.

Fix: the cap delete skips a `RunnerSlotReleaseIntent` whose `FailureReason` starts with `pending:` (`RunnerSlotService.PendingIntentPrefix`). Pending intents still count toward the kept rows. A reconciled or failed intent is ordinary history and is capped. The 30-day age retention is unchanged.

Witness: `C2074IncidentCapIntentTests.Null_agent_cap_never_deletes_a_pending_release_intent`. It uses an isolated database and cap 3. It seeds a real deferred-kill intent, a pending release intent, a reconciled intent and five newer null-AgentId rows, mixing `HostBudgetChanged` and `TaskProgressStalled`.
