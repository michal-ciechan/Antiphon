## Lane categories and the frozen Linux roster

`docs/testing-and-build.md` (the lane-category paragraph beside the slow-test allowlist) says every test class is Unit xor Integration. `TestLaneCategoryGuardTests` enforces that and nothing about the OS. There is no Windows category that a Linux filter consults.

The same doc's Nightly section states the producer roots as Windows backslash paths: `StateRoot` defaults to `C:\Antiphon\nightly`, and the isolated clone is `C:\Antiphon\nightly\checkout`, never `C:\src\Antiphon` and never a worktree.

The CARD-1287 Linux roster is the frozen Unit list in `docs/investigations/2026-10-15-card-1287-linux-unit.md`: 373 of 408 compiled Unit classes, qualified twice at source `f6310a452a911b45b0a0946feb9ac49dcc71bbfd` with 0 skipped. Exclusions are class-wide. A class with an explicit Windows-only method is left out of that list; a skip inside a selected class would have broken the 0-skip certificate. Carrying the list to another SHA needs a new census. `ReleaseGateRunTests` is `[Category("Integration")]` (`ReleaseGateRunTests.cs:16`) and is absent from `docs/investigations/2026-10-15-card-1287-linux-unit-filter.txt`. Editing that filter does not cover this red, and a new `[Category("Windows")]` would not remove the class from an Integration or full-assembly run.

`WindowsUnitSkipRoster` is the other direction: Linux-only Unit methods that Windows must skip, closed by `WindowsUnitPlatformAdmissionTests`. These two methods do not belong on it.

The method-level pattern already in the tree is a first-statement `SkipTestException` when `!OperatingSystem.IsWindows()`, as in `BuildSlotScriptTests.C1048_WrapperWindowsPowerShellGetFileHash` (`BuildSlotScriptTests.cs:137`). `DirectoryBrowseServiceTests.RequireWindowsDrives` (`DirectoryBrowseServiceTests.cs:53-57`) is the same shape for drive-letter fixtures. That skip is placement evidence. The testing doc says an intentional skip is not a clean zero-skip certificate and not host coverage.

Probe at this SHA: `Test-NightlySharedTree` is true for `C:\src\Antiphon` and for `C:\Antiphon\worktrees`, and false for `C:\Antiphon\worktrees\card-task-0233729c`.

## C599_ReportLane — OS-neutral fixture

Fixture: `scripts/test-release-gate.ps1:1177-1189`. The C# method is `ReleaseGateRunTests.C599_ReportLane` (`ReleaseGateRunTests.cs:81-85`), expected row count 5. The required names are the four path and credit-kind rows; the fifth row is `rc credit without a candidate id throws`.

Observed harness: 0 passed, 0 failed, 0 rows, exit 1. No `PASS` or `FAIL` line. The case aborts before `Assert-C487`.

`Get-ReleaseGateStatePaths` for `rc-release` calls `Get-ReleaseGateCandidateRoot` (`scripts/lib/release-gate.ps1:177-180`), which `Join-Path`s `-ReleaseRoot`. The fixture passes `C:\Antiphon\releases` (`test-release-gate.ps1:1181`). On this host `Join-Path` errors `Cannot find drive. A drive with the name 'C' does not exist`, then `Cannot bind argument to parameter 'Path' because it is null`, and the case ends. The same call with `/tmp/releases` and `candidates` returns `/tmp/releases/candidates`.

The rows that never ran pin Windows strings (`test-release-gate.ps1:1184-1185`):

- master `GreenPath` equals `C:\Antiphon\nightly\last-complete-green.json`
- rc `GreenPath` matches `*releases\candidates\rc-20260923T083000Z\complete-green.json` (backslashes)

Those literals match the production defaults, which this case does not call: `Get-NightlyDefaultStateRoot` returns `C:\Antiphon\nightly` (`nightly-run-impl.ps1:13`); the run-core `-CheckoutRoot` default is `C:\Antiphon\nightly\checkout` (`nightly-run-impl.ps1:100`); `release-candidate.ps1:37` defaults `-ReleaseRoot` to `C:\Antiphon\releases`; `release-gate.ps1:18-19` defaults the release root and the coordination root to `C:\Antiphon\releases` and `C:\Antiphon\verification`. Leave those defaults. They are the Windows producer paths in the Nightly section.

`Get-ReleaseGateStatePaths` (`release-gate.ps1:183-214`) already composes with `Join-Path`: master green is `StateRoot` plus `last-complete-green.json` (lines 207-210); rc green is the candidate root plus `complete-green.json` (lines 194-200). The drive letter is what stops Linux from reaching that composition. A method skip would also skip the credit-kind check (`test-release-gate.ps1:1189`), which uses the in-memory states from `New-C599State` and does not need a `C:` root.

Smallest fix, in `Test-C599_ReportLane` only:

- Build `$state` and `$release` under `New-C599Root`.
- Pass those to `Get-ReleaseGateStatePaths`.
- Keep the five assertion names so the C# required rows and the count of 5 stay valid.
- Master green equals `Join-Path $state 'last-complete-green.json'`.
- Rc green equals `Join-Path (Join-Path (Join-Path $release 'candidates') $CandidateId) 'complete-green.json'`.
- Keep the distinct-path check, the missing-candidate-id throw, and the distinct credit-kind check.

On Windows, `Join-Path` still uses `\`, so the composition pin remains. The dropped pin is only that this one case passed the production default root string.

Red-first witness: with the private roots already in place, point the master assert at `Join-Path $state 'green.json'` and the rc assert at `Join-Path $release 'complete-green.json'`. Both named rows must FAIL, and the harness must show 3 passed, 2 failed (the other three rows still pass). Restore the two filenames above and the same case must show 5 passed, 0 failed, on Linux and on Windows. The current 0-row drive abort is the baseline red; it is not the red for the rewritten asserts, because it fires before any row.
