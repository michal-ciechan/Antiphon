## Catch and isolation

The only product edit is `ResumeInterruptedLaunchAsync` in `server/Application/Services/AgentSessionService.cs`. After the session is Running, the recovered-launch catch is the typed `InputDeliveryUncertainException`. Publication `OperationCanceledException` leaves that catch. `TimeoutException`, `HttpRequestException`, `IOException`, and a phone-home request timeout or in-flight close now take the existing kill, fail, and rethrow path for that session. `InvalidOperationException` and `NpgsqlException` already took that path, because `InputDeliveryUncertainException.Is` does not match them.

Each resume is its own `Task.Run` from `AgentSessionLaunchQueue.ResumeInterrupted`. `SessionReconciliationService.ResumeInterruptedLaunchesAsync` does not await the call. `TrackLaunch` observes that task's exception and raises a per-session alert. `WaitForPendingAsync` treats a faulted launch as settled and does not rethrow it. The dispatcher wait rethrows `OperationCanceledException` only when its own token is cancelled. A transient failure of one recovered launch does not abort the other sessions in the batch. The queue passes `CancellationToken.None` into the service, so a catch that rethrows only when that token is cancelled would swallow the publication cancellation `C1150` exists to see. The typed catch is the form that keeps both behaviors.

`C1150_Running_cut_is_discovered_and_delivered_once` passed in the 430 at the reviewed tip. Restoring `catch (Exception ex) when (session.Status == SessionStatus.Running && InputDeliveryUncertainException.Is(ex))` on a scratch edit made that test fail: `ResumeAsync` did not throw `OperationCanceledException` (1 failed, 0 succeeded). The file was restored. The typed catch remains the production clause.
