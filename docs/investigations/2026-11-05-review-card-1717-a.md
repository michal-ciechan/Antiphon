## Blocking findings

### B-1 — Evidence retention authority is lost across absence and retry (high)

**Where:** `server/Infrastructure/Git/GuardedWorktreeRemoval.cs:94-97,127,222,533-549`; `WorktreeSetAside.cs:8-9`.

**Failure:** `D3_MISSING_RETAINED` used the real `FileSystemEvidenceRetention`, asserted its copy existed, removed only that private fixture copy before the next production check, and observed `Outcome=Removed`, `ReasonCode=removed`, source absent, retained absent. `HashAgrees` treats a missing retained destination as success.

Separately, `D3_CRASH_RETRY` interrupted after actual unregister, observed `worktree_removal_incomplete`, changed `.antiphon/note.md` from `retained-old` to equal-length `CHANGED-new!` while preserving mtime, and asserted the listing seal stayed equal. The real `TaskWorktreeRetirementService` retry returned clean, deleted the changed source, and left only `retained-old` in retention. Run exit 10 denotes this observed safety violation, not setup failure (`evidence-retry-run.log`).

**Why:** Retained paths/digests exist only in the first pass's local variable. The pending receipt contains no durable evidence manifest and goes directly from metadata custody to deletion. Source absence and retained-copy absence also have different safety meanings but share one permissive helper.

**Fix:** Require the retained artifact to exist and match its recorded digest before deleting the corresponding source. Persist the authorized evidence manifest in the recovery receipt and revalidate it on every retry; hold changed/unprovable evidence without resealing it. Add real retention-to-retirement regressions for both cases.

**Important boundary:** A first pass that actually detected the post-unregister change returned `evidence_bytes_changed`; its S4a retry was blocked by `cleanup_command_slot_spent` and preserved the source (`D3_FIRST/D3_RETRY`). Do not call that exact higher-level path a demonstrated bypass. The distinct retryable crash path above is demonstrated. The original immediate post-retention byte-change scenario now refuses and preserves the source.

### B-2 — The listing seal does not authorize the bytes it deletes (high)

**Where:** `WorktreeSetAside.cs:49-66`; `GuardedWorktreeRemoval.cs:172-176,557-573`.

**Failure:** After a retryable unregister interruption, the real service's set-aside tracked file was changed to equal-length `Z` bytes with its mtime restored. The probe asserted equal listing seals before/after. Retry returned `IsClean=true` and deleted the changed tracked file (`D4_TRACKED_BYTES`). Those bytes had never been committed or pushed. Thus “every non-evidence file is already moot” is false; the ignored disposable class does not cover modified tracked bytes.

**Why:** The SHA-256 is of path/kind/length/mtime metadata, not file content. The receipt survives a crash but does not retain content authority. Also, Linux identity is only device/inode (`WorktreeNoFollowDelete.cs:313-316`): a native create/delete/recreate probe obtained the exact same identity on cycle 1. That is direct evidence of identity reuse, not a complete replacement-and-retry exploit.

**Fix:** Bind approved remaining entries to content/identity authority from the validated tree, including tracked contents and retained evidence, and verify it at deletion/recovery. Do not rely on device/inode across unbounded recovery without stronger ownership. Unknown replacement custody must hold. Add equal-stat changed-content and matching-seal replacement witnesses.

### B-3 — Late writes and late repository markers are still deleted (high)

**Where:** `GuardedWorktreeRemoval.cs:162-173,216-223,491-526`; `WorktreeNoFollowDelete.cs:232-246`.

**Failure:** `D2_TRACKED_AFTER_STATUS` wrote new unpushed contents to a tracked file immediately after the fourth real status command returned clean. No timestamp restoration was needed. The census accepted its tracked name, the later seal blessed the new state, and retirement reported Removed with the source gone. `D2_AFTER_LAST_CHECK` wrote a new only-copy file at the real delete boundary after the last census; the unchanged production delete removed it and reported Removed.

The native Linux walker also checks repository markers only once before iterating a directory. A joined writer created a `.git` marker after deletion began inside a private child containing 20,000 files. At least 19,968 files still existed after marker creation; all were then deleted. The marker remained and the final `rmdir` failed with `Directory not empty`. This is marker-preservation policy failure, not a claim that the scratch marker referenced a functioning Git repository (`native-marker-run.log`, exit 10). The Windows/previous portable walkers recheck markers during traversal; the Linux replacement drops that protection.

**Why:** Name membership is not byte proof. A listing seal captured after the clean status does not prove those bytes were pushed. A pre-walk census cannot authorize later content, and the final failed unlink does not undo deleted bytes. `CustodyOf` additionally lets a changed seal fall through whenever a nested repository is found, so the walker must correctly preserve it.

**Fix:** Restore fd-relative repository-marker checks during traversal and delete only entries tied to approved authority; never promote a later name/content census to the earlier Git proof. Establish writer custody through the full destructive phase, or retain/quarantine and refuse automatic deletion when it cannot be established. Rename into quarantine plus verification can reduce exposure but does not freeze existing open handles. A check immediately before unlink alone still has a TOCTOU window. Add real producer-to-filesystem tests for all three schedules.

The original ordinary-untracked-file write after clean status now returns `untracked_after_proof` and preserves the source. This improvement does not close the above schedules. Disclosure alone is not an adequate disposition for only-copy data loss.
