## S0 finding and awaited-child inventory

The blocking hypothesis is confirmed with the real hosted `SessionRunnerEventPump`, an
in-memory runner stream and isolated PostgreSQL. While A's SignalR publish or actual terminal
delivery-confirmation callback is held, B's already-produced transcript UUID is absent from
PostgreSQL and B has not reached the stream enumerator. Releasing A permits B storage and
real marked-task settlement. Serial reconnect catch-up exhibits the same obstruction. Each
probe keeps its gate held for a five-second observation window; this establishes the dependency,
not a measured production 45-second latency distribution.

The initial `c432-s0-and-deadlines.trx` has three intentional original-shape S0 assertion reds
(B was expected to persist while A remained blocked). That run also contained two unrelated
test timestamp-precision failures, corrected by rounding fixture timestamps to PostgreSQL's
microsecond precision. The retained S0 tests characterize the current obstruction rather than
claiming S3 is implemented. The later probes add real B settlement and a throwing diagnostics
sink. Early versions of that added settlement fixture needed a complete newline-delimited
report token, shared assistant API-call identity, and a wait for settlement before stopping the
pump; those fixture failures are not evidence against the blocking finding.

The inline await inventory is:

| Entry | Awaited children and significance |
|---|---|
| Pump startup/reconnect | List runner sessions, then `SyncTranscriptAsync` for each session in order before starting the fleet stream. Sync includes persistence, rules reconciliation, settlement and boundary effects. |
| Transcript event | `ObserveTranscriptAsync` awaits the session's `SessionTranscript` SignalR publish **before** persistence; it then awaits successful-boundary queue/routing effects, late-text routing and compaction recovery as applicable. |
| Turn-end routing | Channel reply, review reply, task settlement (including parent-note construction/persistence), queue turn-end/delivery confirmation, then any late-confirmed channel redispatch/warning. |
| Assistant text | Channel, review and task settlement are awaited; late text can therefore block a subsequent fleet event too. |
| Queue confirmation | Terminal writes, transcript catch-up/confirmation and recovery remain awaited by the calling boundary. A confirming prompt that relies on that same stream can remain behind its own delivery callback. |
| Other fleet events | Output observer, exit observer, transcript-fault/binding incident handling, adopted-session SignalR publication and agent-status observer are each awaited in the same loop. They were inventoried, not rewritten or certified nonblocking by this slice. |

S2 removes the nested parent delivery wait from **completion-note admission**: settlement
persists the note and admits optional work before an owned worker confirms idle-parent input.
It does not move the other listed runtime effects out of the pump. S3 must preserve ordered
turn ownership and durable review authorization/consumption before changing that structure.

Debug `RuntimePhase` observations distinguish entry, save start, successful save completion
and scope exit, with session/task/stored-sequence identities, UTC observation times and monotonic
elapsed durations. A scope exit is not a persistence verdict. Diagnostics contain metadata, not
report text. The synthetic traces live under
`tests/Antiphon.Tests/bin-c432/TestOutput/card-0432/s0/`; TRX files live in the adjacent
`TestResults/` directory. Those alternate-build artifacts are ignored by Git.
The final trace files are `signalr-publish-False-False.log`,
`signalr-publish-False-True.log` (diagnostics failure), `queue-confirm-False-False.log`
and `queue-confirm-True-False.log` (reconnect).

## Resulting contracts

- A request carries captured mode, `RequestedAt` and immutable `DeadlineAt`. The bounded
  admission queue uses `TryWrite` with `Wait` full mode, so full/closed/missing admission keeps
  the raw note and records its reason instead of silently losing accepted work.
- The Distill-only runner policy checks canonical pinned model availability before and after
  provisioning, rechecks queued holds, and cancels only still-Queued tasks. Check/Diagnose retain
  their existing policy. Availability failure is distinct from an observed hold.
- The same deadline covers queue wait, provisioning, dispatch wait, settlement observation and
  application. Deadline-bearing queued tasks are rejected both at candidate selection and under
  the dispatcher claim. Never-typed expired briefs are rejected under the terminal queue lock,
  after claim persistence and before the first input; existing attempts retain recovery ownership.
- Apply owns the existing session queue lock plus source/note database row locks, checks exact
  identity, digest, origin, Pending/zero attempts and full-report suppression, and uses remaining
  cancellation/SQL time budgets and a database clock predicate. A valid result losing application
  eligibility is `AppliedLate`; a never-started deadline miss is `DegradedExpired`; an already
  dispatched run expiring is `DegradedTimeout`. Raw source results stay authoritative.
- Request cleanup has one additional two-second allowance across cancellation, hold release
  and ledger writing. Failed cleanup can leave a missing ledger, but the finite raw hold and
  persisted dispatcher deadline still apply. No unobserved database operation outlives its scope.
  Incident delivery has a separate owned queue. `CleanupMs` is sampled before the ledger save;
  the cleanup phase observation covers the final write as well.
- Completion flush wakeups are bounded/deduplicated; four owned consumers use the normal queue
  eligibility/confirmation path. A rotating persisted-Pending scan recovers missed wakeups,
  including parents that are not AlwaysOn. This is not a general runtime-action intent worker.

`DegradedExpired` will absorb formerly queued requests. The headline degrade rate may look
worse after deployment: this is intended fail-fast behavior, not evidence of a regression.
No live Shadow cohort, model latency, production rate improvement or eventual-cost improvement
is claimed. No live model, production runner, real broker, stack restart or mode/budget change
was used for verification.
