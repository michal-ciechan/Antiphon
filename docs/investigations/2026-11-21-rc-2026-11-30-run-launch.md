## First attempt refused (run id 6fe1a38d, no tests ran)

The first launch used the runbook record shape exactly (TaskRoot `C:\Antiphon\releases\task-6fe1a38d`,
StateRoot `C:\Antiphon\releases\state-6fe1a38d`). The supervisor started. launch-rc got its build
slot, nightly-run took and released the locks, and the run ended in 14 s with `launch-rc ... exit 3`.
The JSON result line had `exitCode 3` and empty identity, and `last-run.json` stopped at
`phase=Started`.

Cause: the runbook says "Leave `-ReleaseRoot` unset so it stays `C:\Antiphon\releases`", but
`scripts/nightly-run.ps1` declares `[string]$ReleaseRoot = ''` with no default. The rc profile
always runs the selection step (`scripts/lib/nightly-run-impl.ps1:744-762`). That step builds paths
from `$Request.ReleaseRoot` (`scripts/lib/release-selection.ps1:76`, `:248`, and
`Assert-ReleaseSelectionPath` `GetFullPath`). An empty root throws ("Cannot bind argument to
parameter 'Path' because it is an empty string."), and the catch at `:760` returns
`Phase=selection`, `ExitCode=3`. nightly-run's stdout result line does not print `Refusal`, so the
message is not in the console log. It was identified from the code. The previous successful run
(`task-6068be37`, run `e7f92f66`) passed `-ReleaseRoot C:\Antiphon\releases` explicitly.

Correction: a fresh run id (`3528e6b1`), a new TaskRoot and StateRoot, and the same record with one
added pair, `"-ReleaseRoot", "C:\\Antiphon\\releases"`, which is the value the runbook intends.
`-CoordinationRoot` stays unset, so the real `C:\Antiphon\verification\native-run.lock` was taken.
No lock was deleted and no guard was overridden. The 6fe1a38d dirs remain as evidence. They are
unused, and `start-supervisor` refuses to reuse them.

Runbook fix owed: section 5 of the activation runbook, and any launch-record template derived
from it, must include `-ReleaseRoot C:\Antiphon\releases`. Separately, nightly-run should
print `Refusal` on its result line.
