# Slow qualification groups 17, 126 and 128: first look

2026-11-07; source `71e820366`; Windows desktop (mc-dell-xps2023), one class or case at a time, nothing else running.
Notes for a later fix. **Measured:** where the time goes in `C519_Queue_to_adapter` (group 17) and
`RcFailedFirstExecutionTests.ActualLoopFollowsSchedule` (group 128). **Refuted:** the Redpanda
consumer-group rebalance delay as the C519 cost. **Not yet measured:** inside the C519 recovery probe, and
inside the nightly planner's 135 s. **Not looked at:** the rest of groups 126 and 128 (list at the end).
No product or test source was changed.

## Group 17: C519 queue-to-adapter

`tests/Antiphon.Tests/Application/ChannelOutboundUnifiedTransportTests.cs:38`. Each case starts its own Redpanda
container, then runs 12 scenarios (late gateway yes/no × six cut points). Each scenario builds a fresh
`UnifiedOutboundTransport` (`TestHelpers/UnifiedOutboundTransport.cs:55`): a cloned database schema, a new
topic, a fake Slack server, the full bridge harness and a gateway. It then runs `RecoverAsync` at least once at
the end (line 123); `definite-refusal` adds one more and `refusal-save` two more. Each `RecoverAsync`
(`UnifiedOutboundTransport.cs:216`) starts `dotnet Antiphon.ChannelOutbound.Probe.dll` as a separate process.

**Measured, here:** the three `C519_Queue_to_adapter` cases took 283 s (bodies 102, 87, 87 s). That is about
half the qualification figure, so contention in the group roughly doubles them. Traced spans (harness
create/dispose, SQL, HTTP) explain under 40 s. Untraced gaps by neighbouring spans:

| Gap (between) | Count | Avg | Total | Reading |
|---|---:|---:|---:|---|
| last SQL → harness dispose | 36 | 2.7 s | 98 s | the final `RecoverAsync` probe run plus `AssertReceiptAsync` (one per scenario) |
| SQL → SQL | 64 | 0.9 s | 56 s | mid-scenario probe runs and outbound ticks |
| SQL → fake Slack `POST` | 21 | 2.5 s | 53 s | a probe run, then the gateway delivers |
| first Redpanda + DB pool | 1 | 14 s | 14 s | first container start in the process |

**Refuted:** Redpanda's `group_initial_rebalance_delay` (default 3 s) as the 2.5 s pre-delivery wait. With it
set to 0 through `rpk cluster config set` after start (a plain `--set` is not applied on v25.3.4; see
`KafkaConsumerGroupObservationTests.cs:23`), the run took the same 283 s and the gaps were unchanged
(2.65 s average before `POST`, 2.72 s before dispose).

**Likely, not yet measured inside the probe:** the probe's cost is its own start-up work, not process launch.
A bare `dotnet Antiphon.ChannelOutbound.Probe.dll <missing config>` exits in about 0.2 s. The probe builds
`AppDbContext` with plain `UseNpgsql` and no compiled model (`tests/Antiphon.ChannelOutbound.Probe/Program.cs:27,61,258,287`,
`UnifiedRecoveryProbe.cs:38`). In the test process the same model build is the 1.8 s
`fixture-setup runtime-model` span. About 56 probe runs × ~2.6 s ≈ 145 s of 283 s.

**Next steps, cheapest first:**
1. Time the probe's phases (model build, host start, Kafka producer, recovery) with `AntiphonTrace` spans or
   stopwatch output on stderr, to confirm the split.
2. If the EF model build dominates, give the probe a compiled model (`dotnet ef dbcontext optimize`, with
   `UseModel` in the probe only) or a model shared with the server, so each probe skips the ~1.8 s build.
3. Share one Redpanda container per class (`[Before(Class)]`, as `KafkaConsumerGroupObservationTests` does)
   instead of one per case: about 5 container starts saved per class run.
4. Keep the separate process where the scenario needs a real crash boundary. The final `RecoverAsync` after an
   already-published delivery (line 123) may not need one; check what it proves before moving it in-process.

## Group 128: `RcFailedFirstExecutionTests.ActualLoopFollowsSchedule`

`tests/Antiphon.Tests/Scripts/RcFailedFirstExecutionTests.cs:20` runs
`scripts/test-nightly-failed-first.ps1 -Case ActualLoopFollowsSchedule` (`Test-ActualLoopFollowsSchedule`,
line 1055). It drives the real `nightly-tests.ps1` over the full 19,012-node replay fixture, with every
process launch replaced by an in-process `StartProcess` seam (`Invoke-FFActualLoop`, line 967), then reruns
small fixtures for fallback, the previous-run chain and heartbeats.

**Measured, here:** 336–343 s wall per run (qualification: 353 s, so this case is not contention-bound). From the
harness's own `performance.json`, 317.5 s fall before the first assertion (`actualTrace`); every later
assertion is 0–3.2 s. Temporary stopwatches (reverted) split that first stage:

| Stage | Seconds |
|---|---:|
| `New-FFLoopFixture -Full` (includes `Resolve-NightlySuiteChunks` over 19,012 nodes, 37.5 s) | 39–40 |
| `New-FFLoopHistory` | 1.5 |
| `Invoke-FFActualLoop` (the real `nightly-tests.ps1`) | 271–279 |
| of which inside the fake-launch seam, 158 calls | 6.4–6.6 |
| `Resolve-NightlyPriorFailures` + `New-NightlyDispatchSchedule` | 1.0 |

Inside `Invoke-FFActualLoop`, from per-launch timestamps:

| Part | Seconds | Detail |
|---|---:|---|
| planning the 19,012-node suite | ~135 | one gap between the antiphon suite's discovery (2.4 s) and the next suite's (137 s) |
| per-chunk overhead in `Invoke-NightlyScheduledChunk` | ~113 | 156 chunk launches; median 0.48 s, p90 1.61 s between launches, while the fake launch takes about 0.04 s |
| finalisation | ~20 | after the last launch (summary, projection, coverage) |

So the test is almost all production nightly tooling cost, which real nightly runs also pay: about 175 s of
planning (the fixture's 37.5 s plus the loop's 135 s) and about 113 s of per-chunk bookkeeping.

**Next steps:**
1. Profile the 135 s planning gap after discovery: diagnostic parse of 19,012 nodes, cost lookups,
   chunking, writing `groups-planned-*.json`. Likely PowerShell-object-per-node work (`Where-Object` and
   `ConvertTo-Json` over large arrays) that a dictionary or a single pass removes.
2. Profile `Invoke-NightlyScheduledChunk` (`scripts/lib/nightly-tests-impl.ps1:1026`) per chunk: it copies every
   suite variable with `Set-Variable` on entry, rebuilds the child environment and records chunk timing
   (`Update-QualificationChunkTiming`), then reads results back. Which of these costs 0.5–1.6 s per chunk is
   not yet known.
3. The fixture already plans once (37.5 s) and the loop plans the same nodes again; the fixture's own plan
   could be reused if the assertion does not depend on planning twice.
4. Faster planning lowers this test and every real nightly run; the test's 1,080 s budget and the
   `Timeout(1_140_000)` (`RcFailedFirstExecutionTests.cs:20`) can then come down.

### Follow-up: class-level planning and coverage (same day)

A function-level profile (every nightly library function wrapped with inclusive/exclusive timers; throwaway)
put the per-test work first: the profile skip rules walked once per test (90 rules × 19,012 tests) from the
planner, the discovery census and the index view, and the class-membership check once per test and per
result row. These now resolve once per class: `New-NightlyProfileExclusionIndex` (rules matching a class, in
policy order), `Get-NightlyDiscoveryDispositionIndexed` and `New-NightlyClassAssignmentCache`, used by
`Get-NightlyProfileExecutionChunks`, `Get-NightlyDiscoveryCensus`, `Get-NightlyRequiredDiscoveryUids`,
`Get-NightlyDiscoveryIndexView` and `Test-NightlyTrxDiagnosticCrossCheck`.

- Outputs byte-identical to the previous code on the 19,012-test fixture with the real rc rules and with
  synthetic method-level, ordering and absent-method-list rules: plans, censuses (reasons and owners) and
  required sets, 21 MB of JSON. That workload: 337 s before, 41 s after.
- Planning the fixture: 37.6 s to 5.4–6.1 s (leaf step 36.3 s to 3.1 s).
- `ActualLoopFollowsSchedule`: about 340 s to 178 s; its full-fixture stage 317.5 s to 155.9 s.
- Note for any port: PowerShell 7's `Group-Object` sorts its groups, Windows PowerShell 5.1 keeps first-seen
  order; the leaf builder still groups through `Group-Object` (over one item per class) so its order matches
  whichever runs it.

Next largest, per the same profile: the hand-written JSON writer for timing and evidence records
(`ConvertTo-TestPhaseJsonText`, about 350,000 calls). Its bytes are hashed, so change it only against a
byte-for-byte check; it is also the obvious first piece to move into a .NET library loaded by the scripts.

### Follow-up: compiled core (same day)

The per-test passes and the evidence JSON writer now run as C#: `scripts/lib/NightlyCore.cs`, loaded by
`scripts/lib/nightly-core.ps1` with `Add-Type` (the pattern `nightly-owned-process.cs` already uses), compiled
once per source version and cached in `%TEMP%/antiphon-nightly-core/`, so no build step and about 0.4 s for the
first process only. The PowerShell functions stay the entry points and keep their bodies as the fallback,
used on Windows PowerShell 5.1 and with `ANTIPHON_NIGHTLY_CORE=off`. Group-Object and Sort-Object stay in
PowerShell: their ordering is the PowerShell version's and culture's.

- Byte-identical to the original code on the 19,012-test comparison workload, core on and off; that
  workload: 337 s originally, 40 s class-level PowerShell, 9.6 s compiled.
- `ActualLoopFollowsSchedule`: about 340 s, then 178 s, now 125 s; its full-fixture stage 317.5, 155.9, 102.9 s.
- `scripts/test-nightly-core.ps1` (`NightlyCoreTests`) runs census, plan, index view, cross-check and the
  JSON writer both ways in one process and requires identical output; a deliberate one-character change
  to the C# JSON writer fails it.

Second step, from a fresh function profile with the core on: the pinned TUnit/MTP diagnostic parser (record
splitting, state property, record conversion and the per-log record loop; failure messages and every
refusal text stay as PowerShell had them), the summary CSV cells and native-ID extraction, the identity bag
key, outcome normalisation and file hashing. Two quadratic `+=` array builds became lists (the diagnostic
log's nodes, the summary's test and TRX rows). Real logs (22,383-test discovery, two executions including a
failure with a parsed message) parse byte-identically, core on and off: discovery 15.0 s to 5.0 s.
`ActualLoopFollowsSchedule` 125 s to 105 s; full-fixture stage 102.9 s to 80.7 s. `NightlyCoreTests` now also
compares the parser on the captured C1325/C1375 records, synthetic records for every state, their
truncations and whole logs (version refusal, duplicate IDs, discovery-kind refusals); a one-character
change to a C# refusal message fails it.

Third step, whole loops rather than per-row helpers (a fresh profile showed the remaining cost was PowerShell
call overhead: 131,502 outcome normalisations, because the coverage verdict filtered every row five times,
and 249,491 core-availability checks):
- `NightlyVerdicts`: the verdict's outcome classification in one pass, expanded-row presence, the TRX/diagnostic
  cross-check (hashtables with PowerShell's OrdinalIgnoreCase comparer, so mismatch text keeps its order),
  required-class presence and the index view's required UIDs, each one call per batch.
- Summary rows: per-TRX tagging (`Add-Member -Force` semantics), the native lookup and the unjoined-row pass.
  On the 18,786-row run: rows 8.7 s to 2.6 s, whole summary 13 s to 7.2 s, outputs identical core on and off.
- The active-chunk identity (written twice per batch) re-read, re-parsed and re-hashed the suite's
  planned-groups file each time. It now parses once per content: the SHA-256 it publishes as planDigest,
  taken from the same bytes, keys the parse; every binding check still runs on every write.

`ActualLoopFollowsSchedule` 107 s to 101 s; full-fixture stage 81.9 s to 74.9 s. Smaller than the profile
suggested: the profiler's own per-call cost inflated the many small calls it counted.

### Follow-up: C# project, write-behind evidence (2026-11-08)

- `scripts/lib/Antiphon.Nightly` is now a real project (was one Add-Type file). `nightly-core.ps1` builds it
  once per source version into `%TEMP%/antiphon-nightly-core/Antiphon.Nightly-<hash>` (lock file, own
  artifacts directory) and loads it; no SDK, no project beside the scripts or a failed build keep the
  PowerShell fallback.
- `src/Antiphon.IO.WriteBehind` (publishable, own tests): a System.IO.Abstractions `IFileSystem` decorator.
  Whole-file writes are queued and land on a background thread as temp-file-and-rename; reads, existence
  and size answer from the queue.
- During a nightly run (`nightly-tests.ps1` turns it on) every evidence file goes through one such file
  system (`EvidenceFiles`): sidecars, active identity, owner records, planned files, seed, summary files and,
  when no commit seam is set, the journal records. Barriers: every child launch (and its seam), listings,
  copies, streams, the heartbeat's journal check. `ANTIPHON_NIGHTLY_DEFERRED_WRITES=off` disables it.
- Journal records are flushed to the OS, not fsynced (crash may leave the last record missing or empty).
- Compiled: evidence path identity and bounded read (Windows), the discovery document node loops (one was
  quadratic `+=`) and canonical JSON. The stream-reader C# moved from inline Add-Type into the project
  (script load 0.85 s to 0.45 s per process).

Stage, writes in the background against in line: about 55 s against 60 s; profile of what is left: the
per-batch loop (verdict, TRX reads, diagnostic parse, identity), suite preparation (discovery parse, the
project walk) and the end-of-run summary, each a few seconds.

Then: the active-chunk identity reads its record once (digest of exactly the bytes parsed, from memory while
queued) instead of landing it and hashing the file twice, about 900 file reads fewer per run; the project
walk runs one directory level at a time in parallel (2.7 s to 1.1 s here; the tree holds about 35,000
directories, mostly `.antiphon` run output and `client/node_modules`, kept in the walk so an untracked
project is still found). Case 66 s, stage about 47.5 s. The diagnostic parse is already compiled (execution
logs about 25 ms each, the 9 MB discovery log 0.7 s); what remains is spread across the 154 batches at
about 180 ms each, which in a real run sits beside minutes of test time.
