## 0. Outcome

**Confirmed. Both a data gap and a display gap, and the data gap is the larger one.**

1. **Data gap.** Every matrix cell is genuinely empty: `GET /api/complexity-chains` returns `resolvedFrom: "none"` for all three any-role rows and for every Review/Plan/TestDesign/Code cell; the config default `Delegation:ComplexityChains` ships empty (`server/Application/Settings/DelegationSettings.cs:377-384`). All thirteen routing changes the operator made are stage-wide **routing pins** (`RoutingPins` table), a separate overlay the matrix does not store and does not read into its cells.
2. **The matrix governs nothing today.** A cell is consulted only for a create that passes `-Complexity` (`server/Application/Services/AgentTaskService.cs:923-931`). Of the 1,004 tasks created on the Antiphon board since 2026-10-07, **zero** carry a complexity; of the 158 created after the pins were rewritten (2026-10-13 17:00Z), zero. Every one of those 158 resolved through its stage pin (Plan 5/5 ClaudeCode/Frontier, TestDesign 4/4 ClaudeCode/Frontier, Code 74/74 ClaudeCode/High, Review 71/71 Codex/Frontier; each Created event reads `[pin=the human required stage-wide <Role> routing pin …]`). So "write the change in the cell" would, as the code stands, change no dispatch at all.
3. **Display gap.** The matrix shows a stage pin only as a banner on the role row (`client/src/features/settings/RoutingSettingsTab.tsx:463-473`), while each cell's badge comes from the chain service alone (`:517-531`), so a Required pin that bypasses every cell sits beside three cells labelled `Unset — dispatch blocks` (`client/src/features/settings/routingSettingsModel.ts:46`). The cell never says "this pin is what will actually run".
4. **Even if cells were written today, the thirteen Human Required pins would still win.** A Required pin with a candidate replaces the cell list outright (`server/Application/Services/RoutingCandidates.cs:58-63`; `tests/Antiphon.Tests/Application/RoutingPinCandidateCreateTests.cs:363`). Making the matrix the single surface therefore needs (a) non-complexity dispatches to resolve through the role row, (b) the pins migrated into cells and cleared, and (c) the cell to display whatever overlay still outranks it.

### 1.3 What a cell means and how a task resolves to (kind, level)

A cell is an **ordered fallback chain of complete (kind, level) pairs** for one (role, complexity). It is not a default level and carries no Required/Preferred strength. Resolution at create, `AgentTaskService.CreateAsync` (`AgentTaskService.cs`), in order:

1. **Pin decision** (`:770-777`): `RoutingPinService.ResolveAsync` (`server/Application/Services/RoutingPinService.cs:303-410`) picks the card pin, else the stage pin, as a whole row. An explicit `-Kind/-Level` that disagrees with a Required pin is 409 `routing_pin_conflict` (`:348-358`); with a Preferred pin the request wins with a warning.
2. **With `-Complexity`** (`:923-1017`): `ComplexityRoutingService.WalkAsync` (`ComplexityRoutingService.cs:201-241`) loads the chain (`LoadChainAsync :312-344`: role cell → any-role row → config → empty) and composes it with the pin (`RoutingCandidates.Compose :44-97`): a **Required pin with a candidate replaces the chain** (`:58-63`, the create carries the warning "complexity chain bypassed by …", `AgentTaskService.cs:935-941`); a **Preferred pin prepends** and the chain follows, deduplicated (`:66-74`). The walker then applies four skips in order: not a delegate kind, stage forbid list, model hold, subscription quota (`ComplexityRoutingService.cs:493-527`). First survivor wins; none → `Blocked` with `routing exhausted:` (or 409 with `refuseIfExhausted`). An empty chain blocks with "chain is empty … Set one with complexity-chain.ps1" (`:165-170`). `-Complexity` plus `-Kind/-Level` is 422.
3. **Without `-Complexity`, pin lists two or more candidates** (`:1019-1066`): the pin list alone is walked (`WalkComposedListAsync`), chain not loaded.
4. **Without `-Complexity`, no walked list** (`:1068-1072`): `ResolveLevel` (`:3976-3986`: explicit level, else `RolePolicy[role].Level`, else `DefaultLevel`, clamped by `MinOrchestratorLevel` for orchestrators) and `ResolveAgentKind` (`:4004-4040`: explicit kind, else `RolePolicy[role].Kind`, else ClaudeCode). A single-candidate pin arrives here as the request's explicit kind/level via the overlay at `:801-835`, which is why the Created event says "at High (explicit override)" (`:1558`) followed by the `pin=` note built by `RoutingPinService.EventNote` (`RoutingPinService.cs:487-493`). Then the stage forbid list, the quota gate and the model hold (`:1073-1110`).
5. RolePolicy values: `DelegationSettings.cs:349-372` (Plan/TestDesign/Code/Review Frontier, Investigate/Debug/Coverage/Merge High, Docs/Commit Medium, Mutation/Test/Deploy Low; `Kind` null everywhere), `DefaultLevel = High` (`:375`).

At dispatch, a list-governed task (complexity or pin id set, `ComplexityRoutingService.IsListGoverned :31-32`) whose chosen alias is held is re-walked against the current matrix and pin (`server/Application/Services/AgentTaskDispatcher.cs:710-745`, `WalkTaskChainAsync :1749-1778`); a single-candidate Required pin is never rerouted by a tick (`PinForbidsReroute :1791-1792`). The attention feed's "routing exhausted" item checks whether a live cell now exists for a Blocked task's (role, complexity) (`server/Application/Services/AttentionService.cs:589-627`).

## 2. Pins versus cells, and why the matrix reads Unset (brief question 2)

### 2.1 What `scripts/routing-pin.ps1` writes

`routing-pin.ps1 set -Role <Role> [-Card …] -Provenance Human|Auto -Strength Required|Preferred (-Kind/-Level | -Candidates …) [-Forbidden …] [-NotBefore/-NotAfter] [-Agent] [-Reason]` sends `PUT /api/routing-pins` (`scripts/routing-pin.ps1:245-266`; request `PutRoutingPinRequest`, `server/Application/Dtos/RoutingPinDtos.cs:13-31`). Grain is **the role (stage-wide) or one card+role** (`:16-18`); there is no complexity axis. The row is `RoutingPin` (`server/Domain/Entities/RoutingPin.cs:23-142`): `CardId?`, `Role`, `Provenance`, `Strength`, ordered partial candidates, `AgentId?`, `ForbiddenAliases`, `NotBefore/NotAfter`, `Reason`. Upsert is `RoutingPinService.UpsertAsync` (`RoutingPinService.cs:163-272`): one active row per grain, Auto over Human is 409 `routing_pin_human` (`:233-241`), no revision token, no operator-credential gate. `clear` looks the row up by grain and sends `DELETE /api/routing-pins/{id}` (`:273-291`). `delegate.ps1 -Pin` writes a **card-grain** Human Required pin from what a dispatch resolved to (`scripts/delegate.ps1:1299-1320`).

### 2.2 Relation to the cells

Neither service reads the other's table for display: `ComplexityChainService` builds cell DTOs from `ComplexityChains` and config only (`ComplexityChainService.cs:76-134, 351-367`), and `RoutingPinService` never consults cells. The instructions snapshot that orchestrators read has a "## 5. Routing pins" section and no matrix section at all (`server/Application/Services/OrchestratorInstructionsSnapshotBuilder.cs` has zero references to `ComplexityChain`; live file rev 145 confirms).

### 2.4 Verdict on "display gap or data gap"

Both. The **data** the operator changed lives in `RoutingPins`, never in `ComplexityChains`, so the cells are truly empty. ## 3. Which API sets a cell; could a script write cells; what S3 would change (brief question 3)

- **Route:** `PUT /api/complexity-chains/{role}/{complexity}` (`ComplexityChainEndpoints.cs:25-37`; `role` = `any` or a routable role; `complexity` = Hard/Medium/Easy). Body `PutComplexityChainRequest` (`server/Application/Dtos/ComplexityChainDtos.cs:6-12`): `{ candidates: [{agentKind, modelLevel}, …1..8], provenance: "Human"|"Auto" (default Auto), reason?, notAfter? }`. Response: the cell DTO. **No concurrency token** (last writer wins; compare `expectedRevision` on `PUT /api/runner-defaults`, `server/Api/Endpoints/RunnerDefaultEndpoints.cs:42-47`). Provenance is asserted by the caller; `X-Antiphon-Task-Token` only fills `SourceTaskId` for audit (`:34-36`). Clear: `DELETE /api/complexity-chains/{role}/{complexity}` (204, idempotent).
- **Script already exists:** `scripts/complexity-chain.ps1 set -Role <Role|Any> -Complexity Hard|Medium|Easy -Candidates ClaudeCode/Frontier,Codex/Frontier [-Provenance Human] [-Reason] [-NotAfter]` (`scripts/complexity-chain.ps1:9-20`; provenance default Human). It writes **one cell per call**; "Review only on Codex Frontier" is three calls (Hard, Medium, Easy) or one any-role write per tier. `routing-pin.ps1` could not write cells without becoming a different script: its grain has no complexity and its body has strength, forbid list, dates and agent, none of which a cell accepts.
- **What writing cells would do today:** nothing for dispatch, until orchestrators pass `-Complexity` and the 13 Required pins are cleared (§0 item 4).
- **CARD-0097 S3 as planned** (`docs/superpowers/plans/2026-10-13-card-0097-role-model-settings-plan.md:165`, D-4/D-5 at `:121-136`, held by O-1 and parked in the test design's Appendix A, `docs/superpowers/plans/2026-10-13-card-0097-test-design.md:9-16`): a `StagePinEditor` modal on the Role policy section writing `PUT /api/routing-pins` with `provenance: Human`, a Strength radio defaulting to Preferred and a Required confirm. To edit **cells** instead, S3 changes shape:
  - The write target becomes the three `PUT /api/complexity-chains/{role}/{tier}` calls (plus the matching DELETEs on Clear), reusing `usePutComplexityChain`/`useClearComplexityChain` and `ComplexityChainCellEditor`'s candidate list, validation and copy; the new `usePutRoutingPin`/`useClearRoutingPin` hooks and `StagePinEditor.tsx` are not needed for the role-wide change.
  - The Strength radio and the Required confirm go away (a cell has no strength) and are replaced by one "row" confirm: "writes Hard, Medium and Easy for <Role> as a whole; replaces the inherited Any-role list; the stage pin <X> still outranks this until cleared" when a pin exists.
  - The editor must be able to **clear the role's stage pin** in the same action, or the write is invisible to dispatch. That needs a `DELETE /api/routing-pins/{id}` hook (the only pin write S3 keeps).
  - `RolePolicySection`'s Configure button opens the row editor on the matrix row rather than a pin modal; `pinRequestFrom`/`requiredConfirmCopy` in `rolePolicyModel.ts` are replaced by `rowCellRequests(role, candidates)` and `rowReplaceCopy(role, pin)`.
  - None of this makes dispatch read the cells. That is a server slice (§4 S-A) that S3 depends on; without it the UI would be editing a table the fleet does not consult.

### Risks

- **A Required pin overrides every dispatch** (`RoutingCandidates.cs:58-63`). Until S-E clears the 13 pins, a cell written by script or UI is bypassed and the matrix would lie unless S-B/S-C show the overlay. Keep the pin visible in the cell until it is gone.
- **Fail-closed today, must not become fleet-wide.** With cells on the path of every dispatch, an unset row must fall back to RolePolicy (S-A), otherwise an untouched role (Custom, or any role after a Clear) Blocks the pipeline with `routing exhausted`. The `Unset — dispatch blocks` label must only remain true for explicit `-Complexity` creates.
- **Explicit overrides.** Cells have no Required strength: an orchestrator passing `-Kind Codex` for Review would still run Codex after "Review only on Codex Frontier" is written as a cell, and `-Kind ClaudeCode` would still run Claude. Today a Required pin refuses that with 409 (`RoutingPinService.cs:348-358`). Decision 2 below.
- **Last writer wins** on both PUTs (no revision token on cells or pins; plan D-6). S-A does not fix it; a `expectedUpdatedAt` 409 is a separate card.
- **Live lag.** The desktop server is 216 commits behind master; S1/S2 are not active. Any slice here is invisible until a restart with `GET /api/version` confirming the SHA.
- **Grok hold** until 2026-10-16 05:00Z: a cell naming Grok shows "held" and is skipped; harmless but visible.

### Decisions the operator must make

1. **Which tier does a dispatch without `-Complexity` use?** Recommend a single `Delegation:DefaultComplexity = Medium` (S-A). Alternatives: require orchestrators to always pass `-Complexity` (instruction-only, no server change, silently falls back to RolePolicy whenever they forget), or a fourth "default" column per role.
2. **Does a role cell refuse a disagreeing explicit `-Kind/-Level` (Required semantics) or allow it with a warning (Preferred semantics)?** Recommend allow-with-warning for cells and keep Required pins as the refusal mechanism for the rare case; if the operator wants refusal everywhere, S-A needs a per-row `strength` and the 422 for `-Complexity + -Kind` already exists as the model.
3. **Migrate the 13 pins into cells and clear them (S-E), or keep pins as the stage-wide write and only fix display (S-B/S-C)?** The operator's stated goal needs the migration; display-only leaves two write surfaces.
4. **Concurrency token on cell and pin PUTs** (plan O-3): defer or fold into S-A.
5. **Card pins** stay as card-scoped exceptions shown inside the cell (recommend yes, read-only in the matrix).
