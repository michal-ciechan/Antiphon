## D-1 (round 1): closed

`tests/Antiphon.Tests/Scripts/DesktopPostgresPowerShellTests.cs` runs `scripts/pg-qps.ps1 -Seconds 10`
and `scripts/deploy-local.ps1 -Report` through real pwsh. The scripts are copied into a temporary
root. The only thing on the child's `PATH` is a fake `docker`: a `/bin/sh` shim to the `Antiphon.CustodyTestChild`
dll on Linux, and a `docker.exe` copy of its apphost on Windows. The fake records argv and stdin as JSONL,
and writes a password-bearing marker to stderr on every call. `APPDATA` points at a temporary AppHost
secret whose connection string carries a per-run `Password=`. The class has 16 cases: two scripts times
Match, WrongHost, WrongPort, Stopped, MissingContainer, MissingSecret, QueryFailure and Override.

Each case asserts the following:

- the exact call count;
- `calls[0]` is the exact `--context antiphon-server2 inspect ...` argv, with empty stdin;
- every query is the exact `[--context antiphon-server2] exec -e PGOPTIONS=-c default_transaction_read_only=on -i <pinned 64-hex id> psql -X -A -t -w -v ON_ERROR_STOP=1 [-h /var/run/postgresql -p 5432] -U <secret user> -d <secret db> -f -`, with the exact SQL on stdin;
- no `psql` call happens for a refused target;
- the exit code (pg-qps 3, deploy-local 1) and the fixed refusal text;
- neither the password, `Password=` nor the stderr marker appears in stdout, stderr, any fixture file name or content, or the captured argv and stdin;
- the secret file is unchanged;
- with `-Container`/`-PgContainer` there is no `--context`.

Each assertion is a boolean, so a regression cannot put the secret into the test report.
I checked that the password never appears in any mutant log.
