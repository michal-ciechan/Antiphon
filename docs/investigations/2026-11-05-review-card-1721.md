## A-2 judgement: persisted is sufficient

What the release destroys. `RunnerSlotService.ReleaseAsync` (`server/Application/Services/RunnerSlotService.cs:67`) writes a `RunnerSlotReleaseIntent`, calls the runner's `ReleaseSlotAsync`, then stamps the session Stopped and writes `RunnerSlotForceReleased`. On the runner, `SessionRunnerRuntime.ReleaseSlotUnderGateAsync` (called at `src/Antiphon.SessionRunner/SessionRunnerRuntime.cs:1802`) kills the process tree, records the checkout path in a released-checkout sidecar (`RetainReleasedCheckout`, line 1415), forgets the pty manifest and Herdr sidecar, and appends `slot-releases.jsonl`. It does not touch the worktree files, the branch or the index. The release destroys the provider process and its in-memory conversation state only. The transcript is persisted and a Stopped session can be resumed by id.

What can delete the worktree later. Both automatic destroyers re-inspect the live tree. `RunnerWorkspaceRetention` (`src/Antiphon.SessionRunner/RunnerWorkspaceRetention.cs:305-320`) keeps the mirror on `git status --porcelain --untracked-files=all` output (Dirty), on `rev-list HEAD --not --remotes=origin` > 0 (Unpushed), and on a live `ls-remote` miss. `DesktopLegacyReleasePolicyService.PrecheckAsync` (line 391) does the same on the desktop. `TaskWorktreeRetirementService` is caller-reviewed and source-SHA bound. None of them reads `RemoteSync` from the settlement record as authority.

Operator scenario. A Failed task cannot be Replied or Continued (predecessor Review bbd446f6 traced this). The remaining path is a message sent straight to the session while the task stays Failed. That turn writes transcript rows, output activity bumps `LastSeenAt`, and a mid-turn transcript makes `IsWorkingBatchAsync` true. Each of those holds the seat (V-1 witnesses the three activity sources). Ten idle minutes after the turn ends, the seat is released on the stale clean/equal record. If the operator's turn left edits or an unpushed commit, they stay on disk and every destroyer above keeps the tree. Nothing is lost except the idle provider process.

Can persisted evidence be stale in a way that loses work? Stale in the sense above, yes. Lossy, no, because the release is not the step that removes files.

Cost of a live inspection. One more runner round trip (status, rev-list, ls-remote with its own budget) per attempt, inside a 60 s sweep budget on a 5 s tick. It would protect nothing the destroyers do not already protect. It also would not close the one residual race that exists (A-3), because that race is about the process, not the tree. Verdict: persisted is sufficient.

Production read (desktop Postgres, read only, 2026-11-05 13:12 UTC). A server2 Running session with an open Blocked task had `LastSeenAt` 1549 minutes old and its last transcript row 1624 minutes old. So a remote idle seat does not heartbeat `LastSeenAt`, and the idle clock can elapse on server2. Desktop sessions with no open task showed non-transcript `LastSeenAt` bumps (a cohort 70 minutes old, matching a restart, and three sessions 14 to 26 minutes old with transcripts days old). On the desktop the clock therefore restarts after a server restart or a terminal redraw. That only delays release; it is the safe direction (A-7).

## Advisories

A-1. Attention wording. `server/Application/Services/AttentionService.Seats.cs:251` now says eligible clean/equal seats are released after 10 idle minutes and that dirty, unpushed or unknown mirrors keep the seat. That fixes the CARD-1719 contradiction on the evidence string. Two residues. (a) The client hint `client/src/features/attention/attentionVisuals.ts:57` still reads "Detection only. Open the task; nothing is killed." for `FailedTaskSessionHeld`. The operator sees that hint beside a `mirror=clean-equal` row that will be released. Smallest fix: hint text "A Failed task still holds a live or unconfirmed session. A clean, origin-equal seat is released after 10 idle minutes; otherwise it is kept." plus the matching Vitest case if one pins it. (b) The row is generic. A `mirror=clean-equal` row for a coordinator-owned or standing seat implies a release that this janitor will not do. Acceptable as documentation; mention only.

A-2. `CatchUpTranscriptAsync` bypasses the dispatcher wrapper. `AgentTaskDispatcher.PoolSupervision.cs:267-268` calls `_runtime.CatchUpTranscriptAsync` directly. The dispatcher's own `CatchUpTranscriptAsync` (`AgentTaskDispatcher.cs:4158`) swallows non-caller cancellation and honours the `CatchUpOverride` test seam. `AgentSessionRuntime.PullAndPersistAsync` catches everything except `OperationCanceledException`, so any `OperationCanceledException` that is not caller cancellation (for example an `HttpClient` timeout that surfaces as `TaskCanceledException`, if the runner-transcript resilience pipeline lets it through) escapes, ends `RetireIdleWarmAgentsAsync` for that tick, and skips the TTL, cap and stale passes. A runner that keeps timing out on one eligible seat would do that every tick. Not reproduced here; read from the two catch filters. Failure is fail-safe for the seat (no release) but starves the rest of the janitor. Smallest fix: call `await CatchUpTranscriptAsync(sessionId, ct);` (the wrapper).

A-3. Residual race between the last re-read and the kill. The final reads end at `PoolSupervision.cs:311-324`. `RunnerSlotService.ReleaseAsync` then saves an intent and sends an unconditional `ReleaseSlotAsync(sessionId, reason)`. The runner kills whatever is live under that id: there is no generation, no idle condition and no qualification token. A message delivered to the session in that window (milliseconds plus one runner round trip) is killed mid-turn. This is the same shape as the pre-existing TTL path (`KillPooledSessionAsync` after its recheck) and the window is far narrower than in CARD-1719. Neither persisted nor live Git evidence closes it. The real closure is the conditional coordinator (`TerminalRunnerSeatRelease`, AutomaticEnabled), which qualifies on the runner. Recorded, not a blocker.

A-4. Cap fairness and per-tick cost (brief item A-3). What counts: an attempt is a call to `RunnerSlotService.ReleaseAsync` (`attempts++` at line 334, before the try). Refusals and transport failures count; every earlier `continue` does not. Held seats (dirty, unpushed, unknown, Working, missing boundary, recent activity) are skipped before the budget, so they never starve anyone. Two gaps remain.
(a) No back-off across sweeps. A seat the runner refuses (`ConflictException`/`RunnerProblemException`, e.g. "still live after slot release; custody was retained") or cannot reach is re-attempted on the next 5 s tick, writing one more `RunnerSlotReleaseIntent` row each time. `parsed` comes from an unordered pool query, which is stable in practice, so five persistently refused seats take the whole budget every tick and starve seat six onward. Up to 5 intents per 5 s is about 86,000 rows a day. Smallest fix: skip a session that has a failed or pending `RunnerSlotReleaseIntent` newer than N minutes, or order candidates by their last attempt.
(b) Pre-attempt work is not capped. The transcript catch-up (a full `GET sessions/{id}/transcript` from the runner plus persist) and about ten queries run for every candidate that passes the CompletedAt gate, before the cap is consulted. A clean/equal Failed seat with recent operator activity passes the CompletedAt gate and is then held by the activity bound, so it pays a full transcript pull on every tick for as long as the operator works plus ten minutes. Smallest fix: compare the stored activity (the sweep already loads `lastTranscript`, and `LastSeenAt`/`CodexTokenCountAt` are one read) against the bound before pulling, or count pulls against the per-sweep budget.
Not a hot loop in the unbounded sense: everything is bounded by the 5 s tick and the 60 s sweep budget.

A-5. Pending queued input is not a release fence. The re-check reads transcript-derived working state (`TranscriptWorkingStateQuery`) but not `SessionQueuedMessages` with `Status == Pending`. A parked or modal-withheld operator message older than 10 minutes, with no transcript or output activity since, does not hold the seat. The message is not lost by the release itself; what the queue then does with it on a Stopped session was not traced. Smallest fix: add a Pending-message check beside the working re-read at line 294.

A-6. Witness gaps. (a) No witness drives a real operator message through `SessionMessageQueueService` and ingestion to a Failed seat; V-1 seeds transcript rows and `LastSeenAt` directly. The production writers were read (output `RecordActivityAsync`, manual turns, resume) and the seeded shapes match them. (b) `Clean_equal_failed_seat_is_released_after_the_idle_bound` does not assert that the `FailedTaskSessionHeld` row clears after release. By construction it does (`AttentionService.Seats.cs:190` holds only Created/Starting/Running/Stopping and release stamps Stopped). Add `(await world.HeldAsync()).ShouldBeEmpty()`. (c) No witness for a Failed seat whose agent or session also carries an open Queued/Dispatched/Working/Blocked task. The candidate `busyAgentIds` fence and the re-read query at line 281 cover it, and `FailedTaskSessionOwnership` makes the later task the owner. (d) No witness for a refused release followed by the next sweep (A-4a).

A-7. Desktop `LastSeenAt` bumps without transcript activity (restart cohort, terminal redraws) restart the idle clock. Safe direction; release can be delayed after every server restart. Mention only.

## Brief checklist

Never releases a Blocked task's session: the candidate requires `task.Status == Failed` and both reads exclude an open Blocked task on the agent or session (`Blocked_task_is_untouched`). Standing-agent seats are excluded by the pool query (`AlwaysOn`, `StandingSpecialist*`) and `PoolDelegateRelease.CanRelease` (`Standing_agent_is_untouched`). Warm pooled Succeeded/Canceled sessions are not Failed owners and stay on the TTL (`Warm_pooled_session_is_unchanged`). Open task on the session or agent: fenced twice (A-6c). The attention row is one derived row per owner session and clears on Stopped (A-6b).

A-4 switch-on path. `OwnsAutomaticPath` is a pure function of the task (`TerminalRunnerSeatReleaseService.cs:62`). When it is true the outer sweep hands the task to `TryHandleTaskAsync` and removes the agent from the pool, and both ghost reads skip it. When it is false (switch off, or a desktop-alias runner on a non-Blocked task) only the ghost path acts. SourceLanding tasks are excluded from both and stay with sourced recovery. No task can satisfy both, so there is no double release, and every Failed seat has exactly one owner, so there is no gap. Witness: `Automatic_coordinator_owns_both_hold_and_release_without_force_fallback` asserts the switch and ownership, zero force commands, one conditional command across two sweeps when qualified and zero when held.

PC-9 fix (`FinishPoolRetire(row.Agent, hasIncident: true)` plus save, and `warm.RemoveAll(Stopped)` at `AgentTaskDispatcher.cs:9505`): the released agent leaves `retire` and `warm`. The `stale` pass skips it because its session is still in the sweep's `unfinishedSessionIds` snapshot. `RecordPooledWorkingPastTtlAsync` sees it as idle. No later pass in the same sweep can raw-stop it.
