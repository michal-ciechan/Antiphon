## Blockers

**B-1r2: the runner retention floor misses secrets inside an ignored nested repository (data loss).**

- Where: `src/Antiphon.SessionRunner/RunnerWorkspaceRetention.cs:507-539` (`ReadIgnoredSecretAsync`),
  used at admission/locked recheck (:383), phase B (:152) and residue recovery (:431).
- Scenario: in a clean, pushed runner mirror, an ignored directory holds a nested Git repository
  (`.antiphon/seed/` or `bin/tool/`, the CARD-1590 shape that `Ignored_nested_repo_goes_with_the_tree`
  deliberately removes) with `.env` or `credentials/token` inside it. `git ls-files --others --ignored
  --exclude-standard -z` collapses the nested repository to one entry, `bin/tool/`; it never lists the
  files inside it. `IgnoredSecretFloor.Matches("bin/tool/")` is false, so no secret is found, and
  unforced `git worktree remove` deletes the whole tree, the nested repository and its secret included.
- Witness (real engine, real Git, unmutated 40b176ce1 plus one scratch test, never committed):
  `Review_d6_ignored_nested_repo_secret_survives(.antiphon/seed, .env)` and
  `(bin/tool, credentials/token)`: both **red**, stderr `ls-files=.antiphon/seed/` /
  `ls-files=bin/tool/`, `verdict=removed`, secret file gone. A plain-shell Git 2.47.3 repro
  shows the same collapsed listing and deletion by `git worktree remove`.
- Parity: the server path already handles this exact case. `GuardedWorktreeRemoval.Classify`
  (`server/Infrastructure/Git/GuardedWorktreeRemoval.cs:438`) says "Git may collapse an ignored
  repository to dir/, hiding its private files from globs" and adds `WorktreeNestedRepositories.Find`
  to Protected. The runner completed-card path holds `nested_repository`
  (`RunnerCompletedCardWorkspaceRemoval.cs:208`). Only the active runner retention path, the one
  B-1 was about, lacks it.
- Smallest fix: in `ReadIgnoredSecretAsync`, for a listed entry that ends in `/` (Git's collapsed
  repository), enumerate that directory on disk without following links and apply
  `IgnoredSecretFloor.Matches` to each `entry/relative` path; an unreadable directory, link or
  control-character name is a doubt (keep). That keeps CARD-1590 behaviour (a nested repository
  with no secret still goes with the tree). The coarser option is to keep any tree whose listing has
  a trailing-slash entry; this conflicts with `Ignored_nested_repo_goes_with_the_tree`.
  Add the two witness cases above, plus one in `C1677RetentionServerTests` through the real
  transport, each with one secret only, and assert bytes and registration survive.

   `WorktreeCleanupSettings.DefaultProtectedIgnored` and the runner classifier. Configuration only
   adds to it. `Documented_secret_floor_is_in_the_server_defaults` pins the list, and
   `Both_classifiers_protect_the_secret_floor_under_a_disposable_override` runs both classifiers on
   41 paths. All requested extra shapes are present (`.aws/credentials` through `credentials*`).
3. **B-3.** Each glob has a `/**` companion. Matching is `IgnoreCase` in all three compilers, so
   Windows case variants are protected (Linux over-protects case variants, which is safe). A
   directory named like a secret (`bin/credentials/token`, `bin/tls.pem/token`) is protected on
   server and runner. Over-protection / starve risk: a build output named `credentials*`, `*.key`,
   `*.pem`, `.env*` or `appsettings.*.json` holds the whole tree forever (`ignored_secret`), and
   `credentials*`/`id_rsa*` are prefix globs (`credentials_helper.cs` holds). A census of 163
   runner worktrees on server2 (20 with `server/bin`, none with `client/node_modules`) found
   **zero** floor matches, so there is no starvation today. npm packages that ship test
   `*.pem`/`*.key` fixtures would hold client trees that have `node_modules`. Advisory A-1.

   DryRun is the discriminating case: without the residue guard it answers `would_remove` (red).
   Execute is defence in depth: without the residue guard, the phase-B guard still keeps it. It
   goes red only when both guards are removed. That is by reasoning; I ran no residue-guard mutant.
