# CARD-0806: ScriptHarness timeout leaves child processes alive

## Finding

`tests/Antiphon.Tests/Scripts/ScriptHarness.cs:18-45` starts `pwsh` with redirected stdout/stderr, starts both `ReadToEndAsync` tasks, and gives only `process.WaitForExitAsync` a 300-second cancellation token. If that wait times out, it throws `OperationCanceledException`. The code does not call `Kill`; `using` disposes the `Process` wrapper, and `finally` tries to delete the temporary results directory. The `pwsh` process and its descendants can continue running after the test has failed, potentially retaining redirected pipes and the results directory. The deletion may fail and be silently ignored. This conclusion is from the control flow; no live orphan reproduction was run.

There is a second unbounded path: when the direct `pwsh` exits, `WaitForExitAsync` completes, then the harness awaits both `ReadToEndAsync` tasks without a deadline. A surviving descendant that inherited stdout or stderr can keep a pipe open indefinitely. `scripts/test-run-checkpoint.ps1:129-139` explicitly starts a nested `pwsh` with redirected output, and other harnesses start children too. Killing only the outer `pwsh` is insufficient.

The project targets .NET 9 and runs on Windows and Linux. The [.NET 9 wait API](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.waitforexitasync?view=net-9.0) says its cancellation token cancels the wait. The [.NET 9 kill API](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-9.0) provides `Kill(entireProcessTree: true)`, but `WaitForExit`/`HasExited` then report only the root's exit, not descendant exit; inaccessible descendants may be skipped. A root that has already exited cannot be used to discover descendants that have been reparented. Therefore `Kill(true)` repairs the ordinary live-root timeout, but cannot alone guarantee cleanup in the root-exited/open-pipe case.

## Plan for Plan/Code

1. Put one deadline around the whole process operation: root exit **and** stdout/stderr completion. Keep the existing 300-second normal budget. On expiry or test cancellation, enter cleanup before `Process.Dispose` and before deleting `results`.
2. For the immediate live-root path, call `process.Kill(entireProcessTree: true)` while the root is still associated, tolerate only the expected already-exited race, and wait for the root with a fresh, bounded cleanup token. Retain the timeout failure as the primary result and include kill/drain failures as diagnostics; never report timeout cleanup as a passing harness assertion.
3. To cover the parent-exited/open-pipe case reliably, establish ownership at launch rather than reconstructing ancestry at timeout. On Windows, use a kill-on-close Job Object and terminate it on timeout; the existing `tools/Antiphon.Checkpoints/Execution/WindowsJobProcessHandle.cs` shows the job and descendant-sweep pattern, including its `Process.Start` to job-assignment race. If strict custody is required, start suspended, assign to the job, then resume, so that no child can spawn before assignment. On Linux, launch `pwsh` in a dedicated session/process group (the checkout already uses `setsid` in `tools/Antiphon.Checkpoints/Execution/DetachedLauncher.cs`), confirm and save its group identity at launch, and signal that group, never a guessed/recycled PID or the test runner's group. If the requirement includes descendants that deliberately leave that group, use cgroup containment instead; a group alone cannot own such daemons. Do not claim `Kill(true)` or the current best-effort Windows job assignment provides an absolute guarantee against an escaped descendant.
4. Bound the post-kill pipe drain. If EOF does not arrive, close/abandon the redirected readers and fail with an explicit cleanup diagnostic; then delete only this invocation's results directory. The checkpoint driver already uses a 10-second post-kill drain (`tools/Antiphon.Checkpoints/Execution/ProcessDriver.cs:105-122`).
5. Add a short-deadline test seam to `ScriptHarness` without making production's 300 seconds shorter. An integration test with `[ParallelLimiter<ProcessSpawnLimit>]` should spawn `pwsh` -> child -> grandchild, record their identities in a private temp directory, hold them past the short deadline, assert a timeout, and verify every owned process exits. Add the root-exits-but-grandchild-holds-stdout variant and assert the method terminates within its deadline. Use identity checks to avoid PID-reuse false positives and a `finally` sweep so a failed test does not itself leak processes. Verify on both Windows and Linux, along with a normal PASS-inventory case.

No product or test code was changed and no build or test was run in this investigation.
