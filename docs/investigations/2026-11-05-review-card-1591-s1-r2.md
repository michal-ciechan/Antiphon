## Lock and input safety

- The scan transaction never waits on a row lock (SKIP LOCKED) and bounds relation/FK lock waits with
  `lock_timeout 100ms` and each statement with 2 s, inside a 5 s pass token. Nothing references
  SessionQueuedMessages or ChannelInbounds by foreign key, so the row locks do not block FK checks on new
  inserts. Inbound acceptance inserts a new ChannelInbounds row and does not touch claimed rows.
- The CARD-1716 wake worker selects inbounds with `QueueMessageId IS NULL`; the scan claims only inbounds
  with a queue row, so they are disjoint. A flush that tries to deliver or re-charge a claimed queue row
  waits for the scan transaction (milliseconds normally, at most about 5 s) while holding its session
  semaphore. That is a bounded delay, not a stall, and the scan never waits on the semaphore, so no cycle.
- The scan path (`RunWithheldIncidentLoopAsync` -> `ScanWithheldChannelIncidentsAsync`) calls only
  EF/raw SQL, the static `SessionMessageQueueService.IsWorkingBatchAsync` (a lock-free transcript read),
  and `ColumnText.Clip`. No `_queue`, `GetLock`, `FlushSessionAsync`, runner, adapter or input call.
  `C1591_ScanWritesNoInput` holds the session semaphore during the scan and still sees one incident and
  no adapter input.

## Advisories

A-1 (introduced in ChannelBridgeService.cs:76-93, outside B1-B6). `ExecuteAsync` now awaits whichever
sibling completes first and rethrows it. A fault in `RunWakeWorkerAsync` therefore cancels the consume
loop and faults `ExecuteAsync`; with the default `BackgroundServiceExceptionBehavior.StopHost` (no
override in server/) the whole server stops. Before this diff the same fault left the wake worker dead and
consumption running. The fault path exists: the wake loop's inner catch excludes every
`OperationCanceledException` and its outer catch accepts only host cancellation, so a non-shutdown OCE from
`DrainPendingAsync` (for example a `TaskCanceledException` escaping a wake/flush call) faults the task.
Neither outcome is good; the loud one is arguably safer for Telegram. Smallest fix, in a follow-up card:
give the wake loop the same host-token filter this diff gave the withheld loop, and decide whether a
sibling fault should restart that sibling instead of stopping the host. Not a Telegram false/missed
alarm and not a lock, so not a blocker under the round 2 rules.

A-2 (latency). The page query cannot exclude already stamped inbounds or non-Running sessions (they live
in other tables), so stuck rows stay in the partial index and use page budget every pass. A newly aged
row is reached within about `10 s x ceil(N/64)` plus one wrap tick, where N is the number of indexed rows.
N is 0 on the desktop today; 640 stuck rows would mean about 100 s. Consider dropping rows from the index
once stamped (for example a queue-side stamp) if backlogs of that size become real.

A-3 (observability). If the candidate statement exceeds its 2 s deadline under database load, every pass
fails and only logs a warning, with no incident. This is the deliberate B4 trade-off; a repeating
failure counter or a one-time warning would make it visible.

A-4 (tooling). `dotnet run` under the build slot does not apply `-maxcpucount` to its implicit build; the
mutant probes accepted that as one lease per mutant.
