## Behaviour changes

**D1. Custody is bound to filesystem identity.** A creation record now stores volume (Linux device id, Windows volume serial), file id (inode or file index), and creation stamp (Linux birth time when statx returns it, otherwise 0; Windows `FILE_BASIC_INFO` creation time). The first bound identity wins, so a later replacement at the same path cannot inherit custody. `CheckpointOutputLedger.Check` returns `output-identity-mismatch` when the live identity differs, and `Remove` leaves that tree in place. A byte-identical copy moved onto the recorded path is refused. Cleanup with no producer context still deletes nothing. `WasCreated` stays true for a path recorded without IO. `MatchesCreation` fails closed when the recorded identity is missing or different. Seal adoption records identity at the same time as content. Windows custody `CheckpointStat.Device` is now the volume serial; it used to be 0. Linux `Stat` requests birth time but still requires only mask `0x3CF`.

**D2. Owned deletes go through a nofollow parent handle.** `OwnedOutputLedger.Remove` calls `DeleteAnchored` instead of `File.Delete`. On Linux the parent is opened with `O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC`, parent and child are `statx`'d without following links, and `unlinkat` runs only when `AnchoredDelete.Allowed` matches the recorded identity. There is no pathname `File.Delete` fallback. On Windows the parent is opened with `FILE_FLAG_BACKUP_SEMANTICS|FILE_FLAG_OPEN_REPARSE_POINT`, a reparse parent is rejected, the child is opened with `NtCreateFile` relative to that handle and `FILE_OPEN_REPARSE_POINT`, and deletion is `FileDispositionInfo` on that handle. The Linux witness swaps the owned directory for a symlink to a foreign tree after the ownership check and before the payload delete; the foreign sentinel survives. `AnchoredDelete.Allowed` is the pure-logic witness for a parent that was not opened without follow, a non-directory parent, a reparse parent, a reparse entry, and an identity mismatch. Native Windows proof is still owed for 8.3 aliases, case-insensitive aliases, junction or reparse replacement, drive roots, and real sharing, ACL, and attribute behaviour.

**D3. A failed overwrite keeps a recoverable generation.** `ReplacementPublication.Publish` copies the existing destination to a sibling `.bak` before `Io.Move`. The temporary and that backup are removed only after a nofollow read of the destination matches the new bytes exactly. A clean failure that leaves the destination in place (sharing denial, access denied, lock, disk full `0x80070070`, foreign facility) still deletes the temporary, so the existing `*.tmp` empty assertions stay. `ERROR_UNABLE_TO_REMOVE_REPLACED` (1175), `ERROR_UNABLE_TO_MOVE_REPLACEMENT` (1176), `ERROR_UNABLE_TO_MOVE_REPLACEMENT_2` (1177), and any failure that removes the destination restore the backup when it exists and keep the temporary. `RunStateStore` retries 1175/1176/1177 on the existing five-attempt schedule. A later successful retry uses a new temporary; the failed attempt's temporary can remain. The sweep reaper only removes `c723-<32 hex>.json.<32 hex>.tmp` files older than 10 minutes, so a state recovery temporary is not reaped immediately. Linux `CheckpointNativeIo.Move` is still `File.Move`. Windows overwrite of an existing file now passes a fresh backup name to `File.Replace` and moves that backup back if the destination is missing. Callers on this path: `SafeWrite.Text`, `SafeWrite.Bytes`, `SafeWrite.MoveOverwrite`, `TestRootGuard.MarkDeleting`, and the checkpoint index and cursor writers. `CopyOverwrite` is unchanged. An early refusal, before publication is armed, still deletes the unused temporary.

Report publication now reads the new file three times: destination verification, content record, then the required readback. `HostCleanupCheckpointReceiptTests.Report_writes_require_verified_readback` expects 3 instead of 2. A mismatched readback is still refused.
