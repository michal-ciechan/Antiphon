# C448 V36 flake: the set-aside delete step (2026-11-04)

Task ba8ec885, Investigate. Base master `84e19071e25abc7a595fddfac145b187dc5f2d11`; failing cut
`5a95ae7a5611eedb56c3bea023bb7a4b4fb6683a` (Windows qualification b19a9880). Evidence is from code
reading and the failure text. Windows was not reproduced: the runner is Linux and the desktop is
reserved for the live qualification.

## Verdict

**Confirmed: the failing step and why it gives up at once. The Win32 error code is not recorded.**
The baseline removal reached the set-aside tree's **delete**. The delete either threw or returned with
the tree still present. Neither outcome is retried, so the first transient refusal on Windows became
`worktree_removal_incomplete`. The batch-65 hardening (`e05d39d56`/`84e19071e`, `WorktreeRenames`)
covers only the record replace and the move-aside. It does not cover this step, so it cannot fix this
failure.

## Evidence

`LandingRemovalPolicyControlTests.cs:189`):
`the unchanged command path must be reachable: worktree_removal_incomplete set-aside: C:\...\c448-removal-policy-8815…\.source.removing-24aeecc971e2b19a`.

### (a) Which site produced it

In the cut (`git show 5a95ae7a5:server/Infrastructure/Git/GuardedWorktreeRemoval.cs`), ten sites can
return `worktree_removal_incomplete`. These are excluded for the baseline `RemovalFixture`:

- Cut lines 180/248/270 (unregister failure). After the move, `UnregisterAsync` sees the source absent.
  The fake `UnregisterWorktreeAsync` (test file `:886-897`) then succeeds, sets `Registered=false`, and
  `worktree list` (`:846-853`) no longer names the source. So `failure` is null.
- `cleanup_inspection_error` is a different residue.

That leaves the two delete sites after a successful move-aside and unregister:

| cut line | master line | condition |
|---|---|---|
| 182-189 | 185-192 | `WorktreeNoFollowDelete.Delete(aside, …)` threw `IOException`/`UnauthorizedAccessException` |
| 192-193 | 195-196 | `Delete` returned, but `IsAbsent(aside)` is false (an entry is still in the namespace) |

Both sites return the same residue and detail, so the message does not say which one ran.

**The underlying error is recorded nowhere.** The catch at cut 184 (master 187) discards `ex`.
`outcome` still holds the unregister outcome (`unregister_exit_0`), and `Detail` is only
`"set-aside: " + aside`. `GuardedWorktreeRemoval` has no logger, and the test writes nothing to
stdout. **The TRX contains nothing more than the assertion message. There is nothing to extract.**

### The 49 ms bound rules out a sharing violation at the open

`OpenNoFollow` (cut `WorktreeNoFollowDelete.cs:72-81`, master `:77-85`) retries only Win32 error 32,
with `Thread.Sleep(100)` between attempts (5 attempts, about 400 ms). Any error 32 at the open would
have added at least 100 ms. The whole test (two fixtures, baseline removal and assertion) took
49.4 ms. So the refusal was one of these, none of which is retried:

- the first-attempt open failing with an error other than 32
- `MarkDeleted` failing (`:88-100`). Every error except 87, 1 and 50 throws at once. This includes 5
  (access denied) and 145 (`ERROR_DIR_NOT_EMPTY`) on the directory while a child is still visible.
- `Directory.EnumerateFileSystemEntries` or `WorktreeNestedRepositories` I/O failing
- the tree still being visible after a successful return (cut 192-193). This would be the case if the
  directory fell back to the classic (non-POSIX) disposition. It then stays delete-pending while another
  handle (a scanner or a directory watcher) is open.

The fixture's tree is `source/keep.txt`, written by `File.WriteAllText` microseconds before
(`:801-805`). It is then renamed and deleted within milliseconds, which is the usual moment for a
Defender or indexer scan. The fixture holds no handle of its own: `WriteAllText` closes the file.

### Exception shape (matters for the fix)

`WorktreeNoFollowDelete.Failure` builds `new IOException(msg, code)`, so **`HResult` is the raw Win32
code** (32, 5, 145), not `0x8007xxxx`. `WorktreeRenames.IsSharingConflict` (master
`WorktreeRenames.cs:36-37`) matches only `0x80070020/21/05`. It would therefore not recognise a delete
failure even if it were applied to this step. Exceptions that .NET raises from the enumeration carry
`0x8007xxxx`.

### (b) Does batch 65 help?

No. `84e19071e` routes `WorktreeSetAside.Record` and `MoveAside` through `WorktreeRenames.Retrying`,
and replaces the literals in `OpenNoFollow` with the shared constants without changing its behaviour.
In this failure the set-aside directory exists, so the move had already succeeded. The delete is
unchanged at master: master lines 185-196 still have no retry. **The flake reproduces on master.**

### Production impact

Low. The record is kept, so the next cleanup pass resumes the delete (cut 64-98, the pending-record branch). The test has no
second pass, so the control fails.

## (c) Recommended product fix (minimal, fail-closed)

1. **Seam.** Add `Action<string, bool> DeleteTree` to the injectable record. Its default is
   `WorktreeNoFollowDelete.Delete`. Use `WorktreeRenames` itself as a fourth member, or a sibling
   `WorktreeDeletes` that carries the same `Pause`/`Windows` flags, so the fixture can inject Windows
   faults on Linux.
2. **Bounded settle loop.** Add `WorktreeNoFollowDelete.DeleteSettled(path, preserveNested, r)`. It runs
   at most `SharingAttempts` (5) attempts with a `SharingPause` (100 ms) pause between them:
   - if `IsAbsent(path)`, return
   - try `r.DeleteTree(path, preserveNested)`
   - rethrow `NestedRepositoryPreservedException` at once, never retried
   - catch a transient error while `attempt < 5`, then `Pause` and retry the **whole** walk; the walk is
     idempotent and re-checks every guard
   - if it returned but `!IsAbsent(path)` and `Windows` and `attempt < 5`, `Pause` and loop; this covers
     the delete-pending case
   - otherwise return, and the caller's existing absence check reports the residue
3. **Transient predicate.** Add `IsTransientDelete(ex) = Windows && ex is IOException or
   UnauthorizedAccessException && code ∈ {5, 32, 33, 145}`, where `code = (HResult & 0xFFFF0000) ==
   0x80070000 ? HResult & 0xFFFF : HResult`. That accepts both the raw Win32 codes and the
   `0x8007xxxx` form. Off Windows nothing is transient.
4. **Wire both delete sites:** the resume at master `:91` and the post-unregister delete at master `:185`.
   `Renames` is already on the instance.
5. **Diagnostic.** At the catch, append `"; delete_error_" + code` to the Detail. No server code parses
   the Detail (grep). Two exact assertions must then change to a prefix match or the exact new text:
   `LandingRemovalPolicyControlTests.cs:464` and `WorktreeGuardedCleanupTests.cs:407`.
6. **Worst case** for a lasting hold: about 5 × 400 ms (inner open retries) plus 4 × 100 ms, roughly
   2.4 s. `C665_LockedFileMidDeleteResumesOnLaterPass` (Windows-only; persistent `FileShare.Read`
   hold) stays green and takes about 2.4 s.

Witnesses go in `LandingRemovalPolicyControlTests` through the fixture seam (`Windows=true`, so they run
on Linux). Commit them red first:

- W1: `IOException(msg, 145)` once, then the real delete. Expect a clean result, `Pauses==[100ms]`, two
  delete calls, set-aside tree and record gone, `Mutations.Count==2`.
- W1b: the same with `0x80070005` (`UnauthorizedAccessException`).
- W2: 145 persistent. Expect `worktree_removal_incomplete`, a Detail starting `set-aside: <aside>`
  (with `delete_error_145`), five calls, four pauses, tree and record retained and branch present. Then
  a second pass without the fault comes out clean; this is the resume site.
- W3: a non-transient code, e.g. raw 112 (disk full). Expect one call and no pause.
- W4: `Windows=false` with 145. Expect one call.
- W5: the seam returns without deleting once. Expect a clean result after one pause (delete-pending).
- W6: the resume site with the fault once. Expect a clean result.

Use method-scoped checkpoint filters. A class-wide filter picks up Windows-only skips (`C665_Locked…`),
which `validate` counts as `row_failed`.

## (d) Test hardening

Do not do it in the first slice. A non-clean baseline here is a product transient, and the product
fix covers it. If it recurs after the fix with a recorded `delete_error_*`, the legitimate test-side
fallback is one resume pass. If the baseline's residue is `worktree_removal_incomplete` with a
`set-aside:` detail, call `safe.RemoveAsync()` again. That pass is the product's designed resume path,
and `Mutations` stays at 2 (unregister, then `update-ref -d`). Also update the comment at
`LandingRemovalPolicyControlTests.cs:185-186`, which names only the rename and record.
