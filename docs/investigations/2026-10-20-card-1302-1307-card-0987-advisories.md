## CARD-1302 details

### 1. Containment parity is fixed

`src/Antiphon.HostCleanup/Checkpoints/CheckpointCleanupContext.cs:20-31` and `tools/Antiphon.Checkpoints/Cleanup/OutputCleanup.cs:22-34` now perform equivalent normalization and exception handling. For root `/r` and candidate `/r/`, normalization produces `/r`, which does not start with `/r/`: false. A candidate containing NUL causes the caught `ArgumentException`: false, not an escaping exception. A child `/r/child/` remains inside; `/r-sibling/child` does not.

The source repair is `d0c612cbef3c4a5d7628494f007de1ae620892e0` (`fix(checkpoints): align context containment with output cleanup`), preceded by test commit `e1bbf5cb649977d376b992f52f2b6afbed66f127`. The repair is an ancestor of inspected master. Existing `HostCleanupCheckpointPathTests.Containment_trims_the_candidate_before_comparison` and `Invalid_paths_refuse_without_throwing` pin these inputs at `tests/Antiphon.Tests/Infrastructure/HostCleanupCheckpointPathTests.cs:10-23`. No remaining failure from the original scenario was found.

### 2. The wider stat mask remains fail closed

`src/Antiphon.HostCleanup/Checkpoints/CheckpointNativeIo.cs:338-348` requests mask `0x3CF`, requires all requested facts, and catches unavailable statx bindings. Its portable fallback at `:350-359` cannot supply Linux mode/identity facts. `src/Antiphon.HostCleanup/Checkpoints/CheckpointFileReader.cs:44-49` refuses unknown/absent observations or a nonregular mode before `OpenRead` at `:58`.

Reconstruction: with statx unavailable for an existing ordinary Linux file, fallback metadata lacks the regular-file mode bits; the reader refuses it as nonregular. With an incomplete statx mask it returns unknown and refuses verification. This is conservative compatibility behavior, not a fail-open or a demonstrated regression requiring Code.

### 3. Cancellation propagation was added, but the default runtime is still uncancelable

The S1a source group starts at `c24e46e79d244427d5c9331a52266cf94672e82b`; later caller/context work includes `6332169e15cc7e95dcce53f4874ef963a158ffac`. Current examples:

- `tools/Antiphon.Checkpoints/Commands/WaitCommand.cs:69`, `:74`, `:82`, `:88`, and `:93` carry the caller token through state, ownership, required receipts, removal, and report output.
- `src/Antiphon.HostCleanup/Checkpoints/RunOwnership.cs:22-28`, `ToolCopyAuthority.cs:65-85,152`, and `ReceiptFile.cs:11-24` propagate it to verified reads.
- `src/Antiphon.HostCleanup/Checkpoints/CheckpointFileReader.cs:40-42,68` links it with the three-second read deadline and uses the linked token in the entered read.

Stored Code evidence `docs/superpowers/evidence/2026-10-15-card-0987-s1a-code.md:255-256` explicitly records item 3 as covered. Existing `tests/Antiphon.Tests/Infrastructure/HostCleanupCheckpointAuthorityTests.cs:231-246` cancels an already-entered Wait receipt read, asserts the actual stream token is canceled, expects OCE, and checks zero unlinks. `HostCleanupCheckpointReceiptTests.cs:105-123` separately checks entered-read deadline/cancellation wrapping. These witnesses were only read here.

This is not universal token threading: `SafeWrite.cs:92,125,404`, `tools/Antiphon.Checkpoints/Report/ReportWriter.cs:87-88`, and several synchronous compatibility readers still invoke default-token overloads. They remain bounded by the reader deadline. The original blanket claim that production receipt callers never pass tokens is obsolete, but the normal executable still calls `RunAsync(args)` without a runtime (`Program.cs:9-13`), creates a default runtime (`:34`), and its token property has no initializer (`CheckpointApp.cs:11-14`). No CLI signal-to-token setup was found in the inspected checkpoint production sources. This remaining activation/exit behavior is shared with A1/A2, not a separately proven receipt-read hang.

### 4. The duplicate native primitive is intentionally retained

`scripts/lib/checkpoint-owned-output.ps1:9-13` loads exactly `src/Antiphon.HostCleanup/Checkpoints/ExclusiveDirectory.cs` using `Add-Type` and calls `Create(string)`. That standalone source has only BCL imports and its own mkdir/CreateDirectory bindings (`:1-21`). The context overload in `CheckpointCleanupDefaults.cs:28-34` calls `context.Io.CreateExclusiveDirectory`; `CheckpointNativeIo.cs:97-120` implements that path.

The source consumers now differ on Windows: the standalone method passes a null security descriptor (`ExclusiveDirectory.cs:17-18`); the context implementation creates an owner-only DACL (`CheckpointNativeIo.cs:105-120`). Thus this is not byte-for-byte duplicate policy that can simply be deleted. No current failing consumer caused by this difference was established.

Stored S1a0 Code evidence, `docs/superpowers/evidence/2026-10-15-card-0987-s1a0-code.md` under **Native facade repair**, records an actual earlier Add-Type compilation regression when the standalone file gained a HostCleanup dependency. The S2 owner decision explicitly preserves standalone compilation at `docs/superpowers/plans/2026-10-16-card-0987-s2-extraction-refresh-plan.md:45-51`. Existing script witness `scripts/test-checkpoint-owned-output.ps1:57-80` checks standalone compilation, exclusive collision handling, sentinel/identity preservation, and no library assembly dependency. It does not claim Windows DACL parity.

## CARD-1307 details

### A1. Partial tool removal remains possible and later authority validation refuses

Confirmed by source reconstruction consistent with E4; no new native reproduction was run.

Preconditions: a dead executor; valid run-bound sealed authority; an unchanged tool directory containing at least two regular files; all initial Git/link/identity/inventory checks succeed. A caller supplies a token and cancels it after the first file is unlinked but before the second file's final verified read.

| Step | Current source | Result for this scenario |
|---|---|---|
| Load authority with caller token | `src/Antiphon.HostCleanup/Checkpoints/ToolCopyCleanup.cs:89-90`; `ToolCopyAuthority.cs:65-87` | Authority stores token; complete inventory validates. |
| Preflight and verify complete copy | `SafeDelete.cs:81-95`; `ToolCopyAuthority.cs:119-123` | Initial checks succeed before mutation. |
| Verify/unlink file 1 | `ToolCopyAuthority.cs:124-129` | File 1 is physically removed. |
| Cancellation arrives before file 2 read | `ToolCopyAuthority.cs:145-153`; `CheckpointFileReader.cs:40-42` | OCE occurs before file 2 can be unlinked. |
| Read wrapper converts cancellation | `ReceiptFile.cs:23-24` | IOException escapes the per-file loop; there is no rollback or persistent per-entry progress update. |
| Cleanup retries | `ToolCopyCleanup.cs:113-114`; `SafeDelete.cs:82` | First delay is 50 ms; the complete inventory is checked again. |
| Inventory no longer matches original seal | `ToolCopyAuthority.cs:103-109`; `ToolCopyCleanup.cs:109-110` | Returns Refused, typically `tool-authority-inventory-mismatch`; file 2 and the directory remain. |
| Later invocation with a fresh uncanceled token | `ToolCopyAuthority.cs:85-87,103-109`; `ToolCopyCleanup.cs:93` | The same full-inventory mismatch persists and the receipt directs manual removal. |

No receipt falsely certifies removal in this scenario: `CleanupReceipt.Removed` accepts only Removed/AlreadyAbsent (`ToolCopyCleanup.cs:4-7`), and Wait maps a retained/refused tool with otherwise green state to Invalid (`tools/Antiphon.Checkpoints/Commands/WaitCommand.cs:88-100`). With the original canceled token, the subsequent report read can also fail as an IOException, caught by Program as Invalid (`Program.cs:24-28`).

Timing matters: cancellation after the final file read is not necessarily observed during the remaining nonrecursive directory removals (`ToolCopyAuthority.cs:131-141`). Cancellation before initial authorization can instead leave the entire copy untouched. The claim is partial deletion for the stated interleaving, not that every cancellation leaves residue.

The default CLI has no caller cancellation source, as established above. Independently, every verified read has its own three-second timeout (`CheckpointFileReader.cs:40-42,68`): a timeout on file 2 after file 1's unlink follows the same IOException/retry/inventory-mismatch path even with the default token. This is a reconstructed reachable I/O failure condition, not evidence that it occurred in a particular production run.

Existing entered-read cancellation coverage at `HostCleanupCheckpointAuthorityTests.cs:231-246` occurs before deletion and asserts zero unlinks. `HostCleanupCheckpointCompatibilityTests.marker_survives_partial_deletion` (`:560-572`) concerns the separate temporary-root sweep and its marker, not ToolCopyAuthority. Neither proves a mid-tool-removal outcome. S2 expressly left A1/A2 out of scope (`docs/superpowers/plans/2026-10-16-card-0987-s2-extraction-refresh-plan.md:68-74`).

### A2. Cancellation outcome depends on its observation point

Confirmed contract gap from current source; no process exit code was measured here.

`tools/Antiphon.Checkpoints/Program.cs:15-19` catches only ManifestValidationException at Main; `:24-29` catches IOException, UnauthorizedAccessException and JsonException at RunAsync. Neither catches OperationCanceledException. `Execution/ExitCodes.cs:5-14` has no named caller-cancellation result.

For a valid run path that passes preflight, `Program.RunAsync` with a canceled `Runtime.CancellationToken` reaches `WaitCommand.WaitAsync` through `Program.cs:234-247`. The first loop check at `WaitCommand.cs:67` throws OCE; awaiting RunAsync throws rather than producing an integer command result. Cancellation during `_delay` at `:146` follows the same route. No particular OS unhandled-exception exit number is inferred.

By contrast, cancellation during a receipt read is wrapped as IOException (`ReceiptFile.cs:23-24`). Status can convert that to unreadable state and Invalid (`RunStateStore.cs:52-60`, `Program.cs:260-261`); Validate/Report can also become a generic invalid receipt or I/O refusal. Execute's broad catch reports ExecutorCrashed and returns 6 (`CheckpointApp.cs:77-116`). Wait explicitly rechecks the caller token after its state read (`WaitCommand.cs:69-70`), recovering OCE in that particular location. The outcome is therefore location-dependent; adding a catch at the outer boundary alone would not explain all currently wrapped cancellation paths.

Normal Main supplies no cancelable runtime token, so this remains latent for user cancellation through the CLI. The source exposes it to explicit API callers, including existing fixtures. The expected exit value, signal handling, and treatment of cancellation after partial removal are not defined by the current `ExitCodes` contract or by E4. This uncertainty requires Plan; it is not a reason to invent a code in Investigate.

### A3. File-only lookup already uses the injected registry

At `src/Antiphon.HostCleanup/Checkpoints/SafeDelete.cs:59`, the property is `private CheckpointWrite SafeWrite => new(context);`. The call at `:90` therefore invokes that instance's `MatchesCreation`. `SafeWrite.cs:121-126` reads `context.Registry.Content(path)` and uses the same context for its verified read. Each new context constructs its own registry (`CheckpointCleanupContext.cs:5-10`). The identically named static facade in `SafeWrite.cs:28-29` is not the target of the FileOnly call.

This is not a newly discovered repair after E4: `git show eda1525d9a37c761220c4d045dbcb984d3bbd682:tools/Antiphon.Checkpoints/Cleanup/SafeDelete.cs` shows the same property at line 59 and call at line 90. At that reviewed SHA, `SafeWrite.cs:112-117` likewise uses `context.Registry`. The advisory appears to have mistaken the property name for the static type; the stored record itself cannot establish why the reviewer made that attribution.

S2's stored plan already corrects the allegation at `docs/superpowers/plans/2026-10-16-card-0987-s2-extraction-refresh-plan.md:25,68-74`. The current dedicated witness is `tests/Antiphon.Tests/Infrastructure/HostCleanupCheckpointExtractionTests.cs:87-106`, `File_only_delete_uses_supplied_registry`: a fresh context over the same files refuses with zero unlinks, while the owning context reads and unlinks exactly once. No production fix is justified for A3.
