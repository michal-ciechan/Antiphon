# Antiphon Block Format (ABF), version 1

Status: **draft: breaking changes allowed until v1 is declared settled** (section 1, ABF-6). Draft 3,
2026-11-21. Owner: the review engine design
([docs/features/012-review-engine/design.md](../../features/012-review-engine/design.md), D-28).
Conformance corpus: [conformance/](conformance/README.md).

ABF is a plain-text, line-oriented format for structured messages between Antiphon and agents, and
between agents. It is built for producers that are language models:
- whitespace, key case and key separators are tolerated
- code snippets need no escaping in the common case, and a one-character escape otherwise
- surrounding prose is ignored
- every document maps to one canonical JSON form for storage

Uses: reviewer output, decision requests and responses over standing seats, completion requests,
comment triage, seeding output. The existing `--- next stage ---` and `--- review evidence ---`
report blocks are read as *legacy blocks* (section 6), with the values today's parsers give, except
that the legacy scan does not look inside ABF documents (6.2). The ABF parser replaces those two
parsers in design P0, before any report carries ABF documents.

## 1. Versions

**Draft rule.** Until v1 is declared settled (ABF-6), the version rules in this section don't bind.
Any lexical rule, document type or corpus case may change without a version bump, and each change
is recorded in the changelog. Once v1 is settled, the rules apply in full.

ABF has **two independent version numbers**:

| Version | Example | Changes when |
|---|---|---|
| Syntax version | `abf 1` | The lexical rules in this document change. Rare. |
| Document-type version | `review-findings/1.2` | A document type's records or fields change. |

Rules for document-type versions (`MAJOR.MINOR`):
- **MINOR** only adds: new optional fields, new optional record types, new trailing row columns, new
  enum values that consumers may treat as "other". Consumers **must ignore** fields, records and
  columns they don't know (section 5 says when that is silent).
- **MAJOR** is anything else: renaming or removing a field, changing a meaning, making an optional
  field required.
- A consumer states the majors it accepts. A producer's prompt names the exact version it must emit.
- Every type is listed in the [registry](#7-document-type-registry), with a changelog entry per
  version.
- Within one record type, declared names must stay distinct under the name fold (section 3.3).
  `end` is reserved and is never a record type.

## 2. Document structure

```
<optional preamble: ignored>
@abf 1 review-findings/1.0
=== finding F1
check: CHK-0142
severity: major
confidence: 0.8
file: src/Orders/OrderSaver.cs
anchor: _lock.Release();
--- body
Free text, any markdown, any code.
=== checks
CHK-0142 finding F1
CHK-0007 pass
=== end
<optional trailing text: ignored>
```

**Where a document starts.** At a header line `@abf <syntax> <type>/<major>.<minor>`. When the
consumer expects a type and the text has no header line, the parser starts a *headerless*
document at the first record line (`missing-header`, an error in strict mode). A text with no
header is never searched for
headerless documents unless the consumer expects a type; this keeps delegate reports, which are
mostly prose, from being misread.

**Where it ends.** At the first of:
1. `=== end`;
2. the next header line (a new document starts);
3. a legacy heading with two or more words, such as `--- next stage ---` (section 3.7);
4. for a wrapped document, the line that closes the wrapping fence (below);
5. end of input, after the report envelope cut (section 6.1).

Every end except `=== end` adds `missing-end`. Text after the end is ignored. Only the `=== end` line
belongs to the document; a header, legacy heading or closing fence line that ends it does not. This
decides what the legacy scan skips (6.2).

**Wrapped documents.** Models often put their output inside a markdown fence. The parser tracks
fences in the text outside documents. A header line inside an open fence starts a *wrapped*
document (`wrapped-document`). It ends at `=== end`, or else at the first later line that closes the
wrapping fence (same character, a run at least as long, nothing else on the line) and is not inside
a fence opened within the document.

**Several documents.** One text may hold several documents, each with its own header. A consumer
that expects type T selects one:
- the last document of type T that is not wrapped; if there is none, the last wrapped one;
- when more than one document of type T exists, `duplicate-document` is reported at the header line
  of each one not selected;
- diagnostics of documents not selected are discarded;
- no document of type T, but documents of another type: `wrong-type`; no document at all:
  `missing-document`.

## 3. Lines

### 3.1 Preparing the text

1. A leading U+FEFF (BOM) is removed.
2. **Line breaks** are CRLF, CR, LF, FF, NEL (U+0085), LS (U+2028) and PS (U+2029): the set .NET's
   `string.ReplaceLineEndings` uses, which the legacy parsers call. Lines are numbered from 1. A
   final line break does not start a new line.
3. **Whitespace** means Unicode White_Space as .NET `char.IsWhiteSpace` defines it. U+FEFF is not
   whitespace. (A TypeScript parser must not use `String.prototype.trim`, which strips U+FEFF.)
   A *blank line* is empty or whitespace only.
4. **Report envelope.** When the text is a delegate report, it is first cut at its closing report
   token (section 6.1).

### 3.2 Line forms

Structural lines start at column 0. Trailing whitespace is ignored on every line except content
lines of a multi-line field. Forms are tried in this order:

| Form | Pattern | Meaning |
|---|---|---|
| Header | `@abf <n> <type>/<major>[.<minor>]`, any case, words separated by whitespace | Starts a document. `<type>` is `[a-z][a-z0-9-]*` after lower-casing. A missing minor reads as `.0`. |
| Record | `=== <record-type>[ <id>[ <stray>]]` | Starts a record. `<record-type>` is a name (3.3). `<id>` is the next run of non-whitespace characters. Anything after the id is `stray-text`. |
| End | a record line whose record type folds to `end` | Ends the document. Anything after `end` is `stray-text`. |
| Legacy heading | `--- <words> ---`: single spaces, first word `[A-Za-z][A-Za-z0-9_-]*`, later words `[A-Za-z0-9_-]+` | A legacy block (section 6). Inside a document, see 3.7. |
| Field heading | `--- <field>`, with nothing else on the line | Starts a **multi-line field**. `<field>` is a name. |
| Field | `<key>[spaces]:` followed by whitespace or end of line | A **single-line field**. `<key>` is a name. The value is the rest of the line, trimmed (empty allowed). |
| Blank | empty or whitespace only | Ignored, except inside a multi-line field. |
| Row | any other line inside a record | Appended to the record's rows, trimmed. |

Lines that match no form are never structural: `---` and `===` on their own (a markdown rule, a
setext underline), `--- a/src/x.cs` (a diff header), `--- two words` (no closing `---`),
`===finding` (no space), `http://host` and `C:\path` (no whitespace after the colon).

### 3.3 Names and the name fold

- **Names** are record types, field names (single-line and multi-line), question names and the
  like. A name is one token: `[A-Za-z][A-Za-z0-9_-]*`. Only legacy headings have multi-word names.
- **The fold** of a name deletes `-` and `_`, then lower-cases ASCII letters. Two names are the
  same name when their folds are equal: `reason-category`, `reason_category`, `reasonCategory` and
  `ReasonCategory` are one field.
- **Declared spelling.** Schemas declare names in lower kebab case (`reason-category`). Canonical
  JSON writes the declared spelling. A name written any other way gets `name-spelling` (a warning,
  so an error in strict mode).
- **Undeclared names** keep the first spelling seen, trimmed. Later spellings with the same fold
  join that name.
- **Ids** (`F1`, `CHK-0142`, question names) are compared by fold for uniqueness and are written
  as given; they never get `name-spelling`.
- **Legacy keys are not folded.** Legacy blocks keep the parsers' rule: the whole key, compared
  case-insensitively, with no separator folding (section 6.3). Their canonical JSON keeps the
  camelCase spelling (`subjectTaskId`).

Rationale: models drift between kebab, snake and camel case, so ignoring case and separators
accepts all three without a style rule. Folding cannot merge two real fields, because declared
names must have distinct folds (section 1). Legacy keys stay unfolded because folding separators
would accept `subject-task-id`, which `ReviewEvidence.cs` rejects, and exact equivalence is the
point of section 6. Keeping the original spelling, instead of converting camelCase to kebab case,
keeps legacy JSON identical to the names in the parsers and in the bundle prompts.

### 3.4 Records and fields

- A record runs from its record line to the next record line, `=== end`, or the end of the
  document. Non-blank lines between the header and the first record are `stray-text`.
- Before a record's first field heading, its lines are single-line fields, rows or blank lines.
  After a field heading, every line up to the next structural line belongs to that multi-line
  field. So **rows and single-line fields come before multi-line fields**.
- Inside a multi-line field, these lines are structural: header, record, end, field heading, and a
  legacy heading of two or more words. A one-word legacy heading inside a document is a field
  heading (3.7).
- **Field forms are interchangeable.** A schema declares a field, not its form. The producer may
  write it single-line (`key: value`) or multi-line (`--- key`).
- **Single-line values** are trimmed.
- **Multi-line values** keep their lines exactly: indentation, internal blank lines and trailing
  whitespace. Leading and trailing blank lines are dropped, and lines are joined with LF with no
  final LF. An empty multi-line field has the value `""`.
- **Repeated names.** Every value is kept in source order, and canonical JSON writes an array.
  Schemas mark fields as repeatable. Repeating a field that isn't repeatable gives `duplicate-field`
  at the repeat; the typed value is the last one, as the next-stage parser does.
- **Repeated records.** A record with cardinality `1` or `0..1` that appears again gives
  `duplicate-record`. Canonical JSON keeps both. Typed JSON merges them in order, so rows append and
  fields follow the repeated-name rule. Two records of one type with the same id (by fold) give
  `duplicate-id`, and typed JSON keeps the later one.

### 3.5 Rows and columns

- A schema declares a record's columns, for example `<check-id> <status> [<detail>]`. Bracketed
  columns are optional, and only trailing columns can be optional.
- **Splitting.** Each column except the last takes the next whitespace-separated word. The last
  column takes the rest of the line, trimmed.
- **Quoting.** A column other than the last may be written in double quotes. Inside the quotes,
  `\"` is a quote and `\\` is a backslash. The quotes are removed. If the last column's whole text
  is one quoted string, it is unquoted the same way; otherwise it is kept as written. A quote with
  no closing quote is `bad-row`, and the row is dropped.
- A row without its required columns is `missing-column`, and the row is dropped.
- In a record type that declares no columns, a row is `unexpected-row` and is dropped.
- **Tolerant repairs**, only in record types that declare columns:
  - a leading list marker (`- `, `* `, `+ `, or `<digits>. `) is removed (`row-bullet`);
  - a single-line field whose name is not declared for the record is re-read as the row
    `<key> <value>` (`field-as-row`), so `CHK-0007: pass` in `checks` is the row `CHK-0007 pass`.
- **Tolerant repair in any record:** a row is re-read as a field when its text before the first `:`
  is one or more words (letters, digits, `_`, `-`, single spaces, starting with a letter) whose
  fold names a declared field of the record. The value is the text after the colon, trimmed
  (`row-as-field`). This catches `confidence:0.8` and `reason category: by-design`. Rows such as
  `opened src/a.cs: reason` stay rows, because `src/a.cs` is not a word.
- Rows keep their source order, including re-read rows.

### 3.6 Escaping and fences

**Escaping (backslash stuffing).** Inside a record, a line made of one or more `\` followed by text
that would be a header, record, end, field heading, legacy heading or field line loses exactly one
leading `\`. It is then content (in a multi-line field) or a row, and never structural. So
`\=== end` is the content `=== end`, and `\\=== end` is the content `\=== end`. Any other line
starting with `\` is kept as written. Strict producers escape every content line that would
otherwise be structural, even inside fences.

**Fences.** Inside a multi-line field, a fence opening line has at most three leading spaces, then a
run of three or more backticks or tildes; a backtick fence's info string has no backtick. It is
closed by the next line with at most three leading spaces, a run of the same character at least as
long, and nothing else but whitespace. Rules:
- Lines between the opening and closing lines are **protected**: never structural. A protected
  line that would have been structural gets `unescaped-in-fence`. Fences protect content in both
  modes, but strict mode treats this warning as an error.
- **`=== end` is never protected.** It ends the document even inside a fence, unless escaped. This
  bounds the damage an unclosed fence can do to the current document.
- The closing line is searched for up to the next `=== end` line or the end of input. A fence with
  no closing line **protects nothing** (`unterminated-fence`). Its opening line is ordinary content,
  and parsing continues on the next line.
- Fences in the preamble and trailing text only decide wrapping (section 2). Fences are not tracked
  in rows.

### 3.7 Ambiguities and how they resolve

| Case | Resolution |
|---|---|
| `=== check candidate C1` | Record types are one token. The type is `check`, the id is `candidate`, and `C1` is `stray-text`. Write `check-candidate C1`. |
| A row containing a colon | A line is a field only if it starts with a name followed by optional spaces, `:`, then whitespace or end of line. `opened src/a.cs: reason` is a row. `CHK-0007: pass` lexes as a field and is re-read as a row in a record with columns (`field-as-row`). To force a row anywhere, escape it: `\CHK-0007: pass`. |
| `key:value` with no space after the colon | A row; re-read as a field when the name folds to a declared field (`row-as-field`). URLs, Windows paths and `std::` stay rows or content. |
| `=== end` inside a multi-line field | Always ends the document, even inside a fence. Escape it as `\=== end`. |
| Other structural lines inside a multi-line field | End the field, unless escaped or inside a closed fence. |
| A unified diff in a field | `--- a/x.cs` and `+++ b/x.cs` are content. A deleted line `-- note` shows as `--- note`, which is a field heading: escape it as `\--- note`. |
| `--- name ---` (one word) inside a document | A multi-line field heading for `name` (`field-heading-suffix`). |
| `--- two words ---` inside a document | A legacy heading. It ends the document (`missing-end`), so a reviewer that forgets `=== end` before its `--- next stage ---` block loses nothing. |
| Text after `--- name` on the same line | Not a field heading, so content (or a row). This keeps lines like `--- see below` in prose from being read as fields. |
| A fence that never closes | Protects nothing (`unterminated-fence`). |
| A literal line starting with `\===` | Write `\\===`. |
| Text after the record id, or after `=== end` | `stray-text`, ignored. The document still ends at `=== end`. |
| The same field written single-line and multi-line | One field. Its values are kept in order, as for any repeat. |
| Several documents of the expected type | The last unwrapped one is used (`duplicate-document`). |
| The model wrapped its output in a markdown fence | A wrapped document. It ends at `=== end` or at the wrapper's closing line. |
| An echoed example document in a fence, then the real one | The real (unwrapped) one is used; the example is reported as `duplicate-document`. |

## 4. Canonical JSON

Every document maps to this shape. It is the form Antiphon stores, next to the raw text (design
D-6), and the form parsers are compared on:

```json
{
  "abf": 1,
  "type": "review-findings",
  "version": "1.0",
  "records": [
    {
      "type": "finding",
      "id": "F1",
      "fields": { "check": "CHK-0142", "severity": "major", "confidence": "0.8",
                  "file": "src/Orders/OrderSaver.cs", "anchor": "_lock.Release();",
                  "body": "Free text, any markdown, any code." },
      "rows": []
    },
    {
      "type": "checks",
      "id": null,
      "fields": {},
      "rows": [["CHK-0142", "finding", "F1"], ["CHK-0007", "pass"]]
    }
  ],
  "diagnostics": []
}
```

- `abf` is the syntax version. `type` is lower case and `version` is `MAJOR.MINOR`. They come from
  the header, or from the consumer's expected type for a headerless document. A generic parse of a
  headerless document with no expected type writes `null` for both.
- `records` are in source order. `id` is a string or `null`.
- `fields` maps each name to a string, or to an array of strings when the name repeats. Keys use
  the declared spelling, or the first spelling seen for undeclared names. Member order carries no
  meaning.
- `rows` holds, for a record type that declares columns, one array of column strings per row, with
  absent optional columns left off the end. Other records hold row strings.
- **All values are strings.** Canonical JSON keeps what was written, after the lexical rules and
  tolerant repairs (re-read rows and fields, bullets removed, quotes removed). It keeps unknown
  fields and records, and repeated records, so nothing is lost.
- **Typed JSON** is derived from canonical JSON by the type's schema. It converts values (section
  7.0), fills defaults, applies last-wins and merges, and drops unknown names and rows that fail
  validation. It is a deterministic function of the canonical JSON, so it is not stored.
- `diagnostics` holds every diagnostic from every stage, sorted by line, then code, then name. Each is
  `{ "line": <n>, "code": "<code>", "severity": "error" | "warning" | "info" }`. A diagnostic may
  add `"name"` (the field, record, column or option concerned) and `"message"` (free text).
- JSON values are compared structurally: object member order does not matter, array order does.

## 5. Parsing modes

| Mode | Used for | Behaviour |
|---|---|---|
| **Tolerant** (default for model output) | Reviewers, seats, agents | Accepts a preamble and trailing text, a missing header (when a type is expected), a missing `=== end`, wrapped and duplicate documents, name spelling variants, and the row and field repairs in 3.5. Fixable problems are warnings. Errors are only for what cannot be repaired. |
| **Strict** | Antiphon-produced documents, the conformance corpus | Requires a header, `=== end`, and exactly one unwrapped document. Every warning becomes an error. Info stays info. |

**Unknown names.** A record type or field the consumer doesn't know is `unknown-record` or
`unknown-key`. Its severity is a **warning** when the document's version is one the consumer fully
knows (same major, minor ≤ the consumer's). It is **info** when the document is a newer minor,
because the MINOR rule says the consumer must ignore it.

Recovery for model output: on errors, send one cheap repair call with the diagnostics and the
document, then retry the producer.

### 5.1 Diagnostic codes

Severity is the tolerant-mode severity. Strict mode turns warnings into errors.

| Code | Severity | Raised when |
|---|---|---|
| `missing-document` | error | No document of the expected type and no record line |
| `wrong-type` | error | Documents exist, but none of the expected type |
| `unsupported-syntax` | error | Header syntax number is not `1` |
| `unsupported-version` | error | Type major not accepted by the consumer; the document is not read further |
| `missing-header` | warning | A headerless document is read as the expected type |
| `missing-end` | warning | Document ended other than by `=== end`; reported at the line that ended it, or at the last line |
| `wrapped-document` | warning | Header is inside a markdown fence |
| `duplicate-document` | warning | Another document of the expected type was not selected |
| `stray-text` | warning | Text after a record id or `=== end`, or between the header and the first record |
| `unterminated-fence` | warning | A fence in a multi-line field never closes |
| `unescaped-in-fence` | warning | A structural-looking line protected only by a fence |
| `field-heading-suffix` | warning | `--- name ---` used as a field heading |
| `name-spelling` | warning | A declared name written another way |
| `unknown-record`, `unknown-key` | warning or info | See above |
| `duplicate-field` | warning | A non-repeatable field repeated |
| `duplicate-record` | warning | A `1` or `0..1` record repeated |
| `duplicate-id` | warning | Two records of one type share an id |
| `missing-record` | error | A required record is absent (reported at the header line) |
| `missing-required` | error | A required field is absent or empty (reported at the record line) |
| `bad-enum` | error for a required field, else warning | Value not in the enum; an optional field or a row is dropped |
| `bad-value` | error for a required field, else warning | Value doesn't parse as its type |
| `value-repaired` | warning | A value was normalised: `80%` to `0.8`, `yes` to `true` |
| `unexpected-row`, `bad-row`, `missing-column` | warning | Section 3.5; the row is dropped |
| `row-bullet`, `field-as-row`, `row-as-field` | warning | Section 3.5 repairs. `row-as-field` replaces `name-spelling` for that line. |
| Type codes | per type | Section 7 |

## 6. Legacy blocks

Antiphon delegate reports already end with blocks such as:

```
--- review evidence ---
subjectTaskId: aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee
reviewedSourceSha: 0123456789abcdef0123456789abcdef01234567
reviewedSourceClean: true
ordinaryScopeCompleted: Full
--- next stage ---
next: land
handoff: bind SHA
[antiphon-report:aaaaaaaa done]
```

They are read today by `PipelineHandoff.TryParse` (`server/Application/Services/PipelineHandoff.cs`)
and `ReviewEvidence.TryParse` (`server/Application/Services/ReviewEvidence.cs`). ABF reads them with
one **profile** per block type, so that every block those parsers accept outside an ABF document
gives the same values. (Note: `PipelineHandoff.cs` lives under `Application/Services/`, not
`Application/Core/`.)

**The two parsers are replaced in design P0.** `PipelineHandoff.cs` and `ReviewEvidence.cs` are
replaced by the ABF parser before the review engine's P1 shadow run (design D-28), so the server and
the engine never read the same report differently. Nothing produces ABF documents yet, so the
change breaks nothing. Until the replacement lands, the corpus records where today's whole-text
reading differs (`currentParsers`, section 8); those values retire with the old parsers.

### 6.1 The report envelope and the report token

- The closing line `[antiphon-report:<id8> done|blocked|failed]` belongs to the delegate harness,
  not to ABF. `DelegationReportFormatter.ReportToken` writes it
  (`DelegationReportFormatter.cs:28-32`). `TryReadReportVerdict` reads the verdict only from the
  last non-empty line, checks the 8-character id and the verdict word, and returns the body with
  that line removed (`DelegationReportFormatter.cs:70-128`).
- **Report envelope.** Before reading legacy blocks or ABF documents in a report, the text is cut
  at the **last** line whose trimmed text starts with `[antiphon-report:` (any case) and ends with
  `]`. That line and everything after it are dropped. The id and verdict are **not** checked
  (`PipelineHandoff.cs:180-201`, `ReviewEvidence.cs:156-174`). So a block after the token is never
  read, and a quoted token-shaped line cuts the text too.
- **Stored envelope.** `ReviewEvidence.TryParseStoredBody` reads a stored body whose outer token was
  already removed, and does not cut at token-shaped lines (`ReviewEvidence.cs:31-32, 40`).
  `PipelineHandoff` has no stored variant and always cuts, even on the settled body
  (`AgentTaskReplyService.cs:1292`). ABF keeps this asymmetry: the `next-stage` profile always uses
  the report envelope.
- Other harness tokens, such as `[antiphon-progress:<guid> commit=<sha>]`
  (`DelegationReportFormatter.cs:397-402`), are plain text to ABF.

### 6.2 Where legacy blocks are read

The legacy scan reads the enveloped text **outside ABF documents** (ABF-1, decided 2026-11-21):

1. **Find the documents.** Every ABF document that has a header line (section 2) is found, wrapped
   or not, selected or not. Headerless documents are never looked for here, because the legacy scan
   expects no type.
2. **Spans.** A document's span runs from its header line to the line that ends it. An `=== end` line
   is inside the span. A line that ends a document without belonging to it is outside: the next
   header line, a legacy heading (3.7), or the line that closes a wrapping fence. A document that
   runs to the end of the enveloped text spans to its last line.
3. **Scan the rest.** The profiles (6.3) read the lines outside every span, in order. A span ends any
   legacy block open before it, as a line starting with `---` does. Fence tracking in the profiles
   (the `review-evidence` backtick toggle, the generic profile's fence matching) sees only lines
   outside spans. Line numbers stay those of the full text.

Consequences:
- A legacy heading inside a document is not a block, for example a fenced example in a finding body
  (corpus `legacy/007`, `legacy/011`).
- An unfenced legacy heading of two or more words in a document's field ends the document
  (section 2), so it is outside the span and is read. A reviewer that forgets `=== end` before its
  `--- next stage ---` block loses nothing (`tolerant/008`).
- A fence opened inside a document can't hide a block that comes after the document.
- A text with no ABF header line is read exactly as today's parsers read it.

Producers put legacy blocks after `=== end` and directly before the report token, as
`StageHandoffContract` asks (`DelegationReportFormatter.cs:404-413`).

**Departure from today's parsers.** `PipelineHandoff.TryParse` and `ReviewEvidence.TryParse` read
the whole enveloped text. They give other values only when an ABF document holds a line they act on:
a legacy heading, a key line of a block that runs into the document, or an unbalanced
three-backtick line, which flips `ReviewEvidence`'s fence toggle. The corpus records the old values
in `currentParsers` (section 8) until the parsers are replaced in design P0.

### 6.3 Profiles

A legacy block starts at a heading line and runs over the lines after it.

**Shared rules (both parsers).**
- **Terminator (OQ-8).** A block runs to the first later line whose whitespace-trimmed text starts
  with `---`, to the start of an ABF document's span (6.2), or to the end of the enveloped text.
  **Blank lines do not end a block**, and neither do markdown headings or prose
  (`PipelineHandoff.cs:143-147`, `ReviewEvidence.cs:60-63`). The `---` test catches any later legacy heading, a markdown rule
  `---`, a `----` line, an ABF field heading, and an indented `  ---`.
- Blank lines are skipped. A line without a colon, or with the colon first after trimming, is
  skipped (`PipelineHandoff.cs:149-151`, `ReviewEvidence.cs:67-69`).
- **Key and value.** The key is the text before the first colon, trimmed; it may contain spaces and
  any characters. The value is the rest, trimmed. A key matches a declared key by whole-key
  comparison under .NET `OrdinalIgnoreCase`, with no separator folding (`PipelineHandoff.cs:152-159`,
  `ReviewEvidence.cs:70-79`). Undeclared keys are skipped.
- **No multi-line values.** A value is one physical line. A continuation line is skipped, or read as
  an unrelated key if it has a colon. The contract asks for `handoff` on one physical line
  (`DelegationReportFormatter.cs:409`).
- Legacy blocks raise no diagnostics. Problems show up in the values (`warning`), as they do in the
  parsers.

**Per-profile rules.**

| Rule | `next-stage` (`PipelineHandoff.cs`) | `review-evidence` (`ReviewEvidence.cs`) | Any other `--- name ---` |
|---|---|---|---|
| Heading line | Exactly `--- next stage ---`, any case. No leading or trailing whitespace. (:203-221) | Trimmed text is `--- review evidence ---`, any case. No leading whitespace; trailing whitespace allowed. (:128-131) | Legacy heading form (3.2) at column 0; trailing whitespace allowed. |
| Fences | Not tracked: a heading inside a fence counts (corpus `legacy/002`). | A line whose trimmed text starts with three backticks toggles "in fence"; there is no matching and no tildes. A heading in a fence is not standalone. (:121-127) | Fences matched as in 3.6, over the lines outside ABF documents (6.2) and without the `=== end` bound; a heading inside a closed fence is not a block. |
| Quoted or indented heading | Not a heading. | Leading whitespace and `>` prefixes are stripped to recognise the heading, which is then **not standalone**. (:142-154) | Not a heading. |
| Which block counts | The **last** heading before the envelope cut. (:132) | Exactly one standalone heading. None, but some not standalone: `review_evidence_not_standalone`. More than one: `review_evidence_duplicate`. (:41-45) | Every block is a record. |
| Placement | None | The standalone heading must come before the last `next-stage` heading outside ABF documents, else `review_evidence_after_next_stage`. (:47-50) | None |
| Indented field lines | Read (trimmed). (:145) | Skipped. (:64-65) | Skipped (ABF field-line form only). |
| Repeated keys | Last wins. (:154-159) | `subjectTaskId` and `reviewedSourceSha`: last wins. `ordinaryScopeCompleted` and `reviewedSourceClean`: exactly one, else unknown. (:72-88) | Kept as an array. |
| Declared keys | `next`, `handoff`, `artifact` | `subjectTaskId`, `reviewedSourceSha`, `ordinaryScopeCompleted`, `reviewedSourceClean`; and `reviewRound`, `reviewedRange`, which the bundle asks for (`stage-review.md:13-14`) but the parser ignores | Any ABF field name |

### 6.4 `next-stage` values

Computed from the last `next-stage` block (`PipelineHandoff.cs:162-177`):

| Value | Rule |
|---|---|
| `found` | `true` when any heading was found, even with no keys |
| `rawToken` | The last `next` value, or `null` when there is no `next` key. An empty value stays `""`. |
| `kind` | `rawToken` looked up in the alias table (`PipelineHandoff.cs:24-44`) under `OrdinalIgnoreCase`, then written as the canonical token (`investigate`, `plan`, `test-design`, `mutation`, `code`, `review`, `land`, `decide`, `none`). Otherwise `null` (corpus `legacy/004`). |
| `handoff` | The last `handoff` value, clipped to its first 400 UTF-16 code units, then `null` if blank (corpus `legacy/005`). |
| `artifactPath` | The last `artifact` value, if the whole value matches `` `?docs/[\w./-]+\.md`? `` (`PipelineHandoff.cs:21-22, 169-175`). The value is the path without backticks. Otherwise `null`. `\w` is .NET's Unicode `\w`: `[\p{L}\p{Mn}\p{Nd}\p{Pc}]`. |

The `next=` header bit (`PipelineHandoff.HeaderBit`) depends on the task role, so it is derived from
these values outside ABF.

### 6.5 `review-evidence` values

Computed in this order (`ReviewEvidence.cs:41-93`). The first rule that applies decides the
`warning`, and the result is unusable:

| Step | Result |
|---|---|
| No heading at all | `found: false` |
| Only non-standalone headings | `review_evidence_not_standalone` |
| Two or more standalone headings | `review_evidence_duplicate` |
| Standalone heading after the last `next-stage` heading | `review_evidence_after_next_stage` |
| `subjectTaskId` missing, not a GUID, or all zeros | `review_evidence_subject_invalid` |
| `reviewedSourceSha` not a full object id | `review_evidence_sha_invalid`; `subjectTaskId` is kept |
| Otherwise | `usable: true` |

- `subjectTaskId` is parsed by .NET `Guid.TryParse`, which accepts the N, D, B, P and X formats. It
  is written in D format, lower case.
- `reviewedSourceSha` follows `GitObjectId.TryNormalize`: no CR, LF or tab, trimmed, lower-cased,
  and exactly 40 or 64 hex digits (`GitObjectId.cs:9-19`).
- `scope` is `Full`, `Interim` or `None` when exactly one `ordinaryScopeCompleted` names one of them
  (`OrdinalIgnoreCase`). Otherwise it is `Unknown`, including when there is no block or the block
  is unusable before field parsing (`ReviewEvidence.cs:100-111`).
- `reviewedSourceClean` is `true` or `false` only when exactly one line has exactly `true` or
  `false` (case-sensitive). Otherwise it is `null` (`ReviewEvidence.cs:83-88`; corpus `legacy/009`).
- `scope` and `reviewedSourceClean` are still reported with the `subject_invalid` and `sha_invalid`
  warnings. The round cap (`ReviewEvidence.CapToRound`) and the subject checks in
  `ReviewEvidenceBindingService` (`:39-45`, `:72`) work on these values, not on the text, so they
  are unchanged.

### 6.6 Canonical form

The legacy blocks of a text form one **legacy document**:

```json
{ "abf": 1, "type": "legacy", "version": null, "diagnostics": [],
  "records": [
    { "type": "review-evidence", "id": null, "line": 1, "standalone": true,
      "fields": { "subjectTaskId": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee", "ordinaryScopeCompleted": "Full" },
      "rows": [] } ] }
```

- There is one record per heading the profiles recognise, in source order, including
  non-standalone `review-evidence` headings. `line` is the heading's line number.
- The record type is the heading name, lower-cased, with spaces and `_` turned into `-`.
- `fields` holds only declared keys, written in the declared spelling. Values are as written and
  trimmed, and repeated keys give arrays. A non-standalone record has empty `fields`. `rows` is
  always empty, because skipped lines are not kept.
- The **values** of sections 6.4 and 6.5 are the typed JSON of the legacy document.

### 6.7 Equivalence result (design OQ-8)

- **The draft terminator was wrong.** Neither parser stops at a blank line, at ABF lines or at
  prose. They stop only at a line whose trimmed text starts with `---`, or at the token cut. In real
  reports that means prose after a blank line is still inside the block (corpus `legacy/003`), and
  a key after a blank line still counts (corpus `legacy/010`).
- With the envelope (6.1), the scan outside ABF documents (6.2) and the profiles (6.3 to 6.5), **ABF
  gives the same values as `PipelineHandoff.TryParse`, `ReviewEvidence.TryParse` and
  `ReviewEvidence.TryParseStoredBody` for every input whose ABF documents hold no line those parsers
  act on.** That covers every text with no ABF header line, so every report written before ABF reads
  as it does today.
- **The one departure is deliberate** (ABF-1). A line inside an ABF document no longer counts. Corpus
  `legacy/007` is a quoted review-evidence example in a finding body, which today makes the real
  evidence a duplicate and unusable. `legacy/011` is a quoted next-stage example in a report with no real
  block, which today reads as `next: plan`. Both record today's values in `currentParsers`.
  Earlier drafts scanned the whole text so as to match the parsers exactly; the operator chose the
  safer rule, because the parsers are replaced in design P0, before anything writes ABF documents
  into reports.
- What makes exactness cost something, and how it is handled:
  - The two parsers disagree with each other on fences, quoting, indentation, trailing whitespace
    and duplicates. One generic rule could not match both, so each block type has its own profile.
    Generic ABF tolerance (the fold, trimming the heading, fences) does not apply to them.
  - .NET details must be copied by other ports: the line-break set, `char.IsWhiteSpace`,
    `OrdinalIgnoreCase`, the Unicode `\w`, `Guid.TryParse` formats, and clipping by UTF-16 code
    units. The corpus pins the cases that matter.
- The `legacy/` corpus holds real report tails and the parsers' own test cases. Its expected
  values can be checked against the current C# parsers (using `currentParsers` where a case has
  it) as well as the new ABF parsers.

### 7.0 Conventions

Schema tables list each record with its cardinality, fields and row columns. Fields are written
`name` (type; **req** or opt; *rep* when repeatable). Any field may be written single-line or
multi-line (3.4); "text" fields are usually multi-line.

| Value type | Typed form | Accepts |
|---|---|---|
| `text` | string | anything |
| `id` | string | one run of non-whitespace characters |
| `enum` | lower-case member | any case |
| `bool` | `true`/`false` | `true`, `false` in any case; `yes`, `no` with `value-repaired` |
| `prob` | number in [0, 1] | `0.85`, `.85`; `85%` with `value-repaired` |
| `int` | integer | decimal digits |
| `list` | array of strings | comma-separated, items trimmed, empty items dropped; repeated lines are concatenated, so a list field is always repeatable |
| `sha` | lower-case hex | 40 or 64 hex digits; 7 to 39 with `short-sha` (warning) |
| `path` | string | repo-relative, `/` separators |
| `lines` | `{ "start", "end" }` | `N` or `N-M` |
| `type-ref` | `type/MAJOR.MINOR` | `type/MAJOR` reads as `.0` |

### 7.1 `review-findings/1.0`

| Record | Cardinality | Fields | Rows |
|---|---|---|---|
| `finding <id>` | 0..n | `check` (id; req; a check id, or `none` for an unprompted finding), `severity` (enum `nit`\|`minor`\|`major`\|`blocker`; req), `confidence` (prob; req), `file` (path; req), `anchor` (text; req; one verbatim code line), `body` (text; req), `title` (text; opt), `flags` (list; opt; `security`, `data-loss`, …), `lines` (lines; opt; advisory), `suggestion` (text; opt; replacement code for the anchored lines) | none |
| `checks` | 1 | none | `<check-id> <status> [<detail>]`. `status` is enum `pass`\|`finding`\|`n/a`\|`unverified`. For `finding`, `detail` is a comma list of finding ids; otherwise it is an optional note. |
| `context` | 0..1 | none | `<kind> <path> [<reason>]`. `kind` is `opened` (read beyond the pack) or `missing` (wanted but not found). |
| `summary` | 0..1 | `body` (text; req): the reviewer's overall note, not posted unless policy says so | none |

Validation:
- Every check assigned in the pack appears in `checks` (`missing-check`, error). This needs the
  assignment, so a parser run without one skips it.
- An unknown check id is `unknown-check` (warning). A check listed twice is `duplicate-check`
  (warning; last wins).
- A `finding` row must name existing findings (`dangling-finding`, warning). A finding whose
  `check` is not `none` should have a `finding` row for that check (`check-status-mismatch`,
  warning).
- `n/a` means the check doesn't apply to the change. `unverified` means it applies but could not be
  verified, which feeds the approval rule in design 4.10.
- `anchor` is compared with the file at the reviewed SHA after trimming both. A finding whose anchor
  can't be resolved is dropped and recorded. This is the engine's job (design 4.8), not the
  parser's.

### 7.2 `decision-request/1.0`

A typed decision in the Jev System One shape (design 7.3): one shared `state` and named questions.

| Record | Cardinality | Fields | Rows |
|---|---|---|---|
| `request <request-id>` | 1 | `respond-with` (type-ref; opt; default `decision-response/1.0`) | none |
| `state` | 1 | `body` (text; req): the shared state, billed once per call | none |
| `question <name>` | 1..128 | `type` (enum `noul`\|`choice`\|`score`; req), `instructions` (text; req) | `choice`: `<value> [<description>]`, 1..255 rows. `score`: `<label> [<description>]`, 1..10 rows, lowest first. `noul`: none. |

Validation:
- Question names are names (3.3), unique by fold (`duplicate-id`, error).
- Choice values and level labels are unique within their question, compared exactly
  (`duplicate-option`, error). A `choice` or `score` question with no rows is `missing-options`
  (error). A `noul` question with rows is `unexpected-row`.
- The counts are the LiteLLM route's limits (design 7.3). Token limits are the adapter's job: it
  splits work rather than sending long context.

In the Jev body `{ model, state, questions }`, `state` comes from `state.body` and `model` comes from
the chain entry. Each `questions[<name>]` contains `type` and `instructions`. A `choice` question's
`criteria` maps each value to its description or JSON `null`. A `score` question's `criteria` is the
array of level labels, lowest first. A standing seat gets the ABF document and answers with the
format specified by `respond-with`.

### 7.3 `decision-response/1.0`

| Record | Cardinality | Fields | Rows |
|---|---|---|---|
| `response <request-id>` | 0..1 | `note` (text; opt) | none |
| `answer <name>` | 0..n, one per question | `value` (req unless refused), `confidence` (prob; req unless refused), `refused` (bool; opt; default `false`), `reason` (text; opt) | `choice` and `score`: `<option> <probability>`, one per choice value or level label. `noul`: none. |

Per question type:

| Question type | `value` | Rows |
|---|---|---|
| `noul` | prob: the probability of yes | none |
| `choice` | one of the choice values | a probability per choice value |
| `score` | one of the level labels | a probability per level label |

Validation, against the request:
- A `response` id that differs from the request id is `request-mismatch` (error): the whole
  response is rejected, so a seat cannot answer a stale request. Producers should always include
  `response`.
- A question with no answer is treated as refused (`missing-answer`, warning). This matches the
  LiteLLM rule that a missing answer key is a refusal. An answer with no question is
  `unknown-answer` (warning; dropped).
- A missing option row is probability 0 (`missing-option`, warning). An unknown option is
  `unknown-option` (warning; dropped). Rows whose sum is outside 0.99 to 1.01 are scaled to sum to 1
  (`probabilities-renormalised`, warning, at the answer's record line). A sum of 0 is `bad-value`,
  and the answer is treated as refused.
- A `value` that is not an option is `bad-value`. A `value` that is not the most probable option is
  `value-not-most-probable` (warning); the value is kept.
- `refused: true` escalates that question only (design 7.4); its other fields and rows are ignored.
- `confidence` is the producer's confidence in `value`. It is not calibrated (design 7.5).

The typed answers map onto `DecisionResult.Answers` (design 7.1): `Kind` comes from the request,
then `Value`, `Confidence`, `Probabilities` (the rows) and `Refused`. The engine fills `ServedBy`.

### 7.4 `completion-request/1.0`

| Record | Cardinality | Fields | Rows |
|---|---|---|---|
| `request <request-id>` | 1 | `expect` (type-ref, or `text`; req) | none |
| `instructions` | 1 | `body` (text; req) | none |
| `input [<name>]` | 0..n | `body` (text; req), `title` (text; opt), `source` (text; opt; a path or URI) | none |

- The seat follows `instructions` over the inputs, in order. It replies with one ABF document of the
  `expect` type, read in tolerant mode, or with free text when `expect` is `text`. A free-text reply
  is the whole reply, with the report envelope cut applied.
- `expect` must be a registered type, or `text`. A request type there (`decision-request`,
  `completion-request`) is `bad-value` (error). Input names are unique by fold (`duplicate-id`).
- The engine escapes every input line that would be structural. Diffs are the common case
  (corpus `valid/006`).

### 7.5 `comment-triage/1.0`

The stored triage of one or more human comments (design 6). When triage runs as a decision through
`IDecisionModel` (Jev or seats), the engine converts the `decision-response` into this type, so the
stored shape doesn't depend on the provider. A noul question `intent-<intent>` becomes a row, and
the `scope` and `reason-category` choice questions become those fields, with their confidences.

| Record | Cardinality | Fields | Rows |
|---|---|---|---|
| `comment <comment-id>` | 1..n | `finding` (id; opt; the finding the comment is about), `scope` (enum; opt), `scope-confidence` (prob; opt), `reason-category` (enum; opt), `reason-category-confidence` (prob; opt), `reason` (text; opt) | `<intent> <probability>`, 1..n |

Intents (design 6, multi-label: each row is an independent probability, the rows need not sum to 1,
and an absent intent has probability 0):

| Intent | Design 6 row | Intent | Design 6 row |
|---|---|---|---|
| `dismiss` | Dismiss / by design / won't fix | `request-recheck` | Request recheck |
| `dispute` | Dispute | `new-issue` | New issue raised by a human |
| `claims-fixed` | Claims fixed | `defer` | Defer |
| `will-fix` | Will fix | `instruction` | Instruction to the bot |
| `question-finding` | Question about a finding | `approval` | Approval / LGTM |
| `question-repo` | Question about the repo | `request-fix` | Request fix (P4, D-17) |
| `noise` | Noise | | |

`scope`: `instance` \| `path` \| `repo` \| `team` (this instance, this path, this repo, suggest to
the team). `reason-category`: `false-positive` \| `by-design` \| `out-of-scope` \| `accepted-risk`
\| `fix-later` \| `duplicate` \| `style-preference`. They apply when the comment dismisses, defers
or instructs.

Validation:
- A comment with no intent rows is `missing-intent` (error).
- An unknown intent is `bad-enum` (warning; dropped). New intents arrive with a MINOR version.
- A repeated intent is `duplicate-intent` (warning; last wins).
- `reason` is stored, never posted and never acted on. Comment text is untrusted (design 6
  guardrails).
- Routing thresholds, confirmation and authorisation are engine policy, not ABF.

### 7.6 `seed-candidates/1.0`

Output of a seeding extraction agent (design 14). Rows come before multi-line fields (3.4).

| Record | Cardinality | Fields | Rows |
|---|---|---|---|
| `source` | 0..1 | `uri` (text; req; the source spec), `cursor` (text; opt; the new cursor: last commit, date or document hash), `shard` (text; opt) | none |
| `check-candidate <id>` | 0..n | `title` (text; req), `severity` (enum as 7.1; req), `selector` (text; req), `prompt` (text; req), `humans` (text; req), `rationale` (text; req), `examples` (text; opt), `false-positives` (text; opt), `category` (id; opt), `flags` (list; opt), `globs`, `languages`, `tags`, `symbols`, `related-files` (list; opt), `requires-human` (bool; opt; default `false`), `refines` (id; opt; an existing check this one narrows) | Provenance: `<kind> <ref> [<excerpt>]`, at least one. `kind` is `doc`\|`commit`\|`issue`\|`pr`\|`incident`\|`card`\|`url`\|`other`. `excerpt` is a short verbatim quote. |
| `eval-case <id>` | 0..n | `repo` (text; req), `bug-commit` (sha; req), `fix-commit` (sha; req), `description` (text; req), `check` (id; opt; a candidate id here or a `CHK-` id), `files` (list; opt) | none |
| `related-hint [<id>]` | 0..n | none | `<when-path-glob> <also-load-glob> [<reason>]`, at least one |

Mapping to a check file (design 9):
- Front matter: `title`, `severity`, `flags`, `requiresHuman`, `triggers: { globs, languages, tags,
  symbols }`, `relatedFiles`, and `provenance` from the provenance refs, with `status: candidate`.
  The join stage assigns the `CHK-` id.
- Sections: `selector` → `# @model: Selector`, `prompt` → `# @model: Prompt`, `examples` →
  `# @model: Examples`, `humans` → `# @humans: Why this check exists`, `rationale` →
  `# @maintainers: Rationale`, `false-positives` → `# @maintainers: Known false positives`.

Validation:
- A candidate without provenance is `missing-provenance` (error).
- A candidate with none of `globs`, `languages`, `tags` and `symbols` is `missing-trigger`
  (warning); selection can still use the Selector.
- An unknown provenance kind is `bad-enum` (warning; read as `other`).
- `bug-commit` equal to `fix-commit` is `bad-value` (error). An `eval-case` `check` that names no
  candidate here and is not a `CHK-` id is `unknown-check` (warning).
