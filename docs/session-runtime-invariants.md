## CARD-0254 preserved operational detail

### Preserved Gotcha #76

- **Usage-limit walls pause that model on that kind, not the fleet** (CARD-0022): `ModelAvailabilityHold` is keyed `(Kind, ModelAlias)`. CARD-0072's 30-minute `WallPrompt` is not recovery for a per-model cap (the 2026-09-01 Fable 5 incident died in 1.1 s). `/usage-credits` is not a remaining-quota readout. Session-limit text that names a reset gets one resume at that instant + 2 minutes.

### Preserved Gotcha #3

- **A parked message whose session has no open task is discarded by a sweep, never retried** (CARD-0091): after `ParkedMessages:MinParkedMinutes` (10 by default), a machine-origin parked row is marked `Canceled` on purpose and leaves attention; Ui/Channel rows, completion notes, and rows on sessions with open tasks stay parked for a human decision. `ParkedMessages:DryRun` logs candidates without writing them.

### Preserved Gotcha #22

- **17204 is the canonical production session-runner port.** AppHost, the Scheduled Task daemon, `scripts/restart-session-runner.ps1`, and `server/appsettings.json` target `http://localhost:17204`. Storybook is **17209** (`db7696d`) — it used to squat 17283. The E2E fixture starts and owns a dedicated runner on a random loopback port, with manifests and logs under `tests/Antiphon.E2E/TestOutput/runner/`; session-dependent tests never use the always-on daemon. `AntiphonAppFixture` probes its child runner's `{BaseUrl}/sessions` at startup and `EnsureSessionRunnerReachable()` fails those tests immediately only if that child failed (URL + status or exception), instead of burning a 30–60s "did not reach Running status" timeout. Historical context: on 2026-08-08 a stray `node.exe` was squatting **17283** (the leftover simple-mode runner port the fixture then inherited from appsettings), so launches got **404** instead of connection-refused and failed 30–60s later with no hint as to why.

### Preserved Gotcha #23

- **Transcript-format runner mismatch:** a session-runner that predates a transcript-format change now refuses the launch instead of silently tailing the wrong file; the fix is `pwsh -File scripts/restart-session-runner.ps1`.

### Preserved Gotcha #25

- **A task row that says Succeeded does not end a process, and a process nobody owns is a zombie
  by construction** (CARD-0221): `RecoverFromBindRefusalAsync` (CARD-0085) released a Worktree
  delegate with neither a kill nor a pool mark, so the janitor never saw it, reconciliation saw
  DB-Running/runner-Running, and `claude.exe 17088` burned a core for seven days while the runner
  listed it Running the whole time. Any new release path must leave the session in exactly one of
  three states — killed, pooled warm (`Idle` + `PoolIdleSince`), or owned by a standing agent —

  (dry-run; `-Execute -Class PoolExpired` acts on the pool's own contract); the Failed/Stopped

### Preserved Gotcha #27

- **Never report a DB failure without the DB's own message.** `AgentService` used to catch `DbUpdateException` and rethrow "another operation changed agent data" with the exception discarded, so a duplicate-key error was indistinguishable from a real concurrency conflict — an intermittent test failure looked like a race on a row it had just created. `ConflictException` now takes an inner exception and `AgentService.DescribeDbFailure` names the constraint (`duplicate value on IX_Agents_Slug`). `ExceptionMiddleware.BuildStackTrace` already walks inner exceptions, so attaching one surfaces it in both the log and the problem-details response.

### Preserved Gotcha #29

- **Sessions survive runner restarts (pty-host split)**: Since the pty-host split (spec: `docs/superpowers/specs/2026-07-19-pty-host-split.md`), each agent session's ConPTY child lives in a detached per-session `Antiphon.PtyHost` process, NOT in the session-runner. `restart-session-runner.ps1` no longer kills sessions — the restarted runner re-adopts live hosts from `<SessionLogPath>/pty-hosts/manifests/*.json`. Scorched earth: `-KillSessions` flag or `POST :17204/sessions/kill-all`. Hosts run from shadow-copied binaries under `pty-hosts/bin/<yyyyMMdd-HHmmss>-<sha8>/` (never from `bin/` — running exes there would break builds); unreferenced version dirs are pruned automatically.

### Preserved Gotcha #32

- **Multi-line input to an agent TUI: normalize line endings to LF, wrap in bracketed paste, submit with a separate `\r`** (REQUIREMENT; live miss 2026-07-29, mechanism nailed down by probe runs against real Claude 2026-07-31): in written PTY input, **`\n` is always a literal newline** to Claude (multi-line LF bodies land intact even unwrapped and gap-split), but **a `\r` mid-body acts as Enter and SUBMITS the fragment before it** — CR/CRLF line endings are the real fragmentation hazard. The **inbox** conhost (`%SystemRoot%\System32\conhost.exe`, 10.0.19041.1 here — the one `CreatePseudoConsole` in kernel32 launches, i.e. every pty we create) **strips `\e[200~`/`\e[201~` from written input before ANY client sees them**, so the wrap alone cannot be relied on to protect CR bodies. Corrected 2026-08-12 (CARD-0030): this is a property of that BINARY, not of ConPTY — a modern `conpty.dll`+`OpenConsole.exe` delivers the markers byte for byte, and real Claude does **not** "receive our pastes intact" today, it receives them as typing, which is exactly why it clips them (`PtyBracketedPasteContractTests`; `docs/investigations/2026-08-12-bracketed-paste-conhost-CARD-0030.md`). `SessionMessageQueueService.DeliverAsync` does all three (ReplaceLineEndings("\n") → wrap → separate `\r`); any new code path that types into a session must too. Pinned by `FakeClaudeContractTests` (CR-endings fragment, LF-endings intact — fakeclaude models the measured behavior) and `SessionMessageQueuePtyIntegrationTests.Large_multiline_channel_body_submits_as_one_intact_turn` (CRLF body through the queue lands as ONE turn; red without the normalization).

### Preserved Gotcha #33

- **Local slash-commands strand working/idle — and `/clear` FORKS the conversation file** (REQUIREMENT, live miss 2026-07-31): `/model`, `/clear`, `/status` … write `<command-name>`/`<local-command-stdout>` USER records to the JSONL with NO TurnEnd (no API call). Anything computing working/idle must exclude them from activity (`TranscriptKinds.IsLocalCommandRecord` — used by server `IsWorkingAsync`, client `isWorking()`, kept in lockstep) or the session reads "working" forever and WhenIdle deliveries strand. `/clear` additionally writes its record into a FRESH self-chosen conversation file (the original gains nothing) — the TranscriptTailer must FOLLOW mid-session forks (`TryFindNewerFork`, 10s scan) or ingestion, working/idle, and channel reply dispatch silently die for the rest of the session (an AZ Care reply after a /clear never reached Telegram). Real shapes pinned by `ClaudeLocalCommandCanaryTests` (headed); fakeclaude mirrors them (`FakeClaudeContractTests`); fork-follow pinned by `TranscriptTailerCompactionTests`.

### Preserved Gotcha #34

- **A compaction strands working/idle too — and the two records that do it carry no marker** (REQUIREMENT, live miss 2026-08-11, CARD-0041: a delegate badged Working for two days with a dead session, its brief Pending behind it): a manual `/compact` writes SIX records and no TurnEnd ever follows (compaction makes no API call). Four are already excluded; the two that were not are **the RAW typed `/compact …` prompt** — Claude records the literal typed text as a plain user record *in addition to* the `<command-name>` wrapper, so the 2026-07-31 fix caught only half the shape — and **the synthetic continuation prompt** ("This session is being continued from a previous conversation…", `isCompactSummary: true`). Both fixes are needed and neither may lean on the backfill timestamp override: the real timestamps are non-monotonic against sequence (the boundary is stamped *later* than the continuation that follows it). The rule is now: **a `(manual)` CompactBoundary is a turn END** (`TranscriptKinds.IsManualCompactBoundary`, keyed on the trigger `TranscriptNormalizer.FromSystem` writes into the text) and **the continuation prompt is not activity** (`IsCompactionContinuationPrompt`), in all three lockstep implementations. An **auto** boundary must stay housekeeping — auto-compaction fires when a request starts over the context threshold, i.e. MID-turn, so ending the turn there would type into a working composer and hand the runner's CPU watchdog a false "proven idle". Matching raw `/`-prefixed text stays REJECTED (a real prompt may begin with a slash; the boundary outranks it instead). Because reading idle is not enough on a session that will never take another turn, a manual boundary also fires a **narrow** flush (`SessionMessageQueueService.FlushIfIdleAsync`) — deliver-if-idle only, never `IsTurnBoundary`: the turn-end path would publish a spurious "Agent finished" on every idle `/compact` and attempt task settlement against the STALE pre-compaction report. The fix is retroactive by construction (all three rules recompute over stored rows; no migration). Pinned by `SessionMessageQueueDeliveryVerificationTests` (the real stored shape + auto/raw-slash negatives + the flush), `TranscriptWorkingStateTests` (file order, no override to lean on), the client `isWorking` tests, `TranscriptNormalizerTests`, `FakeClaudeContractTests` (fakeclaude emits the full measured set) and `ClaudeCompactionCanaryTests` (headed; `Fixtures/compact-full-manual.jsonl`).

### Preserved Gotcha #35

- **An HttpClient timeout is an OperationCanceledException — check the token before treating it as shutdown** (REQUIREMENT, live miss 2026-07-31): `HttpClient` throws `TaskCanceledException` (an OCE subclass) on its 100s default timeout. A bare `catch (OperationCanceledException)` that exits a polling/receive loop turns one transient network stall into a silent, permanent death of that loop — the Telegram gateway's ingress stream ended this way and the service ran on deaf for 19h with ZERO log output. Rule: `catch (OperationCanceledException) when (ct.IsCancellationRequested)` for shutdown; everything else is a transient transport failure to log + back off + retry. Background pumps must also log-and-restart if their inner stream ever ends (`TelegramIngressService.PumpAsync`). Pinned by `TelegramResilienceTests` timeout tests (FakeTelegramServer `EnqueueGetUpdatesHang`/`EnqueueSendHang`).

### Preserved Gotcha #39

- **A stale sidecar claim must never beat the session the file is named for** (CARD-0181): C1 is no longer first-wins forever. A claim carries a strength derived from the basename — **Exact** iff the file is named `<this-session-id>.jsonl`, **Heuristic** otherwise. Exact displaces heuristic (the displaced tailer drops the file, resumes discovery, and the server records `TranscriptClaimRevoked`, Warning / Critical when channel-bound, never a `TranscriptBindStuck` escalation); nothing displaces Exact; heuristic-vs-heuristic stays first-wins. Restore from sidecars derives the same way, so a sidecar pointing at `<X>.jsonl` for session `Y ≠ X` is restored as heuristic and yields the moment `X`'s exact-id step runs. **C0** (strictly narrowing): a GUID-named file whose namesake has a sidecar under `<SessionLogPath>/transcripts/` is refused for everyone else, including fork-follow — Claude's self-chosen fork ids are GUIDs too, so "GUID-shaped" is not the gate, "this runner launched that session" is. The 2026-08-09 migration shim (`same cwd, written in the last 20s, unique, no C4`) is **deleted**; a restart-adopted session that never bound stays unbound until new input satisfies C4. C2/C2b/C3/C4 and the fork-follow rules are untouched. Pinned by `TranscriptClaimRegistryTests`, `TranscriptAdoptionSafetyTests` CARD-0181 cases, `TranscriptBindingIncidentTests` ClaimRevoked trio.

### Preserved Gotcha #40

- **A session must PROVE a transcript is its own before tailing it — cwd+recency binds a stranger's conversation** (REQUIREMENT, live miss 2026-08-09, CARD-0006): Claude's transcript root is per-cwd (`~/.claude/projects/<enc-cwd>/`), and several agents plus the human operator share `C:/src/Antiphon`. When an agent's own `<session-id>.jsonl` never appeared, the old discovery fallback took "the most recently written cwd-matching file" — **the operator's own live Claude conversation**. The agent then reported 65 of the operator's file edits as its own work, computed working/idle from a stranger's turns, and a channel-bound agent in that state would have relayed a private conversation to Telegram. `TranscriptTailer` now requires positive evidence for every non-exact bind: **C1** unclaimed (`TranscriptClaimRegistry`, one transcript ⇄ one session, restored from sidecars before `AdoptOrphanedHostsAsync` adopts anything), **C2** cwd match, **C2b** no conflicting `agentName` record (absence stays neutral), **C3** first *timestamped* record not older than the child process (waived on `--resume`, whose copied history legitimately predates the relaunch), **C4** a user prompt matching text this session was actually sent (`SessionInputLog`, fed from `RunnerSession.WriteAsync`) — the only positive id available, since **no transcript record carries a pid**. Restart re-adoption reads `<SessionLogPath>/transcripts/<sessionId:N>.json` and re-tails that exact path; the old "pre-existing but actively written, after 30s" arm is **deleted**, not tightened. Nothing qualifying ⇒ run with NO transcript (which correctly reads **idle** — the launch note is queued WhenIdle before any transcript exists, so "empty ⇒ working" would deadlock every launch) and raise a `TranscriptBindFailed` incident, **Critical when the agent is channel-bound**. Any new code path that picks a transcript file must go through these rules. Pinned by `TranscriptAdoptionSafetyTests` (14) and `TranscriptBindingIncidentTests` (4).

### Preserved Gotcha #41

- **The receiving TUI drops all but one ~1024-byte read chunk per event-loop turn — fakeclaude models it, OPT-IN** (CARD-0027 root cause, CARD-0028 model): our transport is lossless; the loss is in Claude's composer, which keeps ONE read chunk of a turn and discards the rest, cut on a 1024-byte boundary of the body, counted in UTF-8 BYTES. `ANTIPHON_FAKE_STDIN_CLIP=1` arms the deterministic worst case in fakeclaude (`=random` + `ANTIPHON_FAKE_STDIN_CLIP_SEED` for the live non-determinism, replayable; the fake prints `CLIP:mode=... seed=...` at startup). **Default OFF and it must stay that way** — `PtyLargeWriteTests` pins that OUR stack delivers 43 KB whole, which is true. Two transport facts any new test here must respect, both measured: ConPTY hands a single write to the child as SEVERAL reads up to ~14ms apart (so a "turn" window must exceed that jitter — the clip tests set `ANTIPHON_FAKE_BURST_MS=80`, well above the queue's 20ms body→CR gap), and it NARROWS non-ASCII input to one byte per char for a .NET peer regardless of codepage (so byte-vs-char chunking cannot be tested through the pty — `StdinClipModelTests` drives the model directly). Pinned by `FakeClaudeContractTests` (through ConPTY), `StdinClipModelTests` (arithmetic), `DelegationBriefCeilingPtyTests` (the brief ceiling end to end) and kept honest against real Claude by `FakeVsRealClipParityTests` (headed, `[Explicit]`, costs no model turns). **Scope, established 2026-08-12 (CARD-0030): all of this is true of TYPED input, which is all our pty can currently deliver.** Given a real bracketed paste — which needs a modern `conpty.dll`+`OpenConsole.exe` instead of the inbox conhost — the composer takes a different path and real Claude accepted **86 400 bytes in one write with zero loss**, while the same body unwrapped on the same binary still clipped. The ceilings are therefore correct *for the pty we create* and are coupled to it: do not raise them without shipping the binary.

### Preserved Gotcha #47

- **An interrupted turn ends with a marker, not a TurnEnd** (REQUIREMENT, live miss 2026-07-29): rejecting a tool call / Esc-interrupting mid-turn makes Claude write a `[Request interrupted...` USER message to its JSONL and NO TurnEnd. Anything computing working/idle from the transcript must treat that marker as the turn's end (`TranscriptKinds.IsInterruptPrompt` — used by `IsWorkingAsync` server-side, `isWorking()` client-side, and the queue-flush trigger in `AgentSessionRuntime`), or the session reads "working" forever and WhenIdle deliveries strand. Real-Claude behavior pinned by `ClaudeInterruptCanaryTests` (headed): a rejected permission dialog persists the marker; a plain Esc during a pure text stream instead UNWINDS the turn (prompt restored to composer, nothing persisted — no marker to see, and nothing strands because no prompt was recorded).

### Preserved Gotcha #48

- **A brand-new working directory opens Claude on the TRUST DIALOG, and everything downstream reads that as a healthy, idle session** (REQUIREMENT, live miss 2026-08-16, CARD-0047's standing check interpreter): Claude's trust prompt ("Is this a project you created or one you trust?") is per-cwd in `~/.claude.json`, so the FIRST launch into any directory nobody has run Claude in — a purpose-built scratch dir, a fresh worktree — parks the TUI on a modal and waits. That state is invisible to every signal we have: a modal makes NO output, so the quiet-period ready detector calls it READY; the composer then swallows every write; delivery verification correctly reports `NoComposerEvidence`; and the always-on kill restarts the session **into the same directory, onto the same dialog**. The specialist died this way on all seven of its launches, interpreting zero checks, with the deterministic-digest fallback covering for it the whole time. `ClaudeBlockingPromptDetector.ClearStartupTrustPromptAsync` now runs in BOTH Claude adapters' `WaitForReadyAsync`, after the quiet wait (the modal has rendered by then) and before ready is reported. **It answers the trust dialog and nothing else**: choosing the working directory IS the trust decision and the operator already made it, but keying "1" into a tool-permission modal would approve a tool call nobody authorised, and the generic numbered-menu arm is too weak a shape-match to type into a live session on — those are logged and left standing. Answering persists in `~/.claude.json`, so it fires once per directory, ever. The deny-all PreToolUse hook was NOT the cause and did not need narrowing (spec §4.2's open question, settled). Pinned by `ClaudeStartupTrustPromptTests` (unit) and `RunnerClaudeAdapterTrustPromptTests` (through the production adapter); the real-Claude shape stays in `ClaudeTrustPromptCanaryTests`.

### Preserved Gotcha #49

- **Never kill a session on "the transcript does not contain X" without PULLING the transcript first** (REQUIREMENT, live miss 2026-08-16, same run): the live transcript stream is not a reliable clock. On session `e809ce65` Claude wrote the confirming `UserPrompt` **0.9s** after the submit and the server did not store it for **45 seconds** — six records landed in one burst at the exact instant the session was killed, because the flush is triggered by the session ENDING. So the kill produced the evidence that the kill was wrong, and the existing `LateConfirmAttemptedMessagesAsync` then marked the message Sent on the corpse. Worse, `IsWorkingAsync` reads the same rows, so the CARD-0055 working-kill guard reported `working=false` about a session that was visibly mid-turn on screen — **both brakes fail together because they share one dependency**. Waiting cannot win this race: a 90-second grace was tried on session `5536ae88` and still lost by the same 1.2s. `HandleDeliveryFailureAsync` now runs `GraceConfirmAsync` before anything destructive, which calls **`AgentSessionRuntime.CatchUpTranscriptAsync`** — the fetch-and-persist half of `SyncTranscriptAsync` with NO queue side effects, because `SyncTranscriptAsync`'s turn-boundary flush re-enters the queue and the caller holds the per-session lock. Confirmation is the same text match over the same stored baseline, so this can only ever turn a failure into a success on positive evidence; a body too short to identify by text (an auto-continue) is never grace-confirmed. `working` is recomputed after the window, so the pull fixes the working guard too. `PostFailureConfirmGraceSeconds` (20s) is a bound on the pull loop, not a waiting period. Pinned by `SessionMessageQueueDeliveryVerificationTests.A_record_that_lands_just_after_the_deadline_confirms_instead_of_killing`.

### Preserved Gotcha #50

- **A delivery is Sent only when its `UserPrompt` transcript record exists — never because the screen merely redrew** (CARD-0055, shipped `4bb65fb`/`0134964`/`8410d9a`/`165da34`): `SessionMessageQueueService.DeliverAsync`'s old verdict was "the output sequence advanced after Enter" (`WaitForSequenceAdvanceAsync`), and any redraw satisfies that — including the composer re-rendering the text it is STILL HOLDING. Measured on session `cefed08a` (task `817682e9`): a completion note (`ea2feb92`) was marked Sent at 15:16:20Z and sat unsubmitted in the composer for **104 minutes**, only reaching the transcript when the NEXT delivery's Enter pushed it in; the note behind it (`15c9150e`) was lost outright — its own Enter instead submitted `ea2feb92`'s stale body, a new `UserPrompt` record DID appear, the sequence DID advance, and it was marked Sent while its own text died with the composer. The fix (`WaitForTranscriptConfirmAsync`, `server/Application/Services/SessionMessageQueueService.cs:898`) polls `TranscriptEntries` for a `Kind == UserPrompt` row past a pre-write sequence baseline, re-pressing Enter every `ReEnterIntervalSeconds` (7s, default) up to `SubmitAttempts` (3) total, giving up after `TranscriptConfirmTimeoutSeconds` (30s) with the new verdict `NoTranscriptRecord` (`DeliveryVerificationSettings`, `server/Application/Settings/SupervisionSettings.cs`). **A record arriving is not enough — the 15c9150e shape proves the record's TEXT must match**: confirmation is `PromptSubmissionMatch.IsConfirmedBy` (`src/Antiphon.SessionRunner.Contracts/PromptSubmissionMatch.cs:163`, called from `TryFindConfirmingRecordAsync` at `SessionMessageQueueService.cs:967`), which contains-matches the normalized body's **HEAD** window (`MatchWindowChars` = 200 chars) against the normalized record — head, not tail, because the pty's known loss mode (CARD-0027) keeps tails, and a tail match could certify a clipped body as delivered whole. A body under `MinMatchChars` (12 — e.g. an auto-continue "Continue.") is unidentifiable by text and takes a weak-match arm (any new row past the baseline counts) — weaker than a text match, still strictly stronger than the redraw signal it replaces. Retries are **Enter-only, never a re-type**: if the first Enter really did submit, the composer is empty and a re-press is a no-op (the same contract `VerifiedPromptSubmitter` has relied on at boot since 2026-08-08); the per-session queue lock guarantees nothing else can be standing in the composer for a re-press to submit into. **Late-confirm runs before any redelivery** (`LateConfirmAttemptedMessagesAsync`, `SessionMessageQueueService.cs:596`): a message that was already typed once gets the matcher re-run over everything that arrived since ITS OWN stored baseline before it is ever typed again — so a false-negative confirmation (matcher blind, ingestion stall) resolves itself on the next flush instead of double-typing; this is what makes automatic retry safe. A `NoTranscriptRecord` verdict also gets a **working-kill guard** (`HandleDeliveryFailureAsync`, `SessionMessageQueueService.cs:1069`): if the session is mid-turn, the submit may have succeeded with the matcher blind, so the always-on kill is withheld and the message stays Pending for the next turn-end's late-confirm; not-working always-on still gets killed as before, for a fresh composer. At `MaxDeliveryAttempts` (3) a message PARKS instead — stays Pending, visible in the queue UI, excluded from every automatic redelivery path — and the parking incident is Critical when the agent is channel-bound (a parked channel reply is a human waiting on a dead line). The observability gate degrades to the old screen-only verdict, never fails, when the session has zero `TranscriptEntries` at baseline time (unbound, or pre-first-turn). **Boot/card-launch prompts (`VerifiedPromptSubmitter`) are deliberately OUT of scope**: at boot the transcript file does not exist yet — it is CREATED by the first submit, so there is nothing to confirm against. Two assumptions this design bears its full weight on — Enter-on-an-already-empty-composer is a no-op, and a COLLAPSED paste's JSONL record carries the full body rather than the `[Pasted text #N +M lines]` placeholder (CARD-0037) — went unpinned until headed canaries measured them against real Claude; both held, so the spec's planned contingency (a weak-match arm for bodies above the paste-collapse threshold) was never built. Pinned by `SessionMessageQueueDeliveryVerificationTests`, `PromptSubmissionMatchTests`, `SessionMessageQueuePtyIntegrationTests` (through fakeclaude's `ANTIPHON_FAKE_SWALLOW_ENTER`), `ClaudeSubmitConfirmCanaryTests` (headed, `[Explicit]`), and their `FakeClaudeContractTests` CI mirrors (`Enter_on_an_empty_composer_submits_nothing`, `A_swallowed_enter_redraws_holds_the_body_and_the_next_enter_submits_it_once`, `A_collapsed_pastes_transcript_record_carries_the_full_body`).

### Preserved Gotcha #51

- **CARD-0055's Sent now also requires completeness, not just a matching head** (CARD-0024): `PromptSubmissionMatch.IsConfirmedBy` is identity (head window, 200 chars) and is UNCHANGED — C4 still uses it. After identity, `IsCompleteIn` requires the normalized `UserPrompt` row to contain the full normalized body (whitespace-free arm included, same as identity, so a Grok newline-join is not a splice). Identity without completeness is a new `DeliveryVerdict.Truncated`: park immediately (`DeliveryAttempts = MaxDeliveryAttempts`), raise `AgentIncidentKind.TruncatedTerminalDelivery` (25; Warning, Critical when channel-bound), do **not** kill, do **not** re-type (that would double-send). Late-confirm uses the same completeness check — a splice that lands after the confirm window must not be promoted to Sent. Distinct from `OversizedTerminalDelivery` (size-before-send). Boot/`VerifiedPromptSubmitter` stays out of scope. Pinned by `PromptSubmissionMatchTests` completeness cases and `SessionMessageQueueDeliveryVerificationTests` CARD-0024 tests.

### Preserved Gotcha #52

- **A failed launch must kill what it started, and reconciliation must see both directions** (CARD-0056, shipped `1793d6f`/`e9643f5`/`8458961`/`77065c3`): a 15-character `/remote-control` was typed into a healthy, resuming orchestrator (`cefed08a`) mid-resume-render, never reached its composer, and `VerifiedPromptSubmitter` correctly gave up after its 15s `EvidenceTimeoutSeconds` poll and threw `PromptDeliveryException`. The catch in `LaunchInteractiveProcessAsync` (`AgentSessionService.cs`) called only `adapter.DisposeAsync()` — on `RunnerClaudeAdapter` that is literally `=> ValueTask.CompletedTask` (`RunnerClaudeAdapter.cs:170`), because the agent lives in a detached pty-host that deliberately outlives the server. The process **leaked** while the row was marked Failed; the AlwaysOn supervisor then correctly restarted a replacement against that false signal; and `SessionReconciliationService.ReconcileSessionsAsync` only ever queried `LiveStatuses`, so DB-dead-but-runner-alive was invisible to it forever. Two leaked sessions were found live on 2026-08-16 — `cefed08a`, three days old, and `e12439ee` — and the leaked session was the **operator's own working conversation**, marked Failed while healthy. **The knock-on that made it worse than a leak**: `AgentTaskDispatcher.CallerIsListeningAsync` (`server/Application/Services/AgentTaskDispatcher.cs:624`) requires the parent session to be `Created`/`Starting`/`Running` before it will deliver a scheduled check-in, so the false Failed row **silently disabled CARD-0047 check-ins** for about four hours until the row was hand-patched. Four fixes, landed as four independently-testable slices: (1) **`KillAndDisposeAsync`** (`AgentSessionService.cs:427`) — kill with `KillGraceMs` on `CancellationToken.None`, then dispose — now runs first in all **three** leaking catches: `LaunchInteractiveProcessAsync`'s (`:398`), `StartAsync`'s outer catch (`:242`), and **`ResumeAsync`'s** (`:774`) — the third catch was not in the original plan and was found only while implementing; a kill failure is swallowed so it never replaces the launch failure being rethrown, since an `HttpClient` timeout arrives as a `TaskCanceledException` with nothing actually cancelled. (2) `SendRemoteControlCommandsAsync` now degrades instead of failing a healthy launch: a `PromptDeliveryException` on `/remote-control` (interactive AND card paths — it is monitoring, not the session's purpose, on both) is caught, `/rename` is skipped (nothing appends to a composer that may still be holding the first body), and an `RcDegraded` incident (Warning, `AgentIncidentKind.RcDegraded = 7`) is raised instead — the armed-marker timeout got the same incident, upgraded from a log line. (3) **`SendBootPromptWithRetryAsync`** (`AgentSessionService.cs:482`) wraps every launch-time write (`/remote-control`, `/rename`, a card's work prompt) and retries the WHOLE verified submit — type, evidence-poll, Enter — up to `BootPromptAttempts` (3, `SupervisionSettings.cs:180`) with `BootPromptRetryDelaySeconds` (2s) between attempts; re-typing is safe here specifically because the exception means no composer evidence appeared, i.e. the same check that would gate an Enter says the composer does not hold the body, so a retry cannot double-submit — CARD-0055's never-re-type rule governs the phase *after* evidence, this is the phase *before* it. If all attempts still throw, `TryLateConfirmBootPromptAsync` (`:556`) pulls the transcript (`CatchUpTranscriptAsync`, not trusted to have streamed) looking for a `UserPrompt` row past a pre-first-keystroke baseline that either names the command (`TranscriptKinds.TryReadLocalCommandName`) or satisfies `PromptSubmissionMatch.IsConfirmedBy` — proving the submit landed while the screen reads were blind. This is gated to resume-mode relaunches only (a fresh boot has no transcript file yet — CARD-0055's boot scope-out still stands there) and carries a **`BootConfirmClockTolerance` of 30 seconds** (`:461`) on the confirming record's own timestamp: a `--resume` re-ingests the conversation's copied history, which contains the *previous* boot's own `/remote-control` record, and backfill rebases unseen entries past the baseline, so sequence alone cannot tell the old record from a genuinely-late new one — only the wall-clock timestamp can. (4) `SessionReconciliationService` grows a third pass that fetches the runner's session list **once per sweep, unconditionally** (previously fetched only when a DB-live row needed checking) and, for each runner session reporting `Running`, looks up the DB row: no row at all ⇒ alert only, never kill (something nobody claims is still somebody's work); `Failed` ⇒ **re-adopt** (the default, `SessionReconciliationSettings.ReAdoptEnabled`); `Stopped` ⇒ **the only auto-kill arm**, because an operator already expressed stop intent and the kill evidently didn't take. Re-adoption demands *positive* evidence — a `Pid` or `HostPid` naming a real process **and** a per-session buffer probe actually answering (sequence advancement is deliberately NOT required: an idle session's sequence doesn't move, and "quiet therefore dead" is the exact shape of false positive that started this) — writes `Status = Running`, restores the owning agent only if its `PersistentSessionId` still points at this session (otherwise the row goes back to Running **unclaimed but visible**, for the operator to decide), and is capped at 3 re-adoptions per session per server uptime before the 4th flap escalates Critical instead of looping. **The constraint that outranks everything here: unclaimed never implies kill** — the false positive fired on a perfectly healthy session, and a reconciliation pass that resolved the mismatch by killing would have killed the operator mid-sentence. Pinned by `AgentSessionLaunchFailureTests` (11), `SessionReconciliationServiceTests` (14), and `PromptSubmissionMatchTests` (the `<command-name>` wrapper's match on `/remote-control` pinned directly).

### Preserved Gotcha #53

- **A mid-turn `QueuedUserPrompt` must not become the channel-reply turn's identity** (CARD-0233): `ChannelReplyDispatcher.DispatchAsync` used to take the latest `UserPrompt|QueuedUserPrompt` before the latest `TurnEnd` (CARD-0154's queued-only widen). ### Preserved Gotcha #54

- **A channel reply's route OUT must be as durable as the message's route IN — and a lost reply must never be a silent `return`** (REQUIREMENT, live miss 2026-08-17, CARD-0067, shipped `c4df66b`): `ChannelBridgeService` used to call `_dispatcher.Track(...)` into `ChannelReplyDispatcher._pending` — a `ConcurrentDictionary`, the ONLY store — immediately before `_queue.EnqueueAsync(...)` committed the inbound half to Postgres. Two stores for the two halves of one round trip, one durable and one not. A hard restart at 09:05:01Z killed four live correlations mid-conversation; the Family agent then wrote a wedding guest list **twice** (1 849 and 2 487 chars) and neither reply was ever published — Kafka shows nothing produced for that chat for 47 minutes — and `OnTurnEndAsync` returned SILENTLY on the resulting miss, so no log line, no incident and no surface anywhere recorded it. There is now **no correlation map**: `Track`/`PendingChannelReply` are deleted, the bridge no longer knows the dispatcher exists, and the reply target is resolved at dispatch time from the `SessionQueuedMessages` row (`Body` = the prompt to match, `ConversationKey` = `{provider}:{conversationId}`, handle from the channel catalog). **Any new code path that routes a channel message into a session must persist a Channel-origin row with a `ConversationKey`, or its reply is unroutable.** The one new column, `SessionQueuedMessage.ChannelReplySettledAt`, is the IDEMPOTENCY half, not the target half, and zero columns was genuinely insufficient: dispatch is re-triggered for the same turn constantly (a late `AssistantText`, the closing `TurnEnd`, a reconnect's backfilled boundary), so a durable target with no durable consume marker would **re-answer the last turn on every restart** — a duplicate into a live family chat. It is claimed BEFORE the produce and un-claimed if the produce throws, the same shape as the queue stamping `Sent` before it types; the migration backfills every pre-existing Channel row as settled, without which the first turn after deploy could answer a days-old prompt. Every channel correlation now ends in exactly one of two states: a published reply, or a **Critical `AgentIncidentKind.ChannelReplyLost` (21)** incident — raised when it ages past `PendingReplyTtlMinutes` unanswered (clock from `SentAt`, never enqueue) or its conversation key routes nowhere — swept both per-session on turn end and **globally once a minute** from `AgentSupervisorHostedService`, because the 2026-08-17 shape is a session that answers into a void and may never end another turn to be swept on. A turn-end MISS logs a Warning and deliberately leaves the correlation owed (a turn the operator started is normal; the TTL is the backstop). Same defect class as CARD-0055 in the opposite direction. CARD-0068 closed the remaining follow-up drop: `DispatchFollowUpAsync` used to bail when `turn.PromptSeq` was no longer the latest `UserPrompt` in the session, so seq 469 (the guest list) was discarded because seq 471 (a newer prompt) landed in the SAME `PersistTranscriptAsync` batch as the text it concerns — there is no window in which the trailing text exists and the next prompt does not. Follow-up now uses the same sequence window `ExtractTurnResponseAsync` already uses (`PromptSeq < seq < nextPromptSeq`, lower bound `MaxTextSeq`); a newer prompt is the window's upper bound, not a reason to throw in-window text away. Pinned by `ChannelReplyDurabilityTests` (6 — restart survival, no double-answer after restart, the Critical incident, no re-raise, unroutable, and owed-not-settled on a miss) and `ChannelBridgeTests.Trailing_text_still_follow_ups_when_the_next_prompt_landed_in_the_same_batch`.

### Gotcha #83

### Gotcha #84
