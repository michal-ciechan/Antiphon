# Architecture principles

Use these rules when changing ownership, a dependency boundary, a public contract, or the implementation of an existing capability. [Project context](project-context.md) owns conventions and layer direction. [The orchestration loop](orchestration-loop.md) owns stage authority, verification and landing.

## Design rules

1. **Single source of truth.** Give each business rule, state transition, data contract, configuration value and standard a named owner. Derive views, link to the owner, or check the projection against it. `CLAUDE.md:1` imports `AGENTS.md`. The generated operating settings read live state and leave standing policy in the repository (`docs/agent-instruction-file-contract.md:41`). Two tests apply different limits to the same TestDesign body (`tests/Antiphon.Tests/Application/ScopedVerificationInstructionTests.cs:135` and `tests/Antiphon.Tests/Application/InstructionBundleTests.cs:937`), showing how a copied policy can drift.
2. **Canonical implementation.** Find every implementation of the same responsibility and verify which callers and contracts it serves. Route equivalent callers through one implementation. `TestTimings.WriteEvent` and `TimingJournal.AppendAsync` each write the v1 timing journal and handle event identity and producer ownership (`scripts/lib/Antiphon.Nightly/TestTimings.cs:145`, `:163`, and `tools/Antiphon.Checkpoints/Timing/TimingJournal.cs:25`, `:75`). Compare the two producer and durability contracts before treating their differences as redundant.
3. **Deep modules.** In John Ousterhout's sense, expose a small, stable interface that absorbs real complexity. `AddDelegationWorktreeGraph` hides a graph that test harnesses previously registered by hand (`tests/Antiphon.Tests/TestHelpers/DelegationTestServices.cs:68`, `docs/testing-and-build.md:1714`). `NightlyTests.WriteTimingEvent` is a small seam around the journal writer (`scripts/lib/Antiphon.Nightly/NightlyTests.cs:891`). Removing it requires preserving the best-effort failure policy at both callers. Judge it by the complexity it absorbs and where that policy belongs.
4. **High cohesion and low coupling.** Keep related invariants with their owner. Trace dependency direction, cycles, shared mutable state and infrastructure exposure using the existing layer rules. The server layer map and allowlist make exceptions visible. Two pinned dependencies already fail on regression while the wider census runs in warn mode (`tests/Antiphon.Tests/Infrastructure/C1729LayeringGuardTests.cs:87`, `:104`, `:117`).
5. **Locality of change.** Prefer one logical change point per concept. A boundary contract can have a deliberately coupled implementation, caller and test. Keep unrelated consumers out of that fan-out. The Review run pack endpoint is registered and exercised over HTTP, but its route is absent from the feature API route table at the surveyed tip (`server/Api/Endpoints/ReviewRunEndpoints.cs:47`, `tests/Antiphon.Tests/Review/ReviewDelegationRunnerApiTests.cs:123`, `docs/features/012-review-engine/api.md:167`). Link readers to one maintained contract and let checks catch drift where an independent representation earns its keep.
6. **Deletion over accumulation.** Count obsolete paths that can come out with the slice. Migrate callers before removing old entry points. Include CLI and script invocations, scheduled and deployment jobs, configuration, stored data, docs and applicable test selectors when tracing callers. The review CLI commands replaced two PowerShell scripts, while the getting-started instructions still pointed to the deleted files at the surveyed tip (`scripts/lib/Antiphon.Scripts/ReviewEngineCommands.cs:2`, `docs/features/012-review-engine/getting-started.md:346`, `:379`, CARD-2107). Keep compatibility with real callers and explicit contracts. Any required transition bridge has an owner, removal condition and follow-up card.
7. **Enforceable architecture.** Reuse the cheapest reliable guard for a critical invariant. Prefer types and project references for actual dependencies, targeted lint and static checks for observable rules, and contract tests for behavior. The messaging packs already make public API manifest drift a build error (`src/Messaging.Pack.props:15`). Checkpoint selection detects deleted test classes and has an explicit retirement ledger (`docs/testing-and-build.md:322`). Record judgement calls in the Review checklist.

## Deletion Test

If you remove a layer, wrapper, state copy or abstraction, does its complexity disappear or move into its callers? Name the callers and the complexity that moves. Keep an abstraction that hides substantial behavior, preserves a real contract, or concentrates a rule that would otherwise spread. Include a deletion option in the plan when the evidence supports it. Prefer existing seams, concrete classes and readable code. Require current requirements and callers to justify a new interface. Preserve genuinely different behavior and move files only when ownership or dependency direction improves. Line count alone offers no evidence of reduced complexity.

## Close the batch

1. **Scan one area.** Record its base SHA, scope and exclusions. Map the module and its public edges, relevant dependency directions, state authorities and writers, duplicate implementations or technical approaches, and deviations from standards. Use `antiphon.areas.json`, existing layer maps, ADRs, call sites and relevant runtime or contract evidence. Link results from the investigation. Expand to an adjacent owner only where a dependency requires it.
2. **Choose and baseline.** Compare keeping, deleting or consolidating the affected paths where applicable. Choose the lowest overall complexity that meets today's requirements. Capture current behavior at the public seam, including affected stored data, contracts, legacy callers and important failure outcomes. Identify a guard for each standard this batch changes or relies on, or give a reason for independent review when the standard needs judgement.
3. **Migrate and remove.** Migrate every caller of the replaced implementation in the batch and remove it in the same slice after checking that it is safe. Every intermediate slice must be coherent. A transition required by an external contract remains an explicit decision with an owner and removal condition. Give Review the caller census, deletion evidence and precise scoped verification.
4. **Review, verify and record.** Check acceptance in the ordinary Review and landing sequence. Record evidence, remaining uncertainty and guard coverage. Record durable decisions as ADRs, and independent residual work as `architecture` board cards. Stop when high-value work converges, the budget expires, or the next change needs authority or evidence. Continue independent authorized work while a decision is pending.

For acceptance, show that each touched concept has an authoritative implementation and each affected module has a clear responsibility and a stable public interface. Explain any surviving parallel path and any existing dependency exception used. Show that business rules stay on their side of UI, storage, framework and external service boundaries, and that the batch keeps change local to the intended owners. Preserve behavior, stored-data compatibility and external contracts. Cite cheap checks for the critical standards the batch affects. Apply the existing [verification profile and scope](orchestration-loop.md#verification-rounds) and [test performance standards](test-performance-standards.md).

## By role

- **Plan** records evidence and options considered, the lowest-complexity choice and its reason, the owner and dependency changes, every caller to migrate, and a deletion list or a justified compatibility exception. Name acceptance and any pending decisions. Use the same checklist when verification design is folded into Plan.
- **TestDesign** identifies a narrow, reproducible behavior baseline before refactoring and a guard for each affected standard. Cite existing selectors and outcomes, use the plan's `### Checkpoints` for required execution, and give a reason for checks that need independent inspection. Reuse one precise witness where it proves several invariants. Apply the existing positive-control policy where required.
- **Code** executes the landed plan, migrates the listed callers, checks for stragglers, and deletes the replaced path in the same slice. A new abstraction ships with its caller migration. Report deletion and narrowly scoped verification evidence. Report a newly discovered breaking migration or design decision to the caller through the existing handoff.
- **Review** asks whether the diff adds a parallel implementation, shallow wrapper, leaked internals, cross-layer access, or a duplicated rule. Apply the Deletion Test to changed seams. Check caller migration, any intentional compatibility bridge and the affected behavior or guard. Use the current [round policy](orchestration-loop.md#review-rounds) and [D-2 finding policy](orchestration-loop.md#d-2-advisory-policy-card-1281). Evidence or acceptance defects follow those rules. Architectural advisories go to follow-up cards.

## Governance lane

Once a week on an ordinary orchestration tick, consider one area for a bounded evidence pass, rotating by the oldest completed scan or a repeatedly observed problem. GitHub issues, rc failures and operator requests take precedence. Use the live pipeline and runner limits, and defer if an area overlaps a higher-priority task. Admit at most one open governance Code task across the board, including queued work. Defer that Code task while native rc qualification is live on its host. Each delegate works on its own assigned branch. Existing work on another task's branch remains with that task owner. Use existing authorized dispatch, placement, review and landing. A weekly tick alone confers no scheduled spend or authority to land.

Use these brief templates in the normal worktree pipeline. The orchestrator commissions Investigate for a suspected structural problem and can begin at Plan when the mechanism is already known. Follow the parsed handoff. A survey without a defect can settle with evidence and `next: none`.

> **Investigate one area** — At `<base SHA>`, survey `<named area from antiphon.areas.json>` for `<observed symptom or owner question>` within `<agreed time budget>`. Record boundaries and public edges, dependencies and state owners, equivalent implementation candidates and departures from standards, with caller evidence and uncertainties. Save the investigation with the card and name one bounded Plan handoff when evidence supports it. Link any independent defect to its existing card or report it for the caller to file.

> **Plan one batch** — Read `<investigation path and SHA>`. Compare viable options and choose the lowest complexity that preserves the named behavior and compatibility contracts. List callers, deletions, acceptance, guards and decisions. Hand off via the existing Plan/TestDesign process. Defer decisions outside authority and name independent work the caller can commission.

The lane keeps a short index in `docs/architecture/progress.md`. A commissioned Docs delegate updates one row per settled area pass with date, base SHA, area, card, evidence link, state and next obligation. Board cards labeled `architecture` form the optimization pool. Search before filing and link duplicate findings to the existing card. Use `docs/adr/` for durable decisions with Status, Date, Context, Decisions and Consequences, following [ADR 0002](adr/0002-modern-conpty-backend.md). Use `pending confirmation` in the index for a product choice, major boundary change or breaking migration. Record the decision question on the card's move or reopen revision and attention feed under [card lifecycle policy](agent-card-lifecycle.md#card-0254-preserved-operational-detail). Hold dispatches that depend on the decision and continue independent work already within authority. Routine rounds need no additional confirmation.
