A modify/delete conflict on the index itself takes the target blob and regenerates. If the target deleted the index, `checkout` fails and the land refuses.

## Advisories (cards, not land holds)

- **A-1, plan text.** The plan's claim that "verification still runs `DerivedImpactIndexTests.committed_index_matches_the_builder` when the land builds" is wrong for unfiltered lands, which build only. A clean rebase can therefore land a stale index silently. That scope is unchanged by FT-5, but the plan should not claim the test as the backstop.
- **A-2, untested producer path.** `DerivedImpactIndexRegenerator` is not covered by any test: slot outcomes, the build, the two-run loop, stdout parsing and timeout kill. Add one witness that runs the real script in a scratch repo, plus one fake-process witness for the second-run rule.
- **A-3, activation host.** The Docker runtime image (`mcr.microsoft.com/dotnet/aspnet:9.0`) has no SDK and no pwsh. On a containerised server, every regeneration would fail closed with `index-regen-failed:nonzero`, so FT-5 would be inert. Confirm the landing host, and watch for `generated_artifact regenerated=` in the server log after activation.
- **A-4, child custody and temp.**
  - Regeneration children are not recorded as owned land children: there is no observer or ChildProcessId, unlike `LandingGit` and the verifier. A server crash mid-regen orphans them.
  - They also do not get the CARD-1981 lease `TMPDIR`, so SDK empty temp directories leak into `/tmp`.
- **A-5, conflict list on a later refusal.** When commit 2's index conflict was resolved and commit 3 then conflicts elsewhere, the refusal names only commit 3's paths. The Merge helper is told less than today's first-stop list.
- **A-6, sibling containment warning.** Commits whose index hunk was replaced or skipped get different patch ids. `ObserveContainmentAsync` (`git cherry`) then reports a regen-landed sibling branch as "committed work absent from the rebased HEAD" (warning only).
- **A-7, plan counts are stale.** CP-4 expects 40 and CP-5 expects 81; actual counts are 45 and 84.
- **Land note for this subject.** The merge with master is textually clean, but the merged index is stale: the regenerator changes `classes` 611→612 and `owed` 586→587 for the AppDbContext.cs and HostLoadModel.cs cap rows. Both sides made the same bump, so git kept one. The land rebase will be clean, FT-5 will not trigger, and the unfiltered land verifies the build only. Master will then fail `committed_index_matches_the_builder` until someone regenerates. Land, then run the regenerate script on master as a follow-up chore, or have the landing orchestrator regenerate it.
