## Blockers

### D-1: capture detection is an allow-list of five syntax positions, so other escapes stay unflagged

- **Where:** `tests/Antiphon.Tests/Scripts/ReleaseImpactProjectGraph.cs`, `CapturesReflectiveCallable` (lines 277-295).
- **What it inspects:** only `EqualsValueClause.Value`, a *simple* `AssignmentExpression.Right`, `ReturnStatement`, `ArrowExpressionClause` and `ArgumentSyntax`. `IsReflectiveMethodGroup` returns false for any `AnonymousFunctionExpressionSyntax`.
- **Failure:** the review probe compiles the base and tip graph sources side by side and runs the real `Build`. Each of these sources yields **no** `reflection-target-unresolved:tests/Consumer/Reflection.cs` and no target edge at the tip (base=False, tip=False):
  - compound `f += Assembly.Load;`
  - `f ??= Assembly.Load;`
  - `new Func<string,Assembly>[] { Assembly.Load }`
  - `new List<Func<string,Assembly>> { Assembly.Load }`
  - `Func<string,Assembly>? f = b ? Assembly.Load : null;`
  - `k switch { _ => Assembly.Load }`
  - `yield return Assembly.Load;`
  - `Func<Func<string,Assembly>> g = () => Assembly.Load;`
  - `new { F = (Func<string,Assembly>)Assembly.Load }`
- **Why it blocks:** plan D-1 names "assignments" and says "a reflective callable inside a lambda or local-function body must reach the same classification". Compound assignment and a method group returned from a lambda body are exactly those cases. The card makes this classifier a hard prerequisite for S1R6, and the brief makes near-variant false negatives a blocker. A position allow-list is fail-open by construction.
- **Fix:** make the walk position-independent. Classify every `MemberAccessExpressionSyntax`, `MemberBindingExpressionSyntax`, `IdentifierNameSyntax` and `GenericNameSyntax` that is not the `.Expression` of an `InvocationExpressionSyntax` and is not the `.Name` of an enclosing member access. Use the same rule as the invocation path (see D-2). Add independently named witnesses at least for compound assignment, the lambda-body method group, a collection/array initializer and a conditional. Each needs committed assertion-red before the fix.

### D-2: the capture path drops the invocation path's name-list fallback, so receivers that do not expand miss

- **Where:** `IsReflectiveMethodGroup`, `MemberAccessExpressionSyntax` and `MemberBindingExpressionSyntax` cases (lines 302-317). Both require `IsReflectiveType(expanded)` before calling `IsUnrecognisedReflection`.
- **Contrast:** the invocation walk at line 147 calls `IsUnrecognisedReflection(method, ...)` unconditionally, so it also flags a known load/invoke name on any receiver.
- **Failure:** each of these is unflagged at the tip:
  - `Func<System.Type, object?> f = Activator.CreateInstance;` in a file with no `using System;`. Antiphon.Tests has `<ImplicitUsings>enable</ImplicitUsings>`, so this form is realistic.
  - `Func<string, System.Type?> f = Type.GetType;` in the same kind of file.
  - `Func<string,Assembly> f = AssemblyLoadContext.Default.LoadFromAssemblyPath;`, where a dotted receiver never gets namespace expansion.
  - `var asm = typeof(X).Assembly; Func<Type[]> f = asm.GetTypes;` with only `using System;`.

  The same calls written as direct invocations are flagged today.
- **Why it blocks:** D-1 requires reusing the invocation path's receiver classification. Today the delegate-bound form of a recognised load/invoke name is weaker than the direct call, which is the class of omission this card closes.
- **Fix:** in the capture path, use `IsUnrecognisedReflection(method, 1, expanded, bareStaticReflective: HasReflectiveStaticUsing && receiver is null)` without the `IsReflectiveType` precondition, as the invocation path does. Add a witness for implicit-`System` `Activator.CreateInstance` capture and one for a `var` receiver `GetTypes` capture.
