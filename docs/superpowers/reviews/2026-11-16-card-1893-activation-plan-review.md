## Blocker: H-1 pin, Q-6 window, rc cut

Where: plan G-7, D-8, §7 steps 2 and 4–6, and Q-6. Server `HostLoadIngestService.IngestAsync` on master (`server/Infrastructure/HostLoad/HostLoadIngestService.cs:39-70`). Runner `HostLoadStoragePath.Resolve` and `HostLoadSpool` on master (`9cf3e4917`, inside `870a93d21`).

Failure: H-1 is true, and the plan's mitigation is no longer sufficient. The cursor row is created for the first history page of a runner, including a page with no samples (`:60-64`), and a later page whose `RunnerStoreId` differs throws `host_load_identity_conflict` (`:40`) on every batch. `HostLoadIngestPump` logs `Host load ingest failed` and retries (`HostLoadIngestPump.cs:83-86`). Nothing resets the row. Merge 253 is already on master. `git merge-base --is-ancestor 0f1f7bf48 origin/master` exits 1. The subject equivalent is `9cf3e4917` (`fix: harden collector paths and expose bounded diagnostics`). `rc/2026-11-24` is being cut from `870a93d21` without `SessionRunner__HostStats__HistoryPath`. The plan still says the path must ship in the same rc as Merge 253 (G-7, D-8, step 4) and does not forbid rolling that earlier rc's runner.

Why: with `HistoryPath` unset, `HostLoadCaptureService` calls `HostLoadStoragePath.Resolve` (`HostLoadCaptureService.cs:99-108`). A configured path is not set in `docker-compose.server2-runner.yml`. Resolve then uses an absolute LocalApplicationData path, otherwise `$HOME/.local/share/antiphon/host-load`. `docker/session-runner-grok/dind-entrypoint.sh:228` exports `HOME=/home/app` and the process continues as uid 1654. The image `chown`s `/home/app` to 1654 (`docker/session-runner-grok/Dockerfile:264-265`). The standing runner's durable mounts under that home are `/home/app/.nuget/packages` and `/home/app/.npm/_cacache` (`docker-compose.server2-runner.yml:114-127`). `runner-state` is mounted at `/state`, not under that fallback. The spool constructor writes `cursor.json` with `Guid.NewGuid()` before any sample (`HostLoadSpool.cs:52-62`) and `ReadHistory` returns a page carrying that store id when no samples are selected (`:154-157`). `PollOnceAsync` enqueues every non-null page (`HostLoadIngestPump.cs:43-45`). The first successful read therefore pins runner `server2` to a store that the next container recreate deletes. The following durable spool, including later S1 at `/state/host-load`, conflicts forever. Samples are not required for the pin. A desktop AppHost restart of the same rc does not open this spool; `deploy-temp` and `redeploy-old` do.

Q-6 is not a safe repair. It authorizes deleting the one `server2` row before step 6 when its `RunnerStoreId` differs from the new store. The new id is created when the new spool opens, so it cannot be compared before that open. While the runner that owns the pinned store is still serving history, the pump inserts the row again within about 5 seconds (`PollIntervalMs` default 5000). Deleting during that window does not stick.

What happens if that rc is rolled to server2 before S1: `redeploy-old` starts the standing runner from the new image with history enabled (the default) and no `HistoryPath`. The collector opens `/home/app/.local/share/antiphon/host-load` (or the LocalApplicationData equivalent under the same home) on the container layer, phone-home runner id `server2` publishes a page, and the pump inserts `HostLoadIngestCursors` for `server2`. `deploy-temp` does the same for runner id `server2-temp`, a different row, which the next temp lifecycle then conflicts. Later S1 points `server2` at `/state/host-load`, whose new store id mismatches, every ingest throws, samples after the pin are dropped, and the warning repeats. The temp override today sets only `PhoneHome__RunnerId: server2-temp`; it does not set `HistoryEnabled` false.

Fix: amend the plan before TestDesign or Code. Hold every server2 runner phase (`deploy-temp` and `redeploy-old`) of `870a93d21` and of any descendant whose runner image contains this fallback and whose applied compose leaves `HistoryPath` unset, until that compose sets `SessionRunner__HostStats__HistoryPath: /state/host-load` on the standing runner and `SessionRunner__HostStats__HistoryEnabled: "false"` on the temp runner. A hand-set variable on the live container does not survive the `compose up` those phases run, and `compose_host` passes no `--env-file`, so a `stack.env` line is not applied. The cheaper equivalent of holding the image back is `HistoryEnabled=false` in the compose that rollout applies: `HostLoadCaptureService.ExecuteAsync` returns before opening a spool (`:87`). If a `server2` cursor row already exists, delete that one row only after the runner that owns it has stopped serving history and before the pump ingests the first page of the durable spool. Keep the sample and identity rows. Do not delete on a schedule that races the 5-second pump.
