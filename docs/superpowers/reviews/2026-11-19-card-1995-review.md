## D-1 (blocker): a candidate's own build failure is recorded as a broken target and refuses unrelated lands, with no override

**Where.** `server/Application/Services/AgentTaskLandingProtocol.cs:1187-1220` (`RefuseKnownBrokenTargetAsync`), called at `:351`. `RememberFailure` at `:1171` records the projects.

**Failure.** The land build at `:356` runs in the land worktree on `op.RebasedSourceSha`, which is the candidate rebased onto the target. It does not build the target by itself. `RememberFailure` saves the failing projects of that candidate build. The refusal then looks the failure up by target SHA only:

```
.Where(row => row.Id != op.Id && row.TargetBeforeSha == op.TargetBeforeSha
    && (row.VerificationFailureStep == "build" || row.VerificationPassed || row.VerificationFailureStep == "tests"))
.OrderByDescending(row => row.UpdatedAt)
```

The query does not filter by task, repository, target ref or row age, and it does not check whether the failing row's own diff (`TargetBeforeSha..RebasedSourceSha`) touched the failing project.

A concrete case. Master is at X and compiles. Task A changes `server/Application/Foo.cs` and adds a compile error, so its land fails with `error CS... [server/Antiphon.Server.csproj]`, recorded against X. Task B then lands a change under `scripts/`, `tests/...` or `client/` onto X. B's diff does not touch `server/`, so B is refused in seconds with `target_build_broken`, and the refusal carries A's compiler output. B was never built, and its land would have passed.

The same thing happens when A's change breaks `tests/Antiphon.Tests` (a test compile error is common): every land onto X that does not edit `tests/Antiphon.Tests/` is refused. A transient build failure that names a project poisons the target the same way, because the regex also matches `MSB` errors. Examples are MSB3027/MSB3021 copy locks and MSB4166 node exits.

**What clears it.** Only a new target SHA. That happens when some other land reaches master (one that touches the named project, or a docs-only skip) or when a human pushes. Also, every refused row copies the record (`:1215-1217`), so the refusal keeps renewing itself on that SHA. A later passing build of the same target also clears it. But the only lands that still build there are ones that touch the failing project. The record does not age out. When master really is broken (the case the card means), a fix in a dependency project or in root build files (`Directory.Packages.props`, `Directory.Build.props`, `global.json`) does not count as touching the project, so it is refused too. It cannot land through the land path.

**Why it blocks.** This is the false-refusal case the brief named: a refusal that poisons unrelated lands with no override. `target_build_broken` is about the target branch, not about what was built. `Landing:ForceVerificationBuild` does not bypass it, because the refusal is called inside the non-skip branch whatever that setting says. No request flag and no setting turns it off. At 3 am the only ways out are a human push to master or editing a file under the failing project's directory. The refusal message also blames the wrong change: B's caller reads A's compiler errors as "the target is broken". The witness `C1995_KnownBrokenTargetRefusesWithoutAnotherBuild` uses a stub compiler that always fails, so it cannot tell a broken target from a broken candidate.

**Fix (any of these makes it landable; the first two together are the minimum).**
1. Record a target as known broken only when the failing build's own diff left that project, its ProjectReference closure, and the root build inputs untouched. The simplest safe form is to record only when the failing candidate's diff was empty or docs-only against the target. Otherwise refuse nothing.
2. Add an operator override that needs no code change: a `Landing:RefuseKnownBrokenTarget` setting, default off or at least switchable, and/or a per-request `-IgnoreKnownBrokenTarget`. Name it in the refusal detail.
3. Count only `CS` compiler errors, not `MSB` infrastructure errors. Treat root build inputs (`Directory.*.props/targets`, `global.json`, `nuget.config`, `*.sln*`) and referenced projects as touching every project.
4. Add a red witness: task A's own diff breaks project P on target X, then task B with a diff outside P lands onto X and must build, not be refused.

## Answers to the brief's questions

1. **Keying and clearing.** The record is keyed on `TargetBeforeSha` (the target tip before the land) plus the semicolon-joined repo-relative csproj list. There is no age, task, repository or ref key. It clears on a new target SHA (a later land or a human push both change it) or on a later passing build or `tests` failure of the same SHA. A break that was already fixed on master by another land or by a push clears correctly, because the SHA changes. The stale-row-after-fix concern is **not** a defect. The defect is D-1: the candidate's own failure poisons the same target, and there is no override.
2. **Fail-fast skipping a real verification and kept output.** No skip that loses evidence: an unreadable diff, an unreadable project, a glob include or an exception falls through to a real build (`DiffTouchesProjectsAsync` returns null). The kept output is the last 40 lines, capped at 12,000 characters (`LandVerificationFailure.StoredChars`) and stored in a `text` column. The event detail is capped at 3,500 characters, under the 4,000-character event column. The step is cut to 40 characters (varchar(40)). The project list is at most 2,000 characters, and a longer list is dropped (null), so the land builds. On secrets: the verifier runs `dotnet build --artifacts-path ... -c Debug` with default verbosity, and `dotnet run --project tests/Antiphon.Tests` only when a `-Verify` filter is given. Default MSBuild verbosity does not echo the environment. Output is whatever the repo's own targets and tests print, which is the same text an agent's own build shows. No secret is reachable through this change by default. Advisory: the `tests` step output is now persisted and served by `GET /api/agent-tasks/{id}` (`VerificationFailureOutput`). A test that prints configuration would surface there.
3. **Migration.** `20261119045705_AddLandVerificationFailure` adds three nullable columns with no default (a metadata-only change on Postgres, with no table rewrite). It also adds a non-concurrent partial index `IX_AgentTaskLandings_TargetBuildFailure (TargetBeforeSha, UpdatedAt) WHERE "VerificationFailureStep" = 'build'`, which briefly holds a SHARE lock while it scans `AgentTaskLandings` (a small table). It runs `SET LOCAL lock_timeout = '5s'`. If the lock is not taken, `Database.Migrate()` (`server/Program.cs:1148`) throws, the transaction rolls back and that start fails, and the next start retries. This matches the latest migrations: `20261114063858_AddSessionTranscriptSummaries` uses the same `lock_timeout`, and it and `20261110213738_Card1294ShadowCohort` both have a Down that throws. It is not a blocker.
4. **Red witnesses.** The red run on 1a9afb4f is the author's unlisted run, cited in the plan. I did not repeat red at 1a9afb4f, because mutation checks are waived (operator 2026-11-12). The negative cases (`C1995_LinkedCompileStillBuilds`, `C1995_MovedTargetStillBuilds`) assert `BuildPaths.Count` is 2, so removing the touch check would turn them red. None of them can catch D-1 (see above).
5. **Floor 114 and the five-segment filters.** These are count and shape corrections. No guard test file changed in the range.
