## B-3. Replacing the Linux run lock breaks mutual exclusion

- **Where** — `TryOpen` calls `PublishNewBytes` on a multiply linked `run.lock` before taking the gate. Publication unconditionally replaces the name once its same-bytes guard has passed. [Cache open](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L43) · [Publication](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L188)
- **Failure** — Two executors can hold the worktree gate concurrently even with just one pre-existing hard link and no further outside writes. Both can finish their last check against the linked file. The first can publish and lock its replacement before the second publishes and locks another replacement. A live holder is also detached if an extra link appears during its run.
- **Why** — On Linux the open handle carries the exclusive lock and still refers to its original inode after a rename. The later caller locks another inode under the same name. The per-partition seal cannot recover the worktree invariant. It is closed during invalidation and publication, and it is released after the build while later test hosts still evaluate the intermediate path. [Runtime locking](https://github.com/dotnet/runtime/blob/v9.0.0/src/libraries/System.Private.CoreLib/src/Microsoft/Win32/SafeHandles/SafeFileHandle.Unix.cs#L322) · [Linux rename](https://man7.org/linux/man-pages/man2/rename.2.html) · [Seal replacement](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L290) · [Scheduler](../../../tools/Antiphon.Checkpoints/Execution/RunScheduler.cs#L430)
- **Fix** — Keep one stable lock identity. Decline cache reuse if the existing gate cannot be verified. Add a cross-process witness that holds the first gate and verifies a contender runs cold while the gate path is multiply linked. The current competition test covers only an ordinary lock. [Existing test](../../../tests/Antiphon.Tests/Checkpoints/CheckpointWarmBuildTests.cs#L57)

## B-4. An unavailable cache can crash the checkpoint executor

- **Where** — `RefuseReplaceable` throws `unreadable-link-count` for an existing path whose metadata probe returns null, and `TryOpen` rethrows the typed exception. The scheduler also calls the throwing `Invalidate` after selecting warm build properties. [Cache admission](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L150) · [Build launch](../../../tools/Antiphon.Checkpoints/Execution/RunScheduler.cs#L508)
- **Failure** — A Windows holder with `FileShare.None` can leave the lock visible to the existence check while it denies the custody probe's `GENERIC_READ` open. The probe retries for about a second and returns unknown. The contender takes the executor crash path before the ordinary busy-gate cold fallback. A valid seal whose directory denies temporary-file creation can also pass `Prepare` and then crash during invalidation. A Windows rename sharing failure in that same phase has the same outcome.
- **Why** — At open and prepare, ordinary move I/O errors return the cold path. At invalidate, creation, replacement and reopen errors reach the executor because the scheduler catches only cancellation there. `Publish` catches those errors after an already-qualified build, which leaves the invalidation failure unhandled. The Windows custody probe deliberately uses a share-checked open and retries a known sharing violation. [Windows open semantics](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) · [Custody probe](../../../src/Antiphon.HostCleanup/Checkpoints/CheckpointNativeIo.cs#L285) · [Executor handling](../../../tools/Antiphon.Checkpoints/CheckpointApp.cs#L268)
- **Fix** — Distinguish unavailable/busy cache state from invalid path types. Complete cache invalidation before committing to the warm layout, or rebuild the entire invocation and binding for cold fallback after a refusal. Keep seal failure fail-closed for warm reuse. Add a native Windows contention witness and a scheduler witness for denied seal publication before build launch.

## B-5. A nonregular seal can reach the production open and crash

- **Where** — `Prepare` now checks for null stat and real directories. A successful stat of a FIFO is neither. `IsSharedInode` recognizes regular files only and the FIFO proceeds to `OpenGate`. [Seal open](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L99) · [Gate open](../../../src/Antiphon.HostCleanup/Checkpoints/SafeWrite.cs#L403)
- **Failure** — A pre-existing Linux FIFO was previously declined by the regular-file guard. The current read/write open can succeed and `FileStream.Length` throws `NotSupportedException` for the unseekable handle. The exception escapes `Prepare` and fails the executor. The regular-file check excludes a stable FIFO from `PreserveSeal`. A path type change between stat and `File.ReadAllBytes` is still unbounded because the read reopens by name. [Linux FIFO open semantics](https://man7.org/linux/man-pages/man7/fifo.7.html) · [.NET stream length](https://github.com/dotnet/runtime/blob/v9.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileStream.cs#L410)
- **Why** — The preflight checks link components and Git confinement. The cache no longer requires a regular seal before opening it, and its pathname-based equality and preserve reads do not verify the opened handle or enforce the byte limit on the read itself.
- **Fix** — Reject nonregular seal and gate entries before opening and bind checks to a nonblocking, no-follow handle. Read at most the expected bytes from the verified handle. Losing the seal can simply force a cold build. Add a bounded native FIFO witness that asserts the production outcome. [Existing bounded reader](../../../src/Antiphon.HostCleanup/Checkpoints/CheckpointFileReader.cs#L80)

## Other custody checks

The props, replacement lock and seal payload writes target exclusively created, GUID-named temporary files. `OpenCreate` uses `FileMode.CreateNew` without retrying as an overwrite. `File.Move` publishes the directory entry. `OpenGate` still requests read/write access to existing entries, and the reviewed cache class no longer truncates or writes payloads through those handles. `CreateFreshDirectory` continues to create the partition and then its ownership marker. The partition digest uses the bounded reader, which rejects nonregular entries and multiple links.

The two new assertions exercise production cache open and verify outside-sentinel bytes, mtime, and link identity or refusal. The author reported both pre-fix reds at `4d49529ed402b36d95ac76dec329aade5b31e0cd` and 3/3 at `d96a1a11e3197b26fcf3956f3fefd314d2dc9bea`. That verifies the original props write regression. It supplies no outcome assertion for the three new failure paths above. The author also reported 50.80 s for the same-output repeat, with zero of 48 compile cache timestamps changed. No new timing pair was commissioned.

Existing same-account cache directories pass the directory owner comparison across runs. The Linux side compares the effective UID against the filesystem UID. Windows compares matching 32-bit hashes of the token user SID and the handle owner SID, and refuses unobservable or mismatching ownership. That is a SID-derived comparison, with native Windows execution still pending.
