## Fail-safe

`DispatchEligible` is set in two places, both in `PhoneHomeRunnerDirectory`: `MarkRecovered` and `TryRecoverLease`. The pump calls them only after `CatchUpAsync` returns true. `CatchUpAsync` returns true only after `ReadInventoryAsync` has returned in that attempt (the List completed, `LastListAt` was published, and the inventory replace ran). A List that throws or whose step budget, whole budget, or watchdog token cancels before that return logs and returns false. `RunOneAsync` then sets `NextCatchUp` and returns false, so neither setter runs.

Lease re-recovery (`listOnly`) takes the same List gate, then `TryRecoverLease`. A refusal after the List (`replaced`, `epoch_changed`, `disabled`, `socket_closed`, `lease_expired`, `disconnected`, `pending_events`, `draining`, `retired`) is logged and returns false. Expiry during that catch-up therefore does not publish eligibility. Both setters no-op unless `ReferenceEquals(slot.Live, connection)`, so an attempt on a replaced connection cannot flip the new epoch.

A late reply cannot call either setter. `BoundedAsync` abandons the inner task and throws; the setter sits after that await. The abandoned `ListAsync` can still reach `ReplaceKnownLiveSessions`. A stamp older than the entry does not overwrite or remove it. A late stale List can add a session the newer List omitted. That occupies a seat. It does not set eligibility.

A session step that expires is skipped, logged (L2), and counted unverified. The loop does not remove it from the inventory, so the seat stays occupied. Whole-budget or watchdog cancellation after the List has completed logs L3, skips the remainder, and returns true. Eligibility then rests on that completed List, which is D-3.

`ApplyRestartIfRequested` clears `RestartRequested`, stamps `LastRestartAt`, clears `NextCatchUp`, and detaches an incomplete refresh. It does not write eligibility, the socket, or the observers. The replacement attempt starts in the same `RunOneAsync` turn.

## Gate residual

`BoundedAsync` is `Task.WaitAsync`. When the token cancels and the inner task is still running, the pump regains control and `Abandon` observes a later fault. The inner task keeps running.

`SessionStateStore.AcquireAsync` waits on `entry.Gate.WaitAsync(ct)`. Cancel during that wait returns the entry with `releaseGate: false`, so the waiter never holds the gate. After acquire, `PersistTranscriptAsync` on cancellation calls `lease.ReconcileAsync(false, CancellationToken.None)` and holds the gate until that reload returns. `Lease.Dispose` then releases it. A later attempt waiting on the same gate completes when its own step token cancels and does not take the gate, so holders do not stack. The bound is one lingering reconcile per session that got past acquire.

Lease re-recovery is List-only, so it does not enter persist. After a connect catch-up whose List completed, `CatchUpAsync` returns true even when later sessions time out, `MarkRecovered` runs, and later cycles refresh the List only. They do not re-enter persist. A permanently stuck reconcile is the residual the plan assigns to E-4. This slice does not edit `SessionStateStore` or `AgentSessionRuntime`. It does not grow one abandoned persist per pump cycle.

## Watchdog

Ten fields under `WatchLock`: `FirstSeenAt`, `LastListAt`, `LastRestartAt`, `FiredWindowStart`, `RestartRequested`, `AttemptId`, `AttemptStartedAt`, `AttemptStep`, `AttemptCts`, `OverrunFiredAttemptId`. The refusal streak shares that lock.

`WatchdogLoopAsync` starts only when `RecoveryWatchdogIntervals > 0` and `RecoveryWatchdogPollSeconds > 0`. `RunWatchdogOnce` returns immediately when intervals are `<= 0`. Poll seconds `<= 0` leave the loop stopped and the pump running. Off is intervals `<= 0`. Skip is no live socket, or an eligible runner with refresh off and no attempt in flight. Pending is `RestartRequested`: the poll does nothing. Watching is every other open socket.

`WindowStart` is the latest of first sight, last completed List, and last applied restart. `no_list` requires the window fully elapsed, `FiredWindowStart` different from that window, and no List already completed in the in-flight attempt (`LastListAt >= AttemptStartedAt`). `attempt_overrun` is once per `AttemptId` when elapsed exceeds `OverrunLimitSeconds`.

A1 is in the plan and the code. `OverrunLimitSeconds` is `CatchUpBound + ListBound`. The stand-in sum of 360 holds when both budgets are off (300 and the 60-second List request timeout). A small positive budget can make the overrun shorter than 135 seconds while it stays strictly above the List bound, so P-1 holds. A2: `ReadInventoryAsync` writes `LastListAt` under `WatchLock` before it returns, and the poll holds that lock across the fire decision and the cancel. A3: the refresh catch filters on the stopping token, so a budget cancel is logged as `refresh_list_budget`.

Defaults for a large inventory: List 90 seconds (the 60-second reply timer fires first on a silent reply), per session 30 seconds, whole catch-up 300 seconds. The window is `max(6 * 30, 90 + 5 + 10 + 30) = 180` seconds. The overrun is 390 seconds. Once the List in the attempt has completed, `no_list` is suppressed for that attempt. The 300-second budget ends the attempt before the overrun, skips the remainder, and eligibility follows the completed List. A catch-up that is still finishing sessions is not cancelled and restarted on every window. A List that never completes gets one L6 and one restart per window (about 180 seconds), and the runner stays ineligible. With the whole-catch-up bound off, the 300-second stand-in still makes the overrun 390 seconds and the cancel is treated as budget exhaustion after a completed List.

Two polls serialize on `WatchLock`. The second sees `RestartRequested` and leaves the runner alone. A poll that overlaps List completion either observes `LastListAt` and does not fire `no_list`, or cancels an attempt whose List has not yet published. A detached refresh can overlap the replacement refresh. Both are inventory writes under the stamp rules. Neither sets eligibility.
