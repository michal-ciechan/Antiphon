## B-4 remains open. A seal write failure can escape on disposal

- **Where** — `CheckpointNativeIo.Open` creates a buffered `FileStream`. `Entry.Publish` catches the failure from `Replace`. The scheduler's `using var intermediate` then calls `Entry.Dispose` outside that catch. [Native open](../../../src/Antiphon.HostCleanup/Checkpoints/CheckpointNativeIo.cs#L88) · [Publish and dispose](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L365) · [Scheduler](../../../tools/Antiphon.Checkpoints/Execution/RunScheduler.cs#L442)
- **Failure** — A persistent write error during seal publication, such as a quota failure, can still fail the executor after the owned build receipt has already been written. This path was introduced by `4fe0e42416d5b7c6903335c5f12ce3df0805d87e` when publication moved to the retained stream.
- **Why** — The 32-byte seal is buffered. If the underlying write fails during `Flush(true)`, .NET keeps the pending bytes. Explicit `Dispose()` tries to flush them again and propagates the second I/O failure. The scheduler awaits its build task and the exception reaches the executor's terminal crash handler. The cold-directory witness supplies a null cache to a fake scheduler. The FIFO witness stops at `Prepare`. Publication failure has no witness. [Buffered flush](https://github.com/dotnet/runtime/blob/v9.0.20/src/libraries/System.Private.CoreLib/src/System/IO/Strategies/BufferedFileStreamStrategy.cs#L688-L711) · [Explicit disposal](https://github.com/dotnet/runtime/blob/v9.0.20/src/libraries/System.Private.CoreLib/src/System/IO/Strategies/BufferedFileStreamStrategy.cs#L107-L130) · [Terminal handling](../../../tools/Antiphon.Checkpoints/CheckpointApp.cs#L79)
- **Fix** — Own and contain write and close failures at the cache boundary. Use unbuffered seal writes or contain disposal of the buffered stream, and prove that an injected persistent seal write failure still executes the row from the verified owned output. Assert that the next run refuses the failed publication and that the exclusive handle was released.

## B-6. A refused build discards a valid cache before any SDK work

- **Where** — The same `4fe0e42416d5b7c6903335c5f12ce3df0805d87e` commit moved `Invalidate()` ahead of ledger capture, broker acquisition, source and output preflight, and the final launch check. [Prepare and invalidation](../../../tools/Antiphon.Checkpoints/Execution/RunScheduler.cs#L427) · [Slot acquisition](../../../tools/Antiphon.Checkpoints/Execution/RunScheduler.cs#L471)
- **Failure** — A slot timeout or cancellation while waiting for admission makes every later run of that same partition build cold until a reset. It can happen without a build or any change to the cached intermediates.
- **Why** — The routine refused run truncates the matching 32-byte seal and leaves the existing partition directory. The next `Prepare` declines that directory on the empty seal. The cold build does not have a cache entry to republish, so a successful retry cannot recover persistence. In the previously reviewed tree the invalidation was after those admission gates, immediately before the driver launch. [Existing-partition admission](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L164) · [Seal match](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L330)
- **Fix** — Keep an already-valid seal through all refusals before build launch. If last-moment invalidation fails, switch to a freshly captured cold build layout before launch. Add a scheduler test with a valid entry, a refused slot, and a subsequent admitted run that proves unchanged seal bytes and successful reuse.

## Lock, FIFO and fallback audit

- **B-3, lock identity.** `run.lock` is created exclusively only when absent. Cooperating executors never rename or replace it. The path examination rejects a known multiply linked or nonregular entry. If a hard link races that check, the second opener can only request exclusion on that same inode. If the holder is live, sharing rejects it. There is a brief exclusive-open-before-fstat interval when no holder remains, but the handle's regular/type/link-count/owner check precedes props writes and partition use. The test-only `99d1a91865ab3918402920783ed39aefe8972eca` change records the alias/open-path identity after the holder closes, while the contender's refusal is asserted inside the hold. Production has no unlocked identity handoff. [Lock open](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L44) · [Windows and Linux handle checks](../../../src/Antiphon.HostCleanup/Checkpoints/CheckpointNativeIo.cs#L854) · [Test hold and observation](../../../tests/Antiphon.Tests/Checkpoints/CheckpointWarmBuildTests.cs#L199)
- **B-5, FIFO admission.** The Linux path stat refuses a pre-existing FIFO before the ordinary file open. The open has no nonblocking flag or independent deadline. It uses read/write, which Linux permits on a FIFO without a peer, then rejects the opened FIFO by type before reading `Length`. This gives no race-proof path guarantee against a hostile same-account writer. The checkpoint custody contract scopes that attacker out. [Trusted-path check](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L196) · [Open mode](../../../tools/Antiphon.Checkpoints/Execution/CheckpointIntermediateCache.cs#L231) · [Checkpoint custody trust boundary](../../testing-and-build.md#checkpoint-runner-tool-card-0723)
- **I/O and cold layout.** `TryOpen` covers directory setup, lock stat/open, handle validation and props publication. `Prepare` covers seal stat/open, membership digest and directory creation, and the scheduler catches those exceptions plus invalidation. `PathTooLongException` and `DirectoryNotFoundException` derive from `IOException`. Props replacement denied by Windows sharing similarly falls back through I/O/access handling. Argument, unsupported-operation and invalid-state exceptions are outside these filters. Validated build inputs and the real regular-file check cover ordinary path and seek operations. The Windows opened-handle owner lookup separately turns `InvalidOperationException` into a refusal. Temporary props cleanup catches expected deletion errors, the worktree gate only closes a read/write handle with no buffered writes, and the seal-close path is B-4 above. For a rejected cache, `AppendSharedLayout` omits the cache import and sets the owned artifacts layout. The normal binding and build receipt still apply. When the seal has been truncated, a crash, failed attempt or stale digest leaves the partition untrusted. B-6 is the case where invalidation happens before any build can mutate the partition. [Cold layout](../../../tools/Antiphon.Checkpoints/Execution/BuildStep.cs#L36) · [Windows stat and sharing](../../../src/Antiphon.HostCleanup/Checkpoints/CheckpointNativeIo.cs#L285)
- **Witnesses.** The author's red-first report at `ecd187147e30518618d6e68f3c2ea8e494e97fb7` records three outcome failures (linked lock accepted, lock directory raised a typed refusal, FIFO seal raised `NotSupportedException`). The two-entry lock test checks refusal, inode, link count and an outside sentinel. The FIFO witness reaches the real Linux cache factory and checks both outcome and exception. The new lock-directory scheduler witness checks cold argument routing and a green simulated row. Native Windows contention and invalidation/publication failure are still owed through the real platform and production path. PCs remain pending.
