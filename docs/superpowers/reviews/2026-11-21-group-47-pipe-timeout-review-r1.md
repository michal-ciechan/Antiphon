## Blocking findings

### 1. A successful push can settle as LandRefused

- **Where** — `server/Infrastructure/Git/LandingGit.cs:368–437`, `server/Application/Services/AgentTaskLandingProtocol.cs:405–426,1030–1047`, and `server/Application/Services/AgentTaskLandService.cs:1442–1463`.
- **Failure** — A push can update the remote ref, exit zero and leave an inherited stderr handle open. The new exception discards the observed exit before `OwnedAsync` clears the child registration and before the protocol records the exit or checks remote containment. The hosted worker catches the exception and settles a durable `LandRefused` with generic `landing_timeout` classification. The remote already contains the verified SHA. A holder that closes just after the drain deadline makes this a regression even when it would have closed on its own.
- **Why** — `PushStarted` records intent, and publication is confirmed only by observing the target. The exception skips this observation and terminal settlement clears the pending request. The sweep can retry a failure to persist settlement, but a committed refusal leaves no pending request. A fresh permitted resume checks the recorded target before it considers re-pushing, so this path does not show an unconditional duplicate push. A completed rebase with a held pipe likewise escapes before the `Prepared` checkpoint and is later classified as interrupted.
- **Fix** — Preserve the observed exit separately from the drain verdict and handle post-exit mutation outcomes explicitly. For push, confirm the exact destination and verified SHA before terminal settlement and preserve a resumable outcome when the observation itself is unavailable. Add a regression through the real landing protocol with an actual successful local push and inherited pipe, and assert the durable request, publication and notification outcomes across the failure boundary.

### 2. A deadline race can change git_pipe_timeout into git_timeout

- **Where** — `server/Infrastructure/Git/LandingGit.cs:375–422`.
- **Failure** — The wait can already have timed out when both stream tasks complete. The exception filter then rejects that timeout because the two tasks are now complete. The generic catch can replace it with `git_timeout` once the run budget has elapsed. With a still-live run budget, the caller can instead see the unclassified framework timeout.
- **Why** — Current task state in the exception filter does not identify which event completed the timed wait. The existing hung and finite cases exercise the two ends of the timing range and cannot drive this interleaving.
- **Fix** — Separate pipe-deadline expiry from faults in the read tasks and decide from the timed wait itself. Add a deterministic boundary case with the run budget expired and EOF arriving at the drain deadline.

### 3. The Linux-only witness is absent from the Windows rc exclusion

- **Where** — `tests/Antiphon.Tests/Infrastructure/LandingGitTests.cs:924` and `tests/test-execution-policy.json:1505`.
- **Failure** — `HungPipeHolderFailsWithGitPipeTimeout` carries `NativeLinuxOnly` and skips on Windows. The shipped `LandingGitTests` exclusion roster omits it. The marker and exclusion sets must agree for Windows rc coverage.
- **Why** — A runtime skip cannot supply a policy-owned exclusion. The candidate adds the marker and leaves the matching exclusion row unchanged.
- **Fix** — Update the exact method roster and applicable policy pins. Run the A5 pair against the candidate and keep the native Windows job and pipe acceptance separate from the Linux-only witness.

## Pipe custody, output and test cost

The read tasks start before the root exit wait. A large output from the root normally drains while Git is running, since the pipe buffer is finite and the root must complete its writes before it can exit. There is no universal guarantee that decoding, scheduling or late writes by a legitimate inherited writer finish within 30 seconds. On the timeout branch the caller receives no partial stdout or stderr. This keeps a prefix from being accepted as a complete ref or tree listing. It also makes the captured command exit material for mutation callers.

There is one read per stream. Both paths use the original tasks and the same bounded cleanup. A completed drain releases the journal synchronously. When the stream tasks are handed off, the continuation retains the process, waits for completion, removes the journal with root-exit proof and disposes the process. The Windows job handle is disposed by its own scope. The earlier stranger-holder exception is preserved when the ownership probe proves the pipe unowned. For an escaped holder that truly never closes, the read tasks, process and conservative fence remain pending for that lifetime. The production Windows path tries job termination, whose post-start assignment is best effort. The caller returns within the cleanup bound. An unknown holder controls the remaining stream lifetime. The new timeout witness asserts the exception and return time. The paired CARD-1076 tests assert journal retention and release on the budget-kill and finite post-exit paths. The timeout path needs its own retention-then-EOF assertion and native Windows receipt.

The new fixture uses a real POSIX double fork through a substitute executable selected for the push command. The orphaned `sleep 300` inherits the redirected writer. The method limit is 45 seconds for the 30-second drain plus cleanup, and the TUnit timeout is 90 seconds including setup. Under load the two-second root budget also covers journal startup and fixture process scheduling. The fixture waits up to about five seconds for the holder PID, so a sufficiently delayed start can report the root budget instead. The 30-second setting has no measured Windows headroom here. The 8-second finite witness is the only exercised legitimate holder. The new witness is Integration, so build-only verification or a short Unit selection does not include it. A whole-class filter does include its roughly 32-second cost. The existing cost entry predates the witness, and the plan omits a Performance budget. Track these measurements as provisional. An injectable drain duration would make the semantic witness much cheaper while a narrow native test can independently verify the production bound.

The Windows group-47 diagnosis comes from the task's reported capture. Native Windows reproduction and the impacted `/*/*/(RepositoryLeaseWindowsBoundaryTests*)/*` row stay pending. The Linux evidence reaches the real .NET pipe reader and Linux ownership probe. Windows job assignment, membership and termination need their own evidence.

## Durable outcome delivery

The failure path writes the terminal event and outcome notification with the request completion in the same transaction. The hosted scanner recovers the durable note and uses the parent session plus notification ID and content digest. The queue uses `WhenIdle`, so a busy recipient keeps the row pending while an eligible recipient flushes it. A held queue lock leaves the scanner's row untouched and an enqueue error retains retry state. A committed insert followed by a crash or lost acknowledgement is relinked by the notification ID, verifying the destination and digest before reuse. The reconciler pulls the recipient transcript and requires full text above the delivery floor. For this Review, acceptance requires a matching complete `UserPrompt` in the intended session. A queued row, Sent state or transport acknowledgement alone cannot establish receipt.

CP-1 exercises the pipe path through a push stand-in. The resettlement class exercises the incident caller. The successful push with a held pipe still needs a producer-to-recipient test. The caller regression should assert the correct terminal result reaches an eligible recipient after a busy turn and survives the commit/enqueue boundary with one keyed queue row and the matching full transcript prompt.
