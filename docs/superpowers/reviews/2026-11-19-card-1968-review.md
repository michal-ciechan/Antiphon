## Judgements requested by the brief

1. **The 8 GiB cap cannot OOM server2.** The host has 125 GiB RAM and no swap. The runner container's memory cgroup is unlimited (`memory.limit_in_bytes = 9223372036854771712`). The build-slot broker allows `budget=4` concurrent leases, `maxCpuCount=6`, and admits a lease only above 16384 MB available. The policy pipe identity is SDK content, uid, cgroup, mount namespace, idle setting and CPU set. So inside one runner container, every build with the same grant shares one server, and the wrapper's default grant is 6. The worst case is four concurrent compiles on four distinct identities. Their managed heaps sum to at most 4 × 8 GiB = 32 GiB. Servers that are idle but still inside their 120 s timeout could add up to two more grant windows at the default grants, about 48 GiB of managed heap, or roughly 54 GiB RSS including native overhead. That is under half of host RAM. The old cap allowed 24 GiB, so the new cap adds at most 24 GiB. The realistic need is about 5.8 GB per server, about 24 GB for four. The stock compiler (policy off, today's default) has no cap at all, so no policy server can use more managed heap than a stock server would. Not a blocker.
