## Finding

The card's hypothesis holds for the first failure and not for the whole row. With the Linux guard
lifted (S1), both Grok-on-Herdr rows of
`Standing_history_recovery_preserves_native_identity_and_queued_reply` timed out at the first
delivery (`FakeHerdrServer never saw pane.send_text`), the same unready-screen cause CARD-1252
fixed. With the captured Grok 1.0.41 dashboard (S2) both rows passed launch, first delivery and
the second clean start, then failed the queued-reply assertion, as the Claude-on-Herdr rows do.
The S2b diagnostic message shows why: the queued channel row is stored as
`[antiphon-channel:<id>] <nonce>` (`ChannelPromptCorrelation.Mark`), the Herdr fixture
(`ConfirmHerdrDeliveryAsync`) inserts that stored body as the UserPrompt, and the assertion
compares `Text == nonce`. That mismatch is not Grok-specific and not Linux-specific in the code
read here; Windows was not run (disclosure). Choosing whether the assertion, the fixture or the
product owns it is outside this card, so the Herdr rows keep a Linux guard naming that reason.
