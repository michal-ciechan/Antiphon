# CARD-0151 plan: card effort estimates (days) and an effort ledger over the existing revision trail

Card: CARD-0151 (Antiphon board, Backlog, never planned before). Plan task 8bc47225, 2026-10-22.
Base: `origin/master` at `1ba4ac9ff`. Master-only (see [RC](#rc)).

## Outcome in one paragraph

The card asks for two new mechanisms: an estimate field, and a stage-transition audit trail. **Half
of that already exists.** Every column transition has written a timestamped `CardRevision`
(`Kind = Move`, or `Reopen`) with from/to column and status since CARD-0019 (migration
`20260814152152_AddCardRevisionsAndArchive`). Every writer of `Card.BoardColumnId` appends one first,
and there are five such writers. Every content edit snapshots the values it supersedes. The
per-stage "which `AgentTaskRole` worked this card, when, and what it handed to" record is
`AgentTask` (`CardId`, `Role`, `CreatedAt`, `CompletedAt`, `NextStage`), as CARD-0146 says. So this
plan builds **no new audit table**. It adds one nullable `EstimateDays` column to `Card`, plus the
same column on `CardRevision`. Because `AppendContentEdit` snapshots superseded values, the second
column is all it takes to keep estimate history. It then adds one read route that turns
`CardRevision` rows into a flat **effort ledger**, and a `card.ps1 effort` verb that buckets the
ledger and groups it. Recommendation: build S1–S3 (about 2.5 h), and drop the UI slice and the
per-stage effort attribution.

## Decisions

- **D-1 No new stage-transition table.** G-1/G-3: `Move`/`Reopen` revisions are the audit trail, and
  adding a table would duplicate them. Rejected: a `CardStageTransition` table. It would need dual
  writes at five call sites and a backfill from revisions, and the history would then read from two
  places.
- **D-2 Estimate = `numeric(6,2) EstimateDays` nullable on `Card`, plus the same column on
  `CardRevision`.** Valid range: > 0 and ≤ 365, at most 2 decimal places. A value outside that is a
  `ValidationException` (422). Null means "not estimated". Revisable through `PATCH
  /api/cards/{id}/content` (`estimateDays`, `clearEstimate`; both together is 422), and settable at
  create (`CreateCardRequest.EstimateDays`). `CardRevisionLog.AppendContentEdit` snapshots
  `card.EstimateDays`. ContentEdit rows written before the migration read null, which is accurate:
  no estimate existed then. Rejected: a separate `CardEstimate` history table. `AppendContentEdit`
  already snapshots every edit, so a second history would be redundant.
- **D-3 One point value, not a band.** The minute convention (G-9) is a band because it drives
  stall detection for one dispatch. Card days exist to be summed, and sums of bands add little
  and nobody fills two fields. The CLI help says "days of effort, your best single figure". The
  point value is still *revisable*, and a revision is a recorded event in the ledger, so
  re-estimation is visible rather than hidden. Rejected: `EstimateLowDays`/`EstimateHighDays`.
- **D-4 The ledger is computed on read, not stored.** `GET
  /api/boards/{id}/effort?since=&until=` returns flat events plus the outstanding total now. A pure
  `CardEffortLedger.Project(...)` builds them from the card rows and a projected revision list. The
  projection reads only Id, CardId, RevisionNumber, Kind, statuses, EstimateDays and CreatedAt,
  **never Description**. Rejected: a materialized ledger table. It would be a third copy of the
  facts, and it would go stale whenever a projection rule changes.
- **D-5 No new index.** The route filters `Cards.BoardId`, then joins revisions on `CardId` through
  the existing unique index. The projection needs each card's full history before `since` anyway,
  to know the estimate in effect. That rules out a `(Kind, CreatedAt)` index, which would serve
  only a window scan. Code records the route's wall time on the live board in the S2 report.
  Above 2 s is a follow-up card, not a scope change.
- **D-6 Per-stage effort attribution is dropped.** Days are a card-level number. Splitting them
  across Plan/Code/Review would need an invented ratio. Task durations per `Role` already come from
  `AgentTask` with no schema change. Answering "how long in each stage" is a separate small card,
  if anyone wants it.
- **D-7 No backfill.** Existing cards keep `EstimateDays = null` and contribute nothing. The
  ledger is complete for every estimate set after S1 ships. The move history it needs has existed
  since 2026-08-14, and no estimate can predate S1. Effort throughput before S1 is unmeasured, and
  the `effort` verb prints that as a footer whenever `since` precedes the first estimate on the
  board.
- **D-8 Bucketing and grouping run in the script, not the server.** The server returns raw events
  carrying labels, current status and current column, so any consumer can group any way it likes.
  `card.ps1 effort` buckets by UTC `day|week|month` (ISO week, starting Monday) and groups by
  `none|label|status|column`. A card with several labels counts once per label in `-GroupBy label`,
  and the output says so. Rejected: server-side `bucket`/`groupBy` parameters. They would freeze
  the grouping choices into the API before anyone has used them.
- **D-9 UI dropped from this card.** It is not required by the card. Because of G-7 the client
  sees no change. A board badge or edit field is a follow-up card filed at close if wanted.

### Ledger rules (S2)

The estimate in effect at instant *t* is the `EstimateDays` snapshot on the first ContentEdit with
`CreatedAt > t`, or the current card value if there is none. Revisions are ordered by
`RevisionNumber`. A card is **live** when its status is not Done/Canceled and it is not archived.
Its status at *t* is the first Move/Reopen with `CreatedAt > t`'s `FromStatus`, else the current
status. Archived state at *t* comes from the Archive/Unarchive rows. Each event carries `cardId`,
`identifier`, `labels` (current), `status`/`columnId` (current), `at`, `kind`, `estimateDays`
(the value in effect after the event) and `deltaDays`, the signed change to outstanding:

| kind | when | deltaDays |
|---|---|---|
| `estimated` | the estimate goes null → x, at create or on a ContentEdit | +x if live, else 0 |
| `revised` | x → y | y − x if live, else 0 |
| `cleared` | x → null | −x if live, else 0 |
| `completed` | Move/Reopen into Done from a non-Done status | −x (`x` = the estimate then) |
| `canceled` | into Canceled from a live status | −x |
| `reopened` | from Done/Canceled to a live status | +x |
| `archived` / `unarchived` | while not terminal | −x / +x |

Only estimated cards emit events. Same-status moves emit nothing (G-8). Done ↔ Canceled emits
nothing. **Outstanding at any instant = the running sum of `deltaDays`**, so a burndown is a
cumulative sum over the events. "Added" = the sum of `estimated` plus positive `revised`; the
script also shows net revision separately. "Completed" = the sum of x over `completed`, minus x over
`reopened`-from-Done. The route returns `outstandingDays` as the sum of current estimates over live
cards. That is the invariant against which the running sum is checked.

- Migration: additive only. `AddCardEstimateDays` adds two nullable `numeric(6,2)` columns

  stamped after the latest on origin/master, `20261022110953_AddPoolProviderProjection`. Generate it
  with `dotnet ef migrations add` through build-slot, and diff the snapshot so it contains only
  these two columns.
- Red witnesses: new class `tests/Antiphon.Tests/Application/CardEstimateTests.cs`, an integration
  test on the CardCorrectionIntegrationTests fixture pattern:
  - `Create_with_estimate_round_trips_and_omits_the_field_when_unset`: covers create with 1.5, the
    GET shows 1.5, and a card with no estimate has no `estimateDays` key in the JSON.
  - `An_estimate_edit_snapshots_the_superseded_value`: edits 1.5 → 3. The revision carries 1.5 and
    the card 3. A title-only edit after that leaves the estimate unchanged.
  - `Clear_estimate_sets_null_and_snapshots_the_old_value`
  - `Estimate_out_of_range_or_with_clear_is_a_validation_error_and_writes_nothing`: uses
    `[Arguments]` 0, −1, 365.01, 1.005, and a value + clear together. Each is 422, the revision
    count is unchanged and the token is unchanged.
- Risk: low. The only wire risk is G-7, handled by `WhenWritingNull`. Tracker-created cards never
  set the field.
