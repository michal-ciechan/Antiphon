# CARD-0885: one-host repeat proof and bounded repeat work

Date: 2026-10-01. Stage: Plan complete; TestDesign follows. Baseline: `origin/master` at **`4cdd8809b85ed479a8a2b3d43f80e3cd7577bf6e`**. The assigned branch, `feat/card-task-6d82654c`, starts at that same commit and is not rebased. Only this Markdown artifact changes in Plan.

## Outcome and scope

Add `scripts/run-checkpoint.ps1 -Repeat N` and checkpoint-tool `--repeat N`: **N total executions of each selected case, inside one TUnit test-host invocation**. Default N=1 preserves today's execution. Repeated runs retain one complete TRX, per-repetition results, source/build qualification, host-slot custody and phase timings. Codify a maximum of three normal and two loaded proof repetitions unless an existing Review has demonstrated a flake; these are ceilings, not mandatory runs.

Use the repository's pinned TUnit 1.44.0 native repeat generation, selected through a generated assembly attribute in isolated build output. This requires a build for a different repeat count; it does not require a new test process for each repetition. Repetitions are logical sets of independently reported test cases, not a promise that the entire filter executes in chronological rounds. They retain TUnit's hooks, argument expansion, parallel limiters and failure reporting.

Preserve CARD-0835's clean-source certificate, boundary observations, dirty diagnostics, build-source stamp and both strict validators. Do not change land approval, EF models, source resolution, cleanup ownership, real providers or live configuration. No new retry-on-pass/failure loop and no process-start equivalence claim: one-host repetition cannot qualify behavior that specifically requires a fresh process per trial.

## Design decisions

### D-1: compile native repetitions, keep one ordinary TUnit invocation

`-Repeat N` / `--repeat N` means total repetitions, including index 0. Require an integer >=1 and checked arithmetic for `N * MinExecuted`; reject invalid/overflowing inputs before requesting a slot or launching a driver. N=1 follows the existing path. For N>1, pass reserved MSBuild properties `AntiphonCheckpointRepeat=N` and `AntiphonCheckpointRepeatProject=<canonical selected csproj>` to both build and run. Resolve a project directory to exactly one csproj; ambiguity is invalid input.

Import a small `tests/Shared/CheckpointRepeat.targets` from `Directory.Build.targets`. Only the exact selected test project with a TUnit package reference is eligible. Generate `[assembly: TUnit.Core.Repeat(N-1)]` and the evidence receiver attachment under that project's ignored intermediate output, and explicitly include the generated file plus the shared receiver source before compilation/source generation. Do not edit checked-in test methods. Referenced projects must not inherit expansion merely because MSBuild forwards global properties. No environment-driven multiplier and no TUnit package upgrade.

The receiver rejects conflicting method/class/assembly Repeat annotations on selected cases instead of silently overriding/multiplying them. Unknown/custom native ID shapes, dynamic cases lacking the supported identity contract, or unsupported projects cannot yield a successful repeat certificate. Preserve ordinary N=1 support for those projects. TUnit still constructs separate test instances and invokes its own hooks; do not call test methods directly. Existing `ParallelLimiter<ProcessSpawnLimit>` continues to apply to process-spawning cases. No global parallelism increase is introduced. Repeated cases may interleave; per-repetition sets are grouped by native ordinal, not inferred chronological windows.

Rejected: a shell loop (N startups); `[Retry]` or `--known-flaky` (conditional retries can hide an earlier failure); a loop in a custom test executor (body-only repetition changes fixture and result semantics); subclassing RepeatAttribute (sealed); pretending a runtime `--repeat` flag exists in 1.44; reflection mutation of init-only engine metadata; upgrading TUnit to solve this card; generating permanent attributes in tracked source (dirty-tree violation).

### D-2: bind repetition to the existing build and manifest contracts

Expose `repeat` on a YAML checkpoint row and optional Markdown `Repeat` column, default 1. Add `--repeat N` to tool `run`, `start`, and `row`; an explicit CLI value overrides the selected rows and is persisted in the resolved manifest/request before hashing and detachment. `wait`, resume/report and rerun selection must not reread mutable process environment for that value. Command rows reject N>1. A command-only selection with `--repeat >1` refuses; mixed selections do not silently ignore it.

Rows sharing a build/output must resolve to the same repeat count. Reject conflicting reuse with an actionable request for a distinct isolated output; do not silently rebuild a shared output under running rows. Include both reserved properties in `CheckpointBuildBinding`'s existing sorted property binding, without changing the source fingerprint algorithm or stamp version. In N>1 mode even diagnostic `-NoBuild` requires a matching repeat-capable stamp: otherwise an ordinary binary can masquerade as a repeated one. N=1 retains today's diagnostic/strict behavior and property list. Reserve these names against user `-MsBuildProperty` overrides, including semicolon property injection. Source-generation outputs stay ignored; a tracked file under an output directory still counts as dirty exactly as CARD-0835 requires.

This plan's own table uses only the baseline nine required columns plus existing optional columns, so S1 can be run by the baseline importer. **CP-7 is the one explicit row override, `--repeat 5`; every other outer row uses 1.** This is part of the closed roster, not permission to repeat other rows. Tests exercise the new optional column using fixture plan text after its implementation.

Rejected: a repeat count only in an environment variable or report heading (not build-bound); accepting a reused N=1 binary and trusting aggregate counts; mutating the manifest after its hash; automatic build splitting with hidden extra builds; treating `MinExecuted` as an aggregate floor that lets a large first repetition hide an empty later one.

### D-3: native identity evidence plus independently checked TRX results

For repeat builds, attach a small ordinary `Attribute` implementing TUnit's public start/end event receivers; do not derive from `TUnitAttribute`, whose constructor is internal. It emits a versioned, machine-readable marker into **that test's captured output**, using `context.OutputWriter`. A marker contains the compile-time requested N, run nonce supplied by the driver, native `TestDetails.TestId`, repetition ordinal, case key, class/method and test-host PID. The case key removes only the pinned repeat-index segment from the native ID, retaining all data-source, argument-row, generic and inheritance identity. Do not serialize argument values or recover identity from display names.

Use the pinned `TestIdentifierService` grammar with complete validation, not `Split('.').Last()` (generic types contain dots and inheritance has a suffix). Invalid identity emits an explicit diagnostic and makes repeat qualification fail. Keep the receiver stateless; any per-test bookkeeping belongs in `TestContext.StateBag`. Start/end markers permit failure diagnostics; a green repeat result requires exactly one matched pair. Retries/duplicate pairs are never collapsed into a green repeat proof. Class setup failures or skips may lack markers; retain their native TRX failures/skips and mark repetition evidence incomplete rather than manufacturing results.

Parse TRX definitions and results as the existing driver does, then join each result to its own captured marker. Validate unique TRX execution identity, one terminal outcome per `(caseKey, ordinal)`, ordinals exactly `0..N-1`, the same nonempty case-key multiset in every repetition, one host PID, one nonce and N agreement. Duplicate argument display values remain distinct native data rows. `Expect` tokens and the per-repetition `MinExecuted` floor must hold in every repetition. Strict repeat receipts require zero failures/skips and exact agreement between the actual result roster, TRX counters, repetition counters and aggregate receipt; a counter alone is insufficient. Aggregate executed results are `base-case-count * N`, never marker/assertion counts.

One ordinary TRX remains the primary outcome record. Structured evidence adds `repeat: { requested, completed, passed, hostInvocations, hostPid, repetitions[] }`, with per-ordinal counters, case/result identities and native failures. The CHECKPOINT line appends unambiguous tokens such as `repeat=5 repetitions=5/5 hostInvocations=1`; retain all existing tokens. `ReportWriter` shows each ordinal and its failed method/argument cases. Do not reuse `reruns` for native repetitions.

N>1 disables the tool's separate known-flaky subprocess retry for that row, with an explicit diagnostic if configured. A failed native repetition stays failed. N=1's known-flaky path remains unchanged. Aggregate exit precedence remains the repository's existing precedence; real assertion failures remain exit 1, missing/invalid evidence exit 2, a missing per-repetition floor/roster exit 3, slot timeout 4, row timeout 5 and owner-ended 7 as applicable. No completed green result can be synthesized after cancellation, timeout, a lost child or missing teardown/result evidence.

Rejected: sorting display names into N equal chunks; interpreting `executed=115` as five successful 23-case rounds; keeping only the final attempt; JSON counters detached from the TRX; imposing chronological-round barriers that alter TUnit scheduling; mapping unsupported identities optimistically.

### D-4: version repeat envelopes; preserve source qualification and leases

Leave `SourceSnapshot.cs`, `SourceRunGuard.cs`, `scripts/lib/checkpoint-source.ps1`, source evidence v1, fingerprint framing and all boundary checks semantically unchanged. N=1 keeps script `source.json` v1 and report schema 2, with additive timing data. N>1 script `source.json` is an envelope **version 2** containing `source: <unchanged v1 SourceEvidence>` plus receipt, counters, repeat and timings; a report containing repeated rows uses **schema 3**, with unchanged v1 source objects. Existing validators reject these new envelopes instead of silently blessing unfamiliar repeated evidence.

Extend both current validators to accept the new versions only after all existing source/header/receipt/duplicate-property rules and all D-3 repeat checks. Continue accepting legitimate old v1/schema-2 non-repeat receipts; reject repeat claims embedded in legacy shapes. Add `-ExpectedRepeat N` / `--expected-repeat N` for qualifying a selected repeat row. N defaults to 1; CP-7 validation must name 5, so stripping the repeat envelope cannot downgrade its evidence to an eligible ordinary receipt. Selected-row checks still require every requested row. Compare **all four** line counters, structured counters and per-repetition totals in the new path. Do not change old source evidence merely to make it fit a new report.

`ReportMerger` may retain latest-attempt behavior for ordinary rows. For a repeated row, preserve the whole chosen receipt; never combine green ordinal fragments from different processes/runs into N/N. Validate source identity for every input before row replacement, including superseded red attempts as today. Permit compatible schema-2/3 input without allowing repeat-count or build-binding disagreement for the same row. Retain repeated failures and prior-attempt history in reports. Update all row/state-to-report projections so fields survive detached execution, report, merge and wait.

The script retains one existing lease across its build and entire repeated test invocation. The tool retains its build lease and then one row lease across the single repeated host, as it already does. No lease per ordinal, nested build-slot wrapper, new cleanup path or owner-monitor change. All failures/cancellation still join/terminate the owned driver before release. Repeat duration does not multiply or disable existing deadlines; estimates must budget the whole request. No slot-timeout bypass or `-NoSlot` for delegates.

Rejected: changing source version/fingerprint internals; loosening strict `-NoBuild`; allowing old validators to ignore repeat evidence; accepting an expected-repeat mismatch; reusing a green final ordinal to certify the row; increasing host budgets; blanket changes to lease/owner cleanup while adding a reporting field.

### D-5: phases with precise boundaries and honest missing values

Add structured phase fields to both entry points: `slotWaitSeconds`, `buildSeconds`, `startupSeconds`, `testsWallSeconds`, `teardownSeconds`, `testHostWallSeconds`, plus measurement method/completeness. Tool rows link to their ReportBuild for build time/wait; reused rows record `buildSeconds=0` and the producing build ID, without charging that build again. Distinguish build-slot wait from row-slot wait; expose their sum as total slot wait only with both components retained.

Capture process-invocation launch/exit UTC and monotonic elapsed around the actual `dotnet run` driver. TRX `UnitTestResult` start/end boundaries give earliest test start/latest test end. Define startup = invocation launch to earliest start; tests wall = first start to last end; teardown = last end to driver exit. Startup explicitly includes `dotnet run` evaluation, discovery and assembly/shared-store setup before the first reported test. Tests wall includes scheduling gaps and per-test hooks inside that envelope; it is **not** the sum of durations when tests overlap. Per-ordinal duration sums may also be shown, clearly labeled and never added as disjoint wall-clock phases. The one host's teardown is charged once.

Use `TimeProvider` (default System) for tool measurement; pure timing reduction accepts captured timestamps/elapsed values. PowerShell uses a monotonic Stopwatch for durations and passes explicit boundary samples to its pure reducer. Tests supply `FakeTimeProvider`/literal samples, including UTC going backwards, rather than adding sleeps or timing cushions. Missing timestamps, clock discontinuity, negative intervals, inconsistent totals, prelaunch refusal and partial/canceled runs produce null/unavailable phases with a reason, never zero fabricated as a measurement. Partial timing does not change an otherwise existing N=1 outcome; performance acceptance requires complete timing. New successful repeat certificates require complete identity/outcome data independently of timing availability; their benchmark remains pending if timing is unavailable.

Rejected: inferring startup from transcript silence; summing concurrent test durations as wall time; including slot wait in build duration; presenting absent teardown as zero; a new runtime daemon/profiler; a machine-speed assertion in the ordinary unit tests.

### D-6: repeat policy is a budget, not a green-run tax

Put the following template line in `docs/testing-and-build.md` and the Code-brief standards in `docs/orchestration-loop.md`; put its concise equivalent into `server/Bundles/stage-code.md` by rewriting existing prose **net-shorter**:

`repeat-proof: at most 3 normal + 2 loaded repetitions per unchanged proof selection; none required after green. Exceed only for a flake already demonstrated by Review; cite that Review, filter, reason and revised budget.`

Count total native executions per case, not only additional executions after index 0. Aggregate separate proof invocations against the same budget; changing output directory does not reset it. Required first ordinary V/R and a genuine code-change/failure-driven rerun are reported separately, not hidden as routine proof. Loaded means recorded ambient host load; this card commissions no CPU burners. A documented Review-backed exception is explicit, bounded and reported, never an automatic retry-until-green policy.

CARD-0885 explicitly requires a **one-time five-repetition acceptance benchmark**. CP-7 is that named qualification exception to the routine three-normal ceiling, not a reusable override or five mandatory repeats for future cards. No loaded benchmark is necessary to meet this card. The CLI does not pretend to enforce a cumulative cross-task policy from a single N; the brief/checkpoint roster owns that budget.

Leave `server/Bundles/orchestrator.md` unchanged. The owned Code-brief template lives in the orchestration document; duplicating the paragraph into the nearly full composed orchestrator prompt is unnecessary. If subsequent integration requires any orchestrator edit, it must reduce that file's length and pass the actual composition guard; it is not authorized to grow here. Do not edit stage-review, instruction budgets or guard thresholds. Keep stage-code ASCII-only, preserve all pinned checkpoint/slot/source/next-stage obligations, and record its before/after length against the actual Code base after collisions settle.

Rejected: treating 3+2 as required overhead; a new cumulative-budget service; a bare `--repeat 100` convention without Review evidence; changing the 30,000-character guard; adding parallel boilerplate to every bundle; widening a timeout or weakening an assertion to turn a known flake green.

Verification therefore emphasizes unchanged default counts, clean/dirty/source/build custody, slot release, terminal evidence and strict repeated-result qualification. An unimplemented optimization or noisy historical fixture is not relabeled a regression; a reachable false green is a defect. Do not pad the roster with an unfiltered Unit lane, provider tests or landing recovery unrelated to these edits.
