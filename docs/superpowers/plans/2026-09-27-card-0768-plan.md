# CARD-0768 — Retain confirmed channel inbound payloads and surface long holds

Baseline: `2f050e3d2b1cc36a3440d5914089aaded7c68a12`, equal to `origin/master` by `git ls-remote` on 2026-09-27. CARD-0768 has zero history revisions. This investigation changes no production code or tests.

## Verified findings

1. **The journal payload leak is current.** Acceptance serializes the entire `ChannelMessage` into `ChannelInbound.EnvelopeJson` and commits it before broker acknowledgement (`server/Application/Services/ChannelBridgeService.cs:92-95,134-167`). This includes inline attachment content; attachment bytes are also written to the agent inbox during materialization (`:585-620`). Queue handoff stamps `QueueMessageId` and `TransferredAt`, but leaves `EnvelopeJson` intact (`server/Application/Services/SessionMessageQueueService.cs:692-708`). No production path nulls or deletes it (`ChannelBridgeService.cs:204-205,315-318`; `server/Domain/Entities/ChannelInbound.cs:4-19`). The identity row must survive to deduplicate replay after handoff (`ChannelBridgeService.cs:141-145`; `server/Infrastructure/Data/AppDbContext.cs:275-286`). `docs/telegram.md:30-33` explicitly describes the current retention.
2. **The hold claim is partly stale.** Herdr, provider-capacity and 90-second wake-timeout paths already raise Critical `ChannelReplyLost` incidents and a Warning bridge alert (`ChannelBridgeService.cs:321-344,383-438,646-735`). Continuity, suspension and liveness are checked before the Running fast path (`:759-768`), but their two conflict codes fall into the generic warning-only catch (`:335-339`); no channel-inbound incident is recorded there. Continuity has a separate general decision attention row (`server/Application/Services/AttentionService.cs:1718-1726`), which does not say a channel message is waiting. Thus the missing parity is a channel-specific aged hold, especially for suspended/liveness.
3. **Queue status alone is not a retention receipt.** A channel queue row can be marked `Sent` before terminal delivery (`server/Application/Services/SessionMessageQueueService.cs:1299-1315`), and a screen-only degraded verdict can remain `Delivered` without a UserPrompt (`:3108-3113,3631-3633`). The existing complete matcher restricts channel candidates to real `UserPrompt` and checks identity plus completeness, using an attempt sequence or native-time floor (`:3003-3014,3717-3748,3867-3900`). A `QueuedUserPrompt`, first Enter, queue insert, or `SentAt` is insufficient (`docs/session-runtime-invariants.md:82-91`; `docs/telegram.md:26-36`).
4. **Retention ordering can erase proof first.** `DataRetentionService.RunOnceAsync` currently prunes sessions, transcripts, then queued messages (`server/Application/Services/DataRetentionService.cs:51-68`); defaults are 90/7/30 days and a six-hour sweep (`server/Application/Settings/RetentionSettings.cs:11-26`). Session deletion cascades queue and transcript rows (`DataRetentionService.cs:71-79`). Historical journal rows whose queue/transcript proof is already gone cannot be declared delivered from their `QueueMessageId` alone. CARD-0593 deliberately omitted cleanup (`docs/superpowers/plans/2026-09-26-card-0593-plan.md:67,106`). The test base has 37 existing `DataRetentionServiceTests` methods and 21 `ChannelInboundRecoveryTests` methods; the latter covers current hold and replay behavior (`tests/Antiphon.Tests/Application/ChannelInboundRecoveryTests.cs:2038-2107`).

## Smallest fix

### S1. Purge only confirmed journal payloads

Add a bounded, restart-safe `ChannelInbound` payload pass to `DataRetentionService`, before session/transcript/queue deletion. Default grace: **24 hours from the confirming transcript row's server `CreatedAt`**; expose a positive `Retention:ChannelInboundPayloadGraceHours` setting, with `<= 0` disabling this pass. Page IDs/metadata without loading every envelope. For each candidate with non-null `EnvelopeJson` and a committed `QueueMessageId`, require its Channel-origin queue owner to be `Sent`, then find a complete matching recipient `UserPrompt` after that owner's original attempt floor using the queue's existing channel matcher and clock tolerance. One complete marked batch receipt authorizes all mapped members, including the debounced non-owner members. A later complete UserPrompt can confirm a previously uncertain/screen-only attempt. Only after the grace may an idempotent conditional update set `EnvelopeJson = null`; retain provider/conversation/native identity, binding, acceptance order, queue mapping and incident stamps. Never purge a pending, parked, canceled, truncated, unowned, weak/screen-only or `QueuedUserPrompt`-only delivery. Guard the update against a concurrent mapping change and keep each page bounded.

For pre-fix history, run the same proof query before ordinary retention. Protect a queue/session that still has an unpurged inbound payload from losing its last receipt evidence during that sweep; once the payload is null, normal retention resumes. A pre-existing row whose queue or transcript has **already** been deleted is unprovable: leave its bytes intact and report its count without logging content. Do not infer delivery from age or `TransferredAt`. This is a finite legacy exception, not permission for new confirmed rows to accumulate. Keep the durable payload through retries and queue handoff; do not change the queue delivery verdict or Kafka acknowledgement.

The separate agent-inbox attachment files written at `ChannelBridgeService.cs:606-613` are still readable by agent turns after prompt submission. Do not delete them on this journal grace: their lifecycle needs an explicit path/turn-ownership policy and should be filed as follow-up if bounded inbox storage is required. This card's leak is the new serialized journal copy, including attachment bytes.

### S2. Raise an aged channel hold incident

Classify the known continuity and operator-intent conflicts from `EnsureAgentSessionAsync` without changing their refusal semantics. Default threshold: **10 minutes since `ChannelInbound.AcceptedAt`** while the row is still unowned. Before the threshold, retain it with the existing warning. At or after it, record one Critical `ChannelReplyLost` incident per inbound/hold reason with text saying the message is pending and has not reached the agent; distinguish continuity, suspended and liveness in `FailureReason`, using the current supervision state for the shared operator-intent code. Add a nullable hold incident stamp to `ChannelInbound` via a CLI-generated EF migration, and commit it with the incident under the row lock, as `WakeTimeoutIncidentAt` already does (`ChannelBridgeService.cs:410-438`). Repeated drains and restarts must not repage the same hold; a later complete receipt may proceed without clearing history. Herdr, capacity and timeout keep their current incidents and dedupe. Unknown/transient exceptions remain pending and retain their current warning/retry path.

Update `docs/telegram.md` and `docs/session-runtime-invariants.md` with the new retention and aged-hold contracts during Code. Do not change production code or tests in this stage.

## Risks and decisions for TestDesign

- Reuse the queue's marker/completeness and attempt-floor rules; a separate weaker matcher would delete the only recoverable bytes after a clipped or copied prompt. Validate batched spill pointers and every member's mapping, including a late confirmation.
- The cleanup scan must not deserialize or log attachment content, and must avoid an unbounded transcript join. Conditional update and row ordering must tolerate concurrent worker/retention runs.
- Queue and transcript retention are configurable; preserving their last evidence for an unpurged inbound can defer normal deletion. Surface counts for permanently unprovable legacy rows for an explicit later repair policy rather than guessing delivery.
- Critical hold incidents may page once per inbound. TestDesign should verify the expected grouping in attention and incident paging; if that is too noisy, use one durable episode key per agent and hold reason while preserving the same threshold and retry safety.
