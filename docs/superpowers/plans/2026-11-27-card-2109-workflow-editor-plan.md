# CARD-2109 · Review workflow editor

For [GH-62](https://github.com/michal-ciechan/Antiphon/issues/62). Source baseline is `b5b349d968b5c5ae28a66c73201f1ab06a540aa5`, the assigned tip and current `origin/master` when planning began. The [review engine design](../../features/012-review-engine/design.md#33-definition-and-revisions) and [API contract](../../features/012-review-engine/api.md) own execution and wire behaviour. This plan changes both at the points called out below.

## Ground truth

| Card premise or design expectation | Behaviour at the baseline |
|---|---|
| The Workflow tab shows the run graph and validates it. | `WorkflowTab.tsx` uses `useReviewWorkflow(run.workflowRevisionId)`. It already calls `POST /api/review-workflows/validate` and shows grouped diagnostics. The graph remains read-only, and diagnostics have node/edge references but no graph navigation. `RunHeader.tsx` does not currently render the graph hash. |
| Validation rejects unknown steps, cycles and missing inputs. | `ReviewWorkflowValidator` checks graph references, edge outputs, gate rules, sections and bounded cycles, and warns on missing descriptions. It never checks `run:` against `ReviewWorkflowExecutor.StepNames`, checks chain configuration, or resolves declared input producers. Enum binding can reject unknown text before diagnostics, and undefined numeric kinds can reach the service. The default fan-out child `reviewer` is an agent without `run:`, executed through the fan-out adapter. |
| Instance and repo workflows can be selected at intake. | `ReviewService` writes only the embedded `pr-review.yaml` snapshot through `EnsureDefaultRevisionAsync`. `ReviewWorkflowYaml` parses repository-shaped YAML, but intake never reads that file. `ReviewWorkflowRevision` stores name, hash, graph and creation time. The canonical graph hash is unique today. |
| A run knows which revision it used. | `ReviewRun.WorkflowRevisionId` pins the graph for executor walks. Iterations have no revision pin. `ReviewService` still reads the embedded default for parked wait events and gate decisions, and creates a hard-coded `intake` execution. The executor can also create iterations at a back edge and keeps its graph in `ReviewWalk`. |
| Configured policy is visible and editable. | `NodeSidePanel.tsx` displays raw params and a YAML-derived failure hint. `ReviewWalk.OnFailure` gives server config precedence. `ReviewDecideSteps` applies `GatesOff` to optional gates only. Model steps look up a named chain or a step-specific default. The embedded wait's `timeout: 14d` is descriptive today. The wait executor only parks for events. |
| `maxIterations`, outputs and inputs are editable node parameters. | The active traversal limit and overflow target belong to an edge. Node `outputs` describes valid branch labels and does not change what a registered handler emits. Most built-in steps use implicit inputs. Publish reads verify output by step name. |
| Existing review authorization can protect editor saves. | The review sign-in middleware protects authenticated deployments. `ReviewViewer.MayDecideOn` is a gate permission and can include repo readers or everyone. With sign-in off, the resolved viewer is a configured/fallback identity and can be header-overridden in development. |

## Decisions

| ID | Default and reason | Alternative considered |
|---|---|---|
| D-1 | Save a named, noted, immutable graph revision and move one scope pointer. Repo override wins over instance default, then embedded fallback. Resolve those pointers only when a new run is created, for manual and polling intake alike. Existing runs keep their starting revision through ordinary processing, including re-intake, unless explicitly scheduled under D-2. | Replacing the active run graph would reinterpret waits, gates and historical node IDs. A mutable definition row would make old executions unreproducible. |
| D-2 | “This run's next round” is the next numbered round after the one shown at save. Apply it only when a transition advances the round and creates its intake. Keep it for retries and rechecks within that round. Subsequent numbered rounds return to the run's starting revision. A same-round recheck or base-drift pass neither consumes nor shifts the pending revision. | Consuming at the next executor wake could change a live frontier. Consuming at the next iteration would apply to retries in the current round. |
| D-3 | Store all three scopes in Postgres, including the repo override keyed by the code host and canonical repository identity derived from the run. This delivers an immediate in-product save without repo write credentials. Update design §3.3, §10 and the YAML header to distinguish this scoped override from proposed repo-file support. | The design proposes opening a PR for repo workflow changes. That needs a file source resolver and a new code-host write flow, and a successful save could not activate a revision until merge. |
| D-4 | Keep the existing graph DTO as the authored draft format and the existing validator as the graph authority. Add execution-aware checks against server step contracts and chain settings. Use structured fields and the existing graph canvas. | A parallel YAML editor/parser or client-only validation would create two editing contracts. A free-form parameter map would accept fields an executor ignores. |
| D-5 | Require an explicitly allowed signed-in operator in GitHub mode, using `Review:Auth:AllowedLogins` and the authenticated principal. In `None` mode allow saves only through explicit `Review:WorkflowEditor:AllowTrustedInstanceWrites` opt-in for private single-operator deployments. Record the configured instance actor in that mode, ignoring the dev viewer header for this mutation. | Gate eligibility, a viewer header, loopback and arbitrary signed-in review access do not establish operator authority. The server's code-host credential is for execution, never caller authorization. |
| D-6 | Keep canonical content hash and revision identity distinct. Every successful write creates a fresh revision ID, even when equal graph content shares a hash. Keep embedded seeding convergent with a unique hash among embedded rows only, and compare scope tokens by assignment identity, including the relevant round or inherited source. | Deduplication by graph hash alone loses save authorship and notes, and hash-based concurrency misses a change that returns to equal content. |
| D-7 | Expose a per-invocation `timeout` on registered read-only, cancellable decision/completion work. Cap it at the existing safe lease/handler bound, preserve existing behaviour when absent and route expiry through the normal failure policy. Show the legacy wait value as informational. `maxIterations` is edited on the edge with its overflow gate. | Accepting a timeout on every kind would misrepresent the event wait and could interrupt posting, merge or another side effect. Implementing a wait timer would require its own expiry outcome and scheduler. |
| D-8 | Report effective server policy for the selected graph and repo, with provenance. Workflow revisions pin the authored graph and chain name, while policy overrides and chain configuration remain live server settings. Label the response as effective under current settings. | Materializing operator settings into historical graph content would change existing precedence and imply that provider settings and their credentials are versioned. |

## Revision lifecycle and API

Keep the existing GET default/revision and POST validate contracts compatible. The legacy default GET continues to return the embedded graph for historical runs that have no pin. Use a new endpoint class, `server/Api/Endpoints/ReviewWorkflowEditorEndpoints.cs`, for editor operations. Update the feature API contract before code.

| Method and resource | Enforced contract |
|---|---|
| GET `/api/review-runs/{id}/workflow-editor?scope=InstanceDefault` | The same resource supports `Repo` and `NextRound`. Return the target's assigned or inherited graph, resolved rev ID/hash, revision metadata, opaque `expectedRevision` token, scope eligibility and reason, and selected run/round summary. Return the pinned graph separately through existing revision reads. For NextRound, return the pending graph if present, else the run's current pinned graph as draft base. Compute scope and canonical repo from the route's run, with no client-supplied repo/path. |
| PUT `/api/review-runs/{id}/workflow-editor?scope=…` | Body `{ expectedRevision, baseRevisionId, name, note, graph }`. Name is the trimmed definition name (max 200); note is required and bounded (proposed max 2,000). `baseRevisionId` identifies the source the operator edited, including an explicit copy from the run's revision when it differs from the target. Validate again on the server. Return the new immutable revision ID/hash and fresh scope state. 401 follows existing sign-in, 403 for unauthorized writes, 404 for missing run/revision, 409 for stale token, advanced or closed target round, 422 with structured graph diagnostics for a semantically invalid draft. |
| POST `/api/review-workflows/validate` | Keep the raw graph request and `{ valid, diagnostics }` response. Return semantic diagnostics as 200, with node IDs and edge location when available. Decode bad node kinds into a node diagnostic, including numeric undefined values. Malformed JSON stays a transport-level 400. The route reads settings and performs no writes or model/code-host calls. |
| GET `/api/review-runs/{id}/workflow-editor/revisions?scope=…` | Return a bounded, newest-first history for the scoped context, including run/iteration pins and effective or pending choices as appropriate. Use existing GET by revision for graph diff and expose safe metadata additively. Use a run-and-revision keyed read for effective policy, so the cached immutable graph remains independent of repo settings. |

Save under one database transaction. Check the target token and validate the same normalized graph to be inserted. Lock or conditionally update the target pointer, including first-write and inherited-source races. A repo inheriting the instance default must conflict if that inherited baseline moves while the draft is open. Scope tokens advance on every write. Recompute the hash and back-edge flags on the server and record actor, creation time, note, scope, predecessor and base. Concurrent saves from the same token have exactly one winner, with no orphan revisions. Leave the user's draft intact on an ambiguous transport failure and refetch the target before any retry.

Add the authoring metadata, scoped assignments and iteration FK with one additive EF migration in S2. Represent pending NextRound as an assignment keyed to run and target round. Support legacy nullable iteration pins by falling back to the run's pin and then to the embedded definition only for unpinned legacy/demo data. A non-null pin that cannot be loaded is an error. Source metadata can be nullable for legacy revisions, which also identify the embedded-seed unique hash index. Reuse the same assignment table in S3.

At a numbered-round boundary, share one selection routine across direct Refresh and RequestRound paths, walked gate `AnotherRound`, and executor back edges. Finish and interpret the outgoing event using the old pin, including old gate decisions, wait subscriptions and overflow handling. Under the same database transaction, check the latest run state, consume only the matching pending assignment, pin the incoming iteration, and create its intake/frontier using the selected graph. Same-round iterations inherit the previous iteration's pin. The executor must reload/switch graph and per-walk caches at a committed boundary before running another step. Historical lookup uses the revision associated with each execution's iteration. For cross-iteration consumers, resolve step identity against the producing iteration, and count limited edge traversals against the matching definition/edge so stale node IDs or a previous topology cannot be mistaken for the current edge. Run-wide review state, round counters, findings and reviewed head SHAs retain their normal meaning.

Serialize pending save, round advance and close against a fresh run state, using the GH-56 concurrency path after that change lands. A save that wins before a round advance applies once. A save that loses returns 409 and requires reconfirmation for the new round. A closed/merged run or demo cannot receive a pending assignment. Closing supersedes any pending assignment without deleting its revision history. A staged save wakes no executor by itself. Review waits continue to hold no seat and are released by the configured events or gate decisions. This plan adds no new Antiphon session wait or automatic release deadline.

## Validation and editor behaviour

- Reuse existing cycle, gate/overflow and warning diagnostics. Add node ID / kind / step compatibility, required and typed step params, duplicate or ambiguous routing, and missing input/reference checks before executor assumptions can fail. The built-in graph and older stored v1 graphs continue to validate with existing implicit bindings. Treat the built-in fan-out's reviewer as a child-only node, and validate fan-out/join references. Validate chain names against the correct decision or completion chain registry after existing defaults are applied. Only accept emitted branch outputs a registered step can honour. Keep fallback and loop overflow valid after any edge edit.
- Preserve an unambiguous intake node and supported stage/control-flow contracts. Audit hard-coded node IDs and typed consumers before admitting topology edits. Validate that required upstream artifacts are available on admitted paths, including implicit built-in dependencies and failure fallbacks, and keep wait/gate event values compatible with the runtime. An unknown or unavailable producer is an error at the consumer. Use a shared step descriptor where a validator and executor would otherwise duplicate step dispatch rules. GH-62 validates the shape and references of declared inputs, and admits them for a step when its descriptor and executor support the binding.
- Store edited work timeouts as positive whole seconds in `params.timeout`. A supported handler receives a linked deadline and must observe cancellation and release any child work before the executor proceeds. Host shutdown, supersession and lease loss keep their existing handling. Validate against the effective lease and handler/transport limits. Reject values on an unsupported handler, and preserve the embedded wait's legacy string through round trips. Test the expiry, cancellation and failure-policy paths with a controllable clock and fake model.
- Resolve effective `OnFailure` with the same precedence as `ReviewWalk`, `GatesOff` with optional gate and repo rules, and chain with the actual step default and configured chain name. Show origins such as “Instance override”, “Workflow revision” and “Step default”. In Edit mode show a configured override alongside the authored field it supersedes. Never return provider credentials or settings values unrelated to the shown node.
- Keep the selected run iteration and pinned name/hash above the graph. Show historical overlays against each iteration's revision. Put **Edit workflow** beside **Validate**. Editing opens a local draft with a target scope selector, an affected-runs explanation, a name and note at save, and the existing right-hand inspector for typed fields. Separate the observed run overlay from the draft preview. The new-node form offers supported kinds/steps and presents step-specific inputs and outputs. Add endpoint/label, reconnect and deletion controls in the inspector as keyboard-accessible alternatives to canvas gestures. Deletion updates incident edges and section membership, and surviving broken input/fan-out references surface as diagnostics.
- Debounce validate-as-you-edit and keep **Validate** available on demand. Bind each response to the exact draft generation so a slow response never clears newer errors. Place counts/markers on affected nodes and edges, and link diagnostic rows to selection, expansion and focus. Show graph-wide diagnostics in the list. Errors block save, warnings are visible and permit save. Track dirty drafts across run refetch and confirm discard before changing scope, replacing a draft or leaving. A 409 preserves the draft, shows latest versus draft, and offers reload or inspect/reapply. A successful save confirms its target and invalidates the matching assignment/history queries, without changing the displayed execution. Gate permissions and write capability failures surface from the server.
- The revision selector offers compare against a previous saved revision or the iteration pin. Show additions, removals, changed parameters and edge changes in a deterministic side-by-side or field diff. Show note, author and abbreviated hash, with the full ID/hash available. Include edge ordering when it affects route selection. Keep run overlays and draft diff readable at narrow widths and in the existing fullscreen view.

## Performance budget

All candidate checkpoints use the portable lane (server Unit, server/Postgres Integration, E2E contract and client Vitest). The live defaults and runner catalogue were read on 2026-11-27. Keep dispatch unpinned by default, with no `--runner` or `--platform` flags. The shared CDP Edge lane is optional for visual evidence. If used, name a dedicated `BU_NAME` daemon.
