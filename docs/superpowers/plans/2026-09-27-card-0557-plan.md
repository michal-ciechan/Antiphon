## Smallest useful fix

**S1 — server projection.** Extend the existing `/api/agent-tasks/pipeline` DTO with `investigateBacklog: { total, items }`, where `items` is the first five ranked *fresh Backlog candidates* across non-archived boards. This field is explicitly advisory and distinct from `stages[Investigate].ready`. Each item has card id, board id, identifier, title, rank and position (enough to cite and open the card). Query only the columns needed, with `AsNoTracking`, materialize, sort using `CardRanking.OrderKey` at the response's `asOf`, break exact ties with board id then card id, count before `Take(5)`. Do not use the capped cards-list endpoint. Exclude archived cards/boards, terminal columns, cards with an owner session, and Backlog cards with an open or succeeded stage task; a previously failed/canceled task does not by itself hide a still-Backlog card. Label these *candidates*, since rank does not override WIP, scope collisions, human choices, or whether Investigate may be skipped. Keep all existing stage roles and arrays unchanged. Add focused service and HTTP-contract tests, document the field in `docs/antiphon-api.md` and `docs/ops-http.md` for an orchestrator's one-call answer. No new natural-language command: the orchestrator can ask/read this one existing route.

**S2 — ranked ready and client glance.** To align the visible order with the standing lowest-rank-first picking rule, sort each stage's formal `ready` list by the source card's same `CardRanking.OrderKey(asOf)`, then `ReadySince`, board id and card id; expose `rank` on each ready row so a reader can explain the order. This is advisory ordering, not a promise that dispatch occurs in that sequence. `PipelineStagesPanel` displays the five Investigate Backlog candidates under a separate `Backlog candidates` subheading and count (`total`), links each to `/boards/{boardId}?card={cardId}` as `BacklogRow` does (`BacklogRow.tsx:40`), and shows the Investigate group when these are its only rows. Keep formal ready rows visually separate and ordered as returned. Add a short `Ranked by card priority; dispatch is a decision` cue. Preserve the current task drawer, empty/idle states and phone-width layout. Mirror the DTO in `client/src/api/agentTasks.ts`; invalidate the pipeline query on `CardChanged` (`useSignalRInvalidation.ts:69-83`) so ranking edits update without waiting for the 15-second poll. Update the contract snapshot fixture from a deterministic seeded Backlog scenario; `ContractSnapshotTests.SnapshotPipelineAsync` must filter the new fleet-wide items before comparing (`tests/Antiphon.E2E/ContractSnapshotTests.cs:1187-1234`).

No separate aggregate endpoint, new dispatch engine, WIP change, or chat parser. This is one API call for the whole answer and one UI panel for the glance.

## Risks

- The pipeline read already materializes all bound stage tasks (`AgentTaskPipelineStatusService.cs:74-82`); add only a narrow Backlog projection and measure query size rather than loading descriptions or whole boards. `GET /api/cards?status=Backlog` truncates by update time, so it is unsuitable for this field.
- Backlog `Status` may lag a task event until the card transition sweep; exclude represented cards from candidates using the same response snapshot. The two reads are advisory rather than transactional. Never turn this into an automatic dispatch gate.
- Card ids are unique, but `CARD-nnnn` identifiers are board-scoped (`CardService.cs:265-269`); carry `boardId` in the API and UI link, and use it in tie breaks.
- The snapshot is fleet-wide; a new field without fixture filtering will make `Pipeline_status_contract` depend on unrelated tests' cards. Keep its seed/filter deterministic. Backend failure must show an error, not an empty ranked queue.

### Eligibility and the meaning of a candidate

The candidate set is fleet-wide and advisory. A card qualifies when its stored status is Backlog, neither card nor board is archived, its column is nonterminal, it has no `OwnerSessionId`, and its **own GUID** has no open or succeeded pipeline-stage task. Open means Queued, Dispatched, Working or Blocked; all six stage roles participate, including Investigate and Mutation. Thus an in-flight Investigate is excluded even while the card transition sweep still leaves the card in Backlog. Failed/canceled history alone permits retry. An unbound task, a task bound to another card, or a nonstage helper does not satisfy the stage-history exclusion. A succeeded stage remains evidence of already-started work even with `next: none`, `land` or `decide`, or after its artifact lands.

Also exclude the exact `post-land-verification` label from fresh feature candidates, as required by the orchestration owner. Parse the label list; substring matches in titles, descriptions or other labels do not identify companions. This is a necessary clarification to S1, not a companion writer or a new dispatch gate.

Importance contributes to derived rank; it is **not** a High/Critical-only eligibility threshold. Low and Normal cards remain candidates when they are the available work. For example, Critical/Normal has rank 4, Normal/Now rank 6, Low/Now rank 9, Normal/Normal rank 10 and Low/Normal rank 13. Candidate order must use the same `CardRanking.OrderKey` as dispatch, including null-last position/due rules. Only exact key ties add board GUID then card GUID; dispatch does not define these otherwise-equal ties. `UpdatedAt`, identifier, title and handoff age must not outrank that key. Count the complete eligible set before taking its first five.

**Already covered work:** Done/Canceled/archived cards and same-card succeeded stage work (including landed work) are not fresh candidates. A closed card on another board with the same `CARD-nnnn` identifier must not suppress an unrelated Backlog GUID. There is no structured `CoveredBy`/duplicate-card relationship in `Card` at this base. Semantic overlap with a *different* landed/closed card therefore remains an operator check: read the candidate's thread and the cited closure/publication before dispatch, record the supersession/closure on the board when established, and confirm the next glance drops the closed candidate. The API must not infer coverage from matching titles, descriptions, identifiers or a Git probe. The UI's advisory cue must not claim this check was automated. Automatically detecting cross-card semantic coverage would require a separate relationship/design decision; this plan supplies no such authority.
