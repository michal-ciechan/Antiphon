# CARD-0505: live delegation concurrency settings

Date: 2026-09-27. Investigate baseline: `2f050e3d2` on `feat/card-task-b9ca189f`, matching the requested master floor. Next stage: TestDesign. Related: CARD-0749 is the same runtime backend gap and is already in Review; CARD-0506 owns the settings UI. Coordinate their landing before Code to avoid two implementations of this resource.

## Verified findings

- CARD-0505's observed absolute 3 / role 1 is stale. `DelegationSettings.MaxOpenTasks` defaults to **6**, and `RolePolicy` defaults Code and Review to **2**, other named pipeline roles to **1** (`server/Application/Settings/DelegationSettings.cs:33,334-353`). `docs/orchestration-loop.md:450-461` states the current WIP policy. `AgentTaskConcurrencyLimitTests` covers project-local and role-local counts (`tests/Antiphon.Tests/Application/AgentTaskConcurrencyLimitTests.cs:410-635`).
- The create gate already counts **Queued, Dispatched, Working** non-specialist tasks per project, with null project as a separate bucket; `ignoreConcurrencyLimit` is an explicit bypass. Its limits are copied from startup `IOptions<DelegationSettings>`, and the 409 payload takes those snapshot limits (`server/Application/Services/DelegationOpenGate.cs:28-33,40-54,65-94,105-132`). Thus queued tasks already consume the open/role cap, but there is no independent queued-only per-stage cap. A dedicated queue-depth knob would be a separate admission rule; do not relabel `RecommendedInFlight` as one.
- Desktop dispatch uses `MaxConcurrentTasks` (default **2**) at several admission/recovery and hold-text paths (`server/Application/Settings/DelegationSettings.cs:19-25`; `server/Application/Services/AgentTaskDispatcher.cs:490-525,1334-1353`). Pipeline status reads `RecommendedInFlight` and desktop cap from the same startup settings (`server/Application/Services/AgentTaskPipelineStatusService.cs:130-169,358-365`). There is no runtime write path for these values.
- Remote phone-home capacity is different. The runner registers a seat count bounded by its configured `MaxCapacity` (default 10), and `DeclaredCapacity` returns that live registration (`server/Infrastructure/Agents/SessionRunner/PhoneHomeRunnerDirectory.cs:271-276,449-457`; `server/Application/Settings/PhoneHomeRunnerSettings.cs:125-136`). Remote dispatch holds at the declared seats (`server/Application/Services/AgentTaskDispatcher.cs:1064-1070`). An API edit cannot make a runner execute above its registered/compose ceiling.
- The desktop catalogue and host-stat projection also expose startup cap (`server/Application/Services/SessionRunnerCatalogue.cs:45-65`; `server/Infrastructure/Agents/SessionRunner/HostStatsPollService.cs:21-35,142-149`); `/api/session-runners` passes startup settings (`server/Api/Endpoints/SessionRunnerEndpoints.cs:26-36`). `ProjectSetupDtos.DelegationSummaryDto.MaxConcurrentTasks` is a catalogue summary, not a project override (`server/Application/Dtos/ProjectSetupDtos.cs:95-101`; `server/Application/Services/ProjectSetupService.cs:217`). CARD-0749's suggestion that this DTO already implements an override is stale.
- `/api/runner-defaults` demonstrates the existing write contract: required complete PUT, `expectedRevision`, reason, provenance, immutable revisions, and post-commit event (`server/Api/Endpoints/RunnerDefaultEndpoints.cs:12-88`; `server/Application/Services/RunnerDefaultSettingsService.cs:47-177`). Reuse that pattern, without repurposing runner placement defaults.

## Smallest server fix

### S1. Durable settings and API

Add `DelegationConcurrencySettings` current singleton and append-only revisions through a CLI-generated EF migration. Store a complete canonical snapshot in each revision. Seed revision 1 from the three existing configuration sources once: `MaxOpenTasks`, every role's `RecommendedInFlight` (including null/unbounded), and desktop `MaxConcurrentTasks`. Later appsettings edits do not override a persisted choice. Use one scoped service that reads one coherent snapshot per operation, with no mutable process cache. Keep configuration as the first-import/default source; GET reports effective value and source (`config`/`apiOverride`, plus built-in default where no config is supplied), revision, last reason/provenance and caller task ID.

`GET /api/delegation-concurrency` returns the global limits, per-project effective/override values, per-role values, and per-runner effective/requested/advertised seats. `PUT /api/delegation-concurrency` requires the current `expectedRevision`, a complete snapshot, nonblank bounded `reason`, and `provenance: "Human"`; omitted fields are 422, stale revision is 409, a canonical no-op adds no revision. Add `GET /api/delegation-concurrency/revisions` with bounded cursor paging. Preserve the runner-defaults Human/Auto history protection if an internal Auto writer is later added, but this public PUT accepts only Human. Derive caller task identity on the server as runner-defaults does. A transaction commits the current row and history atomically; a concurrent PUT has one winner. Publish `DelegationConcurrencyChanged {revision}` after commit, without making a lost event affect enforcement.

The global object has `maxOpenTasks`, `roleLimits` keyed by defined `AgentTaskRole` (nullable value means unbounded only for a role; absent role means inherit the startup seed), and `runnerLimits` keyed by canonical runner ID, including `desktop`. A project override has optional `maxOpenTasks` and optional role values; removing a project/role entry restores inheritance. An explicit nullable role override means unbounded, so absence and null must remain distinct. Validate known project IDs and runner IDs, reject duplicate keys and unknown/numeric roles, require positive finite integers with a documented safe upper bound, and never allow zero to silently disable dispatch. A project without an override inherits global limits. Counts remain per project; changing a limit below occupancy blocks *new* creates/dispatches and never kills or cancels current work. Keep the existing explicit `ignoreConcurrencyLimit` exception and warning.

Runner limits are server admission limits. For desktop, the effective cap is the configured limit. For a remote runner, effective cap is `min(runtime limit, currently declared capacity)`; if no override, use the declared capacity. GET exposes both values so a requested increase that the runner cannot supply is visible. Validate a remote override against its configured `MaxCapacity`; an offline runner may retain a validated override, but has no effective seats until registration. Raising above declared seats needs runner re-registration/configuration and is outside a server-only live edit. Never send a capacity change to the remote runner as part of this endpoint.

### S2. Live readers

At create, take the effective project/role snapshot **inside** `DelegationOpenGate`'s advisory-lock transaction before count-and-insert, then put those exact limits into the 409 detail. A settings PUT and a create must serialize on the same lock (or equivalent database lock order) so the admission decision cannot use a half-updated revision. The role cap still counts open statuses and absolute cap wins when both are exceeded. `ignoreConcurrencyLimit` continues to bypass only this create gate.

At each dispatch tick, resolve a coherent current runner-cap snapshot and use it for desktop slot claims, retained-capacity returns, cap holds and held-age text; use the effective remote cap with declared seats in remote occupancy checks. Existing active work can temporarily exceed a lowered limit. Pipeline status, `/api/session-runners`, host stats, and project setup catalogue must project the same live effective values. Do not alter runner defaults, placement, model routing, remote registration limits, or task ownership. Documentation: `docs/ops-http.md` for GET/PUT/revisions and examples; `docs/orchestration-loop.md` §1 for the live controls and distinction between open/role admission and runner seats.

### S3. Scope boundary

This is the backend for the existing open-task queue bound and per-role admission bound. It does **not** introduce a second queued-only limit or the CARD-0506 UI. If a distinct queued-only ceiling is required after these controls are live, specify whether excess creates are refused or held and add it as an explicit follow-up to CARD-0505; do not infer that behavior from `RecommendedInFlight`. CARD-0749 should be reconciled with this plan rather than implemented independently.

## Risks

- A process-local cache or `IOptionsMonitor` alone permits stale or mixed revisions across create, dispatch and status. Read persisted immutable snapshots coherently and exercise same-process edits plus restart.
- Raising a remote server cap above advertised seats cannot create real runner capacity; always clamp, show the constraint, and test offline/re-registration behavior.
- Lowering caps below current occupancy must only stop new work. Preserve current sessions and the retained-capacity return priority.
- The original card and CARD-0749 overlap. Coordinate owners before Code; do not land two independently named concurrency endpoints or migrations.
