## Smallest fix

One script/doc slice, **S1**. Add a single post-success deployment prompt to `scripts/card.ps1` after `Write-TaskSettlementLine` for `close` and for `move` into a terminal column. Say plainly that the card move and task settlement succeeded but service activation has **not been verified**. Point to the canonical main-checkout procedure: use the land receipt's verified commit; for server changes compare it with `GET /api/version` and probe the feature; for runner/fake-gateway changes run `pwsh -File scripts/check-daemon-build.ps1` from the updated canonical checkout, then restart only the affected service and recheck its reported build. Print the prompt even if the task-settlement result is empty. Do not let a failed or unavailable build probe turn an already successful card move into an error; the prompt itself is the required close-time signal.

Put that exact standing step in `docs/orchestration-loop.md` at the post-land activation rule and in `docs/apphost-runbook.md` beside the existing verification commands. State that the same step applies to UI/API terminal moves and tracker closes, which bypass `card.ps1`. No server endpoint, data model, automatic restart, or periodic job is needed to meet this card's acceptance. A later cadence/status feature would need its own scope and must distinguish service source changes from unrelated commits and unknown build identity.

The prompt is deliberately advisory. A remote `card.ps1` process can reach the server through `ANTIPHON_API`, while `check-daemon-build.ps1` targets localhost:17204/17208 and its invoking Git HEAD (`scripts/check-daemon-build.ps1:10,35-40,53-59`). Running it automatically from this Linux task worktree would produce misleading or unavailable results. The canonical operator step already has the correct host and source root (`docs/apphost-runbook.md:100-122`).

## Verification design

Add `CardCloseDeploymentPromptScriptTests` in `tests/Antiphon.Tests/Scripts/`, following the real PowerShell/stub-API pattern in `CardDiagnoseScriptTests.cs:15-17,48-71`. Mark it `Integration` and `[ParallelLimiter<ProcessSpawnLimit>]`. Keep its stub entirely local and assert the actual CLI output and the request count; no production ports or restarts. Test methods:

- V-1: `close` succeeds; card line, tracker line, and a CARD-0738 `tasks still working` line precede a clear deployment-unverified prompt naming `/api/version` and `check-daemon-build.ps1`.
- V-2: `move -To Done` prints that prompt; a nonterminal move does not.
- V-3: terminal close with absent `taskSettlement` still prints the prompt.
- R-1: failed PATCH prints no success/deployment prompt and exits nonzero.
- R-2: prompt does not invoke localhost runner, restart commands, or any extra API mutation; the stub sees one PATCH. The prompt names the canonical checkout, so a worktree HEAD is never represented as deployed.

Positive controls after ordinary green: PC-1 temporarily remove the post-success prompt call; V-1 must fail on its missing output assertion, then restore and rerun green. PC-2 temporarily gate the prompt on `Verb -eq 'close'`; V-2 must fail for the terminal `move`, then restore and rerun green. Record test assertion failures, not compile/fixture errors. The TestDesign stage may tighten method names/fixtures but must retain the exact class filter and this coverage floor.

## Risks and cost

- An operator can ignore an advisory, and a UI/API/tracker close cannot show the CLI prompt. The documented standing step covers those paths but this small slice does not mechanically enforce it. If evidence later shows ignored prompts, scope a server-side workflow gate separately.
- A server SHA alone does not prove tracked edits are loaded, and a runner SHA may legitimately precede unrelated commits (`docs/orchestration-loop.md:145-153`; `docs/apphost-runbook.md:118-122`). The step requires a feature probe and closure-aware daemon check rather than raw SHA equality for every service.
- CARD-0738 may leave started tasks working after close. The new prompt follows, and never replaces, the settlement lines; operators must still cancel or reopen those tasks (`docs/agent-card-lifecycle.md:24`).

Ordinary Code floor: **6 minutes** for CP-1 plus about **20 minutes** to author the script, docs and tests: **26 minutes**. Positive-control floor: **2 controls × red and restored green = 4 class/method executions, about 8 minutes**, outside ordinary Code. No build or test was run during this investigation.
