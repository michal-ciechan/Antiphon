## Smallest fix

### S1 — persist evidence from the existing one-row runner

Extend `scripts/run-checkpoint.ps1` so `Invoke-Dotnet` creates a per-phase
`build.log` or `run.log` in its already-fresh results directory **before**
starting the child, streams and flushes stdout/stderr into it while the child runs, and
appends an exit marker only after `WaitForExit` returns. Keep the existing
`CHECKPOINT` line, exit-code meanings, slot custody, forward-slash output-path
guard, TRX parsing, and console output. A killed or detached wrapper then
leaves a partial log with no exit marker; a completed failing build leaves its
actual error and exit code. Do not treat mere creation of a log as proof of a
successful build. Use one writer or synchronization for both streams; avoid
buffering the whole build in memory. Add three offline shim cases to
`scripts/test-run-checkpoint.ps1` and corresponding methods in
`tests/Antiphon.Tests/Scripts/RunCheckpointScriptTests.cs`:

- `C578_BuildLogVisibleBeforeExit`: hold a fake build after one output line;
  require a readable `build.log` while the process is still live and require the
  checkpoint wrapper to remain live too.
- `C578_FailedBuildKeepsLogAndExit`: fake a nonzero build; require the error,
  exit marker and existing exit-2 verdict, with no test invocation.
- `C578_NoSuccessReceiptForInterruptedBuild`: stop the owned fake build/wrapper
  at a controlled boundary; require the partial log to remain and no completed
  exit marker or green checkpoint line.

The first case must go red if streaming is replaced by today's end-of-process
buffer. The second must go red if exit handling is discarded. The third must go
red if an incomplete process is reported green. Keep the process-spawning test
class's existing `ParallelLimiter<ProcessSpawnLimit>`.

### S2 — make Mutation use that runner serially

In `docs/testing-and-build.md`'s Mutation section, give the exact
`scripts/run-checkpoint.ps1` invocation pattern for each baseline, red and
restored-green phase: unique `bin-<phase>/` and results root, the method-name
filter supported by TUnit, `-Expect` for the intended class/method, and a
nonzero `-MinExecuted`. A red control is an expected **test** exit 1 with the
named assertion in its fresh TRX; build/no-TRX exit 2 and zero/roster exit 3
are infrastructure failures. Await each invocation's complete process and
check its build exit and TRX before starting another build in the same
SourceLanding worktree or changing source. Keep logs and results in the
task's external verification evidence root, not in committed source. Preserve
the immutable snapshot and restoration rules. This updates the current generic
`dotnet run` example at `docs/testing-and-build.md:439-452`; it does not restart
Mutation operator-wide or change any production service.

If the desktop roots later reveal an exact failing compiler/restore error,
append that evidence to this plan before Code and address that error separately;
do not infer it from the absence of the old log.

## Risks and limits

- The Windows evidence roots are unavailable from this host. A future
  Windows replay could still reveal a separate MSBuild or shell/transport
  defect. The plan deliberately adds the evidence needed to classify it.
- `run-checkpoint.ps1` currently writes the host output only after the child
  exits. Changing to streaming can interleave stdout and stderr; tests must
  assert content and phase markers, not a total cross-stream order.
- The third successful attempt proves the SourceLanding snapshot can build;
  it does not prove simultaneous builds in that worktree are safe. Serial
  Mutation builds remain required even with a host build slot; CARD-0773
  separately owns whole-table checkpoint build serialization.
- A method wildcard may select several parameter rows. Use fresh TRX roster
  and counters to attribute each row. The original literal parameter suffix
  must not be reused as the sole PC filter.
