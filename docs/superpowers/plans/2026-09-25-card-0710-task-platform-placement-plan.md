## Outcome and scope

A task declares `RequiredPlatform = Any | Windows | Linux`, independently of an optional named runner. A card supplies a default, copied into each new task. A specific requirement must agree with the selected runner's own platform evidence before work can launch or be delivered to an existing process. Named mismatches return HTTP 409 without creating a task or sending work. `Any` follows the runtime default policy: per-kind location, global location, then existing fallbacks.

The desktop becomes a visible named choice, `desktop`, with `local` retained as an alias. Add a runner catalogue showing platform, availability and capacity, task creation controls, card default controls, and task placement display. Replace the one-remote implementation with a configured collection and independent connections. This includes the underlying recovery/store/configuration isolation; changing only the allow-list would be incomplete.

Global and per-agent-kind runner defaults are durable runtime settings, editable through Settings > Routing and the API. Remove the CARD-0660 Codex automatic-placement exclusion for supported worker Worktree tasks. The operator's desired configuration is global `server2`, with Grok, ClaudeCode and Codex inheriting it; Windows requirements select a compatible Windows runner. Do not seed a Codex desktop exception.

This card does not change model/tier selection, supported phone-home workspace/backend shapes, landing ownership, live-process relocation, or the receipt required to prove prompt delivery. Multiple Linux phone-home runners are in scope. Adding a Windows phone-home launch projection is not: the desktop's existing local transport supplies the Windows lane. Platform compatibility is necessary but does not override an unsupported launch projection or custody backend.

The caller's standing instruction authorizes these choices. No further product approval is needed to implement this plan. This Plan dispatch changes documentation only; tests below are required future work, not claimed results.

## Decisions

### D-1. A requirement is a domain enum; omission is distinct from Any

Add `server/Domain/Enums/RequiredPlatform.cs` with stable values `Any = 0`, `Windows = 1`, `Linux = 2`. Add non-null `RequiredPlatform` to `AgentTask` and `Card`, default Any. Add nullable `RequiredPlatform?` to `CreateAgentTaskRequest` and card content PATCH; JSON uses the existing string-enum convention. A new card defaults to Any. PATCH omission/null preserves the current card value; an explicit Any resets it. Reject invalid string/numeric enum values through the established validation/Problem Details path, never silently coerce them to Any.

Resolve a task requirement after its authoritative card binding and existing-process resolution, before provider probes, worktree fetch/preparation, custody reservation, task insertion or prompt enqueue:

1. Explicit request value, including Any.
2. For `FollowUpOnTask`, the prior task's frozen value when the request omits it, including when the delegate has retired and a fresh continuation is made.
3. The resolved bound card's value.
4. Any.

Do not inherit a random caller/parent's platform merely because it created the task. A fresh pipeline stage bound to a card reads that card's current default. Retry/resume of the same task retains its frozen requirement; editing the card never changes queued or running tasks. Internal repair/relaunch/reconciliation task constructors must carry the source requirement when they continue the same work, or resolve the bound card for genuinely new work. Audit the direct `new AgentTask` paths in `AgentTaskService`, `SpecialistRequestService`, `SpecialistTaskRunner` and `AgentTaskLandService`; do not let CLR defaulting silently erase a continued requirement. Specialist tasks cannot gain a new remote lane from this feature.

Persist requirement provenance (`Default`, `Card`, `Request`, `FollowUp`) with the task, plus the create-time observed runner platform (nullable Windows/Linux, never Any as an observation). Legacy tasks backfill Any/Default with unknown observation. The Created audit includes requirement, source, canonical selected runner, reported platform and placement reason. Summary, detail and create response expose the frozen requirement and selected runner; do not reconstruct old choices from today's card or registry. Card content revisions record the superseded default, following the existing verification-policy revision convention. Historical revisions remain null/unknown.

This is a default for **AgentTask creation**, not a new prohibition on all card-associated `AgentSession` starts. Existing direct card-start behavior remains governed by its existing launch path; the UI labels the field “Default task platform.”

### D-2. First-class desktop identity without a storage migration of runner ownership

Reserve `desktop` as the public catalogue ID and display name “Desktop”; accept both `desktop` and `local` case-insensitively, with the existing outer trimming. Preserve `RunnerRequestSource.ExplicitLocal`. Persist local task/agent/session `RunnerId` as null exactly as today. Keep `PhoneHomeProtocol.LocalRunnerId = "local"` as the existing transport/internal token. A single normalizer maps the public name, internal sentinel and legacy null at boundaries; no new persisted `RunnerId="desktop"` or `"local"` rows.

Remote IDs retain their existing ordinal matching. Settings reject IDs that are blank, over 64 characters, contain controls, collide with desktop/local (any case), or duplicate another ID ignoring case. Canonical IDs and display labels are different; do not resolve an arbitrary display label as an ID. Catalogue/task DTOs display the canonical `desktop` for stored null. Runner-specific endpoints accept both aliases; an unknown ID returns 404 instead of a fabricated singleton status.

### D-3. Platform evidence comes from the executing runner

Extend `RunnerCapabilitiesDto` additively with optional `Platform`, using canonical wire strings `windows`/`linux`; unknown OS produces null, never “not Linux therefore Windows.” Share the OS-to-wire helper between local `/capabilities`, `PhoneHomeRuntimeAdapter.Capabilities` and phone-home registration. Normalize case on reads. A remote descriptor uses its registration Platform; if new capabilities also report Platform and disagree, reject registration with 409 `runner_platform_conflict`. Omitted new fields remain compatible with old runner payloads. Unknown/missing platforms cannot satisfy a specific requirement; Any does not invent platform evidence.

Expose runner descriptors through the external I/O seam `ISessionRunnerDirectory` (e.g. `DescribeAsync(id, ct)` and a snapshot enumeration) with canonical ID, display name, platform, evidence time, transport, enabled/dispatch-eligible state, capabilities and declared capacity. Remote reads use directory registration state, not a probe of every runner. Local reads obtain the local runner's `/capabilities` through `ISessionRunnerClient`, with a bounded timeout before any database claim; never query a configured remote as a substitute. UI reads may use a short bounded cache; launch validation must use current evidence or the runner-side guard below.

Retain last registration metadata within that runner's state for offline display, explicitly marked stale. It is not current eligibility. A server restart with no registration produces unknown metadata until recovery. Do not add an OS setting that can override the runner's report.

### D-4. Deterministic placement and refusal table

Extend the existing routing policy rather than layering a second policy after it has inserted a task. Keep intent until placement is final. Factor the shape checks so remote selection always observes `ExclusionFor`/explicit admission, and matching local placement remains possible for local-only shapes. The requirement neither changes kind/tier nor converts Shared/ReadOnly into Worktree.

| Requirement and runner intent | Placement / refusal |
|---|---|
| Any, omitted/blank runner | Try eligible per-kind runtime default, then eligible global runtime default, then desktop with existing exclusion/fallback warning behavior. No round-robin scan of other runners. Null global means built-in fallback; an absent kind override means inherit. |
| Windows/Linux, explicit desktop/local or remote ID | Resolve only that runner. Known opposite platform: 409 `runner_platform_mismatch`, with required platform, canonical runner and observed platform in safe detail. Never try another host. |
| Windows/Linux, named runner with unknown platform | 409 `runner_platform_unknown`; no inserted task. An offline runner with a last-known matching platform can remain a queued explicit choice, but cannot dispatch until it has current matching evidence and required capabilities. Known opposite metadata still gives mismatch. |
| Windows/Linux, no named runner, existing process/pin | Validate the resolved process's actual session/agent binding. A match retains that process; a mismatch is the same 409. The requirement cannot provision a replacement or bypass existing remote OnAgent/pin refusals. |
| Windows/Linux, fresh task, eligible matching runtime default | Filter by requirement first; try per-kind default, then global. Select the first matching eligible default. Full runners remain eligible for selection; capacity governs queueing, not a host substitution. |
| Windows/Linux, fresh task, both defaults absent/ineligible/wrong platform | Select matching eligible desktop, otherwise matching eligible configured remote runners in ordinal ID order. Exclude disabled, unrecovered, unknown-platform, unsupported shape/projection and (for new specific-platform launches) missing-enforcement-feature candidates. |
| No eligible compatible candidate | 409 `runner_platform_unavailable`, with bounded candidate exclusion reasons; no cross-platform fallback or provisional task row. |

For today's Windows desktop and Linux server2, Windows selects desktop and Linux selects server2 for an automatically admitted shape. A second Linux runner can satisfy Linux when the configured default is unavailable. An explicit unavailable runner is still pinned and may queue under the existing availability rules; named selection is not a request to replace it. Unknown runner/config-disabled errors remain the established validation errors; do not change their HTTP contract just to implement the mismatch 409.

Ordering: validate input/card/identity and resolve kind/workspace; for a known explicit target check platform mismatch before provider login/capacity and remote shape errors; then run its existing shape checks. Automatic candidates are filtered by both shape and platform. Propagate unexpected directory exceptions and cancellation; only known eligibility refusals exclude a candidate. Existing-process conflicts must be checked before any side effect in the follow-up branches, even where those branches currently precede the normal create placement block.

**Codex boundary (amended):** `-Kind Codex -Platform Linux -Worktree` may select a matching runtime default or matching fallback without `-Runner`. An Any Codex worker may inherit global server2, or use an editable Codex desktop override. Keep the existing explicit lane's auth, executable/projection and transcript/capability checks. Do not silently switch kind or admit a Codex orchestrator, specialist, named-agent or SourceLanding shape. SourceLanding for supported kinds still asks the selected runner for real custody support and refuses rather than falling back. D-10 specifies the shared worker compatibility rule.

### D-5. Bind once and defend at dispatch and at the runner

Persist the selected host at creation. Card/config/default edits, retry, provider reroute, capacity wait and reconnect cannot move it. Before claim/mirror preparation, and again immediately before delivering work to a reused process, validate the frozen requirement against that binding. A known new mismatch becomes Blocked with `runner_platform_mismatch` and no launch/input; temporary unavailability leaves Queued with the existing runner hold. Unknown evidence for a specific requirement holds until evidence arrives. Retry revalidates; it cannot reset requirement to Any. Any retains existing behavior.

Close the metadata-to-launch race: add an optional wire requirement to `RunnerLaunchRequest`, mapped from an additive `AgentLaunchSpec` field in both `RunnerContractMapper` and the local `SessionRunnerHttpClient` construction path. Keep contracts independent of server Domain: use canonical platform strings/null at this wire boundary. Advertise `required-platform-v1` in local and phone-home capabilities. `SessionRunnerRuntime.StartAsync` validates the actual OS against a non-null requirement before session creation, custody mutation, Grok file materialization or child launch, returning a typed 409 mismatch. Invalid wire values refuse validation. This same guard covers both transports. Preserve the field in remote projection and relaunch specs.

A specific-platform **new launch** requires this feature; an older runner without it returns 409 `runner_platform_enforcement_unsupported` at admission, or holds if it downgraded after admission. An existing process needs positive matching platform/binding evidence before task input, not a pretend relaunch. Any and old requests with no field stay wire-compatible. The runner guard is required because a runner restart between preflight and launch must not turn a hard requirement into advice. Revalidate the accepted connection/store identity when remote preparation becomes a session binding; do not capture an unkeyed last-live store.

An optional field alone is insufficient for the downgrade case: an old binary can ignore it after a cached capability check. Specific launches therefore use a new local route `POST /sessions/platform-constrained` and an additive phone-home `LaunchPlatformConstrained` operation (append a numeric enum value; do not renumber existing operations). Both require a specific valid wire requirement and invoke the same guarded launch implementation, including its existing capacity/adoption/generation/credential checks. A 404/unsupported operation is an enforcement refusal, never a retry through legacy `/sessions` or `Launch`. Any keeps the legacy transport. Tests exercise an old endpoint/dispatcher after a previously positive capability response, proving zero legacy-start calls. Retain the platform guard on ordinary StartAsync too when a requirement is supplied directly.

### D-6. Multiple runners means independent configuration and lifetime

Add `PhoneHomeRunner:Runners`, a map keyed by remote ID, with a typed entry containing `Enabled`, `DisplayName`, `AllowDelegatedTasks`, `StandingAgentId`, `HostWorkspaceRoot`, `RunnerWorkspace`, `RunnerRepository`, `RawExeAllowList`, `MaxCapacity`, child homes, auth-probe flags, `CallbackOrigin` and `SharedSecret`. Global enablement, ticket/heartbeat/lease/retry/refresh/limits and the operator-token policy remain global. Entries use the current Linux projection; Windows remote registration does not make that projection Windows-capable. Its task eligibility reports unsupported projection instead of executing POSIX commands on Windows.

Compatibility rules are explicit: with an empty map, normalize the existing singleton keys into exactly one entry with the existing ID and settings. With a non-empty map, it is authoritative; legacy singleton values (including their defaults) are ignored with one non-secret deprecation warning. Do not union the two sources or unexpectedly accept `grok-linux`. Validate every enabled entry at startup, including unique pinned standing-agent IDs. Root `Enabled=false` still disables phone-home. Keep legacy fixtures through the normalization path while adding multi-entry fixtures.

Each explicit entry has its own secret in existing protected configuration; there is no new shared credential fallback. Registration authentication takes the requested runner ID and checks only that entry's secret with the existing constant-time comparison. Invalid/unknown ID and wrong secret do not reveal configuration details. Tickets remain single-use and bind ID/store/boot/epoch. Do not print secrets, hashes, home contents or settings objects. Legacy mode continues to accept its one existing secret, without rotation or deployment during Code.

Replace singleton connection fields with per-ID state objects: live and last-recovered connection, store/boot, lease reservation, epoch, disconnect record, reconnect count, registration metadata, bootstrap inventory/cache and ticket ownership. Register/connect/disconnect on A may never replace B. `GetInventoryAsync`, `Status`, provider auth, capacity and store lookup must use the requested ID. Replace `LiveStoreId` with `GetLiveStoreId(runnerId)` (or an equally explicit descriptor-bound lookup) and update every implementation/fake/consumer. No compatibility accessor may choose the “first” runner.

The recovery service maintains independent pump, cancellation, catch-up retry and refresh state for each connection. A slow or failed catch-up on A cannot block B's events, recovery or availability; use bounded independently owned work, with cancellation/join on replacement/shutdown. Preserve catch-up-before-dispatch, negative-owner cache, unknown versus gone, per-generation tombstones and in-flight error semantics. Union live/unknown session sets across runners only after each runner classifies its own inventory. `PendingRunnerSessionInventory` must key its single-flight snapshot, failure and five-second TTL by ID; its present method parameter is insufficient. Active persisted bindings to a removed/disabled runner remain remote and unknown until an authoritative absence/operator action; retain read-only binding knowledge even when the entry no longer admits connections. Configuration removal alone must not make reconciliation fail or kill those sessions.

Pass the selected entry into launch projection, provider-home diagnostics, named-agent admission, worktree mirror preparation and `VerificationWorkspaceDirectory`. `AgentControlService` resolves a pinned standing agent to exactly one entry, or uses the agent's own RunnerId; it cannot assign a global AllowedRunnerId. Slot counts, deferred kills, recovery events and verification receipts remain keyed by runner/store/session generation. Existing desktop canonical worktree and remote mirror ownership do not change. Removed/disabled entries refuse new work and never reroute old bound sessions to desktop; they do not trigger automatic kill.

Use the same population as dispatcher accounting, excluding specialist/retained-capacity cases. Remote `capacityKind` is `sessions`. Unknown/stale occupancy is null/marked stale rather than zero. Runner options start with Automatic (omit runnerId), then Desktop and the returned entries with OS, occupancy/capacity and availability. ### D-9. Runtime settings, transactional revisions and API

Add a fleet-wide `RunnerRoutingSettings` aggregate, independent of model routing pins and TUI profiles. Store it in PostgreSQL through `AppDbContext`: one fixed-key `RunnerRoutingSettings` row (`Revision`, nullable `GlobalRunnerId`, `UpdatedAt`), a `RunnerKindDefaults` child table unique on `(SettingsId, AgentKind)` with non-null canonical `RunnerId`, and append-only `RunnerRoutingRevisions` unique on `(SettingsId, Revision)`. Each revision stores the complete global/ordered-kind snapshot, previous revision, UTC time, required bounded reason (1-400 characters), asserted `Human|Auto|Migration` provenance and server-derived caller task ID when present. No provider secrets, executable paths or runner connection configuration belong in this resource. Follow existing domain/DTO/service/EF conventions; migrations are CLI-generated.

In these settings, `desktop` is a real default value; null global means use built-in fallback and an absent per-kind row means inherit global. This differs deliberately from task storage, where selected desktop remains null. Normalize `local` to `desktop` on settings writes. Duplicate/undefined/numeric agent kinds and blank/invalid IDs are 422 validation errors. Kind keys are the actual `AgentKind` enum, not tiers, aliases or display names. A default does not grant that kind a launch shape it otherwise lacks. Choices may be any configured catalogue runner, including a registered runner currently offline; unknown IDs are rejected on new writes. A previously saved runner that disappears stays visible as an unresolved reference, with history intact and an exclusion reason at selection. An unchanged legacy unresolved reference may be retained while editing other fields; a newly introduced unknown reference may not.

Use a new `RunnerDefaultSettingsService` and `RunnerDefaultEndpoints`; do not change the semantics of `PUT /api/routing-pins` or invent a special role/card pin for fleet defaults.

| Route | DTO and contract |
|---|---|
| `GET /api/runner-defaults` | `RunnerDefaultsDto`: `revision`, `globalRunnerId`, ordered `kindDefaults: [{agentKind, runnerId}]`, `updatedAt`, last writer/reason, `supportedKinds`, and unresolved-reference warnings. Include per-kind inherited preference/source for display; this is not a guarantee that a task's platform/shape will accept it. |
| `PUT /api/runner-defaults` | `PutRunnerDefaultsRequest`: required `expectedRevision`, required nullable `globalRunnerId`, required complete `kindDefaults` array (empty clears all overrides), required `reason`, and `provenance: Human\|Auto`. Missing required fields refuse instead of accidentally clearing settings. Return committed `RunnerDefaultsDto`. A complete replacement is one atomic edit; the UI sends the fetched snapshot with its revision. |
| `GET /api/runner-defaults/revisions?beforeRevision=<n>&limit=50` | `RunnerDefaultsRevisionPageDto` with descending immutable snapshots and next cursor; bound limit to 1-100. Revisions include before/after identity and writer/reason. To restore an old snapshot, PUT its values with the CURRENT expected revision and a new reason; history is never rewritten. |

Use the existing routing-pin request authorization/caller-resolution path, with no new approval workflow. As with pins, Human is the caller's assertion that an operator requested the edit, not an authenticated user identity; task attribution comes from the server, not JSON. Auto may not replace an aggregate whose last effective edit is Human (`409 runner_defaults_human`); normal UI edits are Human. Migration is internal-only. Failed validation, stale revision (`409 runner_defaults_revision_conflict`) or provenance refusal creates no new revision/event. Concurrent writes from the same expected revision yield exactly one winner through EF optimistic concurrency plus a database transaction. Compare canonical snapshots: a no-op with the current revision returns the existing row and adds no revision. Initial revision is 1; expected revision 0 is only for internal initialize-if-absent, not an API reset.

Commit current state and its immutable revision together. Read current revision plus its immutable complete snapshot in one database projection; independent current-row/child-list reads under read-committed isolation could mix revisions. Publish `RunnerDefaultsChanged {revision}` through `IEventBus` after commit and map it to TanStack invalidation of `['runnerDefaults']` and `['runnerDefaultRevisions']`. Successful local writes invalidate both queries as well. A lost event cannot make placement stale: create reads a fresh authoritative committed snapshot; the UI also refetches on mount/focus and stale saves 409. An event failure must not roll back or duplicate a committed revision on retry. Revisions are the durable audit; a separate mutable log line is insufficient. Endpoint validation/refusals use the established `HttpException`/Problem Details hierarchy.

### D-10. One create-time precedence chain; no Codex-local exception

The precedence is **explicit task Runner; hard RequiredPlatform constraint; per-kind default; global default; existing fallbacks**. Explicit Runner is the only candidate, not permission to violate RequiredPlatform: an explicit mismatch is 409. With no explicit Runner, RequiredPlatform filters each preference before it can win. Resolve effective kind after model pins/complexity routing, then read one complete settings revision for that creation; never choose a location from a pre-pin requested kind or mix global and per-kind values from different revisions.

Apply D-4 in this order, deduplicating canonical IDs:

1. Existing process, standing pin or retained follow-up binding stays on its actual runner and must satisfy the requirement. An explicit contradictory runner still refuses through the existing conflict contract. Runtime defaults cannot relocate that process.
2. For fresh work, resolve an explicit runner alone and validate requirement/shape using D-4/D-5.
3. Otherwise try this effective kind's configured default, then global, using current directory eligibility and the platform/shape filters. A per-kind choice overrides global when eligible. A platform mismatch on a default excludes that candidate; it is not an explicit-target 409 while another compatible candidate exists.
4. If neither preference qualifies, use D-4's existing Any desktop fallback or specific-platform matching-desktop/ordinal-remote fallback. Exhausting a specific requirement is 409 `runner_platform_unavailable`. Record why preferences were excluded. Full capacity queues on the selected eligible runner; provider sign-in/quota failure is still its launch refusal and must not trigger a lower preference or another kind. Unexpected directory/database errors and cancellation propagate.

Examples: global server2 + no overrides sends supported Any Grok/ClaudeCode/Codex workers to server2. Codex=desktop overrides that for Any; Codex+Linux excludes desktop and selects global server2. Global server2 + Windows selects desktop when it is the compatible eligible host. Explicit server2+Windows is 409 even if desktop is available. Per-kind offline A + eligible global B selects B with an audited exclusion; explicit offline A remains A and may queue. Global desktop is an affirmative desktop preference, while null global defers to the built-in rules.
