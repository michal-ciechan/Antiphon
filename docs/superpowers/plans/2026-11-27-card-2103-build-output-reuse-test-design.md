### Delivery inventory

The new local path is checkpoint producer → existing timing spool → existing finalized timing shard → bounded replay reader/classifier. Its durable identity is `(producer, task, attempt, run, build, event kind)` plus the stable event ID, payload digest and original UTC bound. Persist at the existing staged/flush boundary, outside the slot and receipt-authority path. A fresh reader must return the exact event ID and fields, and the reducer must attribute it to the matching build attempt. A spool file, append response, diagnostic line or flush acknowledgement alone earns no credit. Use the existing on-disk queue in CP-2 with three acknowledged cuts: shard gate busy with a pending spool record, already committed and visible, and after staging before append/after flush before ack. Reopen independently, invoke the real spool import and read the finalized shard. Repeated import yields one event. Inject pre-spool failure too. There is no recoverable record at that cut, so the reader returns named missing coverage with null data. Use `TimingJournal.Fault` and barriers as crash-cut substitutes for a killed process. S0 introduces no session input, message queue, server upload or external delivery. No `UserPrompt` is owed. The live broker and authenticated custody readers are inputs to this path. Their absence is a visible measurement failure.

Before starting the measured observation week, do one bounded, read-only data-path check for each selected authority using a naturally occurring build. For broker input, reuse CARD-2117 LP-1 for the physical authority and require that the same ordinary build's grant and release can be read by bound lease and generation from an authorized history/retained source. For custody input, require an authority-owned read for a recent bound build/output generation, with original UTC validation and existence evidence covering a known request and a corresponding release/cleanup fact. Run the replay reader and retain the same build and lease IDs and its typed verdict from each source. A 405, missing source, stale/unverifiable binding, missing paired identity or missing as-of evidence fails the coverage probe with its source, reason and null metric. Use three reads at most, three seconds per HTTP read where supported, and a 30-second hard probe allowance. No live builds, extra polls per checkout, deployment or authority change. If those sources remain unavailable on a lane, retain its actual attempts and explicit unknown coverage. That lane cannot produce a qualified reuse rate or begin the enablement observation week. Fixture positives prove the consumer handles both sources; live readback certifies deployment reachability.

### Guards the regression

- R-1 — CP-1 rejects SHA-only matches, unknown inputs, future success, failed/canceled predecessors, stale or unauthenticated custody and absent output at the actual request. Run the same method once red first and once as CP-1 on the final implementation.
- R-2 — CP-2 compares executed command vectors, lease trace, receipt bytes, tests and exits. Sink failure keeps the failure red and the green fixture green. The enabled arm must actually write observation evidence.
- R-3 — CP-2 requires a loud coverage failure for unreachable broker history and unreachable custody evidence separately. Missing hold seconds never enter a sum as measured zero. Keep the existing slot-call regression in CP-8.
- R-4 — CP-2 proves receipt of the actual journal record after recovery, deduplication and bounded truncation. A missing record must be classified independently of the product verdict.
- R-5 — CP-3 and CP-4 keep terminal and anchored-receipt behavior. The exact new CP-4 provenance method holds adjacent checks constant so passing count/SHA validation cannot conceal an unverified build. The count-token witness asserts `receipt_counts` on an otherwise matching project receipt.
- R-6 — CP-8 and CP-9 keep the admission/release and ledger order witnesses. A source change at release must stay `refused: tampered` and no dependent row may turn green.
- R-7 — CP-5 through CP-7 bind executed membership separately from policy floor counts and retain the source-class and process-spawn guards. These are qualification roster checks.
