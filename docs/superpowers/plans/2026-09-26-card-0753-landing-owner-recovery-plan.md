# CARD-0753 + CARD-0603 + CARD-0675: recover a reviewed landing source

Date: 2026-09-26. This is one plan for the three cards. It builds on the unlanded [CARD-0684 adoption plan](2026-09-25-card-0684-conflicted-land-and-adopt-repair-plan.md), especially D-6 through D-9, and updates its admission rules for terminal owners. Code is unchanged by this investigation.

## Findings

The runner settlement has three immutable or observed commit identities: **B**, the task's primary local SHA captured at dispatch in `ProgressBaselineJson`; **S**, the exact fetched tip of `refs/heads/feat/card-task-<task-id>` at the configured origin; and **L**, the registered desktop worktree's HEAD. `RemoteWorkspaceService.SyncOwnedCheckoutAsync` checks the endpoint and checkout identity, pins S, then requires `B == S` or `B` to be an ancestor of S. Only after that does it require `L == S` or L to be an ancestor of S and fast-forward L. A force-push after rebase rewrites commit identities: even if the file changes are equivalent, the old B may not be in S's ancestry. Then `runner_sync_diverged` is the **B versus S** refusal. Resetting the desktop mirror to S changes L only, so it cannot clear that first refusal. This explains the reported `ce55c8ef` sequence; its report says desktop and origin both reached `9b7ef957`, while task status still records `runner_sync_diverged`. `6ca40cd0` has the same recorded reason. The exact B values were not available from the status presentation, so the specific graph for those tasks should be confirmed from their stored progress evidence before a live recovery.

`TaskCompletionProgressService.EvaluateRemoteAsync` next requires a Code task's reported claim C, if any, to be reachable from S and novel against both captured baselines. It finally classifies S itself against those baselines. A fresh Code task started at an already reviewed tip that only re-verifies and pushes that same tip has `S == B`: it has no attributed *new* Code progress. If its report includes C, the `NoPushedProgress` arm emits `runner_reported_commit_not_pushed` even when that same C is visible on origin. The code means **no new pushed progress for this task**, not necessarily a missing remote object. `cf6b1915` reported `023f2ac2` on its own remote branch and still settled Failed with that reason; its report also says its push was already up to date. `ac059bce` is a different example: its stored reason is `runner_sync_lease_busy`, so it must not be counted as a force-push divergence reproduction.

A refused or unavailable runner sync produces indeterminate progress and blocks an otherwise successful runner settlement. A definite no-progress Code result can fail the task. Landing then has independent gates: `AgentTaskLandService.RequestAsync` requires `Succeeded`, refuses every `RepairSourceTaskId` with `repair_source_landing_owner_required`, and `RunEnsuredRequestAsync` plus `AgentTaskLandingProtocol.RecheckSourceAsync` recheck eligibility. The schema-3 source resolver reads the owner's branch ref and its remote; ordinary landing refuses `source_remote_diverged` when local and remote refs differ by rewritten ancestry, and `reviewed_source_mismatch` when the reviewed SHA belongs only to a `-StartRef` repair's branch. The `-RepairSource` task has attribution to the owner but no landing authority. The `-StartRef` task owns a different branch and has no automatic adoption path.

Today the supported product path is a **fresh ordinary Code/Worktree task** from the exact desired SHA, which makes a real relevant commit, pushes its *own* branch, settles Succeeded, gets Clean Review on that branch/tip, and lands as that new owner. If its report pushed a sibling branch, the caller must first correct the own-branch push; CARD-0603 records this workaround and a separate stale Unconfirmed operation failure. A `-RepairSource` success cannot make a terminally Failed owner landable; manual force-push of the owner branch can cure source-ref mismatch, but cannot cure the status gate. `-StartRef` without new Code progress is not a re-ownership mechanism. The manual reset/force-push used for CARD-0675 is not a supported landing API recovery. The CARD-0684 adoption design is a plan, not a current operation.

## Decision: explicit reviewed-source recovery

Implement CARD-0684's `-FromTask` adoption and request supersession as the **single recovery lane**, with these changes to its D-6/D-7 rules. Keep automatic runner settlement fast-forward-only; do not silently bless a force-pushed S or rewrite history merely to turn a report green. Do not mutate historical task status to Succeeded. A recovery land remains explicitly commissioned, tied to one full SHA and a Clean Review outcome, and owned by the original Code task.

1. **Admission.** Extend `POST /api/agent-tasks/{owner}/land/v2` and `delegate.ps1 -Land` with `-FromTask <task-id>` (adopt another task's pushed branch) and `-RecoverReviewedSource` (use the owner's already pushed branch). The latter is a distinct, explicit recovery flag, never the default `-Land`. Permit an owner whose status is Succeeded, Blocked, or Failed only in this lane; a Canceled owner remains ineligible. Require Worktree Code owner, exact full `expectedSourceSha`, explicit `reviewEvidenceId`, Clean non-Interim Review that completed Full scope, and no superseding Review. If `RequiresFinalVerificationReview`, retain the existing Final/Full gate. An ordinary Succeeded landing remains unchanged. Reject pending Queued/Held/Running requests; supersede a NeedsResolution request with a new durable row as CARD-0684 D-6 describes. Never reinterpret an old failed or pending operation in place.
2. **Evidence and source.** For self recovery, the Review evidence subject/ref/repository must be the owner and S must equal its *current exact remote branch tip*. For adoption, the evidence must bind to the source task's own branch and S; source task may be Succeeded, Blocked, or Failed, because Review and remote source are the authority in this lane. Require same card/project, same git common directory, Code/Worktree, and recorded start-base provenance from the owner or its superseded request as CARD-0684 D-8 describes. Never accept a free SHA, foreign branch, Mutation/SourceLanding task, or an unpushed repair claim. A `-RepairSource` task remains forbidden as a land target; if its work is on the owner's remote ref, use self recovery with owner-bound Review. A `-StartRef` repair uses adoption with Review bound to its own remote ref.
3. **Source transition.** Reuse CARD-0684 D-7's request journal, lease, pins, identity checks and `--force-with-lease=<owner-ref>:<observed-remote-sha>` for adoption. Account for current schema 3: the landing protocol reads a source ref and works in a detached land worktree; do not use the old schema-2 `source-ff` assumption. For self recovery, remote already equals S: no push. If the owner local branch is stale, update it to S only under the same journaled, pinned, lease-held adoption path, after proving the registered worktree is clean and on its branch. Any local unique commit is pinned and surfaced; refuse unreviewed or actively written local state. CAS-check the local ref, re-observe the remote, and stop if either changed. An interrupted transition resumes from its saved child-operation checkpoint. A force-push race refuses before publication. The ordinary resolver and `LandOperationFactory` then see owner local and remote at S; the normal detached rebase, verification, target push, publication receipt, and guarded cleanup run without a second landing implementation.
4. **Status and audit.** The request and landing receipt carry recovery mode, original owner ID/status, source task/ref/S, B/L before adoption, owner remote before and after, Review evidence ID, superseded request ID, and source adoption relationship. `RunEnsuredRequestAsync`, `RecheckSourceAsync`, `RecheckApprovalAsync`, retry and cleanup must use the persisted recovery authority rather than a later task status flip. An unconfirmed previous publication is resolved by the existing publication recovery rules before a new request; do not paper over CARD-0603's stale Unconfirmed 500 with this status exception. `Landed` still means confirmed target containment, not merely a successful source force-push. Document the new operation in `docs/orchestration-loop.md` and `docs/ops-http.md`; status output names the adopted source and exact reviewed SHA.

This is smaller than relaxing automatic runner sync plus inventing a status rewrite: the existing landing protocol, review binding, remote observation, detached verification and publication remain the only path to the target. It extends CARD-0684's already planned adoption rather than adding another source-selection mechanism. If CARD-0684 R2 is implemented first, implement only its terminal-owner/review-source deltas and self mode here; do not build two adoption paths.

## Slices

- **S1 — recovery request and evidence.** Add durable recovery mode/source fields to request and receipt, CLI parameters, and admission/recheck rules in `AgentTaskLandService`, `LandApproval`, `AgentTaskLandingProtocol`, DTOs, and the request writer. Use CLI-generated EF migration. Preserve ordinary `-Land` and the repair-task refusal. Define clear 409 codes for missing/stale Review, wrong subject/ref, ineligible status, live request, foreign source, and unconfirmed operation.
- **S2 — source transition.** Implement CARD-0684 adoption against current schema 3 in `AgentTaskLandSourceResolver`, `LandOperationFactory` and landing Git seam. Add self recovery as the no-push case. Pin B, L and remote-before; journal CAS reset/ref advance and source push; recheck the exact remote tip/fingerprint before operation creation and again before target push. Keep cleanup authority on the owner worktree/branch; never delete the source task's worktree as a side effect.
- **S3 — visibility and contract.** Print recovery provenance in task status and landing outcome, update `delegate.ps1`, `docs/orchestration-loop.md`, `docs/ops-http.md`, and `docs/session-runtime-invariants.md`. Amend CARD-0684 D-7 admission text when this ships so operators have one contract. Track CARD-0603's stale Unconfirmed 500 separately if it remains reproducible; no broad stale-operation rewrite is authorized by this plan.

## Verification design

Write V-3 through V-10 red against the production line they guard; V-1 and V-2 are existing-behavior controls. Use real Git for ancestry, remote movement and cleanup; mock-only success cannot prove the landing invariant. Process-spawning tests retain their assembly-local `ParallelLimiter<ProcessSpawnLimit>`. Run the checkpoint tool once per committed slice group and wait through exit 75. The table is the Code round's closed build/test list; Review checks the actual counts and failures.

- **V-1** `RunnerSettlementSyncTests`: B and S diverge after force-push while L is reset to S; sync still refuses `runner_sync_diverged`, with B/S/L evidence unchanged. **V-2** `RunnerCompletionProgressTests`: S=B and claim C=S yields no new Code progress, including when C is a real remote tip. These protect the deliberate automatic guard.
- **V-3** land admission: Failed/Blocked owner plus exact Clean Full Review can queue explicit self recovery; plain `-Land` still refuses; Canceled, missing/superseded/Interim/wrong-ref/wrong-SHA Review and mutation source refuse with no request. **V-4** repair target still refuses, while a Failed original owner can adopt a reviewed repair source. **V-5** an existing NeedsResolution row is superseded atomically; a live land or unresolved publication is not bypassed.
- **V-6** real Git: stale owner local ref, reviewed self remote S rewritten from B; recovery pins and advances owner source under lease then lands S; ordinary resolver still refuses. **V-7** real Git: `-StartRef` repair branch S is reviewed; adoption force-pushes owner ref with lease, records both refs and original status, and lands through the owner. **V-8** remote race, dirty or replaced checkout, local CAS race, failed force-push, restart between reset/push and between source transition/publication refuse or resume without target publication on stale evidence. **V-9** cleanup removes only the owner branch/worktree when safe, retains a repair branch, and an already published outcome resumes cleanup without a second target push.
- **V-10** CLI and documentation: `-FromTask`/`-RecoverReviewedSource` send full SHA and Review ID only to `/land/v2`; error exits cause zero POSTs; status displays source and recovery receipt. **R-1** existing ordinary land, CARD-0684 adoption, repair-source refusal, source freshness and runner sync tests stay green.

## Risks and rollout

- **History replacement:** source adoption changes the owner's remote ref. Its observed old tip and every local tip must be pinned before CAS mutation; a rejected lease or stale Review leaves target untouched. Keep the original owner and source task branches until the landing receipt proves publication/cleanup.
- **Status bypass:** the exception applies only to the explicit, persisted, exact-SHA Clean Review recovery lane. Repeat the gate before each unpublished mutation and after restart. Never make `Failed` generally landable.
- **Review identity:** CARD-0684 allows Review on owner or from-task. This plan tightens it to the **actual source ref** at S. Old owner Review cannot approve a different repair branch merely because its SHA is named in prose; commission a fresh Review if necessary.
- **Overlap:** CARD-0684 already plans supersession and adoption. Land its R1 prerequisites first or fold them into this Code round; reconcile its R2 fields and tests before implementation to avoid duplicate migrations. Current schema-3 landing changes supersede its schema-2 reset assumptions.
- **Activation:** after publication and server restart, verify `/api/version` SHA and `land-v2` before relying on the new API. A healthy server alone is not evidence that the recovery endpoint is active.
