[GH-63](https://github.com/michal-ciechan/Antiphon/issues/63) and the Antiphon board's CARD-2110 have the same acceptance criteria. Code and sibling diffs were read against fetched `origin/master` at `d737c5b4226e5a3693af80ea451a597b3075a48a`. The plan branch stays on its assigned ancestry. The [review engine design](../../features/012-review-engine/design.md), [API contract](../../features/012-review-engine/api.md) and [operator guide](../../features/012-review-engine/getting-started.md) own the shipped behavior.

## Ground truth

| Card premise | Behavior on the inspected master |
|---|---|
| Publish is hard-wired to verification and builds a fixed body. | `ReviewReviewSteps.PublishAsync` calls `LatestOf("CollateFindings")` and `LatestOf("VerifyFindings")`. Missing verify output passes the collated candidates through. Verify can supply usable output on `Skipped` or `FailedContinued`. Publish persists findings, applies `ReviewRoundsPolicy.Place`, and calls `PostReviewAsync` only when the target supports PR reviews and there is at least one inline or summary-only finding to post. The fixed body lists both groups, gives the below-bar count and includes the verifier note. `CommentBody` formats inline posts separately. |
| Publish can show data the run page already has. | `ReviewIntakeSteps.CategoriseAsync` returns `CategorisationOutcome` for this iteration. The run page's six blast scores and categories accumulate on `ReviewRun` (maximum score, category union). `ReviewSelectionSteps.SelectChecksAsync` records `SelectOutput`, including usable trigger-based selections on degradation. `client/src/features/review/reviewMeta.ts` labels the six scales. |
| YAML can describe a generic prompt. | `ReviewWorkflowYaml` and `WorkflowGraphDto` already carry a params map. `ReviewNodeKind.Completion` dispatches a registered C# step, such as `VerifyFindings`. Gates, waits and fan-out dispatch by kind, and fan-out owns its agent child. A work node with an unknown step reaches a runtime failure today. |
| A named input can be read in the active graph. | `ReviewWalk.Latest(id)` finds the highest-sequence top-level execution of that node ID in the current iteration by default. Its status and output still need checking. The executor resolves the stored run graph and starts a fresh iteration on edges back to entry. Waits and bounded edges elsewhere can revisit a node ID within one iteration. |
| Completion, failure and usage already have an execution path. | `CompletionChain` walks configured `Review:Completions` entries and returns the first adapter response. Rejected requests stop provider traversal. Verify parses its own response after that traversal. The executor applies effective `onFailure` and records node usage plus run cost. `ReviewNodeExecution.Kind` is a length-32 string column, graphs and outputs are JSON, and there is no per-call review ledger table. |
| The Workflow tab is the authoring surface. | `WorkflowTab.tsx` shows an immutable revision and invokes the graph validator. `NodeSidePanel.tsx` reads raw params and execution rows. Master creates the embedded revision at intake. GH-62 owns editable drafts, save, scope selection and revision assignment. |

## Decisions

| ID | Decision and reason | Alternative considered |
|---|---|---|
| D-1 | Declare a publish node's sources in `params.inputs` with case-sensitive node IDs. Bind by known producer contracts and require one collate and one verify source when the list is explicit. This keeps verification and finding provenance unambiguous. Omitted `inputs` retains the previous lookup and fallback for stored graphs. | Positional inputs are fragile on reorder. Matching by output keys or scanning the latest same-step execution could pick a different branch's output. |
| D-2 | Add `kind: prompt` (`Prompt` on the wire) as completion work using a named `Review:Completions` chain. Allow tool-free HTTP and one-shot CLI adapters only. The example uses `completions-cheap`. Keep creation of this node opt-in so upgrading the server adds no model calls to existing workflows. | Agent seats would add tool and session custody concerns. A new named `run: ComposeSummary` would require server code for the next prompt use case. A decision chain answers typed questions and has different escalation semantics. |
| D-3 | Use one pass of bounded, named substitution and pass payloads as separate `CompletionInput` blocks. A bounded flat map of required string fields is the configured output schema in v1. It covers summaries and other text outputs with one portable parser. | A programmable template or unrestricted JSON Schema would add evaluation and adapter behavior beyond this use case. Substituting PR text into instructions would let the change supply instruction text. |
| D-4 | Use a publish summary template made from typed scalar/section slots, keeping the legacy formatter as the default and the exact fallback when a declared composer fails. Place the composed text through a server-owned attribution block. Keep the existing posting trigger and compute finding membership and placement in code. | Giving the model the entire review body would let it omit summary-only findings or change their meaning. Posting a standalone body for clean rounds would add new review events and require a separate posting trigger and deduplication decision. |
| D-5 | Treat provider traversal and workflow continuation as separate decisions. Use completion-chain classification including the GH-57 rejection fix, with prompt response validation inside the chain. The executor owns `stop` or `continue`. This keeps failure visible and preserves accepted provider behavior. | Retrying in the executor would duplicate traversal and lose the classification or spend for a malformed paid answer. Handling workflow continuation inside a provider would bypass policy overrides. |
| D-6 | Use one graph DTO, validator, step capability contract and Workflow tab with GH-62. Keep server and client support additive and store the new config and result in existing JSON. | A separate prompt editor, workflow store, or migration would compete with GH-62 and duplicate revision and authorization behavior. |

## Runtime and configuration

### Declared inputs

Use the same resolver for prompt and explicit Publish bindings. Read the latest top-level execution of the literal node ID from this iteration with sequence less than the consuming execution. Resolve the latest row first, then decide whether it has usable output. A newer failure or missing output makes the binding unavailable even when an earlier execution succeeded. There is no lookup across iterations, fan-out children or undeclared nodes. The only cumulative context is the explicit run projection below.

| Publish source | Fields and rules |
|---|---|
| Required `CollateFindings` producer | Typed `CollateOutput.Candidates`. Publish applies the declared verify result to it, then runs the existing persistence, finding deduplication and posting policy. |
| Required `VerifyFindings` producer | Typed `VerifyOutput` provides kept candidate IDs, dropped count and the verifier note/status. Usable skipped and degraded outputs are honored. Require one applicable collate producer for Verify on an explicit Publish path. At runtime the collate row bound to Publish must be the same row that the built-in collate lookup selected at the Verify execution boundary. Reject a re-collate after that verification or kept IDs outside that collate result. Invalid or missing required artifacts fail Publish before posting. Legacy graphs retain their existing implicit fallback. |
| Optional `Categorise` producer | This iteration's change kind, category list and six scores. Expose a separate run-wide blast radius and category projection for the run-page figures, clearly identified as cumulative. Preserve unknown values as unavailable. Render the six labels and score descriptions in the same order as the run page. |
| Optional `SelectChecks` producer | Selected check IDs and titles in stable order. Honor the trigger-based selections from a failed-continued execution with usable output. |
| Optional `Prompt` producer with a string `summary` | A validated successful summary from the selected execution. Absence, invalid shape or failed-continued status selects the legacy summary body byte-for-byte for the review that Publish would otherwise post. |
| Built-in publish context | Allowlisted run title and subject label, round and iteration numbers, inline and summary-only findings after placement, below-bar count and verifier note. Keep raw body text, internal IDs, diff, review credentials, arbitrary output JSON and entity properties outside the renderer. Inline anchors, comments, thread IDs, status checks and finding persistence follow the same code path as before. |

### Prompt node

The example belongs in the operator guide and a round-trip fixture. Replace the existing edge in the graph, add `compose-summary` to the Review section, and retain all other graph wiring.

```yaml
nodes:
  compose-summary:
    kind: prompt
    description: Write a short overview of this change and its risk.
    inputs: [collate, verify, categorise, select]
    context: [diff, findings]
    chain: completions-cheap
    onFailure: continue
    outputSchema: { summary: string }
    prompt: |
      Write two short plain-language sentences about the change and its risk.
      Use {{context.diff}} as change evidence, {{context.findings}} for posted findings,
      and {{input.categorise}} for the risk assessment. Use {{input.verify}} to distinguish
      verified and unverified findings. Use {{input.select}} for review coverage.
      If data is unavailable, state uncertainty. Report supported observations only.
  publish:
    kind: code
    run: Publish
    description: Post the review with context and the model-written overview.
    inputs: [collate, verify, categorise, select, compose-summary]
    summaryTemplate: |
      {{defaultBody}}

      {{blastRadius}}
      {{categories}}
      {{selectedChecks}}
      {{composedText}}
edges:
  - intake -> delta -> categorise -> select -> group -> packs -> review -> collate -> verify -> compose-summary -> publish -> route
```

- **Inputs and substitution.** Use the producer catalog for bounded projections from collate, verify, categorise, select and other schema-validated prompts. For raw collate, expose counts only. Verify supplies counts and status. Categorise and select supply projected scores/categories and selected checks. `context: [diff, findings]` opts into a pinned base-to-head diff from the existing per-walk cache and a bounded view of kept, publish-eligible findings. `findings` requires both collate and verify. Derive eligibility using the same round-bar, flags, already-posted and nit-placement rules as Publish, through a small shared read-only projection. Include only severity, path and title of eligible candidates. Use the existing 24,000-character diff cap, up to 8,000 characters for the finding view and a 40,000-character combined data cap. Truncate at safe Unicode and record boundaries with a fixed marker. A refused oversized diff is an explicit unavailable block. Optional branch output is an explicit unavailable block. Preserve producer order and stable field ordering.
- **Trust boundary.** Accept authored templates from the embedded build or GH-62's operator-authorized revision save, using the pinned revision. Substitute markers such as `{{input.verify}}` with fixed references to labelled data blocks. Place serialized untrusted values only in those blocks, with server-generated labels from validated identifiers and the existing fence-length logic in `CompletionText`. HTTP sends instructions and data in separate message roles. One-shot CLI uses its existing scratch directory and tool-free fenced rendering. Add fixed instructions that treat every data block as evidence and reserve output formatting for the authored instruction and server schema. Never reparse substituted data as template text. Keep prompts, patches, raw model responses and provider credentials out of node diagnostics and logs.
- **Output.** Request one JSON object via the text completion contract and append the exact schema requirement in server-owned instructions. Parse once with `System.Text.Json`, accepting only declared keys, all present, exactly once and with nonblank string values. Use a flat schema of 1–8 bounded identifiers, with up to 2,000 Unicode characters per field and 8 KiB for accepted serialized output. Reject excess keys, duplicate keys, nested values, prose wrappers and text after the object. Store only accepted normalized text and bounded call metadata in `OutputJson`. On a failure, metadata may be stored without any usable value.
- **Spend and deadline.** Reuse `CompletionChain` via an opt-in response validation hook and a total prompt budget. Validate adapter results before choosing a winner, count schema-failed paid responses with their model, tokens, latency, cost and cost basis, and continue to the next eligible provider within the budget. Persist bounded per-attempt metadata alongside the prompt output or failure, with stable outcome codes and no provider payloads. Reuse `NodeUsage` and the executor's save for the node and run totals. Display accepted provider/model, falling back to the last billed provider on an exhausted chain. The current aggregate has one basis. For a mixed-basis node, use the estimate basis in that aggregate and preserve the exact split in attempt metadata. Reuse provider deadlines inside a finite total budget, including diff acquisition. Default the prompt's total to the smaller of 120 seconds and the effective executor lease minus 10 seconds. Validate an explicit positive whole-second `timeout` against that lease margin and cap each call by the remaining time. These are application limits and TestDesign will measure test timeouts separately.
- **Failure and restart.** Missing/unconfigured provider, timeout, rate limit, temporary unavailability and schema failure may advance within the chain. A rejected request or credentials failure ends traversal per GH-57. GH-58's Jev System One shape and rejection rules stay in the decision adapter. After chain failure, expose safe failure kind, relevant provider alias and bounded diagnostic code through `NodeResult.Fail` with any recorded spend. Effective `onFailure` follows `Review:Policy:OnFailure:<node>`, then YAML, then `stop`. `continue` persists `FailedContinued` and follows the unlabelled edge in the example. `stop` fails the review and uses the existing error status path. Propagate host cancellation to the executor release path and let supersession discard a stale completion before Publish. A committed terminal prompt result is followed on restart using the pinned graph and current iteration. Reclaim before commit can repeat the bounded model call, with the same existing executor retry boundary. Prompt nodes execute as work in the Publish stage. The permitted transports finish with a response, failure, cancellation or the bound deadline and create no Antiphon input-wait session.

### Rendering and validation

- Render `summaryTemplate` in one pass through a closed set of slots. Scalars are `run.title`, `run.subject`, `round` and `iteration`. Server-rendered sections are `defaultBody`, `findings`, `verification`, `belowBar`, `categorisation`, `blastRadius`, `categories`, `selectedChecks` and `composedText`. Use standalone lines for section slots. Require exactly one coverage slot, `defaultBody` or `findings`, so summary-only findings can be represented. In the implicit default and fallback paths use the current formatter. In a custom template render `defaultBody` from the same data and layout with untrusted fields escaped for Markdown.
- Emit a fixed **Model-written overview** label with the composed block. If the selected prompt succeeds and the template omits the slot, append the labelled block. Only emit the block once. In the new renderer encode untrusted dynamic values as literal display text, including structural punctuation, HTML, mentions, issue references and link syntax/automatic URL activation. Normalize unsafe control characters and line breaks in scalars. Preserve trusted static Markdown, including generated safe sections. Bound template length to 8 KiB and custom output to 48 KiB. A corrupt or over-limit custom render falls back intact to the deterministic body and records a bounded warning. Keep the existing PR SHA, placement rule, inline comment formatting and post condition. A model summary cannot create a review on a clean round or on a non-posting host.
- Extend `ReviewWorkflowValidator.cs` and the shared step descriptor from GH-62. Use typed diagnostics with consumer node ID and field context through the existing validate service, and reuse these checks at revision save. Reject wrong param shapes, blank or duplicate IDs, self-dependencies, unknown producers, illegal types or fan-out children, ambiguous Publish roles, unbound or unknown template tokens, unsupported schema fields, invalid prompt chain transport/dialect, `run:` on Prompt, and unsupported fallback edges. Bound declared sources to eight and authored prompt text to 8 KiB. Reject unknown fields on Prompt. Reserve `context` for supported values. An unavailable chain reported at runtime follows the failure rules above. Save-time validation of a named prompt chain reads effective configuration without contacting a provider.
- For required inputs validate that the producer precedes and dominates the consumer on admitted paths in the same iteration. Ignore transitions into the entry from within the graph because they start a new iteration. Account for labelled, default and overflow targets, and reject required producer dependencies that can only be satisfied through a cycle or on a different branch. Optional context can be absent on a permitted path. A prompt with `onFailure: continue` needs one deterministic usable continuation. If the executor and validator need the known-step registry before GH-62's descriptor lands, introduce the shared seam once. Preserve validation of built-in and legacy pinned graphs, including the child-only reviewer.
- In the existing Workflow tab, the Prompt card has a distinct **Prompt** badge and uses the same node selector, diagnostics and execution rows. Its inspector shows ordered input IDs, diff/findings opt-ins, chain, failure policy, optional timeout, a multiline prompt and typed output fields. The Publish inspector shows ordered input IDs and a multiline summary template with available slots. GH-62 owns the read-only pin versus draft transition, save, scope, revision diff, effective policy display and authorization. GH-63 supplies field controls in that inspector and extends the client API `NodeKind`, node metadata/icons and fake validator/fixture. Preserve graph values when an unrelated node is edited. Display node-scoped errors by the affected control. Editing and validating the template makes no model call. No live preview is required.
