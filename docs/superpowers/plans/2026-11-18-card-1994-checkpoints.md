## Design

1. **Normal exit keeps the generation.** `LandingVerifier` marks the generation `ready` as soon as the `dotnet build` child exits normally, before any test run, whatever the build result. Normal is exit 0 or exit 1 (MSBuild's only result codes: success, or build/restore errors). MSBuild is incremental and the compiler emits nothing for a project with errors, so a failed build leaves every project it wrote valid and every project it did not write stale by timestamp. A verification in which no build child ran (a build-slot timeout) also marks it `ready`: the folder is as `Prepare` found it.
2. **Kill, crash or no exit status sets it aside.** Any other exit code (137 SIGKILL on Linux, -1 `Process.Kill`/`TerminateProcess` on Windows, any signal) or an exception (cancellation, timeout kill, server death mid-build) leaves the state `building`. The next `Prepare` writes `quarantined` and starts a new generation, as today. Choice: the verifier records no binlog, so it cannot know which projects were being written when the build died, and deleting only those is not available. Setting aside is the only rule here that cannot let a half-written DLL be reused; a kill is rare. UNOBSERVED: an external kill of only the root `dotnet` process on Windows can report exit code 1 (Task Manager "End task"), which this rule cannot tell from a build error; a worker node or compiler server killed inside an otherwise normal build makes MSBuild exit 1 with MSB4166. Neither has been observed on a land. A truncated output from such a kill fails metadata load in its dependents and its tests (a false fail, not a false pass), and Roslyn emits only after a compilation with no errors, so a partially written DLL implies its inputs compiled; this argument is from Roslyn and MSBuild behaviour, not measured here.
3. **Pruning.** Every `Prepare` that returns a generation in the owned root then prunes: candidates are direct children of that root whose name is a 32-hex generation id, are not referenced by any lane pointer and are not the generation being returned, carry no link component, carry this repository's `owner.json`, and whose `state` is `quarantined` or `building` (an unreferenced `building` is a pre-CARD-1994 set-aside). The two newest by `state` write time are kept; the rest are deleted by their exact path under the root (`Directory.Delete`, which removes a link and never follows it). A prune failure is a diagnostic, never a cold land. `Prepare` runs under the repository land execution lock L (the existing caller contract), so no other land is building in that root while it prunes.
4. **Target lanes.** One root (`<git-common>/antiphon/land-verify/v1/<toolchain-key>/`) and one owner, with one current pointer per target lane: `current` for master and for no target (the v1 pointer, so master's existing warm generation is kept), `current-rc` for every `rc/*` branch, and `current-<16 hex of SHA-256(branch)>` for any other target. Alternating rc and master lands each rebuild only their own delta. Smaller than a key change: the existing root, its warm master generation and its dead generations stay reachable by pruning. The protocol passes `op.TargetFullRef` (and the prepared ticket's `TargetRef`) in `LandingVerificationCorrelation.TargetRef`.
5. **Mark before scan.** `Prepare` reads `state` before `RequireUnlinkedTree`; only a `ready` generation that will be reused is scanned (about 9.8k files, 3 s). A generation being set aside is never scanned, so a linked entry in it no longer turns the land cold.

No timeout or assertion is loosened. Two C1380 assertions encoded the old rule and are reversed by the operator decision: `C1380_StaleTrxCannotPassASecondRun` now requires the generation after a failed test run to be reused (its stale-TRX assertions are unchanged), and `C1380_FailedBuildRefusesPublicationAndReleasesExecutionLock` now requires `ready` after a compile error (its refusal and lock assertions are unchanged).

## Verification design

- V-1. A failed build (exit 1) leaves the generation `ready`, the next verification reuses the same path, and the root holds one generation (`C1994_FailedBuildLeavesTheSameGenerationReusable`). Red on the base: state `building`, new path.
- V-2. A build ending with exit 137, -1, or no recorded exit status leaves `building`; the next verification uses a new generation in the same root and the old one reads `quarantined` (`C1994_KilledBuildSetsTheGenerationAside`, 3 cases). Red on the base: no `quarantined` state.
- V-3. Pruning keeps the two newest set-aside generations, deletes the older two, and retains the active generation (older than all), a foreign owner, a non-generation name, a generation-named link to a directory outside the root, and that outside directory's content; it logs exactly two `land_artifacts pruned` lines (`C1994_PruneKeepsTwoNewestSetAsideAndNeverTheActiveOrAnEscape`). Red on the base: nothing is pruned.
- V-4. Master and rc lanes get separate generations in one root; master reuse is unaffected by an rc land; no target uses master's v1 pointer; successive `rc/*` lines share one lane; pruning never deletes another lane's current generation; the verifier passes the correlation's `TargetRef` (`C1994_TargetLanesKeepTheirOwnWarmGeneration`). Red on the base: rc reuses master's path.
- V-5. A `building` generation holding a symbolic link is set aside into a new generation in the root without a cold fallback (`C1994_SetAsideReadsTheMarkBeforeScanningTheGeneration`). Red on the base: the scan runs first and the land goes cold.
- R-1. Every existing `LandWarmArtifactsTests` and `LandVerificationBuildSlotTests` method and case passes (cancellation still sets aside; linked ready generations still go cold; foreign and linked roots are retained).
- R-2. Layering and lane-category guards stay green for the touched server and test files.
- R-3. `scripts/audit-land-verification-graph.ps1 -Check` approves the tree (CARD-1991: rerun once alone if it hits its 5 s clock).
- R-4. `scripts/check-evidence-diff.ps1` over base..HEAD.

The not-witnessed piece: that `AgentTaskLandingProtocol` passes `op.TargetFullRef` and the ticket's `TargetRef` (one argument at each of two call sites, read in review). `AgentTaskLandVerifierTests` (Slow, real builds) is not run: operator 2026-11-18, short tests only.
