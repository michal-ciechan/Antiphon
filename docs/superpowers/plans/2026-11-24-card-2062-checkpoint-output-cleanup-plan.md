# CARD-2062 checkpoint output cleanup

Keep the CARD-2052 speedup parked. The useful unit to check with Git is an entire output directory. One affirmative answer covers all its descendants **only while no writer can change either the repository view or the output tree**. The four reviews found ways to change that view without changing the file about to be deleted. A faster fifth version of the stamp would still need to solve that problem.

Recommend a limited path for a provably exclusive finalization window. Use one literal subtree query in that window, keep all the entry ownership checks, and finish deletion synchronously. Ordinary mutable checkouts keep the current implementation. First qualify the window on a disposable Linux checkout. If it cannot be supplied cheaply and independently of the cleanup code, accept the current cost and close the optimization as unqualified. The deliverable on master is this design. Runtime activation requires the acceptance evidence below.

### How exclusive finalization would work

1. **Admit an object, once.** At fresh output admission, before inventory or child writes, bind the run, build, normalized output under the nearest repository, checkout directory, marker, resolved gitdir, common directory and any pointer files. Hold native no-follow handles for the owning objects until release. Compare a fresh anchored walk to the held objects, including kind, device/volume, file ID and birth time where available. Compare pointer bytes as well. A held handle prevents lifetime reuse. It does not freeze content, block a rename, or protect an ancestor. Reject redirects, ambiguous identities, unreadable components and enclosing-repository substitution. An executor that starts with only a path from disk cannot enter this route.
2. **Require an enforceable handover.** The provider owns a private per-run filesystem and admission of *all* processes allowed to access it. A reference Linux implementation uses a dedicated, non-shared worker security identity and supervisor-owned inaccessible parent, a private full checkout including Git metadata (no writable backing shared with another checkout), and a non-delegated process containment group for all build/test descendants. The creating executor retains its in-memory registry outside the descendant group. The worker cannot signal, trace, or acquire the executor's handles. Control and evidence directories have a separate access boundary. The native proof must establish these protections on the actual provider. Close new writer/reader admission, await driver exit, pipe drain, **empty** descendant group and release of every registered consumer. Exclude shared volumes, bind aliases, external gitdirs/common dirs, other processes with that identity, passed-out descriptors and mutable config outside the boundary. Deny worker escape and restart/admission until the finalizer releases the capability. Root/platform administration is part of the existing trusted host. A shared linked mirror, basename, mode 0700, an advisory lock, PID scan, PID death, build slot or heartbeat alone fails this admission. Plain/linked worktrees qualify only if **all** backing objects are within this lifetime. If the provider cannot enforce the boundary, it must return unavailable. Do not attempt to obtain it by changing permissions or stopping processes in a live workspace.
3. **Settle the repository decision inside that window.** An attempted fast removal without a grant must retain the output and return a named refusal. Do not downgrade this attempt to ordinary cleanup. Re-resolve and compare the admitted objects, verify the active owner/cancellation and current-process creation records, inventory, no-follow ancestry and contents. Retain any new/changed entry or nested repository. For v1 accept only a plain understood Git layout, fixed case semantics and hardened config environment. Have Git parse the direct local/common config with includes disabled and inspect parsed keys. Any include/includeIf (even unresolved, symlinked, continued or conditional), per-worktree config, worktree redirection, unsupported index/layout, ambiguous path encoding/folding, override, or inspection error makes the root ineligible. Require a known mapping, including agreement of the effective toplevel with the held checkout. Never synthesize it from a missing marker or force a new mapping by setting `--work-tree`. Use the hardened real Git runner, pinned working directory, validated literal repo-relative directory path, `git --literal-pathspecs ls-files --cached -z -- <path>`. Honor timeout, exit, complete output drain and cancellation. Only exit zero with empty complete stdout under **that** owner permits removal. Keep conservative comparisons for potentially aliasing names and refuse an unsupported case-folding filesystem. Any bytes in stdout protect the tree. No decision survives release or transfers to the next root.
4. **Remove under the same custody.** Keep the validated listing decision and native handles local to the operation. Recheck entry identity/content, single-link regular file or directory, no links/reparse points along the walk, and the creation record at each anchored unlink. Open every ancestor relative to the trusted anchor. Remove files individually, deepest directories nonrecursively, the diagnostic ledger after children and the root last. Check task cancellation before each destructive step. The supervisor must keep writer admission closed until the executor has acknowledged stop and joined the operation, including an in-flight syscall. A timed-out lease that lets another writer in while unlink can still run is invalid. A new file, hard link, symlink, junction, changed bytes, unavailable handle, nonempty directory or IO failure retains the remaining tree. Owner data, receipts and the persistent intermediate cache stay outside the removal set.
5. **Report and recover.** Keep the path, file/directory stage and specific refusal in the normal cleanup result. Record the count actually removed and the surviving root, and return the existing invalid/RED outcome on a would-be green run. A failure halfway commits no promise to undo prior unlinks. Dry-run, explicit keep and red-without-clean-on-red must cause zero unlinks. On crash, process-local authority is lost. Retain residue for existing separately authorized recovery. A retry with path, run ID or copied ledger alone cannot resume deletion. Recovery must first prevent entry to a still-active finalization. No reinterpretation of an admitted repository as “outside repository.”

## Rollout and rollback

1. Land this document on master. Keep the parked code and its failed receipts on their historical refs. TestDesign qualifies S1 first. Compare read-only decisions against known tracked/foreign controls. Unavailable custody is a valid feasibility result and rules out activating batching on that lane.
2. In a disposable, qualified workspace, run the committed red witness and narrow green with an owned positive control. Run the one native handover proof and request one Code Review before product land. Then run the isolated performance trial. The six Windows rows at `4a67dd87:docs/superpowers/plans/2026-11-23-card-2052-r2-checkpoints-windows.md` remain historical evidence debt. A Windows implementation requires its own native same-SHA acceptance. Leave it disabled during the current Windows qualification.
3. Start opt-in on a single capable execution lane. Compare deletion counts, retained bytes/reasons, protected-file survival, end-to-end wall, warm build time and receipts against the paired reference. Abort on any missing sentinel, unverifiable owner/query, unexpected partial success, unsupported capability, or failed budget. Any expansion requires repeatability on the new lane.
4. Disable new admissions immediately on rollback. Join in-flight finalizers under their existing custody or cancel and retain. For new runs use the existing mode, or `--keep-outputs` if ownership is in doubt. Revert the product commits on master through normal review if needed. A recorded path or an older successful receipt cannot authorize cleanup of leftover files. This plan ships no runtime change, schema migration or rc activation.
