# CARD-1836 incremental Windows RC qualification

On a recut, run every chunk without a proven clean pass and every chunk affected between the comparison commit and the candidate. A green carried forward must lead back to the Windows execution that earned it. Ship the new writer and selector in Full mode. Switching on selective execution requires a five-run replay against actual outcomes, followed by a prospective Full comparison.

This plan applies the 25 November operator rules to the [CARD-1836 activation design](2026-11-12-card-1836-incremental-activation-plan.md) and the [19 November measurement plan](2026-11-19-incremental-rc-qualification-plan.md). ## Decisions

**D-1. Choose a comparison baseline for qualification independently of release publication.** Resolve an explicitly recorded eligible release, otherwise the most recent eligible ancestor release, otherwise the last sealed Windows RC attempt on the same line. Bind repository, source tree, ref/line, profile, run, attempt, timestamp and receipt digest. Prefer the latest completed attempt at a repeated SHA, and retain later partial attempts and open failures as obligations. On the same SHA the diff can be empty and the outstanding work still runs. A cross-line release needs verified ancestry and a compatible contract. Reject a moved ref, conflicting receipts or incomplete history. Record the baseline choice and the latest observed execution for each chunk. For a newer execution at a different source, prove input equivalence from that source to the candidate too. Never skip across a gap in the chain.

Store the comparison receipt’s kind alongside its digest and path in the v2 attempt. Route a v2 RC inventory through its own strict reader, leaving the v1 full-release reader exclusive to its own format. A run may close its **evidence inventory** with red rows. This lets independently sealed clean rows on one failed cut save work on the next. A partial run with an intact expected roster can contribute verified individual rows over an admitted baseline. Unfinished obligations stay open. An older release pass cannot erase a later FAIL, interrupted attempt or missing required result. Keep CARD-1823 fix containment for open failures. Reject the alternative of requiring a published green for every recut, which reproduces `baseline-absent` throughout a repair series.

**D-2. Give each real execution an immutable receipt.** Version the RC chunk evidence separately from the existing run selection JSON. Add `chunkReceiptVersion=2` on the run and `sha` (full execution commit, 40 lowercase hex here) and `contentDigest` (64 lowercase SHA-256 hex) to each observed chunk row in `summary.json.suites`. Preserve existing names and values. Use the discriminator `antiphon-rc-chunk-execution-v2` on the sealed execution record. Persist the same fields there and reference it by relative path and byte digest. Include repository, platform/architecture, profile, suite, stable work identity, run/attempt, disposition, start/end/duration, source tree/build/discovery seals, inputDigest, evidence kind/path/digest, exit/timeout/drain, per-case outcomes, counts and evidenceReasons. Reference the canonical roster/case evidence once by digest. Require the source seal to match the checkout, build, launch and run. Use typed dispositions for executed, carried, missing and unexecuted. A never-launched row has planned candidate and content identity where known, null execution SHA. A carried row keeps the original execution SHA/run/receipt, and records the separate candidate that validated it. For example, if a clean receipt at B is carried to A, summary.sha is A, row.sha is B and the disposition is carried. An A execution writes A in both places. Both rows bind the full digest of the roster they account for.

* Content digest v1 hashes a domain/version tag, suite, execution kind and semantic selection parameters, and the ordered complete expanded Windows roster (project/assembly identity, fully qualified class, method and stable case key). Reuse the length-prefixed UTF-8 encoding and ordinal sorting in `RcBoundary`. Version the content projection independently of its label-bearing chunk ID. For a command suite, hash its ordered required commands/arguments and logical test or script manifest. Exclude checkout path, group ordinal, presentation/boundary label, run ID, elapsed time, binaries with volatile IDs and the full plan/commit hash. Keep case keys case-sensitive. Ambiguous parameterizations, collisions, empty or duplicate identities are unproven.
* Keep **inputDigest** separate. Hash the chunk's owner/read closure and execution inputs under a versioned policy, including actual toolchain, packages and runtime receipts. Project-wide digests are appropriate where ownership is only provable per project. Use an admitted trusted contract at a guarded dependency edge as specified in D-4. The candidate SHA binds provenance outside the equality projection. Otherwise every commit, renumber or timestamp would invalidate every chunk.
* Start from current discovery, cut single-boundary chunks, and match full content digests across runs. An ordinal change with identical content remains matchable. After a split/merge every new unmatched roster runs. Retire old-only members in the coverage diff, and report moved identities and retired obligations. A boundary configuration edit with identical chunk contents adds zero work on that ground. Keep the full policy blob as provenance. For v2 invalidation, project packing thresholds, cost weights, boundary maps and labels out of the global policy/catalog hash and suite-wide inputs. Recompute the partition and compare content digests. A change to the packer implementation must still pass the partition validator. Separate changes to coverage rules, exclusions, evidence semantics or genuine runtime reads retain their own invalidation rules.
* Prewrite the expected partition. Finalize rows only after custody cleanup, evidence validation and count reconciliation. Publish the inventory by atomic create/rename with a digest and monotonic attempt revision. Identical retries reuse a seal. Conflicts, duplicate rows, torn writes, changed files, stale invocation IDs, escaped paths or a moved source cannot grant credit. Keep pending results visible after interruption. Old readers can consume the existing fields. V2 admission treats missing/malformed fields as unproven. The first instrumented Full seeds live v2 receipts. Reconstructed historical rows are for replay only.

**D-3. Build one decision for every current obligation.** First apply global reasons (D-6). Otherwise take the union below, retaining every reason even when a higher-priority reason already selected a row.

1. Join expected chunks to the last attempted results. A reusable pass requires actual eligible Windows execution, result `pass`, skipped=false, zero exit code, no timeout/drain failure, empty evidenceReasons, fresh verified evidence, positive expected execution count and exact case coverage. For native TRX verify the digest, identities and counters, including **zero skipped/NotExecuted**, zero failed and all required cases passed. A tolerated skip inside a nominally passing row owes a rerun. A declared exclusion outside the Windows universe adds no chunk. Apply equivalent validated JSON/census evidence to client/scripts, otherwise execute them. FAIL, skip, timeout, nonzero tolerated exit, unexecuted, absent, contradictory, stale or malformed evidence all owe execution, even for an empty diff. A legitimate carry points back to the last actual clean execution. A scheduled launch recorded missing can never take that path.
2. Verify B and A as full Git objects and ancestry. Read `git diff --name-status --no-renames -z B..A --` at the two pins. Delete/add pairs preserve both sides of renames, copies contribute the added path and modifications consult both sides. Bind the index at `B:tests/derived-impact-index.json` and `A:tests/derived-impact-index.json` by Git blob ID and SHA-256 of its bytes. Pin builder/version and inputs used for freshness. Cache deterministic regeneration evidence per input-tree/builder digest, comparing canonical bytes with the pinned blob, with no writes into either candidate. Regeneration detects stale bytes. It cannot detect a missing semantic dependency. The bound input inventory must include all tracked inputs the builder uses, including path listings, OS overrides and hand-table inputs.
3. Union old and new path→class hits, declared tests from changed test files, applicable hand-table hits, and known runtime readers (including directory listings, fixtures and linked data). Map each to **all** matching current chunks via project, suite and expanded identities. Follow old-only identities to their surviving consumers, or prove retirement. If a simple name matches several projects, include every match. Preserve Windows-only and mixed classes under the candidate policy. Use changed old/new index edges as positive evidence when the index changes independently. An index regeneration is not itself an all-chunk dirty bit. Include the index's actual readers.
4. Resolve owners in both project graphs. For changed product logic, select direct affected tests plus proven consumer closure. For a test harness/helper, include its own tests and all test projects/chunks that consume it through references, linked Compile/Content, imports, generated inputs, staged executables or recorded runtime reads. Use separate reachability, including transitive consumers, at B and A. Handle simultaneous reference and file deletion. Within a monolithic project, narrow only where reader/class ownership is independently established. An unbounded reader owes its entire consumer batch. Replace the corresponding all-suite owner rows, suite-wide digests and global harnessHash with these scoped inputs in v2. Keep census tests for readers. A change limited to an owned harness can select all of its consumers even when the resulting roster is large.
5. On capped, allowlisted, missing, stale or conflicting edges, record the path, side and reason. Widen to a proven enclosing project/reader closure. If that upper bound is unknown on either side, select Full. A verified explicit no-op must have no conflicting reader. Global SDK/runtime/package or selector/evidence contract uncertainty also selects Full. The two recent [runtime-reader](../../investigations/2026-11-23-why-missed-rc-input-owners-map.md) and [deleted-driver](../../investigations/2026-11-24-why-missed-live-lane-callers-deleted-drivers.md) incidents are required regression inputs.

Record a reasoned partition of the complete current universe. Each entry records execute, hold for an own-test gate, or carry with its origin receipt. Prove exact, disjoint membership. Only proven carries leave the queue. Store the pinned input hashes, policy/trust version, contributing paths and source edges in the selection sidecar. Bind its digest to the existing attempt/summary fields, and revalidate at launch and closure.

**D-4. Trust is a reviewed, revocable exception for a specific shared application project.** Ship an empty versioned allowlist. Each later entry names an exact in-repository project, Windows target configurations, owned test projects/complete case rosters, downstream edges it may satisfy and an independently versioned contract producer. Unmarked projects and test harnesses always propagate through their consumers. A candidate cannot self-authorize a new trust entry: adding/removing/changing trust policy invalidates old decisions and needs review, Full shadow and the same replay gate. Reject a wildcard, missing tests, a project without a bounded contract, and any SDK/toolchain, framework, NuGet/npm package, lockfile, generator/analyzer or external runtime entry. SDK and package changes bypass trust and invalidate the applicable build inputs. Treat shared resolution/toolchain changes as global Full.

At B and A generate the canonical contract for each eligible build target from reference metadata, including visible/protected signatures, base/interface shapes, constraints, constants/defaults, relevant attributes and friend-visible elements. Include explicitly declared wire/serialization schemas, configuration keys/defaults, stored formats, DI/plugin registrations, native or content contracts used by consumers. Hash sorted logical entries with the extractor version. Raw assembly bytes include build IDs and timestamps and are unsuitable for comparing a public surface. A project with unmodelled reflection, side effects or external contracts stays untrusted. A code change can preserve a signature and change behavior, which is why a same-candidate execution gate is required as well.

Before suppressing propagation along a trusted edge, run **all** of the project's own required tests at A and require the D-3 clean predicate plus identical proven B/A contract hashes. Treat these as prerequisites. If either hash differs/is missing, or any own test fails, skips, times out or cannot be accounted for, expand the held consumers and their downstream closure into the same attempt and record the reason. A red gate remains red. Retain every independent direct hit, nonclean row, boundary change or path around the trusted project. With several changed trusted projects every influencing gate must pass. Write the resolved partition as a new sealed revision. A crash before resolution leaves the held work owed.

**D-5. Order the ready queue by impact.** Use CARD-1823 failure history and map failed cases to their current groups. Choose the lowest tier a chunk qualifies for: (0) unresolved failures, (1) end-user product tests directly exercising changed logic, (2) other direct hits, (3) transitive dependents, (4) remaining mandatory work, including missing/unrun rows without stronger impact and periodic-Full remainder. Determine tier 1 from checked-in product/app category and direct owner/edge evidence, e.g. a changed messaging behavior and its messaging or E2E scenario. A suite named E2E alone does not establish a match. Use the highest eligible tier even when several paths select a group. Within each tier sort ascending by prior verified Windows chunk wall time for equivalent contents, then a sum of priced members, then unknown cost last, then ordinal stable key. Record cost source and chosen rank. Use only earlier runs' timings. Gate prerequisites run before their blocked consumers, with failed-first and cost ordering among ready jobs. Reevaluate the ready queue after expansion. Preserve native serialization, setup/preflight prerequisites, failed-first history and the same order for Full where feasible. Never admit a second copy of a chunk.

**D-6. Enforce periodic Full and isolate release authority.** Retain the existing seven-day bound measured in UTC. Explicit Full, missing/non-ancestor baseline, invalid global evidence, unknown/future/expired Full-sweep proof, unqualified policy version or replay/shadow discrepancy forces the complete candidate Windows profile. A carry, recut, restart or replay never renews the clock. Keep periodic Full at least weekly during ongoing cuts, and enforce age again at admission even if scheduling missed a run. For scheduling, add a distinct `lastFullSweep` proof. It binds completion UTC, Windows candidate SHA, run/attempt, frozen universe and execution-inventory digests. It can renew only when the full universe was scheduled, every required chunk actually launched, and terminal outcomes reconcile to the roster. A completed Full containing assertion failures can start the scheduling clock. A partial run, incomplete census or composite ledger cannot. This lets an instrumented run shaped like `acca11ba` provide clean sibling evidence on the next recut while its six failures remain open. Keep the stricter `RcForcedFull.ExecutedFullAnchor` and publication checks for release credit. Bootstrap with instrumented Full when a verified sweep is absent, including when an older summary has a run-level SHA.

Use explicit opt-in Incremental, only for Windows RC qualification after rollout gates. Full remains the default at all public entry points. An incremental cut reports separate executed, carried, failed, expected-skipped, missing and held counts, origin SHAs, oldest anchor and outstanding eligibility. Reconcile its ledger against exact candidate discovery before recording qualified-by-ledger. Emit a distinct coverageScope and receipt; an unproven or open item prevents closure. Even if an Incremental request falls back to Full, keep that request qualification-only at the publication boundary. Only the existing explicitly authorized Full path can produce Full publication/green authority. Release branch creation, tags, promotion, master readiness and changes to live qualification scheduling are separate operations. This implements the recut design without granting an automatic release from a composite ledger.

Keep the incumbent Full path until the replay criterion and two prospective Full shadows pass. A sample discrepancy invalidates that candidate's carry partition and schedules Full verification before credit. Keep explicit Full and the seven-day backstop. Historical releases and tag eligibility retain their own authority.
4. Roll back by disabling Incremental admission, withdrawing the affected trust policy/measurement approval and requesting Full on the pinned SHA. Before any further launch or credit, revalidate the enablement and policy revision.
