# CARD-0235 — authenticated positive commit attribution ledger for Shared tasks: plan

**Status:** plan only, with no source change. **Recommendation:** park the card in Backlog with no
build. If nobody revisits it, close it as Won't Do. **Lane:** none, because this plan has no Code
stage. If the operator overrides the recommendation, re-plan on master only.

## 1. What the card asks for, point by point

| # | Card ask (from the CARD-0227 plan §5 deferral) |
|---|---|
| A1 | An explicit per-commit report tied to the current task token: the agent says "I made commit X". |
| A2 | A durable `(AgentTaskId, commit SHA)` record. |
| A3 | A reachability check before a reported SHA is rendered as evidence. |
| A4 | An identity model that survives warm reuse (the live process keeps its raw token while the server moves the hash to a new task). |
| A5 | An optional Git hook, plus a decision on what a forgotten report means. |
| A6 | An operator's manual commit in the same checkout is never tagged as task evidence. |
| A7 | (Folded in from CARD-0227 §5.) Audit `DelegateBindRefusalRecovery`'s Shared card-needle match. |

## 2. Ground truth: what the card assumes vs what the code does today

| Card assumption | What the code does (master at `c5f35c862`) |
|---|---|
| Shared tasks can't show `PRODUCED` from Git facts. | True, and deliberate. `DelegateCheckProbe` returns `CheckGitEvidenceScope.SharedWorkspaceUnattributable` for Shared tasks, with no log and no status. `RenderDigest` prints `SharedWorkspaceUnattributableExplanation` (`server/Application/Services/DelegateCheckProbe.cs:181-189,447-463,609-611`). `BlockedContextBuilder` uses the same disclaimer (`:202,226`). |
| A Shared task's settled header could falsely credit commits. | No longer possible. `TryDescribeGitAsync` (`AgentTaskReplyService.cs:5008-5034`) never counts a commit range for `Shared`/`ReadOnly`. It produces only `git=unattributable` (no repo, no reported paths, or status unavailable), `git=landed` (the paths the report names are clean) or `git=uncommitted:N`. `git=N commits` and `git=base unknown` are Worktree-only. They come from the `WorktreeBaseSha`/`MergeTargetRef` base (`DelegationGitFacts.ResolveBase`) through the task-branch tip. |
| Positive evidence needs a new ledger. | Partly built already, by the server itself. Commit-on-settle (`docs/orchestration-loop.md` "Commit on settle") commits a Succeeded Shared task's own footprint through `GatedCommitService`. The footprint is the dirty paths the session edited (`AgentFilesService.GetEditedPathsAsync`) or the report names. Settlement then writes a `Committed` event `"<sha7> <files>"` (`RecordCommitted`, `AgentTaskReplyService.cs:4886`) and the header `git=committed:<sha7>`. The server made the commit, so this is an authenticated `(AgentTaskId, SHA)` record and needs no agent self-report (A1 and A2 for the settle-time commit). A footprint it cannot attribute goes to a Commit-role child with reason `unattributable`. |
| The delegate and the operator share one Git identity. | Still true, and still the reason a range or author cannot prove authorship (CARD-0227 §2). |
| Shared is a normal delegation shape. | No longer true. The project/global default is `DefaultWorkerWorkspace` `Worktree` (`ProjectDto.GlobalDefaultWorkerWorkspace = "Worktree"`). Runner tasks refuse Shared (422). See §3 for the numbers. |
| `DelegateBindRefusalRecovery` collisions (A7). | Unchanged. `TryGitAsync` (`DelegateBindRefusalRecovery.cs:110-150`) reads `HEAD --since DispatchedAt` for a non-Worktree task and keeps lines that match the task short id or card needles. A concurrent commit on the same card could be offered as bind-refusal recovery evidence. That path only runs when a delegate refused to bind, and it is evidence offered to recovery, not a header. |

## 4. The true remaining gap

The only thing still missing is A1, A3 and A4 for a commit the delegate makes itself, by hand, in a Shared
checkout. That means a commit made mid-task outside the settle gate. The `antiphon-commit: gated` trailer audit covers
only Commit-role children, not this case. Such a commit cannot be credited as `PRODUCED` during check-ins.
At settlement it is not counted either: it shows as `landed`, because the paths are clean.
In 30 days, at most 5 tasks could have been affected. The usage trend is toward zero because Worktree is the default and runners refuse
Shared. The only cost of the gap is a weaker progress signal on a check-in. Correctness does not suffer: CARD-0227
removed the false positive and nothing regressed since.

## 5. Decisions

- **D-1 Do not build the ledger.** It needs a new table and a token-authenticated report API.
  It also needs a warm-reuse identity model (A4) and a forgotten-report semantics decision (A5). That is
  several days of launch, API, schema and failure-semantics work for at most about 5 tasks a month, and the number is falling.
  *Rejected:* building it as the card describes, because the cost far exceeds the benefit. A
  Git-hook-only variant (a `prepare-commit-msg` trailer carrying the task id) was also rejected. It needs
  the hook installed in the shared checkout, which affects the operator's own commits. It cannot
  authenticate anything either, because an operator commit made while the hook's env is set would be tagged, which violates A6.
- **D-2 The settle-time gated commit is the supported positive evidence for Shared tasks.**
  It already gives a server-authenticated `(task, SHA)` record (`Committed` event, `git=committed:`).
  A delegate that needs its commit credited should leave the change for the gate, or run in
  `Worktree`. *Rejected:* rendering the `Committed` event in check-in digests. The gate only commits at
  settle, after check-ins stop, so there would be nothing to render.
- **D-3 Leave A7 as is.** `DelegateBindRefusalRecovery` only offers evidence to a refused-bind
  recovery. It does not write a header, and its card needles need a same-card concurrent commit within the
  dispatch window on a Shared task. That is now a vanishing population. *Rejected:* narrowing it to
  short-id-only needles, which would lose the main way it recovers legitimate work today.
- **D-4 Reopen trigger.** Re-plan only if delegated Shared tasks climb back above about 100 a month, or
  if a Shared false-credit or missing-credit incident is filed. Either fact is measurable with the
  §3 query.
- **D-5 rc applicability.** None, because no source changes.

## 6. Slices

None. If the operator overrides D-1, the smallest viable design still needs a fresh plan. It would be
roughly: (S1) an additive `AgentTaskCommitClaims` table plus `POST /api/agent-tasks/{id}/commit-claims`
authenticated by the current task token hash. (S2) Reachability and Shared/HEAD-ancestry verification
at render time in `DelegateCheckProbe` and `TryDescribeGitAsync`. (S3) Warm-reuse token rotation
semantics. Each slice is longer than 60 minutes, and S3 depends on the pool's token-move design. This plan does not
size them further.
