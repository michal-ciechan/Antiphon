# CARD-0593: preserve channel inbound across a failed agent wake

Base inspected: `origin/master` and this worktree at `4e873cf20a61b0475f9a013b57168e6ecdd7aea5` (2026-09-26). This is an investigation and implementation plan; no production or test code changed here.

## Verified findings

1. `ChannelBridgeService` records the inbound catalog entry before routing (`server/Application/Services/ChannelBridgeService.cs:101-119`), attempts to start a bound agent once, and polls until the configured deadline (`:425-476`). A timeout returns without entering the debouncer or durable session queue (`:170-186`). The Warning alert at `:399-418` is the only timeout signal; Herdr and model holds already create Critical `ChannelReplyLost` incidents (`:136-168`, `:329-397`). `AgentStartTimeoutSeconds=90` and `AgentReadyDelaySeconds=12` remain current (`server/Application/Settings/ChannelBridgeSettings.cs:18-22`). A queued launch can return from `StartAsync` before Running (`server/Application/Services/AgentControlService.cs:180-181`), so the poll cannot simply be removed.
2. The consumer auto-commits offsets (`src/Antiphon.Messaging.Client/KafkaAntiphonMessagingConsumer.cs:22-55`), including while the handler is waiting for a wake; a crash before durable acceptance can therefore lose the message even if a journal is added. Even a forced Kafka replay is insufficient today: catalog upsert stores only the **last** native message ID and a 200-character preview (`server/Application/Services/ChatChannelService.cs:20,148-195`); the bridge skips that last ID at `ChannelBridgeService.cs:111-116`. Its catalog write is not an acceptance receipt for the full envelope. Older redeliveries may also miss this one-slot dedupe.
3. `SessionMessageQueueService.EnqueueCoreAsync` requires an existing `AgentSession` (`server/Application/Services/SessionMessageQueueService.cs:405-410,4847-4853`), but persists a `WhenIdle` Channel row before typing (`:641-675`) and leaves a non-Running row Pending (`:716-726`). Launch flushes pending rows after boot (`server/Application/Services/AgentSessionService.cs:628-634,866-879`); a new session carries never-attempted pending rows from the old session (`server/Application/Services/AgentControlService.cs:672-676,730-761`). These mechanisms help **after** a queue row exists, not when no session was reserved. The stranded sweep only selects AlwaysOn sessions or machine origins; Channel is excluded (`server/Application/Services/SessionMessageQueueService.cs:1397-1420`, `server/Application/Services/QueueAttention.cs:80-90`). A non-AlwaysOn idle Channel row needs a direct boot or turn-end flush, not this sweep.
4. The bridge catches only Herdr hold and `ModelDisabledException` (`ChannelBridgeService.cs:131-169`). Other start conflicts reach the outer consume-loop catch, delay 15 seconds and resubscribe (`:61-83`). The current start path can refuse specialist starts, continuity holds, launch ownership races, and runner drain (`server/Application/Services/AgentControlService.cs:164-179,515-537,624-635`). The card's exact `standing_resume_current_active` citation is stale: its current early branch (`:175-177`) requires explicit Fresh/resume, which the bridge does not request; the later reservation branch (`:534-537`) returns the same source for ordinary resume. Do not write a test that assumes this code is reachable from an ordinary channel wake; cover an actually reachable conflict and keep a generic conflict fallback.
5. The bridge calls `StartAsync` with its default `automatic=false` (`ChannelBridgeService.cs:465-469`; `AgentControlService.cs:148-149`). Manual starts clear suspension/liveness via `ClearSupervisionLatchAsync` (`AgentControlService.cs:206-211,730-746,1214-1239`). This is a real separate hazard. Preserve `IgnoreSubscriptionQuota:true` (`ChannelBridgeService.cs:466-468`; `AgentControlService.cs:214-224`), while channel wake uses automatic intent and honors `Suspended`, `LivenessLatchedAt`, `HerdrFailureHeldAt`, and `ContinuityHeldAt` (`AgentControlService.cs:170-179,541-548`). Automatic must still be allowed for ordinary non-AlwaysOn agents; only capacity recovery has the AlwaysOn prerequisite (`:183-190`).
6. The card's `ChannelBridgeService` and queue line numbers, and the specific early conflict example, predate current master; the behavior in findings 1-3 remains. Current `ChannelBridgeTests` still asserts Herdr-held inbound is **dropped** (`tests/Antiphon.Tests/Application/ChannelBridgeTests.cs:35-71`); that expectation must change with parking. Its provider-capacity notice says the message is kept (`:825-890`), currently contrary to the bridge's drop path. `HerdrAlwaysOnChannelParityTests` is a process-spawning Windows lane, so it is not a portable checkpoint for this Linux worktree. CARD-0484's timeout-cost note remains in `tests/Antiphon.Tests/slow-tests-allowlist.txt:80`.

## Smallest complete fix

### S1. Accept the full inbound envelope before wake

Add an agent-bound `ChannelInbound` durable row (entity, EF mapping, CLI-generated migration) keyed uniquely by `(provider, conversationId, nativeMessageId)`. Persist the complete normalized `ChannelMessage`, including attachment bytes and reply handle, and the bound `AgentId`/`ChatChannelId` snapshot. Commit it with the catalog upsert for every enabled, bound, deliverable inbound message **before** calling `EnsureAgentSessionAsync` or an in-memory debouncer. A duplicate finds the existing inbound row; never equate `LastChannelMessageId` with delivery. Keep disabled/unbound and empty-message routing policy as today. Preserve accepted rows across server restart. The catalog must not consume the only dedupe identity ahead of acceptance. Existing catalog metrics remain one count per native message.

Replace `EnableAutoCommit=true` with explicit per-record commit after this database transaction succeeds (or after a deliberate self/unbound/disabled/empty disposition). Extend the consumer's delivery API and fake with an acknowledgement handle carrying the consumed topic/partition/offset; commit through the Kafka consumer only after the bridge reports the durable disposition. On a database failure or cancellation before acceptance, do **not** commit; resubscribe/reconsume and let the unique inbound key make that replay harmless. A commit failure after acceptance may replay, also harmless. Define an explicit malformed-payload disposition so it cannot silently advance past an unrecorded valid envelope. The bridge should signal the durable wake worker after acceptance, then acknowledge Kafka promptly; the worker, not the consumer iterator, can spend the 90-second start window.

### S2. Wake and materialize exactly once

Keep one start attempt and the bounded Running poll, including the 12-second settle on a fresh start. Return early only when the launch has a concrete terminal failure; retain the poll while the launch queue owns a pending session. Use `automatic:true` with the existing quota override. Catch all `ConflictException` start refusals explicitly and classify known hold/race codes; park without trying another start while a deliberate hold or launch reservation exists. Unknown conflicts and unexpected failures retain the durable row and surface diagnostics, not an assumed drop.

Add a bounded, restart-safe pending-inbound drain: run after acceptance, on startup, and when a bound agent reaches Running (with a periodic backstop for missed wakeups). Select pending rows FIFO by agent; under a per-agent/row claim, materialize each into **one** Channel `WhenIdle` queue row on the current persistent session. Give the queue row a unique `SourceChannelInboundId`, so a crash between queue insert and inbound-state update reuses the same row. Store the formatted envelope and saved attachment paths in that row before any terminal write; attachment filenames derive from the inbound ID so replay does not create ambiguous files. Leave the inbound payload durable until the queue row owns the complete message; retain a tombstone identity after transfer for dedupe. The existing queue marker, conversation key, delivery attempts, restart transfer, and matching complete `UserPrompt` receipt remain authoritative. A queue insert or flush result is only acceptance/attempt, never proof of delivery. Do not automatically retype an attempted row on a different session without the queue's receipt/attempt checks; park it for a decision at the attempts cap. Avoid routing through `FlushStrandedQueuesAsync` for Channel rows on non-AlwaysOn agents.

The current debouncer buffers only in memory (`server/Application/Services/ChannelInboundDebouncer.cs:58-92,116-162`). Keep its coalescing behavior only as an optimization over accepted row IDs; a restart or callback failure must leave every member recoverable and preserve sender/conversation ordering. Ensure the old `FlushLaneAsync` catch at `ChannelBridgeService.cs:195-236` cannot turn a failed queue insert into a terminal drop.

### S3. Report failed wakes without claiming delivery

On a timeout, add a Critical `ChannelReplyLost` incident with a stable inbound-row/episode key and reason `ChannelWakeTimeout`, plus the existing Warning alert if useful; its text should say the message is **pending** and has not reached the agent. Apply the same durable park to Herdr, capacity, continuity, specialist, suspension/liveness, and other start refusals; preserve existing once-per-hold Critical behavior and provider notice, with truthful wording. Persist incident creation and its dedupe marker together so a restarted drain does not page repeatedly. A later complete matching `UserPrompt` is the only delivery verdict; incident history may remain as a record of delay. Update `docs/telegram.md` and `docs/session-runtime-invariants.md` when implementing.

## Verification design

New `ChannelInboundRecoveryTests` should provide at least eight independent `[Test]` methods:

| ID | Required outcome |
|---|---|
| V-1 | A stopped agent whose wake never reaches Running retains the complete inbound payload, no typed input, and exactly one Critical timeout incident. |
| V-2 | A new server/bridge instance drains that payload on a later Running session, including a non-AlwaysOn agent; verify the marked queue row and a complete matching `UserPrompt` before calling it delivered. |
| V-3 | Kafka acknowledgement is withheld before acceptance, committed after acceptance, and a replay after the queue insert yields one catalog count and one queue row per native message, including redelivery after a newer message. |
| V-4 | Two same-sender messages accepted inside the debounce window survive a restart/flush failure in order; their distinct IDs and full bodies remain recoverable. |
| V-5 | Herdr, capacity, continuity, specialist, suspension/liveness, and an unexpected conflict preserve the envelope; deliberate holds do not auto-start, and incident/notice dedupe holds. |
| V-6 | Channel wake retains `IgnoreSubscriptionQuota:true`, uses automatic intent, and never clears a supervision latch; an ordinary non-AlwaysOn agent still wakes. |
| V-7 | A queued launch that returns before Running is waited for, then delivers exactly once after boot; a failed launch does not spend the full poll window if an explicit terminal failure is already known. |
| V-8 | Transfer to a new persistent session and a failed/uncertain terminal write retain the original queue attempt and full marked body; a screen redraw or enqueue alone cannot settle delivery. |

R-1: the full existing `ChannelBridgeTests` class keeps ordinary inbound, attachments, batching, reply correlation, and the adapted held-agent behavior green. R-2: a new `KafkaInboundCommitTests` class pins manual Kafka commit and fake-consumer acknowledge behavior, including failed handling and replay; use an isolated broker fixture only if that is needed to observe an actual committed offset. Use a fake clock/runner for wake deadlines; do not wait on production 90+12 seconds. A new test must fail against the pre-fix path for the production condition it guards. No production broker or runner is required.

## Risks and decisions for TestDesign

- The journal adds storage for attachment bytes (bus maximum is much larger than catalog preview). Bound payload size, retention after confirmed transfer, and cleanup must be explicit; never delete the only complete copy before queue ownership commits.
- Queue transfer and journal state must be idempotent across commit ambiguity. A unique inbound-to-queue key is required even if a process-local lock exists.
- Manual Kafka commit changes the `IAntiphonMessagingConsumer` public API and fake. Update the public API inventory and cover rebalances/commit exceptions; never acknowledge a valid record before its full envelope is durable.
- A fresh session can differ from the originally attempted session. Preserve queue attempt floors and refuse duplicate terminal writes until transcript evidence resolves uncertainty; do not claim a mere Running status, buffer redraw, or `SentAt` is receipt.
- Keep the one-start/90-second poll for launch-queue ownership; only shorten it when a concrete terminal launch failure is observed. A blanket retry can defeat Herdr/continuity/suspension holds or start concurrent sessions.
- CARD-0519 covers the outbound mirror. Coordinate any touched `ChannelBridgeTests` timeout setup with CARD-0484; avoid using Windows-only Herdr process tests as this plan's Linux checkpoint.
