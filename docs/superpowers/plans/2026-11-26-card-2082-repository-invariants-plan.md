# CARD-2082 · Run repository invariants first

Make a repository invariant individually addressable and execute all admitted invariant cases on every Merge and at the start of every Windows Full. An invariant here asserts a property of **this checkout**. Examples include agreement between discovery and a roster, the binding of historical plans to today's tests, and consistency between the compiled migrations and their snapshot. The fast failure should identify the checkout, offending input, test and repair before ordinary qualification work starts.

The [inventory](2026-11-26-card-2082-invariant-inventory.md) lists declaring types, representative inputs, physical projects, linked compilations, observed outcomes and runtimes. The two Windows qualification runs used different source pins. The Windows per-class timing matrix is deferred to TestDesign. The plan can land now. ## Decisions

- **D-1. Keep each test in its owning assembly.** Place whole guard fixtures in an Invariants directory and namespace, for example `Antiphon.Tests.Invariants`. Use the declaring project's equivalent namespace elsewhere and `Antiphon.TestSupport.Invariants` for shared linked sources. Apply class-level `[Category("RepositoryInvariant")]` **in addition** to its existing Unit or Integration lane. Keep current isolation, platform attributes, explicit status, limiter and app ownership. TestLaneCategoryGuardTests checks Unit xor Integration. A third exclusive lane would remove coverage from current selections. A new assembly would change discovery, linked classes and deployment dependencies.
- **D-2. Classify the assertion and its inputs.** Move a whole class when its subject is the shipped repository or its compiled census. For mixed classes extract an independently named fixture, preserving the behavior method and fixture at its existing entry point. If one method does both, move the source comparison to a separate case. Keep a guard's small positive and negative controls with it. Executing shipped code with a test-owned input, reading a golden response for a parser or operating a private Git repository qualifies as product behavior. Categorizing every scan hit would put E2E canaries, database upgrades and native worker tests in every Merge.
- **D-3. Use a single logical first phase with project-sized children.** A single TUnit filter works within one test host. Run `/*/*/*/*[Category=RepositoryInvariant]` in each owning test assembly on its admitted platform, compare the resulting case set to the classified discovery, and support the same selection for a standalone rerun at an exact SHA. Keep the existing app batch, native requirements and explicit/paid exclusions. Where a category filter would broaden an existing profile, execute the exact admitted case IDs instead. A class-name list cannot detect a newly classified guard or distinguish a linked copy.
- **D-4. Execute on every Merge, including docs-only and empty impact results.** The normal Merge plan needs an unconditional invariant group independent of the subject's narrow tests, labels or changed paths. Give each eligible platform-native member its actual lane. Use the platform-equivalent portable run once per Merge and require native receipts for platform-specific members. Preserve existing Windows-only and Linux-only evidence obligations. A narrow single-host Merge cannot report full coverage if a required native child is pending. Keep platform-neutral metadata assertions portable to minimize that extra cost. Platform placement follows live runner defaults and eligibility. The Plan read both runner APIs. No host pin is needed.
- **D-5. Keep historical evidence immutable.** Bind executable historical plan rows to the migrated case set or record an exact, justified retirement. Never preserve an obsolete selection with an empty test or retire an active survivor. Fresh execution at candidate HEAD is required for every invariant in an incremental cut, including resume, argument-level packing and receipts from earlier packaging versions. Extra stable chunk IDs or an all-path glob cannot prove the current global inputs.
- **D-6. Fail before ordinary work.** After prerequisites needed to build/list the invariant hosts, run the cheap source/roster/map checks first and flush the first failure immediately. Stop launching ordinary groups on an invariant failure. Emit a failed prefix and a manifest of outstanding cases. Successful standalone or repaired-prefix runs diagnose the candidate. Promotion still uses the release gate's complete required-run evidence. Preserve streamed progress for a slow case and cancellation/cleanup of only this run's children. [Release rules](../../release-gates.md)
