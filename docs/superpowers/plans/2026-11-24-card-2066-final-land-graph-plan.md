# CARD-2066 · Record the graph and impact index on the tree master receives

**Outcome.** A managed Antiphon master land publishes one verified Git tip. Its impact index can be reproduced byte for byte, its manifest describes the selected definitions at that tip, and its evaluation record binds that digest to approved target pins and a selectable SDK. The reviewed task ref keeps its original SHA. A target race costs another preparation and verification. A refusal costs no write to master.

Plan base `b3c8a192e0d89599e1a83956a4464991e3481500`. The November 24 board decision selects option B. Two target pin changes after clean Review justified keeping the audit. Over 60 days its maintenance cost included 67 master record-only commits, 10 more on rc-only history, four affected cuts, one held top-up, five batches holding a subject and 14 audit retries. These are lower bounds. At the failed November 24 cut the count was still 80 while the digest and index bytes had both drifted. ## Decisions

**D-1. Finalize every newly prepared, participating master candidate.** Run the canonical index builder and evaluate the graph in the detached worktree even when the rebase was clean or the target carried inherited drift. A successful, current pair keeps the recorded selectable SDK. Commit only changed bytes, with no SDK-only churn on hosts using different selectable SDKs. This pays a measurable preparation cost to avoid another incomplete input classifier. A refresh on the reviewed branch, a post-push repair, and removing the audit (option C) all lose the publication guarantee.

**D-2. Determine participation from trusted target state.** Match `refs/heads/master` and the Antiphon artifact layout on the pinned target. Use its tracked `Antiphon.sln` and the known driver/graph/index paths as identity markers. A partial target layout with an Antiphon solution or artifact marker is a configuration/record refusal. Deleting paths on the candidate cannot opt out. Foreign repositories without the layout retain the generic land path. The existing FT-5 conflict behavior still applies where it did before. An already-contained source, a confirmed-push replay and a cleanup retry have no new candidate to publish.

**D-3. Pins are reviewed inputs.** Use the committed `LandVerificationBuildGraph.pins.txt` blob. `TargetPins.Check` must accept the candidate's actual XML, including additions, removals and inactive OS branches. When candidate pins differ from `TargetBeforeSha`, require explicit current Clean Final/Full evidence for the same original SHA, repository and subject/ref (including the existing adoption identity), with the exact candidate pins blob present in that reviewed source. Reuse `LandApproval` and the publication-time approval recheck. For inherited pins, verify the target evaluation's recorded pins SHA against the trusted target blob. An inherited, unbound pin change also needs exact Review evidence. Refuse a synthesized union of two differently reviewed pin files until the actual integrated pins are reviewed. File ownership in the diff, a successful build and `--print-pins` each lack this authority. Never generate, stage or commit pins during automatic finalization.

**D-4. Keep strict checking, add a cut-specific advisory.** Proposed spelling is `scripts/antiphon land-graph-audit --rc-cut` on the clean exact cut SHA. The cut consumes this mode's receipt before creating the rc ref. Ordinary `--check` continues to fail for a stale digest. Both modes validate both record formats, the recorded SDK against `HEAD:global.json`, pins blob and actual targets, definition coverage, and the two real solution passes with the docs canary. The cut accepts a well-formed, mutually consistent old digest in the manifest and evaluation record **only** when the selected count matches, the pins retain approval and every fresh check succeeds. The read-only tool checks the HEAD pins blob against the existing evaluation record. The cut operator checks this blob against the last approved pins on the source line. For a changed blob, attach the existing exact-source Review/land receipt and verify the approved commit is represented at the cut (including recorded cherry-pick provenance when applicable). Missing provenance, count drift, missing/malformed records, unclassified files/properties/imports, a docs consumer, failed copy/evaluation, timeout, or an unexpected additional difference blocks the cut. No writes and no automatic rc refresh. The advisory identifies cut SHA, old/new digest, count, pins blob, SDK and successful check phases. Index consistency and other rc gates retain their independent verdicts.

**D-5. Limit the publication claim to the writer.** Route routine master work through land-v2. Git cannot run this server step for an out-of-band push. For the documented Merge-role merge-commit exception, run the same index regeneration and strict approved-pin evaluation on the exact integrated tree before the fast-forward, and repeat against a new parent on rejection. A direct push that skips that procedure is still a bypass. Branch protection changes and rc/host deployment are separate operations. [Merge exception](../../release-gates.md#merging-the-rc-line-into-master-merge-role)

## Performance budget

Apply the [performance standards](../../testing-and-build.md#performance-standards). Historical full-tree evidence gives loaded Linux pass p95 **22.328 s** (3 samples), with a **45 s** timeout per MSBuild pass. Linux canary-copy p95 was **3.751 s** (20 runs), with an **8 s** timeout. Preserve the existing startup grace, platform budgets and watchdog cleanup. Successful full pass pairs observed on Linux took 20–40 s, and four native Windows cut checks took 75–85 s. FT-5 observed about 38 s per full-tree index run, including a 2.3 s warm driver build in one sample. Its existing 180 s execution ceiling covers the probe, build and up to two driver passes. These historical samples do not establish finalizer or CP p95. [Evaluation budgets](../../../tools/Antiphon.LandGraphAudit.Core/EvaluationBudget.cs) · [FT-5 measurements](2026-11-20-fast-track-lane-plan.md) · [Audit receipts](../../investigations/2026-11-24-land-graph-audit-value.md)

Provisionally budget 1–3 min of work per participating master attempt (one index build, one or two index runs, one evaluation pair if current or a second strict pair after a write). Record extra retry attempts separately. A cheap Git fingerprint does not measure this cost. For CP-1 allow about 4–5 min for isolated build/discovery and up to 1 min for its small fixture. For CP-2 allow 4–5 min for build/discovery, about 1 min for fixture preparation/cleanup and 2 min for the bodies. Individual integration methods target 5–30 s on tiny solutions, text/helper assertions under 5 s. Use the staged evaluator and shared test database infrastructure once per invocation, one schema and disposable repository per scenario, and the same origin for the two lands. Reuse the existing strict process limiter. No full-solution-per-test build, external services beyond the test DB, or sleeps to manufacture races.

Treat CP budgets as provisional on CARD-2066. Capture elapsed build-slot queue separately from restore/build/discovery, schema setup, Git I/O, index, audit precheck, both passes/copy, verification, publication, cleanup and unassigned remainder. Use fresh TRX, checkpoint `report.json`, phase timings and structured operation logs correlated by SHA, operation, OS and load. Report the checkpoint slot wait (default 45 min) and runtime land wait (`Landing:BuildSlotWaitMinutes`, default 30 min) separately from execution. A slot timeout ends that attempt. Use a provisional 12 min execution cap for CP-1 and 16 min for CP-2 (`--row-timeout` in minutes per invocation); missing p95 is an estimate. Use measured timings from the first five naturally occurring runs on each applicable lane for an initial nearest-rank p95, refine at 20, and set method/row ceilings near 2× p95. No repeated green run to fill the sample. A projected or observed selection over 30 min goes to Debug with its receipt and phase breakdown before repeating.

## Rollout, risks and rollback

- **Toolchain and throughput.** The root server Dockerfile ships an ASP.NET runtime, while FT-5 probes for a selectable SDK. A runtime-only writer cannot certify every master candidate. Before activating the new writer, qualify index generation and real evaluation in its actual land workspace under a slot with the selected SDK, targeting packs and a matching evaluator. Use the established SDK-equipped landing environment or provision those prerequisites before activation. Report toolchain/slot refusal and leave the ref intact on failure. Measure repository lease occupancy as well as build time during the first lands.
- **Cutover and recovery.** Drain legacy in-flight lands through confirmation or explicit unpublished resolution before changing versions. Never promote an old unverified `Prepared`/`Verified` candidate to a new-style receipt. On cold resumption, if finalization cannot be established, inspect saved-push containment first and strictly revalidate the saved candidate before any new push, or reprepare under a fresh operation against the same approved source. Preserve every published or uncertain push's existing recovery evidence. A crash mid-refresh is covered by the existing unpublished `RebaseStarted` interruption/reset path.
- **Rollback.** Stop admitting new lands, settle issued pushes, and redeploy the last compatible land writer through the normal release path. Restore the strict cut command and the former pre-land/wave procedure together. For a bad published record use a reviewed forward repair on the newly observed target with both byte checks. Preserve historical receipts and remote ancestry. A master land of this card is publication only. No rc move, live configuration change or activation is part of this plan.
