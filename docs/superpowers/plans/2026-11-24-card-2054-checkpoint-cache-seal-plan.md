# CARD-2054 checkpoint cache seal

A checkpoint must be able to run its row from a verified binary even if writing the intermediate-cache seal fails. A build refused admission must leave a previously reusable partition reusable. Keep the worktree gate and the existing 32-byte seal format. Delay invalidation until the build has permission to launch. Publish a new digest from a file that has already flushed **and closed successfully**.

## Decisions

- **D-1. Publish both seal transitions by same-directory replacement.** Stage an empty file for invalidation or a 32-byte digest for certification, flush and close it, then rename it into place. The worktree gate supplies exclusion. This costs one tiny temporary per transition and preserves the previous state if preparation fails. Older readers already understand both the empty and complete states. This also handles the case where the bytes reached the OS but close reported an error.
- **D-2. Reject a catch around the existing in-place writer as the entire fix.** It can protect the current row while leaving a complete digest visible after a failed flush or close. Unbuffered I/O alone has the same uncertainty. **Reject restoring an old digest after a general exception.** Once a build might have run, its inputs may already have changed. Copy-on-write generations with a pointer swap could preserve an older warm generation, but would require another intermediate tree, a reader lifetime protocol and reclamation. Neither open defect needs that cost.
- **D-3. A cache refusal before launch selects the ordinary cold layout once.** A warm transition requires a positive broker grant. A zero exit from a slots-off, unavailable or unleased mode can use only the existing policy's cold path. Preserve the grant, cancellation token, deadline, source checks, original pre-wait ledger and fresh output reservation. A cache error after a qualified build costs future reuse. It does not require a second build.
- **D-4. Deliver the port as a fresh master-based Code subject.** This gives Review the actual integrated source, including current driver, validator and roster changes. Keep the parked branch and historical reviews as evidence. This commission authorizes the new subject. Landing the old candidate or automatically requesting a fifth review of it would skip the new evidence.
- **D-5. Use the eligible Linux lane for the short Code run.** The Plan read `GET /api/runner-defaults` and `GET /api/session-runners`. Resolve placement again at dispatch. Omit the host pin. Native Windows observations wait for a separately available qualification lane. The live desktop qualification has exclusive use of its slot.

## Seal lifecycle and ownership

| Boundary | Owner and operation | Failure or interruption |
|---|---|---|
| Open worktree | `CheckpointApp.ExecuteCoreAsync` opens one stable, exclusive `obj/run.lock` for the scheduler and all its no-build hosts. Create a missing gate exclusively. Check path and opened-handle type, owner and link count. Generate the confined props while holding it. | A contender or an unverifiable gate takes the cold path immediately. Cooperating executors never replace the gate. Kernel close on exit releases it. Independent worktrees have independent gates. |
| Prepare | Under that gate, derive the key from the pre-layout properties. For an existing partition, validate the adjacent regular, single-link, owned seal handle and its exact 32 bytes against a fresh digest of bounded reads of member files. Record the eligible entry. A completely absent pair is only a candidate for creation. | Preflight refusal, unavailable/foreign entry, dangling or partial pair, wrong digest, or unsupported layout selects cold. Before admission, observing or disposing a candidate leaves its existing seal bytes untouched. Temporary files confer no authority. |
| Admit and invalidate | The scheduler captures the ledger before waiting, acquires a permitted build slot, observes clean source, checks project/output, reserves a fresh bin once, checks the owner and admits the original ledger. Prepare the confined driver request including its read-only graph evaluation and log. At the last cancellable check immediately before the potentially writing SDK build starts, perform the cache transition. For a new pair exclusively create its partition and blank seal. For a hit, stage and close an empty sibling. Close the original validation handle before replacing its name (required by Windows sharing). Recheck the destination against the validated regular file identity and publish the empty sibling atomically. Hold the worktree gate across the entire transition. | Denied/timed-out slot, waiting cancellation, ended owner, source/output/ledger or read-only driver preflight refusal leaves an existing valid seal intact and starts zero build children. A refused staging write, close or replacement prevents a warm launch. A refusal before the replacement retains the original seal. Only an accepted transition permits a warm build. A process death or ambiguous start after that point conservatively leaves the partition cold. |
| Build, bind and publish | Run one SDK build in the selected layout. When it exits successfully, join the driver, confirm source and post-build ledger, then write the owned build receipt **including** the output ledger seal. Only then compute the intermediate digest. Exclusively create a confined sibling temporary, write exactly 32 bytes, flush to disk and close successfully. Recheck the empty destination's identity, custody and length under the gate. Publish by same-directory atomic rename over that entry. The rename is the publication point. | Failed build, timeout, cancellation, source/ledger drift or refused receipt leaves the invalid seal and the existing non-green outcome. Publication I/O, access, closed-stream or custody refusal leaves the current verified binary usable and the next run cold. The destination holds the empty seal throughout a write, flush or close fault. A filesystem without atomic same-volume replacement takes the cold path. Avoid copy-overwrite or delete-then-move fallbacks. |
| Dispose and release | One owner detaches each stream before closing it. Include close in the operation's fault boundary, ensure native handle release in cleanup, and make repeat disposal harmless. Only a successfully closed temporary may be renamed. Best-effort cleanup concerns the owned temporary alone. Publish `ResolvedProperties` for the layout that built the binary and release row readiness after the binding is written. `CheckpointApp` releases the gate after its scheduler, hosts and cleanup of in-flight drivers have drained. | Record a bounded phase and reason using the cache diagnostic callback. Contain expected `IOException`, `UnauthorizedAccessException`, `ObjectDisposedException` and typed cache refusals at the cache boundary. Preserve cancellation and real scheduler, receipt and confinement failures. A failed diagnostic cleanup cannot publish a temporary or mask the primary outcome. |

Use the confined exclusive-create primitive already used by `WriteProps`. Seal installation must check the destination's expected identity and disposition on every transition. The props helper's same-bytes shortcut is unsuitable for seal publication. On Windows close all validation handles that deny delete sharing before rename. Keep `run.lock` held and retain the separate regular-file and link checks.

The disk state machine is **absent → invalid → sealed → invalid**. A successful build can publish only from the invalid state it owns. An existing partition with missing, empty or malformed evidence stays cold across retries that lack the original writer's publication authority. A crash before final rename leaves the empty seal. A crash after rename leaves a complete digest that the next opener must recompute. The guarantee covers cooperating processes and ordinary process interruption on the supported local filesystems. Recovery from power loss still requires valid bytes and a matching recomputed digest.

The gate is per executor and the scheduler has one build task, but no-build rows can overlap a later build. Reuse a single build binding for rows sharing a build ID. If distinct build IDs resolve to the same partition while earlier dependent rows may still evaluate its assets, give the later build its private cold layout. A read-only handle to a seal is insufficient to protect readers of the partition.
