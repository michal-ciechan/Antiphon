### Fixture and oracle rules

- **Graph**. Clone the embedded DTO for an execution-aware negative so handlers, topology and sections remain otherwise valid. Keep existing structural validator tests using their small graphs, including the gate `autoRetries` arguments 1, 0, 4, 1.5 and forever. Include an older stored v1 graph with implicit inputs in the compatibility HTTP case. Change one field or relation per negative unless a case identifies the schedule. Use stable code, severity and attached IDs/edge identity as assertions. Bind any new diagnostic literal to the contract in Code.
- **HTTP/PostgreSQL**. Use the real endpoint, scoped DI and the `AntiphonWebAppFactory` pattern, with one container per test host run and one cloned database/host per shared fixture configuration. Use real Npgsql connections on the same database with separate request scopes and independent transactions. Use unique run and revision IDs, controlled repo keys and cleanup of instance-wide assignments between cases. Take before/after snapshots from a fresh scope with tracking disabled. Use the fixture's refusing session runner. Replace GitHub, the models and review-agent backends with existing scripted fakes. Keep secrets out of the fixtures and receipts. Count unexpected external calls with spies.
- **Race barriers**. Follow GH-56's `IntakeRace` approach for acknowledgements, before a contended operation when two participants can both arrive. For the lock-holder/lock-wait schedule, hold the winner at a named transaction barrier and observe the other backend waiting for the actual PostgreSQL lock using fixture-owned connection identities. Release in `finally` and join both requests. Check that no requests shared a context or backend connection. Bound barriers with watchdogs and report arrival and release phases. A parallel launch or wall-clock delay alone does not establish order.
- **Migration**. Use `MigrationTestDatabase.CreateAsync(actualPredecessor, ct)` against the assembly's PostgreSQL container. Confirm predecessor in `__EFMigrationsHistory` and seed old rows via predecessor SQL with the same revision/run/iteration identities carried through the assertions. Use real `IMigrator` and fresh unmodified Npgsql options for tested Up and Down. Compare columns, FKs, partial/unique index predicates, migration history and identified data after refusal and after successful rollback. Keep migrations in separate scratch databases from the application host. Only use the fixture detach helper for its own legacy rewind regression.
- **Executor**. Reuse the scripted code host, decisions and reviewer pattern from `ReviewEndToEndApiTests` with the real PostgreSQL claim and walk. Disable autonomous timers only in deterministic tests and drive the actual hosted service's `RunPendingAsync` against the same database, with new scopes or a second owned executor instance for reclaim. Drive the real poller for polling cases. Use the existing `ControlledTimeProvider` pattern for deadlines and reclaim. Read receipt from a new DB scope and where applicable GET run detail. Never use service invocation count, signal count, status change alone or an in-memory queue as receipt.
- **Client**. Use real Workflow tab/container and inspector, query client and route, with existing Testing Library/Vitest setup and resettable deferred HTTP fixture promises. Switch run, revision, section and pending state through the public UI. A thin canvas adapter may supply deterministic layout bounds and record viewport calls in jsdom. Assert actual selected content, marks and focus target as well as any adapter call. Use actual debounce timers under a fake clock and restore timers/cache/store after each case.

### Delivery inventory

The durable work queue is the committed run, iteration and execution rows. `ReviewExecutorSignal.Wake` accelerates the hosted executor's polling and has no persistence. The existing queue claims Queued runs and stale Running runs with an eligible head. A database row at Pending, a 2xx response and a wake or event acknowledgement all stop short of delivery proof.

| Slice and producer | Destination and persistence boundary | Recovery and actual receipt |
|---|---|---|
| S1 Validate and policy GET → Workflow tab | No background producer. Client query/response identity is run plus revision. | V-2–V-4 cover response and cache scope. |
| S2 manual intake and `ReviewPoller` true-new-run intake | Review executor, via the existing committed run/first iteration/intake and its starting revision. Already-open intake returns that run on the GH-56 path. | V-7 and R-3 drive both producers through the real claim and read a completed revision-specific successor keyed by run, iteration, revision and execution ID. Save only changes the scope assignment. Queue recovery shared with S3 is exercised in V-12. |
| S3 direct Refresh, direct RequestRound and gate decision, including the path that first completes a parked node | Existing queue to the executor. Commit the outgoing interpretation and the matching pending consumption, incoming iteration pin and frontier in the same numbered-boundary transaction. | V-11 and V-12 prove completed work on the expected head and pinned graph. Test busy active work, an already-Queued run before a pass, and producer commit followed by lost signal and worker reclaim. |
| S3 walked gate/wait back edge and same-round event | `FollowAsync/StartIteration` create the next iteration and continue the current walk, or a fresh claimant resumes after worker loss. Pin switch and outgoing/next receipt are separately identifiable in PostgreSQL. | V-11–V-13 read old completion and new downstream completion, and distinguish retry/recheck and later numbered rounds. Inject pre-commit failure (no orphan frontier, assignment still pending) and post-commit worker loss before next step (fresh claimant completes under the pin). |

Use two graph revisions with distinguishable downstream node IDs and outputs even when they share some node IDs. Assert `(runId, iterationId, round, revisionId, nodeExecutionId, nodeId, outcome)`, expected head, completed timestamp and branch/output marker in each delivery method. For fixture code-host receipts use the recorded target and PR/head identity. The model/code-host doubles are substitutes only at those external interfaces. These slices add no Antiphon session input delivery. A separately admitted session-input path would require the matching complete UserPrompt transcript in addition to the real queue receipt.

### Guard inventory

The following witness tables are also the guard inventory. Each numerical row `n` records one `G-n` and its sole `PC-n`. Where one production branch has multiple callers, separate controls break the call site for the named producer. Cases in a single method have no TUnit expansion unless specified. The method asserts the matrix internally with case labels. In a red phase only the stated mutated case may fail. Assert boundary/schedule reachability before the decisive assertion. All 65 controls are required after their corresponding slice lands.

### Positive controls

**Status and execution.** All payloads have **binding required after Code**. Each row names a single variant `PC-n/A`. The binder fills the literal path, symbol, unique context and match count, allowed file set, preimage and mutant hashes, branch reachability trace, exact case/assertion and receipt commands at the confirmed source landing. This document describes compiling production edits and proposes cases. It does not supply raw mutation bytes. A plain **M** marks a *candidate* for mechanical classification once a literal payload, exact runner roster and decisive failure are proven. **H** remains higher-tier-required with the quoted reason until the binder demonstrates closure. Use a separate attempt directory and forced build for baseline, red and restored. Exact .NET filter is `/*/*/ClassName/ExactMethodName` with the class and expanded name below. Baseline and restored execute one, pass one, fail/skip zero, exit 0. The mutant executes one, fails at the stated assertion, skips zero, exit 1. For Vitest use its row's file with a title-anchored `-t ^<title>$` through the same client driver and build-slot. Retain the JSON method roster and asserted message. Its command-row receipt alone supplies no per-case counts. Build error, fixture timeout, wrong failure, zero tests and an accidental extra red all invalidate proof.
