# CARD-0173 — Watermark digest: tell Family when a GitHub issue becomes a card — plan

**Date:** 2026-10-22 · **Card:** CARD-0173 (`f17f4d17-cf93-443d-99b9-07733df843b7`) ·
**Status:** plan; **recommendation: close the card without building** (D-1). If the operator
keeps it, two slices are planned below and S1 is ready to hand to Code.
**Verified against:** `origin/master` @ `158b25606`. Live facts were read from
`https://antiphon.desktop.codeperf.net` on 2026-10-22.

## Verdict

The card wants Family to hear "a household member's new issue became CARD-0172". The data
says that case has never happened:

- **46 cards on the Antiphon board have a linked GitHub issue** (all 1,498 cards were paged,
  archived cards included). **Every one is authored by `michal-ciechan`**, the board's only
  `operator_logins` entry. No household member has ever filed an issue.
- **The newest import is 2026-09-20.** None in the 32 days since.
- **The rest of the card's sketch is already covered or is low value** (ground truth below).
  Comments in from GitHub are pulled only by the bidirectional run, which already announces
  them under CARD-0171. The `external-tracker` revisions are echoes of edits, moves and closes
  the issue author made on GitHub, so that person already knows about them.

A digest built now would only ever tell Family about the operator's own issues. The operator
already sees them on the board. **Recommend closing CARD-0173** and reopening it, with this plan
as the design, the first time a non-operator author files an issue. If the operator wants it
anyway, S1 and S2 below deliver the one valuable line ("issue became a card") in about 1.5 hours
of Code. They need no watermark race handling and no new timestamps on comments.

## Decisions

- **D-1 Close the card; do not build now.** Evidence G-9. Reopen it when the first
  non-operator issue author appears, and hand this plan to Code unchanged. *Rejected:*
  building it speculatively. It needs a migration, a notifier branch and a new message line,
  all to announce the operator's own issues back to them.
- **D-2 If built: one change kind, `Imported`, inside the existing CARD-0171 message.**
  Add `TrackerSyncChangeKind.Imported` and give `TrackerSyncSummaryFormatter` a line
  `- N issue(s) became cards: CARD-0172 (#16), …`, placed first because it is the news the
  household cares about. It uses the existing ≤5 identifiers + `+N more` rule and the 3,500-char
  cap. *Rejected:* a separate digest message or a separate cadence. That is a second sender to the
  same chat with its own channel resolution and its own failure model. The 3-hourly `-Notify`
  run already exists, and import news three hours late is acceptable.
- **D-3 If built: a per-row `ExternalIssueRef.AnnouncedAt` (nullable `timestamp with time
  zone`), not a board watermark.** Pending = `Origin == ExternalImport && AnnouncedAt == null`
  for the board's cards. After a successful send, stamp **exactly the ref ids that went into
  that message**. A failed send stamps nothing, so the imports carry forward. A ref committed by a
  concurrent tick after the read is still null and goes in the next run. This makes the card's
  "not-yet-committed watermark advance" race impossible, rather than just handled. *Rejected:*
  `Board.TrackerNotifiedAt` plus a lag window (G-7). The lag is a guess, and a stuck long
  transaction still loses rows.
- **D-4 Not the away digest** (G-8). *Rejected:* adding a "new cards" section to
  `AwayDigestProjection`. That digest is operator-only by content.
- **D-5 Backfill: the migration stamps every existing row** with
  `UPDATE "ExternalIssueRefs" SET "AnnouncedAt" = "LastSyncedAt"`. Without it, the first digest
  would announce all 46 historical imports. Export-origin rows are stamped as well, so the
  pending query does not depend on `Origin` for history.
- **D-6 Consent and trigger unchanged.** Pending imports are read only inside
  `TrackerSyncNotifier.NotifyAsync`, so only on `?notify=true` triggers, and only for boards
  whose `tracker.notify_channel` resolves. On a board with no `notify_channel`, rows stay pending
  and nothing is stamped. If the channel is configured later, the first message names at most
  5 cards plus `+N more`, which is acceptable.
- **D-7 The gate widens from "boards with changes" to "boards with changes or pending
  imports".** Today `NotifyAsync` filters `run.Boards` to `Changes.Count > 0`. A tick-imported
  card arrives on a run whose own `Changes` is empty, so the pending read must happen before
  that filter. It appends `Imported` items to the board's change list in memory and never
  writes them to the DTO the sync produced.
- **D-8 No new endpoint, setting or Windmill change.** The 3-hourly Windmill run with
  `-Notify` is the cadence.

## Slices (only if D-1 is overruled)

Each slice can land on its own. Master-only: this is a new feature and fixes no defect on the
rc, so no rc port.

### S1 — `ExternalIssueRef.AnnouncedAt` column + backfill (inert, ~30 min)

- `server/Domain/Entities/ExternalIssueRef.cs`: `public DateTime? AnnouncedAt { get; set; }`,
  with an XML doc naming CARD-0173 and D-3.
- `server/Migrations/<UTC stamp after 20261022110953>_AddExternalIssueRefAnnouncedAt.cs`
  (+ Designer, + `AppDbContextModelSnapshot`). Use `dotnet ef migrations add` through
  `build-slot.ps1`. `Up`: one `AddColumn` (nullable) followed by one `Sql` backfill (D-5).
  `Down`: `DropColumn`. The change is additive only.
- `ExternalTrackerSyncService` is unchanged: new imports leave the column null by default.
- Tests: new `tests/Antiphon.Tests/Migrations/ExternalIssueRefAnnouncedAtMigrationTests.cs`,
  following `CommitOnSettleMigrationTests`:
  - `AddExternalIssueRefAnnouncedAt_is_nullable_and_backfills` checks the `UpOperations`:
    one `AddColumnOperation` on `ExternalIssueRefs`/`AnnouncedAt`, `IsNullable`, then one
    `SqlOperation` containing `"AnnouncedAt" = "LastSyncedAt"`. The red witness is a compile
    failure: the migration type does not exist before S1. Commit the test first as WIP.
- Risk: low. Nothing reads the column until S2.

### S2 — announce pending imports in the CARD-0171 message (~60 min)

- `server/Application/Dtos/TrackerSyncDtos.cs`: append `Imported` to `TrackerSyncChangeKind`.
  Appending keeps existing ordinals. The enum is serialized as a string, but do not reorder it.
- `server/Application/Services/TrackerSyncSummaryFormatter.cs`: an `Imported` line, first in
  order, `issue became a card` / `issues became cards`, identifiers plus `(#key)` as for
  `Created`.
- `server/Application/Services/TrackerSyncNotifier.cs`:
  - For every `run.Boards` entry without an `Error`, resolve the config and target as today.
    When a target resolves, load the pending refs (`ExternalIssueRefs.Include(Card)` where
    `Card.BoardId == board && Origin == ExternalImport && AnnouncedAt == null`, ordered by
    `Card.CreatedAt`), project them to `TrackerSyncChange(Imported, Card.Identifier,
    ExternalKey, Url)` and form the board's effective change list (run changes + imported).
    A board with an empty effective list is skipped exactly as today (no
    `notify_channel_unset` entry for a board that changed nothing).
  - After `SendAsync` succeeds for a channel group, set `AnnouncedAt = now` on the collected
    ref ids of every board in that group (tracked load or `ExecuteUpdateAsync` by id set),
    then `SaveChangesAsync`. A stamp failure is logged at Warning and never thrown. The worst
    case is one duplicate announcement next run, which is better than a lost one.
  - Inject `TimeProvider`. It is already registered, and `AwayDigestNotifier` uses it.
- Tests: extend `tests/Antiphon.Tests/Application/TrackerSyncNotifierTests.cs` and
  `TrackerSyncSummaryFormatterTests.cs`. Each is red on S1's tip:
  - `A_pending_import_is_announced_once_on_a_run_with_no_changes`: board with
    `notify_channel`, run result with empty `Changes`, one `ExternalImport` ref with
    `AnnouncedAt == null`. Expect one `SentReplies` entry containing `became a card:
    CARD-` and the ref stamped. A second `NotifyAsync` sends nothing.
  - `A_failed_send_leaves_imports_pending`: throwing producer, then reason `send_failed` and
    `AnnouncedAt` still null. Swap to a working producer: announced on the next call.
  - `Export_origin_and_already_announced_refs_are_not_announced`: an `AntiphonExport` ref and
    an `ExternalImport` ref with `AnnouncedAt` set produce no message.
  - `A_board_without_notify_channel_leaves_imports_pending`: no send, no stamp.
  - Formatter: `Imported_line_comes_first_and_names_cards`. Singular and plural, ≤5 plus
    `+N more`.
- Docs: `docs/workflow-tracker-block.md`, the CARD-0171 paragraph. Replace the closing sentence
  ("GitHub→card creates are out of the signal … that is CARD-0173") with one sentence: pending
  imports (`AnnouncedAt` null) are announced on the next `-Notify` run and stamped only after a
  successful send.
- Risk: medium-low. It is the only writer in the notifier, so it must not throw after a
  committed sync (CARD-0171 D8). Live effect: the first `-Notify` run after deploy sends nothing,
  because the backfill stamped history. Family hears only real new imports.

### Dropped (with reasons)

- `ImportedAt` on `CardComment`, `SyncedAt` scans, `external-tracker` revision scans: G-4..G-6.
- `Board.TrackerNotifiedAt`: G-7 / D-3.
- A separate digest cadence or Windmill job: D-2 / D-8.
