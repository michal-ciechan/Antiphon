## Smallest fix

S1. In the remote `$verify` command in `scripts/deploy-am-service.ps1:352`, replace only the one-shot `/api/channels` assignment with a bounded loop: at most five attempts, two seconds between attempts, and `curl --connect-timeout 2 --max-time 3 -fsS`. Put the assignment in an `if` condition so `set -e` does not abort on an intermediate failure. Capture and print only the successful JSON body, once. If all attempts fail, exit 44 before migration or log checks; 43 already belongs to Compose ambiguity at lines 186-189. This adds at most 23 seconds (five 3-second calls plus four 2-second sleeps). Retain exit 41 for the Running poll and exit 42 for the log scan. A retry exhaustion verdict should say that HTTP readiness was not confirmed, using the exit code and a safe fixed diagnostic, without printing curl response bodies, Compose environments, or arbitrary logs. Keep the existing migration comparison, adapter parsing, monitor check, image comparison, backup, and no-rollback behavior.

S2. Extend `scripts/test-deploy-am-service.ps1` with deterministic local execution of the captured remote verification shell: prepend fake `docker`, `curl`, and `sleep` commands to `PATH`, substitute only the fixed remote working directory with a temporary fixture, and run the command in `sh`. Assert the actual shell exit and output for (a) two curl failures followed by valid channels JSON, (b) five failures giving exit 44 and no migration/log checks, and (c) immediate HTTP success with one curl and no sleep. Stub the migration and log commands; never contact server2. Update the existing fake runner at lines 145-156 to recognize the endpoint independently of the curl option order. Keep the existing fake-runner suite. Add a small `AmServiceDeployReadinessTests` TUnit class under `tests/Antiphon.Tests/Infrastructure` with `[ParallelLimiter<ProcessSpawnLimit>]` that invokes the PowerShell harness and checks its exit, reported case names, and absence of a remote connection. Use three separately reported TUnit methods, one for each case, so the class-level checkpoint has an honest `Min` count of three. TestDesign may simplify the fixture wiring, but the shell command must actually execute, and the transient case must fail against the unmodified one-shot command.

## Verification design

V-1: two refused/failed HTTP attempts followed by valid `/api/channels` JSON produces one channel output line and proceeds to migrations/log scan; the original one-shot command fails this test. V-2: persistent HTTP failure makes exactly five calls, has four bounded sleeps, exits 44, and does not run later checks. V-3: immediate success makes one call and no sleeps. R-1: the existing offline deploy contract suite remains green, including its redaction and preflight assertions. The new TUnit class runs the complete script harness and checks its V-1 to V-3 case markers rather than treating a zero PowerShell exit alone as sufficient. TestDesign should ensure the harness exits nonzero on a missing marker or assertion failure and uses a fresh temporary fixture per invocation.

## Risks

- A retry must not turn a permanent 4xx/5xx into a success or hide the final failure. The five-call bound and distinct exit 44 make the unresolved readiness state visible; later checks still require a real successful JSON response.
- `set -eu` and PowerShell interpolation both affect the generated shell text. Test the executed command rather than only searching for retry tokens; preserve the first output line as the channel JSON because `scripts/deploy-am-service.ps1:354-358` parses it positionally.
- The target shell is Linux `sh`; a Windows host needs an available `sh` for the behavioral fixture. The deploy script itself remains ASCII-only and compatible with Windows PowerShell 5.1.
