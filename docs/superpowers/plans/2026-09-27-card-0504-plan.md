## Smallest fix

S1. In the remote `$verify` command in `scripts/deploy-am-service.ps1:352`, replace only the one-shot `/api/channels` assignment with a bounded loop: at most five attempts, two seconds between attempts, and `curl --connect-timeout 2 --max-time 3 -fsS`. Put the assignment in an `if` condition so `set -e` does not abort on an intermediate failure. Capture and print only the successful JSON body, once. If all attempts fail, exit 44 before migration or log checks; 43 already belongs to Compose ambiguity at lines 186-189. This adds at most 23 seconds (five 3-second calls plus four 2-second sleeps). Retain exit 41 for the Running poll and exit 42 for the log scan. A retry exhaustion verdict should say that HTTP readiness was not confirmed, using the exit code and a safe fixed diagnostic, without printing curl response bodies, Compose environments, or arbitrary logs. Keep the existing migration comparison, adapter parsing, monitor check, image comparison, backup, and no-rollback behavior.

S2. Extend `scripts/test-deploy-am-service.ps1` with deterministic local execution of the captured remote verification shell: prepend fake `docker`, `curl`, and `sleep` commands to `PATH`, substitute only the fixed remote working directory with a temporary fixture, and run the command in `sh`. Assert the actual shell exit and output for (a) two curl failures followed by valid channels JSON, (b) five failures giving exit 44 and no migration/log checks, and (c) immediate HTTP success with one curl and no sleep. Stub the migration and log commands; never contact server2. Update the existing fake runner at lines 145-156 to recognize the endpoint independently of the curl option order. Keep the existing fake-runner suite. Add a small `AmServiceDeployReadinessTests` TUnit class under `tests/Antiphon.Tests/Infrastructure` with `[ParallelLimiter<ProcessSpawnLimit>]` that invokes the PowerShell harness and checks its exit, reported case names, and absence of a remote connection. Use three separately reported TUnit methods, one for each case, so the class-level checkpoint has an honest `Min` count of three. TestDesign may simplify the fixture wiring, but the shell command must actually execute, and the transient case must fail against the unmodified one-shot command.

## Verification design

V-1: two refused/failed HTTP attempts followed by valid `/api/channels` JSON produces one channel output line and proceeds to migrations/log scan; the original one-shot command fails this test. V-2: persistent HTTP failure makes exactly five calls, has four bounded sleeps, exits 44, and does not run later checks. V-3: immediate success makes one call and no sleeps. R-1: the existing offline deploy contract suite remains green, including its redaction and preflight assertions. The new TUnit class runs the complete script harness and checks its V-1 to V-3 case markers rather than treating a zero PowerShell exit alone as sufficient. TestDesign should ensure the harness exits nonzero on a missing marker or assertion failure and uses a fresh temporary fixture per invocation.

## Risks

- A retry must not turn a permanent 4xx/5xx into a success or hide the final failure. The five-call bound and distinct exit 44 make the unresolved readiness state visible; later checks still require a real successful JSON response.
- `set -eu` and PowerShell interpolation both affect the generated shell text. Test the executed command rather than only searching for retry tokens; preserve the first output line as the channel JSON because `scripts/deploy-am-service.ps1:354-358` parses it positionally.
- The target shell is Linux `sh`; a Windows host needs an available `sh` for the behavioral fixture. The deploy script itself remains ASCII-only and compatible with Windows PowerShell 5.1.

Each method runs only its corresponding readiness case; method 3 also runs the complete legacy suite once. Fixture requirements (implemented in S2):

- Dot-source the production script and call `Invoke-AmServiceDeployment` with all three fake runners explicitly supplied. Only the captured technical-verification command containing `/api/channels` is executed locally. Every other remote command, SCP operation, server identity/version read and monitor probe remains fake; unexpected commands fail closed. Stub `ssh`/`scp` in the child PATH to record and reject accidental native use, and require zero such calls. This harness must never invoke the deploy script's standalone entry point, live preflight, Docker daemon or a real broker.
- Run the captured command under real POSIX `sh`, keeping `set -eu`, substitutions, loop, curl arguments and subsequent verification intact. Replace only the fixed `cd '/home/mc/antiphon-messaging'` target and the single `http://localhost:18090/api/channels` URL with fixture-owned values, requiring exactly one replacement of each. Do not implement a second retry loop in the fixture. Use a fresh temporary directory per subcase with LF shell files and correctly quoted paths.
- The TUnit fixture owns a socket bound exclusively to `127.0.0.1:0` and records the chosen port without releasing it. For refused connections, bind without listening. After the configured failed attempt has completed, start listening on that same socket and acknowledge readiness before the curl wrapper returns that attempt's failure to the shell. Coordinate by fixture journal/acknowledgement files with bounded waits, not a guessed startup delay. The first two curl calls therefore encounter a real refusal; attempt 3 deterministically reaches the HTTP stub. The final-attempt boundary uses four refusals then success on attempt 5.
- For HTTP cases the stub listens before shell launch and accepts only `GET /api/channels`. Return the literal success body `[{"channel":"telegram"},{"channel":"slack"}]` with a valid HTTP response. Timeout mode accepts and reads each request but sends no response until curl disconnects/cancellation; 503 mode returns a fixed synthetic body containing `c504-response-must-not-leak`. All bindings and requests stay on the owned loopback port.
- Prepend an executable curl wrapper that records argv, attempt number, completion/exit and order, then delegates to the absolute real curl executable; it must not invent responses, failures, retry counts or timeouts. Reject any URL except the assigned loopback endpoint. Use an isolated curl configuration (`--disable` first) and disable proxy routing for this child. Keep the production `-f`, connect/total timeouts and retry decisions observable. Record native exit 7 for refusal, 28 for the unanswered response, and 22 for HTTP 503. A separate journal receives instrumentation, never shell stdout/stderr.
- Fake `docker inspect ...State.Running...` returns `true` immediately and records its position before HTTP attempt 1. Fake migration and startup-log commands record their execution and return fixture migration IDs/clean logs; reject any other local Docker command. The `sleep` wrapper records its arguments and delegates to absolute real sleep. Thus requested backoff and its placement are verified without shortening production delays. Container-running sleeps are absent in these cases.
- Merge shell stderr into stdout **at process execution**, as real SSH does; do not concatenate independently buffered streams afterward. Feed this merged result and actual exit back to the fake `SshRunner`. Verify both raw shell results and the surrounding deployment outcome. Drain the PowerShell child's two output streams concurrently. Strip inherited task credentials from child environment; do not print environments or remote command payloads.
- Own every socket, accepted connection, child and temporary path. Use a 45-second watchdog per verification-shell execution (23-second designed HTTP budget plus scheduling margin), bounded handshake waits and a 300-second outer harness deadline. On failure cancel/dispose the stub, terminate only the fixture's child tree, await exit/drain, then remove only its own temporary directory. A watchdog expiry is a test failure, not readiness exhaustion. Record failed fixtures' safe counters/exit/output before cleanup. Require `pwsh`, `sh`, real curl and existing archive tools; Windows uses an available POSIX shell with its path conversion handled in the fixture, not a Linux-only skip.
