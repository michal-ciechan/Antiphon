## Decisions

D-1 to D-10 (G1-G3 plan) stand. New:

- **D-11 (helper): `scripts/lib/windows-phone-home-env.ps1`, pure and 5.1-compatible.** It does no
  file IO, makes no `Get-Command` call, and makes no HTTP call. Functions:
  - `New-WindowsPhoneHomeRunnerEnv -RunnerId -Root -Port -Capacity -ServerOrigin -ClaudeHome -CodexHome -GrokHome -PwshPath -Executables`
    returns the ordered table that `start-windows-phone-home-runner.ps1:75-97` builds today, key for key.
  - `ConvertFrom-WindowsPhoneHomeConfig -Text <json> [-RequirePort 17204]` returns
    `@{ ok; reason; runnerId; serverOrigin; capacity; root; port }`.
  - `Resolve-SessionRunnerAutostartPlan -ConfigText <string or $null> -ExplicitConfigPath <bool> -SecretPresent <bool> -HomeDir -PwshPath -Executables -RepoRoot`
    returns `@{ mode = 'direct' | 'phone-home' | 'refused'; reason; env; exeArgs }`.
  - `Get-WindowsPhoneHomeLaunchRefusal -ConfigPresent <bool> -ConfigPath` returns `$null` or the refusal text (D-15).
  - The callers do the IO: read the config file if it exists, `Test-Path` the secret, resolve `pwsh`,
    `claude`, `codex` and `grok`. That keeps every rule testable on Linux pwsh.
  - *Rejected: put the logic in `autostart-session-runner.ps1` and test it by running the script.* The
    script blocks in `run-daemon.ps1` and launches `cmd.exe`, so it cannot run on server2.
- **D-12 (config schema, closed).** `phone-home.json` is ASCII JSON with exactly these keys:

  | Key | Required | Rule |
  |---|---|---|
  | `runnerId` | yes | `^[a-z0-9][a-z0-9-]{0,63}$`, not `local` or `desktop` (ordinal-ignore-case) |
  | `serverOrigin` | yes | absolute `https://` URI, no path beyond `/`, no query, no user info |
  | `capacity` | yes | integer 1 or 2. The compose `MaxCapacity` is 2 (G1-G3 D-5) |
  | `root` | no, default `C:\Antiphon\runner` | drive-rooted absolute, no UNC or device path |
  | `port` | no, default 17204 | 17204 or 17214 only |

  - An unknown key is refused (`unknown-key:<name>`). That covers any `secret` or `sharedSecret` key:
    the secret stays in `<root>\secrets\phone-home`.
  - Malformed JSON is `config-malformed`.
  - `-RequirePort 17204` applies when the autostart script uses its **default** config path, so the
    phase 2 file can never move the runner off the broker address (D-9). Refusal: `port-not-broker`.
  - Missing secret file: `secret-missing`. The helper is told only whether the file exists. Nothing
    reads its content except the runner.
- **D-13 (phase 1 runs the phase 2 code path).** Phase 1 runs from `C:\Antiphon\runner\app`.
  - Command: `pwsh -NoProfile -File C:\Antiphon\runner\app\scripts\autostart-session-runner.ps1 -PhoneHomeConfigPath C:\Antiphon\runner\phone-home.phase1.json`,
    by hand from a normal terminal.
  - The phase 1 config: `runnerId desktop-win`, `serverOrigin` the public origin, `capacity 1`, `port 17214`.
  - Through `run-daemon.ps1`, this gives crash relaunch and build-before-launch, leased from the 17204
    broker. It writes the clone's own pid and state files (`C:\Antiphon\runner\app\logs\session-runner.*`).
  - The main checkout's restart census never matches the clone's executable path (T-9), and the
    AppHost never adopts 17214.
  - *Rejected: `start-windows-phone-home-runner.ps1 -Port 17214` (G1-G3 D-7).* It has no crash
    relaunch, and the code that takes 17204 at the window would run for the first time at the window.
    It stays the fallback if S4 misses the rc cut (see Order).
  - *Rejected: a second Scheduled Task for phase 1.* Same reason as G1-G3 D-8.
- **D-14 (autostart behaviour).**
  - `autostart-session-runner.ps1` gains `param([string]$PhoneHomeConfigPath = 'C:\Antiphon\runner\phone-home.json')`.
  - Config absent: today's direct runner, byte for byte. No `PhoneHome__*` variable is set, and the
    args stay `--urls http://localhost:17204`.
  - Config present and valid: set the env in the process, then `run-daemon.ps1` with `--urls http://localhost:<port>`.
  - Config present and refused: append `[autostart] phone-home config refused: <reason>` to
    `logs/session-runner.log`, exit 2, and start nothing. **There is no fallback to the direct runner**:
    a runner under the wrong identity is worse than no runner. Build leases then go `unleased` after
    the grace period, which `build-slot.ps1` already reports.
  - The task's `RestartCount 3` retries and then stops, which is visible in Task Scheduler.
- **D-15 (AppHost launch guard).**
  - `restart-apphost.ps1` checks once, right after its worktree check and before any stop, lock or
    POST: when `C:\Antiphon\runner\phone-home.json` exists, it refuses with exit 3,
    `REFUSED: phone-home-config-present`, followed by the recovery: delete the file, run
    `restart-session-runner.ps1 -Hard`, then retry. `-StopOnly` (with or without `-WhatIf`) is still
    allowed, because stopping cannot adopt.
  - `dev-aspire.ps1` makes the same check after its worktree check and before the launch lock. It
    refuses with exit 3. It is the one launch point that the restart, the watchdog and the logon task all reach.
  - It checks only the phase 2 path. The phase 1 file (`phone-home.phase1.json`) coexists with the
    desktop AppHost by design.
  - The guard text must not contain `restart-linux-server` (T-21).
  - *Rejected: the runbook rule alone (G1-G3 D-10).* Rollback runs under stress, and one missed line
    gives one runner two identities (T-14).
  - *Rejected: a guard in `Antiphon.AppHost` C#.* That would put a desktop-config file read into the
    AppHost, and change the AppHost build for a rollback-only rule.
- **D-16 (capacity).**
  - Phase 1: `capacity 1`, with desktop user-secrets `MaxCapacity=1`.
  - Phase 2: `capacity 1` at the window, raised to 2 by the operator (edit the JSON, then
    `restart-session-runner.ps1 -Hard`, between Full runs) after one Full run has finished beside it.
  - The compose `MaxCapacity` of 2 is the ceiling.
  - *Rejected: 2 from the start.* The desktop host runs the Windows Full run, and the CPU figure with
    three Windows seats is unmeasured.
- **D-17 (S5 rehearsal shape).** A real R-2 rehearsal on production:
  - window phases 0, 1 and 2 against the production database;
  - **no** origin switch;
  - **no** agent re-home;
  - **no** project-path PUT;
  - the protector proven with a throwaway API key name (T-20);
  - an optional phase 2 `desktop-win` against a test hostname (RH-3);
  - then R-2 back to the desktop, with every step timed.

  Rejected alternatives:
  - *A staging-only rehearsal.* It cannot exercise the sidecar, the `desktop-win` entry, the X.509
    ring or the gate (T-19). Staging stays precondition P-3.
  - *The full window with R-3 as the planned rollback.* The vhost switch and its TTL add risk before
    the first measured R-2.
  - *Pointing the production compose at a scratch Postgres.* The compose joins `antiphon-server2` and
    names `Host=postgres`. Overriding that breaks the closed compose list (`docs/docker-stack.md`),
    and a mistake gives a second writer.
- **D-18 (operator token).** The host `OPERATOR_TOKEN_FILE` holds the **same** value as the desktop
  `%LOCALAPPDATA%\Antiphon\operator-token`. Parent step 2.3 then becomes a check, and R-2 needs no
  token restore. The value is copied without display, by the operator.
- **D-19 (harness and wrapper).** `scripts/test-windows-phone-home-runner.ps1` (the name the G1-G3
  plan fixed) runs `-Case <name>` and prints `PASS C1744G3 <row>` lines and the C487 trailer, in the
  shape of `scripts/test-qualification-supervisor.ps1`.
  - It is wrapped by `tests/Antiphon.Tests/Scripts/C1744G3PhoneHomeSupervisionTests.cs`, which calls
    `ScriptHarness.RunHarnessCaseAsync` with `[Category("Unit")]` and `[ParallelLimiter<ProcessSpawnLimit>]`.
  - The class has **no** `NativeLinuxOnly`: the cases are pure functions and file parses, so the
    Windows rc lane runs them too, and no policy row or reseal is needed.
  - The harness creates one `c1744g3-<guid>` temp directory and removes only the exact paths it owns.
  - *Rejected: a bare pwsh row only (G1-G3 CP-7/CP-8).* rc qualification would never run it again.
