# CARD-0767 — Isolate channel wake drains by agent

Baseline: `a56c3a7e7889f120630faa412d51b40f8c3458d0`, verified equal to `origin/master` with `git ls-remote` on 2026-09-27. The local `master` ref is older (`25564530`) and is not the comparison baseline. CARD-0767 has no history revisions. This plan changes no production code or tests.

## Verified findings

1. The card is **still valid**. `ChannelBridgeService.DrainPendingAsync` takes one process-wide `_drainGate`, selects up to 64 pending **rows**, and awaits `ProcessInboundAsync` for each before releasing it (`server/Application/Services/ChannelBridgeService.cs:195-237`). Each row obtains its own agent advisory lock and calls `EnsureAgentSessionAsync` (`:240-257`). That method limits a *single call* to one `StartAsync`, but can poll until `AgentStartTimeoutSeconds` (default 90) and then waits 12 seconds after a fresh Running start (`:630-695`; `server/Application/Settings/ChannelBridgeSettings.cs:19-22`). Thus multiple pending rows for one failing agent each spend a wake window in one pass; a healthy agent later in the page waits behind them. A healthy agent beyond row 64 is not even selected until another pass.
2. CARD-0593's plan explicitly required one start attempt and a bounded pending-inbound drain (`docs/superpowers/plans/2026-09-26-card-0593-plan.md:24-28`). Its **one attempt per `EnsureAgentSessionAsync` invocation** is already implemented (`ChannelBridgeService.cs:633,679-689`); the stale part of CARD-0767 is any implication that one invocation itself retries `StartAsync`. The missing boundary is **one wake per agent per pass** and isolation of other agents while it waits. The bridge's direct `HandleInboundAsync` entry point is internal/test-oriented (`:123-128`); production broker intake commits the envelope and signals the worker (`:70-80`).
3. Durable acceptance is already in place: a complete deliverable envelope and captured binding commit before acknowledgement (`ChannelBridgeService.cs:130-167`); failed wakes leave it pending (`:275-280`). An agent-scoped PostgreSQL advisory claim already prevents competing bridge instances from waking the same agent concurrently (`:248-250,327-365`). Debounced handoff enqueues a marked `WhenIdle` Channel owner and then flushes (`:413-424`); source bytes stay in the inbound journal. The only delivery verdict remains a complete matching recipient `UserPrompt` past the queue attempt floor (`docs/telegram.md:26-36`; `docs/session-runtime-invariants.md:82-91`).
4. Recovery tests already cover timeout persistence, restart, a 65-row page and transcript-based recovery (`tests/Antiphon.Tests/Application/ChannelInboundRecoveryTests.cs:83-119,155-223,628-662`). They use one recipient at a time, so they do not prove cross-agent latency or one wake for a batch. The existing 65-row test asserts eventual scanning, not prompt delivery by a second healthy agent. No production patch or existing test closes this card.

## Smallest fix

### S1. Give each agent one wake in a bounded drain pass

In `ChannelBridgeService`, select **agent heads** (minimum pending `AcceptanceSequence` per `AgentId`) rather than the first 64 raw rows. Page distinct agents in FIFO order with a bounded cursor/wrap so a permanently held agent cannot monopolize later pages. For each selected agent, read a bounded FIFO batch of its pending rows. Keep the current per-agent PostgreSQL advisory claim while deciding the wake and scheduling that group's handoff; re-read pending state after acquiring it. Resolve the agent's Running session once, with at most one `StartAsync` and the current 90-second poll/12-second fresh-start settle. On a failed wake, leave every envelope pending and apply the existing per-inbound timeout/hold incident policy without issuing another start in that pass. On success, feed the rows in acceptance order through the existing debounce/queue ownership path; preserve idempotent source mapping and attachment names. A later debounce callback still relies on the durable queue source key for idempotency. A claim miss leaves rows for a later pass.

Replace the process-wide lock around wake/queue I/O with a short gate for only cursor/page selection and update. Run selected **distinct-agent** groups concurrently, with an explicit small concurrency cap (e.g. 4) and no shared gate held during a wake, debounce callback or queue flush. A failing agent may occupy one slot for its configured deadline but cannot block a concurrently selected healthy agent. Keep the scan cursor moving across agent heads and wrap on the next scan so a page full of pending rows from one agent cannot hide a healthy agent. Continue the owned-queue flush sweep after grouped materialization; run it without a global wake gate and do not treat `FlushSessionAsync` as a delivery receipt. Preserve cancellation and ensure all launched group tasks are awaited on worker stop.

The direct internal `HandleInboundAsync` path may reuse the one-agent group function. The existing advisory claim is the cross-instance exclusion; a local semaphore is only a concurrency bound, not delivery authority. Do not add a new table, migration, queue status or receipt heuristic.

### S2. Pin the failure and ordinary bridge behavior

Add a two-agent offline integration fixture to `ChannelInboundRecoveryTests`: seed at least two accepted messages for a non-Running failing agent before one accepted message for a Running healthy agent (also place the healthy head after 64 failing rows in one variant). Drive one real `DrainPendingAsync` pass with a controlled clock/barrier. Before advancing through the failing agent's wake deadline, require the healthy agent's marked queue owner and an ingested **complete matching `UserPrompt`** on its own session. After advancing the deadline, require one wake/start attempt for the failing agent in that pass, all its envelopes still pending, no failed-agent terminal input, and the existing incident behavior. A second pass may retry once, proving the bound is per pass rather than permanent suppression. Force the old implementation red by waiting for the healthy receipt while the failing wake is held; do not assert on enqueue or adapter input alone.

Use the existing isolated-schema `BridgeQueueHarness`, its fake runner/adapter and transcript sync seam (`ChannelInboundRecoveryTests.cs:31-79`); make the healthy session available to the bridge's runtime. Keep `ChannelBridgeTests` green for ordinary routing, batching and replies. TestDesign may split the two-agent checks into two methods to keep failure diagnostics clear, but the class-level checkpoint remains fixed below.

## Risks and TestDesign decisions

- Preserve FIFO within each agent and the debouncer's same-sender grouping. Parallelize only across distinct agents; an agent's advisory claim must cover wake and handoff scheduling, while the existing durable queue key protects later debounce materialization. Claim misses remain pending rather than advancing delivery state.
- Do not lose a signal while a prior pass is waiting. The periodic backstop and cursor wrap must eventually rescan failed/claim-missed rows; select by pending rows, not by a process-only cache. Avoid holding a shared `DbContext` across concurrent tasks.
- A concurrency cap bounds DB/runner pressure; it must allow at least two agent groups at once. Fair agent-head paging prevents one agent's backlog from filling the page. A very large number of failing **distinct** agents may still consume all slots until their bounded deadlines; test the explicit one-failing/one-healthy guarantee and retain the periodic recovery path.
- A timeout, `Starting` state or advisory-lock miss says nothing about delivery. Keep `ChannelInbound` bytes and queue attempt evidence; only a complete matching `UserPrompt` confirms the healthy message. Do not relax `SessionMessageQueueService` receipt or retry rules.

### Deterministic fixture and receipt oracle

Keep the fixture local to `tests/Antiphon.Tests/Application/ChannelInboundRecoveryTests.cs`, extending shared helpers only where necessary. Use one isolated schema and one provider/runtime/queue for A and B, different working directories and channels, `AlwaysOn=false`, and a separately registered fake adapter for B. Insert B through normal test setup, register `Runtime.Register(BSession, BAdapter)`, and bind its own channel. Every assertion is scoped to these identities. A second bridge for R-3 uses a separate DI provider/DB connection against this schema; it must contend on PostgreSQL, not share a local lock.

Add a test-local bridge-construction overload accepting a **bridge-only** timer-capable fake `TimeProvider`. Keep the queue/runtime on their advancing harness clock. Wrap the fake's `CreateTimer` to signal registration of the bridge's two-second wake poll and ten-second worker backstop. The controller advances registered timers, awaits each corresponding gate/event, and never spins on DB state with sleeps. Do not give the entire queue graph a frozen `GetUtcNow` provider with real timers (CARD-0222). A fake whose timers never get driven is also invalid. Use completion sources with `RunContinuationsAsynchronously`, EF interception for commit/read boundaries, and explicit release in `finally`. Diagnostic `WaitAsync` timeouts may fail a stuck test; elapsed real time must never release a barrier or satisfy an ordering assertion.

For V-1, make A have no live session/pointer and intercept its parameter-bound `SELECT * FROM "Agents" ... FOR UPDATE` at the **first** `AgentControlService.StartAsync` lock, after seeding is complete. Increment `startEntries[A]` and throw a named synthetic start-refusal exception before executing that statement. `EnsureAgentSessionAsync` calls real control; no launch task or session is created. A remains start-eligible on every invocation, so one entry corresponds to one wake and an extra per-row wake cannot hide behind `Starting` or launch ownership. Scope the interceptor to A and this SQL shape, and assert the intended fault was hit. This is an external database fault seam, not a mocked bridge. V-2 separately proves the actual configured timeout path. Keep the existing successful fake launch/quota test for positive start behavior.

For V-2, A has a persisted `Starting` session, bridge timeout 90 seconds, and B is Running/idle. Freeze only the bridge clock at t0; wait until A registers its wake poll. B's submission callback reads the real queue attempt and publishes a `SessionRunnerTranscriptEvent(UserPrompt)` with the **submitted** body to B's runner snapshot, then awaits `SyncTranscriptAsync`. Signal `BReceiptPersisted` only after a fresh DB read finds it. Seed an initial B TurnEnd so the queue has a nonzero observable floor. Receipt must already exist **before** this advance. Do not await `DrainPendingAsync` before checking B. Parameter cases are 2 and **64** earlier A rows, then B (65 total in the latter); commit A rows individually or assert their persisted `AcceptanceSequence`s all precede B. No fabricated order from GUIDs/timestamps. Seed envelopes as accepted journal rows for controlled page setup; R-1 separately tests real broker acceptance.

Generalize the receipt installer by explicit `(sessionId, adapter)` and keep per-session sequence/snapshot updates serialized. Use a concurrent dictionary/lock for `EmptyRunnerClient` transcript access, or a local thread-safe runner substituted into the same provider; independent adapters must never share a mutable composer buffer. Default receipts include a TurnEnd only in tests needing subsequent idle deliveries; the latency test waits for the complete UserPrompt itself. Register a completion gate after each ingested receipt instead of copying `WaitForAsync`/`Task.Delay(25)` into new work.
