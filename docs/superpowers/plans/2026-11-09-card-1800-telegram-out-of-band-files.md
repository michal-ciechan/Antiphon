# CARD-1800 plan: Telegram out-of-band file transfer (slice 2 of CARD-1799)

Date 2026-11-09. Plan task `121cbdd3` (Frontier). Base `origin/master`
`d2ff7e8d4d63d67cf611b2c567c2da97416bd8fa`. Documents only: no product code, nothing deployed,
started or restarted on any host, no secret read or printed. Root cause:
[2026-11-08 investigation](../../investigations/2026-11-08-telegram-attachment-not-reaching-bot.md)
(on `origin/feat/card-task-aff9b6f2`). Slice 1 is CARD-1799 (branch `feat/card-task-09726111`,
Review round 2 at `2ce435545`); its over-cap note, `Attachment.InlineLimitBytes`,
`AttachmentSize` and the sender notice are the baseline this plan extends. Topology facts come from
the [CARD-1746 broker decision](../../investigations/2026-11-07-decide-card-1746-broker-placement.md)
and the [CARD-1744 cutover plan](2026-11-08-card-1744-cutover-plan.md).

## Plain-English summary

- Today a Telegram file over 14 MiB never leaves the gateway: the bytes would travel base64 inside
  one 20 MiB Kafka record, so the gateway skips the download and the agent gets a note. Telegram
  itself serves bot downloads up to 20 MB. This plan carries the bytes outside the bus.
- The gateway (`am-service` on server2) downloads a file between the inline cap and 20 MiB into
  its own Docker volume and publishes a small **reference** on the bus instead of the bytes: a
  key, an HTTPS-style fetch URL on the gateway's existing port 18090, the size, the MIME type and a
  SHA-256. The server fetches the file from that URL, checks the hash and writes it into the agent
  inbox exactly where small files already land. The session runner reads the inbox as it does today.
- The brief asked for a volume shared between the gateway, the server and the runner. That only
  works once the server also runs on server2 (CARD-1744 window 2, not yet scheduled). The bus
  consumer today is the desktop AppHost server, which can reach server2 port 18090 but can never
  mount a server2 Docker volume. The gateway serving its own store over HTTP works in both
  topologies with one code path, so that is the design (D-1). A mounted-path reader can be added
  later from the same reference key; it is not in this plan.
- Files up to the inline cap keep today's inline path, byte for byte. Old gateways and old servers
  keep working: the new field is optional and unknown properties are already ignored on both sides.
- Caps: inline 14 MiB (unchanged), out-of-band 20 MiB (Telegram's `getFile` limit), 256 MiB per chat
  per rolling 24 h, 2 GiB for the whole store, 72 h retention. Over any of these the sender still
  gets the CARD-1799 notice, now naming the limit that applied, and the agent note names the file.
- Security: keys are generated by the gateway (date plus GUID, never from channel data); the fetch
  URL carries a per-file random token checked in constant time; the server fetches only from an
  operator-allowlisted origin, verifies size and SHA-256, writes through the existing sanitised
  inbox filename, never executes anything and never logs the token. Virus scanning stays out of scope.
- No database migration. Deploy the server before the gateway; the gateway store stays off until
  its two settings are set. Operator-only steps are listed at the end: one compose edit on server2,
  one allowlist setting on the server, the existing `deploy-am-service.ps1` run, one manual smoke.

## Design

### Components and data flow

```
Telegram ──getFile──▶ am-service (gateway, server2)
                        │  size <= 14 MiB: inline bytes (unchanged)
                        │  14 MiB < size <= 20 MiB: stream to /inbound-files/<yyyyMMdd>/<guid>.bin.part
                        │      rename -> .bin, write <guid>.meta.json {token, name, mime, size, sha256, chat, expiresAt}
                        ▼
                 channels.inbound: Attachment { Content: null, Reference: { store, key, url, size, sha256, expiresAt } }
                        ▼
                 Antiphon server (bridge): origin allowlisted? -> GET url (60 s) -> <inbox>/<id>-<n>-<name>.part
                        │  size and sha256 verified -> rename -> "[file attached: <path>]"
                        │  any failure -> reason note + one sender notice (ChatChannelService.SendAsync)
                        ▼
                 agent reads the inbox (desktop disk today; shared `work` volume in topology B)
am-service sweep (15 min): delete blobs and metas past expiresAt; enforce 2 GiB oldest-first.
```

### Wire contract (additive, S1)

`src/Antiphon.Messaging/ChannelMessage.cs`:

```csharp
public sealed record Attachment
{
    // ... existing members, including InlineLimitBytes (CARD-1799) ...

    /// <summary>Out-of-band location of the bytes when the gateway stored the file instead of inlining it
    /// (CARD-1800). Null for an inlined file, a metadata-only file or a gateway that predates the field.</summary>
    public AttachmentReference? Reference { get; init; }
}

public sealed record AttachmentReference
{
    /// <summary>Store kind. v1 defines <c>gateway-http</c>: fetch <see cref="Url"/> with a plain GET.</summary>
    public required string Store { get; init; }
    /// <summary>Gateway-generated key, <c>yyyyMMdd/&lt;32 hex&gt;</c>. Never channel data.</summary>
    public required string Key { get; init; }
    /// <summary>Absolute fetch URL including the capability token. Treat as a secret: never log it.</summary>
    public required string Url { get; init; }
    public required long Size { get; init; }
    /// <summary>Lowercase hex SHA-256 of the stored bytes.</summary>
    public required string Sha256 { get; init; }
    public required DateTimeOffset ExpiresAt { get; init; }
}
```

### Gateway store (S2)

`src/Antiphon.Messaging.Gateway/InboundFiles/`:

- `InboundFileStoreOptions` (section `InboundFiles`): `Root`, `PublicBaseUrl`, `MaxBytes` = 20 MiB,
  `RetentionHours` = 72, `SweepMinutes` = 15, `MaxStoreBytes` = 2 GiB, `PerConversationWindowBytes` = 256 MiB,
  `PerConversationWindowHours` = 24, `DownloadTimeoutSeconds` = 120. Enabled only when `Root` **and**
  `PublicBaseUrl` are set; the validator refuses one without the other, a relative `Root`, a
  `PublicBaseUrl` that is not absolute `http`/`https` without path or query, and `MaxBytes` outside
  1 byte..1 GiB.
- `FileSystemInboundFileStore : IInboundFileStore`. Layout `<Root>/<yyyyMMdd>/<guid:N>.bin` and
  `<guid:N>.meta.json` (`key, token, name, mime, size, sha256, conversationId, createdAt, expiresAt`).
  `PutAsync` creates the day directory, writes `<guid:N>.bin.part` while hashing (SHA-256) and counting;
  aborts and deletes the part at `MaxBytes + 1`; `File.Move` to `.bin` (same directory, atomic), then
  writes the meta. `Key` = `yyyyMMdd/<guid:N>`; `Url` = `{PublicBaseUrl}/api/files/{key}?t={token}`;
  token = 32 bytes from `RandomNumberGenerator`, base64url. `TryOpen(key, token)` validates the key
  against `^\d{8}/[0-9a-f]{32}$` before any path operation, reads the meta, compares the token with
  `CryptographicOperations.FixedTimeEquals`, refuses past `expiresAt`, and returns a read-only
  `FileStream` plus the meta, else null. Quota: an in-memory per-conversation list of
  `(createdAt, bytes)` pruned to the window; a `TimeProvider` is injected for tests.
- `InboundFileRetentionService : BackgroundService`: every `SweepMinutes`, delete `.bin`/`.meta.json`
  pairs past `expiresAt` and any `.part` older than one hour; then, while the store total is over
  `MaxStoreBytes`, delete the oldest pair. One pass is bounded by a 5-minute cancellation. Logs
  counts and bytes, never names.
- Registration: `services.AddAntiphonInboundFileStore(configuration)` registers the options,
  validator, the store and the sweep only when enabled; otherwise a `DisabledInboundFileStore`
  (`Enabled=false`). `PublicAPI.Unshipped.txt` in Gateway gains the public surface.

### Gateway file route (S4)

`src/Antiphon.Messaging.Service/InboundFileEndpoint.cs`, mapped in `Program.cs`:
`GET /api/files/{day}/{id}?t=` → `InboundFileEndpoint.Serve(store, $"{day}/{id}", t)`. Disabled store,
bad key shape, unknown key, wrong or missing token, expired: all `404` with an empty body and no
disk access beyond the meta read. Hit: `200`, `Content-Type: application/octet-stream` (never the
stored MIME, so a browser never renders it), `Content-Length`, `Content-Disposition: attachment;
filename="<RFC 5987 safe name>"`, `Cache-Control: no-store`, streamed. `HEAD` is not mapped. The
route logs the key and the outcome, never the token or the name.

### Telegram adapter (S3)

`HydrateAttachmentsAsync` (`TelegramChannelAdapter.cs`): with `_store.Enabled`, the effective limit
is `_store.MaxBytes`, else `MaxInlineAttachmentBytes`.

1. Declared `Size > effective limit` → unchanged CARD-1799 path with `InlineLimitBytes = effective limit`.
2. Declared `Size <= MaxInlineAttachmentBytes` → unchanged inline download.
3. Otherwise → `getFile`; a `400 ... too big` answer or a resolved `file_size > MaxBytes` →
   `OverLimit(attachment, size, MaxBytes)`. Else stream the file endpoint response (bounded by
   `DownloadTimeoutSeconds`) into `_store.PutAsync(conversationId, attachment, stream, ct)`. A
   `Reference` → `attachment with { Reference, Size = reference.Size, Content = null }`; a refusal →
   `OverLimit(attachment, size, result.LimitBytes ?? MaxInlineAttachmentBytes)`.
4. Any exception on the stored path falls back exactly like a failed inline download does today
   (metadata-only, no `InlineLimitBytes`, warning log), so no message is lost.

`NoticeOverLimitAsync` keys off `Reference is null && InlineLimitBytes is not null` (D-5). The notice
text keeps the CARD-1799 sentence with the applied limit; an `OverConversationQuota` refusal uses
`"Daily file quota for this chat is used up (256 MiB per 24 h), so the file was not delivered. Try
again later or send a smaller file."` The adapter constructor gains an optional
`IInboundFileStore? store = null`; `Program.cs` passes `sp.GetRequiredService<IInboundFileStore>()`.

### Server import (S5)

- `ChannelBridgeSettings.InboundFiles` (new nested class): `AllowedOrigins` (string[], default
  empty), `MaxImportBytes` = 20 MiB, `FetchTimeoutSeconds` = 60. Validator: each origin absolute
  `http`/`https` with empty path and query; `MaxImportBytes` 1..1 GiB.
- `server/Application/Services/ChannelInboundFileImporter.cs` (registered singleton, named
  `HttpClient` `"channel-inbound-files"`): `ImportAsync(Attachment, inboxDir, fileName, ct)` →
  `InboundFileImport { Path? , Failure? , Bytes, Elapsed }`. Order: `Reference.Store == "gateway-http"`
  else `UnsupportedStore`; parse `Url` absolute, origin in `AllowedOrigins` (ordinal, scheme+host+port)
  else `OriginNotAllowed` (`NotConfigured` when the list is empty); `Sha256` matches `^[0-9a-f]{64}$`
  and `Size <= MaxImportBytes` else `Invalid`; GET with `HttpCompletionOption.ResponseHeadersRead`
  under a linked `FetchTimeoutSeconds` token; 404 → `Expired`; other non-2xx → `FetchFailed`;
  stream to `<inboxDir>/<fileName>.part` hashing and counting, abort past `Size` → `SizeMismatch`;
  hash differs → `IntegrityMismatch` (part deleted); rename to `<fileName>`; on Unix
  `File.SetUnixFileMode(path, UserRead | UserWrite | GroupRead | OtherRead)` (no execute bit). Logs
  key, bytes, elapsed and outcome; never the URL.
- Filename: `SafeFileName` as today. When the sanitised name has no extension, append one from a
  small MIME map (`pdf, pptx, docx, xlsx, zip, png, jpg, mp4, mp3, ogg, txt, csv, json`), else `.bin`.
  A MIME/extension disagreement is logged at Information and kept; nothing is renamed or executed.
- Bridge integration: before the `string.Join` at `ChannelBridgeService.cs:708`, an async pass
  `await MaterializeReferencesAsync(batch, inboxDir, memberIds, ct)` imports every referenced
  attachment into a `Dictionary<(Guid inboundId, int index), InboundFileImport>`; `RenderMessageBody`
  stays synchronous and consults it. Notes:
  - imported: `[file attached: <path>]` (unchanged format);
  - `NotConfigured`: `[file attached — "<name>" (17.6 MiB) was stored by the gateway but this server has no inbound file origin configured; not delivered]`;
  - `Expired`: `... is no longer available from the gateway (kept 72 h); not delivered]`;
  - `IntegrityMismatch` / `SizeMismatch`: `... failed its integrity check; not delivered]`;
  - `OriginNotAllowed`, `UnsupportedStore`, `Invalid`, `FetchFailed`, timeout: `... could not be fetched (<reason word>); not delivered]`.
  The name and size reuse `OverLimitSubject` (CARD-1799) so the neutralisation rules hold.
- Sender notice (D-10): after the batch, for each failed import, one
  `ChatChannelService.SendAsync(channel.Id, "The file could not be imported on our side (<reason>). Please try again later or send a smaller file.", new ChannelSendOptions(ReplyHandle: message.ReplyHandle ?? channel.ReplyHandle), ct)`,
  best effort, same exception handling as the CARD-0281 capacity notice. The reason words are
  `not configured`, `expired`, `integrity check failed`, `fetch failed`.
- Timing: the importer records `Elapsed` per file and logs it with the byte count (R4/R6); the
  wake worker already owns the prompt build, so one import of up to 20 MiB adds at most
  `FetchTimeoutSeconds` to that inbound and never blocks other sessions.

### Size caps, quotas, retention

| Limit | Where | Default | Over it |
|---|---|---|---|
| Inline cap | `Telegram:MaxInlineAttachmentBytes` | 14 MiB | stored out of band (store enabled) or CARD-1799 note + notice |
| Out-of-band cap | `InboundFiles:MaxBytes` (gateway), `ChannelBridge:InboundFiles:MaxImportBytes` (server) | 20 MiB | note + notice naming 20 MiB; `getFile` never called when declared over it |
| Per-chat window | `InboundFiles:PerConversationWindowBytes/Hours` | 256 MiB / 24 h | note (inline cap) + quota notice |

### Security checks

- **Keys** are `yyyyMMdd/<32 hex>` generated by the gateway; the route and the store validate the
  shape before touching the filesystem; `Path.GetFullPath` of the candidate must start with `Root`
  (defence in depth); the opened file must not be a reparse point (`File.GetAttributes`, fail closed).
- **Token**: 256-bit random, constant-time compare, in the URL only; never logged by gateway or
  server (log the key). The URL sits in the bus record and in both envelope journals until payload
  retention; it dies with the blob at 72 h.
- **Server fetch**: allowlisted origin only (D-6), no redirects (`AllowAutoRedirect=false`), 60 s
  deadline, hard byte ceiling at `Reference.Size` and `MaxImportBytes`, SHA-256 verified before the
  rename, part file deleted on any failure.
- **Filenames**: `SafeFileName` unchanged (both separators removed, invalid characters replaced,
  journal-id prefix); the extension is kept or derived from MIME; the note name goes through
  `OverLimitSubject` neutralisation. Nothing is ever executed; the server writes without the execute
  bit; the route serves `application/octet-stream` with `attachment` disposition and `no-store`.
- **Per-chat quota** (D-8) and store cap (D-7) bound disk use; `MaxBytes` bounds memory and time.
- **Out of scope, noted:** malware scanning of inbound files; the agent decides what to open.

Nothing here is done by a Code, Review or land task; nothing is activated, restarted or secret.

   restarted by the usual rc activation (not this card). With no allowlist the server behaves as

2. **Operator, server2:** edit `/home/mc/antiphon-messaging/docker-compose.yml` (the base file, not

## Performance budget

- **Selection and categories.** Messaging assembly (`Antiphon.Messaging.Tests`, Unit-only
  classification, no Slow entries touched): CP-1 to CP-4, 104 tests. Server assembly: CP-5 Unit
  (11), CP-6 `ChannelBridgeTests` is `[Category("Integration")]` + `Slow` with the shared Postgres
  (`TestDbFixture`) plus the Unit `ChannelContractsTests` (62 together), CP-7 guards (75). Project
  graph: `Antiphon.Messaging` → `Gateway`, `Telegram`, `Service`, `FakeGateway`, `Client`, server;
  the Messaging assembly references them all, so CP-1..CP-4 cover the messaging downstream closure;
  CP-6/CP-7 cover the server consumer and the layering guard (R7).
- **Measured basis (provisional).** CARD-1799 run `20261108-234758-3036` on server2 at
  `6ecfdcc14`: three rows (78 + 58 + 52 tests) executed in 3m48s sequential-equivalent, wall 13m15s
  including two cold builds; slot waited 0 s. Per-row durations were not retained, so the row
  estimates above are about 2x a pro-rata share (Messaging rows ≈ 1-2 min each, the bridge row
  ≈ 3-5 min, the guard row ≈ 3 min at 52 tests) and are **provisional** (R5): TestDesign is folded,
  so the first Code task (S1) records the fresh per-row `timing.json`/TRX durations in its report
  and the S6 task tightens `EstimatedMinutes` to 2x the observed p95 across the slice runs before
  the final run. The derived total comes from `DeriveTotalMinutes`; no explicit
  `totalTimeoutMinutes` is set. Nothing approaches 30 minutes, so no Debug obligation is expected;
  if any row exceeds 30 minutes the Code task files Debug with the receipt (R1).
- **Phases.** Build: one cold build per After group (four Messaging, two Antiphon.Tests), reported by the tool as `build=ok`
  with their own duration, separate from row execution and slot wait. Container start: none new;
  `ChannelBridgeTests` uses the once-per-run shared `TestDbFixture` Postgres (R3), no migration per
  test. Web hosts: `FakeTelegramServer` and `KestrelLoopback` are per-test Kestrel loopbacks that
  start in well under a second (existing pattern in the 44 adapter tests); the new route test adds
  one. Data preparation: temp directories per test, deleted in `finally`. Teardown: part files and
  temp roots removed; the retention sweep in tests runs one pass synchronously with a fake

- **Fixture lifetime and isolation.** Store tests use a fresh temp root per test (cheap, no shared
  state); the importer tests use a fake `HttpMessageHandler` (no sockets); bridge tests reuse the

  ~80 s; Telegram's CDN is far faster; card: this plan), server fetch 60 s (20 MiB over the tailnet,
  measured sub-millisecond handshake in CARD-1746, expected under 10 s), sweep pass 5 min, per-test

  of milliseconds). Row budgets: the `EstimatedMinutes` above.
- **Recording.** TRX and `report.json` per row under `.antiphon/checkpoints/<run>/rows/CP-n/`

  importer logs `bytes` and `ms` per fetch; the store logs `bytes` and `ms` per put; the sweep logs

## Risks and follow-ups

- **CARD-1799 land timing.** S1 and S3 edit `ChannelMessage.cs` and `TelegramChannelAdapter.cs`,
  which 1799 also changes. Start no slice before 1799 is on master; a slice that must start earlier
  branches from the 1799 branch tip and expects the land rebase to drop the carried commits.
- **Topology.** If the server2 server (CARD-1744 window 2) cannot reach the host's 18090 from the
  `antiphon-server2` network, the allowlisted origin is the host's LAN or tailnet address, both
  measured open from a container on that host (CARD-1746). A mounted-path reader remains possible
  from `Reference.Key` as a later card.
- **Edited messages** redeliver the document and would store it twice (two keys, quota counted
  twice). Acceptable; a `file_unique_id` dedupe is a follow-up card.
- **Slack** keeps the 14 MiB inline cap; a follow-up card gives `SlackChannelAdapter` the same store.
- **Sessions waiting for input:** this plan adds or changes no session that waits for input; the
  CARD-1083 parking checklist does not apply.
