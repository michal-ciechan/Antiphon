# CARD-0383 — a Grok `--resume` is typed only when the native session directory exists; a row id is not a conversation

**Date:** 2026-09-05

**Plan task:** 084b82af (Frontier, plan; verification design folded in)

**Card:** CARD-0383 / GitHub #40 — "Grok Herdr launch: --resume of an Antiphon session GUID is not a native Grok session; detect and start fresh"

**Evidence base:** `AgentSessionService.BuildSessionIdentityArgs` and its one call site; `AgentControlService.StartInteractiveSessionAsync` / `FindResumableSessionAsync`; `AgentSupervisorService` restart arm; `HerdrPaneChild.LaunchAsync` / `CompleteTypedLaunchAsync` / `WaitForExpectedAgentAsync` / `KillAsync` and the CARD-0213 attach check; `GrokTranscriptTailer.TryLocateSessionDirectory`; `SessionRunnerRuntime.StartAsync` + `RunnerSession.StartHerdrAsync` catches; `SessionRunnerHttpClient.ThrowForRunnerProblemAsync`; `HerdrGkpLaunchGuard` (CARD-0341, the pattern this plan copies); `docs/herdr-sessions.md` §3a/§4/§8, `docs/agent-kinds.md` §5, `docs/session-runtime-invariants.md`; `grok --help` (1.0.13) and four live measurements of `grok.exe` on this machine (below). Herdr 0.8.x is live here (`%APPDATA%\herdr\herdr.sock`, two `herdr` processes since 2026-08-25) and the runner has `Herdr.Enabled: true`, so the positive control in V4 can run on this box.

## Summary

Grok's own contract (measured, `grok --help` 1.0.13): `--session-id <uuid>` is **create** ("for a **new** conversation … does not resume existing sessions"); `--resume <uuid>` is **resume** and, when nothing exists locally, tries a remote restore, gets `404 Not Found`, and exits 1 in about two seconds. Antiphon decides between the two from the *row's* history (`resume: true` on a Stopped/Failed row), not from whether Grok ever created a conversation under that id. Every launch that fails **before grok starts** — the CARD-0341 gkp gate, `pane_occupied`, `herdr_unreachable`, a herdr detect timeout, a runner refusal — leaves a Failed row with no native directory, and the next AlwaysOn start types `--resume <that id>`. Grok exits, the pane returns to an idle PowerShell prompt, herdr never reports `agent=grok`, and after 60 s the runner's catch `pane.close`s the dedicated tab. The following backoff attempt, now with no last-pane, splits an unrelated tab.

The fix has three layers and a small pane-safety change:

1. **Server decides from disk, not from the row.** Before composing argv for a Grok launch with `resumeMode == Resume`, look for `sessions/*/{id:D}/` under the launch's `GROK_HOME` — the bar CARD-0213 attach already uses. Present → `--resume <id>` unchanged. Absent → same row, `resumeMode = null`, so `BuildSessionIdentityArgs` emits `--session-id <id>` and Grok **creates** the conversation under the row id. After that the row id *is* the native id, which today is only true after attach.
2. **Runner refuses a dead resume before touching herdr.** A herdr Grok launch whose argv carries `--resume <uuid>` with no native directory is a 409 `herdr_grok_native_session_missing` (same shape as `herdr_gkp_env_missing`): nothing allocated, renamed, or typed; the last-pane record is kept. The server stores the detail as `FailureReason` (CARD-0341 plumbing) and treats the code exactly like Claude's "No conversation found" — kill what it started, relaunch the same row fresh.
3. **A detect timeout on an idle shell keeps the pane.** When `pane.get.agent` never became the expected kind *and* the pane holds nothing but its own PowerShell, the launch fails but the pane is retired to a last-pane record instead of being closed, so the next attempt relaunches in place (CARD-0224 arm) rather than allocating into a stranger's tab.

No change to `AgentSupervisorService`: with layer 1 the `Fresh: false` retry re-reads the disk and creates; `FreshAfterResumeFailures` (2) stays as the ceiling for a resume that fails for a reason we cannot see.

## Decisions

- **D-1 — Same row, mode downgraded to create; not a new row.** The check flips `resumeMode` from `Resume` to `null` inside the one launch funnel (`LaunchInteractiveProcessAsync`, `ResumeAsync`) so `BuildSessionIdentityArgs` emits `--session-id <row id>`. This is Claude's existing "conversation not found → fresh conversation under the same id so the terminal still opens" shape (`AgentSessionService.cs:349-359`), decided before typing instead of after a 60 s failure. It keeps the row's queued messages and in-flight tasks (no remap), hits the last-pane record by the row's own id, covers the pty lane and the card `POST /api/sessions/{id}/resume` path for free, and yields the invariant *any Grok row that ever reached grok has native id == row id*.
  *Rejected:* making `FindResumableSessionAsync` return null for a Grok row with no native directory (new row, `ReusePaneOfSessionId` → previous pane). It matches the card's literal "new guid" wording but burns a row id, `PersistentSessionId`, and a message/task remap on every refused-before-grok launch, misses `ResumeAsync` and the CARD-0334 policy-refresh relaunch, and leaves the row/native identity split the card complains about.
- **D-2 — Existence bar = `sessions/*/{id:D}/` directory present under the launch's `GROK_HOME`, any cwd encoding.** Literally `GrokTranscriptTailer.TryLocateSessionDirectory` (attach's bar, `HerdrPaneChild.cs:169-178`), with `GROK_HOME` resolved launch-env-first (`GrokCredentialStore.ResolveGrokHome(launchEnv)`, the child's own view). Measured: grok creates the directory at launch (before any submit; 195 of 1088 directories on this machine have no `updates.jsonl`), `--resume` of a populated directory starts a TUI, `--resume` of an absent id exits 1. No `updates.jsonl` requirement — a session stopped before its first submit is still resumable.
  *Rejected:* the deterministic per-cwd path (`ResolveUpdatesPath`'s parent). An attach-bound row's directory can sit under a different cwd encoding (operator launched from another path spelling); attach already tolerates that with a Warning, and `--resume` takes a global id.
- **D-3 — The locator moves to `Antiphon.Agents.Pty` so server and runner call one function.** `server/Antiphon.Server.csproj` references `Antiphon.Agents.Pty` and `Antiphon.SessionRunner.Contracts`, not `Antiphon.SessionRunner`; `GrokCredentialStore` (same project) is the precedent for the server reading `GROK_HOME` pre-spawn (CARD-0324, `AgentTaskDispatcher.cs:1964-1966`). `GrokTranscriptTailer.TryLocateSessionDirectory` becomes a forwarding call so `GrokTranscriptTailerTests` and `HerdrAttachTests` are untouched.
- **D-4 — Runner gate is defensive, not primary.** It exists for server/runner skew (old server in front of a new runner) and for a server whose `GROK_HOME` resolution disagrees with the runner's, and it converts a 60 s wait plus pane loss into a sub-second refusal with a name. It gates only `--resume <uuid>` / `-r <uuid>` / `--resume=<uuid>` on a Grok launch; a title-shaped `--resume <text>` (grok supports it; Antiphon never emits it) and every `--session-id` pass through. Copies `HerdrGkpLaunchGuard` exactly: pure function of the request, runs before `ConnectAndValidateAsync`.
  *Rejected:* rewriting `--resume` → `--session-id` inside the runner. The server owns what `resumeMode` means downstream (launch note body, `EnqueueResumeContinueAsync`, restart boundary); a silent argv rewrite would hand a `RestartResumeBody` note to a brand-new conversation.
- **D-5 — Server maps the runner code onto the existing not-found fallback.** `LaunchInteractiveProcessAsync`'s catch treats `ConflictException { Code: "herdr_grok_native_session_missing" }` on a `Resume` launch as `ClaudeSessionNotFoundException` (renamed to `ResumeTargetMissingException`, kind-neutral): kill-then-dispose the first adapter, relaunch the same row with `resumeMode: null`. `ResumeAsync` (card path) does not fall back — it never did for Claude either; it records the reason and fails, and the operator retries with `Mode: New`.
- **D-6 — Detect timeout on an idle shell retires the pane instead of closing it.** Scoped to: our launched/created pane, `pane.process_info` foreground = shell only, launch script already typed. A last-pane record is written straight from the request (`LaunchEnvNames = request.Env` keys, `ExitReason = HerdrLaunchDetectTimeout`) and the child's `KillAsync` raises `Exited(LaunchDetectTimeout)` without `pane.close`. That string maps to `AgentExitReason.HerdrLaunchDetectTimeout` (Failed, Warning log, **no** `HerdrPaneLeftOpen` incident — the pane is an idle shell kept on purpose, not a foreign process). A wrong-kind detection or any foreign foreground process keeps today's `PaneLeftOpen` behaviour. The redacted script stays on disk (CARD-0341) and is overwritten by the relaunch.
  *Rejected:* a general "shell is idle ⇒ fail fast" poll inside `WaitForExpectedAgentAsync`. There is a real window between the typed `& '…launch.ps1'` and `grok.exe` appearing where the shell is the only foreground process; a fast-fail there needs a settle count and a measurement this card does not have. Filed as a follow-up in Out of scope.
- **D-7 — No supervisor change.** `AgentSupervisorService.cs:195` computes `fresh = ConsecutiveFailures >= FreshAfterResumeFailures` (default 2, `SupervisionSettings.cs:23`). Under D-1 the very next `Fresh: false` attempt re-evaluates the disk and creates, which is what the card's "AlwaysOn backoff should start fresh (create)" asks for; a new row is not needed. If the resume target exists and grok still dies, the existing ladder escalates to a new row on the second failure, unchanged.
- **D-8 — A new `AgentIncidentKind` is not added.** The distinct reason the card asks for is the runner's problem code, stored in `AgentSession.FailureReason` via `SessionRunnerHttpClient.ThrowForRunnerProblemAsync` (`:580`, `409 → ConflictException(detail, code)`), plus one Warning log line on the server-side downgrade naming the session, the resolved `GROK_HOME`, and the decision. Incident kinds carry client badges and retention policy; a launch that now *succeeds* does not warrant one.

## Verification design

The card's acceptance is *Grok appears, herdr detects `grok` well under the detect timeout* — a unit test against `BuildSessionIdentityArgs` proves the argv, not that. So the design is layered from pure functions up to the real binary in a real herdr pane.

**V1 — server unit (Antiphon.Tests, `[Category=Unit]`).** `GrokNativeSessionResumeTests` (S1.4) and the two `AgentSessionLaunchFailureTests` additions (S1.4, S2.4). Run: `dotnet run --project tests/Antiphon.Tests --property:OutputPath=bin-c383/ -- --treenode-filter "/*/*/GrokNativeSessionResumeTests/*"` and `…/AgentSessionLaunchFailureTests/*`. Expected: every case above green; specifically the fixture GUID with no directory yields argv with `--session-id` and **no** `--resume` (card acceptance 4).

**V3 — real grok binary, no herdr, zero spend (Antiphon.Agents.Pty.Tests, `[Category("Headed")]`, `[NotInParallel("Headed")]`, `[ParallelLimiter<ProcessSpawnLimit>]`, `GkSession.SkipIfNotEligible()`).** `GrokNativeSessionCanaryTests` launches `GkSession.GrokExePath` through the existing ConPTY harness with a **temp `GROK_HOME`** and `RealCliStubEnv.ForGrok(stubBaseUrl, "canary")` (`src/Antiphon.FakeLlmApi/RealCliStubEnv.cs:47`; API-key auth, so no OAuth screen — CARD-0324 states profiles/API-key paths are never sign-in gated), cwd = a temp directory:

## Out of scope (say so in the report, not silently)

- **Logical named-session mapping (`gkp --session <slug>`, card Wanted 2 "optionally").** The wrapper is not on this machine and its mapping file format is unknown; resuming a wrapper-mapped native id would need the wrapper's own lookup. If it matters, a follow-up card should read `gkp.ps1` on the work laptop and decide whether the profile should pass the mapped id explicitly.
- **Fast-fail when the typed launch command exits before detection** (D-6 rejected alternative). Worth its own measurement: `pane.process_info` shell-only for N consecutive polls after the script was typed, with a settle window that survives the pwsh → grok.exe hand-off.
- **Pty-lane ready semantics on a 2 s exit** (ground-truth row): layer 1 removes the cause; whether `WaitForReadyAsync` reads a dead process as ready is a separate observation.
- **`AgentIncidentKind` for the downgrade** (D-8).
