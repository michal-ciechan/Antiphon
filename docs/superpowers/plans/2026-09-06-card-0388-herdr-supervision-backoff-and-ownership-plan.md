## Decisions

### D-1: Three qualifying failures, with a separate durable streak

Add `Supervision:HerdrFailureLimit` with default **3**, validated as an integer from 1 through 10. Three counts the initial failed process attempt plus two more failed attempts, not three retries after the initial failure. It allows transient recovery while stopping well before attempt 7. No time-based half-open probe and no automatic unlimited reset after a cooldown. Changing the limit cannot clear an existing hold.

Eligibility when recording/consuming an outcome: owning persistent standing session (`CardId == null`, non-pool agent), agent AlwaysOn, and **session snapshot** backend Herdr. Apply across ClaudeCode, Grok and Codex on that backend, not only one agent name or cwd. Maintain the existing general `ConsecutiveFailures`, delay formula, fresh threshold and escalation tiers; they have different meanings.

| Actual terminal evidence | Herdr streak action |
|---|---|
| Failed attempt with typed HerdrPaneClosed | Increment once. |
| Failed attempt with typed HerdrChildGone (confirmed dead child) | Increment once, in the same family. Excluding it would let the recorded mixed loop evade the limit. |
| Failed launch with runner code `detect_timeout`, including kept-pane HerdrLaunchDetectTimeout exit | Increment once. A timeout and its cleanup close are one outcome. |
| New terminal attempt with a confirmed different cause | Reset the Herdr streak; ordinary backoff remains. |
| Synchronous refusal before a new process/session attempt, e.g. `grok_rules_argv_unsafe`, `pane_occupied`, missing native session, quota/model hold | Neither count nor reset the pane-failure streak; retain its existing refusal/backoff path. No pane was launched. If the refusal occurs asynchronously on a new row, its nonqualifying terminal outcome resets the Herdr streak. |
| Runner/Herdr unreachable with no confirmed terminal outcome; Starting; unknown evidence | Do not infer a failure. No probe/kill/retype is added. |
| HerdrRestartPresumedDead; HerdrPaneLeftOpen; HerdrStatusDisagreement; provider stall; delivery failure; intentional Stop/detach/policy refresh | Not a qualifying cause. Preserve their existing recovery rules. Never count a pane-close cleanup of an intentional termination. |

The unit is a process-attempt outcome, not incident rows, timer ticks, pane count, or session ID alone. Both the observer and reconciler can report one outcome, while resume reuses the ID and refreshes `StartedAt` (`AgentControlService.cs:324-330`). Dedupe by **(SessionId, StartedAt)** using persisted database precision. Separate agents never share a counter, even in the same cwd. Mixed PaneClosed -> detect_timeout -> ChildGone reaches three.

### D-2: Record typed outcome evidence; consume it before another launch can erase it

Add a small domain enum `HerdrSupervisionFailureKind` with NonQualifying, PaneClosed, ChildGone and DetectTimeout; add nullable `AgentSession.HerdrSupervisionFailureKind`. Null means no classified evidence (including legacy/unknown), while NonQualifying positively identifies an excluded terminal cause and can reset the streak. This is narrowly scoped attempt evidence, not a second general termination taxonomy. Map the existing Application exit enum and runner exception code into it outside Domain. No Domain dependency on Application/runner contracts and no new runner wire protocol is needed.

Write the field in the same save as the terminal outcome at `AgentSessionRuntime.ObserveExitAsync`, `AgentSessionService.LaunchInteractiveAsync`'s failure catch, and the reconciler's runner-reported-exit arm. Capture the typed `ConflictException.Code` before the launch catch discards it into prose. Preserve first-closer termination semantics. DetectTimeout takes diagnostic precedence over its secondary cleanup PaneClosed; compatible observations may enrich the same attempt, never create another count. An unrelated later exception must not erase already proven qualifying cause for that attempt. Do not classify using arbitrary `FailureReason.Contains(...)` or backfill guessed causes from old incident text. Old rows have null evidence; the limit becomes effective as new attempts produce evidence.

Clear this session evidence on an actual new launch generation, including same-row resume and same-ID missing-resume fallback, alongside existing exit/termination reset. Existing ownership/liveness checks remain the authority for accepting an exit event; this change does not make a raw historical Herdr pane event authoritative. A fresh queued launch must not inherit the prior generation's evidence.

Extend `AgentSupervisionState` with:

- `HerdrConsecutiveFailures` (default 0).
- `HerdrFailureHeldAt` (nullable UTC timestamp).
- `LastHerdrFailureKind` (nullable enum, for the hold/agent display).
- `LastHerdrObservedSessionId` and `LastHerdrObservedStartedAt` (nullable pair identifying the consumed terminal attempt, including a nonqualifying terminal attempt).
- `HerdrHealthySince` (nullable timestamp for observed continuous Running).

Use one small concrete `HerdrSupervisionStateService` for consuming terminal evidence and changing this state, called from both SuperviseAsync and StartAsync. It uses AppDbContext, typed settings and TimeProvider; no runner/pane client and no dependency on AgentSupervisorService (avoid a control -> recorder -> supervisor -> control cycle). Add the hold audit incident directly in the same unit of work, as existing user-latch code does.

Consume the most recent classified terminal persistent attempt **before** scheduling/due-start logic and **before** Start clears/reset/replaces a resumable row. Do not consume null/unknown evidence. A queued launch whose failure cleanup is still owned by the launch queue is not yet a finalized attempt: let its catch finish classifying before consuming/relaunching it, using the existing launch-ownership seam. This prevents cleanup's generic killed outcome being consumed as NonQualifying before the actual detect-timeout catch arrives. Persist the dedupe pair, streak, hold and single audit incident together. Use the existing agent row lock with an actual transaction spanning the read/change/save; `FOR UPDATE` in an autocommit query alone is not mutual exclusion. Join an ambient transaction when present; keep this lock/transaction short and out of runner RPCs or detection waits. Re-read state when handing off to Start rather than saving a stale supervisor entity over an explicit retry. A concurrent manual/bridge Start must consume the same outcome once and observe the hold before enqueue. Tests must interleave these entry points.

On the third consumed qualifying outcome, set HeldAt, clear NextRestartAt and HealthySince, and save the hold. Do this even if a delay was already scheduled. Do not increment the ordinary counter a second time for merely processing the hold, and do not leave a misleading next-retry timestamp. The supervisor checks the hold again before invoking Start. If Start observes a concurrently committed hold and throws `herdr_supervision_held`, handle that separately from the generic StartFailure catch: reload state and leave NextRestartAt null, with no extra failure/escalation incident. Later ticks and server restarts perform no start, scheduling, or fresh-conversation fallback for that agent. The hold owns **future starts only**: it never calls kill, pane.close, tab.close, or a global runner stop. Existing cleanup and retained last-pane behavior remain unchanged.

### D-3: Healthy reset and explicit operator retry

Observe Running for the existing `HealthyUptimeResetMinutes` (10 by default) before clearing the Herdr streak. Start the new `HerdrHealthySince` at the first Running observation; clear it while Starting/terminal and when creating/resuming a new generation. Do not count the launch's 60-second detect wait as healthy time. Persist the timestamp across server restart. A brief Running interval, successful Start return, ready banner, or isolated transcript row does not reset the streak. Do not alter the general ladder's existing health calculation in this card.

A tripped hold stays until **explicit retry**, even if the failure limit, backend, cwd, labels or AlwaysOn setting changes. Add optional trailing `StartAgentRequest.ResetHerdrFailureHold = false`. While held, an ordinary dead-agent Start refuses `ConflictException` / 409 code `herdr_supervision_held` with the agent, count, last cause and remedy. Crucially, check this before `ClearSupervisionLatchAsync`, composition, named-placement preflight, row mutation and enqueue. An already-live Start remains idempotent and never kills/moves that process; merely observing a live session does not acknowledge the hold.

The operator's explicit retry sends `{"resetHerdrFailureHold":true}` (optionally alongside existing `fresh:true`). Under the same short state transaction, consume any unobserved old outcome first, then clear HeldAt and the Herdr streak/healthy timestamp, retain the consumed-attempt pair so the old failure cannot be counted again, and record a timeline-only retry acknowledgement. Preserve general ConsecutiveFailures and existing fresh/resume semantics. Normal launch validation still applies; this flag bypasses no Grok, provider, quota, placement or foreign-occupant guard. After another three qualifying failures it holds again. Do not require a new endpoint or permission modal.

Supervisor, channel bridge, policy refresh and other automatic callers leave the flag false. In ChannelBridgeService, handle this specific conflict as an unavailable held agent using the existing non-delivery/drop-reporting path: no retry loop, no reroute to the twin, no false delivery confirmation and no unhandled consumer exception. Do not create a new Slack send route. In the agent UI the existing Start affordance becomes **Retry and resume** when held and sends the explicit flag only on that click. Ordinary starts do not send it.

Stop keeps its user-Suspended behavior and does not relabel the automatic hold as SuspendedByUser. Existing LivenessLatchedAt behavior remains separate. An attach operation may bind an operator-started live process under its existing safety rules but must not silently clear the Herdr hold through the shared latch helper; explicit retry/acknowledgement remains necessary to permit later automatic relaunch.

### D-4: State-backed Attention, with one audit incident per hold

Append `AgentIncidentKind.HerdrSupervisionHeld` using the next free numeric value **on the rebased Code base** (53 is already used here; do not reserve a stale number across CARD-0384/other lands). Record Error severity once when HeldAt transitions null -> nonnull. Detail: agent ID/name, count and limit, terminal attempt ID/StartedAt, last typed cause, and the remedy to inspect/fix then explicitly retry. Keep rules bodies, environment values and provider secrets out of the record.

Use timeline-only recording (`raiseAlert:false` semantics). The human action lives in **Attention**, per the repository's decision contract; no new alert sink, direct Slack publisher, pager kind or recurring notification is part of this change. Existing operational failure alerts continue unchanged. If the operator wants a Slack summary, that is an explicitly configured existing digest/notification choice, not an acceptance condition or another delivery mechanism here.

Add `AttentionKind.HerdrSupervisionHeld`, one row per held agent, derived from nonnull HeldAt rather than a recent-incident query. Show even beyond the usual lookback, after incident pruning, or after disabling AlwaysOn while the hold still exists. Include OpenAgent (and the failed session drawer when available). Register its client type/visual/group and use existing SignalR invalidation through AgentChanged. Exclude the dedicated hold incident kind from the generic recent-incident projection so one unresolved episode is not two rows, and an acknowledged episode does not linger as a stale actionable incident.

Extend AgentSupervisionDto and mappings with held timestamp, Herdr count and last cause; include this state when present even if AlwaysOn was later disabled. Update SupervisionBadge to display **Herdr retries paused** and the reason, independently of the user-suspended badge and ordinary backoff countdown. Clearing the hold removes the Attention row; the incident stays as history. Attention itself is read-only and never schedules/spawns/moves a card.

### Rejected alternatives and boundaries

- Reuse ConsecutiveFailures as the threshold: mixes unrelated failures and doesn't identify one terminal attempt; would change the general never-give-up policy.
- Count Crash/RestartScheduled/StartFailure text: duplicates one failure, misses the kept-timeout path, loses typed codes and breaks after retention.
- Reuse Suspended or LivenessLatchedAt: confuses human Stop/provider-stall semantics and is cleared by automatic Start.
- Auto half-open every few minutes or silently fall back to PtyHost: restores the pane loop or silently changes the chosen backend.
- Kill remaining panes when the threshold is reached: exceeds the hold's purpose and violates ownership/kept-pane guarantees.
- A new generic circuit-breaker framework, attempt-history table, fleet-wide rate limiter, cwd lease or channel election system: unnecessary for this bounded per-agent hold.
- Treat CARD-0384 as already deployed, or make a multiline rules transport here: duplicates other cards and would misstate the remaining dependencies.

## Acceptance and TestDesign handoff

This medium-complexity change has a separate TestDesign stage. The following are required outcomes, not tests claimed to have run. TestDesign must supply named V/R cases and economical red-then-green positive controls before Code.

1. A standing Herdr agent fails three process attempts (initial plus two retries): after the third terminal outcome is consumed, HeldAt exists, NextRestartAt is null, and every later tick produces zero launch/placement calls. Verify ordinary 5s/10s/... scheduling before the threshold and retained general fresh-after-two policy. With a configured limit of 1, the first failed attempt holds; invalid limits fail validation.
2. Same session ID with different persisted StartedAt counts separately; a fresh session ID counts on the same agent; observer+reconciler+timeout cleanup for one generation count once, in either failure-writer order. Saving only a typed code or only a helper return is insufficient: drive the real terminal-writer and supervisor/start seams.
3. Mix PaneClosed, DetectTimeout and ChildGone; all three reach the same threshold. Include current kept-pane timeout with no AgentIncidentKind timeout row, and exact runner exception code propagated through the real interactive catch. Confirm generic crash/restart incidents do not multiply counts.
4. Negative controls: PtyHost and pool/card sessions; intentional Stop/detach/policy refresh; raw replayed Herdr event while the process is live; runner unreachable/unknown; HerdrRestartPresumedDead; provider/model/rules/placement refusal. Verify nonqualifying new terminal attempt reset versus pre-session refusal no-count/no-reset. A pending held retry must not bypass using fresh fallback.
5. Recreate service/context after two failures, then after the hold; preserve streak/dedupe/latch. Prune incidents and advance over 24h: one Attention row remains. Reset it explicitly: no actionable stale duplicate appears from the old hold incident. Concurrent Tick/Start consume once and cannot schedule/start through a committed hold; late stale tracked state cannot undo an acknowledgement or hold.
6. A queued Start or <10min Running interval does not reset. A 60s Starting interval contributes zero healthy time. Continuous observed Running for the configured interval resets the Herdr streak. New generation resets the health timestamp; server restart preserves it. Test general backoff recovery unchanged separately.
7. Held Start without flag: typed 409 before clearing other latches, preflight, row/enqueue and runner side effects. Explicit retry clears only the intended hold/streak, preserves ordinary failure count and the consumed old key, records acknowledgement, and runs all normal guards. Another three failures hold again. Changing labels, backend, limit or AlwaysOn does not silently acknowledge.
8. Channel inbound/automatic Start cannot set the flag or recreate panes. The bridge records its established non-delivery outcome, and never confirms/queues a delivered UserPrompt or reroutes to a twin. UI displays the actual hold and emits the flag only on explicit Retry and resume; Stop and LivenessLatchedAt regressions remain green.
9. Assembled named-placement scenario in S4 proves zero fourth pane-producing attempt, unchanged specialist tab and retained timeout last-pane. The hold introduces zero kill/close RPCs. CARD-0382 unsafe-rules refusal still reaches zero runner/pane side effects; named-placement refusal remains distinct from a detect failure.
