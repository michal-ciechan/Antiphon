Date: 2026-09-27. Investigate task: `fcb2e819`. Source: `2f050e3d2b1cc36a3440d5914089aaded7c68a12` (also the live `/api/version` SHA during investigation).

## Verified findings

1. CARD-0772 remains open. Its three named tasks were Codex Worktree workers on `runnerId=desktop`, with `requiredPlatform=Windows`. The live task API identifies sessions `5786d2d9-76a8-4060-9ade-e2ae5d7e882c`, `32f81ff0-4179-4c45-978c-599e56012000`, and `4f7cf634-df7d-4de1-b34a-ae64dfb614d5`. They ended 72.5, 72.4, and 69.3 seconds after dispatch, respectively; their tasks were marked Failed about three minutes **after the session exits**. Thus the card's “~4 min” is task reconciliation latency, not process life.
2. `GET /api/sessions/{id}/transcript?since=0` returned `entries=[]` for all three. `GET /api/sessions/{id}/messages` returned the delegation brief as `Pending` with `deliveryAttempts=0` in all three. The diagnostic bundle's `session.json` for the first records `Failed`, exit code 1, and `Process exited (KilledByRequest, code 1).` Its `runner-log.txt` says that session is no longer present. This is a **pre-delivery launch failure**; there is no evidence that Codex received any brief, built code, or reported.
3. `KilledByRequest` is the runner/pty exit classification for an explicit kill, not Codex's own normal exit: `src/Antiphon.Agents.Pty/PtyAgentRunner.cs:488-491`, `src/Antiphon.SessionRunner/SessionRunnerRuntime.cs:827-851`, `server/Application/Services/AgentSessionRuntime.cs:227-239`. The server's launch path waits for readiness at `server/Application/Services/AgentSessionService.cs:503-514`, before Running and queue flush at `:573-575` and `:633-639`. Its failure catch calls a generation-bound kill at `:648-658` and `:769-783`. A Codex not-ready result becomes an exception at `:2203-2216`. The installed Codex gate has a 60-second total deadline (`server/appsettings.json:147-148`; `server/Infrastructure/Agents/SessionRunner/RunnerCodexAdapter.cs:137-171`; `src/Antiphon.Agents.Pty/CodexStartupReadiness.cs:349-356,394-419`). The three ~70-second lifetimes plus untouched queues fit **readiness timeout → launch cleanup kill** closely. They do not establish the exact caller or the last screen state: a distinct explicit kill during Starting remains possible.
4. CARD-0574's unsafe “quiet/absent MCP means ready” path is already replaced on this master. `CodexStartupScreen.Classify` requires a loaded model, supported empty composer and model/effort/cwd footer (`src/Antiphon.Agents.Pty/CodexStartupReadiness.cs:53-105,176-255`); `CodexReadyWait` returns false on deadline (`:394-419`). The brief's suggestion that the old cold-start bypass might still be present is stale. The current gate may be correctly refusing a Windows screen that is blocked, or may fail to recognize a valid layout. No historical current screen was retrievable to decide which.
5. The documented desktop log helper (`docs/logs.md:5-23`) resolved the Linux main checkout and found no `desktop-server` or `session-runner` files here. The live diagnostics bundle contains only the newest 2026-09-27 log tails, not the 2026-09-26 incident lines; it has no failed-session buffer (`errors.txt: buffer 404`). The desktop SSH attempt was denied. The precise kill request and last `codex-startup not-ready reason=...` need the desktop's 2026-09-26 server/runner log files or a retained runner capture. Do not claim a parser defect or lengthen the readiness deadline without that evidence.
6. Desktop placement is still admitted at create and dispatch. A null `RunnerId` means desktop (`server/Application/Services/DefaultRunnerRoutingPolicy.cs:30-69,143-152`). After defaults and platform selection, `AgentTaskService` stores that host at `server/Application/Services/AgentTaskService.cs:1212-1274,1343-1356`; the dispatcher pre-claim kind fence currently admits every desktop kind (`server/Application/Services/AgentTaskDispatcher.cs:597-603`). `TaskPlatformPlacementTests` even pins a Codex desktop kind default (`tests/Antiphon.Tests/Application/TaskPlatformPlacementTests.cs:105-135`). The server2 Codex worker lane now exists (`AgentTaskService.cs:1190-1197` and `DefaultRunnerRoutingPolicy.cs:244-250`); the live task API returned several server2 Codex successes from 2026-09-25, including task `0353ecae`. Thus `docs/agent-kinds.md:24-32` saying Codex is absent on server2 is stale. A Windows requirement cannot silently move to Linux server2.

## Smallest safe fix

**S1 — Fail closed at task placement, and fence old queued rows.** Add one task placement predicate/reason, e.g. `codex_desktop_unqualified`, whose condition is resolved kind `Codex` plus canonical local/desktop host. Call it after the final host and platform decision but before `AgentTaskService` inserts a row. Return a `ConflictException` with that stable code and a sentence saying that desktop Windows Codex starts died before input; choose another kind for Windows work, or a qualified non-desktop Windows runner if one exists. Explicit `local`/`desktop`, kind/global defaults, Windows fallback, and ordinary Any fallback must all refuse. Keep the frozen platform and requested kind; never reroute silently.

Use that same predicate in the dispatcher's pre-claim guard so already queued desktop Codex tasks become `Blocked` with the identical reason before worktree/session creation. A reroute or model walk to Codex on a desktop-bound task must also refuse or block with that reason; retain successful remote Codex workers and desktop Grok/Claude. Keep `IsHostKindCompatible` semantics and its messages coherent across reroute/rewalk; do not reuse `RunnerKindBlockedReason`'s remote-only text for desktop. Do not change the runner's generic kill behavior, the CARD-0574 gate, delivery, transcript matching, or provider credentials.

**S2 — Qualification path, separate from this mitigation.** From the canonical Windows checkout, inspect the exact 2026-09-26 rotated `desktop-server`, `session-runner`, and `pty-host` log files at the paths in `docs/logs.md`; the helper's newest-file tail does not select yesterday's rotation. Correlate each session ID with its `codex-startup not-ready` line, launch exception, and kill request. If still absent, collect a sanitized rendered snapshot and adapter diagnostic on a controlled Windows cold launch in an isolated runner, with no production broker. Classify the screen against `CodexStartupScreen`, fix only the proved detector/startup condition, then demonstrate Running plus a complete matching `UserPrompt` before removing the desktop refusal. The mitigation ships independently; an empty transcript, ready screen, or runner health alone cannot qualify delivery.

## Risks and acceptance

- This intentionally blocks Windows-required Codex work on the desktop until it is qualified. A Windows-only task can use Claude/Grok or a later qualified Windows runner; no Linux fallback is implied.
- A create-only check would leave queued tasks able to launch; a dispatch-only check would create work that cannot run. Both boundaries need the same reason. A broad desktop-kind ban would break working Claude/Grok paths; a broad Codex ban would break server2.
- The incident's exact killer remains an evidence gap. The mitigation does not claim to cure Windows startup. Keep the failed-session IDs and the 2026-09-26 log retrieval commands in S2; do not remove the guard from a green unit test or a single visually idle frame.
- After landing and activation, verify `/api/version` SHA, then an isolated create test or a controlled live API 409 proves the desktop Codex refusal before any real Codex canary. If a live API create is used, ensure its 409 creates no task. The canonical desktop restart must follow `docs/apphost-runbook.md`, not this worktree.

### Refusal contract

The common predicate is **resolved `AgentKind.Codex` AND `RunnerRequestIntent.CanonicalRunnerId(finalHost) == null`**. It is a desktop-placement rule, independent of the OS executing the test and of model tier. Apply it after the existing platform decision, including retained-process placement, and before task insertion/workspace admission. Explicit platform mismatch/unknown errors retain precedence. `IsHostKindAdmitted` and `IsHostKindCompatible` must agree on this pair, while retaining the existing remote worker admission set. The tests invoke real service/dispatcher boundaries, not only the predicate.

Create and explicit reroute throw `ConflictException`, HTTP status 409, with literal code `codex_desktop_unqualified`. Assert diagnostic clauses naming **desktop**, **Windows Codex startup not qualified**, **observed exits before task input**, and the alternatives **ClaudeCode/Grok for desktop Windows work** or **an explicitly selected qualified non-desktop runner satisfying the required platform**. Do not claim the exact killer was proved or recommend Linux server2 for Windows work. Assert against literal expected clauses/code, not a reason generated by the helper under test.

Automatic refusal persists `Blocked` with `routing exhausted: ` followed by that same code and explanatory reason; the prefix keeps the existing manual reroute recovery usable. It must not use the old remote-only "Grok, Claude Code or Codex only" explanation for a desktop Codex refusal. A previously valid current kind stays unchanged when a candidate is refused; no host/platform/pin rewrite, alternate-kind walk, or automatic migration is allowed. A queued legacy Codex row retains Codex while becoming Blocked. No flag or default-setting change bypasses this mitigation.
