# CARD-0566 — refuse an unsafe `rm` approval in a delegate

Baseline: task checkout `2f050e3d2b1cc36a3440d5914089aaded7c68a12` (descendant of local `master` `25564530cd51ff9b02e5b8c9a5ac4793225d2541`). CARD-0566 has no history. This is a plan; no production code or tests were changed here.

## Verified findings

1. The card's `run() { ... rm -rf $R/$name ... }` is **agent-authored shell input**, not a tracked helper. An exact repository search found no `rm -rf $R/$name`. The stage bundles already direct Code to the checkpoint tool (`server/Bundles/stage-code.md:5`) and Review to rerun its named checks (`server/Bundles/stage-review.md:3`); `docs/testing-and-build.md:144-210` defines isolated output and a closed checkpoint manifest. The historical reason to write the scratch-deleting helper has largely gone, but arbitrary commands can still be typed. Neither PowerShell `-Confirm:$false` nor an imagined `rm --yes` is a fix for a Bash `rm -rf` variable expansion. Quote and validate both components before deletion, or use the checkpoint tool.
2. The reported string is a **numeric approval UI** (`Dangerous rm operation on possibly-empty variable path: ... Do you want to proceed? 1. Yes 2. No`). Antiphon launches provider TUIs with permission-bypass flags (`docs/agent-kinds.md:169-178`), but those flags do not prove every provider/tool-specific confirmation is suppressed. The observed approval was in the live session buffer according to the card; the exact provider/version and a current captured screen are not available in this checkout. Do not claim the shell itself emitted that text.
3. `WatchdogService.ScanAsync` already examines live rendered screens and sends configured responses (`server/Application/Services/WatchdogService.cs:43-102`); `AgentSessionRuntime.ListLiveSessions` includes cached live phone-home sessions (`server/Application/Services/AgentSessionRuntime.cs:1284-1296`). Current defaults answer `Press Enter`, `(Y/n)` with **yes**, and `[y/N]` with no (`server/Application/Settings/WatchdogSettings.cs:3-22`). `WatchdogMatcher` has no rule for the numbered `1. Yes 2. No` approval (`server/Application/Services/WatchdogMatcher.cs:6-38`). `WatchdogCooldownStore` suppresses repeats until a prompt clears (`server/Application/Services/WatchdogCooldownStore.cs:9-53`). Thus the reported prompt receives no automatic answer on the default path.
4. The card's **"forever" claim is stale for the task**. `TaskDeadlinePolicy` applies a 90-minute local-tool deadline and a 240-minute role ceiling (`server/Application/Services/TaskDeadlinePolicy.cs:16-22, 119-210`; `server/Application/Settings/DelegationSettings.cs:473, 1022-1030`). `AgentTaskDispatcher.TryFailOverdueAsync` pulls the transcript, then fails and notifies without killing the session (`server/Application/Services/AgentTaskDispatcher.cs:2630-2740`). This still costs up to 90 minutes and leaves a live approval waiting. The 30-minute progress-stall policy only recognizes enough *repeated* transcript rows (`server/Application/Services/TaskProgressPolicy.cs:65-105`; `server/Application/Settings/DelegationSettings.cs:1093-1121`), so a quiet prompt is outside that detector. CARD-0551's zero-ingested-row guard is also already present at `AgentTaskDispatcher.cs:2674-2694`; it prevents the old false-success recovery for a bound transcript, but does not answer the prompt.

## Smallest fix

### S1 — fail closed on the one observed approval

Add a narrowly named unsafe-delete recognizer to the existing watchdog path. Match only an **active rendered prompt**, requiring both the distinctive `Dangerous rm operation on possibly-empty variable path:` heading and the numbered `Do you want to proceed? 1. Yes 2. No` choice in the bottom visible prompt region. Allow line wrapping and ANSI stripping; reject text found only in raw scrollback, ordinary prose, different choice ordering, or a partially rendered menu. Give this recognizer priority over the generic configurable `(Y/n)` yes rule. For this one confirmed shape send the menu's **No** selection (`2` plus the input required by a headed canary), once per visible episode through the existing cooldown store. Do not send `1`, `y`, `--yes`, or generic Enter. Emit `WatchdogAutoResponded` with a distinct safe-refusal rule name, as the existing watchdog does. If the exact key sequence cannot be demonstrated from a headed TUI fixture, leave the recognizer detection-only and let the existing task deadline fail; do not guess a keystroke.

Add one short instruction to `docs/testing-and-build.md` beside the checkpoint guidance, and to `server/Bundles/stage-review.md`: use the checkpoint tool for repeated class runs; any ad hoc destructive shell cleanup must check both variables, quote expansions, and confine the resolved target to the intended scratch root. A missing component must produce a nonzero exit before `rm`. This reduces recurrence without attempting to intercept arbitrary tool calls. No new settings, incident enum, attention kind, or provider launch flag are needed for this observed prompt. A broad approval-popup detector would require fresh provider screen evidence and is a separate card if this narrow refusal does not cover later occurrences.

### Evidence gate for S1

TestDesign should first capture or construct the observed rendered menu in the existing `WatchdogServiceTests` fixture. The card's prose alone does not prove whether the menu accepts `2`, `2\r`, or arrow/Enter. If a headed canary shows that `2\r` does not select No, record the observed key sequence and adjust the test and implementation together. If the menu is not reproducible, ship only the instruction and a detection/attention proposal, not an unverified automatic answer. The current 90-minute deadline remains a hard failure backstop in either case.

## Verification design

V-1 exact, wrapped and ANSI-colored live rendered menus select No once; assert the input bytes and `WatchdogAutoResponded` rule name. V-2 near matches, historic/raw-only text, a changed choice order and an idle composer send no refusal bytes. V-3 an unchanged menu is not answered twice after cooldown; clearing it and showing a new menu permits one new refusal. R-1 existing Press Enter, `(Y/n)` and `[y/N]` behavior still passes. R-2 a fake clock past the 90-minute local-tool limit still fails the task if prompt recognition has no safe match; this is already covered by `TaskDeadlinePolicyTests` and does not require a new deadline.

TestDesign adds **four** focused tests to `WatchdogServiceTests` for V-1 through V-3; that class has six `[Test]` methods at baseline. Existing `TaskDeadlinePolicyTests` supplies R-2. Keep the tests in the existing classes so the checkpoint filters are exact and the one-project isolated build is sufficient. A recognizer test must fail when its production match/response is removed; a pure fixture self-comparison is a stub.

## Risks and limits

- A safety prompt is not authorization to delete. Auto-refusal is the only safe automatic response. A generic yes rule matching a future variant must not precede this recognizer.
- Rendered screens may contain stale text; the match must be limited to the active prompt region and use the cooldown's clear/rearm behavior. An empty/unavailable rendered screen with only raw buffer evidence is not enough to type.
- The provider-specific menu may change its wording or input semantics. The headed evidence gate protects against a false key sequence; unmatched forms still reach the existing deadline, and can motivate a later attention detector.
- Failing a task at its existing deadline does not stop or release the underlying process. Do not change that session ownership contract in this card.
