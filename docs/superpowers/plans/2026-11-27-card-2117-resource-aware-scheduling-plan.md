# CARD-2117 — Resource-aware scheduling

Schedule delegated sessions and managed build, test and Git work against scoped slot counts and measured CPU, memory and storage capacity. Preserve the existing project, role, host and seat ceilings. Ship telemetry and a week of shadow decisions before admitting work on resource requests. Allow an operator to hold a single runner and stage and let an authorized release workflow reserve build slots on the host of its qualification run.

Source baseline is `263a2880dde33eac23b542b133baba0c87008ac7`. The card is platform Any. Live GETs returned 200 for runner defaults (revision 2), the runner catalogue and host stats. The catalogue had eligible Linux and Windows lanes and an unavailable entry. Both active runners advertised `hostStatsV1` and `hostLoadHistoryV1`. The active Linux history read returned zero items and the shared broker still returned 405 for both `/metrics` and `/host-load`. Treat these as deployment and coverage gaps. Resolve lanes from the live endpoints when dispatching. [Runner placement](../../orchestration-loop.md#runner-placement) · [Host load telemetry](../../ops-http.md#host-load-telemetry-card-1514-s1)

## Decisions

### D-1 — Account once per physical host and once per managed unit

Use the authority identity and physical-host binding from CARD-1514, with a bound runner identity and a monotonic authority generation. Expand the existing host-local `BuildSlotBroker` into the single writer for counts and, in later slices, resource grants for that host. Keep one grant transaction/lock across applicable dimensions and all runner aliases. The server owns policies and task lifecycle, and projects a bounded broker snapshot. A server-only ledger would miss concurrent script and CLI builds. Per-runner resource ledgers would give two co-located runners duplicate CPUs, memory and disk headroom.

Charge the resident session CLI, its supervised helpers and unmanaged descendants to the delegate's base request. A managed build, test/fixture, workspace-Git or other managed phase owns its execution subtree and its grant. Attribute it to the parent task for display, exclude it from base usage and charge its reservation once. Claim before the phase starts. For an independently supervised shared compiler, shared database fixture or Docker daemon that cannot be charged exclusively, keep a measured shared allowance and unassigned usage. Charge dedicated test fixtures to the owning run/lease and capture separately owned container counters where available. A PID with an ambiguous root, including a child that escaped before capture, contributes to unknown attribution and cannot train a lower request. Summed task display may include children, with concurrent peaks computed on aligned samples. Persistent warm and standing sessions consume a measured resident baseline or retain a known grant until transfer/exit is proved. Reuse transfers that charge without opening a second spectator grant.

### D-2 — Use measured capacity, explicit headroom and bounded request defaults

Store CPU in integer millicores (1 logical CPU = 1,000m) and memory in integer MiB (1,048,576 bytes). Use a fresh, trusted host sample of logical CPU and total memory, constrained by attested runner/child affinity and effective cgroup or Windows limits where applicable. For aliases or shared quotas apply both the host envelope and any identified narrower quota envelope. Limit a report by operator-verified inventory, reject invalid values and stale or mismatched bindings, and require verification for capacity increases after a boot, binding or quota change. Use three sampling periods (15s at the present default) as a provisional freshness bound. History calibrates headroom and cohorts. Instantaneous CPU and total memory use different denominators from capacity.

Per dimension, allocatable is the validated capacity minus fixed system, shared-service and workstation headroom, then multiplied by that dimension's overcommit factor. Free is allocatable minus committed requests, including relevant active reservation claims. Evaluate the live memory floor and storage pressure separately to catch unaccounted load. Avoid subtracting the same consumption via live availability and via grants. Default factors are 1.0 for CPU and memory. An operator may raise CPU overcommit after observing the effect. Keep memory and storage at 1.0 for rollout. Calibrate headroom per host against baseline and service tails, including concurrent desktop use and production database demand. No automatic activation from historical totals alone.

Request precedence is operator-approved exact override, qualified recent history for the closest compatible cohort, the next broader compatible cohort, then versioned conservative bootstrap profiles. Key cohorts by activity, platform, verified resource/driver class and relevant shape: delegate kind/role/model level, build entry project/closure and cache/worker class, test project and manifest group, or Git/metadata phase. Keep a fallback at the activity/platform level and refuse explicit selection of an unknown profile. Proposed Observe-only seed examples are 1,000m/2,048 MiB for the base CLI, 6,000m/8,192 MiB for an unknown heavy build, 2,000m/4,096 MiB for a test row including its dedicated fixtures, and 1,000m/1,024 MiB plus a metadata permit for managed heavy Git. Derive activation values through bounded controlled samples and approve them per lane. For an unseen cohort on an enforcing host, inherit the validated broader profile. If none is available, require a profile or run the bounded calibration on an Observe lane. A verified oversized request returns typed `resource_request_exceeds_capacity` with the request, allocatable bound and limiting dimension. A transient floor, hold or unsupported measurement gets its own reason. Explicit sized work that fits the validated worker envelope may wait for free capacity. Do not retry until a permanently oversized request or policy changes.

### D-3 — Budget storage by physical device and phase

Instrument the existing CARD-2103 monotonic boundaries for graph evaluation/source scan, restore (cache hit/miss where known), compile/output staging, fixtures, test host, Git clone/fetch/worktree add or reset, npm install/build, output discovery/custody walk/deletion and receipt publication. Tag cache state, changed file/byte counts where already known, logical volume/device, and which phases ran outside today's build gate. Reuse native incremental output and verified checkpoint caches where eligible. Count repeated SHA/fingerprint/project/toolchain/property combinations as reuse candidates and measure actual hits and I/O avoided. Keep producer identity, filesystem custody and independent Review requirements. Avoid assuming duplicate graph work is entirely redundant.

In the host sample add Linux blocked tasks and per-device read/write operation and byte deltas, queue depth/weighted I/O time and latency, with mount-to-device mapping through the LV/parent stack and no summing an LV and its backing device. PSI is optional. On Windows use available disk performance counters matched to volume/device and keep unsupported Linux-only signals absent. Where existing supervision allows, sample per-cgroup I/O where available or process counters labelled logical versus device I/O. Capture only known lineage and report device-level flush/await, PostgreSQL write/fsync/checkpoint latency when measured, and server health/DB tail separately. Shared journal work will often remain host-attributed. Capture free bytes and inodes alongside pressure, with separate ENOSPC reasons. Avoid privileged changes, production load tests and per-file probes in S1.

The first enforceable I/O request is an integer permit per contention domain and heavy metadata phase, held for actual work, with one permit as the initial canary maximum for a device that shares database and runner traffic. Cleanup, clone/worktree materialization, npm install and cold restore/output staging are default candidates. In a composite lease reserve a conservative permit through inseparable heavy subphases, then return it at a safe boundary. On confirmed high database/device pressure, or headroom loss, issue zero new heavy permits for that device. An operator-approved DB/device SLO and calibrated high/low thresholds, with three bad samples to close and six healthy samples to reopen as provisional hysteresis, reserve headroom for PostgreSQL. Missing device binding or stale counters hold new heavy work on an enforcing shared device. Keep running work under its current grant. Arrange independently granted cleanup before destructive work and outside build/delegate admission locks. Where an existing safety unwind cannot wait, finish the bounded owned unwind, report its demand as reserved system work and retain custody/receipt semantics.

Permits and the database guard are the initial I/O admission limit. A measured IOPS or byte/s request can become useful when attribution and hardware limits are stable. Evaluate runner `io.weight` or `ionice` only after readback proves that scheduler, cgroup, filesystem and journal paths honor the setting. Weights are relative and can miss shared-journal writes. Treat a separate device for production PostgreSQL as the durable isolation option if the matched canary still misses its SLO. A separate LV on the same device gives no such guarantee. Storage moves, limits applied to live processes, rollback and activation belong to a separately authorized infrastructure change.

### D-4 — Store policy by runner and scope and keep native rc custody

Define typed scopes `delegate:<AgentTaskRole>`, `build`, `test`, and `git` for managed Git phase admissions. Keep I/O permits per physical contention domain. A missing override inherits the existing ceiling, with no new stage limit where none exists. Positives only narrow existing limits. A zero override is an expiring hold with authenticated owner, reason, timestamps and revision. It affects only new claims of that scope on the selected runner. Expiry or clear recomputes the underlying limit, even after a restart. No wildcards or automatic redirect. A compound standalone row declares its real scopes under a single lease, with atomic scope conversion or one composite grant, so a test hold also reaches a covered row.

Persist operator caps, hold rows and audit in PostgreSQL with additive CLI-generated EF migrations. Use revision-checked writes and server time, and reflect pending versus effective policy revisions when the broker has yet to acknowledge. Persist last applied policy and active reservation/grant ownership under broker state outside worktrees. Use bounded authenticated distribution with resync on connect. Stale or missing rights on an enforcing scope refuse new grants. Existing grants drain using custody, and removals/expiry need neither a process restart nor an orchestrator wake-up. Do not report a hold as applied until the authority has acknowledged it. Operator-only writes set ceilings, headroom, request overrides, overcommit and enforcement. An authenticated standing orchestrator may place or clear its own finite narrowing hold on an explicitly delegated runner/scope, for up to four hours initially, with reason. Other callers are read-only for these controls. The operator can clear any hold. Ordinary task tokens and caller-supplied owner strings grant no write authority.

Bind rc reservations to an authenticated launch record, exact run/attempt, verified holder generation, runner and physical broker. Default quantity is two in the opt-in launch policy, subject to operator bounds and current broker capacity. Acquire N atomically after existing preflights and before starting native work. An unavailable quantity queues under the finite reservation admission budget or fails fast if larger than the maximum. The launcher replaces its legacy outer lease with the reservation. The rc reservation owns N count slots total and may lend them only to the matching run. Native phases consume reservations or convert within them with no second count. Normal claims consume at most configured physical slots minus active reservation slots and their own runner limits. Explicit stage holds still bar new work in that stage, including a new reservation on that runner. Existing native runs continue. An authorized release workflow may acquire, renew and release only its own reservation. Final release happens on verified exit after child drains. An expiring unowned or unused reservation is reclaimed at expiry. A live native run at an expiry or renewal failure retains a custody fence for its active work, refuses new run claims under the expired reservation, and surfaces an incident until reconciliation safely releases it. No scheduler path takes, clears or transfers a live native lock.

### D-5 — Apply eligibility first, then fit work with bounded bypass

Retain the create, role/parallel, platform, budget, provider and custody gates. Stage slot and request admission are additional checks for the already resolved binding. The existing absolute-cap override continues under its existing conditions and cannot override resources or holds. Preserve settlement, released answers and provider-recovery ordering where existing policy grants them precedence. Terminal work and receipt publication do not wait for a new delegate seat. For normal eligible queued work, use ascending persisted card rank, importance for ties or unranked work, then queue age and stable ID. Resolve rank in a bounded batch. Use eligible-since for aging, retaining it across polls and restarting it when the placement or request changes. After an initial 30 minutes of continuously eligible wait, promote that request to an old-first tier. While unaged, choose the best-fitting request within the same priority band. When an aged feasible head cannot fit, stop admitting younger requests on its constraining dimensions until current grants drain or its eligibility changes. Unrelated scopes/devices can proceed. No guaranteed start during a hold, outage or capacity occupied by indefinitely running work. Recheck on grants released, revised policy, pressure recovery and the existing periodic tick. Give visible reasons and oldest eligible age. Preserve the governing execution deadline/cancellation and avoid touching a running session to make room.

Before activating delegate request admission, protect a worker allocation in CPU/memory plus applicable I/O capacity sized for at least one approved child grant including a bounded cleanup path. Delegate base claims cannot borrow that floor. Large approved children may use free common capacity subject to their verified runnable envelope and aged-head draining. Reserve each unit's applicable dimensions together. Obtain workspace preparation's Git/I/O grant at the preparer boundary and release it before launch, with no long Git lock or database transaction held while waiting. A task waiting on a child may keep its base grant. Child progress does not depend on another parent releasing its base, provided that child fits the guaranteed worker envelope. Reject nested driver leases and circular acquisition paths. Each rc and ordinary worker partition must independently leave a feasible completion path before enabling the combined policy.

An admission wait is a queued task or bounded driver wait, with no newly launched waiting session. An existing session that waits for input keeps its seat and base charge. An accepted answer resumes the turn. Confirmed exit or an existing conditional release/parking operation can free the seat and charge. While parking is disabled there is no automatic release deadline. Admission aging, lease timers and hold expiry give no authority to stop the session. [Session runtime invariants](../../session-runtime-invariants.md)

### D-6 — Use one admission evaluator for live and shadow decisions

S1 runs the proposed evaluator in shadow mode under the currently trusted bindings. Log observed decision and constraints alongside simulated request/version, would-grant/would-queue/oversize/unknown reason and age. Emit once per admission transition or changed reason and aggregate unchanged polls. Test a separate per-authority shadow ledger that consumes real arrivals and terminal boundaries with cohort duration estimates for work that would have moved. Keep one same-snapshot decision for comparability and label any replay with estimated service as counterfactual. No launch, queue-order, grant-cap, exit-code or build-argument change in S1. Cohort the comparison by workload mix, OS, native rc/foreground load, cache mix and device. Surface coverage for unattributed time, refused runs, missing leases and unknown requests. Correlation fields come from CARD-2103 and the existing host/lease identities. Do not make another telemetry transport.

For task/lease/row summaries retain user+system CPU seconds, peak simultaneous tree working set in MiB, elapsed monotonic wall, sampled CPU rate and storage counters with attribution quality, outcome and coverage. CPU sizing uses the per-unit peak sustained 5-second core rate (CPU seconds over the sample interval), never raw total CPU seconds. Keep mean/p95/p99 of CPU seconds, sustained core rate, peak working set and wall by cohort with sample counts and window. Working set can double-count shared pages across PIDs, so retain native cgroup peak or private/shared provenance and treat summed RSS as an upper estimate. Short-lived children, wraps, unavailable job accounting and process reuse require explicit coverage. Start from runner supervision and existing Linux cgroup/Windows Job Object custody when defined. Otherwise use bounded PID/start/generation-matched deltas, record missed exits and omit unqualified measurements from sizing. Publish only bounded per-unit aggregates and drop counters through existing CARD-2103 summaries, never per-process data in the scheduling database.

### D-7 — Freeze grants and tune cautiously

Feed S5 from a rolling 30-day qualified cohort. With at least 30 qualified completions, recommend the rounded p95 sustained CPU and p95 memory peak times 1.25, subject to operator floors and verified envelopes. Report p99 as provisional below 100 observations and show sample counts. Classify throttled, OOM, pressure-deflected and interrupted runs separately. Use trustworthy exceed/OOM evidence as an upward signal and keep those censored samples out of downward fitting. Flag a sustained CPU or qualified memory peak over 125% of request and associate confirmed or suspected OOM with typed exit/cgroup evidence. Never infer OOM solely from a generic failure code. On an operator-enabled cohort, apply bounded weekly adjustments to future requests, with at most 10% downward movement per week and an override/freeze. Keep request and policy revision on each active grant. A proposed increase above the worker envelope requires explicit resolution and no silently capped grant. A request is admission pricing. Optional limits remain validated metadata until native enforcement can prove custody and overhead. Initial enforcement covers admission, storage permits, and MSBuild grant propagation, with exceed feedback and no automatic kill.

### D-8 — Expose one operator view and use reconciled ownership

Extend runner catalogue and pipeline with additive policy and capacity summaries. Use stable reason codes and dimensions with a rendered queue message, for example “waiting for 6 cores / 8 GiB on server2” with needed and free amounts. Separate budget/hold, drain, provider wait, memory-floor, unknown capacity, I/O/DB protection, oversize and ordinary request fit. In generated orchestrator text render effective scope ceilings, active/pending holds (owner, reason, expiry) and reservations or their policy revision, without live per-poll occupancy churn. Delete stale prose build holds only when the typed controls are published. Keep legacy host budget and provider-hold meanings. Make `scripts/antiphon capacity [--runner <id>] [--json]` the read front door and use the same projection in the existing Hosts page and orchestrator pipeline. Show mode, sample age/coverage, allocatable/free/granted by dimension, stage occupancy, reservations, queue age and next retry or expiry if known. Use bounded paging/details for lease inventory. Mutating subcommands use revision and the existing operator/caller authorization. Read the originating authority for brokers shared by several runner IDs and show that identity next to each scoped row.

Issue grants with immutable IDs bound to authority generation, invocation or task attempt and a verified holder. Duplicate request or lost acknowledgement returns the same grant. Launch consumes a pending grant only after recording its identity at the existing claim/preparer seam. Reconcile failed DB claim, ambiguous launch, PID reuse, retry, drain rebind or crash by confirming terminal custody or explicitly fencing the old generation. A proved pre-launch abandonment releases immediately, and ambiguous/live ownership stays charged. After restart rebuild from durable ownership and inventory before enabling new admissions. An outage in Enforce never falls back unleased on a managed lane. Hold existing work and expose `capacity_unavailable` with finite driver admission timeouts. Observe preserves and counts legacy fallback. A stale queue emits a deduplicated attention row initially after 30 minutes, with limiting resource, first eligible time and holder blockers when known. Wake when the underlying condition changes and clear on admission, cancellation or reason change. Downgrade modes by binding, drain incompatible authorities and keep reconciling existing grants. Avoid any best-effort all-fleet cutover.
