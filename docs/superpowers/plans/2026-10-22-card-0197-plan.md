# CARD-0197 plan: card auto-progression from agent-emitted keyword signals

Date: 2026-10-22. Task a2c38e52 (Plan, High). Base `c5f35c862`. Master only; no rc applicability
because nothing is built.

**Recommendation: close CARD-0197 as superseded. Build nothing.** The keyword channel the card
proposes already exists as the CARD-0146 `--- next stage ---` block, with a closed vocabulary that
fails safe. Card column moves for task-bound work are already automatic (CARD-0040). Stage presets
shipped in CARD-0196. The only remaining gap is a server-triggered dispatch of the next stage
without a caller. Standing policy deliberately leaves that out: dispatch belongs to the
orchestrator, every spend must be explicitly accepted, and tracker writes need YAML activation.
CARD-1281 D-3 already owns that question as a gated "later opt-in handoff service" with
measurable rollout criteria (R1), and CARD-1303 R10 shipped its caller-side pilot routes. Building
it again under this card would create a second signalling channel and a second dispatch
authority.

## Decisions (stated defaults; the operator may override any of them)

- **D-1: Do not build a server-side automatic next-stage dispatcher under CARD-0197.**
  - *Why:* any automatic dispatch is a scheduled spend. Standing rules make dispatch the
    orchestrator's job and require explicit, YAML-activated tracker writes and `acceptSpend`.
    CARD-1281 D-3 already holds the question behind a measured caller pilot: R1 asks for 95% of
    eligible handoffs requested within 5 minutes, unexplained waits over 15 minutes investigated,
    and a rollback on misclassification or duplicate dispatch. It also fixes what any later
    service must be: opt-in, deduplicated on predecessor/attempt/settlement/stage/workflow
    revision, created through ordinary task creation with no overrides, and keeping tracker
    activation and spend acceptance.
  - *Rejected:* (a) build it here as a background service consuming `NextStage`. That
    duplicates CARD-1281's owner, bypasses its pilot evidence and creates a second dispatch
    authority. (b) Build an opt-in flag now with no consumer. That is dead configuration and
    implies a capability that does not exist.
- **D-2: Do not add a keyword vocabulary (`OK_BUILD`, `NEEDS_ANSWER`, ...).**
  - *Why:* the next-stage block plus the report token already carry every verdict the card
    lists, with a closed alias table and fail-safe unknown handling. A second ALL-CAPS channel
    would need precedence rules whenever the two disagree.
  - *Rejected:* adding the keywords as aliases of `PipelineHandoff.Aliases`. They give no new
    meaning, and `NEEDS_ANSWER` would blur the `blocked` versus `decide` distinction that §1
    depends on.
- **D-3: Do not add per-stage board columns or a stage-driven column move.**
  - *Why:* stages are `AgentTaskRole` values (CARD-0146). The CARD-0040 sweep already covers
    In Progress and Review. Done is gated by CARD-1281 D-4.
  - *Rejected:* "NeedsDecision on `next: decide`". The decision is the orchestrator's triage
    under §1 (Mutation `decide` gets explicit triage first, not an automatic human question),
    and a decision belongs on the move or reopen revision that the caller writes.
- **D-4: Close CARD-0197 as superseded, with this plan as the reason.** No new card is filed.
  The residual automatic-continuation question stays with CARD-1281 R1/D-3. If the operator
  wants it tracked separately, file it then as "CARD-1281 R1 opt-in handoff service, after
  pilot criteria", not here.
