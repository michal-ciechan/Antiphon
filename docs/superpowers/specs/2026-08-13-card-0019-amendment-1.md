# CARD-0019 amendment 1 — what landed since 2026-08-11, and what it changes

**Date:** 2026-08-13. **Amends:** `2026-08-11-card-0019-card-correction.md` (which stays as
written — this doc records deltas, it does not rewrite history). **Status of the original:**
still planned, not implemented; everything below was checked against master at `71e7ce8`.

Two commits landed that the original plan predates, and the set of work waiting on this card
has grown from two record corrections to at least five distinct dependents. The verdict up
front: **the three slices still hold as a structure, but slice 1 grows two pieces of scope
(move revisions, reopen), slice 3 grows one (CARD-0040), and slice 1 is now on feature 011's
critical path and should land first and alone.** One caller condition (the 20k cap) has been
partly overtaken by CARD-0037 and is re-stated below.

## 1. `cdabe32` — a move now carries a `Reason`, and moves become a second revision writer

`MoveCardRequest` gained an optional `Reason` (`BoardDtos.cs:92-106`). Verified current
behavior (`CardService.ApplyColumnMove`, `:224-268`): on a move into a terminal column the
reason becomes `Card.TerminalReason` (a supplied reason overwrites an existing one); **on any
non-terminal move it is accepted and dropped** — the DTO comment and the commit message both
say so explicitly, and both name CARD-0019's `CardRevision` as the intended home. The API shape
shipped deliberately ahead of the storage.

The original plan designed `CardRevision` for one writer: content edits, storing the
*superseded* title/description/priority/labels ("revision n + current card = complete history
with no duplication"). A move breaks that model twice: it changes no content (snapshotting
content per move duplicates data and violates the no-duplication invariant), and what it
actually needs to record — from/to state, when, why — has no fields in the planned entity.

**Amendment: `CardRevision` gains a `Kind` discriminator** — `Content`, `Move`, `Archive`,
`Unarchive`, `Reopen` — with per-kind fields:

- `Content`: the planned superseded snapshot (title/description/priority/labels), all four now
  nullable at the schema level, populated only for this kind. Semantics unchanged.
- `Move`: `FromStatus`, `ToStatus`, `FromColumnId`, `ToColumnId` (nullable columns, populated
  for Move/Reopen), no content fields. Written by `MoveAsync` on **every** column move.
  `TerminalReason` on the card stays as the current-surface denormalization; the revision row
  is the history. The "accepted and dropped" caveat in the DTO comment gets deleted when this
  ships.
- `Reason` stays **required for `Content`** (a correction must say why) but is **nullable for
  `Move`** — cdabe32 shipped it optional on the wire, a routine drag is not a correction, and
  making it mandatory now would break the only move surface (drag-and-drop sends none). The
  divergence is deliberate and should be stated in the API docs.

Why one table with a discriminator rather than a sibling `CardTransition` table: the card's
history view needs one totally-ordered timeline per card anyway (`RevisionNumber` gives it
without timestamp comparisons — house precedent says never lean on timestamp order); a reopen
is *simultaneously* a transition and a correction, which in a two-table design is two rows
needing coupling; and it is one migration and one writer discipline instead of two. Feature
011's board-wide aggregation (join Cards on BoardId, filter `Kind = Move`) is served by adding
`Kind` to the planned `(CardId, RevisionNumber)` unique index's table — an index on
`(CardId, Kind)` is cheap if measurement wants it; leave that to 011.

## 2. `b48f928` — the widened state machine, and the reopen gap it hands this card

`CardStateMachine` now lets **any live state move directly to any other**; `Done` and
`Canceled` have **no transitions out**, and both the commit message and the code comment
explicitly defer reopening to "CARD-0019's history, where undoing a close is recorded as a
correction rather than a quiet row rewrite" (`CardStateMachine.cs:38-44`).

The original plan has **no reopen mechanism**. Its `POST /unarchive` is the `ArchivedAt` axis —
a card can be archived in any status — not the status axis. So b48f928 assigned this card a
responsibility the plan doesn't contain. 

**Amendment: slice 1 adds `POST /api/cards/{id}/reopen`.** Contract: `ConcurrencyToken` +
**required** `Reason` (reopening is always a correction) + target live column (default: the
board's Backlog column). It writes a `Reopen` revision first, capturing the superseded terminal
facts — from-status, `TerminalReason`, `CompletedAt` — then moves the card via the existing
`ApplyColumnMove(enforceStateMachine: false)` seam (the seam already exists at
`CardService.cs:230-231`; `ApplyColumnMove` already clears `CompletedAt`/`TerminalReason` on a
non-terminal landing, which is exactly why the revision must be written before the mutation —
same snapshot-then-mutate rule as content edits). Token rotates, `CardChanged` publishes.
Side-effect warning to document: moving into an `IsActive` column spawns an agent (the CARD-0040
constraint), and that applies to reopen like any move — defaulting to Backlog is what makes
reopen safe-by-default.

Two things b48f928 does **not** change in the plan: content editing in terminal columns stays
allowed (terminal immutability is about *status*, not text — correcting the record of done work
is the CARD-0026 case and remains in scope), and archive/unarchive semantics are untouched
(orthogonal axis).

## 3. The dependents: two became five

The original justified itself on two wrong records (CARD-0018, CARD-0026). Now waiting on this
card:

1. **CARD-0026's wrong note** — slice 3, as planned (including the caller's addition: record
   *what was actually wrong*, checkout-path dependence fixed by `f078dd2`, not merely retract).
2. **CARD-0040's refinements** — the card text needs corrections/refinements recorded via the
   edit endpoint once it exists. **Added to slice 3.**
3. **Non-terminal move reasons** — currently dropped (cdabe32); persisted by slice 1's `Move`
   revisions (§1).
4. **Feature 011's edge weights and time-in-state** — 011's proposal states "no transition
   history exists" and bounds its graph accordingly. `Move` revisions with timestamps are that
   history: edge weights = counts over `Move` rows, time-in-state = deltas between consecutive
   ones. **This history is non-retroactive** — rows exist only from the day slice 1 ships, and
   nothing can backfill beyond the coarse `StartedAt`/`CompletedAt` approximations. Every week
   slice 1 waits is a week of history 011 never gets. This is the strongest sequencing pressure
   on the whole card.
5. **Reopening a wrongly-closed card** — the new reopen endpoint (§2). Until slice 1 ships, a
   wrongly-closed card has no legal path out of Done at all (b48f928 closed the workaround of
   moving it through the state machine).

## 4. Do the slices still hold?

**Yes as a structure, resequenced in emphasis:**

- **Slice 1 (server) — grows and goes first, alone.** Adds: `Kind` on `CardRevision` (§1),
  `Move` revision writing in `MoveAsync`, the reopen endpoint (§2). Everything else as planned
  (content PATCH, archive/unarchive, the 4000-char two-part fix, single migration). It is now
  the bottleneck for dependents 3–5 and accumulates 011's history from ship date; land it
  before slice 2 and independent of it.
- **Slice 2 (client) — as planned, plus history rendering of move/reopen rows.** Do **not** add
  a move-with-reason UI here: feature 011's plan already specs the move menu with reason on the
  graph surface; duplicating it in `CardModal` under this card would collide.
- **Slice 3 (correct the record) — as planned, plus CARD-0040.** API-only; can run any time
  after slice 1, before slice 2 if convenient.

Test additions to the original list: move writes a `Move` revision with from/to and the
optional reason (terminal and non-terminal); revision numbering interleaves content and move
rows in one sequence; reopen writes the `Reopen` revision with the superseded terminal facts,
clears them, 409s on token mismatch, 400s on missing reason or terminal target column; reopen
into an active column spawns (or explicitly pin whatever is decided about that side effect).

## 5. The 20k-cap caller condition, re-read after CARD-0037

The 2026-08-11 caller decision accepted the 20,000-char cap **conditional on** spill-to-pointer
for the spawn prompt, because `BuildPrompt` output is typed into the PTY and (per CARD-0027)
typed input clips at ~1 KB. Since then **CARD-0037 landed**: the modern ConPTY backend is
shipped and this deployment runs it (`SessionRunner:PtyBackend = modern`; AppHost sets
`ANTIPHON_PTY_BACKEND=modern`); a bracketed paste on modern carries **86,400 bytes in one write
with zero loss**, ceilings are resolved per-backend by `PtyDeliveryProfile` (inbox: 900 B
brief; modern: 43,200 B), and the spill-and-pointer path is retained as the inbox fallback.

So the condition's substance — "don't ship 20k over a path that loses data at 1k" — no longer
requires *building* spill for the spawn prompt; it requires **verifying the spawn prompt path
is governed by the same ceiling machinery briefs use**. `CardService.SpawnAsync` builds the
prompt and enqueues it (`CardService.cs:179-194` → launch queue → `SendPromptAsync`); the
delegation brief path already resolves `PtyDeliveryProfile` and spills over the ceiling
(`AgentTaskDispatcher.cs:529`). Amendment to the condition:

> The 20,000 cap ships with slice 1 **if** the spawn-prompt delivery is confirmed (or made) to
> route through the backend-resolved ceiling with the spill fallback, deciding in **UTF-8
> bytes** at the delivery edge (20k chars can be up to 80 KB; the cap stays a char policy, the
> edge decides in bytes — the profile machinery is already byte-based). On modern that means a
> typical 20k description travels whole; on an inbox-fallback machine it spills to a pointer
> exactly as briefs do. If that verification fails and the routing is out of reach, the
> original fallback stands: cap stays 4,000 and the spawn path gets its own card.

This is a strictly smaller ask than the original condition and removes the main reason the cap
might have been deferred.

## 6. Stale statements in the original (recorded, not edited)

- §"Delete is archive" and §3's "no global query filter" both justify themselves via the
  **count-based** `NextIdentifierAsync`. The CARD-0005 plan
  (`2026-08-13-card-0005-identifier-allocation.md`, written today, sequenced to land before
  this card) replaces count+1 with parse-max+1. The archive decision is unaffected (its real
  ground is that the record is never destroyed), and the **no-global-filter rule survives** —
  the allocator must see archived rows so max+1 stays monotonic — but "archived rows keep the
  count monotonic" stops being the reason. The planned identifier-guard test (create A, archive
  A, create B ⇒ B ≠ A) stays, and CARD-0005's plan defers the "archived rows still count"
  test here because `ArchivedAt` arrives with this card's migration.
- Line references have drifted a few lines (`MoveAsync`'s token check, the `HasMaxLength(4000)`
  config); mechanisms all re-verified present on master as of `71e7ce8`.
