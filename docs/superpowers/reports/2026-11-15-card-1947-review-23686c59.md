## Memo

The key is the full work-tree path plus the full argument list (`$start.WorkingDirectory` and the arguments joined by NUL). `HardenGit` removes `GIT_DIR` before git runs and sets `GIT_NO_REPLACE_OBJECTS=1`, so the work tree is the repository identity. A probe with two fixture repositories returned repo A's `ls-tree` for A's id and refused the same id in repo B (`git-read-failed:ls-tree:128`). A short or symbolic `rev-parse HEAD^{tree}` was not memoized: a second commit changed the answer. An uppercase id was not served from the lowercase entry. `rev-parse <40-hex>^{tree}`, `merge-base <id> <id>`, and `show -s --format=%ct <id>` matched a fresh git answer, exit 0. The on-disk `rev-parse` pattern matches only a lowercase 40-hex id plus `^{tree}` (a short id, `HEAD^{tree}`, an uppercase id, and a trailing suffix do not match).

The stored value is the same `Result` instance. `Stdout` is a string. No caller in `scripts/` assigns `.Stdout`. Assigning that property poisons the entry; the existing cat-file memo has the same shape. Advisory only.

`merge-base` output is graft- and shallow-sensitive, as the existing `merge-base --is-ancestor` memo already is. `ls-tree`, `rev-parse ^{tree}`, and `show %ct` read the object. The memo lives in script scope for the process that dot-sourced the library. These readers do not unshallow or replace objects mid-call.
